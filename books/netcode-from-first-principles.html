Your single-player game only ever has one clock and one copy of the truth. Add a second player on a second machine, and both of those guarantees disappear. This book is about the handful of ways production games put them back together — and why fighting games, card games, and RTS games each rebuild them completely differently.

TICK 00

Preface — one question, three answers

Almost every online game, from a two-player fighting game to a forty-player battle royale, is an answer to one question.

You already know how to build distributed systems: replication, consensus, RPC, eventual consistency. Networked games are that same problem wearing a costume — the "database" is a physics simulation running at 30–60 updates a second, the "clients" have eyes and reflexes, and the "consistency model" has to feel invisible to a human holding a controller. If you've built a chat backend or reasoned about a Raft log, you already have most of the vocabulary you need. This book supplies the rest.

We'll lean on three running examples, one per architecture, because "network game" is not one problem — it's three different problems that happen to share a genre label:

CodenameGenrePlayersWhat makes it hard
VanguardRTS — base & battle2–8Thousands of units; state is too big to send over the wire every tick.
TabletopTrick-taking card game2–6Hidden information and real money mean the server must never trust a client.
Duel-71v1 fighting game260 fps combat where a 100 ms round trip is a lifetime.

Each gets its own chapter and its own architecture. By the end, the three will look less like unrelated tricks and more like three points on a single spectrum — and you'll be able to place any new game you're handed on that spectrum yourself.

Out of scope: specific engine APIs (Unity/Unreal), matchmaking algorithms, and MMO world-sharding. We stay at the level of "what goes on the wire, and who is allowed to be wrong."

TICK 01

The single-player baseline

Before anything can go wrong across a network, notice how much is quietly going right on one machine.

A single-player game is a loop. Read input, advance the world by a fixed slice of time, draw the result, repeat. That's it — every game you've ever played is some variation of this loop.

Nobody calls this a "synchronization problem" because there's nothing to synchronize — there is exactly one input source and exactly one world. Determinism (same inputs + same dt always produce the same next state) is a nice property, but nobody notices it, because there's no second copy to compare against. The moment you add a second machine, this whole loop has to answer a question it never had to ask before: whose loop is right when the two disagree?

single_player.py
import time

TICK_RATE = 60
DT = 1 / TICK_RATE

def run_single_player(world):
    accumulator = 0.0
    last = time.perf_counter()
    while world.running:
        now = time.perf_counter()
        accumulator += now - last
        last = now
        while accumulator >= DT:
            inputs = poll_local_input()
            world.update(inputs, DT)      # the only truth that exists
            accumulator -= DT
        render(world)                     # as often as the display allows

Keep this fixed-step accumulator in mind — it's the seed every networked architecture in this book grows from. The word "tick" in "TICK 04," "TICK 06," and everywhere else in this book just means one pass of that inner while accumulator >= DT loop.

TICK 02

Two computers, one reality

Add a second machine and three things you got for free disappear at once: a shared clock, a shared memory space, and mutual trust.

The network connecting them is slow relative to a 16-millisecond frame budget — even a good connection costs 20–100+ ms round trip, and speed-of-light alone puts a floor under that number once players are on different continents. It's also unreliable: packets get lost, arrive out of order, or arrive in bursts (jitter) instead of steadily. And, depending on who wrote the client, it may be actively lying to you.

The core question — every multiplayer architecture in this book is a different answer to exactly one question: which machine's simulation counts as the truth, and how do you hide the time it takes to find out? Lockstep answers "all of them, in lockstep." An authoritative server answers "the server, always." Rollback answers "yours, provisionally — you'll be told if you guessed wrong." Hold onto this; every chapter from here on is a variation on it.

Genres differ enormously in how much they can afford to get this wrong. A card game that briefly shows the wrong hand is a bug report; a fighting game that adds 150 ms of input delay is unplayable; an RTS where one client secretly sees through the fog of war (the parts of the map that client hasn't scouted, and so shouldn't be able to see) is a banned player. The next chapter turns those differences into a map.

TICK 03

Three genres, three architectures

Line up Vanguard, Tabletop, and Duel-7 on one axis, and a pattern falls out.

At one end, the server (or one designated peer) decides everything and clients are little more than a screen. At the other end, every machine simulates the entire world itself, and the network carries almost nothing but raw player input. Where a genre sits on that axis is decided by two things: how expensive the simulation is to reproduce, and how much it costs you if a player's client turns out to be lying.

A note on this axis — Lockstep and rollback sit at the identical point on this trust axis, drawn above as the same x-position at the far "every peer simulates everything" end: both are fully peer-to-peer, every machine holds the complete, ungated simulation state, and no referee is involved. The vertical spur marks that shared position and splits them on a second, separate axis instead — whether the genre's tempo can tolerate a synchronized wait before acting. Tick 06 spells out why that wait is the only real difference between them, and Tick 07 turns it into its own explicit question.

GameTempoCheating stakesArchitecture
Tabletopturn-basedhigh — hidden hands, ranked stakesAuthoritative server
Duel-760 fpslow — symmetric, both see the same arenaPrediction + rollback
Vanguard10–20 Hz simmedium — full map state sits on every peer, so a modified client could see through fog of war, but there's no hidden hand or stake to steal outrightDeterministic lockstep

Notice cheating stakes and tempo point in different directions for Vanguard: an RTS would love an authoritative server for trust reasons, but 1,500 archers' worth of state simply doesn't fit down a modem-era (or even fiber-era, at scale) connection every tick. That constraint — not trust — is what pushes RTS games toward lockstep. The next three chapters take each architecture in turn.

TICK 04

Lockstep — how RTS games sync 1,500 archers

Project: Vanguard

Don't send what happened. Send what was ordered, and let every machine work out what happened, identically, on its own.

This is the founding insight of RTS netcode. It comes from a classic 2001 postmortem, "1500 Archers on a 28.8", written by Age of Empires' Mark Terrano and Paul Bettner. Their problem was simple to state and brutal in practice: how do you keep two players' games in sync over a 28.8 kbps modem?

The obvious approach is the one Tabletop will use in the next chapter — have every machine broadcast what its own units are doing, and let everyone else update their picture of the world from those broadcasts. Do the arithmetic and you'll see why that doesn't work here. Vanguard has 1,500 archers on the map. Each one needs roughly 20 bytes to describe its position, velocity, and status. Broadcast that for every archer, ten times a second, and you're already pushing about 300 KB/s — two orders of magnitude past the ~3.6 KB/s a 28.8 kbps modem could spare for the job, and still far more than most players' shared broadband can absorb once you add in everyone else's units too.

A systems programmer's next instinct is a reasonable one: an authoritative server doesn't have to send raw state. Tick 08 covers two real techniques — delta compression and interest management — that make modern shooters affordable despite this exact same bandwidth problem. So why not use them here? Because neither one has anything to work with in an RTS. Delta compression saves bandwidth by skipping units that haven't changed since the last update — but in the middle of a battle, most of Vanguard's 1,500 archers are changing on most ticks, so there's no large idle majority to skip. Interest management saves bandwidth by not telling a client about entities far outside its view — but an RTS player can see most of their own army and base at once, so there's no "it's far away, they don't need to know" locality to exploit either. Both tricks work great for a shooter's mostly-static world seen through a narrow first-person viewport. Neither one applies to an overhead view of a battlefield where everything is doing something at once.

So Age of Empires did something different: instead of sending state, it sent commands. "Unit 42, move to (x, y)." Every machine receives the same commands, in the same order, and runs the exact same simulation to work out what happens next on its own. Nobody ever describes the world over the wire, because every machine already knows how to compute it, given the same instructions.

That last sentence is hiding a large assumption, though: that "the same simulation" really does mean the same thing on every machine. Getting there is the entire price of admission for lockstep, and it's a stricter requirement than it sounds.

Start with something you already know: floating-point addition isn't associative. (a+b)+c can round to a different bit than a+(b+c). Now imagine you're summing up the positions of 1,500 units by iterating over a hash set or a dictionary — a container whose enumeration order isn't guaranteed to be identical on every machine. Two "identical" simulations can end up disagreeing in the last bit of a floating-point number on the very first tick, from that ordering difference alone.

It gets worse before it gets better. Left to their defaults, compilers and CPUs are free to reorder, fuse, or vectorize floating-point math however they like, and they'll round differently depending on the machine, the compiler, and the optimization flags a build used. Pinning all of that down, build after build and platform after platform, is enough of a minefield that many shipped RTS engines skip floating-point simulation math entirely and use fixed-point — integer — math instead. Integer addition is exact and order-independent, up to overflow, so there's simply no rounding left for two machines to disagree about.

Two more rules close the remaining gaps. Fix one canonical order for iterating over units, so "which order do we process things in" is never ambiguous. And seed your random number generator from a value every machine already agrees on — never from the system clock, which is by definition different on every machine. Get any of these wrong — the math, the order, or the randomness — and the two machines' simulations quietly drift apart. That's called a desync, and the unsettling part is that nobody notices right away: both players keep playing, unaware they're now looking at two different games.

That identical-simulation guarantee depends on one more rule, though: nobody is allowed to simulate tick N until they personally hold every peer's command for tick N. Call this rule the "barrier."

Here's the part that's easy to get wrong the first time you hear it: don't picture a machine. There's no third party sitting between the two peers, refereeing this. Each one enforces the rule on itself — it simply refuses to advance to the next tick until its own inbox for that tick is full. That barrier is the whole tradeoff, in one picture: lockstep is only ever as fast as its slowest participant. It's also lockstep's particular answer to the second half of Tick 02's core question — how do you hide the time it takes to find out whose simulation is right? Lockstep's answer is that you don't hide it. You make every peer sit through the wait together, and the barrier is the mechanism that enforces that. (Tick 06 shows the other bet you can make instead: guess rather than wait, and only pay a cost on the guesses that turn out wrong.)

This is also why classic RTS games cap their lobbies at a handful of players, buffer a tick or two of input delay to absorb small hiccups, and why one player with a bad connection visibly drags the whole match down with them. And notice what's missing from this whole description: a server. It's a peer-to-peer model. No referee is required, because every machine is independently computing the same answer as everyone else.

Supplementary reading — what the barrier doesn't handle by itself

Packet loss isn't just late, it's fatal. A shooter can drop a position update and shrug — the next one supersedes it. Lockstep can't: every command must eventually reach every peer, in order, exactly once, or that peer's simulation permanently diverges. So lockstep can't run on raw fire-and-forget UDP — it needs a layer underneath, plain TCP or a custom ack-and-retransmit scheme, that guarantees eventual delivery, not just fast delivery. The barrier isn't waiting for a packet to show up by some deadline; it's waiting for a command, resent as many times as it takes, to actually arrive.

Your own command isn't exempt. It's tempting to assume your own input should apply instantly — it's your machine, after all. It doesn't: your client queues its own command for tick N and waits at the same barrier as everyone else. That's why lockstep games buffer a fixed input delay, commonly 100–200ms, before any command takes effect, including yours — it's the time budget for that command to physically reach every other peer before the tick it's scheduled for arrives.

Peers don't cross the barrier in unison. Each peer's barrier is a purely local condition — "have I personally received everyone's command for tick N?" — and that turns true at a different wall-clock moment on every machine, since every peer-to-peer link has different latency. Peer A's inbox for tick 500 can fill up 17ms before Peer B's does, so Peer A simulates first and may already be on tick 501 or 502 while Peer B is still stuck on 498. This is harmless, because determinism is a guarantee about sequence, not simultaneity: every peer eventually applies the same commands in the same order through the same math, regardless of when in real time it gets there. What it does need bounding is how far a fast peer is allowed to run ahead — left unchecked, it would buffer an ever-growing pile of unconfirmed future state and face a brutal catch-up burst once the slow peer recovers. So engines cap it with a run-ahead window: a peer may simulate at most K ticks ahead of the slowest acknowledged peer, then it blocks too — the same sliding-window flow control TCP uses, applied to ticks instead of bytes.

Going offline is a different failure than going slow, and from silence alone a barrier can't tell them apart at all. A dropped packet and a permanently dead peer look identical on the receiving end. This isn't a lockstep-specific gap — it's the same wall every asynchronous network hits. With no bound on message delay, nothing can prove "very slow" apart from "gone forever." You can only approximate the difference.

Real engines approximate it by stacking two things. First, a heartbeat, sent on a fixed interval, independent of game commands — so silence in the heartbeat channel ("the pipe itself is gone") reads differently from silence in the command channel ("the pipe's fine, this tick's command just isn't ready yet"). Second, a timeout threshold: a policy tradeoff, not a detection, where missing heartbeats for a few seconds gets treated as disconnected. Once that threshold trips, the match pauses ("waiting for Player 2…"), then either drops that player from the peer set — their army goes idle, the barrier now only waits on the survivors — or ends the match. Reconnection is where determinism pays for itself: since state is just the replay of every command from the start, a peer that drops and rejoins can resync by replaying the full command log instead of needing a bespoke catch-up protocol.

The lobby-size cap is this same problem, at scale. Waiting for the slowest of N peers gets worse than linearly worse as N grows. It's the same tail-latency problem as synchronous replication to N replicas: effective latency is the max across peers, not the average, and the odds that at least one of N peers is having a bad moment climb fast as N grows. That's the actual reason classic RTS lobbies top out around 2–8 players, not an arbitrary design choice.

None of this is chaos, though — it's the opposite. Every failure mode above resolves to the group pausing, never the group silently disagreeing. Lockstep buys zero divergence by refusing to let anyone proceed on incomplete information; that refusal is the whole mechanism, not a side effect of it.

lockstep_tick.py — vanguard
import hashlib

class Link:
    """A fake network: delivers a message N ticks late."""
    def __init__(self, delay_ticks):
        self.delay = delay_ticks
        self.buffer = {}   # tick -> list[(peer_id, cmd)]

    def send(self, tick, peer_id, cmd):
        self.buffer.setdefault(tick + self.delay, []).append((peer_id, cmd))

    def peek(self, tick):
        """Look at whatever has arrived for this tick so far — does NOT remove it,
        so a peer that isn't here yet doesn't cost the ones who already are."""
        return self.buffer.get(tick, [])

    def clear(self, tick):
        """Drop this tick's raw buffer. Only safe once every peer is accounted for."""
        self.buffer.pop(tick, None)

def submit_local_command(tick, local_peer, link):
    """Call this exactly once per tick — never again on a retry."""
    link.send(tick, local_peer.id, local_peer.poll_command())

def try_advance_tick(tick, peers, link, world):
    """Call this as many times as you like until it returns a hash.
    It never polls input or sends anything, and it never discards a command
    that hasn't been consumed yet — so retrying is free."""
    # BARRIER — nobody simulates until every peer's command has arrived.
    # peek(), not receive(): a command that HAS arrived must stay right where
    # it is until the barrier is actually satisfied, or the next poll would
    # find it gone and this tick could never be completed.
    commands = dict(link.peek(tick))
    if len(commands) < len(peers):
        return None   # still waiting: nothing buffered is lost, so this is free to retry

    link.clear(tick)   # every peer is in — safe to drop the raw buffer now

    # identical order, identical math, on every machine
    for peer_id in sorted(commands):
        world.apply(peer_id, commands[peer_id])
    world.advance(DT)   # DT is Tick 01's local sim step (60Hz) — illustrative here.
                        # Tick 07's "10-20Hz" is how often production lockstep engines
                        # batch and exchange command packets, not the sim step rate;
                        # this simplified example ties one barrier to one tick to keep
                        # the mechanism readable, decoupling the two is an optimization.

    # catch desyncs before they become "the game feels haunted"
    return hashlib.sha1(world.serialize()).hexdigest()[:8]

# game loop, sketched:
#   submit_local_command(tick, me, link)         # exactly once
#   result = None
#   while result is None:                        # safe to retry: peek() never
#       result = try_advance_tick(tick, peers, link, world)   # consumes, so nothing is lost

Why the checksum matters — real lockstep engines hash the world state every N ticks and compare hashes across peers for that same tick: peer A calls try_advance_tick and gets back 7f3a91c2 for tick 4000; if peer B gets that same 7f3a91c2 for tick 4000, the two worlds still agree and play continues. If peer B instead gets b1e04dd0 for tick 4000, that mismatch is the desync signal — something upstream (a stray float op, an unpinned iteration order) made two "identical" simulations diverge, and the engine logs it and disconnects the pair rather than let them keep drifting apart unknowingly. The hash is how you find out before the players do, from a bug report titled "the game is haunted."

TICK 05

Authoritative server — how card games stay honest

Project: Tabletop

Lockstep trusts every machine equally. A trick-taking card game can't afford to trust any of them.

Tabletop's actions are sparse (a handful of plays per minute) and its stakes are high (hidden hands, ranked ladders, real money in some titles). So it flips the model completely: the server holds the only copy of the truth. Clients never mutate the canonical game state — they send intent ("I'd like to play the 7 of hearts"), the server validates it against rules the client can't see all of (is it even your turn? do you actually hold that card?), and only then updates the real state and broadcasts the result.

This buys three things at once. No determinism requirement — the server is the only place logic runs, so client CPUs, OS versions, and rounding never matter. Trivial reconnects — a disconnected client just re-requests the current state instead of replaying history. And a hard ceiling on cheating — a modified client can lie about wanting to play a card, but it can't fabricate a card it doesn't hold, because the server never told it anyone else's hand in the first place.

Failure mode — the model breaks the moment the server sends a client information it shouldn't have yet "for convenience" (e.g. everyone's hand, to simplify a debug view). A client-side authoritative check is not a security boundary; a client-side display of secret data is a leak, full stop. Broadcast only what that recipient is allowed to see.

table_server.py — tabletop
class TableServer:
    """The only place the real game state lives."""
    def __init__(self, players):
        self.hands = deal(players)          # server-only — clients never see this
        self.turn = 0
        self.trick = []

    async def handle_intent(self, player_id, card):
        if player_id != self.current_player():
            raise IllegalMove("not your turn")
        if card not in self.hands[player_id]:
            raise IllegalMove("you don't hold that card")

        self.hands[player_id].remove(card)
        self.trick.append((player_id, card))
        self.turn += 1

        await self.broadcast(public_state(self))   # never the hidden hands

    async def broadcast(self, state):
        for conn in self.connections:
            await conn.send_json(state)

The price is latency, plain and simple: every action costs a full round trip before any client sees the result. This is authoritative server's answer to Tick 02's second question — how do you hide the time it takes to find out whose simulation is right? It doesn't hide the wait at all; it bets that the genre's own pace makes an un-hidden round trip invisible anyway. For a card game, one played every second or two, that bet pays off completely. For Duel-7's 60 fps combat, the same un-hidden wait would be unplayable — which is exactly the problem the next chapter exists to solve.

TICK 06

Prediction & rollback — faking zero latency

Project: Duel-7

A 100 ms round trip is invisible in a card game and catastrophic in a fighting game. Duel-7 can't wait for the network, so it stops waiting — and corrects itself later, before you notice.

There are three escalating answers to "the network is too slow for this genre," and production games have used all three:

1 — Input delay

The blunt fix: hold your own input for a couple of frames before applying it, so it lines up with when the remote input would realistically arrive. Simple and perfectly synchronized, but every player feels it as sluggishness — this was standard in fighting games before rollback became widespread.

2 — Client-side prediction + server reconciliation

This is the technique used by Source-engine games, and by Overwatch. (Timothy Ford's 2017 talk at GDC — the Game Developers Conference, the industry's largest technical conference — titled "Overwatch Gameplay Architecture and Netcode," is the canonical writeup on it.) Here's how it works: the client applies your input immediately and shows the optimistic result, while an authoritative server catches up and either confirms it or snaps you back to the corrected reality. Valve's lag compensation takes this further for hit detection — the server briefly rewinds the world to what the shooter actually saw before deciding whether a shot landed.

"Snaps you back" is doing a lot of work in that sentence, and it's worth unpacking, because it's the same trick as rollback below, just triggered from the other direction. Here's how it actually works: the client tags every outgoing input with an increasing sequence number, and keeps a small buffer of every input it's sent but hasn't yet had confirmed.

The server processes those inputs and periodically tells the client, "as of input N, your state should be X." If the client's own record already matches X, it just discards everything up through N and moves on — no visible change, nothing to correct. But if it doesn't match, the client resets its local simulation to the server's state X, then replays every buffered input after N back through its own simulation to catch back up to the present. That replay is exactly the rewind-and-resimulate move you'll see in rollback's code below. The only difference is what triggers it: there, it's a peer's own guess turning out wrong; here, it's a correction arriving from the server.

3 — Rollback netcode

Despite the name, nobody here is reading the opponent's mind or reasoning about their strategy. "Prediction" means something almost embarrassingly mechanical: assume the remote player's input hasn't changed since the last packet you actually received from them, and simulate ahead on that guess immediately, with no waiting at all.

It's the same bet a CPU's branch predictor makes. The CPU doesn't understand your program's logic either — it just bets "this branch went the same way last time," executes ahead speculatively on that bet, and pays a defined, bounded cost, flush the pipeline and redo the work, on the occasions the bet is wrong. Rollback is that exact pattern, applied to game ticks instead of instructions.

This is the technique behind GGPO, the rollback netcode SDK that popularized this approach across the fighting-game community (more in Tick 08's further reading), and it's what most modern fighting games use. It's fully peer-to-peer, fully deterministic, and built entirely on that one guess. And the guess works because human input is sticky relative to a single frame: a held direction, a held button, usually doesn't change from one frame to the next. So on the overwhelming majority of frames, nobody's input changes at all — which means most predictions are already correct before the real input even arrives.

When the real remote input finally does arrive, one of two things happens. If it matches the guess, nothing happens — the guess was right, so there's nothing to fix. If it doesn't match, the peer rewinds its simulation to the last confirmed frame and replays every frame since, using the corrected input this time, all inside a single rendered frame. You never see this correction happen on your own character. The only visible sign, when it happens at all, is a remote character occasionally "snapping" to a different state — proof that your peer's guess about them was wrong.

That replay is only affordable because a resimulated tick is a stripped-down tick. It re-runs game logic and physics against the corrected input, but skips rendering, audio, and everything else that makes a normal frame expensive. A handful of logic-only steps fit inside a 16-millisecond budget in a way a handful of fully-rendered frames never could.

Even so, resimulation isn't free, which is exactly why shipped rollback engines — GGPO included — still cap the maximum rollback window, commonly to a handful of frames, instead of assuming they can absorb an arbitrarily late input. That cap is also why option 1 doesn't disappear once you have rollback: real fighting-game netcode typically layers a small, fixed amount of input delay underneath a bounded rollback window, so the worst case a late input can produce — resimulating all the way up to that cap — stays inside the frame budget instead of growing without limit.

Why it works — rollback needs the same deterministic-simulation property as lockstep (Tick 04) — it's often described as lockstep's more optimistic sibling. The difference is when you find out you were wrong: lockstep never lets a peer proceed until it knows; rollback lets every peer barrel ahead on a guess, and pays for wrong guesses with a cheap, invisible rewind instead of a visible stall. This is rollback's answer to Tick 02's second question: it doesn't make you wait (lockstep) and it doesn't just accept the wait as invisible (authoritative server) — it hides the wait by guessing, and only pays for the guesses that turn out wrong.

rollback.py — duel-7
LOCAL, REMOTE = 0, 1

class RollbackSession:
    def __init__(self, world):
        self.world = world
        self.snapshots = {}          # tick -> serialized world
        self.confirmed = {}          # tick -> {LOCAL: input, REMOTE: input}

    def advance_predicted(self, tick, local_input, remote_guess):
        self.snapshots[tick] = self.world.snapshot()
        self.confirmed[tick] = {LOCAL: local_input, REMOTE: remote_guess}
        self.world.step({LOCAL: local_input, REMOTE: remote_guess})

    def on_remote_input_arrives(self, tick, real_remote_input):
        guessed = self.confirmed[tick][REMOTE]
        if guessed == real_remote_input:
            return   # predicted correctly — nothing to undo

        latest_tick = self.world.current_tick                 # how far we'd predicted ahead
        self.world.restore(self.snapshots[tick])              # rewind (this also resets current_tick to `tick`,
                                                                # which is why latest_tick had to be captured first)
        for t in range(tick, latest_tick):                     # resimulate every predicted tick since
            local_i = self.confirmed[t][LOCAL]
            remote_i = real_remote_input if t == tick else self.confirmed[t][REMOTE]
            self.world.step({LOCAL: local_i, REMOTE: remote_i})

Notice this is peer-to-peer, just like lockstep. Most fighting games don't run a server-authoritative simulation at all, because the two players are equally trusted — there's nothing hidden to protect here, unlike Tabletop. That symmetry is exactly what makes rollback possible in the first place: rewinding and resimulating only works if every peer already holds, and is trusted to act on, the complete, ungated simulation state before any referee confirms a thing. Each side's guess about the other player is built from that same full state.

A server-authoritative genre can't make that same trade. A shooter's client must never be able to see through the fog of war, and can't be allowed to unilaterally decide that a shot landed — so it can never be handed the complete, ungated state that rollback needs in order to guess. That's why it reaches for option 2 instead: predict locally, but let the one party that actually holds the full state, the server, be the one that confirms it. This is exactly what Overwatch and Source-engine games do.

Supplementary reading — what "prediction" does and doesn't guarantee

Confirmed state is guaranteed to converge — but rollback doesn't invent that guarantee, it borrows it. The predicted ticks are explicitly provisional, never final, exactly like a CPU's speculatively-executed instructions before a branch resolves. The moment the real input for tick T arrives, the guessed version is thrown away and tick T — and everything after it — is replayed using the confirmed input. Once both peers hold the real input for tick T, they're replaying the identical sequence of confirmed commands through the identical deterministic math: Tick 04's "identical simulation over an identical command sequence" argument, applied after the fact instead of gated upfront by a barrier. That guarantee carries the exact same prerequisites as lockstep's — a genuinely deterministic simulation, and eventually-reliable delivery of every input. Rollback doesn't remove the need for either; it only changes what gets shown to the player while waiting for delivery to catch up.

What's never guaranteed is that both screens agree at the same instant. Lockstep at least stalls everyone at a barrier until they share a tick; rollback never stalls, so at any wall-clock moment one peer may already be showing the confirmed, correct tick while the other is still showing a provisional guess about to be corrected. A visible "snap" isn't a leak in the system — it's the proof, rendered on screen, that the two peers briefly disagreed. And like lockstep's peers racing ahead of a slow one, rollback's speculation is bounded too: shipped engines cap the maximum rollback window to a handful of frames, and if the real input still hasn't arrived once that cap is hit, the engine falls back to actually waiting — briefly behaving like lockstep rather than assuming it can eat an arbitrarily late input.

The rewind never plays out as a visible "flashback" — because only the last tick of a replay batch is ever drawn. Every intermediate tick in a resimulation runs game logic only; rendering and audio are skipped, which is also what makes replaying several ticks cheap enough to fit inside one frame's budget. So the player never sees a frame mid-rewind — only two consecutive displayed frames: one built from the wrong guess, the next built from the fully-corrected result. What's visible, when it's visible at all, is a discontinuity — the remote character's position pops between frames, like a scratched record jumping grooves — not an animated rewind-and-fast-forward. A small misprediction produces a jump of a few pixels, invisible the same way 24fps film hides its own discreteness; only a large one — a long delay, or a guess that was very wrong — produces the visible "teleporting" that shows up in complaints about poorly-tuned rollback implementations.

The one place the CPU analogy actually breaks: audio has no commit point. An unpresented frame can be silently discarded and replaced, because the display only shows whatever gets flipped to it once per frame — a safe holding area, much like a CPU's reorder buffer for speculative results. Sound has no equivalent. A hit sound that starts playing because the game predicted a connect has already reached the player's ears the instant it starts; there's no way to un-play it once the real input reveals the hit actually missed. That's why shipped rollback engines typically delay or gate sound and hit-effects behind confirmation rather than firing them optimistically like everything else — a genuinely unavoidable seam in the technique, not an implementation bug.

TICK 07

Making it feel good, and choosing your architecture

Getting the state right, which is what chapters 4 through 6 were about, is half the job. The other half is what the player actually sees between updates — and then, now that you've met all three architectures, how you actually pick one.

Snapshot interpolation

An authoritative server — Tabletop, or any server-authoritative action game — only sends full state updates a few times a second for remote entities. And those updates don't arrive on a steady beat. This is Tick 02's jitter showing up again, just now as an animation problem instead of a timing one. Render each snapshot the instant it lands, and motion on screen speeds up and slows down with the network instead of with time — everything looks like it's teetering between positions.

The standard fix is to deliberately render slightly in the past. Buffer the last two snapshots you've received, and interpolate — smoothly blend — between them as you draw each frame. You're trading a small, constant delay for motion that's always smooth, which is almost always the right trade to make.

Extrapolation ("dead reckoning")

What do you do when no new snapshot has arrived yet at all? You can keep moving a remote entity along its last known velocity, as a guess. It hides small gaps in the data well. But the guess compounds the longer it runs: the more time passes without a real update, the further it can drift from where the entity actually is. So most engines cap how far ahead they'll extrapolate before they just freeze the entity in place, or let it visibly snap back once a real update finally arrives.

Tick rate is a bandwidth budget, not a quality slider

How often should you actually update the world? It's not that some genres care more about smoothness than others — it's that they're paying for updates in a completely different currency, as the table below shows.

GenreTypical rateWhy
Turn-based / cardson-actionNothing to send between plays — event-driven, not tick-driven.
RTS lockstep10–20 HzOnly command packets, so higher rates are cheap — bounded by input-delay tolerance, not bandwidth.
Shooters / action20–128 HzFull state per tick is expensive; Valve/Source titles famously ship 64 or 128 tick servers as a paid-for precision tradeoff.

Every one of these is the same tradeoff, just wearing a different unit: bytes per second, traded against how stale the world is allowed to look.

Choosing an architecture

You've now seen three answers to Tick 02's question — lockstep, an authoritative server, and prediction with rollback. So how do you actually pick, when you're staring at a new game idea? Two questions, asked in order, get you most of the way there.

The first question is about tempo: can this genre's pace tolerate everyone pausing together for a network round trip? Tick 02 told you that round trip usually costs somewhere between 20 and 100-plus milliseconds. A slow, forgiving tempo — Vanguard's command-based RTS pacing, or Tabletop's one-play-every-second-or-two rhythm — can afford to make every peer sit through that wait. A genre where players react to each other in real time, at something close to human reflex speed, generally can't: added delay starts to feel bad to a hand on a controller at around 50 milliseconds, which is well under a typical round trip.

If the answer is "yes, we can wait," ask a second question: is the simulation cheap enough to replay from just the players' inputs, and are the peers trusted enough with each other's full state? Vanguard answers yes to both — replaying commands is exactly what makes lockstep work, and while its cheating stakes are real, they're not severe enough to be worth a much bigger bandwidth bill just to eliminate them. So it lands on lockstep. Tabletop answers no — hidden hands and real stakes mean it can't hand any client the full truth — so it lands on an authoritative server instead.

If the answer is "no, we can't wait," the same second question splits the twitch-critical genres too. Duel-7 is cheap to replay and its two players are equally trusted, so it lands on rollback. A shooter is also twitch-critical, but its world state is large and its clients can't be fully trusted with things like enemy positions behind cover — so it lands on prediction plus server reconciliation instead, even though it's chasing the exact same responsiveness Duel-7 is.

Real production games rarely settle on one answer for the whole game, though. An MMO is the clearest example: an authoritative server holds the truth, the way Tabletop's does. Interest management narrows what any one client is even told about — only nearby entities matter to them, so nobody needs a full-world snapshot every tick. And client-side prediction smooths movement, the way Duel-7's option 2 does, so walking around doesn't feel like a laggy card game. The architecture gets chosen per subsystem, not once for the whole game: movement gets prediction, inventory and trading get strict server authority, and chat needs neither.

The pattern to take away — "what architecture is this game" is usually the wrong question. The right one is "what does this subsystem need to feel right, and what can it afford to get wrong for a moment?" Movement can afford a wrong guess corrected next frame. A trade cannot.

TICK 08

Production notes, and a cheat sheet

Everything so far has been about game logic — who's allowed to be wrong, and for how long. Shipping any of it adds a layer underneath that every chapter so far quietly assumed away: the wire itself.

UDP vs. TCP. TCP guarantees that data arrives in order and arrives at all, which sounds like exactly what you'd want — until you notice the cost. One lost packet blocks every packet behind it until it's resent, a stall called head-of-line blocking. That's a real problem for a real-time game: nobody wants a visible freeze caused by a stale position update from half a second ago.

But "reliable enough" actually means different things depending on what's in the packet. Take a shooter continuously broadcasting position and velocity: a newer packet genuinely supersedes an older one, so these games run lightweight UDP with no real reliability layer at all. They just drop old, superseded packets and never bother recovering them, because the next packet already tells you everything the lost one would have.

Lockstep and rollback can't get away with that trick, though. Each tick's command is unique data — it isn't superseded by the next tick's command the way a stale position is — so a truly, permanently lost input either stalls a lockstep barrier forever, or produces exactly the desync Tick 04 spent a whole section warning about. So instead of dropping old data, these genres send more of it: a GGPO-style rollback packet piggybacks a short window of the sender's most recent, not-yet-confirmed inputs on every send (lockstep engines use the same trick for their own command packets). If one packet is lost, the next one already contains the data it was carrying — recovered for free, with no acknowledgment and no retransmission required. Tabletop, event-driven and low-frequency, never has to make any of these tradeoffs. It's perfectly happy running on plain TCP or WebSockets.

NAT traversal. Two home routers usually can't open a direct connection to each other without help. Even a "peer-to-peer" game like Duel-7 typically still touches a server briefly for matchmaking and connection setup — including a trick called hole-punching, where a rendezvous server tells both players' machines to send each other a packet at the same moment. Each side's own outgoing packet opens a temporary return path through its own router, letting the other player's reply through without either router ever being reconfigured. And when a particularly strict NAT won't allow even that, the game falls back to relaying all its traffic through a server instead.

Serialization. JSON is perfectly fine at Tabletop's tempo. At 20 to 60 updates a second, though, JSON's overhead adds up fast, so production real-time games switch to compact binary formats and send only what's changed since the last acknowledged snapshot — delta compression — instead of the full state on every tick.

Interest management. This is the other half of the promise from Tick 04: a server doesn't have to tell every client about every entity in the whole world, only the ones actually relevant to that client — usually, whatever is near them, or inside their field of view. A shooter's server might be tracking thousands of entities across a large map, but any one player only needs updates about the handful of players and objects close to their own position. That's exactly the locality Tick 04 pointed out an RTS doesn't have: an RTS player can see most of their own base and army in a single glance, so there's no "it's far away, they don't need to know" audience to exclude. A shooter's narrow, ground-level viewport has plenty of that kind of audience to exclude, which is why this trick works so well there and not in Vanguard.

Full circle to Tick 02 and Tick 03 — anti-cheat turns out to be a direct consequence of the trust question you answered all the way back in Tick 03. An authoritative server, like Tabletop's, sits at the trust-nobody end of that spectrum, and it makes most client-side cheating structurally impossible — the truth simply never leaves the server, so there's nothing on a player's own machine worth attacking. A trust-everyone model, like Vanguard's or Duel-7's, puts the truth on every machine instead, so it has no equivalent wall to hide behind. It leans on other things: the symmetry of both players seeing the same battlefield, replay verification after the fact, and, for competitive titles, kernel-level anti-cheat software — which needs the operating system's own privileges, because ordinary game code can't see a cheat program running alongside it at that same privileged level.
