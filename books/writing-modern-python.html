Chapter 1Day One: A Project the 2026 Way

In 2020, starting a project meant mkdir, python -m venv .venv, an activate dance, and a requirements.txt you would regret by March. In 2026 the whole scaffold is one command, and the daily loop around it never touches a virtualenv by hand. This chapter walks the scaffold file by file, then the loop you will actually live in: add, sync, run, lock, lint, CI.

1.1 The five-minute scaffold, annotated

Start every project with uv init --package. uv ubiquitous is the default project manager of 2026 — over 126 million downloads in February 2026 alone — and its scaffold is the one this book assumes. (Book 1, ch. 4.2) introduced the command; here is what it writes and why each file earns its place.

$ uv init --package orders
Initialized project `orders`
$ cd orders

orders/
├── .python-version    # interpreter pin — uv installs it for you
├── .gitignore         # .venv and friends, already excluded
├── README.md
├── pyproject.toml     # the one config file; 1.2 walks it
└── src/
    └── orders/
        └── __init__.py

Three things to notice. There is no requirements.txt — dependencies live in pyproject.toml and exact versions live in uv.lock, which appears on your first uv add. There is no .venv in the listing — uv creates it lazily and manages it forever after. And the package sits under src/, which is the part worth defending.

The src layout exists to break one specific lie. With a flat layout, Python puts the project root on sys.path, so import orders works from the repo even when the installed package is broken. Tests pass on your machine and fail everywhere else. With src layout the only way to import orders is to install it, so tests run against the installed package. That catches missing data files and bad build config at test time, not at release time. Flat layout remains fine for Django apps and scripts that never ship; everything that ships gets src/.

1.2 pyproject.toml, section by section

One file configures your build, your dependencies, uv, Ruff, pytest, and coverage. Here is the canonical 2026 skeleton, annotated. Every tool you add later reads another section of this same file.

[build-system]
requires = ["hatchling"]       # build backend; boring by design
build-backend = "hatchling.build"

[project]
name = "orders"
version = "0.1.0"
requires-python = ">=3.12"     # floor for your code and your CI
dependencies = ["httpx>=0.28"] # what users install, as ranges

[dependency-groups]            # PEP 735 — dev-only, never shipped
dev = ["pytest>=8", "ruff", "pytest-cov"]

[project.optional-dependencies] # extras — shipped, for users
cli = ["rich>=13"]

[tool.uv]
package = true                 # build and install the src package

[tool.pytest.ini_options]
addopts = "-ra --strict-markers"
testpaths = ["tests"]

[tool.coverage.run]
source = ["src"]

The section people get wrong is dependencies. PEP 735 gave us two homes with opposite audiences, and picking the wrong one either ships pytest to your users or asks contributors to install dev tools by hand.

[dependency-groups][project.optional-dependencies]
AudienceYou and your contributorsYour users
Shipped to PyPINeverYes, as extras
Installed byuv sync, uv run (the dev group is on by default)pip install orders[cli]
Typical contentspytest, ruff, coverage, type stubsOptional features: rich, extra backends

Groups compose: typing-test = [{include-group = "typing"}, {include-group = "test"}] builds one CI group out of two smaller ones. Optional-dependencies stay for user-facing extras only.

1.3 The daily loop

Four verbs cover a normal day: add, sync, run, and the occasional lock --upgrade-package. Two more replace tools you may still have installed. uvx runs one-off tools, replacing pipx. uv python pin picks the interpreter, replacing pyenv — uv installs standalone CPython builds itself. A Tuesday, end to end:

$ uv python pin 3.13            # writes .python-version
$ uv add httpx                  # pyproject + uv.lock + .venv in one step
$ uv add --dev pytest respx     # lands in the dev dependency-group

$ git pull
$ uv sync                       # rebuild the env to match the lock

$ uv run pytest                 # runs in the project env; no activate
$ uvx ruff check .              # one-off tool run, cached

$ uv lock --upgrade-package httpx   # targeted update; rest of lock kept
$ uv sync

Notice what never happens: no source .venv/bin/activate, no pip install, no "which Python is this terminal using". uv run always resolves the project environment, so the wrong-interpreter class of bug is gone.

1.4 Lock files and the pinning spectrum

Commit uv.lock. For an application this is not a debate. The lockfile records exact, hash-verified versions of every transitive dependency. And uv sync --locked in CI fails loudly if the lock has drifted from pyproject.toml. Libraries sit at the other end. Publish wide ranges in [project.dependencies] so downstream projects can resolve you alongside everything else, and test your lower and upper bounds in CI. Many libraries now commit the lock too — for contributors and CI — while the ranges stay what users see.

Two interop notes. If a deploy target only speaks pip, uv export --format requirements-txt emits a pinned requirements file from the lock. And PEP 751's pylock.toml, a tool-neutral lockfile standard, is the emerging format to watch — for now uv.lock is what you commit.

1.5 Scripts that carry their own dependencies

PEP 723 lets a single file declare its own environment. Put a TOML block in the header, run it with uv run, and uv builds an ephemeral cached environment — no project, no README telling teammates what to install first. This is the right home for ETL jobs, ops scripts, and reproducible bug reports.

#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.12"
# dependencies = ["httpx>=0.28", "polars>=1"]
# ///
"""Nightly ETL: pull orders, write a parquet summary."""

import httpx
import polars as pl


def fetch_orders() -> list[dict]:
    resp = httpx.get(
        "https://api.example.com/orders", timeout=30
    )
    resp.raise_for_status()
    return resp.json()


def main() -> None:
    df = pl.DataFrame(fetch_orders())
    summary = df.group_by("status").len()
    summary.write_parquet("orders_summary.parquet")


if __name__ == "__main__":
    main()

The shebang makes it directly executable: chmod +x etl.py && ./etl.py. Add a dependency later with uv add --script etl.py polars, which edits the header block for you. One honest caveat: editors do not always resolve inline dependencies, so expect red squiggles in VS Code even when the script runs fine.

1.6 Ruff as the house style

Use Ruff ubiquitous for both linting and formatting. It replaces flake8, black, isort, and pyupgrade with one binary. The adoption numbers are not close: roughly 262 million downloads a month as of June 2026, and about 46× faster than flake8 on a 47K-line codebase (0.18s). It does not type-check; that is chapter 3's job.

[tool.ruff]
target-version = "py312"
line-length = 88

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]
# grow into: "SIM", "RUF", "ASYNC", "PTH"
ignore = ["E501"]  # the formatter owns line length

[tool.ruff.lint.isort]
known-first-party = ["orders"]

Start with E, F, I, UP, B — pycodestyle, pyflakes, import sorting, the auto-modernizer, and bugbear's bug patterns. Add SIM, RUF, ASYNC, PTH once the team stops noticing the first five. Run ruff check --fix . before ruff format .: autofixes can alter semantics, so you want them visible in the diff, while the formatter only moves whitespace. The formatter's output matches black on more than 99.9% of lines, so nothing you have already formatted needs reformatting.

The UP rules deserve special mention. Gated by target-version, they rewrite dated idioms to the newest syntax your Python floor allows. With the py312 floor above, legacy typing imports rewrite themselves:

Then · 2020
from typing import Dict, List, Optional

def fetch_user(
    uid: int,
) -> Optional[Dict[str, List[int]]]:
    ...
Now
def fetch_user(
    uid: int,
) -> dict[str, list[int]] | None:
    ...

ruff check --select UP --fix made this edit, not a human. Builtins replace typing.Dict/List, and X | None replaces Optional — same signature, no import line, nothing to explain to new hires.

1.7 Guardrails: pre-commit and CI

(Book 1, ch. 4.6) showed a four-line CI job; here is the production version. The workflow pins the interpreter matrix, caches uv's downloads, and refuses to run on a stale lockfile. Chapter 6.7 references this same matrix for testing across versions.

name: ci
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.12", "3.13", "3.14"]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
        with:
          enable-cache: true
          cache-suffix: ${{ matrix.python-version }}
          python-version: ${{ matrix.python-version }}
      - run: uv sync --locked
      - run: uv run ruff check . && uv run ruff format --check .
      - run: uv run pytest

Locally, catch the same things before push with a pre-commit hook. The config is a small YAML file at the repo root:

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.14.0   # example — pin the tag you actually run
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
Verdict: prek vs pre-commit.
Our default: prek — a Rust rewrite that reads the same .pre-commit-config.yaml, with no Python dependency of its own.
Also reasonable: pre-commit — still the incumbent; every teammate's muscle memory and every existing answer on the internet assumes it.
Why: the config file is shared, so switching costs one install command in either direction. The decision is nearly free, and either choice is correct.
Who owns your toolchain? In March 2026 OpenAI announced it would acquire Astral, the company behind uv, Ruff, and ty. As of August 2026, reporting described the deal as pending regulatory approval — treat it as announced, not closed. The tools remain MIT-licensed, and uv is still 0.x with no stable-API promise. The honest cost of this book's near-all-Astral stack (uv + Ruff + prek) is vendor concentration: you get one coherent toolchain and accept one company's roadmap. If that worries you, nothing here is a trap — pyproject.toml, the lockfile, and the Ruff config all transfer to PyPA tools with modest edits.

1.8 When one repo holds several packages: workspaces

When the repo grows a second package — a shared core next to your orders app — do not split it into repos. Declare a workspace at the root and uv gives you one lockfile and one virtualenv for everything:

# root pyproject.toml
[tool.uv.workspace]
members = ["packages/*"]

# packages/core/pyproject.toml
[project]
name = "core"
dependencies = ["orders"]

[tool.uv.sources]
orders = { workspace = true }  # resolve from the repo, not PyPI

[tool.uv.sources] with workspace = true is the line that matters: it tells uv to resolve orders from the sibling directory instead of an index, so members always test against each other's current code. One rough edge, stated honestly: editable installs across members can confuse IDE type resolution, so a restart of your editor's language server is occasionally part of the workflow. Chapter 7 covers how the build backend changes when a workspace member ships to PyPI on its own.

Chapter 2Reading 2026 Code: The Idioms That Replaced Yours

Syntax is what the interpreter accepts. Idiom is what your colleagues accept. Nothing dates a codebase faster than the small patterns typed a hundred times a day. Optional[X] at the top of a file. os.path.join in a helper. A % format in a log line. None of it is wrong; all of it tells the reader when you learned Python. This chapter is the fastest perceived upgrade in the book: each section is one habit, replaced. Book 1 taught the syntax; here it becomes policy.

2.1 Imports that date your code

Stop importing List, Dict, Tuple, Optional, and Union from typing. Builtins carry their own generics since 3.9, and the | operator spells unions since 3.10. (Book 1, ch. 3.3) taught that syntax; this section is the style policy around it.

Then · 2020
from typing import Dict, List, Optional
from typing import Union

class Repo:
    def fetch_user(
        self, uid: Union[int, str]
    ) -> Optional[Dict[str, List[int]]]:
        ...
Now
class Repo:
    def fetch_user(
        self, uid: int | str
    ) -> dict[str, list[int]] | None:
        ...

Same signature, no import line. The builtin generics and the | unions read left to right and need nothing explained to a new hire.

You do not have to make this edit by hand. ruff check --select UP --fix rewrites every occurrence, gated by your target-version (chapter 1.6 set it up). One honest note: the typing docs still list the removal date of the old aliases as "undecided". Treat them as dead anyway — they cost an import, and every senior reviewer reads them as a timestamp.

2.2 pathlib by default

Reach for pathlib.Path whenever a path crosses a function boundary. It is stdlib, needs no install, and turns string surgery into method calls.

Then · 2020
import os

def find_configs(root: str) -> list[str]:
    hits = []
    for dp, _, files in os.walk(root):
        for name in files:
            if name.endswith(".toml"):
                hits.append(
                    os.path.join(dp, name)
                )
    return hits

def load_task(path: str) -> str:
    with open(path, encoding="utf-8") as f:
        return f.read()
Now
from pathlib import Path

def find_configs(root: Path) -> list[Path]:
    return list(root.rglob("*.toml"))

def load_task(path: Path) -> str:
    return path.read_text(encoding="utf-8")

The walker was nine lines of bookkeeping; rglob is one line of intent. The / operator joins paths, read_text handles the context manager, and a Path in a signature says more than str ever did.

Default, not dogma. Keep os where it genuinely wins: os.environ for environment access, and os.scandir inside a hot directory loop, where it skips building a Path per entry. And when a library API wants a path-like object, pass the Path — everything modern accepts one.

2.3 Strings: f-strings by default, t-strings on purpose

The f-string won. % formatting and str.format remain in old code and in logging calls that defer interpolation; everything you write fresh uses f-strings. (Book 1, ch. 2.6) covered the syntax.

Then · 2020
msg = "Task %s: %s (%d pts)" % (
    task.id, task.title, task.points,
)
Now
msg = (
    f"Task {task.id}: {task.title} "
    f"({task.points} pts)"
)

The values sit where they appear in the output. No counting placeholders, no tuple to keep in sync.

Template strings (3.14, PEP 750) are a different tool, not a better f-string. A t-string evaluates to a Template object that keeps the literal parts and the interpolated values separate. It pays off only when a library consumes that object and does something safe with it: SQL parameter binding, HTML escaping, shell quoting.

from string.templatelib import Template  # 3.14

def find_user(name: str) -> Template:
    return t"SELECT * FROM users WHERE name = {name}"

stmt = find_user("ada")
# db: a connection whose execute() accepts a Template
db.execute(stmt)   # db receives the Template; {name} stays a
                   # parameter, never spliced into the SQL text

# ✗ anti-pattern, linter-flagged:
db.execute(str(t"... WHERE name = {name}"))
# str() splices the value back in — you rebuilt
# the injection bug with new syntax

The rule: if nothing downstream wants the Template, you wanted an f-string. Converting a t-string with str() throws away the one thing it was for.

2.4 The classics that still bite

Three traps older than type hints, still flagged in review every week. Each fix is mechanical.

Then · 2020
def add_line(item: LineItem,
             items: list = []) -> list:
    items.append(item)
    return items
Now
def add_line(
    item: LineItem,
    items: list[LineItem] | None = None,
) -> list[LineItem]:
    items = [] if items is None else items
    items.append(item)
    return items

The Now side is longer because the fix is real work: [] as a default is built once, at function definition, and shared by every call that omits it. The None sentinel makes a fresh list per call. Inside a dataclass the same fix is field(default_factory=list).

Then · 2020
if type(item) == LineItem:
    total += item.price
Now
if isinstance(item, LineItem):
    total += item.price

type(x) == rejects subclasses; isinstance accepts them. A GiftLineItem should price like a LineItem. Same one-line guard in tests, where assert type(x) == Foo is a 2026 review flag.

Then · 2020
report = ""
for task in tasks:
    report += f"- {task.title}\n"
Now
lines = [f"- {t.title}\n" for t in tasks]
report = "".join(lines)

Repeated += copies the whole string on every iteration; join allocates once. On a long report the difference is the algorithm, not a micro-tweak.

2.5 namedtuple's afterlife

collections.namedtuple gave you a class factory before dataclasses existed. In 2026 it has two heirs, and which one you pick depends on a single question: does anything unpack or index this value as a tuple?

Then · 2020
from collections import namedtuple

Task = namedtuple(
    "Task", ["title", "points", "done"]
)
Now
from typing import NamedTuple

class Task(NamedTuple):
    title: str
    points: int
    done: bool = False

typing.NamedTuple keeps every tuple behavior — unpacking, indexing, _replace — and adds annotations, defaults, and a class body a checker can read.

If nothing relies on tuple semantics, go one step further: @dataclass(frozen=True, slots=True) (chapter 4 covers the full dataclass case). You trade task[0] for named-only access and cheaper attribute storage. Keep plain namedtuple only where unpacking or indexing is the contract — CSV-shaped rows, APIs that promise tuples.

2.6 match, with restraint

(Book 1, ch. 2.4) taught match syntax. The policy question is when it beats the if-chain you already write. The answer: when it destructures.

Then · 2020
def price_of(item) -> float:
    if isinstance(item, LineItem):
        return item.qty * item.unit_price
    if isinstance(item, dict):
        if item.get("discounted"):
            return item["price"] * 0.9
        return item["price"]
    raise TypeError(item)
Now
def price_of(item) -> float:
    match item:
        case LineItem(qty=q, unit_price=p):
            return q * p
        case {"price": p} as d \
                if d.get("discounted"):
            return p * 0.9
        case {"price": p}:
            return p
        case _:
            raise TypeError(item)

The Now side is not shorter; it is flatter. The capture pattern pulls qty and unit_price out of the object, and the guard carries the discount condition, so no case body holds an if. That is the only payoff match has to offer — take it or leave the if-chain.

Verdict: match vs isinstance chains.
Our default: if/elif with isinstance for plain dispatch; match when a case destructures a shape or needs a guard.
Also reasonable: match everywhere, for one consistent dispatch style across the codebase.
Why: as a spelling of isinstance, match is longer and no clearer — a case LineItem(): with an empty pattern does the same check with more machinery. It earns its keep on structural dispatch: dicts of mixed shape, dataclass fields pulled into locals, guarded branches.

2.7 The small modernizations, and the quick map

Some replacements are one call each. The one worth its own pair:

Then · 2020
from datetime import datetime

stamp = datetime.utcnow()
Now
from datetime import UTC, datetime

stamp = datetime.now(UTC)

utcnow() is deprecated: it returned a naive datetime that claimed to be UTC, and every downstream astimezone had to trust that claim. datetime.now(UTC) returns an aware datetime, so the timezone is in the value, not in the reader's head.

The rest of the dated calls fit in one table. Print it; it doubles as a cheat sheet for reading any 2020-era file.

That is the whole chapter's thesis in miniature: none of these changes what your program does. All of them change what a reader concludes about when it was written — and how carefully it was maintained since.

Chapter 3Typing for Real Projects

Book 1 taught the syntax. What teams struggle with is the decisions: how strict to be, which checker to run, which modeling tool fits the data. This chapter is those decisions, each with the config or idiom that implements it. The legacy-import cleanup (List → list) was chapter 2.1's job, and is assumed done here.

3.1 The ratchet: three tiers of strictness

Do not turn on strict = true for a 40K-line codebase on day one. You will get a thousand errors, fix none, and delete the config by Friday. Roll out in three tiers — the config below is the entire plan.

# pyproject.toml — the ratchet, annotated

# Tier 1 · baseline: an empty [tool.mypy] table.
# Checker defaults, zero flags. Add it to CI today.

# Tier 2 · mid: five flags worth turning on within a month.
[tool.mypy]
check_untyped_defs = true       # look inside unannotated bodies
disallow_incomplete_defs = true # all-or-nothing signatures
warn_redundant_casts = true     # cast() that changes nothing
warn_unused_ignores = true      # stale type: ignore comments
strict_equality = true          # no == between mismatched types

# Tier 3 · strict = true — per new package or cleaned
# module. Never repo-wide on an old codebase.

# The ratchet itself: legacy code stays silent until fixed.
[[tool.mypy.overrides]]
module = "legacy.*"
ignore_errors = true
TierExact configWhen to be there
1 · Baseline[tool.mypy] present, no flagsDay one. The point is the CI gate, not the bugs caught.
2 · MidThe five flags aboveWithin the first month; real bugs, no ceremony.
3 · Strictstrict = true, per package or cleaned moduleNew code starts here; old modules graduate one at a time.

The override table is why this works. legacy.* stays silent while new code is checked honestly, and the silenced list only shrinks — fixing a module means deleting its line. Then gate CI with uv run mypy src in the workflow from 1.7, and the typed surface cannot regress.

3.2 Pick one checker and run it in CI

(Book 1, ch. 3.6) showed a checker catching a bug; here is which one to install. Default to mypy ubiquitous. It is not the fastest. It is the most widely run checker in CI, owns typeshed (the stub repository nearly every checker consumes), and has the deepest plugin ecosystem — django-stubs is the canonical case. Section 3.1's config is already written in mypy flags, so the chapter stays coherent.

Whichever you pick, the practice is identical: config in pyproject.toml, one command in CI, no editor-only checking. And Ruff is absent from the table on purpose — it lints and formats; it does not type-check.

3.3 Protocol vs ABC

(Book 1, ch. 3.4) introduced Protocol syntax. The decision rule: use a Protocol for caller-defined interfaces, seams where the consuming function states what it needs. Use an ABC when you own the hierarchy, share implementation, or need runtime isinstance. The same report renderer, both ways:

Then · 2020
from abc import ABC, abstractmethod

class Renderer(ABC):
    @abstractmethod
    def render(
        self, order: Order
    ) -> str: ...

def print_report(
    r: Renderer, order: Order
) -> None:
    print(r.render(order))
Now
from typing import Protocol

class Renderer(Protocol):
    def render(
        self, order: Order
    ) -> str: ...

def print_report(
    r: Renderer, order: Order
) -> None:
    print(r.render(order))

The seam moved from implementor to caller. With the ABC, every renderer must import and inherit your class — awkward when a teammate's HtmlReport already exists. With the Protocol, anything with a matching render method qualifies, no inheritance required.

The runtime_checkable trap. Decorating a Protocol with @runtime_checkable makes isinstance(x, Renderer) legal — but the check verifies only that a method with the right name exists, not its signature. An object with render(self) passes against a Protocol demanding render(self, order). Treat it as a coarse filter, never as proof of compatibility.

3.4 TypedDict vs dataclass vs pydantic

The slogan: TypedDict to talk to type checkers, pydantic for runtime safety. TypedDict annotates dict-shaped data you do not own — a JSON blob from an API, a **kwargs signature — and vanishes at runtime; the value is still a plain dict. A dataclass is your internal domain object: fast, no validation. Pydantic belongs where untrusted data crosses in, because parsing once at the edge beats checking ad hoc forever after.

3.5 Narrowing that works: TypeIs

Reach for TypeIs (3.13+, PEP 742) when writing a narrowing predicate. TypeGuard, its predecessor, narrows only the if branch; TypeIs narrows both, which is what you meant almost every time.

from typing import TypeIs   # 3.13+, PEP 742

def is_line_item(x: LineItem | Task) -> TypeIs[LineItem]:
    return isinstance(x, LineItem)

def unit_price(x: LineItem | Task) -> float:
    if is_line_item(x):
        return x.unit_price   # x is LineItem here
    return x.estimate       # and Task here — the else
                            # branch narrows too

TypeGuard keeps one job: narrowing to a type that is not a subtype of the input, like list[object] to list[str], where invariance blocks the subtype relation and TypeIs refuses. Everywhere else, TypeIs wins.

3.6 Decorators that keep their signatures

A decorator typed Callable[..., R] erases the wrapped function's signature — a top-three review red flag, because the checker stops verifying arguments at every decorated call site. ParamSpec carries the parameter list through unchanged.

Then · 2020
from collections.abc import Callable
from typing import TypeVar

R = TypeVar("R")

def logged(
    fn: Callable[..., R],
) -> Callable[..., R]:
    def wrapper(*a, **k) -> R:
        print("call", fn.__name__)
        return fn(*a, **k)
    return wrapper
Now
from collections.abc import Callable
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")

def logged(
    fn: Callable[P, R],
) -> Callable[P, R]:
    def wrapper(
        *a: P.args, **k: P.kwargs
    ) -> R:
        print("call", fn.__name__)
        return fn(*a, **k)
    return wrapper

The Now side buys one thing: @logged def fetch_user(uid: int) still flags fetch_user("ada") as an error, because P preserves the parameter list the ... was swallowing. When the wrapper must prepend an argument — injecting a connection or self — add Concatenate, same import line.

3.7 Aliases, overloads, generators

Three small policies that clean up API surfaces. Name complex types with the 3.12 type statement; reach for @overload only when a TypeVar cannot express the relationship; expose Iterator[T], not the full generator type:

from collections.abc import Iterator
from typing import Any, overload

type Json = dict[str, Any]   # 3.12 type statement: lazy,
                             # self-documenting, can be generic

@overload
def fetch_user(uid: int) -> User: ...
@overload
def fetch_user(uid: None) -> None: ...
def fetch_user(uid: int | None) -> User | None:
    ...                       # return type depends on arg type:
                            # the one case overloads are for

def pending(tasks: list[Task]) -> Iterator[Task]:
    return (t for t in tasks if not t.done)

Keep overloads to two or three arms, ordered specific to general; a fourth arm says split the function. For generators, callers care about what comes out, so Iterator[T] (or AsyncIterator[T] in async code) is the right surface. Write the full Generator[Yield, Send, Return] only when send or the return value matter. And import Callable, Iterator, and friends from collections.abc, not typing.

One closing note. On 3.14+, deferred annotation evaluation (PEP 649/749) is the default — (Book 1, ch. 3.5) covered the mechanics — so from __future__ import annotations is unnecessary there. Pre-3.14 libraries keep the import; check your requires-python floor first.

3.8 Living with untyped libraries

You will depend on packages without annotations. The escalation ladder: first look for a types-* stub package from typeshed (uv add --dev types-requests and the like). If none exists, write a small local stub and import the real names behind TYPE_CHECKING:

from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from oldsdk import Client  # resolved from stubs/oldsdk.pyi

# pyproject.toml — scoped, never global:
[[tool.mypy.overrides]]
module = "oldsdk.*"
ignore_missing_imports = true

The per-module override is the discipline. A global ignore_missing_imports = true also silences your own misspelled imports — how Any gets in through the back door. Going the other way, when your library ships annotations, drop an empty py.typed marker next to __init__.py (PEP 561) so downstream checkers trust them.

Review red flags — typing edition.
✗ cast(list[LineItem], cast(Any, rows)) — chained casts patching over a bad boundary. Fix: model the boundary once (3.4); prefer a TypeIs predicate.
✗ # type: ignore with no error code — silences every error on the line, present and future. Fix: always use a code, as in # type: ignore[attr-defined]; warn_unused_ignores sweeps the stale ones.
✗ Any leaking inward from an untyped call — one unannotated boundary function turns its call tree into Any. Fix: annotate the boundary function's return; add stubs or a local .pyi for the library.

Chapter 4Data at the Boundaries

"Should this be a pydantic model?" is the most common modeling question in modern Python. The wrong default costs twice: slow where you did not need validation, unsafe where you did. Chapter 3.4 gave the decision rules; this chapter is the practice.

4.1 The rule and its reason

The rule: dataclass inside, pydantic ubiquitous or msgspec niche at the edges. The reason has a number. Constructing a pydantic v2 model is about 6.5× slower than constructing a dataclass, because construction is validation — every field is checked and coerced on the way in. Pay that cost where untrusted data crosses in; inside, values are known-good and coercion buys nothing.

pydantic v2 is itself the pattern to notice: all validation runs in pydantic-core, a Rust library, while the Python layer assembles schemas from your type hints. The split made v2 5–50× faster than v1 — and it is still the slow side of this chapter's rule. Compiled core, ergonomic Python surface: polars is built the same way, and Litestar is the framework that absorbed the lesson.

4.2 dataclass, done right

Stop hand-writing data-holder classes. An __init__ that only assigns its arguments, with the __repr__ and __eq__ behind it, is code a decorator generates better. The same LineItem, both eras:

Then · 2020
class LineItem:
    def __init__(
        self, sku: str, qty: int,
        unit_price: float,
    ) -> None:
        self.sku = sku
        self.qty = qty
        self.unit_price = unit_price

    def __repr__(self) -> str:
        return (
            f"LineItem({self.sku!r},"
            f" {self.qty},"
            f" {self.unit_price})"
        )

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, LineItem):
            return NotImplemented
        return (
            (self.sku, self.qty)
            == (other.sku, other.qty)
            and self.unit_price
            == other.unit_price
        )
Now
from dataclasses import dataclass

@dataclass(slots=True, kw_only=True)
class LineItem:
    sku: str
    qty: int
    unit_price: float

The Now side is not a shorter spelling of the same work; the work is gone. slots=True drops the per-instance __dict__; kw_only=True forces call sites to name arguments — cheap insurance against a swapped qty/unit_price.

Two more moves cover the rest: frozen=True for values that should not change after construction, and field(default_factory=...) for any mutable default — the classic bug from 2.4. A @property still earns its keep for a computed attribute like total: behavior, not storage.

from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Order:
    id: str
    items: list[LineItem] = field(default_factory=list)

    @property
    def total(self) -> float:
        return sum(i.qty * i.unit_price for i in self.items)

4.3 pydantic at the boundary

(Book 1, ch. 6.2) introduced the static-vs-runtime split; here is the usage pattern. Parse, don't validate ad hoc: turn raw bytes into a typed model once, at the edge, and let the rest of the program trust it. The webhook handler:

from pydantic import BaseModel

class LineItemIn(BaseModel):   # the payload's shape,
    sku: str                   # not the domain's
    qty: int
    unit_price: float

class OrderIn(BaseModel):
    order_id: str
    items: list[LineItemIn]

def handle_webhook(raw: bytes) -> Order:
    payload = OrderIn.model_validate_json(raw)  # the edge
    return Order(
        id=payload.order_id,
        items=[
            LineItem(
                sku=i.sku, qty=i.qty,
                unit_price=i.unit_price,
            )
            for i in payload.items
        ],
    )

The one call that matters is model_validate_json(raw). A malformed payload raises here, every bad field named — not three functions later as a KeyError. Past that line, the core sees only the frozen dataclasses from 4.2, and no validation code runs again.

BaseModel is for shapes you name. For a bare list or scalar, TypeAdapter parses it directly — TypeAdapter(list[LineItemIn]).validate_json(raw) — with the same error quality.

The edge is also where configuration enters. pydantic-settings reads environment variables into a typed model at startup; SecretStr keeps credentials out of reprs and logs:

from pydantic import SecretStr
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    api_key: SecretStr   # reprs as '**********'

settings = Settings()    # reads env at startup — the edge

Fail-fast at startup is the point: a missing API_KEY raises before the server binds a port, not on the first request. The full secrets treatment is chapter 7.5's.

4.5 Serialization out

Data crosses the boundary going out too — responses, fixtures, snapshots. Normalize models back to builtins with the same library that parsed them in. On a BaseModel that is model_dump(); a TypeAdapter handles anything, including dataclasses:

from pydantic import TypeAdapter

adapter = TypeAdapter(Order)   # dataclasses included

def order_response(order: Order) -> dict:
    return adapter.dump_python(order, mode="json")

mode="json" is the detail that matters: datetimes, decimals, and UUIDs come out as JSON-safe builtins, so the result stays stable across refactors of the model itself. Chapter 6.2 builds snapshot testing on exactly this — a normalized dict is what a snapshot can diff.

Chapter 5Errors and Structure

How a codebase fails is its clearest timestamp. The 2020 habits — the bare except, the re-raise that severs its history, the manager class hiding every wire — are still everywhere. This chapter is the 2026 discipline for both halves: exceptions that keep their history, and modules that keep their shape.

5.1 EAFP, still

EAFP is still the Pythonic default: try the operation, handle the failure. LBYL earns its keep exactly where the check is the logic — parsing, probing a mapping — because dict.get answers "present or not?" in one call.

# EAFP: attempt, then handle what you expect.
def parse_points(raw: str) -> int:
    try:
        return int(raw)
    except ValueError:   # specific, and the try stays minimal
        return 0

# LBYL: the check IS the logic here.
def owner_of(meta: dict[str, str]) -> str:
    return meta.get("owner", "unassigned")

Two rules hold either way: keep the try block to the line that can fail, and name the exception you expect. A wider net catches bugs you meant to see; a bare except: swallows even KeyboardInterrupt.

5.2 Always raise ... from

When a layer translates an exception into its own vocabulary, chain it: raise RepoError(...) from exc. The from sets __cause__, and the traceback tells the whole story. The same failure, both ways:

Then · 2020
Traceback (most recent call last):
  File "app.py", line 4, in load
    row = self.db.one(uid)
KeyError: 42

During handling of the above exception,
another exception occurred:

Traceback (most recent call last):
  File "app.py", line 6, in load
    raise RepoError("lookup failed")
RepoError: lookup failed
Now
Traceback (most recent call last):
  File "app.py", line 4, in load
    row = self.db.one(uid)
KeyError: 42

The above exception was the direct cause
of the following exception:

Traceback (most recent call last):
  File "app.py", line 6, in load
    raise RepoError("lookup failed") from exc
RepoError: lookup failed

The code differs by eight characters — from exc — and the second panel's "direct cause" line is what they buy: a deliberate translation, not a handler that crashed mid-recovery.

The escape hatch is from None: it hides the chain on purpose, for the rare case where the cause is noise. A clean usage error at a CLI boundary need not expose an internal KeyError. Leave a comment when you use it.

5.3 Context without wrapping

Often the failure is already the right exception; it is just missing context. Python 3.11 added add_note for exactly this: attach what you know, re-raise what you caught. No wrapper type, no re-invented traceback.

def import_batch(rows: list[dict]) -> list[Task]:
    tasks = []
    for i, row in enumerate(rows):
        try:
            tasks.append(parse_task(row))
        except ValueError as exc:
            exc.add_note(f"row {i}: {row.get('title')!r}")  # 3.11+
            raise
    return tasks

The note prints under the exception's message in the traceback. Retry loops and batch imports are the natural home.

ExceptionGroup and except*, same release, are for errors that arrive in bulk: a TaskGroup fan-out (Book 1, ch. 5) can fail three of ten tasks at once, and you need all three. That is the only case that earns them:

import asyncio

async def refresh_all(repos: list[Repo]) -> None:
    try:
        async with asyncio.TaskGroup() as tg:
            for repo in repos:
                tg.create_task(repo.sync())
    except* RepoError as group:   # 3.11+; bulk errors only
        for exc in group.exceptions:
            log.warning("sync failed", exc_info=exc)

Everywhere else, plain except on a specific type remains the whole toolkit. Catch an ExceptionGroup directly only to filter it programmatically — group.split(...) — never as a habit.

5.4 Result types: why we don't

The minority view, in its strongest form: make failure a return value — Ok or Err — and the type checker can prove every caller handled it. Libraries like result and returns niche implement exactly this, and in languages without exceptions the argument wins.

Verdict: Result types.
Our default: exceptions for the exceptional; None or a sentinel for expected-absent.
Also reasonable: a Result monad in a codebase that commits to it — returns is maintained, and checker-verified handling is a real property.
Why: no stdlib traction, and the idiom fights the language. Every boundary with ordinary Python — stdlib calls, framework hooks — unwraps back into exceptions anyway, so the proof holds only inside the walled garden.

In practice: fetch_user raises LookupError when a uid should exist, and returns None when absence is an expected answer — a cache probe, a search with no hits. The signature says which is which: -> User versus -> User | None.

5.5 Small modules, Protocol seams

The manager class is where 2020 code hides its wiring. A TaskManager that opens its own database and sends its own mail can be tested only with both running. The 2026 shape: a dataclass holds the data, functions carry the behavior, and the Protocol from 3.3 is the seam where each collaborator plugs in.

Then · 2020
class TaskManager:
    def __init__(self, dsn: str):
        self.db = Db(dsn)
        self.smtp = Smtp()

    def create(self, title: str) -> int:
        return self.db.insert(title)

    def complete(self, tid: int) -> None:
        self.db.set_done(tid)
        task = self.db.get(tid)
        self.smtp.send(
            task.owner, task.title
        )
Now
from dataclasses import dataclass
from typing import Protocol

@dataclass(slots=True)
class Task:
    title: str
    points: int
    owner: str
    done: bool = False

class Store(Protocol):
    def insert(self, t: str) -> int: ...
    def set_done(self, tid: int) -> None: ...
    def get(self, tid: int) -> Task: ...

class Mailer(Protocol):
    def send(self, to: str, m: str) -> None:
        ...

def create(db: Store, title: str) -> int:
    return db.insert(title)

def complete(
    db: Store, mail: Mailer, tid: int
) -> None:
    db.set_done(tid)
    task = db.get(tid)
    mail.send(task.owner, task.title)

The Now side is longer because the wiring the manager hid in __init__ is now written out in every signature — that is the cost, and also the point. A test passes fakes for Store and Mailer; swapping one database for another touches a call site, not a class hierarchy. Dependency injection, no framework.

In library modules, __all__ declares the public API and a leading underscore marks everything private. Circular imports get fixed structurally — move the shared names to a third module, or import for checkers only, behind TYPE_CHECKING with a string annotation:

from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from orders import Order  # checkers see it; runtime doesn't

def discount(order: "Order") -> float: ...

Function-local imports as a habit are the tell that a cycle is being hidden, not fixed. On packaging: an empty __init__.py stays the default. Namespace packages (PEP 420) — directories with no __init__.py at all — are for plugin systems and distributions split across wheels. If neither is your situation, a missing __init__.py is a bug, not a choice.

5.6 Lazy imports (3.15)

PEP 810 ships in 3.15 — release candidate today, final October 2026 — and adds a lazy modifier to imports:

# 3.15 (PEP 810) — RC-era; final October 2026
lazy import numpy as np   # module scope only

def summarize(values: list[float]) -> float:
    return float(np.mean(values))  # np loads here, on first use

The restrictions are the point: module scope only, never inside functions or try blocks, and no star imports. For library authors the statement retires the __getattr__ boilerplate that kept heavy optional dependencies out of import time — the PEP cites Instagram's measurements of 50–80% faster CLI startup. Until 3.15 is your floor, that __getattr__ pattern remains the way to do it.

5.7 Docstrings and comments

Pick a docstring convention and let Ruff's pydocstyle rules enforce it; Google style is the de-facto default for application code, NumPy style holds scientific Python. The real shift is what the docstring says. With annotations on the signature, a docstring that restates types is noise; its job is the semantics the signature cannot carry — which errors, which units, which guarantees.

Then · 2020
def fetch_user(uid: int) -> User:
    """Fetch a user.

    Args:
        uid: An int, the user id.

    Returns:
        A User object.
    """
Now
def fetch_user(uid: int) -> User:
    """Fetch a user, or raise LookupError.

    Deleted accounts raise instead of
    returning a tombstone: callers treat
    absence as exceptional, never as data.
    """

The annotations already said uid: int and -> User; the Now side spends its lines on what raises, and on why absence never comes back as a value.

Comments follow the same rule one level down: explain invariants and intent, never narrate the line below. # retry: the gateway closes idle connections after 60s survives refactors; # loop through the tasks does not. And delete commented-out code outright — git remembers it better than your source file does.

Review red flags — error handling.
✗ except: — bare, it catches KeyboardInterrupt, SystemExit, and every bug in the block. Fix: name the exception you expect; except Exception is the floor, not the goal.
✗ raise RepoError("lookup failed") inside an except block — severs the cause, and the traceback reads as an accident. Fix: raise RepoError(...) from exc (5.2).
✗ except Exception in library code — catches the caller's bugs along with your own. Fix: let it propagate, or translate to your own exception type with from exc.

Chapter 6Testing That Scales

In 2020 the average suite was unittest classes, HTTP patched out of existence, and a coverage badge nobody trusted. This chapter is the 2026 practice — fixtures, snapshots, async, fakes — the suite a flagship library would recognize as normal.

6.1 pytest house style

Write test functions, not TestCase classes. (Book 1, ch. 6.6) introduced pytest ubiquitous; here is the house style at scale. No base class, no setUp, no self.assertEqual — a plain assert gets a full diff on failure. Shared state comes from fixtures: functions that build whatever a test asks for by name.

Then · 2020
import unittest

class TestOrder(unittest.TestCase):
    def setUp(self) -> None:
        self.order = Order(
            id="o-1",
            items=[
                LineItem(sku="a", qty=2,
                         unit_price=10.0),
            ],
        )

    def test_total(self) -> None:
        self.assertEqual(
            self.order.total, 20.0
        )
Now
import pytest

@pytest.fixture
def order() -> Order:
    return Order(
        id="o-1",
        items=[
            LineItem(sku="a", qty=2,
                     unit_price=10.0),
        ],

    assert order.total == 20.0

Same order, same assertion; the plumbing changed. The fixture is one function any test can request by name, instead of a setUp every sibling inherits whether it wants the object or not.

Three more idioms cover the daily work. parametrize runs one test over a table of cases; give it readable ids, because those strings are what a failure prints. def test_report_written(tmp_path: Path) -> None:
    out = tmp_path / "report.parquet"
    write_report(orders, out)
    assert out.exists()

def test_api_base(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("API_BASE", "http://localhost:9")
    assert get_settings().api_base.startswith("http")

6.2 Snapshot testing went mainstream

Snapshot testing — assert the output equals a recorded copy — used to mean separate files that drifted out of review. The 2026 default is inline-snapshot common: the snapshot lives inside the test source, and pytest --inline-snapshot=fix rewrites the file when the output legitimately changes. pydantic officially recommends it and runs its own suite on it. The update lands in code review like any other change, which is the whole point.

Snapshot normalized data, not objects. Normalize the model to builtins first — the TypeAdapter(...).dump_python move from 4.5 — then snapshot that, here against the webhook handler from chapter 4:

from inline_snapshot import snapshot

def test_handle_webhook() -> None:
    raw = (
        b'{"order_id": "o-1", "items": '
        b'[{"sku": "a", "qty": 2, "unit_price": 10.0}]}'
    )
    order = handle_webhook(raw)
    result = TypeAdapter(Order).dump_python(order, mode="json")
    assert result == snapshot(
        {
            "id": "o-1",
            "items": [{"sku": "a", "qty": 2, "unit_price": 10.0}],
        }
    )

You write snapshot() empty, run pytest --inline-snapshot=fix, and the expected dict appears in the source. Dynamic fields — timestamps, generated ids — come from dirty-equals, pydantic's companion library; each value asserts a property instead of an exact match, inside the same snapshot:

from datetime import timezone
from dirty_equals import IsJson, IsNow

assert event == snapshot(
    {
        "type": "order.created",
        "sent_at": IsNow(tz=timezone.utc),  # aware, close to now
        "payload": IsJson(),  # a string that parses as JSON
    }
)

One gotcha: bare IsNow() compares against a naive datetime.now(). With the aware timestamps 2.7 recommends, pass tz=timezone.utc as above.

Verdict: inline-snapshot vs syrupy.
Our default: inline-snapshot — snapshots in the test source, updated by rewriting the file, reviewable in the diff.
Also reasonable: syrupy, which stores snapshots in separate files — still the pick for large or text-heavy snapshots (Textual's terminal-UI tests are syrupy-based).
Why: for the common case — a dict or model of modest size — the snapshot next to the assertion reviews better than a second file. pydantic's endorsement settled the default. Big payloads are the exception syrupy owns.

6.3 Three hypothesis properties worth writing

Property-based testing is real and niche. An ACM empirical study from October 2025 found it used mainly for roundtrip properties, oracle tests, and math or optimization code — PyTorch and NumPy are the flagship users. Skip the methodology; keep the three properties that pay for themselves on ordinary code: roundtrip, invariant, never-crashes.

from hypothesis import given, strategies as st
from pydantic import ValidationError

line_items = st.builds(
    LineItemIn,
    sku=st.text("abc123-", min_size=1),
    qty=st.integers(min_value=1),
    unit_price=st.floats(min_value=0.01, max_value=999.99),
)

# 1. Roundtrip: serialize, parse, get the same value back.
@given(item=line_items)
def test_roundtrip(item: LineItemIn) -> None:
    raw = item.model_dump_json()
    assert LineItemIn.model_validate_json(raw) == item

# 2. Invariant: holds for every input, not just your examples.
@given(items=st.lists(line_items, max_size=8))
def test_total_never_negative(items: list[LineItemIn]) -> None:
    payload = OrderIn(order_id="o-1", items=items)
    order = handle_webhook(payload.model_dump_json().encode())
    assert order.total >= 0

# 3. Never crashes: arbitrary input fails politely or not at all.
@given(raw=st.binary())
def test_parser_never_crashes(raw: bytes) -> None:
    try:
        OrderIn.model_validate_json(raw)
    except ValidationError:
        pass

Note the bounded strategies: unbounded text and floats produce lone surrogates and infinities that no JSON roundtrip survives. Each property is five lines replacing a hand-picked table of edge cases, and hypothesis shrinks any failure to the smallest reproducer and replays it next run.

Verdict: property-based testing.
Our default: the three properties above, on parsers and anything with a roundtrip.
Also reasonable: no PBT at all — most application suites live without it, and example-based tests carry CRUD code fine.
Why: the three properties are cheap and find real bugs — the third one is how you learn your parser raises something other than ValidationError on malformed bytes. The full methodology is a larger commitment than app code repays.

6.4 Async tests

Async tests need a plugin; pick one and configure it once. For application code the default is pytest-asyncio in strict mode, with one module-level marker. Set asyncio_mode = "strict" in pyproject. The "auto" mode, which collects every async test without markers, is convenient and debated; explicit markers keep collection honest:

import pytest

pytestmark = pytest.mark.asyncio   # strict mode, per module

async def test_sync_marks_repo(repo: Repo) -> None:
    await repo.sync()
    assert repo.last_synced is not None
Verdict: pytest-asyncio vs anyio.
Our default: pytest-asyncio for application code — your app picked its event loop at the door, and the tests should run on it.
Also reasonable: the anyio pytest plugin (@pytest.mark.anyio) if you publish a library on anyio or trio — it runs each test on both backends. aiobotocore switched its runner to anyio in 2025, and the httpx/starlette family tests through it.
Why: an app tests on the one loop it ships; a library must prove it runs on the caller's loop. Follow the runner of the ecosystem you ship into.

6.5 Fakes over mocks

Mock what you own, fake what you don't. Deep mocks of a third-party library test your guesses about its internals, and they break when those internals move. The modern HTTP example is the cleanest: httpx takes a transport, so a fake server plugs in at the boundary instead of a patch reaching into requests:

Then · 2020
from unittest.mock import patch

def test_fetch_user() -> None:
    with patch("requests.get") as get:
        resp = get.return_value.json
        resp.return_value = (
            {"id": 1, "name": "Ana"}
        )
        assert fetch_user(1).name == "Ana"
Now
import httpx

def test_fetch_user() -> None:
    def handler(
        req: httpx.Request,
    ) -> httpx.Response:
        return httpx.Response(
            200,
            json={"id": 1, "name": "Ana"},
        )

    transport = httpx.MockTransport(handler)
    client = httpx.Client(
        transport=transport,
        base_url="https://api.example.com",
    )
    user = fetch_user(client, 1)
    assert user.name == "Ana"

The Now side exercises the real client — URL joining, response parsing, error handling — and no request leaves the process. The Then side asserts that a MagicMock was configured to behave the way you hope requests behaves. This works because fetch_user takes the client as an argument: the dependency-injection habit from 5.5 is what makes fakes possible at all.

Companions cover the rest: respx mocks httpx at the routing layer when you want URL matching instead of client injection. time-machine (or freezegun) fakes the clock — datetime.now() buried in business logic is otherwise untestable. When you genuinely must mock, patch at the use site: patch("orders.billing.stripe.charge"), where your code looks the name up, never patch("stripe.charge") at the source.

6.6 Coverage without worship

Measure coverage on every run; gate on the diff, not the total. A global percentage rewards tests that execute lines without asserting anything, and punishes deleting dead code. The honest gate is changed lines only: coverage emits the report, diff-cover fails the build if the patch itself is undertested:

$ uv run pytest --cov=orders --cov-report=xml
$ uv run diff-cover coverage.xml --fail-under=80

Around 80% on the diff is the working number: high enough to stop backsliding, low enough that nobody writes a test for a __repr__.

Verdict: 100% coverage.
Our default: the changed-lines gate above for application code.
Also reasonable: enforced 100%, the rule FastAPI, httpx, and Litestar all run in CI.
Why: those are libraries with an enormous downstream blast radius — every line is somebody's production code, so no line ships untested. An app's blast radius is its own deploy; the last 20% of lines cost the most to cover and matter the least. Gate the diff; spend the savings on better tests.

6.7 The declining and the advanced

Two tools to stop reaching for, one to know about. tox and nox are declining for most projects. Multi-version testing now lives in the CI matrix from 1.7; locally, uv run --python 3.12 pytest covers the same ground — you get 90% of tox's value by wrapping uv. The flagship libraries agree: nox and tox are simply absent from their repos. nox survives where programmatic sessions genuinely help, Google's client libraries being the standing example. If you cannot name the session logic you need, the matrix is your answer.

Mutation testing is the advanced, optional extra. mutmut rewrites your code in small ways — flipping a comparison, deleting a line — and checks that some test fails each time; survivors are assertions your suite never actually makes. Run it incrementally on core logic only, with a kill threshold in the 75–85% range, and treat it as an occasional audit, not a CI gate. It answers "would my tests notice a real bug" better than coverage does, at a cost most suites should not pay on every push.

7.2 Versions

Libraries get semver, applications get calver, and the git tag is the only version string in the repo. A library's version is an API contract: MAJOR.MINOR.PATCH tells the resolver what an upgrade can break. An app's version is a label — pip and black style 2026.8 stamps are enough for things nobody depends on.

Either way, do not store the number in pyproject.toml or a version.py. hatch-vcs derives it from the git tag at build time, so the tag is the single source of truth and the version-bump commit disappears:

[build-system]
requires = ["hatchling", "hatch-vcs"]
build-backend = "hatchling.build"

[project]
name = "orders"
dynamic = ["version"]   # no version = "..." line anymore

[tool.hatch.version]
source = "vcs"

Releasing is then git tag v1.4.0 && git push --tags — also the trigger for 7.3's workflow. Built version, PyPI version, and git tag can no longer drift apart.

Verdict: semver vs calver.
Our default: semver for libraries, calver for applications and CLIs.
Also reasonable: one scheme for everything — many teams calver their libraries too, and the consistency argument is honest.
Why: a library version carries meaning a resolver can act on; an app version only needs to be sortable. Consistency matters more than the scheme — pick one, automate it with tags, and never hand-edit a version string.

7.3 Trusted publishing, or don't publish

Publish from CI with trusted publishing, or do not publish from CI at all. The 2020 pattern — a long-lived PyPI API token in repository secrets — is now the standard way packages get hijacked. Trusted publishing replaces it with OIDC: GitHub mints a short-lived token for one job run, PyPI verifies it against the publisher you registered, and nothing long-lived exists to steal. Adoption is already mainstream: over a million files published through trusted publishing by September 2025, and 132,000+ packages with Sigstore attestations by March 2026.

Why this is not optional. The litellm incident is the standing warning: attackers stole the project's publishing token and pushed malicious releases to one of the most-installed AI packages. A stolen OIDC token dies with the job run; the stolen API token was valid until someone noticed.

The publish job extends the CI workflow from 1.7. Version tags join the trigger, and the new job runs after the tests pass, inside a GitHub environment that requires reviewer approval:

# 1.7's trigger, extended so version tags fire the workflow
on:
  push:
    branches: ["**"]
    tags: ["v*"]
  pull_request:

jobs:
  # the test job from 1.7 stays unchanged
  publish:
    needs: test
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment:
      name: pypi          # configure required reviewers here
    permissions:
      id-token: write     # lets this job mint an OIDC token
    steps:
      - uses: actions/checkout@<full-commit-sha>
      - uses: astral-sh/setup-uv@<full-commit-sha>
        with:
          enable-cache: true
      - run: uv build
      - uses: pypa/gh-action-pypi-publish@<full-commit-sha>

Three details do quiet work here. Every action is pinned to a full commit SHA, not a movable tag — non-negotiable on this job, and 7.5's zizmor check nags until the rest of the workflow matches. The pypi environment gates the job on human approval, so a tag proposes a release rather than executing one. And the publish action has generated Sigstore attestations automatically since v1.11. The one-time setup lives on PyPI: register repo, workflow, and environment as a trusted publisher.

7.4 The 2026 Dockerfile

The modern image is two stages and no pip. The builder copies the uv binary from its own image and syncs the lockfile into a virtualenv; the runtime stage inherits only that venv. Every line earns its place:

# syntax=docker/dockerfile:1

7.5 Dependency security

Security in 2026 is a set of small tools in CI, not a posture. The baseline is auditing the lockfile for known vulnerabilities on every run:

- run: uv audit   # checks uv.lock for known vulnerabilities

uv audit and the PyPA's pip-audit do the same job; run whichever matches your toolchain. The lockfile itself is the second layer: uv.lock records hashes by default, and --locked makes CI fail rather than install a tampered artifact. For update automation, use Renovate common — Dependabot's pip ecosystem cannot read uv.lock; Renovate has native uv support. For a cooling-off window against just-published malware, uv pip compile --exclude-newer pins resolution to packages older than a date — an optional extra layer, not a default.

On the code side, skip bandit and add "S" to the Ruff select list from 1.6 — the same checks, in the tool you already run. semgrep earns its place when your organization needs its own rules. And run zizmor on your workflows: it flags unpinned actions and template injection, the weaknesses behind the GhostAction and Shai-Hulud workflow compromises.

4.3 showed the shape of settings at the edge; here is the policy. Settings load once at startup from the environment. A .env file is for development only: listed in .gitignore, never committed — git history is forever. Production values come from the platform's real environment or secret store. And every credential is a SecretStr, so a stray print(settings) or log line shows asterisks instead of the key:

Private indexes close the last hole. pip's --extra-index-url queries every index and installs the best version found anywhere — the exact shape of a dependency-confusion attack. uv's first-match strategy is the inverse: the first index that has the package wins, so a public package can never shadow your private one. Belt and suspenders: mark the internal index explicit = true so it serves only packages that name it:

Chapter 8Running It: Logs, Traces, Speed

Writing the code was the first seven chapters. Now it has to run: emit logs you can query, traces that cross service boundaries, and responses fast enough that nobody files a ticket. The 2026 defaults for all three are cheap to adopt — structured logs, OpenTelemetry, and profiling before optimizing.

8.1 The logging policy

Logging splits cleanly by what you ship. A library emits; an application configures. The one unforgivable sin is mixing them up: a library that calls basicConfig hijacks the application's handlers and format. Inside a library, emit only:

# inside a library — emit, never configure
import logging

log = logging.getLogger(__name__)

# in the package __init__.py, once:
logging.getLogger("orders").addHandler(logging.NullHandler())

The NullHandler silences the "no handlers found" warning; where records go is the application's decision. 5.3's log.warning(..., exc_info=exc) is this pattern — stdlib logging stays the library default, full stop.

An application owns its logging end to end, and the 2026 default for that is structlog common. The evidence line: Airflow 3.1 switched all of its logging to structlog. The reason: your logs are data. A processor pipeline turns every event into structured JSON that log systems can query, instead of regex fodder from 2009.

Verdict: loguru.
Our default: structlog for services; stdlib logging for libraries.
Also reasonable: loguru for scripts and small apps — the developer experience is genuinely good, and logger.catch is a delight.
Why: one global logger, an InterceptHandler needed to unify stdlib records, and no processor pipeline. Those costs land exactly when a script grows into a service, so start services on structlog.

8.2 structlog in practice

A structlog event is a dict flowing through a pipeline of processors. Each one adds or transforms keys; the last one renders. Configure once, at startup. The renderer switch is one field on the Settings class from 4.3 and 7.5: debug: bool = False.

import logging
import sys

import structlog

if settings.debug:  # pretty console in dev
    renderer = structlog.dev.ConsoleRenderer(colors=True)
else:               # JSON in prod
    renderer = structlog.processors.JSONRenderer()

shared = [
    structlog.contextvars.merge_contextvars,
    structlog.stdlib.add_log_level,
    structlog.processors.TimeStamper(fmt="iso"),
]

structlog.configure(
    processors=[
        *shared,
        structlog.stdlib.ProcessorFormatter.wrap_for_formatter,
    ],
    logger_factory=structlog.stdlib.LoggerFactory(),
    wrapper_class=structlog.stdlib.BoundLogger,
    cache_logger_on_first_use=True,
)

formatter = structlog.stdlib.ProcessorFormatter(
    foreign_pre_chain=shared,  # stdlib records join the pipeline
    processors=[
        structlog.stdlib.ProcessorFormatter.remove_processors_meta,
        renderer,
    ],
)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(formatter)
logging.basicConfig(handlers=[handler], level=logging.INFO)

Two pieces do the heavy lifting. LoggerFactory routes structlog events through stdlib, and ProcessorFormatter with foreign_pre_chain runs the same pipeline over records from httpx, SQLAlchemy, and every library doing the 8.1 thing. One format out, no matter who logged.

Per-request context goes in contextvars, not in every call:

from structlog.contextvars import bind_contextvars

bind_contextvars(request_id=request.id)  # once, in middleware

log = structlog.get_logger()
log.info("order.placed", order_id=order.id)
# every record this request now carries request_id

8.3 Telemetry without vendor lock

Logs are one signal; traces and metrics are the other two. OpenTelemetry common is the standard for all three — tracing and metrics stable for years, logs stable since 2025 — and its Python agent needs no code changes at all:

The OTLP environment variables are the lock-in insurance: point them at Jaeger, Grafana, or your next vendor by changing an endpoint, not a codebase.

8.4 Profile first

Speed work starts with a measurement, not a hunch. The first tool is py-spy: a sampling profiler that attaches to a running process — production included — and writes a flamegraph, with zero code changes:

$ py-spy record -o profile.svg --pid 4821   # live process
$ py-spy top --pid 4821                     # live top(1)

$ python -m cProfile -o orders.pstats -m orders.worker
$ uvx snakeviz orders.pstats                # local deep dive

A true story in one act. An orders API is slow; the team's guess says JSON serialization, so someone reaches for orjson. py-spy says otherwise:

Then · 2020
import json
import re

def normalize(code: str) -> str:
    return re.sub(r"[^A-Z0-9]", "", code)

def render_orders(rows: list[dict]) -> bytes:
    out = [
        {
            "id": r["id"],
            "code": normalize(r["code"]),
        }
        for r in rows
    ]
    return json.dumps(out).encode()
Now
import json
import re

# flamegraph: 70% of request time was
# re.compile, inside normalize(), per row.
# module scope:
CLEAN = re.compile(r"[^A-Z0-9]")

def normalize(code: str) -> str:
    return CLEAN.sub("", code)

# render_orders unchanged.

The guess would have optimized the wrong quarter of the request. The flamegraph showed 70% of request time inside re.compile — the pattern was recompiled on every row — and the fix was one module-level constant. orjson never shipped.

8.5 The usual wins (and the usual wastes)

Once a profile points, these are the fixes that usually pay. For new data code, polars' lazy frames over pandas row loops. Databricks' comparison puts polars around 10× faster on joins and groupbys, on roughly an eighth of the memory — and the lazy query plan is the actual win. In hot JSON paths, orjson — after the profile says so, not before (8.4). And before you reach for Redis, reach for functools.cache:

import functools

@functools.cache
def load_tax_table(region: str) -> dict[str, float]:
    ...  # process-local, free, and usually enough

resp = httpx.get(url, timeout=10)  # explicit, every call

That last line is a standing rule: timeout= on every network call, no exceptions. requests waits forever by default, which means one hung dependency can pin every worker you have.

The usual wastes: string formatting, micro-loop tweaks, and anything unprofiled. And do not hand-roll what polars, pydantic-core, and numpy already do in Rust or C — your Python loop will not beat their query optimizer. One emerging item to watch: free-threaded CPython (3.13+) makes threads viable for CPU-bound work where today only ProcessPoolExecutor is; check whether your dependencies support it before planning around it.

Review red flags — performance.
✗ requests.get(...) inside async def — a sync call blocks the whole event loop for its duration. Fix: httpx.AsyncClient, or asyncio.to_thread for libraries with no async API.
✗ asyncio.gather(...) for structured fan-out — one failing task leaves the rest orphaned. Fix: asyncio.TaskGroup (Book 1, ch. 5), which cancels its siblings and reports every failure.
✗ network calls without timeout= — an unbounded wait dressed up as a call. Fix: pick a number, any number, and pass it.

The data layer, in full:

# tasks/models.py
import sqlite3
from datetime import datetime
from typing import Dict, List

SCHEMA = (
    "CREATE TABLE IF NOT EXISTS tasks ("
    "id INTEGER PRIMARY KEY, title TEXT,"
    " points INTEGER, owner TEXT, done INTEGER)"
)


class TaskStore:
    """Every question the API asks the database."""

    def __init__(self, dsn: str = "tasks.db"):
        self.conn = sqlite3.connect(dsn)
        self.conn.execute(SCHEMA)

    def add(self, title, points, owner):
        self.conn.execute(
            "INSERT INTO tasks (title, points, owner, done)"
            " VALUES ('%s', %d, '%s', 0)" % (title, points, owner),
        )
        self.conn.commit()

    def get(self, task_id):
        cur = self.conn.execute(
            "SELECT * FROM tasks WHERE id = %d" % task_id
        )
        row = cur.fetchone()
        if row is None:
            raise KeyError(task_id)
        return self._to_dict(row)

    def open_tasks(self) -> List[Dict]:
        cur = self.conn.execute("SELECT * FROM tasks WHERE done = 0")
        return [self._to_dict(r) for r in cur.fetchall()]

    def _to_dict(self, row) -> Dict:
        keys = ("id", "title", "points", "owner", "done")
        return dict(zip(keys, row))


def summary(tasks: List[Dict]) -> str:
    # weekly digest, mailed every Monday
    report = "Open tasks as of %s\n" % datetime.utcnow()
    for t in tasks:
        report += "- %s (%s, %d pts)\n" % (
            t["title"], t["owner"], t["points"],
        )
    return report


def tag(task: Dict, labels: List[str] = []) -> Dict:
    labels.append(task["owner"])
    task["labels"] = labels
    return task

C.4 The checklist

Print this page. It is the book as a merge-time checklist — the defaults, phrased as what you verify before you hit the button.

  • Project setup. pyproject.toml is the only config file. uv.lock is committed. src layout for anything that ships. Ruff and mypy run in CI on every pull request.
  • Code. Builtin generics and X | None. pathlib at the boundaries. f-strings. None sentinels, never []. isinstance, never type() ==. join, never a += loop.
  • Typing. Every public function annotated. Decorators use ParamSpec. No type: ignore without an error code. No Any leaking past a boundary.
  • Data. pydantic parses at the edge; dataclasses inside. SQL takes parameters, never formatting. Secrets are SecretStr, loaded from the environment at startup.
  • Errors. Catch what you expect, in the smallest try that works. Translate with raise ... from exc. No bare except, anywhere, ever.
  • Tests. pytest functions with fixtures. Fakes at the boundary — MockTransport, not patched internals. Snapshots of normalized data. diff-cover gates the patch at ~80%.
  • Shipping. The git tag derives the version. Publishing is trusted (OIDC), never a stored token. Actions pin to a full SHA. uv audit and zizmor run in CI. The image is two stages and does not run as root.
  • Running. structlog emits JSON in prod, pretty console in dev. Every network call carries a timeout=. Nobody optimizes without a profile.

The 2020 listing was not bad work. It was 2020 work, and it passed every review 2020 gave it. What changed is the baseline: six years of defaults, each one cheap to adopt and expensive to skip. You now have all of them, and one table to check them with.
