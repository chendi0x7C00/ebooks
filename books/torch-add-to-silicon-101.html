01 / THE CAST

Four Layers, One Job Each

From torch.add on CUDA tensors to the arithmetic units — four layers, one job each.

You know the top of this stack: tensors, the dispatcher, the tape, streams as queues. This run covers everything below it.

PyTorch decides what. Op semantics, dispatch — and, the fact most people miss, the entire launch configuration: block size, grid size, vector width, all computed right here on the CPU (section 03). CUDA never hears "add these tensors" — it receives a function handle plus integers PyTorch already chose.

The CUDA runtime (libcudart) is a thin C API layered over the driver. Its job is convenience and bookkeeping: validate arguments, track the current device and context, pack the launch.

The kernel driver (libcuda) is the only software in the picture that touches hardware. It owns the command channels, loads kernel modules, and JIT-compiles PTX for chips the binaries never targeted.

The hardware runs two kinds of worker: streaming multiprocessors (SMs), which execute kernels, and copy engines, DMA units that move bytes while SMs compute. A compiler sidecar supplies the code: nvcc built libtorch's kernels at compile time; NVRTC and Triton build new ones at runtime, on first use.

The map for the rest of the run: sections 02 and 03 are pure PyTorch, 04 is runtime-plus-driver, 05 is silicon, 06 is the compilers.

Takeaway: PyTorch decides what, the runtime packs it, the driver delivers it, the GPU executes it.

02 / DISPATCHER

Dispatch Is Bit Arithmetic

A 64-bit key set per tensor, one union-subtract-index per call — and every grad mode is a different perturbation of the same arithmetic.

Every tensor carries a DispatchKeySet: a single 64-bit word stored in its TensorImpl. Two orthogonal halves — 16 low bits for backends (CPUBit, CUDABit, …), 47 bits above for functionality (Dense, Autograd, Python, …). A runtime key is a pair, never a bit: dispatching on CUDA means (Dense, CUDABit) — the functionality bit picks the layer, the backend bit picks the hardware.

Per call, dispatch is arithmetic, not search. Union the key sets of all tensor arguments (bitwise OR), OR in the thread-local include set, subtract the thread-local exclude set — exclusion wins — then extract the highest-priority bit: enum order is priority, computed as a count-leading-zeros. That bit converts directly into an index into the operator's 137-slot kernel table. No loop, no name matching: one OR, one subtraction, one bit count, one indexed jump.

The three modes you use daily are perturbations of exactly this arithmetic:

  • torch.no_grad() sets a TLS boolean and touches no keys — the Autograd kernel still runs, reads the flag, and skips recording.
  • torch.inference_mode() is real set surgery: the TLS exclude set gains the Autograd keys, ADInplaceOrView drops out of the include set, and tensors created inside are stripped of autograd keys entirely — no version counters, so they error if grad-recording code later touches them.
  • torch.compile includes the Python key, letting a TorchDispatchMode — FakeTensorMode underneath — intercept every op for tracing before the backend sees it.

The priorities interleave on purpose: every Autocast key outranks every Autograd key, so casts get recorded; Python sits below Autograd and ADInplaceOrView, so dispatch modes observe ops after autograd.

Takeaway: one bitset union, one TLS subtraction, one indexed jump — the modes differ only in which piece they disturb.

03 / THE CONFIG

PyTorch Computes the Launch

TensorIterator picks every number CUDA will be told; the kernel body itself is one line of math.

Once dispatch lands on the CUDA kernel for add, TensorIterator does the planning. It broadcasts the shapes, promotes the dtypes, and reorders dimensions so the memory traffic comes out coalesced. Then it picks every number CUDA will be told: 128 threads per block; float4 vector loads (16 bytes per lane) when every operand pointer is 16-byte aligned; 8 elements per thread; 1,024 elements per block; grid = ceil(N / 1,024).

The kernel body is one line — self + alpha * other. All the intelligence lives in the planned numbers. Thread t of block b computes idx = b·128 + t; the vectorized path hands each thread 4 consecutive floats per slot, slots strided by 128 threads, so every warp's loads stay contiguous. Load, add, store — a dumb loop over handed indices. Even the vector width is decided per launch, from the operand pointers' alignment: planned numbers, not baked constants.

>>> N = 4_000_000                     # fp32 elements
>>> grid = (N + 1023) // 1024         # ceil(N / 1,024)
>>> grid, 8 * 128                    # blocks, elements per block
# → (3907, 1024)

Past 2³¹ elements the scheme changes, and not the way the folk story tells it: there is no grid-stride loop. TensorIterator detects that the element count or an operand's byte offsets would overflow 32-bit indices, recursively splits the iteration into sub-iterators, and issues one launch per piece.

Takeaway: launch config is a PyTorch product, computed on the CPU; the kernel is a dumb loop over handed indices.

04 / THE LAUNCH

A Launch Is a Buffer Write

cuLaunchKernel packs your arguments into one contiguous buffer; the GPU fetches the commands itself.

The launch entry point is cuLaunchKernel: a function handle, three grid dims, three block dims, shared-memory bytes, a stream — and your kernel's arguments. The contract worth memorizing: the API packs "all kernel parameters in one contiguous buffer." There is no RPC into the GPU and no shared call stack: the CPU writes bytes, and the GPU later reads those same bytes — your float* pointers travel as plain data.

How the commands physically travel is known — per NVIDIA's open kernel driver and instrumentation research — deliberately not part of the documented contract: the driver translates the launch into command words written into a pushbuffer ring in pinned host memory, then rings a doorbell register; the GPU's front-end fetches the commands by DMA, and reports completion as a writeback the host polls. Back on documented ground, one structural fact survives: a launch is asynchronous by construction, because everything up to the doorbell is the CPU writing its own memory. The stream you know as a queue is the ordering discipline the hardware enforces on those fetched commands.

That CPU-side work is a tax, and it has no official figure. Measurements put it at 1.8–10 µs of CPU time per launch, with one core emitting commands at only 205–450 MiB/s. Run thousands of kernels shorter than their own launches and the GPU starves while a single core saturates in driver code. CUDA graphs are the amortization: record the launches once, replay the whole graph with a single submission, pay the packing once.

Completion flows back the expensive way. The host learns a stream finished by polling — spin, yield, or block, your choice of schedule flags. .item() is the full round trip made visible: allocate a pinned CPU scalar, enqueue a device-to-host copy, drain the stream, only then read the value. Every Python branch on a GPU value pays for one.

Takeaway: a launch is CPU-packaged commands the GPU fetches itself; sync is polling, and .item() is where you pay.

05 / ON THE GPU

Warps and Bytes

The warp is the unit of execution, the 32-byte sector is the unit of memory — the silicon serves one or the other.

Each block from the launch lands on one SM and is immediately partitioned into warps of 32 threads — the SIMT execution unit. A warp has one program counter: each cycle, a warp scheduler issues one instruction for all 32 lanes. Divergent branches serialize — the warp walks each taken path with the other lanes disabled — though predication and independently scheduled warps blunt the cost in practice.

The memory counterpart is the 32-byte sector. A warp loading 32 consecutive 4-byte words touches 128 B — exactly 4 sectors, one transaction each: fully coalesced. Give the same warp a strided access pattern and those 32 words land in 32 different sectors — 32 transactions for the same data, roughly an 8× bandwidth collapse. PyTorch's float4 loads exist precisely to keep every warp access a clean 128 B group.

Why so much machinery per byte: loads are slow, and the machine hides it. Shared memory answers in ~30 cycles, L2 in ~200–500, HBM in ~600 (Hopper microbenchmarks — approximations, not spec). No lane waits alone: the SM keeps many warps resident and issues from another whenever one stalls. That is occupancy — a latency-hiding reservoir, not a score. Past the point where latency is hidden, more resident warps just split registers and instruction-level parallelism thinner, and plenty of kernels run fastest below full occupancy.

One vocabulary correction: the chip never executes PTX. It executes SASS, the native instruction set; PTX is the forward-compatibility contract, JIT-compiled by the driver to SASS whenever no native binary matches the chip (section 06).

Takeaway: the warp is the execution unit, the sector is the memory unit — align your accesses with both.

06 / GO DEEPER

Where Kernels Come From, and Where to Go

Every kernel — built ahead of time or just in time — ends as SASS in a driver module.

The kernels launched above had to be built. nvcc did libtorch's at build time: CUDA C++ → PTX, a virtual ISA designed to span GPU generations → SASS, the native code → a fatbin embedded in libtorch, one SASS copy per architecture in the build list. On a GPU with no matching SASS, the driver JIT-compiles the embedded PTX — the first-run lag people blame on CUDA — caching results on disk (1 GiB default). Triton, the compiler behind torch.compile, is the runtime door: Python → TTIR → LLVM IR → PTX → ptxas → cubin, loaded through the same driver API. From there the launch path is the one you just read.
