TL;DR — the whole design in six lines

  • A bot is the week-one harness — a model calling tools in a loop — relocated to a server that sleeps when idle and wakes on demand with full state, plus its own cloud computer, memory, and event triggers.
  • Thick server, thin clients: exactly one tool, send_user, crosses the client/server boundary.
  • The computer is a disposable Firecracker microVM — boot it on demand, snapshot it, rebuild it. The agent loop never lives on it.
  • Everything expensive is kept out of the context window: files, subagents, tool-name-only discovery, aggressive prompt caching, compaction while the cache is warm.
  • Security is a second model (autoreview) plus product guardrails — not a human approving hundreds of shell commands.
  • Improvement runs on two loops: a daily bug → eval → fix loop, and a monthly train-a-new-model loop.

00 · From harness to bot

A model calling tools in a loop — that's the seed

Everything in this teardown grows out of one small idea that you can build in a week: give a model tools and let it call them in a loop. That simple harness unlocks enormous capability — but it has a fatal flaw. Close your laptop and the process is dead. ▶ 00:21

An always-on agent — Lee calls it a bot — keeps the loop but changes where it lives and when it runs:

It runs on a server, not your terminal. It survives crashes and reboots, and keeps working after you close your laptop.
It owns a computer. A Linux machine in the cloud with its own desktop, files, and browser — where it saves state and builds a memory of how you work.
It knows when to be quiet. Unlike a terminal harness that responds to every message, a bot behaves like a colleague: it works in the background and only reports when there's something worth saying.
It can be woken by more than you. A Slack message, an email, a phone call, a meeting, a scheduled routine — any event can trigger work. ▶ 01:41

The interface got simpler as the system got more capable: it feels like texting a friend, because everyone already knows how to text. And the safety story inverts, too — instead of you approving every shell command (approval fatigue), a separate AI model reviews every command before it runs — the industry calls this autoreview (§09). ▶ 05:02

02 · Why now

Six model changes that made bots possible

Bots are a co-design of product and model. Six training-side changes did the heavy lifting: ▶ 06:15

M1Long-horizon instruction following

Models stop drifting over hours or days of work — provided the harness compacts (summarizes) context well (§08).

M2Hand-off to helpers

Subagents with fresh working memory absorb the token-expensive work and report back — effectively unlimited context.

M3Reliable tool calling

Hallucinated tool calls are mostly a solved problem. You can onboard the model like a new hire: shell, files, then far more powerful tools.

M4Computer use

The model clicks around a screen like a human. Any SaaS or website without an API or MCP server (the standard agent-to-tool protocol) is now usable headlessly.

M5Files as memory

State lives in files the model can grep and search on demand — “what did I do last week?” becomes a lookup, not a hallucination.

M6Learning skills on the job

Show the bot a process once and it encodes it as a skill, memory, or routine it can reuse — markdown files all the way down.

That last one deserves a concrete shape, because under the hood it's all files: ▶ 08:31 a user profile (“texts in lowercase”) injected into every prompt; a working log — a colleague's dated notebook, searchable later; skills as markdown recipes for bespoke processes, written by you or by an ecosystem of authors; and in Grokbot, every tool arrives as a plugin (skills + servers), while routines are cron jobs for prompts — an instruction on a schedule. ▶ 09:20

03 · Everything is a computer

The system at a glance

Here is the whole machine. Triggers wake the agent; a router decides what matters; a durable workflow runs the agent loop; state survives in a database; and a disposable virtual machine is the bot's hands. ▶ 10:03

Two design rules explain almost everything else in this document:

1. The agent loop runs on the server, never on the VM. If the loop lived on the virtual machine, you could never shut that machine down independently — and you will need to. Keep durable state on the server and the VM stays disposable. ▶ 14:53

2. Thick server, thin client. Push agent-code updates to servers instantly — not through an app-store release. Heavy work (transcription, image generation) runs on server hardware. Servers scale with well-understood patterns. ▶ 14:07

04 · Always-on ≠ always-running

The sleep / wake cycle

“Always-on” is a product experience, not an infrastructure fact. Both the server process and the computer are normally asleep — there aren't enough computers in the world to give every user a machine that idles 24/7. What's always-on is the ability to wake up instantly with full memory. ▶ 10:14

The router's two judgment calls

How does a trigger become a turn? Everything — your chat, a Slack ping, a call, a finished background job — lands in one router that deduplicates, decides how events fold into the conversation, and applies a priority: your direct message can interrupt the current agent loop (“actually, move that event to Thursday”); group chats and routine results wait in line. Three or four rapid messages from you get batched into a single turn. ▶ 17:35

Should the bot speak at all? Not everything deserves a ping. The router runs a heuristic — do I need to bug the user about this? — because a colleague who announces every inch of progress is unbearable. Daily status updates, not per-commit narration. Getting this silence/proactivity balance right is still an open problem. ▶ 12:00

05 · The server side

Queue → agent loop → save everything

The server's core is small: commands enter a queue, the agent loop processes one turn (model calls tools until it's done), and every step is written to the database. All the sophistication is in what surrounds that small piece. ▶ 13:32

When you hit send ▶ 15:27

1. Acknowledge instantly. The client confirms your message locally before the server has done anything — no spinner on send.
2. Run the turn. The loop executes, writing each step to the DB as it goes.
3. Notify by subscription. Clients hold subscriptions to server signals; on a change, they fetch the latest state.
4. Dedupe. Retries can duplicate messages; deduping keeps the transcript clean.

This is a distributed-systems exercise in strong vs. eventual consistency — and it leads straight to the most important infrastructure choice.

Durable workflows, not job queues. A job queue that dies mid-task replays the whole task on retry — re-sending the email, re-running the migration. A durable workflow (Grokbot uses Temporal, open source) resumes exactly where it stopped, completed work intact. An agent that runs for hours will hit infrastructure failures; this choice is the difference between an annoyance and a catastrophe. ▶ 16:20

06 · The bot's hands

A disposable Linux computer

The computer is a Firecracker virtual machine — Firecracker is AWS's open-source microVM toolkit, chosen because it makes it trivial to snapshot the machine's state, shut it down, and bring it back exactly as it was. Computers come from a shared pool: when a bot needs hands, it gets a machine of its own — its own screen and browser — in seconds, and hands it back on sleep. ▶ 12:20

Files & shellThe bot saves its work, its notes, its skills. Commands run in a secured environment — not on your laptop.
Chrome + computer useA full browser, driven by clicks, for anything without an API or MCP server.
Virtual desktopsRunning many bots? Each gets its own screen and browser session — no cross-talk between them.
Live viewYou can connect in and watch the bot's screen — or take the wheel yourself.
SnapshotsState persists across sleep/wake; the machine is exactly as the bot left it.
RebuildableZero-day patch? Throw the VM away and rebuild it — durable state lives on the server, so nothing irreplaceable is lost.

07 · The harness

One boundary, cheap ladders, a sparse main agent

The boldest decision in Grokbot's harness: of all the tools the system has, exactly one crosses the client/server boundary — send_user — and it points outward, from the agent to you. Inbound, you just text it; your messages are triggers for the router, not tools. Outbound, send_user is the only tool the client ever has to understand. Every heavy tool — shell, files, cloud agents, screen recording, demos — lives server-side, so new clients (iOS, web, Slack, email) are trivial to build: one integration point. ▶ 18:30

Dynamic tool discovery ▶ 20:01

A context window is finite, and every installed connector (Google Drive, Gmail, YouTube…) brings a pile of tool schemas. Stuff them all in and there's no room left for actual work. The fix — some harnesses call it the tool search tool — is to keep only tool names in the prompt; the model reads a tool's full schema from a file only when it decides to use it.

Always climb the cheapest ladder first ▶ 21:32

Two ladders govern how the bot solves problems without bothering you. The instinct in both: try the cheap and reliable option first; escalate only when it fails — the way a good colleague exhausts their options before interrupting you.

The orchestrator and its helpers ▶ 23:30

The main agent is an orchestrator, and its conversation is kept deliberately sparse. Token-heavy work — hundreds of shell commands, screenshot analysis, long research — is handed to helper subagents, each with its own fresh context and its own skills. Helpers are durable workflows too: if the video helper crashes or eats all its memory, it restarts without losing progress. Only the finished result returns to the main agent's context. That's the trick behind a product that feels like it has infinite context — no model does, but the main conversation never bloats, so you never feel the wall.

Engineering tidbits from the team ▶ 25:14

Don't add or remove tools mid-turn — it busts the prompt cache.
Trim tool descriptions and schemas. Verbose schemas burn the window and the budget.
“Just one tool: shell” is elegant but not always right. If the model spends 90% of its shell calls on one kind of task, build a dedicated tool — it's cheaper and more legible for humans reviewing behavior.
Write error messages for agents, not just humans. “This failed — click here, do X next” helps a model as much as a person. Agent-facing DX is real DX.

08 · Context engineering

Context engineering = harness engineering

Every turn resends the whole conversation plus one new message. Most tokens in an agent workload should therefore be cached tokens — providers discount them heavily. The entire discipline of context engineering is, to a first approximation, don't break the cache. ▶ 27:26

Two rules keep that head stable in practice: prompt sections are hashed and kept in a fixed order — even an A/B-tested prompt change gets its own slot, or you'd bust the cache for every user — and a cache miss is treated as a bug, not bad luck. ▶ 30:37

Compaction is lossy — treat it as an algorithm problem. A 200k-token window eventually fills; the harness must summarize without losing the details that matter. Two rules of thumb from the talk: push long outputs to files (the model reads them on demand), and delegate expensive work (screenshots, big research) to helpers so they never enter the main context at all. And garden constantly — trim dead weight as you go, for cost as much as for recall. The talk's cautionary tale: when the viral personal-agent OpenClaw exploded in January 2026, its unoptimized harness produced constant cache misses — every turn re-read the whole conversation at full price, on flat-rate subscription plans — and taming it took a pile of fixes. This layer is load-bearing. ▶ 31:33

One more trick: when you open the chat and start typing, the server prepares the prompt early to warm the cache — the same way a website prefetches a page on link-hover. Small optimizations like this compound into how long and how smart a bot can be. ▶ 31:06

09 · Trusting a bot with your work

Security: the reviewer is a model

You're handing an autonomous machine your accounts, your browser sessions, and your words. Four guardrails from the talk: ▶ 26:30

Autoreview every command. A separate AI model reviews each shell command before it runs. Paradoxically safer than a human approving hundreds of commands with fatigue-numbed eyes — in blind tests the model now catches more.
Untrusted input is never an instruction. An email in your inbox could be a phishing lure; a webhook could be hostile. Those texts must be treated as data, never folded into the prompt as user intent — the industry is still working hard on prompt-injection defense.
Confirm irreversible actions. Sending email or posting to Slack can't be undone — the client renders an editable draft and waits for approval (FIG.04).
Keep secrets out of the conversation. Passwords and credentials flow through product workflows (like the 1Password-wired sign-in form), never through model context.

10 · Getting better while you sleep

The training flywheel

The product improves on two coupled loops — one daily, one monthly — riding the standard LLM training pipeline: pretraining (world knowledge from internet-scale text) → SFT, supervised fine-tuning (behavior — including examples of working inside this harness, so the model knows its tools) → reinforcement learning (instruction following, picking the right skill out of hundreds, clicking the right pixel). Inference is tuned per role, too: the main agent you chat with needs low latency, while helpers can be slower — the difference between ten minutes and twelve is negligible when a job runs for hours. ▶ 34:27

And when a new model lands, it unlocks behaviors nobody trained for. Bots in group chats are emergent — and early public failures (like the Hugging Face incident) show how poorly untrained agents behave in the wild, which is exactly why multi-agent behavior needs to make it into the next training run.

11 · Build for the next model

“Delete the product”

“Assume the models today are the worst they'll ever be. In six months you might need to completely rebuild the UI. Build for the next generation of the model — build as little as possible, and keep the interface really simple.”— the principle, from Cursor and now SpaceX

Most of what this document describes didn't exist a year ago. That's the planning assumption behind “delete the product”: don't over-build around today's limits — sometimes that means deleting what you built. ▶ 37:42

Safe bets for the next 6–12 months ▶ 38:36

Agents that work for weeks or months, not hours · much better recall (graphs? files? new representations?) · bots granted all the tools a human hire would get · interfaces fading toward speech (talk to your bot all day from a Jony-Ive-style device) · skills learned on the job, encoded into files automatically · companies writing down their bespoke processes so they're legible to agents.

Open problems worth a career ▶ 40:22

How do you evaluate an agent that runs for a month when models ship every month? · What's the right memory representation? · How do you make a harness and its infrastructure secure against takeover? · Where exactly is the line between helpfully proactive and annoying? · And as token volume explodes, token efficiency becomes an engineering discipline of its own.

And the macro picture, as Alex from OpenRouter put it on X: the sidebar-plus-chatbox app everyone mocks as “all the same” is this era's “server + database + CRUD” — the new normal. Every product will have an agentic side or become headless data that some agent consumes. The new primitives on the board: durable workflows, sandboxes, cloud computers, memory, skills, connectors, voice, payments, identity, evals, observability. ▶ 42:05

12 · One message, end to end

Follow a message through the machine

You've now met every component individually. Here they are in one run: you type a message and hit send — and the whole system moves. Even step zero happens before send: while you're typing, the server may pre-build the prompt to warm the prompt cache, the same way a website prefetches a page on link-hover. ▶ 31:06

The same run, in words

00While you type — the server may already pre-build the prompt from the conversation so the cache is warm the instant you send (§08).
01You type and hit send. Your text is a trigger — an event for the router — not a tool call. The only tool that crosses the client/server boundary points outward (§07).
02The client acknowledges instantly. Your bubble shows “sent” before the server has done anything (§05).
03The router dedupes (client retries, multi-device), folds the text into the conversation, batches if you fired 3–4 messages in a burst, and applies priority — a direct message from you can interrupt the turn that is currently running (§04).
04The turn enters the queue. One turn runs at a time; everything else waits for its priority slot.
05The turn starts as a durable workflow (Temporal). If the server was asleep, this trigger woke it; the loop restores its world from the State DB — profile, core facts, memories, skills, conversation history — and rebuilds the prompt head byte-identically (§03, §04).
06The agent loop calls the model: cached head + your new message as the only full-price delta. Tool names only are in context; each schema is read from a file the moment it's needed (§07, §08).
6aExpensive work? Big research, screenshot analysis, rendering — delegated to a helper: its own durable workflow, own skills, fresh context. Only the result returns to the loop (§07).
6bIrreversible action? Sending email or Slack goes out as a draft card via send_user, and the workflow waits on an approval signal before anything leaves (§07, §09).
07The model requests a tool call. Before it runs, the autoreview model checks the command — approval at machine speed, not human fatigue (§09).
08The computer, if needed. A microVM comes from the shared pool — snapshot restore or fresh boot, one machine per active bot, handed back on sleep (§06).
09Execute: shell, files, Chrome (accessibility tree first, pixels as fallback), full desktop for long jobs — and you can live-view or take the wheel yourself. Results return to the loop (§06).
10Loop until the model replies. Each round: results feed the next model call, every step is appended to the workflow's event history, and the conversation keeps persisting — so any crash resumes exactly where it stopped (§05).
11The answer leaves via send_user — the one outbound tool, the same whatever the client is (§07).
12Your devices render it. Every subscribed client gets the signal, fetches the latest state, dedupes retries, and renders richly: plain text, an editable draft, a sign-in form — or you just tap 👍 (§05).
13Persist + compact. The finished turn is written to the State DB; if you've gone idle, compaction runs now, while the cache is still warm, so your next message lands on a cheap summary (§08).
14Wind down. The VM snapshots and returns to the pool; the server sleeps. The next trigger — a Slack ping, a phone call, a cron routine, a finished background job — wakes the whole machine again (§04).

Elapsed time, end to end: the ack is milliseconds; a plain answer takes seconds; anything touching the computer takes minutes — and when it's done, every machine involved is asleep again, with all of it written down. That single cycle is the product; everything else in this document is why each arrow is safe, cheap, and resumable.

13 · The napkin test

Design Grokbot from memory

If this teardown worked, you can now rebuild the machine from these eleven moves. Close the tab and try.

  1. Start from the seed: a model calling tools in a loop.

    That's the whole agent. Everything below is what it takes to run that loop reliably, forever, for millions of people.

  2. Move the loop onto a server.

    Thick server, thin clients. Agent updates deploy server-side; heavy work runs on server hardware; the loop must be independent of anything you might want to reboot.

  3. Give it a disposable computer.

    A Firecracker microVM from a shared pool: files, shell, Chrome, a virtual desktop per active bot. Snapshot it, sleep it, rebuild it for zero-days — and never run the agent loop on it.

  4. Persist all state in a database; sleep when idle.

    Conversations, memories, skills, routines. “Always-on” means wake-instantly-with-full-memory, not machines idling 24/7.

  5. Wake it from everywhere; let it stay silent.

    Chat, Slack, calls, meetings, cron. A router dedupes, batches, prioritizes your direct messages — and applies the “is this worth bugging the user?” heuristic.

  6. Give the agent exactly one client-facing tool: send_user.

    One integration point, rich client-side rendering: sign-in forms, payments, draft approvals, emoji reactions.

  7. Keep the context window for thinking.

    Tool names only — schemas live in files. Climb the cheap ladders first (conversation → connectors → search → browser → desktop → you). Delegate expensive work to helper subagents; only results return.

  8. Engineer the cache like a feature.

    Static, ordered prompt head; hashed sections; cache miss = bug; warm the cache while the user types; compact while the cache is warm.

  9. Layer the memory.

    Core facts in every prompt → ephemeral scratchpad → dated logs → everything else greppable in files, with garbage collection on top.

  10. Guard it: autoreview, distrust, confirm, isolate.

    A model reviews every command; untrusted input is data, never instructions; irreversible actions need draft approval; secrets stay out of the conversation.

  11. Run the two loops.

    Daily: bug → eval → fix → ship. Monthly: train on failures → climb evals → deploy. And build as little as possible, because the next model changes the calculus.

One-sentence version: Grokbot is the simple harness — a model calling tools in a loop — wrapped in a durable workflow on a server, wielding a disposable cloud computer, fed by event triggers through a polite router, talking to thin clients through a single send_user tool, and disciplined by context engineering so the loop can run for weeks.
