Part I — Foundations

Chapter 1: The Shape of OpenHands

The Problem: An Agent Is Not One Program

A coding agent sounds like one program: send it a task, it edits files, it reports back. In practice it is at least four jobs that want to live in different places.

Someone has to think: build a prompt, call a model, turn the reply into tool calls. Someone has to act: run shell commands and edit files somewhere, ideally not on the only laptop you own. Someone has to remember: keep a record of what happened so a run can pause, crash, resume, or be audited. And someone has to show it: a UI where a person watches, approves, and steers.

If all four live in one process, every change is a change to everything. If they live in four processes, you need a contract between them that does not rot.

The Options

  • One monolith. A single app that owns the UI, the loop, and the sandbox. Simple to ship, hard to embed, and the sandbox boundary ends up wherever the UI happens to run.
  • A UI with a private backend. The frontend talks to a server only it understands. Works until a second client (a script, a CI job, another product) wants the same agent.
  • A library first, with a server and a UI as clients. The agent is an importable SDK. A server wraps it with a public API. The UI is one client of that API among many.

OpenHands’s Choice: SDK at the Bottom, Canvas on Top

OpenHands takes the third option and splits it across repositories. The OpenHands/OpenHands repository is now Agent Canvas, a React and TypeScript frontend described as a self-hosted control center for coding agents and automations. The agent itself lives in OpenHands/software-agent-sdk, which owns the Python SDK, the Agent Server, agents and tools, conversations, events, workspaces, and the canonical REST and WebSocket API. Reusable skills and plugins live in OpenHands/extensions; scheduling and webhooks live in OpenHands/automation.

This book reads both main repositories, because neither makes sense alone. Canvas’s own architecture notes say it is not responsible for executing agent actions or providing sandbox isolation. Those jobs are below it.

The Contract Runs One Way

Both repositories state the dependency direction in their contributor notes: Agent Server contract → OpenAPI → TypeScript client → Agent Canvas. A feature that crosses the line is built in the SDK first, exposed through clients/typescript, and only then consumed in the UI. Canvas is told not to reimplement server endpoints.

This one rule explains a lot of the structure. Canvas has a test named no-direct-agent-server-calls. Its service layer wraps typed client classes rather than hand-written HTTP. When Canvas starts needing a newer server feature, it raises compatibility.minimumAgentServer in config/defaults.json, and at runtime it refuses servers older than that floor.

Three Ways to Run It

The README offers three install shapes, and they map directly onto where the “act” job happens.

The local stack is three processes behind an ingress: the Agent Server, the automation backend, and the static frontend. Default ports are recorded in config/defaults.json (ingress 8000, Agent Server 18000, automation 18001), and the ingress matches the longest path prefix first, so /api/automation goes to automation before /api goes to the Agent Server.

The Thesis of This Book

Strip away the UI and the deployment options and one design remains. Each conversation is an append-only log of events. The agent is a stateless function that reads that log and appends to it. Every other layer is a way to carry that log across a boundary: to disk, to a container, over a WebSocket, into a browser.

The SDK says so in its own words. AgentBase describes agents as “stateless and fully defined by their configuration”. The condenser documentation calls the event log append-only and “an almost perfect record of what transpired”, even if the environment is lost. The rest of this book follows that log outward.

The Trade-offs

  • Three repositories, pinned together. Canvas records exact versions for the server and client, and mixing unpinned branches is called unsupported. Coordination cost is real.
  • A library-first agent needs a server to be useful to a UI. The server is extra surface: auth, capacity limits, persistence.
  • The thin UI cannot fix backend gaps. Anything the server does not expose, Canvas cannot do.

Apply This

Make the agent a library, and the server one client of it. Other clients then come for free.

Write the dependency direction down. “Contract first, client second, UI last” prevents a UI from growing its own private backend.

Pin versions in one file and enforce a minimum at runtime. A clear refusal beats a mysterious half-working UI.

Name the isolation level in the install instructions. “This mode can touch your whole filesystem” belongs on the first page.

Find the one data structure everything else carries. For OpenHands it is the event log.

Chapter 2: Everything Is an Event

The Problem: What Exactly Happened?

Chapter 1 claimed the event log is the center. Before trusting that, ask what a log has to capture for an agent.

A model call produces text, reasoning, and tool calls. Tools produce results, errors, or nothing because a person said no. Users send messages, pause, and interrupt. The system prompt itself is a decision worth recording. If any of these lives outside the log, a resumed conversation will not match the original, and the model will be shown a history that never happened.

There is a second constraint. Model APIs are strict about history: every tool call must be followed by its result, roles must alternate, the system message comes first. The log has to be easy to turn into exactly that shape.

The Options

  • Store the chat messages. Simple, and close to what the API wants. But pauses, rejections, state changes, and condensation do not fit in a chat transcript.
  • Store snapshots of state. Easy to restore, impossible to audit, and every snapshot repeats the whole past.
  • Store typed events, and derive messages from them. More types to design, but nothing is lost and the message list becomes a projection.

OpenHands’s Choice: Typed Events, Some of Which Become Messages

Every event inherits from Event, which carries an id, a timestamp, a source, and a parent_id. A subset inherits from LLMConvertibleEvent, which adds one method: to_llm_message(). Only those events can ever reach the model.

The Core Pair: Action and Observation

When the model asks for a tool, the agent records an ActionEvent. It holds the model’s thought, any reasoning or thinking blocks, the validated action, the tool_name, the tool_call_id, the id of the model response it came from, and a security_risk label (Chapter 9).

Everything that answers a tool call inherits from ObservationBaseEvent, which carries the same tool_name and tool_call_id. There are three kinds:

Answer When
ObservationEvent The tool ran and returned a result
UserRejectObservation A person rejected it, or a hook blocked it (rejection_source says which)
AgentErrorEvent The scaffold failed: bad arguments, a crash, an interrupted call

Because all three are observations, “every action gets exactly one answer” is checkable. ConversationState.get_unmatched_actions() finds actions with no answer yet. Those are either waiting for confirmation or were interrupted. Error events match by tool_call_id rather than action id, which matters after a crash, when an error is written for an action the new process never saw.

Messages Are Also Events

User and agent text is a MessageEvent. A user message can carry activated_skills and extended_content: knowledge injected because a skill’s keyword matched (Chapter 12). It can carry a sender, which matters when one agent talks to another. An agent message can carry a critic_result.

The system prompt is an event too. SystemPromptEvent stores the static prompt, the tool definitions, and an optional dynamic_context block. It converts to a single system message with one or two content blocks; Chapter 4 shows why the split matters for caching.

Batches and the Projection

One model reply can contain several tool calls. Each becomes its own ActionEvent, but only the first carries the thought and reasoning. LLMConvertibleEvent.events_to_messages() folds a batch back into one assistant message with several tool calls, so the provider sees what it sent. The docstring calls this a read-only projection: events are immutable once created.

A Log That Can Branch

Every event has a parent_id. Usually that is just the previous event, but it lets the log become a tree. navigate_to(event_id) moves the conversation’s HEAD back to an earlier event; appending after that creates a sibling branch. Abandoned branches stay on disk and simply drop out of what the model sees. fork() copies a conversation, optionally only up to one event, into a new id.

graph LR S["system"] --> U1["user: fix test"] U1 --> A1["action: run tests"] A1 --> O1["observation: 2 failed"] O1 --> A2["action: edit file"] O1 -.->|"navigate_to + new message"| U2["user: try another way"] U2 --> A3["action: read docs"]

The Trade-offs

  • Many event types. Every new feature is a schema decision, and old events must keep loading.
  • The projection has to be perfect. A bug in converting events to messages becomes a provider error. Chapter 5 shows the recovery path.
  • Trees complicate everything that reads history. Stuck detection, the view, and condensers must read the active branch, not the raw log.

Apply This

Record decisions, not just dialogue. Pauses, rejections, and state changes belong in the log.

Give every tool call exactly one answer, with three possible kinds. Result, rejection, error. Then “unanswered” is a query.

Mark which events the model may see. A single to_llm_message() boundary keeps internal events out of prompts.

Treat the message list as a projection. Never edit history; derive it.

Add a parent pointer early. Branching later is cheap if every event already knows its parent.

Chapter 3: The Conversation State and Its Log

The Problem: A Log That Survives Real Life

Chapter 2 defined what goes into the log. Now the log has to live somewhere, and real life is unkind to it.

Several threads touch one conversation at once: the run loop appending events, a user sending a message, a UI reading a snapshot, a pause request. Processes restart. A server may be asked to resume a conversation it did not start. Secrets end up in state and must not end up in plain text on disk. And a user may resume with a different model or a new tool, and expect it to work.

The Options

  • A database. Strong guarantees, but a heavy dependency for an SDK that should run in a script.
  • One big JSON file per conversation. Easy, but every append rewrites the whole history, and a crash mid-write loses everything.
  • One small file per event, plus a small file for everything else. Appends are cheap and atomic per event; the rest of the state is small enough to rewrite.

OpenHands’s Choice: Base State Plus an Event Directory

A conversation’s persistence directory holds two things:

  • base_state.json: everything in ConversationState except the events. Status, confirmation policy, security analyzer, activated skills, blocked actions, the HEAD pointer, stats, the secret registry, tags.
  • events/: one JSON file per event, named event-{index:05d}-{event_id}.json. The index is padded to five digits but not capped.

Events are written through one chokepoint. ConversationState.append_event() stamps the parent_id, appends through EventLog, and advances HEAD. Stamping there, not only in the emit callback, guarantees no event enters the log without a parent, even one a hook swapped in.

The log locks across processes. EventLog.append() takes a file lock from the FileStore and keeps a small length marker so it can tell whether another process appended since it last looked. If so, it scans only the new files. The code warns that flock() is not reliable on NFS, so shared network storage needs a different coordination mechanism.

Base state saves itself. Assigning a public field on ConversationState writes base_state.json immediately. Inside a with state: block, writes are deferred until the block exits, so several changes cost one write.

One Lock, First Come First Served

Every mutation of the state happens while holding ConversationState’s lock, which is a FIFOLock: reentrant like RLock, but threads acquire it in the order they asked. A standard lock can starve a thread; here a user’s send_message() cannot be starved by a busy run loop.

sequenceDiagram participant RL as Run loop participant LK as FIFOLock participant UM as send_message() participant UI as Snapshot reader RL->>LK: acquire (step) UM->>LK: wait (queued 1st) UI->>LK: wait (queued 2nd) RL->>LK: release LK-->>UM: granted UM->>LK: release LK-->>UI: granted

The async run path goes further. While waiting on the network for a model reply, it releases the state lock and reacquires it afterwards, so send_message() and snapshots stay responsive during a long completion. Chapter 6 shows why this matters.

Secrets on Disk: Encrypt or Forget

State contains secrets: API keys inside the LLM config, values in the secret registry. When the state is saved with a cipher, secrets are encrypted. Without one, they are redacted, meaning lost. A resumed conversation without a cipher will not have its keys back.

The Agent Server makes this explicit. Its OH_SECRET_KEY setting encrypts sensitive values in stored conversations, and its README calls it required for persistence across restarts. Chapter 10 covers the rest of the secret path.

Resuming: Same Agent Type, Tools Only Grow

ConversationState.create() either starts a new conversation or loads a persisted one. On load, it does not merge old and new configuration. It checks compatibility and then uses the runtime agent.

AgentBase.verify() holds two rules: the agent class must match, and tools may be added but never removed. The reason is in the docstring: the model may already have been told about a tool, and history may contain calls to it. Adding a tool is safe; the model simply gains a capability next turn. Everything else, including the LLM, the condenser, the prompts, and the agent context, may change freely between sessions.

flowchart TD R["Resume conversation"] --> T{"Agent class matches?"} T -->|no| X["Refuse"] T -->|yes| U{"Any persisted tool missing?"} U -->|yes| X U -->|no| OK["Use runtime agent
new LLM, prompts, condenser allowed"]

The View Is Cached

The model never reads the raw log. It reads a View of the active branch, with condensation applied (Chapter 11). Rebuilding that from thousands of events every step would be slow, so state.view is maintained incrementally: a normal append replays only the new tail. A branch switch, a fork, or a cold load triggers one full rebuild with all API-shape rules enforced.

The Trade-offs

  • Many small files. Cheap appends, but large conversations mean large directories, and counting events means scanning them.
  • File locks are local. Shared network filesystems need extra care.
  • No cipher, no secrets. Redaction is safe by default but surprises people who expected a full resume.
  • Tool removal is forbidden. Cleaning up a tool list means starting a new conversation.

Apply This

Split append-only history from small mutable state. Each gets the storage it deserves.

Write events through one function. Stamping, appending, and moving HEAD in one place keeps invariants from leaking.

Use a fair lock when users and loops share state. Starvation shows up as an unresponsive Send button.

Encrypt secrets or drop them, never store them plain. Make the choice explicit in configuration.

On resume, verify instead of merge. “Tools may only grow” is a rule you can state and check.

Chapter 4: Talking to Models

The Problem: Every Provider Is Slightly Different

The agent needs one call: here are messages and tools, give me a reply. Behind that call sit dozens of providers with different endpoints, tool-calling formats, caching rules, reasoning formats, error messages, and rate limits. Some models have no native tool calling at all. Requests fail transiently. Users want to switch models mid-conversation and see what each one cost.

The Options

  • Write one client per provider. Full control, endless maintenance.
  • Use a provider-neutral library and accept its lowest common denominator. Fast to start, but caching, reasoning, and error handling get lost in translation.
  • Use a neutral library for transport, and own the behaviour on top. Retries, caching marks, tool-calling fallback, error classification, metrics, and profiles live in your code.

OpenHands’s Choice: One LLM Class Over LiteLLM

The SDK’s LLM class is a Pydantic model that wraps litellm. LiteLLM handles transport to each provider; LLM owns everything the agent depends on. It is configuration, not a connection: like Agent, it is treated as frozen and may be shared across conversations. Per-call context is threaded through each request instead of stored on the object.

What LLM Owns

Endpoint mode. api_mode is auto, chat, or responses. Auto resolves from model metadata; the explicit values exist for proxy aliases and brand-new models. capability_overrides can force flags like vision or prompt-cache support when metadata is wrong.

Retries. The defaults are five retries with exponential backoff between 8 and 64 seconds (num_retries, retry_min_wait, retry_max_wait, retry_multiplier). Hard timeouts sit inside each attempt so a timeout is itself retryable; a streaming idle timeout resets every time a chunk arrives.

Tool calling without native support. native_tool_calling defaults to on. When it is off, a mixin converts tool definitions into prompt text and parses the reply back into tool calls, so the rest of the agent never knows the difference.

A risk field in every tool schema. The agent calls generate() with add_security_risk_prediction=True. The tool schema sent to the model gains a security_risk field so the model labels each action. Chapter 9 explains who reads that label.

Caching Without Moving the Prefix

Prompt caching pays only if the beginning of the request stays byte-identical. LLM._apply_prompt_caching() places two breakpoints:

  1. The system message’s first block. The system prompt is built as two blocks, a static prompt and a per-conversation dynamic context, and only the static block is marked. That lets different conversations share one cached system prompt.
  2. The last user or tool message, so the cached prefix extends every turn. The code notes this second mark is Anthropic-specific; Gemini is excluded because its cache cannot extend that way.

The SDK also enforces an invariant for every request it builds, including condenser and security-analyzer calls: a system message comes before the first user message. Exceptions must be documented.

Errors Are Routed, Not Just Raised

LLM classifies provider errors into a small set of typed exceptions, and the agent loop treats each differently (Chapter 5):

Error What happens next
Malformed function call Sent back to the model as a user message, so it can correct itself
Content policy block A nudge asking the model to rephrase; the run continues
Context window exceeded A condensation request, if the condenser can handle one
Malformed history View rebuilt with full rules, then condensation
Authentication The conversation goes to ERROR with a clear message

Many Models in One Conversation

Registry and metrics. An LLMRegistry keeps instances by usage id and gives each its own metrics. Cost tracking can then say how much the agent, the condenser, and each sub-agent spent separately.

Profiles. An LLMProfileStore saves named configurations. A conversation can switch_llm() or switch_profile() between steps.

Fallback. A FallbackStrategy tries alternate profiles when the primary fails with a transient error after its retries. Fallback is per call: the next request starts with the primary again.

Routing. RouterLLM is itself an LLM that picks one of several underlying models per request and delegates everything else to it.

OpenHands-hosted models. Public config uses openhands/<model>. It is translated to LiteLLM’s proxy form only at the LiteLLM boundary, so nothing upstream needs to know.

The Trade-offs

  • A large configuration surface. Dozens of fields, many of them escape hatches for one provider’s quirk.
  • Caching marks are provider-specific. The second breakpoint helps Anthropic models only.
  • Prompt-mocked tool calling is less reliable than native calls. It exists so weaker or self-hosted models can play at all.
  • Fallback hides failures unless metrics are watched. Each call silently may use another model.

Apply This

Own behaviour, rent transport. Let a library talk to providers; keep retries, caching, and error policy in your code.

Split the system prompt into static and dynamic blocks. Cache the static one across conversations.

Put the timeout inside the retry. A slow attempt should be retried, not fatal.

Give every error a next step. Correctable errors go back to the model; context errors trigger condensation.

Track metrics per usage, not per process. “The condenser cost more than the agent” is a finding you want to be able to make.

Part II — The Agent Loop

Chapter 5: One Step of the Agent

The Problem: Turning a Log Into the Next Move

Chapters 2 to 4 gave us a log, a place to keep it, and a way to call a model. The agent’s job is to connect them: read the log, decide what happens next, and append the result.

That sounds like one function call, but a step has many ways to go. The model may answer with text, or ask for three tools at once, or return nothing useful. The history may be too long for the model. A tool call may need a human’s approval first. A hook may have blocked the user’s message. And the step must leave the log in a shape the provider will accept next time.

The Options

  • One loop that does everything. Call the model, run tools, repeat, all inside one function. Hard to pause, hard to test, and approval has nowhere to wait.
  • A planner and an executor as separate components. Clean on paper, but they need a shared notion of “what happened”, which is the log anyway.
  • A single, small step over the log. Each call to step() does at most one model call or one batch of pending work, appends events, and returns. Something outside decides whether to call it again.

OpenHands’s Choice: Agent.step() Does One Thing and Returns

Agent.step(conversation, on_event) is the whole agent. It holds no state of its own between calls; everything it needs is in conversation.state, and everything it produces goes out through on_event. Chapter 6 covers the loop that calls it.

Before Calling the Model

Pending actions come first. If the active branch has actions without answers, the step executes them and returns. This is how approval works: a previous step proposed actions and stopped; the user approved by simply running again. The code calls this implicit confirmation.

Blocked messages end the turn. A UserPromptSubmit hook can block a user message. If the latest one was blocked, the step marks the conversation finished without calling the model.

The view becomes messages, or a condensation. prepare_llm_messages() takes the cached view and the condenser. If the condenser decides to condense, the step emits a Condensation event and returns; the next step sees the shorter view. Otherwise it gets the message list.

The Call and Its Failures

The step calls llm.generate() with the messages and every tool in tools_map. Chapter 4 listed the typed errors; here is where they are caught. A malformed tool call becomes a user message with the error text. A content-filter block becomes a polite nudge. A context-window error, or a provider rejecting the history as malformed, becomes a CondensationRequest, but only if the condenser can handle requests. Without one, the error is raised and the run ends in ERROR.

Four Kinds of Reply

classify_response() is a pure function. It sorts every reply into exactly one type, first match wins:

Type Test What the step does
TOOL_CALLS the reply has tool calls build action events, check confirmation, execute
CONTENT non-blank text emit an agent MessageEvent, set FINISHED
REASONING_ONLY reasoning but nothing visible emit it, then nudge
EMPTY nothing useful emit it, then nudge

The nudge is an environment-sourced message telling the model its last response had neither a tool call nor a message. The model sees a user-role message, but the event’s source records that the framework, not the human, sent it.

Notice what CONTENT means: a plain text answer ends the task. In OpenHands, talking to the user is how the agent says “your turn”.

Executing a Batch

Each tool call becomes an ActionEvent. The first one carries the thought and reasoning. Then:

return without running"] C -->|no| B{"Blocked by a PreToolUse hook?"} B -->|yes| RJ["UserRejectObservation
source: hook"] B -->|no| EX["Parallel executor runs tools"] EX --> EM["Emit results in original order"] RJ --> EM EM --> FIN{"Finish executed?"} FIN -->|yes| CR{"Critic asks for another pass?"} CR -->|yes| FU["Follow-up user message"] CR -->|no| DONE["FINISHED"]

finish is a tool. Two built-in tools are attached to every agent: FinishTool (carrying the final message) and ThinkTool (logging a thought). Any calls the model placed after finish are discarded with a warning.

Confirmation is checked for the whole batch. If any action needs approval, none run yet (Chapter 9).

Results are emitted in the model’s order, even though tools may run concurrently (Chapter 7). Hook-blocked actions get a rejection in their place, so every action still gets exactly one answer.

A critic can veto finishing. If a critic with iterative refinement is configured and its score is too low, the step injects a follow-up message instead of setting FINISHED.

The Trade-offs

  • One step, many exits. The function is long because every exit must leave a valid log.
  • Text ends the task. A model that chats mid-task will stop early; the nudge and the finish tool push it toward tools.
  • Batch-level confirmation. One risky call holds up its harmless siblings.

Apply This

Make the agent a step, not a loop. Something else decides whether to step again.

Do pending work before new work. Then “approve” is just “continue”.

Classify replies with a pure function. Exactly one type per reply, tested in isolation.

Route each failure to a next step. Correctable errors go back to the model; size errors go to the condenser.

Emit results in call order. Concurrency is an implementation detail; the log should read like the model’s plan.

Chapter 6: The Run Loop and Its States

The Problem: When to Step Again

Chapter 5’s step does one thing and returns. Someone must call it again, and decide when to stop. That someone also has to answer questions the step cannot: Has the user paused? Is the agent stuck repeating itself? Has it spent its budget? Did a stop hook object to finishing? Can a new user message arrive while the agent is busy without being lost?

The Options

  • Loop until the agent says done. Simple, and wrong: agents loop, budgets run out, and users need a brake.
  • A hard cap on steps. Necessary but blunt; it stops a healthy long task and an obvious loop at the same point.
  • An explicit status machine. Every reason to stop is a named status, checked between steps, visible to every client.

OpenHands’s Choice: LocalConversation.run() and Eight Statuses

ConversationExecutionStatus names the possible states: IDLE, RUNNING, PAUSED, WAITING_FOR_CONFIRMATION, FINISHED, ERROR, STUCK, and DELETING. Three are terminal for a run: FINISHED, ERROR, and STUCK. IDLE is deliberately not terminal, because a WebSocket delivers the initial IDLE state on connect and clients would otherwise think the run had ended.

stateDiagram-v2 [*] --> IDLE IDLE --> RUNNING: run() RUNNING --> WAITING_FOR_CONFIRMATION: risky actions WAITING_FOR_CONFIRMATION --> RUNNING: run() again (approve) WAITING_FOR_CONFIRMATION --> IDLE: reject_pending_actions() RUNNING --> PAUSED: pause() / interrupt() PAUSED --> RUNNING: run() RUNNING --> FINISHED: text reply or finish RUNNING --> STUCK: stuck detector RUNNING --> ERROR: exception, iteration cap, budget FINISHED --> IDLE: send_message() STUCK --> IDLE: send_message() ERROR --> RUNNING: run()

One Iteration

run() first sets the status to RUNNING from IDLE, PAUSED, ERROR, or STUCK. Then, under the state lock, each iteration:

  1. Breaks if the status is PAUSED or STUCK.
  2. If the status is FINISHED, runs stop hooks. A stop hook may refuse; its feedback becomes an environment message and the status goes back to RUNNING. Otherwise the loop ends.
  3. Checks for stuck patterns.
  4. If the status is WAITING_FOR_CONFIRMATION, sets it back to RUNNING. Calling run() again is the approval.
  5. Calls agent.step().
  6. Breaks on WAITING_FOR_CONFIRMATION, on an exceeded budget, or on the iteration cap.

The iteration cap is max_iteration_per_run, default 500. Reaching it sets ERROR with a MaxIterationsReached event, unless the agent finished on that very iteration. A budget overrun emits MaxBudgetReached. Any exception sets ERROR, emits a ConversationErrorEvent (unless the agent already emitted a more detailed one), and re-raises as ConversationRunError carrying the conversation id and persistence directory.

Messages That Arrive While Running

send_message() takes the same FIFO lock. If the conversation is FINISHED or STUCK, a new message resets it to IDLE. The loop body deliberately does not check for FINISHED right after a step. The code comments spell out why: if the agent finishes while a user message is waiting for the lock, the message gets in, resets the status, and the next iteration processes it. Checking too early would drop that message on the floor.

Pause Versus Interrupt

sequenceDiagram participant U as User participant C as Conversation participant L as LLM call U->>C: pause() Note over C: status = PAUSED, PauseEvent C-->>L: current call finishes normally C->>C: loop sees PAUSED at next iteration U->>C: interrupt() C->>L: cancel the running task now Note over C: CancelledError, status = PAUSED, InterruptEvent C->>C: orphan actions get AgentErrorEvent

pause() takes effect between steps. If a model call is in flight, it finishes first.

interrupt() works on the async path. It sets a cancellation token, so pending tool calls can be skipped, and cancels the running task. Cancellation propagates from the HTTP stream through the step to the loop without per-layer interrupt APIs, because the LLM and agent hold no per-conversation state. The loop catches it, sets PAUSED, and emits an InterruptEvent. Any action left without an answer gets a synthetic AgentErrorEvent, because providers reject histories with unanswered tool calls.

The Stuck Detector

StuckDetector scans events since the last user message on the active branch. It looks for five patterns:

Pattern Default threshold
The same action and observation repeating 4
The same action repeatedly erroring 3
Agent monologue: messages with no user input 3
Two action–observation pairs alternating 6
Repeated context-window errors —

For a repeating error, the loop first nudges once with a message about the streak. Only if the pattern continues does it set STUCK. Event comparison ignores ids and metrics, so identical work with fresh ids still counts as a repeat.

The Trade-offs

  • Implicit approval is subtle. “Run again” meaning “yes” is elegant for code and confusing in a UI unless the UI hides it behind an Approve button.
  • Pause is not instant. Only interrupt() cancels a model call, and only on the async path.
  • Heuristic stuck detection. Thresholds catch obvious loops; a creative loop slips through until the iteration cap.

Apply This

Name every reason to stop. A status per reason makes UIs and logs honest.

Check control flags between steps, under the same lock as writes. Pause then has a well-defined moment.

Do not check “finished” too eagerly. Let a racing user message in before ending.

Backfill unanswered tool calls after a cancel. The next request must still be valid.

Nudge before you stop. One warning often breaks a loop more cheaply than a hard stop.

Chapter 7: Tools — Schemas In, Observations Out

The Problem: Giving a Model Hands

A model can only produce text. To do work it needs tools, and each tool raises the same questions. How does the model learn the tool exists and what arguments it takes? How are bad arguments caught before anything runs? What comes back, and in what shape? Which tools may run at the same time without corrupting each other? And how do tools from outside the codebase, such as an MCP server or a browser UI, join in without special cases?

The Options

  • Functions with docstrings. Easy to write, but the schema, validation, and output format are all implicit.
  • A central list of tools in the agent. Explicit, but every new tool edits the agent, and outside tools do not fit.
  • Typed tool definitions, a registry, and a spec in the agent config. Each tool declares its input and output types. The agent config names tools by spec; a registry resolves them when the conversation starts.

OpenHands’s Choice: Typed Definitions Resolved by Name

A tool is a ToolDefinition: a frozen model with a class-level name, a description, an action_type (the input schema), an optional observation_type, optional MCP-style annotations, and an executor that does the work. Inputs subclass Action, outputs subclass Observation. An observation carries a list of text and image content plus an is_error flag, and decides how it renders for the model in to_llm_content().

The agent does not hold tool objects. It holds specs: Tool(name="TerminalTool", params={...}). When the agent initializes for a conversation, each spec is resolved through the registry, and the tool’s create() builds instances bound to that conversation’s state. That is why an agent can be serialized, sent to a server, and rebuilt there.

What Every Agent Gets

Two tools are attached to every agent by default: FinishTool and ThinkTool. Other built-ins (invoking a skill, switching models, inspecting an image) attach when their feature is configured. include_default_tools controls the list, and filter_tools_regex can hide tools by name; built-in defaults are exempt from the filter.

AgentBase.tool_concurrency_limit defaults to 1: tools run one at a time unless you raise it. When you do, the ParallelToolExecutor runs a batch on its own thread pool and uses declared resources to decide what must be serialized.

Each executor instance has its own pool and lock manager, so a sub-agent running inside a tool call cannot deadlock its parent.

Tools From Outside

MCP servers. mcp_config on the agent is a map of server names to server configs. At startup the SDK connects to each server, lists its tools, and wraps each as an MCPToolDefinition. Those runtime tools go through filter_tools_regex like any other.

Client tools. A frontend can register tools purely as JSON in POST /conversations, with no Python. When the agent calls one, the action goes out over the WebSocket for the client to handle, and the SDK returns an acknowledgment observation immediately so the loop continues. Canvas uses this for UI-side tools such as forms.

The Trade-offs

  • Serial by default. Safe, but a batch of independent reads runs one at a time unless you opt in.
  • Locking depends on honesty. A tool that declares no resources but shares state will race.
  • Specs need a registry at runtime. A server that cannot import a tool’s module cannot rebuild the agent; the Agent Server rejects such a conversation up front.
  • Client tools are fire-and-acknowledge. The model learns only that the request was delivered, not its outcome.

Apply This

Put specs in config and objects at runtime. A name and parameters travel; executors do not.

Type both directions. Validate arguments into an action; render results from an observation.

Make the safe default serial, and let tools opt into parallelism. Declared resources beat a global flag.

Distinguish “unknown” from “safe”. Treat undeclared as serialize.

Let outside tools enter through the same door. MCP and client tools become ordinary definitions.

Chapter 8: Where Actions Run

The Problem: The Laptop Is the Wrong Place

Chapter 7’s tools run commands and edit files. On a laptop that is convenient and dangerous: the agent sees everything you see. For a team, a CI job, or many conversations at once, it is also the wrong machine. Actions need to run somewhere chosen on purpose, and the agent’s code should not change when that place changes.

The Options

  • Run tools locally, ship commands to a sandbox. Keep the agent here and proxy each command over the network. Every tool needs a remote twin, and every tool call pays a round trip.
  • Containers per tool call. Strong isolation, slow, and state such as a shell session does not survive.
  • Move the whole agent next to the files. Run a server inside the sandbox that hosts the agent, the tools, and the log; the client only sends messages and receives events.

OpenHands’s Choice: A Workspace Interface, and Remote Means “Agent Server Elsewhere”

BaseWorkspace is a small interface: execute_command, file_upload, file_download, git_changes, git_diff, pause, resume, and context-manager cleanup. LocalWorkspace implements it on the host filesystem; pause and resume are no-ops.

Every other implementation is a RemoteWorkspace, which connects to an OpenHands Agent Server. The remote side is not a command proxy. It is the same SDK running behind an HTTP API, with its own tools and its own event log.

The Factory Picks the Conversation Too

Workspace(working_dir=...) returns a local workspace; add a host and it returns a remote one. Conversation(...) follows the same switch. With a local workspace you get a LocalConversation: the agent loop runs in your process. With a remote workspace you get a RemoteConversation: the loop runs on the server, and your process holds a mirror.

The mirror is built from two pieces. RemoteEventsList fetches existing events once, then appends new ones as they arrive over a WebSocket, and can reconcile with the server on demand. RemoteState caches state fields and updates them from ConversationStateUpdateEvents on the same socket. Calling run() triggers a run on the server and, by default, waits for it to finish.

The Agent Server itself can play the same trick. The Trade-offs

  • Remote means a second server to run, secure, and version. The client SDK and the server must agree on the API.
  • The mirror lags. Remote state is eventually consistent; reconcile() exists because sockets drop.
  • Isolation depends on the backend. A local workspace is no sandbox at all. Even the per-conversation containers share any host workspace you point several conversations at.

Apply This

Abstract the place, not the tool. A workspace interface lets the same tools run anywhere.

Move the agent to the files. Shipping the whole loop into the sandbox beats proxying every command.

Make the remote client a mirror of the log. Fetch once, stream after, reconcile on demand.

Harden containers by default. Drop capabilities, bind to loopback, mount only what that conversation owns.

Keep warm capacity for cold starts. A pre-warmed pool turns provisioning into a claim.

Part III — Safety

Chapter 9: Risk, Confirmation, and Hooks

The Problem: Who Decides Whether an Action Runs?

The agent now has hands (Chapter 7) and a place to use them (Chapter 8). Some actions are harmless: reading a file, listing a directory. Some are catastrophic: deleting a home directory, piping a download into a shell. Most are in between, and which is which depends on context the model may or may not understand.

There are really two questions. How risky is this action? And given that risk, should a person approve it? Mixing the two leads to systems where changing who must approve means rewriting how risk is judged.

The Options

  • A blocklist of commands. Fast and predictable, easy to evade with quoting or a second step.
  • Ask the model to rate its own actions. Cheap, uses context, and trusts the very actor you are worried about.
  • A separate judge. Another model or a rule engine reviews each action. Better separation, more cost.
  • Split the job. Analyzers assign a risk label; a policy turns the label into “run” or “ask”. Either side can change alone.

OpenHands’s Choice: Analyzer Labels, Policy Decides

Every action gets a SecurityRisk: LOW, MEDIUM, HIGH, or UNKNOWN. A security analyzer on the conversation assigns it. A confirmation policy reads it and returns one bit: should a person confirm? If any action in a batch should be confirmed, the conversation enters WAITING_FOR_CONFIRMATION and nothing in the batch runs.

flowchart LR A["Action batch"] --> Q{"Only finish or think?"} Q -->|yes| RUN["Run"] Q -->|no| AN{"Analyzer set?"} AN -->|no| UK["All UNKNOWN"] AN -->|yes| LBL["analyze_actions()
SecurityAnalysisEvent"] UK --> POL["Policy.should_confirm(risk)"] LBL --> POL POL -->|"any true"| WAIT["WAITING_FOR_CONFIRMATION"] POL -->|"all false"| RUN

Policies

Three policies ship:

Policy Confirms when
NeverConfirm never
AlwaysConfirm always
ConfirmRisky risk is at or above threshold (default HIGH), or risk is UNKNOWN and confirm_unknown is true (the default)

ConfirmRisky’s comparison is reflexive: with threshold HIGH, a HIGH action is confirmed. The threshold itself may never be UNKNOWN. A lone finish or think action never needs confirmation, whatever the policy.

The default for confirm_unknown matters. An action no one could assess is treated as risky, not safe.

Analyzers

Analyzer How it labels

A few details carry the design:

The model’s own label is ignored without an analyzer. If no analyzer is configured, any security_risk the model returned is discarded and the action is UNKNOWN. Tools annotated read-only are also UNKNOWN; their risk is not evaluated.

Two corpora. The pattern analyzer scans the executable part of an action (tool name and arguments) for destructive shell and code-execution patterns, and all fields, including the model’s thought, for injection and social-engineering text. An agent that merely thinks about rm -rf / while running ls is not flagged as destructive.

Uncertainty is reported. Shell analysis uses a shared tree-sitter-bash parse. When the parse cannot resolve a relevant structure, the analyzers return UNKNOWN rather than LOW, and ConfirmRisky then asks.

Fail closed. In the ensemble, a child analyzer that throws contributes HIGH. If all children say UNKNOWN, the result is UNKNOWN; otherwise unknowns are dropped and the highest concrete level wins. A stricter mode makes any UNKNOWN win.

Actor and judge can be separated. The guardrail-model analyzer exists because multi-step attacks are built from steps that each look benign. The acting model has no reason to flag its own reconnaissance; a separate judge reading the sequence might.

Approving and Rejecting

Approval is “run again” (Chapter 6). Rejection writes a UserRejectObservation for each pending action with the reason, so the model learns it was refused and why.

Hooks: Deterministic Rules You Own

Analyzers judge risk; hooks enforce your own rules. A HookConfig, loaded from .openhands/hooks.json or built in code, attaches hooks to six events: PreToolUse, PostToolUse, UserPromptSubmit, SessionStart, SessionEnd, and Stop. A matcher selects tools by exact name, wildcard, or regex. A hook can be a shell command, a single model prompt, or an agent with tools.

For command hooks, the exit code is the contract: exit 2 blocks; any other non-zero exit is a non-blocking error. Exit 1 does not block, and the code says so explicitly. A blocked PreToolUse turns into a UserRejectObservation with source hook. A blocked user prompt ends the turn. A Stop hook that refuses sends the agent back to work with its feedback.

The Trade-offs

  • Confirmation is per batch. One risky call pauses harmless siblings.
  • Asking on UNKNOWN is noisy. Safe by default, but users facing frequent prompts learn to approve without reading.
  • The model’s self-label is cheap and biased. It is the label source for LLMSecurityAnalyzer, and the reason other analyzers exist.
  • Hooks are only as good as their exit codes. A policy hook that exits 1 by mistake allows everything.

Apply This

Separate “how risky” from “who approves”. Labels and policies should change independently.

Treat unknown as risky. If no one could assess an action, ask.

Fail closed in combinators. A crashing checker should raise the risk, not lower it.

Scan what will execute separately from what was thought. Different threats live in different fields.

Use one exit code for “block”. Make it hard to block by accident and impossible to allow by crash.

Chapter 10: Secrets

The Problem: The Agent Needs Keys It Must Not See

Real tasks need credentials: a GitHub token to push, an API key to call a service. The agent’s commands need the values. But everything the agent touches is recorded: the log on disk, events streamed to a browser, the next prompt to the model. A secret that leaks into any of those is leaked for good.

Secrets also change. Tokens rotate, some are fetched from a server on demand, and a conversation may move to a container that cannot reach the place the secret came from.

The Options

  • Put secrets in the prompt. The model can use them directly, and they are now in the log and the provider’s records.
  • Put secrets in the process environment. The agent’s shell inherits everything, including keys it should never touch.
  • Give the model names, inject values at execution time, and mask outputs. The model writes $GITHUB_TOKEN; the runtime supplies the value only to commands that mention it, and scrubs the value from anything that comes back.

OpenHands’s Choice: A Registry of Named Sources

Each conversation has a SecretRegistry that maps names to secret sources. A StaticSecret holds a value. A LookupSecret fetches one from a URL when needed; a relative URL resolves against the current Agent Server. The model sees only names and descriptions, rendered into the dynamic part of the system prompt.

using $GITHUB_TOKEN"] --> SCAN["Registry scans the command
for secret names"] SCAN --> RES["Resolve only those sources"] RES --> ENV["Export as env vars
for this command"] ENV --> RUN["Terminal runs it"] RUN --> OUT["Output"] OUT --> MASK["Mask every known value

Inject Narrowly

Before a terminal command runs, get_secrets_as_env_vars(command) finds the secret names the command mentions and returns only those as environment variables. A command that never mentions AWS_SECRET_ACCESS_KEY never receives it. Failed lookups are remembered for a while, so a broken secret server does not stall every command.

Mask Broadly

Masking is the opposite: it covers every registered secret, not only the ones a command asked for. The docstring gives the reason: a value can reach output without its name ever appearing, for example a token embedded in a git remote URL. Cached values are not re-resolved for masking, so after a rotation the previous value is still masked.

Masking happens at several points:

Tool observations mask_secrets_in_model() walks every nested string in the observation, because tool output is not one text field

Streamed tokens A streaming mask, below

Streaming needs a buffer. A secret can be split across two chunks of a streamed reply, so per-chunk masking misses it. StreamOutputMask holds back the shortest suffix that could still grow into a secret, the length of the longest registered value minus one, and releases text only when it is safe.

Secrets at Rest and in Transit

On disk, secret fields go through one set of helpers in pydantic_secrets: serialize with a cipher (encrypt), or redact to a fixed sentinel; deserialize by decrypting, or treat the sentinel as missing. The repository’s contributor notes forbid a second, parallel redaction path. Chapter 3 covered the consequence: no cipher means no secrets after a restart.

Across a runtime boundary, sources are resolved first. Before handing secrets to a per-conversation container (Chapter 8), the server materializes them: each source is resolved and turned into a static secret, because the container may not be able to reach the original lookup URL.

The Trade-offs

  • Name matching is textual. A command that reads a secret indirectly, through a script that uses the variable, does not mention the name and will not receive it.
  • Masking only knows known values. A secret the registry never saw is not protected.
  • The stream mask delays text by up to the longest secret’s length.
  • Materializing breaks dynamic rotation inside the container; it gets a snapshot.

Apply This

Give the model names, never values. Describe what each secret is for.

Inject per command, mask per output. Narrow on the way in, broad on the way out.

Mask structured output deeply. Walk every string, not just the main text field.

Buffer streams by the longest secret. Otherwise a split token slips through.

Route all secret serialization through one helper. Two redaction paths will disagree eventually.

Part IV — Context

Chapter 11: Forgetting on Purpose

The Problem: The Log Grows, the Window Does Not

Every step appends events. A long task produces hundreds of them, and every model call resends the whole history. Cost grows with each step, and eventually the request no longer fits in the model’s context window.

The log, though, is append-only (Chapter 2), and that is a feature: it is the audit trail. So the question is sharper than “how do we shorten history”. It is: how do we make the model forget without deleting anything, and without producing a history the provider will reject?

The Options

  • Truncate the oldest messages. Cheap, but the task description and early decisions vanish, and a cut in the middle of a tool call breaks the provider’s pairing rules.
  • Summarize everything, every time. Keeps meaning, costs a summary call per step, and destroys the prompt cache constantly.
  • Summarize half, occasionally, at safe boundaries. Keep the head and the recent tail; replace the middle with a summary, and record that decision in the log itself.

OpenHands’s Choice: Condensation Events and a View

A condenser never edits the log. It emits a Condensation event that names the events to forget, carries a summary, and says where the summary goes. The condenser documentation compares these events to tombstones in systems like Cassandra and Kafka.

The model reads a View, not the log. The view applies every condensation it encounters: forgotten events drop out, the summary appears in their place. The log keeps everything; the view is what the model sees.

When to Condense

The main strategy is LLMSummarizingCondenser. It asks three questions every step:

Reason Trigger Strength
REQUEST Someone asked: the user via condense(), or the agent after a context-window error hard
TOKENS The view’s token count exceeds the smaller of max_tokens and the model’s input limit hard
EVENTS The view has more than max_size events soft

Soft means “condense if you can”. If a safe condensation is impossible right now, the condenser returns the view unchanged and tries again next step. Hard means the agent cannot proceed without it, so if the balanced strategy fails, it falls back to a hard context reset: summarize everything after the system prompt, trimming each event’s text and retrying up to five times if the summary call itself overflows.

How Much to Forget

The condenser keeps the first keep_first events and forgets enough of the middle to reach a target:

  • For EVENTS: keep about half of max_size.
  • For REQUEST: keep about half of the current view.
  • For TOKENS: cut until the view is under half the token limit.

If several reasons apply, the strictest wins. The class defaults are max_size 240 and keep_first 2; the default_condenser() used by the default agent and its sub-agents is tighter, with max_size 80 and keep_first 4. A condensation that would forget less than 10% of the view (minimum_progress) is treated as an error rather than a pointless summary call.

Safe Boundaries

Forgetting is not allowed just anywhere. The view computes manipulation indices: positions where events can be inserted or a range deleted without breaking the rules providers enforce. Four properties produce those rules:

graph TD MI["Manipulation indices"] --> P1["Tool-call matching
every action keeps its observation"] MI --> P2["Batch atomicity
tool calls from one reply stay together"] MI --> P3["Tool-loop atomicity
uninterrupted action/observation runs stay whole"] MI --> P4["Observation uniqueness
one answer per tool call"]

The condenser computes a naive cut, then moves both ends forward to the next safe index. The leading system prompt is never forgotten, whatever keep_first says, so the condensed request still opens with a system message. Observation uniqueness exists for crash recovery: a synthetic error can be written for an in-flight call, and then the real result arrives late.

Why Half, Occasionally

The condenser documentation explains the strategy as a balance of four things:

  1. Cost per call stays bounded because the view stays bounded.
  2. Cache damage is limited. Condensation destroys the prompt cache, but condensing regularly, by half each time, keeps the cost of rebuilding it low.
  3. Early context survives as a summary, and summaries are themselves summarized later.
  4. Recent context is untouched, so the agent can continue mid-task.

The summarizing condenser is configured with its own LLM, which can differ from the agent’s, and it turns off streaming for summary calls except for providers that require streaming. Because every LLM carries its own usage ID and metrics (Chapter 4), summary costs can be reported apart from the agent’s.

The Trade-offs

  • Summaries lose detail. Anything not in the summary is gone from the model’s view, though not from the log.
  • Each condensation breaks the cache. Condensing by half is a compromise, not a cure.
  • Event count is a weak proxy for size. One huge tool output can matter more than fifty small events; the token trigger exists for that.
  • Boundaries can block a condensation. A long unbroken tool loop may leave no safe place to cut until it ends.

Apply This

Never delete from the log; record a forgetting decision instead. The view applies it.

Keep head and tail; summarize the middle. The task and the current work are what matter most.

Distinguish soft from hard triggers. Skip a soft one when unsafe; always satisfy a hard one.

Compute safe cut points from API rules. Then a condensation can never produce an invalid request.

Condense by a large fraction each time. It caps cost and limits how often the cache is rebuilt.

Chapter 12: Prompts, Skills, and Memory

The Problem: What the Agent Knows Before It Starts

A capable model still knows nothing about your repository, your team’s conventions, the tools in this sandbox, or what it learned last week. Somebody has to tell it. But every word added to the prompt costs tokens on every call, and anything that changes per conversation can break the prompt cache from Chapter 4.

So there are three pressures: give the agent the right knowledge, give it only when relevant, and keep the cacheable part of the prompt stable.

The Options

  • One big system prompt. Everything always present. Simple, expensive, and the agent drowns in rules for situations it is not in.
  • Retrieval for everything. Embed knowledge and fetch by similarity. Flexible, but hard to predict which rule will appear.
  • Tiers and triggers. A stable base prompt; a per-conversation block; knowledge that loads when a keyword, a task, or a file path calls for it; and an index the agent can read on demand.

OpenHands’s Choice: Sections in Two Tiers, Skills With Triggers

The system prompt is assembled from sections. Each section is a pure function of a prompt context, with no template engine and no file access, so each can be tested alone. Every section renders into one of two tiers, matching the two blocks of SystemPromptEvent:

  • STATIC: stable across conversations and cached across them. Role, problem solving, code quality, version control, pull requests, security policy, risk assessment, tool guidance, process management, and more.
  • DYNAMIC: per conversation. Date and time, repository context, the list of available skills, secret names, memory, and any custom suffix.
graph TD SP["SystemPromptEvent"] --> ST["Block 1: STATIC
cached across conversations"] SP --> DY["Block 2: DYNAMIC
this conversation only"] ST --> S1["Role · persona · workflow"] ST --> S2["Security policy · risk assessment"] ST --> S3["Tool guidance · process management"] DY --> D1["Date / time"] DY --> D2["Repo context · available skills"] DY --> D3["Secret names · memory · custom suffix"]

Two override levels exist. persona replaces the built-in persona and coding-workflow sections but keeps the capability and policy sections, including security. system_prompt replaces everything and is documented as not recommended unless you know what you are doing.

Skills: Knowledge That Arrives When Needed

A skill is a named piece of knowledge, usually a Markdown file. What happens to it depends on its format and its trigger:

Skill Behaviour
AgentSkills format (SKILL.md), no trigger Listed in <available_skills> with name, description, and location; the agent reads the full text on demand
AgentSkills format, with trigger Listed, and also injected automatically when triggered
Legacy format, with trigger Listed; content injected on trigger
Legacy format, no trigger Full content always in the repository context

Three triggers exist. A keyword trigger fires when a word appears in the user’s message. A task trigger fires for a task type and may ask for input. A path trigger fires when the agent touches a file matching a glob; the code calls these skills “rules”.

sequenceDiagram participant U as User participant C as Conversation participant AC as AgentContext participant M as Model U->>C: "deploy the docs site" C->>AC: match keyword triggers AC-->>C: skill text, names activated C->>M: user message + extended content M->>C: edit docs/config.yml C->>AC: match path triggers for docs/** AC-->>C: rule text added after the observation

A triggered skill is recorded on the user’s MessageEvent (activated_skills, extended_content), so the log shows exactly what knowledge the model received. Skills already activated in a conversation are skipped next time.

Where skills come from. Project skills load from .agents/skills/ (preferred) and the legacy .openhands/skills/ and .openhands/microagents/ directories, including the git repository root when the agent runs in a subdirectory. User skills load from ~/.agents/skills/ and ~/.openhands/skills/. Third-party instruction files are recognized as always-on skills: AGENTS.md, CLAUDE.md, GEMINI.md, and .cursorrules. Public skills come from the OpenHands/extensions repository. disabled_skills turns individual skills off.

Memory: Two Indexes, Not a Diary

The agent can maintain MEMORY.md files in two tiers: the user tier in ~/.openhands/memory/ and the project tier in <workspace>/.openhands/memory/. With load_memory on, both indexes are read into one prompt-ready string on the first send_message() or run(), when the workspace path is finally known. Daily logs named by date live in the same directories but are deliberately not loaded; the agent reads them when it needs them.

Plugins: Bundles of Everything Above

A plugin bundles skills, hooks, MCP configuration, sub-agent definitions, and slash commands in one directory. The format follows Claude Code’s plugin layout for compatibility. Plugins can come from a marketplace, and a running conversation can load_plugin(); the server exposes the same as an endpoint.

graph LR PL["Plugin"] --> SK["skills/"] PL --> HK["hooks"] PL --> MC["MCP config"] PL --> AG["agents/"] PL --> CM["commands/"] SK --> CTX["AgentContext"] HK --> HC["HookConfig (Ch. 9)"] MC --> TL["MCP tools (Ch. 7)"] AG --> REG["Sub-agent registry (Ch. 13)"]

The Trade-offs

  • Triggers are literal. A keyword skill fires on a word, relevant or not, and misses synonyms.
  • On-demand skills cost a tool call. Progressive disclosure saves tokens up front and spends a step later.
  • The dynamic tier still varies per conversation. Only the static block is shared across conversations.
  • Many sources of instructions. Project, user, public, plugin, and third-party files can disagree; precedence rules must be learned.

Apply This

Build prompts from small, pure sections. Each can be tested and cached by tier.

Separate what is stable across conversations from what is not. Mark only the stable part for caching.

Let knowledge arrive by trigger, and record what arrived. The log should show what the model was told.

List skills by name and load bodies on demand. An index line is cheaper than a page.

Read other tools’ instruction files. Treating AGENTS.md and friends as skills meets users where they are.

Part V — Scaling Out

Chapter 13: Sub-agents, Goals, and Critics

The Problem: One Context Is Not Enough

Some work is better done by someone else. Exploring a large codebase fills the context with file listings the main task never needs again. A web search produces pages of text to extract one fact. A long task may stop early, sure it is done when it is not.

Three related needs follow:

  1. Delegation: hand a sub-task to a fresh agent and get back only the result.
  2. Persistence: keep going until an objective is truly met, not until the model says “done”.
  3. Quality checks: judge the result and try again if it falls short.

The Options

  • Do everything in one conversation. No coordination cost, but the context fills with detail, and the agent judges its own work.
  • Spawn independent processes. Full isolation, but configuration, secrets, and cost tracking have to be rebuilt each time.
  • Child conversations that inherit from the parent. Same machinery, a fresh context, settings passed down, costs rolled up.

OpenHands’s Choice: A Task Tool That Runs Child Conversations

The task tool set gives the agent one tool. Its action has a short description, the prompt to send, an optional subagent_type, and an optional resume with a previous task ID. A task manager turns that into a child conversation, runs it to completion, and returns the child’s final answer as the observation. The call blocks until the child finishes. Each task is tracked as running, completed, or error.

sequenceDiagram participant P as Parent agent participant T as Task tool participant TM as TaskManager participant C as Child conversation P->>T: TaskAction(description, prompt, subagent_type) T->>TM: start task TM->>C: create with inherited settings TM->>C: send prompt and run() C-->>TM: final answer TM-->>T: status completed + result T-->>P: observation

What the child inherits, from the task manager source:

Setting Rule
LLM A copy of the parent’s, with streaming off and its own fresh metrics
MCP servers The parent’s MCP configuration and tool provider; a definition may add its own mcp_config
Hooks The definition’s own hooks
Confirmation policy The parent’s, unless the definition sets one
Iteration and budget limits From the definition, else the parent
Workspace The parent’s working directory
Cost Recorded in the parent’s stats under task:<id>

A sub-agent also may not use a tool its parent lacks when the parent’s scope restricts tools; the manager refuses to create it. The task tool declares no resources (Chapter 7), so with a tool concurrency limit above 1, several tasks can run side by side in one step.

Defining Sub-agents

A sub-agent type is a Markdown file with YAML frontmatter: name, description, tools, model, skills, and similar fields, with the body as its system prompt. Definitions are registered with first-wins de-duplication by name, in this priority: agents registered in code, then plugin agents, then the project’s .agents/agents/ and .openhands/agents/, then the user’s ~/.agents/agents/ and ~/.openhands/agents/. Built-in types include general-purpose, code-explorer, bash-runner, and web-researcher.

graph LR P0["register_agent() in code"] --> P1["Plugin agents"] P1 --> A["{project}/.agents/agents"] A --> B["{project}/.openhands/agents"] B --> C["~/.agents/agents"] C --> D["~/.openhands/agents"] D --> R["Registry
first name wins"]

An older delegate tool also exists. It has two commands: spawn creates named sub-agents (at most five by default), and delegate sends each a task and runs them in parallel threads.

/goal: A Judge Outside the Agent

The /goal loop pursues an objective across several runs. A goal controller holds the objective, a separate judge LLM, and an iteration cap (10 by default). After each run, the judge audits the result and decides: continue with a follow-up message, or stop. The controller does no I/O itself. A driver, either the synchronous run_goal or an async task in the Agent Server, sends messages and runs the agent; both share the same decision logic.

stateDiagram-v2 [*] --> Running: start(objective) Running --> Judging: agent run finished Judging --> Running: not met, send follow-up Judging --> Complete: judge says met Judging --> Capped: max_iterations reached Running --> Interrupted: user interrupts Complete --> [*] Capped --> [*]

The outcome says whether the goal was complete or merely capped, so a caller never mistakes running out of rounds for success. The server publishes live goal status as a state-update event, which a UI can show as a progress chip.

Critics: Scoring the Work

A critic takes the events, and optionally a git patch, and returns a score. By default it runs when the agent finishes or sends a message; an all_actions mode evaluates every action, which the code warns is much slower. With iterative refinement configured, run() sends a follow-up prompt and runs again while the score stays below a threshold, up to a limit. The defaults are a threshold of 0.6 and 3 iterations.

Built-in critics include simple ones, such as “did the agent finish” and “is the patch empty”, and an API-based critic that calls a scoring service.

The Trade-offs

  • Blocking tasks. The parent waits for each child; parallelism needs a concurrency limit above 1.
  • Inheritance can surprise. A child that silently shares the parent’s confirmation policy or MCP servers is convenient until it is not.
  • Judges and critics are models too. They cost tokens and can be wrong in their own ways.
  • Summaries hide detail. The parent sees the child’s answer, not the child’s reasoning.

Apply This

Make delegation a tool call. It fits the existing event, confirmation, and cost machinery.

Pass settings down explicitly and document the rules. Then a child is predictable.

Charge child costs to the parent under a clear label. One bill, itemized.

Separate judging from doing. A controller that only decides can be shared by sync and async drivers.

Report “capped” separately from “complete”. Running out of tries is not success.

Chapter 14: The Agent Server

The Problem: An Agent Behind a Network Boundary

So far the agent has been a library: create a conversation, call run(). A real product needs more. A browser UI must start conversations, stream events as they happen, approve actions, and reconnect after a dropped Wi-Fi link. A cloud service must run many conversations in many sandboxes. A sandboxed workspace must be driven from outside (Chapter 8).

All of that requires putting the agent behind a network API without changing its semantics. The question is what that API should look like, and what happens when the connection is imperfect.

The Options

  • Request-response only. Poll for new events. Simple and robust, but slow and wasteful.
  • A single WebSocket for everything. Fast, but commands lose the clarity of HTTP status codes, and a reconnect has no standard way to catch up.
  • REST for commands and history, WebSocket for live events, with sequence numbers for catch-up. Each channel does what it is good at.

OpenHands’s Choice: FastAPI REST Plus Event Streams

The Agent Server is a FastAPI app. REST endpoints create and control conversations; WebSockets stream events. Inside, three services do the work:

  • ConversationService keeps track of all conversations and hydrates them lazily from disk when first used.
  • EventService wraps one conversation: it runs the agent, persists events, and publishes them.
  • PubSub fans each event out to every subscriber: WebSocket clients, webhooks, and anything else listening.
graph TD UI["Canvas / SDK client"] -->|REST| R["Routers"] UI <-->|WebSocket| WS["Socket endpoints"] R --> CS["ConversationService"] CS --> ES1["EventService
conversation A"] CS --> ES2["EventService
conversation B"] ES1 --> LC["LocalConversation
(the SDK loop)"] ES1 --> PS["PubSub"] PS --> WS PS --> WH["Webhooks"] CS -.-> SLOT["Run slots

Inside the server, each conversation is an ordinary LocalConversation. The server adds transport, not new agent behaviour. On the client side, RemoteConversation speaks the same API, so code written against the SDK works whether the agent runs in-process or across the network.

The Control Surface

The conversation routes map directly onto the concepts of earlier chapters:

Route Concept
run, pause, interrupt The run loop and its two ways to stop (Ch. 6)
confirmation_policy, security_analyzer The safety gate (Ch. 9)
switch_llm Changing models mid-conversation (Ch. 4)

Admission control. At most max_concurrent_runs conversations (10 by default) can run at once. A run that cannot get a run slot is refused with HTTP 429 rather than queued indefinitely.

Shell commands outside the agent. A separate BashEventService runs commands sent directly by a client. Its events are not added to the agent’s event stream and are not visible to the agent.

Deferred initialization. For warm pools of pre-started server pods, OH_DEFERRED_INIT=true boots the server dormant: stateless services start, but every /api/* route answers 503 until an authenticated POST /api/init delivers credentials, workspace paths, and session keys.

Streaming Without Losing Events

WebSockets authenticate with the first message rather than a URL token. The newer session protocol at /sockets/session/{id} sends three kinds of frames:

persisted events, numbered;

streaming tokens;

announces an item;

A reconnecting client sends the last sequence number it saw (after_seq) and receives every durable frame after it. Deltas are disposable because the durable event they build up to arrives anyway. Frames are capped at 4 MB.

sequenceDiagram participant C as Client participant S as Agent Server C->>S: GET events (REST history) S-->>C: events up to seq 120 C->>S: WebSocket connect + auth message C->>S: resume after_seq = 120 S-->>C: durable 121, 122... S-->>C: deltas (tokens) as they stream Note over C,S: connection drops C->>S: reconnect, after_seq = 131 S-->>C: durable 132...

The Trade-offs

  • Two channels to keep consistent. REST history and WebSocket events must agree on numbering, and the client must merge them.
  • Dropped deltas mean jumpy text. Correctness is preserved; smoothness is not guaranteed.
  • 429 pushes retry logic to clients. Better than hidden queues, but every client must handle it.
  • Lazy hydration delays first access. A cold conversation pays a load cost on first touch.

Apply This

Put the network around the loop, not inside it. The server runs the same conversation the library does.

Use REST for commands and WebSockets for events. Each keeps its strengths.

Number durable events and resume by number. Reconnects become a simple catch-up.

Mark streaming fragments as droppable. Only durable events need delivery guarantees.

Refuse work explicitly when full. A 429 is honest; an invisible queue is not.

Chapter 15: Agent Canvas, the Face on Top

The Problem: One UI, Many Backends, Many Agents

The repository named OpenHands/OpenHands is now the Agent Canvas, a React and TypeScript web app. It has to show conversations that may run on a laptop or in the cloud, with agents that may be OpenHands’s own or another vendor’s coding CLI. It must stay correct while the server API evolves in a separate repository.

The Options

  • Call the server directly from components. Fast to write, and every API change ripples through the whole UI.
  • A hand-written client layer. Centralized, but it drifts from the server unless someone keeps it in sync by hand.
  • A generated client from the server’s schema, behind data hooks. The schema is the contract; the UI only talks to hooks.

OpenHands’s Choice: A Generated Contract and Data Hooks

The contract flows one way: the SDK’s Agent Server publishes an OpenAPI schema; the TypeScript client is generated from it; the Canvas uses that client. Canvas code reaches the server only through TanStack Query hooks for server data, with Zustand stores for client state. A test, no-direct-agent-server-calls, fails the build if a component calls the Agent Server directly.

agent-server calls"] -.guards.-> UI

The Canvas also records the minimum Agent Server version it needs in config/defaults.json, so an old server is detected rather than misread.

Local or Cloud

A backend is either local or cloud. Locally, an ingress on port 8000, a small reverse proxy, routes requests by longest matching prefix: in its documented example /api/automation goes to the automation service on 18001, /api to the Agent Server on 18000, and everything else to a default backend serving the UI. The same UI talks to OpenHands Cloud when the backend kind is cloud.

Developer run modes cover the cases in between: a full stack, a minimal stack, static files only, and a mock backend for UI work with no server at all.

Loading a Conversation

Opening a conversation follows the pattern from Chapter 14. The Canvas loads history over REST, then opens a WebSocket and asks the server to resend everything after the last sequence number it has. Streaming text deltas are batched before rendering so a fast token stream does not re-render the page on every token.

Other Agents in the Same Window

Canvas can drive agents that are not OpenHands’s own. Through the Agent Client Protocol (ACP), the Agent Server spawns a coding CLI such as Claude Code, Codex, Gemini CLI, Pi, or OpenCode as a child process and talks JSON-RPC to it over stdio. In the SDK this is an ACPAgent, so the conversation, event log, and UI are the same whichever agent is inside. If the CLI is already logged in, that login is used before any API key. Pi and OpenCode are local-only.

sequenceDiagram participant UI as Canvas participant AS as Agent Server participant ACP as ACPAgent participant CLI as Coding CLI UI->>AS: send message AS->>ACP: step ACP->>CLI: JSON-RPC over stdio CLI-->>ACP: updates, tool calls ACP-->>AS: events AS-->>UI: WebSocket frames

The Trade-offs

  • Two repositories, one product. A UI change may wait on a server release; the version pin makes that explicit.
  • Generated clients follow the schema exactly. A badly modelled endpoint is faithfully reproduced in TypeScript.
  • ACP agents are black boxes. Their internal loop, tools, and safety checks are their own, not OpenHands’s.
  • Local mode is a small distributed system. Three services and an ingress must all be up.

Apply This

Generate the client from the server’s schema. Make the contract a file, not a convention.

Fence API calls behind hooks, and enforce it with a test. Rules that are checked are rules that hold.

Pin the minimum server version in config. Incompatibility should be an error message.

Wrap foreign agents in your own event model. Then one UI can show them all.

Part VI — Looking Back

Chapter 16: What Holds It Together

Looking Back

Fifteen chapters covered a lot of parts: events, state, models, the step, the loop, tools, workspaces, safety, secrets, condensation, prompts, sub-agents, the server, and the Canvas. A few ideas show up again and again.

Five Recurring Ideas

1. The log is the truth. Everything is an event, events are appended and never edited, and state is rebuilt from them. Pausing, resuming, forking, condensing, streaming, and auditing all follow from this one choice.

2. Separate what the model sees from what happened. The view is computed from the log: condensations hide events, secrets are masked, skills are attached. The model gets a curated picture; the log keeps everything.

3. Same interface, different place. Local and remote conversations, local and remote workspaces, and the in-process and server loops share interfaces. Location is a deployment choice, not a code change.

4. Explicit limits everywhere. Iteration caps, budgets, stuck detection, concurrency slots, retry policies, minimum condensation progress, frame sizes. Each turns a vague failure into a named state.

5. Policy as data. Confirmation policies, security analyzers, hooks, tool filters, sub-agent definitions, and skills are configuration, not code paths. They can be swapped, combined, and inherited.

The SDK repository’s own AGENTS.md files, kept next to the code in many packages, explain local design rules and are the best next step for readers who want to change OpenHands itself. The condenser README and the agent and conversation modules are good starting points.

Apply This

Pick one source of truth and derive everything else. For agents, an event log works well.

Give each failure a name. Every limit should end in a state a user can understand.

Keep the boundary interfaces boring. If local and remote look the same, everything above them stays simple.
