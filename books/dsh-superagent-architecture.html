An Architecture Analysis

The Architecture of dsh-superagent

How a proactive coding agent spends the least human attention — design goals, high and low levels, the reasons behind them, and one request’s walk through the source.

Subject: dsh-superagent, a DeepSeek research prototype 10 chapters · 6 figures · ~18.8k words November 2026

Every agent system competes for the same scarce resource: the attention of the people it works for. An agent that can act for a whole team can also waste a whole team’s attention — with questions nobody needed to answer, notifications nobody needed to see, and pull requests nobody needed to review. dsh-superagent, a research prototype from DeepSeek, is built around that observation. It is a proactive coding agent for one GitHub repository that listens, decides, works, and speaks, and every part of it is judged by how little attention it costs.

This book reads that prototype from the outside in. It begins with the design goals and the small domain vocabulary the system is built on, then walks through the high-level runtime and the low-level machinery — a synchronous, transactional core surrounded by a durable effect queue — and asks the more interesting question: why this shape, and not another. A complete request is followed from a GitHub mention to a merged pull request, and the closing chapters equip the reader to walk the source alone.

The analysis is grounded in the repository’s own code and documents; the file paths cited throughout refer to the public prototype. Like the system’s own numbered documents, the chapters are meant to be read in order — each one assumes only what came before.

      Chapter 1

      A Coding Agent That Asks to Be Ignored

      dsh-superagent is a proactive coding agent that serves exactly one GitHub repository. It grew out of a DeepSeek team's day-to-day development work, with much of the engineering done by coding agents, and its README is blunt about its status: research code, adapted for publication, not production-ready software. It ships as a bundle for DeepSeek Harness — DSH, the host application that runs agent sessions, equips them with tools, and serves their web interface. Installed into a DSH profile, the bundle turns the agent into a quiet member of the repository's daily life: it reads issues, comments, pushes branches, and opens pull requests under a GitHub account the whole team can see and talk to.

      What it does with that membership is deliberately narrow. The agent listens to GitHub — normally by polling its own account's notifications, with optional switches for every new issue, pull request, comment and default-branch CI run — and, if the team wants, to Feishu chats through a bot. When someone the team has allowed mentions the agent and asks for work, the request becomes a Ticket, the system's unit of authorized work, usually within the default one-minute polling interval. The agent confirms once, naming what it will do. It then works in its own agent session and its own working directory, and answers in the conversation where it was asked, often as a pull request. A web panel summarizes everything and shows first what needs a person.

      Two kinds of sessions divide the labor. A single main Session, called orchestrator in the code and prompts, receives every incoming event, judges which deserve work, and dispatches; one Executor Session per Ticket, called worker, does the actual coding in its own directory. The split matters for the theme of this book: the part that talks to people is not the part that changes files, so each can be given exactly the permissions, and the manners, its job needs.

      Operationally the system is one small thing rather than a cluster. It runs as a single DSH process, started by a service script inside a tmux session so it survives a detached terminal, with its panel bound to localhost (docs/006-deployment.md). All durable state — every event received, every Ticket, every queued side effect — lives in one SQLite file inside a configured state directory; that file is the thing to back up before an upgrade. The agent's identity is a dedicated GitHub account with write access and its own signed-in GitHub CLI, and the host steers workers' git and GitHub calls onto that account's credentials and away from the operator's.

      Why so much care around what the agent does not do? Because an agent that can act for a whole team can also waste a whole team's attention. The project's founding observation, written down in its philosophy document, is that attention is the resource the system actually consumes: every message, notification, question, setting, panel element and paragraph of documentation costs someone's attention, and each must give back more value than it costs, or it is removed (docs/000-philosophy.md). Code is cheap for an agent to produce and expensive for a person to review; an agent that generates both without limits does not create capacity. It destroys it.

      The title of this chapter compresses that rule. The agent acts only when an allowed person asks, or when a rule the team wrote allows it; work nobody requested begins in an observe mode that records what the agent would have done without doing it, so autonomy is widened from evidence rather than assumed. It speaks only when a person must act or can use a result: one acknowledgement, silence while it works, a message when a result is ready, a decision is needed, or it cannot finish. Between those moments, being ignored is what it is designed for.

      The panel is the other half of the same idea. A supervisor opening it should be able to leave quickly: it answers three questions in order — does anything need me now, is the system healthy, what is the history of this work — and a healthy state takes no space on the screen (docs/005-panel.md). An agent that spends attention carefully and a panel that spends screen time carefully are one design, not two.

      An honest caveat before going further. The README states that this code was adapted for publication, so it is not identical to the team's internal version, nor to the system described in their paper, Exploring Super-agent Design: Towards a More Autonomous Agent System; some designs discussed in the article are directions for future work and are not implemented in this prototype. This book therefore grounds every claim in the published repository — its documents and its TypeScript source — and where the code is rough, it says so.

      The rest of the book follows the repository's own reading order, because the repository numbers its documents so that each builds only on the ones before it. The next chapter states the design goals in full and traces each one to the engineering that makes it hold. A chapter on the domain model then introduces the working vocabulary — Source, Trigger, Thread, Eval, Mandate, Ticket and their neighbors — together with the rules that decide who may start work and how permission becomes recorded data. Two chapters descend to the low level: the pure core where every decision is made, and the edges — the effect queue, the outbox, the executor, the sessions and the Source plugins — where every decision is carried out. The chapter after them asks why this shape and not another. One request is then followed end to end, from a GitHub mention to a merged pull request, and the final chapters are a guide to reading the source alone, and the observations that close the analysis.

      Chapter 2

      Design Goals

      At the top of its philosophy document, dsh-superagent names the quantity it works to minimize: "Take as little human attention as possible, and give as much value as possible" (docs/000-philosophy.md). The sentence is a unit of account, not a motto. A message, a notification, a question, a setting, a panel element and a paragraph of documentation each cost someone's attention, and every part of the project is judged by that cost: each must give more value than it takes, or it is removed. The rest of the chapter reads the goal through the agent's behavior, the design, the machinery, and finally the operator.

      What the principle demands of behavior

      The behavioral half of the principle is a set of habits the host enforces rather than requests. The agent acts only when asked, or when a written rule allows it. "Asked" has a strict meaning: the request must address the agent directly and come from someone on the allowed list of a Source — a stream of events the agent listens to, such as GitHub or Feishu — and that list is the Source's part of the Policy, the versioned rules for accepting work. Work nobody asked for needs a rule the team wrote, and even then it starts in observe mode: the agent assesses what it would have done and records an ignore marked "would accept", and nothing is accepted (docs/002-authorization.md).

      The agent speaks only when a person must act or can use a result. It confirms a request once, naming what it will do, stays quiet while it works, and writes again when a result is ready, when it needs a decision, or when it cannot finish. Messages are short, and they go to the conversation where the request was made.

      When it needs a person, the agent asks one concrete question at a time. The question is an Attention — the open question on a Ticket, the system's unit of authorized work, that waits for a person's answer — and it travels as a structured field in the report of the Executor Session, the worker session that runs one Ticket, not as prose. The domain model explicitly rejects inferring "waiting on a person" from a report's free text (docs/001-domain.md); a structured fact reaches the panel and the right conversation, while a question buried in a paragraph stays buried.

      The agent stops by impact, not by effort: a local change goes as far as a reviewable result, and a change that needs a design decision stops with a clear question. And it reports honestly — a draft is marked unfinished, a failure is reported as a failure, and a limit is never bypassed to avoid asking.

      What the principle demands of design

      The design-side goals concern the cost of understanding the system itself. The first is few concepts: the domain holds only its domain concepts — Source, Trigger, Thread, Ticket and their neighbors — plus concrete implementations such as GitHub and Feishu. A business need becomes an attribute of an existing concept or a line of prompt text, never a new concept. The clearest example is a person, which is not a domain concept: a Trigger, one immutable event, carries its actor's identifier as the Source gives it; an allowed list is a Source's part of the Policy; the fact that one human has accounts on two Sources is prompt text the agents read (docs/001-domain.md).

      The second is few settings. A default replaces a setting when one value suits almost every team, and behavior a team can describe in words is prompt text, not a setting. Merging shows the split plainly: the host has no merge-specific decision logic, and when auto-merge is allowed, and under what line-count limit, is governed by a prompt section called Delivery requirements (docs/003-execution.md). The team edits words; the behavior changes.

      The third is a panel that shows only what needs a person. Opening it answers, in order, whether anything needs the reader now, whether the system is healthy, and what became of one piece of work; healthy states take no extra space, and a number appears only when it changes what the supervisor does (docs/005-panel.md). The fourth is documents that read in order: each numbered document builds only on the ones before it, introducing no concept ahead of its turn.

      What the principle demands of machinery

      Each product goal above implies an engineering requirement, visible in the repository as a concrete mechanism. The first is idempotent intake, because discipline begins at the door. A poller sees the same event twice, and a duplicate work item would charge the team twice for one request. A Trigger is therefore stored once: intake checks the Trigger's id and returns duplicate for a repeat (src/core/intake.ts), and accepting a Trigger twice creates one Ticket — a later decision for a Trigger that already started a Ticket returns that Ticket's existing Decision (src/core/engine.ts).

      The second is durable stored work, because an agent that speaks rarely cannot afford to lose its one message. Everything the system does after a decision — relaying a candidate to the main Session, the orchestrator session that judges requests, whose assessment role the code calls MasterAssessor; launching an Assignment, the binding of a Ticket to one Executor instance; delivering an Input to a Ticket; or sending a reply on a Channel, the write side of a Thread — is stored first and done afterwards (docs/003-execution.md). The mechanism is Effects, a durable SQLite-backed queue that persists side effects inside command transactions and dispatches them after commit, with per-kind ordering and exponential backoff (src/app/effects.ts); the Outbox persists outgoing messages as receipts before any send is attempted (src/app/outbox.ts).

      The third is authorization as recorded data. What an accept grants is a Mandate: an immutable record of the request's strength, the scope of work it allows, the Policy version it was accepted under, and the basis — how the Gate, the deterministic first layer of Eval, admitted the Trigger, and from whom (src/core/model.ts). Before an ended Ticket resumes, its Mandate is revalidated against the current Policy; if the sender has left the list or the matched rule has gone, the Mandate is revoked and the work stays ended (src/policy.ts, docs/002-authorization.md). Authorization is data the system can show you, not a recollection it reconstructs.

      The fourth is restartability. All state lives in one SQLite file, <stateDir>/orchestrator.sqlite, opened by the Store (src/app/runtime.ts). After a restart, Assignments that were running end with "host restarted", and their replacements start with a recovery note telling the worker to check its directory, git history and GitHub before repeating any outside action (docs/003-execution.md). Waiting effect rows sit in SQLite until the next start (src/app/effects.ts).

      The fifth is full auditability, because silence about an input is acceptable only when every input has a visible fate. Each Trigger receives a Disposition, the record of where it went: filtered by its Source's scope, evaluated to a Decision, fanned out to subscribed Tickets, or handed back by an Executor that found it beyond its Ticket (src/core/model.ts). Even a filtered Trigger keeps its record, with the Source's reason (src/core/intake.ts). What happened to a message is a lookup, not an investigation.

      The operator's side of the contract

      The philosophy document ends by turning to the person running the agent: the agent messages people under accounts the team sees every day, every message costs colleagues' attention, and the operator is responsible for it (docs/000-philosophy.md). This is the same contract, seen from the operator's side.

      Start narrow, with a short allowed list and proactive work only recorded, and widen both once what the agent would have done looks right. Tune for less noise: when the agent is noisy, make its prompts shorter and stricter, or pause it — not more messages that explain the noise. Do not use it to produce volume; mass pull requests and broadcast messages cost the team more than they give. And own what it says: read what it posts in your name, and correct it in the prompts when it is wrong.

      The principle thus binds agent, machinery and operator into one budget. Its measure is the philosophy document's closing line: the right help at the right time, and nothing at any other time.

      Chapter 3

      The Domain Model: A Small Vocabulary with Strict Rules

      Every event that reaches dsh-superagent travels one path, and the domain model is that path written as nouns. A Source watches a stream of events and turns one event into a Trigger. The Trigger lands on a Thread, where the path splits: a Subscription fans it out as context to the Tickets already subscribed to that Thread, while every other Trigger enters an Eval. The Eval ends in a Decision, and an accepting Decision creates a Ticket carrying a Mandate. An Assignment hands the Ticket to an Executor, and the results travel back to the Source through a Channel. The discipline is stated outright: code, tools, panel and documents use these terms and no others (docs/001-domain.md).

      The listening side

      Five concepts stand where the outside world becomes domain data. A Source is a stream of events; a Source kind is a reusable implementation, and a Source instance is one configuration of it — whether it runs and what it listens to. The Source is the model's customs office: it defines what counts as an event, including conditions that only hold over time — "no assignee for N hours" is an ordinary Source that waits and checks again — and it drops the agent's own messages and out-of-scope events before they enter the domain. It also holds its own read position and bot identity, so a restart never replays old events as new work.

      What passes the door becomes a Trigger: one immutable event carrying the Source's own metadata, such as its actor. The type in src/core/model.ts keeps it that small: text and meta are untrusted external data, and human and addressed are Source-declared facts, not conclusions the core draws. A Trigger belongs to one or more Threads and is the unit of idempotence and of audit: accepting the same Trigger twice creates one Ticket, and Engine.receive in src/core/engine.ts answers stored, duplicate or filtered — a replayed event is recognized, not rejudged.

      A person, pointedly, is not one of these concepts. A Trigger carries its actor's identifier as the Source gives it; an allowed list is a Source's part of the Policy, written in that Source's identities; and one human holding accounts on several Sources is prompt text the agents read when they need it. The model never joins identities across Sources: each Source speaks only its own names.

      A Thread is Triggers in time order, with the Source defining which Triggers form one: an issue's conversation, a chat topic. At most one Eval runs on a Thread at a time, and Triggers that arrive meanwhile merge into the next batch. A Thread may carry several Tickets, and it holds its Subscriptions, its running Eval and its Decision history, giving each Eval a consistent view and its context. One Trigger can land on several Threads; the Threads it spans are Correlated, and Correlation adds context and never routes: it lets an Eval follow related evidence, while routing belongs entirely to Subscriptions.

      A Channel is the write side of a Thread: an address to write to, defined by the Source — a topic reply, a review comment — and a Thread may have several. A Ticket holds a set of Channels rather than one, because acknowledgments, replies, pull requests and resolved reviews are all writes through a Channel (ChannelRef in src/core/model.ts).

      The judging side

      The Policy is the versioned rulebook: the assessment rules, plus each Source's part of it — who may originate work through that Source, in that Source's identities, how the list is synchronized, and which bots may produce candidates. Rules, accept mode and Source parts together form a Policy version. A change that bears on a live Ticket, such as a changed rule it was accepted under, is delivered to its Assignment as an Input; it does not revoke Mandates, but it discards a running Eval rather than let it finish against a rulebook that no longer holds.

      The Eval is the judgement on a batch of Triggers, in two layers. The first, the Gate, is deterministic: it checks the sender against the Source's Policy and answers who may originate work, and with what strength. The second, the Assessment, is the model's judgement, run by the main Session through the MasterAssessor (src/app/assessment.ts). An Eval's inputs are exactly the Trigger batch, a snapshot of the Thread, every Ticket on the Thread including ended ones, and the current Policy; its output is a Decision; it holds no state between those moments. Each Source's Policy also carries an admission table, whose cells decide whether a message becomes an explicit request, an inferred candidate, or nothing (docs/002-authorization.md).

      The Decision is the recorded outcome: accept, stop, ignore or unavailable. Decisions explain themselves in structured reason codes — timeout, policyChanged, stopNotExplicit — defined in src/core/reasons.ts, with said carrying words an assessor or a person wrote.

      Strength belongs to the vocabulary itself, not to any one module: an Eval carries it, a Decision records it, and a Mandate freezes it. An explicit request comes from a listed person who addresses the agent, from a person's follow-up on a Thread that already has a Ticket, or from an admission cell set to explicit. An inferred candidate is everything the system might act on without a direct ask: a follow-up from an unlisted person, a cell set to inferred, or the message of a bot on the Source's bot list — a listed bot can produce an inferred candidate, never an explicit request. Everything else is not admitted.

      The accept mode, part of the Policy version, is the Policy's answer to how far inferred strength may carry. In off, nothing inferred becomes a candidate. In observe, the default, inferred candidates are assessed but a positive assessment is recorded as an ignore marked "would accept", and nothing starts. In auto, a positive assessment accepts. Explicit requests work in every mode, which is why the intended path is to start in observe and switch to auto once the recorded Decisions look right.

      The working side

      An accepted Decision grants a Mandate: the Policy version it relied on, the scope, the strength, the matched rules, the sender's identity on that Source, and how the Source received the Trigger (MandateBasis in src/core/model.ts). The Mandate is a warrant, not a lease. It is immutable — wider scope means a new Ticket — and a Ticket's end does not end it. Exactly three operations change a Mandate: an accept creates it, a person's stop withdraws it, and a failed revalidation revokes it. Before an ended Ticket resumes, its Mandate is revalidated against the current Policy, where a weakened admission cell or a removed sender quietly catches up with old work.

      The Ticket is the unit of authorized work, and only an Eval creates one. It refers to its Mandate and holds its Channels and Inputs. Its life is its own: it goes open to ended, and back to open when a person's message on one of its Threads resumes it — unless a person stopped it — defining its own state instead of following the Executor's session, because a Ticket can be handed off, resumed, or run by several Executors.

      The Executor itself, with its Sessions and directories, is outside the domain. It connects through an Assignment, the binding of a Ticket to one Executor instance. A Ticket has several over time, each going pending, running, ended independently of the Ticket; on the Executor's side, only an Assignment's final report may end the Ticket. Who executes is inside the domain; how execution lives is not.

      The Subscription is the many-to-many relation between Tickets and Threads, held by the Thread. A matching Trigger fans out to every live subscribed Ticket with no check of who sent it — which is the point: later discussion reaches the Executor without anyone mentioning the agent again. A person's message that reaches a Ticket this way takes no Eval; it belongs to that Ticket's Executor to decide. An Executor may also follow a Thread for context only, which reaches its Ticket the same way but lends no authority and does not resume it. An ended Ticket keeps its Subscriptions — even that of a closed or merged pull request — so a person's message resumes the same work under the same Mandate, with no Eval or Decision; a Ticket a person stopped receives nothing.

      Inside a Ticket, the remaining concepts record the conversation. A Report is the state an Assignment reports to its Ticket — progress, waiting, ready, blocked, failed or dropped; the predicate waitsForPerson in src/core/model.ts reads them: a Ticket waits for a person when its latest Assignment reported blocked or failed and no human message has arrived since. An Attention is a question that waits for a person's answer, carrying the Trigger that raised it so the answer returns to its conversation. An Input is any context delivered to a Ticket: a fanned-out Trigger, a Policy change, a resume, or plain text. A Disposition records where a Trigger went — filtered, evaluated or fanned out. It grants nothing, but it decides who decides a person's follow-up: the fact the resume and hand-back rules turn on.

      What the model refuses

      The most instructive page of docs/001-domain.md may be its last table: concepts considered and turned away. Recording rejections is itself a design artifact: a vocabulary stays small only if the pressure to re-grow it is answered in writing, and each rejection encodes a rule that would otherwise live in a maintainer's memory — the next contributor who wants "just a simple wait state" meets the documented reason why waiting belongs to Sources.

      Aggregates and code homes

      The model groups its concepts into three aggregates, each one boundary of consistency. A Source holds its read position, so replay is its problem alone. A Thread holds its Subscriptions, its running Eval — serial, merging Triggers that arrive meanwhile into the next batch — and its Decision history. A Ticket holds its Assignments, Channels and Inputs, and refers to Decisions by id.

      In code, the vocabulary has two homes. src/core/model.ts defines the types — Trigger, Thread, Evaluation, Decision, Mandate, Ticket, Assignment, TriggerDisposition — and the predicates that keep those rules consistent: followupOwners, settled, waitsForPerson, liveTicket. src/core/stage.ts classifies a Ticket's stage — waiting on a person, working, idle or ended — in ticketStage, reading the same Reports. The deterministic halves of judgement sit just outside the core: the Gate and Mandate revalidation in src/policy.ts, the reason codes in src/core/reasons.ts. And every record above has one writer, the Engine in src/core/engine.ts, so the vocabulary is not just shared but centrally enforced.

      Chapter 4

      The High-Level Architecture

      dsh-superagent does not run as a service beside DeepSeek Harness (DSH); it runs as plugins inside a single DSH host process. The main entry, src/index.ts, exports an apply function that constructs one Runtime and awaits its readiness. The same package builds two more plugins — src/sources/github.ts and src/sources/feishu.ts, bundled by tsdown.config.ts and exported in package.json as ./github-watch and ./feishu-watch — and the bundle's cordis.patch.yml inserts all three into the host, with Feishu disabled until a bot is configured, alongside the two agent presets the Sessions run under. A Source, the term for a connection to a platform such as GitHub or Feishu, is therefore not a watcher process of its own: each Source plugin injects the orchestrator service that the Runtime publishes on the Cordis context and registers its kind through it (src/sources/github.ts:111).

      One process owns one state directory and one SQLite file. The Runtime's constructor creates machine.stateDir, locks the directory with lockSync from proper-lockfile (src/app/runtime.ts, the lock considered stale after thirty seconds), and only then opens the Store on <stateDir>/orchestrator.sqlite. The lock sits on the directory rather than the database file because opening the database may migrate its schema, and a second process writing the same state would race that migration. If construction fails, the Runtime closes the Store and releases the lock, so an in-process restart can reacquire both. Everything durable lives behind that one lock: Triggers, Tickets, queued effect rows, outbox receipts, settings and prompt versions.

      Three layers, one direction

      The layering is a rule about imports, and the repository holds to it. At the center sits the pure core, src/core: the Engine, the domain types in src/core/model.ts, and the ports the Engine consumes. It is synchronous, performs no I/O, and imports nothing outside itself except Node's hashing (node:crypto in src/core/ids.ts, used to derive ids). The rule is stated in docs/007-architecture.md under "Dependency rules"; the directory's imports amount to exactly that. The payoff is that every domain rule — batching, resume, the attention lifecycle — can be exercised against the in-memory repositories of src/core/memory.ts with no database, no clock and no network.

      Around the core sits the application layer, src/app. The Runtime (src/app/runtime.ts) is the composition root, the one class that knows how all the parts connect; it contains no domain rules. Alongside it live the Store (SQLite persistence), the Effects queue, the Outbox, Sessions, Settings, Prompts (revisioned configuration), and src/app/http.ts with the panel's routes. This layer owns durability and timing, and it implements the ports the core declared: the Store realizes Repositories, the Outbox realizes the core's Outbox interface, so the core never learns which database or chat platform stands behind its types.

      At the edges, adapters translate. src/sources implements GitHub and Feishu behind the SourceKind protocol (src/sources/kind.ts) and imports nothing from src/app; its plugins reach the application only through the injected SourceHost interface, and a kind's own code sees the narrower SourceContext. src/executor holds the DshExecutor, which turns accepted work into agent Sessions. src/client is the management panel, a browser bundle that imports only types from the host side plus a fixed list of plain values such as error codes and filter lists, so it can be bundled without pulling the server along. Dependencies point inward: the edges may know the core's types, and the core knows nobody.

      The Engine: one decision point

      Every state change that matters passes through one class. The Engine (src/core/engine.ts) is the only writer of Triggers (inbound events), Threads (conversations), Decisions (recorded outcomes), Tickets (units of accepted work) and Assignments (the runs of a Ticket); Sources, Executors and the panel all ask it to change these things rather than changing them. It receives its collaborators as ports from src/core/ports.ts: Repositories for durable state, a getter for the current Policy (the versioned authorization rules), SourceScope for whether a Source listens to a Trigger, an Assessor for judging candidates, an Executor for running accepted work, and an Outbox for Channel writes (a Channel names the conversation a reply goes to).

      All Engine methods are synchronous, and each command wraps its work in one transaction through repo.atomic(...); evaluateDue opens a separate transaction for each Eval or Ticket it changes, so a failure abandons little. Invalid requests throw UserError. Callers do not receive the Engine itself but the Pick of their role: EngineForSources exposes receive, bindThread and threadClosed; EngineForMainSession carries decide and attach; EngineForPeople the stop and retry commands; EngineForSettings only policyChanged; EngineForExecutor the past-tense facts such as assignmentStarted and report. The naming encodes the contract — commands are imperative (stopTicket), facts reported by adapters are past tense — and a Source literally cannot stop a Ticket, because the type it holds has no such method.

      Two asynchronous engines around a synchronous one

      The Engine's synchrony is half the design; the other half is what happens outside its transactions. Two schedulers turn the synchronous core into a running system.

      Passes (src/app/passes.ts) is the heartbeat. Started by the Runtime, it runs one pass every two seconds — setInterval(..., 2000) — and immediately whenever a Source stores a Trigger, or a tool, a settings save or an HTTP route asks for one. A pass is effects.kick() followed by Engine.evaluateDue(): dispatch whatever queued work has come due, then let the Engine start the Evals (the evaluations of queued Triggers, each ending in a Decision) whose time arrived. Only one pass runs at a time; requests that arrive mid-pass coalesce into a single follow-up, and while setup is incomplete or the system is closing, a pass returns without doing anything.

      Effects (src/app/effects.ts) is the durable queue that makes side effects survive crashes. A command calls enqueue(kind, key, payload) inside its own transaction, so the row is written with the state change, and handlers run only after commit. Each kind and key has one row — re-enqueuing a waiting key replaces its payload but keeps its queue position — failures retry with exponential backoff, and throwing Later defers work without counting a failure, as when no worker slot is free. Six kinds exist, each owned by one adapter: assessment (MasterAssessor), launch and delivery (DshExecutor), relay and notice (Sessions), and reply (Outbox).

      This command/effect split is the load-bearing idea of the architecture. A command changes state and enqueues work inside one transaction; adapters perform the work only after commit. The system can therefore crash between decision and delivery without inconsistency — on restart the effect rows are still in SQLite, and what was decided still happens. The Engine stays synchronous because nothing it calls waits for the world; the world is queued.

      The supporting cast

      The Store (src/app/store.ts) owns the one SQLite database, opened with WAL and synchronous=FULL, and groups its surface by purpose: domain repositories wrapped in atomic, read queries that never write, revisioned settings, outbox receipts, and typed key-value records. Generated columns with partial indexes define the working sets — open Tickets, active Threads — so a pass scans only live rows, and only the Store ever opens the file.

      The Outbox (src/app/outbox.ts) implements the core's Outbox port. send records a receipt and queues a reply effect in one transaction, and the effect's handler pushes the message through its Source. Ordering is per conversation: a later message for the same Ticket and conversation waits behind an earlier pending one, everything waits while its Source is off, and a receipt settles as dropped when the conversation is gone or no longer listened to.

      Sessions (src/app/sessions.ts) manages the DSH agent conversations of both roles: the main Session, the coordinator that routes and decides, and one worker (Executor) Session per Ticket, named worker-<ticketId> (src/executor/dsh.ts). It decorates each with prompts, skills and tools, delivers each message once per request id, and binds each model request to the current prompt revision — a record kept durably, so a worker may reread exactly the prompt it worked under and nothing newer.

      MasterAssessor (src/app/assessment.ts) lets the main Session assess inferred candidates: work nobody explicitly requested. request queues an assessment effect that steers a candidate card into the main Session's turn, and the orchestrator_eval, orchestrator_eval_read and orchestrator_eval_decide tools give the Session bounded Thread context and a decision path back into Engine.decide. The Eval's deadline starts only when the card is delivered (candidateDelivered), so a busy Session does not burn evaluation time.

      DshExecutor (src/executor/dsh.ts) gives each Ticket one Session and one working directory. start and deliver enqueue launch and delivery effects; stop cancels a worker's turn through Store.afterCommit, so a command that rolls back never stops a worker; and prepare supplies the Engine's prepareTicket hook with the Ticket's short name, directory and assignment text.

      The panel (src/client, over the loopback-only, same-origin /orchestrator/api routes of src/app/http.ts) shows a person only what needs a person: Tickets waiting on a human, problems, unavailable Evals, the workers' load. Some actions exist only there — dismissing an unavailable Decision, rerunning setup — because no agent should be able to take them.

      Starting and stopping

      Startup is ordered so that failure degrades rather than crashes. initialize() in src/app/runtime.ts registers the HTTP routes first, so an operator can reach the panel even when setup cannot complete. Setup then probes the repository and accounts; if it fails, the Runtime reports setupPending and stops there — Sources still record incoming Triggers, but nothing evaluates or sends. Once setup resolves, the Runtime installs the Session and Executor hooks, ensures the main Session exists, syncs each syncable Source's Policy part, resumes interrupted Assignments through assignmentInterrupted, and only then starts passes and effects. ready resolves when startup has finished, including the case where setup stopped it short.

      Shutdown runs the same list backward. stop() is idempotent; it sets the closing flag, stops the passes, and aborts the lifetime signal that cancels running reads and subprocesses. It cancels the turns of the main and every worker Session, keeping their inboxes, then waits for the last pass, the effect drain — pending rows stay in SQLite for the next start — and the agents to go idle, stopping the workers' background jobs and subagents. After disposing the hooks and flushing Session persistence, a finally block restores the process environment Setup had changed, closes the Store, and releases the directory lock, in that order, so no other process can open the database mid-write.

      Chapter 5

      Inside the Machine, Part I: The Pure Core

      Everything dsh-superagent knows about work — what may start it, how it proceeds, when it ends — lives in one directory. src/core imports nothing outside itself apart from Node's hashing and does no I/O; its rules are pure functions over stored records, and the whole domain also runs on in-memory repositories in tests (src/core/memory.ts). The tour runs from the inside out: the Engine and its five parts, authorization as computation, assessment, the store beneath, and the predicates that keep every part's answers consistent.

      5.1 One Engine, Five Parts

      The Engine (src/core/engine.ts) is the domain's single entry point and the only writer of Triggers, Threads, Decisions, Tickets and Assignments. A Trigger is one immutable event delivered by a Source, the adapter for GitHub or Feishu; a Thread is the conversation it belongs to; a Ticket is a unit of accepted work. Every method is synchronous and wraps its command in one repo.atomic transaction: repositories change inside it, ports enqueue external work inside it, and adapters perform that work after commit. Callers never hold the whole Engine; each role receives a Pick of the methods it may call (EngineForSources, EngineForMainSession, EngineForPeople, EngineForSettings, EngineForExecutor).

      The Engine delegates to five parts, each extending EnginePart (src/core/part.ts), a base class of shared reads and helpers. Replies depends on nothing, Tickets on Replies, Assignments on Tickets and Replies, Intake and Evals on Tickets — one way only; the Engine sequences a command that spans parts, such as attach, inside its transaction. The naming grammar is uniform: commands take imperative names (stopTicket, bindThread, retryTicket) and may be refused; facts that adapters report take past-tense names (assignmentStarted, inputsDelivered, deliveryFailed, threadClosed) and are recorded, not refused; the query candidate uses a noun.

      Intake (src/core/intake.ts) owns a Trigger's arrival. Reception is store-once: a known id answers duplicate; a Trigger no Source listens to is stored with a Disposition — the record of where a Trigger went — marked filtered; everything else answers stored. A stored Trigger fans out to every Ticket subscribed to its Threads, a delivery that bypasses the Gate of Section 5.2 because it grants nothing: the message arrives as an Input, a message or fact delivered to a worker. Only a person's message, on a Thread not followed merely for context, resumes an ended Ticket — never a stopped one. A person's message that reached a Ticket stays with that Ticket: receive queues a Trigger for an Eval — the evaluation of a Thread's queued Triggers — only when followupOwners finds no Ticket whose worker decides it.

      Evals (src/core/evals.ts) owns the Eval lifecycle and the Decision — the recorded outcome — each Eval ends with. Batching is per Thread: all queued Triggers form one batch, and Triggers that arrive while an Eval runs wait for the next one. The batch takes its strength, actor and Gate basis from its strongest admissible Trigger. The deadline counts from candidate delivery: candidateDelivered starts the clock when the candidate card reaches the main Session, the coordinating agent, and an undelivered candidate never expires. An expired Eval queues its Triggers again, at most REQUEUES (two) times in a row; the third expiry records an unavailable Decision with reason timeout.

      Tickets (src/core/tickets.ts) owns the Ticket lifecycle. Creation from an accept is atomic: in one transaction, Tickets.create writes the Ticket, its Mandate — the authorization an accept produces — the first Assignment (one worker run), a Subscription — a Ticket's following of a Thread — for each Thread of each Trigger in the batch, and the acknowledgement the accept carries; all of it commits or none of it does. The part also owns the end rule for Tickets that follow Threads: followsDone holds once no Thread the Ticket opened is still open or, when it opened none, once every followed Thread closed, and the Ticket ends with the latest close's outcome, merged or closed. Inputs are added once by id; automated Inputs — CI results, bot messages, notes — are held while the Ticket waitsForPerson.

      Assignments (src/core/assignments.ts) owns what the Executor and its workers report: past-tense facts — an Assignment started, Inputs delivered or failed, Inputs read into a step, a turn ended, a host restart interrupted. A worker's Report has six states from progress to dropped. A blocked or failed report holds back automated Inputs until a person writes; a dropped report ends the Ticket; a ready report ends it as completed, or with the followsDone outcome when it follows Threads. A report may carry a question for a person — an Attention — asked, kept or cleared; a replaced question withdraws its unsent reply from the Outbox, the outgoing-message queue.

      Replies (src/core/replies.ts) owns the Engine's messages to Channels — write-only addresses on Threads — each purpose allowed by its own rule. An acknowledgement requires an open Ticket, a message that reached it on a Thread it does not follow merely for context, and a person as its author; an answer requires that the worker's report answered that person's question; a result is allowed only for a Ticket that is ready, completed, merged or dropped; an attention message must match the Ticket's currently open question. Each message is queued at most once, under a deterministic id such as key('ack', trigger.id).

      5.2 The Gate: Authorization as Computation

      Authorization is not a checkpoint a request passes once but a computation the system can re-run at any time. settingsPolicy (src/policy.ts) builds a fresh, stateless Policy — the configuration of who may start what — on every use; nothing is cached, so a save takes effect on the next call. Its surface is small: version, paused, evalTimeoutMs, the gate function, revalidate for existing Mandates, and admitsInferred for proactive accepts.

      The Gate is gate(trigger, thread, tickets): its answer is an admission — explicit or inferred — plus a basis, via: 'addressed' for a listed sender who addressed the agent, 'followup' for a message on a Thread with participating Tickets, 'admission' for an admission-table cell, 'bot' for a listed bot. An allowed sender who addresses the agent is always explicit. An admission cell set to explicit is checked before follow-up strength, so a Thread's Tickets never weaken an explicit request. A follow-up on a participating Thread is explicit for an allowed sender and inferred for anyone else, unless the accept mode is off. Machines take a separate path: only listed bots pass, as inferred candidates at most, a senderless CI event uses the unlisted-unaddressed cell, and every other bot is rejected as not_human.

      The admission table (src/admission.ts) is per Source; its rows are receiving scopes — Feishu chats and direct messages; GitHub new Issues, pull requests, comments and default-branch CI. A row has up to three cells, by whether the sender is listed and addresses the agent: listedUnaddressed may be inferred or ignore, unlistedAddressed may be explicit, inferred or ignore, unlistedUnaddressed may be inferred or ignore — an unaddressed message can never be explicit. Defaults are inferred, ignore and ignore; unaddressed cells exist only where the Source receives every message in that scope.

      What an admitted candidate may become depends on the accept mode. In off, nothing inferred becomes a candidate. In observe, the default, inferred candidates are assessed, but a positive assessment is recorded as an ignore marked "would accept" and nothing is accepted. In auto, a positive assessment accepts. Explicit requests work in every mode.

      All of this rolls into the Policy version: policyVersion hashes the rules, the accept mode and each Source's policy parts — allowed lists, admission tables, bot lists — under a revision tag, mandate-v3. Every Mandate and Decision records its version; a Decision arriving under an older one is recorded unavailable and its batch queued again. A version change does not reach every Ticket: policyEffects (src/policy.ts) computes which live Tickets it bears on — a matched rule changed or disabled, the requester no longer allowed, proactive work no longer accepted — and only those receive a policy-changed Input.

      An ended Ticket keeps its Mandate, and a person's message on one of its Threads resumes it without a new Decision, but only after revalidate(mandate) passes under the current Policy: the Source must still listen to the original Thread, an explicit follow-up Mandate passes, an inferred one needs auto mode with its matched rules still enabled, a table-cell Mandate must still receive at least its original strength, and a bot's needs the bot still listed. A Ticket that fails stays ended and releases its waiting messages to Eval. Only three operations ever change a Mandate: an accept creates it, a person's stop withdraws it, a failed revalidation revokes it.

      5.3 Assessment and Decision

      An inferred candidate becomes a Decision through the MasterAssessor (src/app/assessment.ts), the Engine's Assessor port. When an Eval starts, the assessor enqueues a durable assessment effect; its handler steers the candidate card into the main Session's turn and then calls candidateDelivered, the moment the Eval's deadline begins to count. Explicit candidates never come here: the assessor refuses them with a pointer to orchestrator_route, because an explicit request is routed, not assessed.

      The main Session works with three tools. orchestrator_eval returns context, not instructions: the Trigger's text up to 4,000 characters, its batch peers, up to eight related Tickets, the Policy version the Eval was built from, and a bounded Thread window — the first five messages and five on either side of the Trigger, truncated to 400 characters, or 1,200 for the two nearest neighbors. orchestrator_eval_read expands any of it — full messages, further thread pages, files, images — under cursors that must be copied from a returned reference. orchestrator_eval_decide submits the judgement, the Assessment.

      assessmentOutcome (src/policy.ts) converts that judgement into an Engine outcome, and it is strict. It requires exactly one rule assessment for every enabled rule, matched or not; anything else throws. An accept must carry a settled direction — implementation requested, a target specified or resting on an existing standard, no open design decision (directionAllowed) — or it is downgraded to an ignore with reason directionUnsettled; it must match at least one enabled rule, else noRuleMatched; and it must quote intent_evidence, the words that establish intent. Outside auto mode an inferred accept becomes an ignore marked would_accept with reason observed. The Engine takes none of this on faith: Evals.decide re-checks every inferred accept against admitsInferred and refuses it with notExplicit.

      One shortcut spares the trivial cases. An inferred candidate whose card clearly touches no enabled rule — plain chat, unrelated discussion — may be ignored directly from its card, and the Decision records the code ignoredFromCard beside the supplied reason, distinguishing it from a full assessment.

It runs in WAL mode with synchronous=FULL, and its nine tables split the state by who may write it.

      Rows are JSON, and the working columns are generated from it: ticket.open while value -> '$.ended' IS NULL; ticket.active while Inputs are undelivered or the latest Assignment is pending or running; thread.active while Triggers are queued or an Eval runs; thread.subscribed, the Source, while any Ticket subscribes. A database predating a column gets it added on open, populated by SQLite from the stored JSON.

      Time is text, deliberately. Every Trigger timestamp is normalized at intake by isoTime (src/core/model.ts) into the one form Date#toISOString produces, so stored times compare lexicographically in memory and in SQL — deadline <= now is a string comparison.

      Transactions nest through savepoints, and afterCommit is the seam between commit and consequence: a callback queued inside a transaction runs only after the outermost commit, a rollback discards its level's callbacks, and a throwing callback is reported without failing the committed transaction. It serves in-memory follow-ups that need not survive a crash; durable side effects belong to the Effects queue instead.

      The kv table holds everything else, and KV (src/kv.ts) is its registry: each key-value record is declared once, with its type and the single component that owns it — the schema version to the Store, settings revisions to Settings, the main Session's id to Runtime, read cursors to the Sources. A key is spelled once, with its owner plain.

      Schema movement is deliberately conservative. SCHEMA_VERSION is 11 and only increases (src/app/migration.ts): a newer database refuses to start, one older than OLDEST_SCHEMA (10) is refused outright, and a schema 10 database is rewritten into its schema 11 shapes in one transaction at open; a failure leaves the file unchanged.

      5.5 Shared Predicates

      The rules that span parts live not in the parts but beside the model, as small predicates each part calls. waitsForPerson (src/core/model.ts) answers whether a Ticket's latest Assignment reported blocked or failed and no person's message has reached it since. While it holds, Tickets.addInput holds back automated Inputs, ticketStage classifies the Ticket as waiting on a person, and canRetry (src/core/stage.ts) makes it retryable; a later report that is neither, a person's message, or a retry lifts it.

      followupOwners answers who decides a person's follow-up: the Tickets it reached on their own Threads that can still decide it and have not handed it back — live ones, and ended ones not stopped by a person with the message waiting to resume them. While any owner exists the message takes no Eval, and the main Session may only stop the work on it, a refusal Evals.decide enforces through leftToWorkers. settled answers whether a Decision resolved the request — stops, unavailables, refused stops and routings do not count — which is what lets a Ticket end without sending already-decided messages back to Eval.

      ticketStage (src/core/stage.ts) is the stage table of docs/003-execution.md as code, read top to bottom with the first matching row winning: a failed delivery, an open Attention or a ready report puts the Ticket in a person stage, a blocked or failed report only when waitsForPerson holds, then queued, idle and working. canRetry closes the loop, making exactly the person-stage stalls a person may remedy — a held Ticket or a failed delivery — retryable.

      The reason to centralize these is not elegance but sameness. Whether a Ticket waits for a person is asked by Input delivery, the stage classifier, the retry command and the panel; if each answered with its own reading of reports and Inputs, the held Inputs and the "Blocked" label would eventually disagree. As pure functions over stored records — followupOwners takes a records interface, so the same code runs against SQLite, in memory and in the panel — they give one answer everywhere, change in one place, and are pinned by their own tests (tests/stage.spec.ts).

      Chapter 6

      Inside the Machine, Part II: The Edges

      Part I followed the Engine, the synchronous core that owns every decision. A core that only decides would be a brain in a jar. This part follows the machinery that connects it to the world: the queue that remembers promised work, the outbox that makes the agent speak in order, the executor that gives each Ticket — the system's unit of accepted work — a shell and a worker, the manager of its model conversations, and the Source plugins that listen to GitHub and Feishu. One rule repeats: decide inside a transaction, do the work afterwards, from storage.

      6.1 The Effect Queue: Stored Work

      Everything dsh-superagent does after a decision — relaying a worker's Report, launching an Assignment (one run of a Ticket's work), delivering an Input, a message bound for that worker, sending a reply — is stored first and done later. The durable bridge is Effects (src/app/effects.ts). A command calls enqueue(kind, key, payload) inside its transaction; the row lands in SQLite with the decision, and execution begins only after commit. A crash between the two moments loses nothing.

      The queue keeps one row per kind/key pair. Re-enqueuing a waiting key replaces its payload, resets its failure count and makes it due immediately, while the row keeps the sequence number it was first given — coalescing never costs queue order. A generation counter marks each replacement, so a running attempt cannot delete a newer payload. Handlers register once per kind with a concurrency limit and backoff bounds; due rows dispatch oldest first, and failures retry with exponential backoff up to the kind's cap.

      Not every refusal is a failure. Throwing the Later exception — no worker slot free, processing paused — reschedules the row after the initial delay without counting it. Real failures count, and once one item of a kind has failed three times in a row (FAILURES_BEFORE_ERROR in src/app/effects.ts), the kind's health entry turns to error for the panel.

      Six kinds cover the edges. The assessment effect steers the candidate card of an Eval — the assessment of a proactive request — into the main Session's turn; once received, the MasterAssessor tells the Engine, which starts the Eval's deadline. The launch effect starts a pending Assignment — prepare command, Executor Session, assignment message. The delivery effect hands a Ticket's waiting Inputs to its running Assignment, in order; its failures are quiet, since they already show on their Ticket. The relay effect steers a worker's Report or question, or a person's follow-up, into the main Session's turn, and the notice effect injects without waking it; both are strictly ordered, a failed one holding back the later ones of its kind. The reply effect carries the Outbox's messages. A pass — the two-second sweep of src/app/passes.ts — also picks up due rows.

      6.2 The Outbox: Ordered Speech

      When the Engine decides to speak on a Channel, the address a reply goes to — the acknowledgement of an accepted request, the answer to a question, the result of finished work — the Outbox (src/app/outbox.ts) makes the message real. send records a receipt and enqueues a reply effect in one transaction; receipts are inserted ignore-on-duplicate and kept forever, so a message id is never queued twice, even across restarts.

      Ordering is per Ticket and per conversation. Before sending, the handler asks receipts.behind (src/app/store.ts) whether an earlier message of the same Ticket to the same conversation is still pending with fewer than three failures; if so, the later one waits. The threshold is an escape hatch: once the earlier message has failed three times and surfaced as a problem, its successors go out rather than pile up behind it. Messages of other Tickets never wait.

      Waiting and dropping are kept distinct. While a message's Source is off or not installed, it waits. It is dropped only when the conversation can never receive it: the Source answers gone for a deleted Issue or a locked conversation on GitHub, or a recalled Feishu message (channelGone), or the Source no longer listens to that conversation (channelIgnored). Dropped receipts stay on record, with when, why and the Ticket they were for, and a dropped acknowledgement reads as dropped, not sent. Retries back off from 5 seconds doubling to 300. The order exists because conversations are chronological and read by people: the acknowledgement must precede the answer, and the answer the result, or a reader will conclude the agent never heard them.

      6.3 The DshExecutor: One Session and One Directory per Ticket

      Each Ticket gets one worker Session, named worker-<ticket id> (workerSessionId in src/executor/dsh.ts), and one directory. The prepare(ticket, outcome) hook fills the execution facts at acceptance: a kebab-case short name of one to four words plus a 12-character id suffix, the directory under the configured execution root (default <stateDir>/work), and the assignment text.

      Before the first Assignment, if the directory does not exist, the configured prepare command runs once through sh -c in the execution root, with ten minutes to finish; the typical command is a git worktree checkout. A failed prepare is deliberately not retried — an existing directory counts as prepared, so a retry would bless whatever the failed command left behind. The Ticket is marked failed and waits for a person or a retry to prepare it again.

      WorkerSlots governs concurrency. Work reaches the executor as the launch and delivery effects above. A Ticket holds a slot from the start of a launch, including preparation, or from the delivery that wakes its idle worker, and keeps it through the turn. The configured maxWorkers applies, plus one extra slot that only a person's message may take; wakes take priority over launches, so new work can never prevent a person from continuing an existing Ticket. Launches run concurrently, and a slow prepare delays only its own Ticket.

      Passing failures get three tries: the transient test recognizes HTTP 408, 429 and 5xx, and refused, reset or timed-out connections. A transient launch failure runs again on effect backoff; a failed turn receives a "continue where it stopped" message after 15, 30 and 60 seconds. Any other failure fails the Ticket.

      A turn may end with shell jobs or subagents still running. The Ticket keeps its slot and stays working; untilQuiet (src/executor/background.ts) watches both, and a finished job or subagent wakes the worker with its result. After each turn, background work has at most thirty minutes: at the limit shell jobs are killed — the worker is told which at its next turn — while subagents continue, since stopping them would only wake the worker again, and the Ticket is reported waiting with the worker's last words. When an Assignment ends, jobs are killed and subagents released, their wake-up turns dropped. A handoff to a person frees the slot at once: subagents stop, but jobs left for review, such as a running server, go on until the Assignment ends, exempt from limits, their ends collected.

      A restart follows the same discipline. At startup resume() walks open Tickets oldest first: a running Assignment is reported assignmentInterrupted, which starts a new Assignment carrying a recovery note — check the directory, git history and GitHub before repeating any outside action — and a pending launch is enqueued again unless its Ticket waits for a person. The prepare command and the worker's prompt receive the same execution variables from src/app/execution-environment.ts: DSH_SUPERAGENT_DIR, NAME, TICKET and BLOCKED_COMMANDS from the Executor, repository and pull-request variables from GitHub, chat and bot variables from Feishu; none contains credentials.

      6.4 Sessions, Delivery and the MasterAssessor

      Sessions (src/app/sessions.ts) manages the conversations of both roles: the main Session that routes and assesses, and the workers. ensure creates a Session under its role's model — seeded once at creation by src/app/role-models.ts, without touching the host's global default — and under its preset. The presets, dsh-superagent-router and dsh-superagent-worker, are defined in cordis.patch.yml: both move a foreground shell command to a background job after 5 seconds and cap job waits at 5 seconds; the router keeps only routing tools, the worker only work tools.

      Prompts are versioned, and each model request binds the Session to the current revision; the revisions a Session has worked under are stored durably, and promptVersion with mayRead restrict a worker to the prompt text it actually ran under. Content flows in through two effect kinds: relay steers into the main Session's turn, notice injects without waking it. The noWait guard keeps that Session from idling — it refuses a shell command that runs sleep at a command position, a timeoutMs above 30 seconds, and a job wait above 5 seconds — explaining that what it waits for arrives on its own.

      Delivery is deduplicated by AgentDelivery (src/app/delivery.ts): a message goes in once per request id, across live and restored Sessions, with delivered ids tracked from session events, persisted history and pending inboxes. Every message carries the plugin's own source marker, so the system's words can never pass for a person's.

      The MasterAssessor (src/app/assessment.ts) is the main Session's window into an Eval. Its context, read and decide serve the three orchestrator_eval tools. context returns the candidate — the Trigger's text up to 4,000 characters, batch peers, related open Tickets, the Policy version — plus a bounded Thread window read through the Source's own reader: the first five messages and five on either side of the Trigger, cut to 400 characters, or 1,200 for its two nearest neighbors, everything else a 50-character stub (src/sources/admission-context.ts). read expands stubs, pages the Thread, and reads repository files and images from a per-Eval cache. decide converts the assessment for the Engine, which re-checks it against the current Policy; when the Eval ends, release drops the cached state and later reads are refused.

      6.5 Sources: Plugins Behind a Protocol

      A Source is a plugin that connects one outside service to the domain: it turns events into Triggers, the normalized records the Engine stores, answers scope questions, sends replies and reads Thread context for assessments. The contract is SourceKind (src/sources/kind.ts): identity, configuration schema and form fields, derived facts, and owned health entries; the rest is optional — a scope listening rule, a channel with allowed, send and link, a threadContext reader, search find, a Policy part, execution variables.

      The SourceRegistry (src/sources/registry.ts) owns the installed kinds and stored instances, and implements the Engine's SourceScope, answering scope questions through the kind. Registration claims the kind's health entries — duplicates and reserved sync: names are refused — and a Source whose stored configuration no longer validates is disabled. Plugins receive a SourceHost (src/sources/host.ts); the kind's code sees only the narrow SourceContext built by src/app/source-context.ts: receive a Trigger, read and patch its own Threads and state, change Tickets only through bindThread and threadClosed, notify through the Outbox, and report on exactly its declared entries.

      The GitHub Source (src/sources/github.ts) runs a poll round: notifications first, then observed repository streams of new Issues, comments and default-branch CI, then the pull requests of open Tickets with their CI, then subscribed Threads. Each Issue, pull request and Thread is read independently; a failed read keeps its error on its Thread and counts toward the Source's error, reported after three failed rounds by default, while a deleted Issue (HTTP 410) is dropped at once and a read failing for a day is abandoned. github-trigger.ts normalizes comments, reviews, Issue bodies and CI transitions into Triggers. github-pull.ts binds pull requests to Tickets — claimPull accepts the origin pull request or an agent-authored one whose branch's last path segment is the Ticket's short name; observePull reconciles closes; pullEndNotices writes the terminal chat notice. github-channel.ts posts comments and review replies with an embedded idempotency marker, falling back to the pull request's conversation when the target review comment is gone; github-read.ts serves CI snapshots and repository reads.

      The Feishu Source (src/sources/feishu.ts) rests on three loops in feishu-loops.ts: a live event consumer spawned from the bot's lark-cli, restarted with backoff and reporting every failure; a history pass over configured chats and known direct chats each minute, which also recovers topic replies the live stream missed; and polling of subscribed topics. One translation rule in feishu-trigger.ts serves live events, history pages and topic pages alike, so every read path derives the same deterministic Trigger id for a message. feishu-channel.ts replies in the target's topic with the message id as idempotency key, and a recalled target is gone; feishu-read.ts reads a Trigger's message, root, parent, thread and surrounding chat; feishu-image.ts downloads an image by its img_ key from the message that carries it.

      Both stand on src/sources/poll.ts. POLL_HORIZON_MS, fourteen days, bounds how long a subscribed Thread with no live Ticket is still polled; cursorAt steps each poll's start back five seconds so late events are not missed, with Trigger id deduplication absorbing the overlap; and pollThreads keeps a failure on its Thread as pollError, cleared on the next success, so one bad read neither poisons the others nor disappears silently.

      6.6 The Panel and Health

      The panel's backbone is the Ticket stage model, implemented by ticketStage (src/core/stage.ts): every open Ticket has one stage, determined by what it waits for. The table is read from the top; the first matching row wins.

      The endings mirror that honesty. A ready Report on a Ticket that follows no pull request completes it; a dropped Report ends it without a message unless a matched rule asks for one, keeping its Subscriptions so a later human comment resumes it. A Ticket that follows pull requests is done only when none it opened remain open — or, having opened none, when every pull request it follows has closed — and then ends with the outcome of the last relevant close, merged or closed, with one final notice to chat Channels from pullEndNotices (src/sources/github-pull.ts). "Awaiting review" therefore means a ready Report with a pull request.

      Health follows the same single-writer rule as everything else. HealthBoard (src/infra/health.ts) holds one entry per part — runtime, evals, models, one per effect kind, worker, each Source kind's entries, sync:<id> for Policy syncs — and each entry is claimed by exactly one writer; a second claim throws. Errors surface only after three consecutive failures, so a one-off network error stays quiet, and a failed Input delivery shows on its own Ticket instead. That is the panel's promise (docs/005-panel.md): a healthy state takes no space, and what the supervisor does see is either work that needs them or a problem they can act on.

      Chapter 7

      Why It Is Designed This Way

      dsh-superagent turns event streams into teammate work. A Source — a GitHub repository or a Feishu chat — produces immutable events called Triggers, gathered into Threads, the conversations they belong to; an Eval decides whether a batch of Triggers may start work; an accept grants a Mandate (the work's recorded authorization) and opens a Ticket, which an Assignment hands to an Executor running in an Executor Session (worker). One Session, the main Session, does the judging and routing. The philosophy that governs the whole (docs/000-philosophy.md) is an attention budget — take as little human attention as possible. Six structural decisions carry that budget, and each exists because a cheaper-looking alternative was refused on paper; the strongest artifacts here are the refusals.

      7.1 A Synchronous Core in an Asynchronous World

      The Engine (src/core/engine.ts) is the only writer of Triggers, Threads, Decisions, Tickets and Assignments, and every one of its methods is synchronous. Each command wraps its work in a single call to Repositories.atomic: receive, decide, attach, stopTicket and report all share that shape. Even the sweep method evaluateDue, which visits many Threads and Tickets, opens a separate transaction for each Eval or Ticket it changes (src/core/engine.ts:75). The core also does no I/O. src/core imports nothing outside itself except Node's hashing (node:crypto in src/core/ids.ts), and it touches the world only through the ports of src/core/ports.ts, whose every method is synchronous "so atomic can wrap a unit of work."

      The rejected alternative is the familiar async orchestration core: create the Ticket, await the launch, record the Subscription that fans a Thread's future messages out to the Ticket, await the acknowledgement. Every await is a crash window, and every crash window is a distinct observable state — a Ticket with no Assignment, a Subscription pointing at work that never started. The domain tests state the intended invariant as a test name: "records an accept with its ticket, subscriptions and acknowledgement together, or none of them" (tests/core-engine.spec.ts:136). When the prepareTicket hook throws mid-accept, the Decision, Ticket, Subscription and queued acknowledgement all disappear; nothing interleaves because nothing can.

      The payoff compounds outward. Because the core does no I/O, the whole domain runs on MemoryRepositories (src/core/memory.ts), whose atomic snapshots its maps and restores them on throw. The 1,600 lines of tests/core-engine.spec.ts — intake, Eval batching, fan-out, resume, pause, Policy changes, interrupted Assignments, failed deliveries — mock no network at all; the ports are small in-memory doubles and the clock is injected through the Engine's optional now. Determinism is structural: ids derive from their inputs (key in src/core/ids.ts), and a test ticks time forward by hand. The asynchronous world — polling Sources, thinking Sessions, retrying deliveries — has been pushed to the edges, where a crash costs a retry and not a lie.

      7.2 Commands Today, Effects Tomorrow

      Every state change the Engine commits has a shadow: the side effects it licenses. Launching a worker, delivering an Input (context for a Ticket) to its running Assignment, relaying a worker's Report to the main Session, sending a reply on a Channel (the write side of a Thread) — none of these happen inside the command. The command calls Effects.enqueue(kind, key, payload) inside its transaction (src/app/effects.ts:61), the transaction commits, and only then does a handler run. This is the transactional-outbox pattern generalized to all side effects: the intent is a SQLite row, as durable as the state it follows. A crash between "decided" and "did" is therefore unobservable, because the record of intent was written in the same transaction as the decision; on restart the rows replay instead of losing work.

      Two refinements matter. Coalescing by kind and key — an INSERT ... ON CONFLICT — replaces a still-waiting row's payload, resets its failure count and makes it due immediately without losing its queue position: five Inputs arriving together produce one delivery. And Later (src/app/effects.ts:5) is backpressure made explicit: an effect that throws it — processing paused, worker slots full — is rescheduled without counting as a failure.

      The Outbox (src/app/outbox.ts) is the purest instance. send records a message's receipt and queues its reply effect in one transaction; a message id recorded once is never re-queued, and receipts are kept permanently, so an acknowledgement that was sent stays sent. Delivery is ordered per Ticket and conversation: receipts.behind (src/app/store.ts:259) holds a message while an earlier one for the same Ticket and conversation is still pending, until that one has failed three times and surfaces as a problem instead. That is why an acknowledgement can never overtake the answer that follows it: a person who reads "done" before the result would stop trusting the agent.

      7.3 One Writer per State

      The dependency rules of docs/007-architecture.md state a plain invariant: each kind of state has exactly one writer. The Engine owns Triggers, Threads, Decisions, Tickets and Assignments; Settings owns settings and their history; Prompts owns prompt versions; Effects owns effect rows; the Outbox owns receipts; each health entry belongs to the part that claimed it on the HealthBoard, which refuses a second claim; a Source owns its read positions and its Thread metadata. A Source cannot even edit a Ticket directly — it may only call bindThread and threadClosed, which are Engine commands.

      The rejected alternatives are locks and conventions. A mutex serializes access but assigns no responsibility; a convention ("Sources should not write Tickets") rots silently until a bug proves it was never load-bearing. Here the invariant is checkable by reading type signatures, because the Engine never hands itself out whole. Each caller receives its role's Pick:

      export type EngineForSources = Pick<Engine, 'receive' | 'bindThread' | 'threadClosed'>
export type EngineForPeople = Pick<Engine, 'stopTicket' | 'retryTicket' | 'reevaluate' | 'unsubscribe' | 'dismiss'>

      The full set — EngineForSources, EngineForMainSession, EngineForPeople, EngineForSettings, EngineForExecutor (src/core/engine.ts:261) — makes misuse unrepresentable: a Source's code has no method that could stop a Ticket, and the Executor's interface is almost entirely past-tense facts (assignmentStarted, inputsDelivered, turnEnded) rather than imperatives. One writer per state, plus one process per Store (the Runtime locks the state directory), buys concurrency discipline without a single lock in the domain.

      7.4 Authorization as Recorded Data

      An accept could simply mean "this was allowed once." Instead it produces a Mandate (src/core/model.ts:126): an immutable record of the Policy version — the Policy is the versioned rules for accepting work — the strength, the scope, the sender's identity on that Source, and a basis saying how the gate admitted the Trigger — addressed by a listed sender, a followup on a Thread with Tickets, an admission-table cell, or a bot on the Source's bot list, each with the matched rules where rules decided it. The rejected alternative is the access-control list checked at every action, which would make current rules govern work accepted under older ones and would scatter permission logic across call sites, where it drifts.

      The design lets work outlive the rules it was accepted under. When the Policy changes, policyEffects (src/policy.ts:144) computes exactly which open Tickets the change bears on — a matched rule changed or was disabled, the requester may no longer start work, proactive acceptance ended — and Engine.policyChanged delivers that as an Input to those Tickets only. Nothing is cancelled; the rejected-concepts table in docs/001-domain.md refuses "cancelling running Tickets on a Policy change" because a cancelled change leaves half-finished work. Revalidation happens only at resume: an ended Ticket that a person's message wakes must still pass revalidate against today's Policy (src/core/tickets.ts:113, src/core/tickets.ts:257), or it stays ended and the message goes to Eval. Between those moments, the Mandate is the truth.

      The same document refuses a deeper temptation: a person as a domain concept. A Trigger carries its actor's identifier as the Source gives it; an allowed list is a Source's part of the Policy in that Source's own identities; that one human has accounts on GitHub and Feishu is prompt text the agents read when they need it — src/policy.ts says so in its header comment. Mapping identities across Sources would build a shadow identity system with its own sync failures, buying nothing the Mandate does not record.

      7.5 The Ticket Owns Its State, Not the Session

      The obvious way to know what a Ticket is doing is to ask the agent Session running it. The repository refuses this: "Ticket state that follows the DSH Session" is on the rejected list, because a Ticket can be resumed after it ended, retried, restarted after a host crash, or carried by several Assignments over time. The Executor Session is one assignment's container, outside the domain and reached only through Assignments. So the Ticket's stage is computed from its own recorded facts by ticketStage (src/core/stage.ts:9): ended; a delivery that failed; an open Attention (a question awaiting a person's answer); a ready Report awaiting review; blocked or failed work waiting for a person; queued; idle; working.

      The subtlest of these is waitsForPerson (src/core/model.ts:349): a Ticket waits for a person when its latest Assignment reported blocked or failed and no human message has reached it since. That is computed from stored Reports and Inputs, never inferred from a report's prose — the rejected list refuses inferring "waiting on a person" from free text. Because the computation reads only durable rows, a restart keeps it (docs/003-execution.md: "It is worked out from the stored Reports and Inputs, so a restart keeps it"), and a retry — which ends the stalled Assignment and starts a new one under the same Mandate — lifts it by writing new facts, not by probing a process. The Session may lie or die; the Ticket's state is what the domain recorded.

      7.6 Prompts as Versioned Data

      Most of the agents' instructions live in prompts/*.md, written one sentence per line so that edits make readable diffs; promptFile (src/app/skill-files.ts:29) joins each paragraph's lines with spaces at load time. Prompts (src/app/prompts.ts) stores configurations as numbered Versions, with team sections for communication, scope and delivery, and overrides of built-in parts that record the hash of the text they were edited from, so an upgrade can report exactly what changed underneath a team's wording.

      The rejected alternative is behavior-as-settings or behavior-as-code. The philosophy draws the line directly: "Behaviour that a team describes in words is prompt text, not a setting" (docs/000-philosophy.md). When the agent is noisy, the remedy is shorter, stricter words — a save, applied on the next request — not a deploy. Attribution is the second purchase: each model request binds its Session to the current prompt revision, recorded durably (promptFor in src/app/sessions.ts:329, stored under KV.sessions.prompts), so any action can be traced to the words that produced it. tests/model-surface.spec.ts keeps these surfaces honest: it checks the prompts, tool descriptions and delivered messages against the tool schemas and the glossary, retires old terminology, bans known-misleading phrases and enforces a character budget per role. Prompt text changes what the agents are told, never what the system allows; the gate and the tools stay in code.

      7.7 Small Vocabulary, Few Settings

      The philosophy's design rules read as subtractions: few concepts, so a business need becomes an attribute of an existing concept or a paragraph of prompt text rather than a new entity; few settings, so a default replaces an option whenever one value suits almost every team; a panel that lists first what waits for a person, because a healthy state takes no space. The overview does exactly that — Tickets in the person stage come first, from the same ticketStage computation (src/app/views/overview.ts).

      The codebase polices its own vocabulary. Why the core recorded a Decision is a Reason code from the closed REASONS list (src/core/reasons.ts); what a person or agent can be refused is a UserError from the fixed USER_ERRORS codes (src/core/errors.ts), which the management API answers with a status and the panel words in its language. The glossary of docs/001-domain.md is consumed by the panel itself — its question-mark button opens the same terms, in both languages, from GLOSSARY in src/client/locales.ts. A new concept cannot slip in half-introduced: the words on the screen, the reasons in the records and the terms in the documents are one list.

      The strongest discipline, though, is the last table in docs/001-domain.md: the rejected concepts. Principal or Membership; Eval scheduling its own delays; waiting Eval states; one live Ticket per Thread; Ticket state that follows the Session; cancellation on Policy change; locks on a failed worker's tools. Each row is a design that almost fit, with the reason it was refused. Most architectures can say what they do; this one can say what it refuses to become — and a design that knows where it ends can keep everything inside that line simple.

      Chapter 8

      A Request Walks Through the System

      8.1 The Figure

      The scene is a small team's repository watched by dsh-superagent, a host process that turns messages into authorized work. Its GitHub Source — the adapter that observes one repository for the agent's account — is enabled, and the team's Policy (the configuration of who may originate work) lists a teammate we will call Mara among the accounts that may. The accept mode is observe, so proactive work is only assessed, never started on its own, and one proactive rule is enabled; it will play no part here, because what Mara writes is an explicit request. She opens issue #412, "Flaky test: scheduler occasionally drops a job," and comments: "@agent the scheduler test flakes about one run in five on CI — please find the race and fix it."

      Everything that follows is a chain of named modules. The Source translates her comment into a Trigger (the domain's record of one incoming message); the Engine — the transactional core that is the only writer of Triggers, Threads, Decisions, Tickets and Assignments — gates it, evaluates it, and on the main Session's routing turns it into a Ticket (an authorized unit of work) with a Mandate (the record of why it is authorized); an Executor Session does the work; and the GitHub Channel carries the agent's words back. This chapter walks that chain hop by hop.

      8.2 From GitHub to a Trigger

      The GitHub Source has no webhook; it polls. A watch loop in src/sources/github.ts runs pollRound every pollSeconds (sixty by default, or longer if GitHub's x-poll-interval header asks). A round reads, in order: the agent account's notifications, any repository-wide streams the team has switched on, the pull requests of open Tickets with their CI, and finally every subscribed Thread. All reads go through Commands in src/infra/commands.ts, a subprocess wrapper whose api method shells out to the deployment's gh CLI (gh api repos/<owner>/<name>/...), restricted to the configured repository and schema-validated on return.

      Mara's mention produces a notification, so pollNotifications schedules issue #412 for a read. readNotified fetches the issue, emits a Trigger for its body only if the issue was opened since the cursor by someone other than the agent, and then intakeComments reads the conversation comments since the same cursor. The issue's own body, arriving in an earlier round without a mention and with observeIssues off, had been gated out as no_mention and recorded as an ignored Decision — which is why the comment, not the issue, is the request.

      Each comment becomes a Trigger through commentTrigger in src/sources/github-trigger.ts. The Trigger carries a deterministic id built from the comment's URL, id and update time; the actor (human: true, since Mara is a person and not the agent itself); the Thread (github:412, the conversation the Trigger belongs to); a Channel back to reply on (githubChannel); and, because mentions finds @agent in the body, addressed: 'mention' — the Source-declared fact that the sender addressed the agent.

      Deduplication is a property of those deterministic ids plus the cursor. readNotified advances the per-thread cursor to cursorAt(round.started) — src/sources/poll.ts steps the timestamp back five seconds so late-arriving remote events are re-read — and re-reading is harmless: Intake.receive in src/core/intake.ts opens one Engine transaction, finds the Trigger id already stored, and answers duplicate. On the first read the Trigger is stored, Thread github:412 records its time and Correlation, and the fan-out loop finds no Ticket subscribed to the Thread, so nothing is reached. Because no Ticket's worker decides this message and its sender addresses the agent, queueForEval places the Trigger id on the Thread's pending queue. The Source reached the Engine through SourceContext.receive (src/sources/host.ts), which routes through Passes.receive (src/app/passes.ts) so a stored Trigger also requests an immediate pass.

      8.3 Gate and Candidate

      A pass is the Runtime's heartbeat: Passes (src/app/passes.ts) runs one every two seconds and one more whenever a command asks, first kicking due Effects (the durable side-effect queue) and then calling Engine.evaluateDue (src/core/engine.ts). That method finds Thread github:412 with a pending Trigger and no Eval in progress — an Eval being the Thread-level assessment that ends in a Decision — and Evals.start (src/core/evals.ts) begins one transactionally.

      First the Gate. settingsPolicy in src/policy.ts builds a fresh, stateless Policy whose gate(trigger, thread, tickets) classifies the message: Mara is on the allowed list and the Trigger is addressed, so the answer is admissible with strength: 'explicit' and a basis of via: 'addressed' naming the mention and the sender. Had she not mentioned the agent, the admission table and the accept mode would decide between an inferred candidate and rejection. The Eval record lands on the Thread (thread.evaluating) with the gate's strength, actor, basis and the Policy version, the pending queue empties into it, and assessor.request hands its candidate to the MasterAssessor (src/app/assessment.ts), which enqueues an assessment effect.

      The effect's handler builds the candidate card (candidateCard in src/app/links.ts) — the message rendered the way workers will read it, with its source link and replied-to preview, the Thread, the batch, related and referenced Tickets, the strength and the mode — and steers it into the main Session's turn (sessions.prompt(..., 'steer')), then calls Engine.candidateDelivered so the Eval's deadline counts from the moment the Session actually received the card. The bounded Thread window and the Policy version that MasterAssessor.context serves through orchestrator_eval belong to inferred candidates; an explicit card says to route it, and prompts/dispatch.md tells the main Session how.

      The main Session — the persistent orchestrator-facing Session the Runtime owns — reads the card and calls orchestrator_route with one accept item: a title, a worktree_name, and an acknowledgement naming the change. route() in src/app/tools/main.ts turns that into Engine.decide(triggerId, { kind: 'accept', ... }), each item its own Engine command.

      8.4 The Atomic Accept

      Engine.decide wraps Evals.decide in a single repository transaction, and everything the accept means happens inside it. Evals.accept builds the Mandate — strength explicit, the gate's basis, the Policy version, the actor, and the scope the main Session wrote — derives the Ticket id deterministically from the Eval id, and records the accept Decision. Tickets.create (src/core/tickets.ts) then writes the Ticket: its origin Trigger, the Channel taken from Mara's comment, a first Assignment in state pending (an Assignment being one run of the Ticket's worker), and Subscriptions on every Thread of the Eval's Triggers, so issue #412 now belongs to this Ticket. The prepareTicket hook lets DshExecutor.prepare (src/executor/dsh.ts) fill the execution facts — the worktree name, the workspace directory, the assignment text. Finally, if the accept carried an acknowledgement, Replies.acknowledgeAccepted (src/core/replies.ts) queues it through the Outbox, and executor.start enqueues the launch. Decision, Ticket, Mandate, Assignment, Subscription, acknowledgement receipt, launch row: one transaction, one crash domain.

      The acknowledgement cannot be lost or reordered because it is a fact before it is a message. Outbox.send (src/app/outbox.ts) persists a receipt under the deterministic id key('ack', trigger.id) and enqueues a reply effect in the same transaction; only after commit does the effect run, and it retries with backoff from five seconds up to five minutes for as long as it takes. Ordering is enforced twice: the reply effect kind runs one at a time in queue order, and receipts.behind holds a later message of the same Ticket to the same conversation behind an earlier pending one. When sendGithub (src/sources/github-channel.ts) finally posts the comment, it embeds an HTML marker holding the message id and first scans for its own marker, so a retry after a lost response posts nothing new. Mara sees a reply on #412 saying what the agent will do.

      8.5 Launch and Work

      After the commit, the launch effect runs (launchQueued in src/executor/dsh.ts), reserving one of the WorkerSlots before any awaiting work so two launches cannot take the last slot. launch finds no workspace directory, so prepareDirectory runs the team's configured executor.prepare command — typically git worktree — with the Ticket's execution variables (DSH_SUPERAGENT_DIR, DSH_SUPERAGENT_NAME, DSH_SUPERAGENT_TICKET, and the GitHub account and repository), under a ten-minute cap; a failed prepare fails the Ticket rather than retrying over a half-built directory.

      Sessions.ensure (src/app/sessions.ts) then creates the worker Session worker-<ticket> in that directory with the dsh-superagent-worker preset, seeds it with the executor model, decorates it with the composed prompt — the role instructions from prompts/worker.md and its sections, plus the Mandate's own limits, which for an explicit request add nothing — and registers its six work tools. The first message is queued under the id assignment:<ticket>:<assignment>: a JSON card with the Ticket id, the title, up to 1,500 characters of assignment text, and the origin Trigger rendered inline; once the Session accepts it, Engine.assignmentStarted marks the Assignment running.

      The worker owns the technical work. It reads the repository's instructions and the bundled GitHub skill, reproduces the race, edits the scheduler, and reaches GitHub only through gh as the agent account, committing with the account and its DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL. Long test runs are not a problem for the message loop: the preset moves foreground commands to background jobs after five seconds, and a Ticket holds its worker slot while such work runs, up to the thirty-minute BACKGROUND_LIMIT_MS, past which shell jobs are killed and reported while subagents continue.

      8.6 Reporting, Binding, and the Reviewer

      The worker finishes with orchestrator_report (src/app/tools/executor.ts), state ready and the pull request's number. The tool reads the PR, then in one transaction claims and records. claimPull (src/sources/github-pull.ts) checks that the PR was opened by the agent account from a branch whose last path segment is the Ticket's short name, and binds it — ctx.tickets.bindThread with own: true adds a Subscription on Thread github:413 and a follows entry, so the PR's lifecycle, not a bare report, will end this Ticket. Engine.report (src/core/assignments.ts) records the Report on the running Assignment; because the Ticket now follows an open PR, ready does not end it, and its stage becomes person/review.

      The same transaction queues reportRelay (src/app/notices.ts) as a relay effect, which steers a worker_report message into the main Session; per prompts/dispatch.md it completes the handoff in the originating conversation with orchestrator_reply purpose=result, which lands as a comment on issue #412 linking the PR.

      Then a reviewer requests changes. Their review arrives — through a notification or the subscribed-Thread poll, both ending in intakeComments — as a human Trigger on github:413. This time the Thread has a subscriber: Intake.receive fans the Trigger out as an Input on the Ticket, and because a live Ticket's worker decides messages on its own Threads (followupOwners in src/core/model.ts), no Eval is queued and the gate's follow-up strength never comes into play. The Runtime's event hook relays a follow_up notice to the main Session — its ticket's worker has it and decides — while the delivery effect, reserving the extra slot kept for a person's message, steers the rendered Trigger into worker-<ticket> and reports Engine.inputsDelivered; when the worker's Session takes the message into a step, Engine.inputsRead records that too. The worker pushes the fix and reports progress, which stays internal. CI results on the PR arrive the same way as machine Triggers: fanned out to the Ticket as Inputs, with the Gate filing the batch as not_human in an ignore Decision — recorded, delivered, never mistaken for a request.

      8.7 Merge and End

      A maintainer merges the PR. On the next poll round, pollTicketPulls re-reads the PRs of open Tickets; observePull sees merged, and closePull reports the fact through SourceContext.tickets.threadClosed. Inside the Engine, Tickets.threadClosed marks the follows entry closed with the merge's outcome and time; followsDone confirms the Ticket is done with the Threads it opened, and since its work finished and it took up nothing unanswered, the Ticket ends — by: 'executor', outcome: 'merged', dated at the merge itself. Its Subscriptions stay, so a later human comment on #412 or #413 can resume it under the same Mandate; its worker's background work is stopped after the ending transaction commits.

      The ticket.ended event becomes a ticket_ended notice to the main Session, and pullEndNotices (src/sources/github-pull.ts) would send exactly one terminal notice to each chat Channel the Ticket holds — here it sends none, because the only Channel is GitHub, whose timeline already shows the merge. What remains is the record, all of it in the Store (src/app/store.ts, one SQLite file): the Trigger with its Disposition (which Eval and Decision took it, which Tickets it reached), the accept Decision with its Mandate, and the Ticket with its Assignment, Reports, Inputs and followed Threads — every hop of this chapter readable afterwards through the same resources the Sessions read.

      8.8 What the Walk Proves

      The trace exhibited four properties, each by construction rather than by vigilance. Every hop is idempotent: Trigger ids, Eval ids, Ticket ids and message ids are derived deterministically from their inputs (key in src/core/ids.ts), so re-reads answer duplicate, a repeated accept finds its Ticket, and a retried comment recognizes its own marker. Each fact has one writer: the Engine alone writes Triggers, Threads, Decisions, Tickets and Assignments; the Source owns its cursors; the Outbox owns receipts; Effects owns its queue. Work is stored before it is done: receipts, launches, deliveries and relays are rows inside the transaction that decided them, dispatched only after commit. And a person appears only where the domain says so — the mention that authorizes, the review that corrects, the merge that finishes, and a stop only from an allowed sender.

      A Feishu chat request would differ only at the edges: a different Source (src/sources/feishu.ts, fed by live events rather than polls) and a different Channel for the replies, down the same domain path from Trigger to merged Ticket.

      Chapter 9

      Reading the Source

      dsh-superagent is a hundred-odd TypeScript source files, fifteen prompt files and sixty test files—small enough to hold in mind after a few evenings. The project was written to be read: documents numbered, code layered, two tests keeping the documentation honest. This chapter is a guide to the first pass.

      9.1 Where to Start

      Begin with the documents, in order. docs/000-philosophy.md states the standard every feature is judged by—take as little human attention as possible—and docs/001-domain.md names the vocabulary the code, tools and panel share: Source, Trigger, Thread, Eval, Mandate, Ticket and the rest, each with the rules it keeps, plus a table of concepts deliberately rejected. From there each document adds one layer: authorization, execution, prompts, the panel, deployment, the architecture, and a cookbook for adding a Source. The README says each builds only on the ones before it; tests/docs.spec.ts enforces that numbered documents link only to earlier ones.

      SETUP.md is the fastest tour of the moving parts: a script an agent follows to negotiate a deployment with an operator. Its nine questions, one per message, walk the domain model's flow—where Triggers come from (which Sources, which repository, whose account the agent acts as), who may ask for work (the allowed lists), and what the Executor does with a Ticket (checkout, commit identity, auto-merge). It shows every decision a running system must name, and the defaults chosen where one value suits almost every team.

      Then open the code at three points. src/index.ts is 28 lines: apply reads the machine configuration, constructs the Runtime, and awaits its ready promise. src/app/runtime.ts—254 lines—is the whole system assembled in one constructor: it locks the state directory, opens the Store (the one SQLite database), and builds Setup, Effects, SourceRegistry, Sessions, Settings, the DshExecutor, the MasterAssessor, the Outbox, the Engine and Passes, each wired with the narrow interface it uses; the Executor and Assessor get getters, since they call back into the Engine. It contains no domain rules. Finally src/core/engine.ts (270 lines) is the decision point: one class, five internal parts, every command wrapped in a single repo.atomic transaction, and the role-scoped Pick interfaces at the bottom telling you exactly who may call what.

      9.2 Three Traces

      With the map roughed in, walk three paths; each ends at a question the reading should answer.

      An explicit request, from intake to accept

      Start at src/sources/github.ts, the GitHub Source: its configuration schema (repository, the agent's gh CLI wrapper, four observe switches), the scope function deciding which events are listened to, and the poll round over the agent account's notifications. Then src/sources/github-trigger.ts, where payloads become domain objects: each comment, Issue body or CI transition is a Trigger—one immutable event—with a deterministic id, an actor, whether a person wrote it, and addressed: 'mention' when the text names the agent.

      The poll round hands the Trigger to its SourceContext, which reaches Engine.receive through Passes (src/app/passes.ts), the scheduler that also runs a pass every two seconds. src/core/intake.ts (63 lines) stores the Trigger once—a second delivery of the same id returns duplicate—records its Disposition (where the Trigger went), updates its Threads and their Correlations, fans the message out to subscribed Tickets as context, and queues it for Eval on its primary Thread unless a Ticket's worker already decides it. src/core/evals.ts starts the Eval on a later pass: it batches the Thread's queued Triggers, asks the gate for admission strength and basis, and has the MasterAssessor steer a candidate card into the main Session (the orchestrator's own DSH Session). An accept—typically orchestrator_route in src/app/tools/main.ts calling Engine.decide—lands in Evals.accept, which builds the Mandate (what the accept grants: strength, Policy version, basis, scope) and calls Tickets.create.

      That runs in the same transaction (src/core/tickets.ts:37): the Ticket and its Channels are assembled, the prepareTicket hook adds a worktree name, directory and assignment text, the first Assignment is created, the Ticket subscribes to its Triggers' Threads, the acknowledgement is queued through Replies, and the Executor is asked to start. src/app/outbox.ts records the acknowledgement's receipt and enqueues its reply effect in one transaction; after commit, the effect sends it through the Source. The question: why can the same comment arrive twice, or be decided twice, and still yield one Ticket and one reply? The answer is idempotence at three layers—the Trigger id at intake, the already-accepted check in Evals.decide, and the deterministic acknowledgement id in the Outbox's receipts.

      Work and its reports

      The second trace follows execution. src/app/effects.ts is the durable side-effect queue: a command calls enqueue inside its transaction, and execution begins only after commit; six kinds exist (assessment, launch, delivery, relay, notice, reply), throwing Later defers without counting a failure, and failures retry with backoff. src/executor/dsh.ts enqueues launch and delivery effects: one Executor Session (the worker) and one directory per Ticket (Session worker-<ticketId>), WorkerSlots capping concurrency, a prepare command readying the workspace. src/app/sessions.ts creates and decorates both roles' Sessions—prompts, skills, the worker's restricted tool list, the main Session's no-wait guard—and delivers each message once per request id, recording which prompt revision each Session worked under.

      The facts flow back through src/core/assignments.ts: assignmentStarted, inputsDelivered, inputsRead, turnEnded, and above all report, where a worker's speech becomes domain state—the Attention question is asked, kept or cleared, a replaced question's unsent reply is withdrawn, and a blocked or failed report holds automatic Inputs back until a human message arrives. src/core/stage.ts, all 26 lines, collapses those facts into the one stage row the panel shows. The question: when a worker reports ready, who ends the Ticket? The answer—the Threads it follows do, unless it follows none—is the system's sharpest idea about who owns an outcome.

      A Policy change, end to end

      The third trace starts in src/app/settings.ts save: an optimistic revision check, validation, origin guards (only the panel may change the execution environment), and a comparison of policyVersion before and after—a hash of the rules, the accept mode and the Sources' parts. When the version changed, the save computes policyEffects and, in one transaction with the settings write, calls Engine.policyChanged. policyEffects in src/policy.ts walks the open Tickets: a matched rule disabled or changed, the requester no longer allowed (separating a sender's lost authorization from a mode change by revalidating under the old rules and the new lists), or proactive acceptance withdrawn when auto mode ended. Engine.policyChanged (src/core/engine.ts:255) runs both halves in one transaction: Tickets.policyChanged records the notice, and Evals.policyChanged ends in-progress Evals unavailable with reason policyChanged and requeues their Triggers. The notice itself is an Input: Tickets.policyChanged (src/core/tickets.ts:200) adds a policy-changed Input to each affected Ticket, and the delivery Effect hands it to the worker, rendered by policyMessage (src/executor/dsh.ts): finish what stays within the rule as it now reads, or report dropped. The question: what does a Policy change do to work already accepted? Nothing is cancelled and no Mandate is revoked by the change itself; it is recorded and delivered, and only revalidation can bar continuation.

      9.3 The Map

      The directory tree mirrors the layering. src/core holds the domain—no I/O, no imports outside itself—and the three files carrying the most understanding are engine.ts (the entry point and its five parts: Intake, Evals, Tickets, Assignments, Replies), model.ts (the domain types and shared predicates such as waitsForPerson), and tickets.ts, the lifecycle most rules converge on. src/app is the host-side machinery; beyond runtime.ts, read effects.ts and outbox.ts, which define how state changes become actions. src/app/tools translates tool arguments into Engine commands—main.ts for the main Session's fourteen tools, executor.ts for the worker's six. src/app/views derives the panel's read models without writing; overview.ts and tickets.ts show what the panel considers worth a person's attention.

      src/sources contains the SourceKind protocol (kind.ts), the SourceRegistry that owns instances and implements the Engine's scope (registry.ts), and the two implementations, GitHub (github.ts and its neighbors) and Feishu. src/executor holds the DshExecutor (dsh.ts) and the worker's background-work helpers (background.ts). src/infra is the process side: commands.ts for the CLI transport, environment.ts for the agent's process environment, health.ts for its claimed health entries. src/client is the React panel, importing only types from the host side: app.tsx for its shape, api.ts (typed by src/app/api.ts) for every route. prompts/ holds the instructions models read (orchestrator.md, worker.md, admission.md), skills/ the two Source skills, and tests/ the suite. The module and test tables in docs/007-architecture.md are the complete index; tests/docs.spec.ts verifies they list every module and every test, so it cannot rot.

      9.4 Conventions a Reader Must Know

      The naming grammar comes first. A method that asks for something uses an imperative verb and may be refused (stopTicket, bindThread); a method recording what an adapter did uses the past tense and cannot (assignmentStarted, threadClosed); a query uses a noun (candidate). A past-tense name means there is no refusal path to read—docs/007's "Requests and facts" rule.

      Refusals and explanations are both enumerated. A refusal a person or an agent can cause is a UserError with a fixed code from USER_ERRORS in src/core/errors.ts, each marked missing or refused, worded identically for the API (404 or 400) and the panel. Every Decision explains itself: its reason is a list of Reason { code, values, triggerId } from src/core/reasons.ts, where gates and Source scopes contribute their own codes (not_a_member) and said carries words a person or assessor wrote—so no record in the system is mute. Auxiliary state has its own map: src/kv.ts spells every key-value record's key, type and owner exactly once.

      Two tests are enforced documentation. tests/class-docs.spec.ts fails if any class in src lacks a JSDoc block immediately before it; tests/model-surface.spec.ts checks everything models read—tools, prompts, skills, delivered inputs—against the tool schemas, the glossary and a size budget per role. Last, prompts/*.md is written one sentence per line and joined into paragraphs by promptFile (src/app/skill-files.ts:29), so edits diff sentence by sentence.

      9.5 Tests as the Second Documentation

      The suite encodes behavior in three widening rings. tests/core-engine.spec.ts runs the Engine on MemoryRepositories (src/core/memory.ts) with fake Assessor, Executor and Outbox ports; its describe blocks are named for domain rules—intake, subscription fan-out, follow-up owners, interrupted assignments, the pause—so the file doubles as a catalogue of invariants. tests/runtime.spec.ts runs the whole application on the simulated DSH host in tests/fixtures/host.ts: a fake session controller with real inbox mechanics (steered versus queued messages, claimed steps, cancels), fake CLIs, a job registry and a subagent runtime. The panel tests render each page against tests/fixtures/panel-server.ts, a typed fake of every management route that records misuse. pnpm check runs the typecheck, the tests and the build (package.json).

      Three specs repay reading next. tests/policy.spec.ts covers admission end to end—source scope, the gate, the admission table, Mandate revalidation, policy effects—the fastest way to understand who may start work. tests/followups.spec.ts shows the path that bypasses Eval entirely: a person's follow-up on a subscribed Thread reaching the worker directly while the main Session is only told. tests/runtime-concurrency.spec.ts exercises overlap—Triggers arriving during a pass, Tickets changing during deliveries and launches—where the one-writer design either holds or would show its seams.

      Chapter 10

      Closing Observations

      The README calls dsh-superagent a research prototype, "not an official DeepSeek product," adapted for publication rather than lifted from production. The documentation is unusually specific about what the system does not decide. The interesting closing question is which of those gaps are accidents of a prototype and which are load-bearing omissions—places where the designers chose recording over deciding.

      What Is Deliberately Left Open

      The most concrete gap is retention. docs/007-architecture.md's Persistence section says it plainly: nothing deletes old records yet. Triggers, their Dispositions and Decisions accumulate forever; so do ended Tickets and their Threads, the Outbox's receipts (one per outbound message), and in the key-value area every saved settings revision, every prompt version, the prompt revisions each Session worked under, and the Sources' per-Thread bookkeeping. The statement is a design position more than a to-do: the audit trail is the system's memory of why it acted, and pruning it is a policy question—who may forget, and when—rather than an engineering chore. A team running the prototype for a year carries every message it ever received.

      The trust question is sharper. A Trigger's actor and Thread membership come from the Source itself; its body and quoted text are written by whoever sent the message. The prototype records the basis of every Mandate—who sent it, through which gate cell, under which Policy version—but it has not yet drawn the line between fields it treats as evidence and fields it treats as claims. Until it does, a convincing message body can say anything, and only the gate's verdict on the sender stands behind the work it starts. Deployment isolation is a cousin of the same problem: the agent runs on its own DeepSeek Harness profile, and the open question is pinning the installation beneath it, so upgrading DeepSeek Harness elsewhere on the machine does not break the agent. And the system is single-repository by design: one github.com repository, no GitHub Enterprise Server, one agent account—spanning repositories is not a mechanism it offers, only a second deployment.

      What Transfers

      The transferable ideas are structural, and none of them depends on DeepSeek Harness or on coding work. The first is the command/effect split: a command changes state and enqueues its side effects in one transaction, and adapters perform them only after commit (src/app/effects.ts). Crashes between deciding and doing become impossible, and retries become a property of the queue rather than a concern of every caller. The second is one writer per state: each kind of record has the single class allowed to write it, and everyone else reads or asks. The rule costs a little indirection and buys the ability to reason about any record by reading one file.

      The third is authorization as recorded, revalidatable data. A Mandate is not a session flag or a policy lookup at request time; it is a stored record of what was granted, to whom, under which Policy version, on what basis, and it can be revalidated against the current Policy whenever the system needs to know whether the grant still holds. The fourth is attention as the budget: docs/000-philosophy.md judges every message, setting, panel element and paragraph of documentation by the attention it costs, and removes what does not repay it. Applied relentlessly, it is why the system's outputs are so few. The fifth is a small vocabulary defended by a rejected-concepts list—twelve entries in docs/001-domain.md, each a temptation with its reason for refusal—so the domain model grows by argument or not at all. The sixth is prompts as versioned data: configurations are numbered snapshots, each Session is bound to the revision it worked under, and workers may read only the versions they used, which makes every model request attributable to the exact instructions that produced it.

      The Philosophy as the Artifact

      Strip away the code and the durable artifact is a set of refusals. The agent speaks only when a person must act or can use a result; notices are injected without waking the main Session, and workers hold no tool for asking or presenting to a person except one structured Attention question. It acts only when asked by someone on a list or when a written rule allows it, records what authorized the work, and submits that record to revalidation instead of trusting its past. It declines to grow: new concepts arrive by rejecting named temptations, not by accreting features. Each refusal costs something in capability, and together they buy predictability—a team can predict what the agent will never do, which is the precondition for tolerating what it does. That is the conservative core worth carrying into any autonomous system: autonomy survives in a team only while it is cheap to watch, and it stays cheap only while the system treats human attention as the one budget it cannot print.

      第 1 章

      一个宁愿被忽视的编码智能体

      dsh-superagent 是一个主动式编码智能体，只服务一个 GitHub 仓库。它从 DeepSeek 一个团队的日常开发工作中长出来，大量工程本身就由编码智能体完成；它的 README 对自身定位毫不掩饰：研究代码，为公开发表而整理，不是可用于生产的软件。它以 DeepSeek Harness——简称 DSH——的 bundle 形式发布；DSH 是宿主应用，负责运行智能体的各个 Session、为它们配备工具、并承载它们的 Web 界面。装进一个 DSH profile 之后，这个 bundle 让智能体成为仓库日常里一个安静的成员：它读 issue、读评论、推分支，用一个全团队都看得见、也说得上话的 GitHub 账号开 pull request。

      它用这个成员身份所做的事，刻意收得很窄。智能体监听 GitHub——通常靠轮询自己账号的通知，也可打开可选开关，覆盖每一条新 issue、每个 pull request、每条评论和默认分支的每次 CI 运行——团队需要的话，还能通过一个 bot 监听 Feishu 聊天。当团队允许的人提及智能体并请它做事时，这个请求就变成一张工单（Ticket），即系统里授权工作的单位，通常落在默认一分钟一次的轮询间隔之内。智能体确认一次，说明自己将做什么。随后它在自己的智能体 Session 和自己的工作目录里干活，并在被请求的那段对话里作答，答案常常是一个 pull request。一个 Web 面板汇总一切，并把需要人处理的事摆在最前面。

      两类 Session 分担了劳动。单独一个主 Session，在代码和提示词里叫 orchestrator，接收每一个进入的事件，研判哪些值得做事，然后分派；每张工单配一个执行器 Session，叫 worker，在自己的目录里做真正的编码。这个拆分关系到本书的主题：同人说话的部分，不是改动文件的部分，因此可以给每一部分恰好其工作所需的权限，以及恰好所需的分寸。

      在运维上，这套系统是一件小东西，不是一个集群。它以单个 DSH 进程运行，由 tmux 会话里的一个服务脚本启动，终端脱离后仍能存活，面板绑定在 localhost（docs/006-deployment.md）。所有持久状态——收到的每个事件、每张工单、每条排队中的副作用——都放在配置好的状态目录下的单个 SQLite 文件里；升级之前要备份的，就是这个文件。智能体的身份是一个有写权限的专用 GitHub 账号，登录着它自己的 GitHub CLI；宿主会把各个 worker 的 git 与 GitHub 调用引到这个账号的凭据上，避开操作者的凭据。

      为什么在智能体不做的事情上如此用心？因为一个能为整个团队行动的智能体，也能浪费整个团队的注意力。项目的立身观察写在它的哲学文档里：注意力才是这个系统真正消耗的资源——每条消息、每个通知、每个提问、每项设置、每个面板元素、每段文档，都在花某个人的注意力，而每一项都必须还回比成本更多的价值，否则就会被移除（docs/000-philosophy.md）。代码让智能体来写是便宜的，让人来评审是昂贵的；一个不加限制地同时产出二者的智能体，并不创造产能。它摧毁产能。

      本章的标题压缩的正是这条规则。智能体只在获准的人开口要求时行动，或者在团队写下的规则允许时行动；没有人请求过的工作，从 observe（观察）模式开始——只记录智能体本会做什么，并不真的去做——自治的边界因此随证据放宽，而不是先行假定。它只在有人必须行动、或有人用得上结果时开口：一次确认；干活期间的沉默；结果就绪、需要决定、或无法完成时的一条消息。在这些时刻之外，无人理会正是它为之而设计的。

      面板是同一个想法的另一半。主管打开它，应当能很快离开：它按顺序回答三个问题——现在有没有事需要我；系统是否健康；这件工作的来龙去脉如何——而健康状态在屏幕上不占地方（docs/005-panel.md）。一个仔细花注意力的智能体，和一个仔细花屏幕时间的面板，是同一个设计，不是两个。

      在继续之前，先交代一个诚实的告诫。README 声明这份代码为公开发表做过整理，因此它既不等于团队的内部版本，也不等于他们论文 Exploring Super-agent Design: Towards a More Autonomous Agent System 所描述的系统；文中讨论的某些设计属于未来工作的方向，并未在这个原型里实现。因此，本书的每一个论断都以公开的仓库为根据——它的文档和它的 TypeScript 源码——代码哪里粗糙，书里就照直说。

      本书余下的部分沿用仓库自身的阅读顺序，因为仓库给文档编了号，每一篇只建立在它之前的那些之上。下一章完整陈述设计目标，并把每一条追溯到让它站得住的工程。随后的领域模型一章引入工作词汇——来源（Source）、触发（Trigger）、线程（Thread）、评估（Eval）、授权（Mandate）、工单，以及它们的邻居——连同决定谁可以开工、许可如何变成记录在案的数据的那些规则。再往下，两章深入低层：做出每一个决定的纯核心，和执行每一个决定的边缘——效果队列、Outbox、执行器、各个 Session、来源插件。它们之后的一章追问：为什么是这个形状，而不是别的。随后跟着一个请求从头走到尾，从 GitHub 上的一次提及，到一个已合并的 pull request；最后几章，一章是独自阅读源码的指南，一章是收束整个分析的观察。

      第 2 章

      设计目标

      在哲学文档的开头，dsh-superagent 点名了它要最小化的那个量："尽可能少地占用人的注意力，尽可能多地给出价值"（docs/000-philosophy.md）。这句话是一个记账单位，不是一句口号。一条消息、一个通知、一个提问、一项设置、一个面板元素、一段文档，各自都要花掉某个人的注意力，而项目的每个部分都按这一成本接受评判：每一项给出的价值必须多于它取走的，否则就移除。本章余下的部分，沿着智能体的行为、设计、机器，最后是操作者，来读解这个目标。

      原则对行为的要求

      原则的行为一半，是一套由宿主强制执行、而非口头请求的习惯。智能体只在有人请求时行动，或在一条成文规则允许时行动。"请求"有严格含义：请求必须直接点到智能体，而且必须来自某个来源（Source）的允许列表上的人——来源是智能体监听的事件流，比如 GitHub 或 Feishu——这份列表就是来源在策略（Policy，带版本的接受工作规则）里的一部分。没有人请求过的工作，需要一条团队写下的规则；即便如此，它也从 observe 模式起步：智能体研判自己本会做什么，记录一条标注 "would accept"（本会接单）的 ignore，而不真的接下任何工作（docs/002-authorization.md）。

      智能体只在有人必须行动、或有人用得上结果时才开口。它对请求确认一次，说明将要做什么；干活时保持安静；到结果就绪、需要人来决定、或无法完成时，再写一条。消息很短，而且发到提出请求的那个对话里。

      需要人时，智能体一次只提一个具体的问题。这个问题就是一个待人工决定（Attention）——挂在一辆工单（Ticket，系统里授权工作的单位）上、等人作答的悬而未决的问题——它作为结构化字段，随执行器 Session（运行单个工单的 worker Session）的报告（Report）传递，而不是写成一段自由文字。领域模型明确拒绝从报告的自由文本里推断"正在等人"（docs/001-domain.md）；结构化的事实能到达面板和正确的对话，而埋进段落里的问题，就一直埋着。

      智能体在哪里停下，看影响，不看投入：本地的改动，推进到可评审的结果为止；需要设计决定的改动，停在一个明确的问题上。它也如实报告——草稿就标为未完成，失败就照失败报告，绝不为了免开一次口而绕过限制。

      原则对设计的要求

      设计一侧的目标，关乎理解这套系统本身的成本。第一是概念要少：领域里只放领域自己的概念——来源、触发（Trigger）、线程（Thread）、工单，以及它们的邻居——再加 GitHub、Feishu 这样的具体实现。一项业务需求，要么成为既有概念的属性，要么成为提示词里的一行文字，绝不会成为一个新概念。最清楚的例子是人：人不是领域概念。一个触发，作为一次不可变事件，按来源给出的样子带着行为者的标识；允许列表是来源在策略里的那一部分；同一个人在两个来源上各开有账号，这个事实是智能体读到的提示词文字（docs/001-domain.md）。

      第二是设置要少。当一个值适合几乎所有团队时，用默认值顶替设置；团队能用言语说清的行为，是提示词文字，不是设置。合并把这条分野摆得明明白白：宿主没有任何针对合并的决策逻辑；什么时候允许自动合并、行数上限设多少，由一段名为 Delivery requirements（交付要求）的提示词管辖（docs/003-execution.md）。团队改几个字，行为就变了。

      第三是一个只把"需要人"的事摆出来的面板。打开它，按顺序回答：此刻有没有事需要这位读者；系统是否健康；某一件工作后来怎样了。健康状态不多占一块地方，数字只在能改变主管做法时才出现（docs/005-panel.md）。第四是按顺序读得下去的文档：每篇编号文档只建立在它之前的那些之上，不把任何概念提前引入。

      原则对机器的要求

      上述每个产品目标都隐含一条工程要求，在仓库里表现为一个具体机制。第一条是幂等的 intake，因为纪律从门口开始。轮询器会把同一个事件看到两次，一个重复的工作项，等于让团队为一次请求付两次钱。因此一个触发只存储一次：intake 检查触发的 id，再来一次就返回 duplicate（src/core/intake.ts）；对同一个触发的两次接受也只创建一张工单——某个触发已经开启过工单时，后来的决定返回的是该工单既有的决定（Decision）（src/core/engine.ts）。

      第二条是持久存储的工作，因为一个很少开口的智能体，丢不起它唯一的那条消息。决定之后系统要做的每一件事——把候选转达给主 Session，即研判请求的 orchestrator Session，代码把它的研判角色称为 MasterAssessor；启动一次派工（Assignment，把一张工单绑定到一个执行器实例）；向一张工单投递一个输入（Input）；或在一条渠道（Channel，线程的写侧）上发出回复——都先存储，后执行（docs/003-execution.md）。机制是 Effects：一条以 SQLite 为底座的持久队列，在命令事务内持久化副作用，提交之后再分发，按类别保序，带指数退避（src/app/effects.ts）；Outbox 则在尝试任何发送之前，先把外发消息作为回执持久化（src/app/outbox.ts）。

      第三条是把授权做成记录在案的数据。一次 accept（接单）授出的是一份授权（Mandate）：一份不可变的记录，写下请求的强度（strength）、这项授权允许的工作范围、接受它时所依据的策略版本（Policy version），以及依据——评估（Eval）中确定性第一层的准入（Gate）如何放行了该触发，以及放行自谁（src/core/model.ts）。一张已结束的工单在恢复之前，其授权会对照现行策略重新校验；发送者若已离开列表，或匹配的规则已不复存在，授权即告撤销，工作维持结束（src/policy.ts、docs/002-authorization.md）。授权是系统拿得出来给你看的数据，不是事后重构出来的回忆。

      第四条是可重启。所有状态都在一个 SQLite 文件里，即 <stateDir>/orchestrator.sqlite，由 Store 打开（src/app/runtime.ts）。重启之后，当时正在运行的派工以 "host restarted" 收场；接替它们的派工带着一条恢复提示起步，叮嘱 worker 先查看自己的目录、git 历史和 GitHub，再重复任何对外动作（docs/003-execution.md）。等待中的 Effects 行留在 SQLite 里，直到下一次启动（src/app/effects.ts）。

      第五条是完整可审计，因为对一条输入保持沉默，只有在每条输入都有看得见的下场时才可接受。每个触发都会收到一个去向（Disposition），即它去了哪里的记录：被来源的范围过滤掉，评估成一个决定，扇出（Fan-out）给订阅了它的各张工单，或由一个发现此事超出自己工单范围的执行器交回（src/core/model.ts）。即便被过滤的触发也留有记录，连同来源给出的理由（src/core/intake.ts）。一条消息的下落是一次查询，不是一场调查。

      契约的操作者一侧

      哲学文档的结尾把话转向运行这个智能体的人：智能体以团队天天见得到的账号向人发消息，每条消息都在花同事的注意力，对此负责的是操作者（docs/000-philosophy.md）。这是同一份契约，从操作者一侧看过去的样子。

      从窄处起步：允许列表短一点，主动的工作只做记录；等智能体"本会做"的事看起来确实对，再把两者一起放宽。朝更少的噪声调：智能体吵的时候，把它的提示词改短、改严，或者把它暂停——而不是用更多消息去解释噪声。不要用它堆产量；成批的 pull request 和群发的消息，从团队那里拿走的，比给回去的更多。还有，它说的话归你担：以你的名义发出来的东西要读，错了就在提示词里纠正。

      这条原则就这样把智能体、机器和操作者绑进同一份预算。衡量它的尺度，是哲学文档的最后一句：在正确的时刻给出正确的帮助，其余任何时刻，一概不给。

      第 3 章

      领域模型：一套小而严的词汇表

      每一条到达 dsh-superagent 的事件都走同一条路，领域模型就是把这条路写成名词。来源（Source）盯住一条事件流，把其中一条事件变成触发（Trigger）。触发落在某个线程（Thread）上，路径在这里分岔：订阅（Subscription）把它当作上下文，扇出（fan-out）给已订阅该线程的各张工单（Ticket）；其余的触发则进入一次评估（Eval）。评估以一个决定（Decision）收尾，accept（接单）的决定会创建一张携带授权（Mandate）的工单。派工（Assignment）把工单交给执行器（Executor），结果再经由渠道（Channel）送回来源。这套约束是明说的：代码、工具、面板和文档只用这套词汇，不用别的（docs/001-domain.md）。

      监听侧

      外部世界变为领域数据的地方，立着五个概念。来源是一条事件流；来源种类（SourceKind）是一种可复用的实现，来源实例则是它的一份配置——要不要运行、监听什么。来源是这个模型的海关：它定义什么算一条事件，包括只有随时间推移才成立的条件——"N 小时无人认领"就是一个普通的来源，它等一等，再查一次——并且赶在智能体自己发出的消息和范围外的事件进入领域之前，就把它们丢弃。它还握着自己的读取位置和 bot 身份，因此重启绝不会把旧事件当作新工作重放。

      过了这道门的东西就成了触发：一条不可变的事件，携带来源自己的元数据，比如它的 actor。src/core/model.ts 里的类型把它保持得就这么小：text 和 meta 是不受信任的外部数据，human 和 addressed 是来源声明的事实，不是核心自己得出的结论。触发属于一个或多个线程，它是幂等与审计的单位：同一个触发接两次，只会创建一张工单；src/core/engine.ts 里的 Engine.receive 对此回答 stored、duplicate 或 filtered——重放的事件得到的是识别，而不是再一次裁决。

      有一处是刻意的：人不在这些概念之中。触发携带的是来源给出的 actor 标识；允许名单是策略（Policy）里属于某个来源的那一部分，用那个来源自己的身份写成；同一个人在多个来源上持有账号，这件事只是智能体需要时去读的提示词文本。模型从不在来源之间归并身份：每个来源只说自己那套名字。

      线程是按时序排列的触发，哪些触发算作一个线程由来源定义：一个 issue 的对话、一个聊天话题。一个线程同一时刻至多运行一次评估，期间到达的触发并入下一批。一个线程可以带着几张工单，它持有自己的订阅、正在运行的评估和决定历史，让每次评估都拿到一致的视图和自己的上下文。一个触发可以落在多个线程上；它横跨的这几个线程构成关联（Correlation），而关联只补上下文、从不路由：它让评估能顺着相关证据追下去，路由完全归订阅管。

      渠道是线程的写入侧：一个可写入的地址，由来源定义——对一个话题的回复、一条评审评论——一个线程可以有多个。工单持有的是一组渠道而不是一个，因为确认、回复、pull request 和评审的解决，都是经由渠道完成的写入（src/core/model.ts 里的 ChannelRef）。

      研判侧

      策略是带版本的规则书：研判（Assessment）规则，加上每个来源自己的那一部分——谁可以经由这个来源发起工作（以该来源的身份表述）、名单如何同步、哪些 bot 可以产出候选。规则、接受模式（accept mode）和来源部分合起来构成一个策略版本（Policy version）。与一张进行中的工单相关的变更——比如它当初据以接单的那条规则改了——会作为输入（Input）送到它的派工那里；这种变更不撤销授权，但会丢弃正在运行的评估，而不是听任它对着一本已经不作数的规则书跑完。

      评估是对一批触发的裁决，分两层。第一层是准入（Gate），确定性的：它拿发送者对照来源的策略检查，回答谁可以发起工作、以什么强度（strength）。第二层是研判，是模型的判断，由主 Session 通过 MasterAssessor 执行（src/app/assessment.ts）。评估的输入恰好是这四样：触发批次、线程的快照、该线程上包括已结束在内的全部工单、当前策略；输出是一个决定；输入与输出之间，它不保存任何状态。每个来源的策略还带着一张准入表，表里的格子决定一条消息成为明确（explicit）请求、推断（inferred）候选，还是什么都不是（docs/002-authorization.md）。

      决定是记录下来的结果：accept、stop、ignore 或 unavailable。决定用结构化的原因码解释自己——timeout、policyChanged、stopNotExplicit，定义在 src/core/reasons.ts，其中 said 装着研判者或某个人写下的话。

      强度属于词汇表本身，不属于任何一个模块：评估带着它，决定记录它，授权把它冻结下来。明确请求来自名单之内、点名找智能体的人，来自某个人在已有工单的线程上的追问，或来自设为明确的准入格子。推断候选是系统在没有直接请求时可能动手去做的一切：名单之外的人的追问、设成推断的格子、来源 bot 名单上某个 bot 的消息——上了名单的 bot 能产出推断候选，永远产不出明确请求。其余的一概不获准入。

      接受模式是策略版本的一部分，是策略对"推断强度能走多远"的回答。在 off 下，任何推断都成不了候选。在默认的 observe 下，推断候选照常研判，但阳性研判记作一个 ignore，并标注"本会接单"，什么也不启动。在 auto 下，阳性研判即接单。明确请求在任何模式下都有效，所以预设的路径是先在 observe 下运行，等记录下来的决定看着可靠了，再切到 auto。

      执行侧

      一个 accept 的决定授出一份授权：它依据的策略版本、范围、强度、命中的规则、发送者在该来源上的身份，以及来源收到该触发的方式（src/core/model.ts 里的 MandateBasis）。授权是一纸委任状，不是一份租约。它不可变——想要更宽的范围，就开一张新工单——工单结束也结束不了它。恰好三种操作会改动授权：accept 创建它，人的 stop 撤回它，复验失败废止它。一张已结束的工单在恢复之前，它的授权要对照当前策略复验，一处收严的准入格子或一位除名的发送者，就在这里悄悄追上旧工作。

      工单是获准工作的单位，只有评估能创建它。它引用自己的授权，持有自己的渠道和输入。它的生命归它自己：从 open 走到 ended，它的某个线程上来了人的消息，就再回到 open——除非人已经 stop 过它——它定义自己的状态，而不跟随执行器的会话，因为一张工单可以转手、恢复，或者由几个执行器一起运行。

      执行器本身连同它的 Sessions 和目录，都在领域之外。它通过派工接入，派工就是一张工单与一个执行器实例的绑定。一段时间里一张工单会有多个派工，每个派工各自经历 pending、running、ended，独立于工单；在执行器一侧，只有派工的最终报告（Report）才能结束工单。谁在执行属于领域之内；执行以什么方式存在，不属于。

      订阅是工单与线程之间的多对多关系，由线程持有。一条匹配的触发会扇出给所有订阅在案、仍在进行的工单，不检查是谁发的——这正是要点：后来的讨论不需要再有人点名智能体，也能到达执行器。以这种方式到达工单的人的消息不经过评估，怎么处理由那张工单的执行器决定。执行器也可以只为获取上下文而跟随一个线程，这样的消息同样到达它的工单，但不附带任何权力，也不会让工单恢复。已结束的工单保留它的订阅——哪怕对应的是已关闭或已合并的 pull request——于是人的消息无需评估或决定，就能在同一份授权下恢复同一件工作；人 stop 过的工单则什么也收不到。

      工单之内，剩下的概念负责记录这场对话。报告是派工向它的工单汇报的状态——progress、waiting、ready、blocked、failed 或 dropped；src/core/model.ts 里的谓词 waitsForPerson 读的就是它们：最近一次派工报告了 blocked 或 failed、且此后没有人的消息到来，工单就在等人。待人工决定（Attention）是一个等着人来回答的问题，它携带引发它的那条触发，好让回答回到原本的对话。输入是送达工单的任何上下文：一条扇出的触发、一次策略变更、一次恢复，或者一段纯文本。去向（Disposition）记录一条触发去了哪里——filtered、evaluated 或 fanned out。它不授予任何东西，但它决定"谁来决定人的追问"——恢复与交回的规则正是开在这个事实上。

      模型拒绝什么

      docs/001-domain.md 最有教益的一页，也许是它最后那张表：考虑过又放弃的概念。把拒绝记录在案，本身就是一件设计产物：一套词汇表要保得住小，就得让每一次想把它重新撑大的压力都得到书面回应；每一条拒绝都固化了一条规则，否则这条规则只会活在维护者的记忆里——下一位想"加个简单的等待状态"的贡献者，会撞见白纸黑字的理由：等待为什么归来源管。

      拒绝的概念当初拒绝的理由
      把 Principal 或 Membership 做成实体，或跨来源映射身份人是触发的元数据；允许名单是策略里属于来源的那部分；跨来源映射只是提示词文本
      评估自行调度延迟的触发需要等待的条件就是一个普通的来源，因此评估从不反过来依赖来源
      每个线程至多一张进行中的工单一个线程可以承载几件独立的工作；研判凭借工单列表避免重复
      一种"追加到工单"的决定追加就是订阅的扇出，不需要评估
      对订阅做准入检查订阅覆盖的是整个线程；授权已把许可与上下文分开
      跟随 DSH Session 的工单状态工单可以转手、恢复，或由几个执行器运行，因此它定义自己的状态

      聚合与代码落点

      模型把它的概念归成三个聚合，每个聚合是一条一致性边界。来源持有自己的读取位置，因此重放只是它一个人的问题。线程持有它的订阅、正在运行的评估——串行，把期间到达的触发并入下一批——以及它的决定历史。工单持有它的派工、渠道和输入，并通过 id 引用决定。

      在代码里，这套词汇表有两个家。src/core/model.ts 定义这些类型——Trigger、Thread、Evaluation、Decision、Mandate、Ticket、Assignment、TriggerDisposition——以及维持这些规则一致的谓词：followupOwners、settled、waitsForPerson、liveTicket。src/core/stage.ts 用 ticketStage 给工单的阶段分类——在等人、working、idle 或 ended——读的是同一批报告。判断中确定性的那些部分就放在核心之外不远处：src/policy.ts 里的准入与授权复验，src/core/reasons.ts 里的原因码。而上述每一种记录都只有一个写入者，即 src/core/engine.ts 里的 Engine，于是这套词汇表不只是共享的，更是集中强制的。

      第 4 章

      高层架构

      dsh-superagent 并不是跑在 DeepSeek Harness（DSH）旁边的一个服务，而是作为插件运行在单个 DSH 宿主进程之内。主入口 src/index.ts 导出一个 apply 函数，构造出一个 Runtime 并等待它就绪。同一个包还构建出另外两个插件——src/sources/github.ts 和 src/sources/feishu.ts，由 tsdown.config.ts 打包，在 package.json 里以 ./github-watch 和 ./feishu-watch 导出——而包内的 cordis.patch.yml 把这三个插件全部插入宿主，其中 Feishu 在机器人配置好之前保持禁用，与之一同插入的还有 Sessions 运行时所用的两个智能体预设。来源（Source）这个术语，指的是连到 GitHub 或 Feishu 这类平台的一条连接，因此它并不是一个独立的监听进程：每个来源插件注入 Runtime 发布在 Cordis 上下文上的 orchestrator 服务，并通过它注册自己的 kind（src/sources/github.ts:111）。

      一个进程独占一个状态目录和一个 SQLite 文件。Runtime 的构造函数创建 machine.stateDir，用 proper-lockfile 的 lockSync 锁住该目录（src/app/runtime.ts，锁超过三十秒即视为过期），然后才在 <stateDir>/orchestrator.sqlite 上打开 Store。锁加在目录而不是数据库文件上，因为打开数据库时可能迁移表结构，而第二个进程若写同一份状态，就会与这次迁移竞争。构造一旦失败，Runtime 会关闭 Store 并释放锁，进程内的重启因此能把两者重新拿回来。所有需要持久保存的东西都在这把锁后面：触发（Trigger）、工单（Ticket）、排队的效果行、outbox 回执、设置和提示词版本。

      三层，一个方向

      分层是一条关于导入（import）的规则，这个代码仓库也确实守着它。正中央是纯核心 src/core：Engine、src/core/model.ts 里的领域类型，以及 Engine 消费的那些端口。它是同步的，不做任何 I/O，除了 Node 的哈希（src/core/ids.ts 中的 node:crypto，用来派生 id）之外，不导入自身之外的任何东西。这条规则写在 docs/007-architecture.md 的「Dependency rules」一节；这个目录的导入恰好就止于这些。收益是：每一条领域规则——批处理、恢复、待人工决定（attention）的生命周期——都能对着 src/core/memory.ts 的内存仓库完整演练，不需要数据库、时钟和网络。

      围在核心外面的是应用层 src/app。Runtime（src/app/runtime.ts）是组合根，是唯一一个知道所有部件如何连接的类；它自身不含任何领域规则。与它并存的有 Store（SQLite 持久化）、Effects 队列、Outbox、Sessions、设置（Settings）、提示词（Prompts，带版本的配置），以及承载面板路由的 src/app/http.ts。这一层掌管持久性与时间，并实现核心声明的端口：Store 实现 Repositories，Outbox 实现核心的 Outbox 接口，于是核心永远不会知道自己的类型背后站着哪个数据库、哪个聊天平台。

      在边缘上，负责翻译的是适配器。src/sources 在 SourceKind 协议（src/sources/kind.ts）背后实现 GitHub 和 Feishu，不从 src/app 导入任何东西；它的插件只通过注入的 SourceHost 接口接触应用层，而某个 kind 自身的代码看到的只有更窄的 SourceContext。src/executor 里是 DshExecutor，它把已接单的工作变成智能体 Session。src/client 是管理面板，一个跑在浏览器里的打包产物，只从宿主侧导入类型，外加一份固定的普通值清单（错误码、过滤列表之类），因此可以单独打包而不把服务器拖进来。依赖一律指向内层：边缘可以认识核心的类型，核心则谁也不认识。

      Engine：唯一的决定点

      每一个要紧的状态变更都要经过同一个类。Engine（src/core/engine.ts）是触发（入站事件）、线程（Thread，即会话）、决定（Decision，即记录在案的结果）、工单（已接单工作的单元）和派工（Assignment，即工单的一次运行）的唯一写入者；来源、执行器（Executor）和面板想改这些，都是请它来改，而不是自己动手。它以端口的形式从 src/core/ports.ts 接收各个协作者：存放持久状态的 Repositories，获取当前策略（Policy，一套带版本的授权规则）的 getter，判断某个来源是否监听某个触发的 SourceScope，负责研判（Assessment）的 Assessor，运行已接单工作的 Executor，以及负责渠道（Channel）写入的 Outbox（渠道指明一条回复发往哪个会话）。

      Engine 的所有方法都是同步的，每条命令都通过 repo.atomic(...) 把自己的工作包进一个事务；evaluateDue 为它改动的每个评估（Eval）或工单单独开一个事务，因此一次失败丢弃的工作很少。非法请求抛出 UserError。调用方拿到的不是 Engine 本体，而是各自角色的 Pick：EngineForSources 暴露 receive、bindThread 和 threadClosed；EngineForMainSession 是 decide 和 attach；EngineForPeople 是停止与重试命令；EngineForSettings 只有 policyChanged；EngineForExecutor 是 assignmentStarted、report 这类过去时的事实。命名本身就编码了这层契约——命令是祈使式的（stopTicket），适配器上报的事实是过去式的——而且来源持有的类型上根本没有这样的方法，它想停一张工单也停不了。

      围着同步引擎的两个异步引擎

      Engine 的同步只是一半设计；另一半发生在它的事务之外。两个调度器把这个同步核心变成一个真正运转的系统。

      Passes（src/app/passes.ts）是心跳。它由 Runtime 启动，每两秒跑一个 pass——setInterval(..., 2000)——而每当有来源存入一个触发，或某个工具、一次设置保存或某条 HTTP 路由提出请求，也会立即再跑一个。一个 pass 就是 effects.kick() 接上 Engine.evaluateDue()：先派发所有已到期的排队工作，再让 Engine 启动那些时机已到的评估（对排队触发的评估，每一个都以一个决定收尾）。同一时刻只有一个 pass 在跑；pass 运行途中到来的请求会合并为一次后续执行，而在初始化尚未完成或系统正在关闭时，pass 什么都不做、直接返回。

      Effects（src/app/effects.ts）是那条让副作用在崩溃后依然幸存的持久队列。命令在自己的事务内调用 enqueue(kind, key, payload)，因此这行记录与状态变更一同写入，而处理器只在提交之后运行。每个 kind 加 key 只有一行——对仍在等待的 key 重新入队会替换它的 payload，但保留它在队列中的位置——失败按指数退避重试，抛出 Later 则把工作推迟且不计为一次失败，比如没有空闲的执行器槽位的时候。kind 一共六种，每种归一个适配器所有：assessment（MasterAssessor）、launch 和 delivery（DshExecutor）、relay 和 notice（Sessions）、reply（Outbox）。

      命令与效果的这条分界是整个架构的承重结构。命令在一个事务内改变状态并把工作入队；适配器只在提交之后执行这些工作。因此系统可以在决定与送达之间崩溃而不产生不一致——重启时那些效果行仍在 SQLite 里，已经决定的事仍然会发生。Engine 保持同步，是因为它调用的一切都不等待外部世界；世界都排进了队列。

      配角阵容

      Store（src/app/store.ts）独占那一个 SQLite 数据库，以 WAL 和 synchronous=FULL 打开，并按用途归组自己的对外接口：包在 atomic 里的领域仓库、绝不写库的只读查询、带版本的设置、outbox 回执，以及带类型的键值记录。生成列配合部分索引定义出各个工作集——打开状态的工单、活跃的线程——于是一个 pass 只扫描仍在活动的行，而且从头到尾只有 Store 会打开这个文件。

      Outbox（src/app/outbox.ts）实现核心的 Outbox 端口。send 在一个事务里记下回执并把一个 reply 效果放入队列，该效果的处理器再经由所属来源把消息推出去。顺序按会话维护：同一工单、同一会话里较晚的消息，排在较早的待发消息后面；来源关闭期间一切都等待；会话消失或不再有人监听时，回执落定为 dropped（丢弃）。

      Sessions（src/app/sessions.ts）管理两种角色的 DSH 智能体会话：主 Session，那个负责路由并做决定的协调者；以及每张工单一个的执行器 Session（worker），命名为 worker-<ticketId>（src/executor/dsh.ts）。它为每一个 Session 配上提示词、技能和工具，按 request id 对每条消息只投递一次，并把每个模型请求绑定到当时生效的提示词版本——这份绑定作为记录持久保存，因此一个 worker 事后重读时，读到的正是自己当时工作所依据的那份提示词，不会有任何更新的内容。

      MasterAssessor（src/app/assessment.ts）让主 Session 能够研判推断（inferred）候选：没有人明确请求过的工作。request 排入一个 assessment 效果，把一张候选卡引到主 Session 的当前轮次；orchestrator_eval、orchestrator_eval_read 和 orchestrator_eval_decide 这几个工具给这个 Session 有界的线程上下文，以及一条通回 Engine.decide 的决定路径。评估的截止计时只在卡片送达（candidateDelivered）之后才开始，因此一个忙碌的 Session 不会白白消耗评估时间。

      DshExecutor（src/executor/dsh.ts）给每张工单一个 Session 和一个工作目录。start 与 deliver 分别把 launch 和 delivery 效果入队；stop 通过 Store.afterCommit 取消某个 worker 的轮次，因此一条回滚的命令绝不会停掉 worker；prepare 则把工单的短名、目录和派工文本交给 Engine 的 prepareTicket 钩子。

      面板（src/client，架在 src/app/http.ts 那些仅限回环、同源的 /orchestrator/api 路由之上）只把需要人来处理的东西展示给人：等人处理的工单、问题、处于 unavailable 的评估，以及各执行器的负载。有些操作只存在于面板——驳回一条 unavailable 的决定、重跑初始化——因为任何智能体都不应该有能力执行它们。

      启动与停止

      启动的次序安排得让失败表现为降级，而不是崩溃。src/app/runtime.ts 的 initialize() 先注册 HTTP 路由，这样即便初始化无法完成，运维人员也打得开面板。初始化随后探测仓库与账号；若失败，Runtime 报告 setupPending 并到此为止——各来源仍会记录到来的触发，但不会有任何评估或发送发生。初始化一旦有了结果，Runtime 就装上 Session 与执行器的钩子，确保主 Session 存在，同步每个可同步来源的策略部分，通过 assignmentInterrupted 恢复被打断的派工，然后才启动 pass 与效果。启动全部结束时 ready 才 resolve，初始化让它中途止步的情况也包括在内。

      关闭则把同一份清单倒着执行一遍。stop() 是幂等的；它设置关闭标志，停止 pass，并中止用于取消运行中读取与子进程的那个生命周期信号。它取消主 Session 和每一个执行器 Session 的轮次，同时保留各自的收件箱，然后等待最后一个 pass、效果的排空——未完成的行留在 SQLite 里等下一次启动——以及各智能体转入空闲，并停掉各执行器的后台任务与子智能体。在注销钩子、刷写 Session 持久化之后，一个 finally 块按顺序恢复初始化曾改动过的进程环境、关闭 Store、释放目录锁，这样就不会有别的进程在写入中途打开数据库。

      第 5 章

      走进机器内部（上）：纯核心

      dsh-superagent 关于工作的全部知识——什么可以启动工作、工作如何推进、何时结束——都在同一个目录里。src/core 除 Node 的哈希之外不引用任何外部模块，自身也不做任何 I/O；它的规则是对已存储记录的纯函数，整个领域在测试中也能跑在内存仓库上（src/core/memory.ts）。本章的路线由内向外：Engine 与它的五个部分、作为计算的授权、研判（Assessment）、底下的 Store，以及让各个部分的答案保持一致的谓词。

      5.1 一台引擎，五个部分

      Engine（src/core/engine.ts）是整个领域的单一入口，也是触发（Trigger）、线程（Thread）、决定（Decision）、工单（Ticket）和派工（Assignment）的唯一写入者。触发是一条不可变的事件，由来源（Source）送达，Source 是对接 GitHub 或 Feishu 的适配器；线程是这条触发所属的会话；工单是一个被接受的工作单元。每个方法都是同步的，并把命令包进一个 repo.atomic 事务：仓库在事务内变更，端口在事务内把外部工作排入队列，适配器在提交之后再执行这些工作。调用方从不持有整个 Engine；每个角色拿到的是一个 Pick，只包含它可以调用的方法（EngineForSources、EngineForMainSession、EngineForPeople、EngineForSettings、EngineForExecutor）。

      Engine 把职责委托给五个部分，每个部分都继承 EnginePart（src/core/part.ts）——一个提供共享读取与辅助方法的基类。Replies 不依赖任何部分，Tickets 依赖 Replies，Assignments 依赖 Tickets 和 Replies，Intake 和 Evals 依赖 Tickets——方向只有一个；跨部分的命令，比如 attach，由 Engine 在自己的事务里编排先后。命名语法是统一的：命令用祈使式命名（stopTicket、bindThread、retryTicket），可能被拒绝；适配器报告的事实用过去式命名（assignmentStarted、inputsDelivered、deliveryFailed、threadClosed），只记录、不拒绝；查询 candidate 用名词。

      Intake（src/core/intake.ts）掌管触发的到达。接收的规则是只存一次：已知 id 回答 duplicate；没有任何来源监听的触发同样会存下来，并带上去向（Disposition）——记录一条触发去了哪里——标记为 filtered；其余情况回答 stored。已存储的触发会扇出（fan-out）到订阅了其线程的每张工单，这次投递绕过 5.2 节的准入（Gate），因为它不授予任何东西：消息以输入（Input）的形式到达，Input 是送达 worker（执行器 Session）的一条消息或事实。只有人发来的消息，且落在一条并非仅为上下文而跟随的线程上，才能恢复已结束的工单——被叫停的工单永不恢复。一条人的消息到达了某张工单，就留在那张工单那里：只有当 followupOwners 找不到由其 worker 决定这条消息的工单时，receive 才把触发排进一次评估（Eval）——Eval 评估的是一个线程上排队的触发。

      Evals（src/core/evals.ts）掌管 Eval 的生命周期，以及每次 Eval 收尾时留下的决定——记录在案的结果。分批以线程为单位：所有排队的触发构成一批，Eval 运行期间到达的触发等下一批。一批的强度（strength）、行为者和准入依据，取自其中最强的一条可受理触发。截止时间从候选送达起算：候选卡片到达主 Session——负责协调的那个智能体——时，candidateDelivered 开始计时，未送达的候选永不过期。过期的 Eval 把触发重新排队，连续至多 REQUEUES（两次）；第三次过期记录一条值为 unavailable 的决定，原因为 timeout。

      Tickets（src/core/tickets.ts）掌管工单的生命周期。从 accept（接单）出发的创建是原子的：一个事务里，Tickets.create 写入工单、它的授权（Mandate）——接单所产生的授权——第一份派工（一次 worker 运行）、批中每条触发的每个线程各一份订阅（Subscription，即工单对线程的跟随），以及接单携带的确认消息；要么全部提交，要么全部不提交。这个部分还掌管跟随线程的工单的结束规则：一旦工单开启的线程都不再开放，或者在它一个也没开启时所有被跟随的线程都已关闭，followsDone 即成立，工单以最近一次关闭的结果——merged 或 closed——收尾。输入按 id 只添加一次；自动化输入——CI 结果、机器人消息、备注——在工单 waitsForPerson 期间被扣住。

      Assignments（src/core/assignments.ts）掌管执行器（Executor）及其 worker 报告的内容：过去式的事实——一次派工已开始、输入已送达或投递失败、输入已读入某个步骤、一轮已结束、被宿主重启打断。worker 的报告（Report）有六个状态，从 progress 到 dropped。blocked 或 failed 的报告会扣住自动化输入，直到有人写入；dropped 报告终结工单；ready 报告把工单按 completed 收尾，跟随线程的工单则按 followsDone 的结果收尾。报告可以携带一个提给人的问题——待人工决定（Attention）——可以被提出、保留或清除；问题被替换时，它尚未发出的回复会从 Outbox——外发消息队列——中撤回。

      Replies（src/core/replies.ts）掌管 Engine 发往渠道（Channel）的消息——渠道是线程上的只写地址——每种用途各有自己的放行规则。确认消息要求工单处于打开状态，消息经由线程到达过它，且工单并非仅为上下文而跟随那条线程，作者是人；答复消息要求 worker 的报告确实回答了那个人的问题；结果消息只对处于 ready、completed、merged 或 dropped 的工单放行；待人工决定消息必须对上工单当前打开的问题。每条消息至多入队一次，挂在确定性的 id 之下，例如 key('ack', trigger.id)。

      5.2 准入：授权即计算

      授权不是请求一次性通过的检查站，而是系统随时可以重跑的一套计算。settingsPolicy（src/policy.ts）每次使用都构建一个全新的无状态策略（Policy）——谁可以启动什么的那份配置；什么都不缓存，所以一次保存下一次调用即生效。它的表面很小：version、paused、evalTimeoutMs、gate 函数、用于既有授权的 revalidate，以及用于主动接单的 admitsInferred。

      准入就是 gate(trigger, thread, tickets)：它的回答是一次准入——明确（explicit）或推断（inferred）——外加一个依据，via: 'addressed' 表示列入名单的发送者称呼了智能体，'followup' 表示消息落在一张有参与工单的线程上，'admission' 表示命中准入表的某个单元格，'bot' 表示一个列入名单的机器人。被允许的发送者只要称呼了智能体，就总是明确准入。设为 explicit 的准入单元格先于跟进强度检查，因此线程上的工单绝不会削弱一条明确的请求。参与线程上的跟进，对被允许的发送者是明确的，对其他任何人是推断的——除非接受模式（accept mode）为 off。机器走另一条路：只有列入名单的机器人能通过，至多作为推断候选；没有发送者的 CI 事件使用未列出且未称呼（unlistedUnaddressed）的单元格；其余机器人一律以 not_human 拒绝。

      准入表（src/admission.ts）按来源划分，行就是各个接收范围——Feishu 的群聊与私聊，GitHub 的新建 Issue、pull request（PR）、评论和默认分支 CI。按发送者是否列入名单、是否称呼了智能体，一行至多三个单元格：listedUnaddressed 可取 inferred 或 ignore（忽略），unlistedAddressed 可取 explicit、inferred 或 ignore，unlistedUnaddressed 可取 inferred 或 ignore——未被称呼的消息永远不可能明确。默认值依次是 inferred、ignore 和 ignore；未称呼的单元格只存在于来源能收到该范围内全部消息的地方。

      被准入的候选最终能成为什么，取决于接受模式。在 off 下，任何推断都不会成为候选。在默认的 observe 下，推断候选会进入研判，但阳性研判记为一条 ignore 并标注 “would accept”，并不接单。在 auto 下，阳性研判即接单。明确的请求在任何模式下都有效。

      以上一切收拢进策略版本（Policy version）：policyVersion 在修订标签 mandate-v3 之下，对规则、接受模式以及每个来源的策略组成——允许列表、准入表、机器人列表——做哈希。每份授权、每条决定都记录自己依据的版本；带着旧版本到来的决定记为 unavailable，其所在批次重新排队。版本变更不会波及每张工单：policyEffects（src/policy.ts）计算它牵动哪些存活工单——匹配的规则被改动或禁用、请求者不再被允许、主动工作不再被接受——只有这些工单会收到一条 policy-changed 输入。

      已结束的工单保留其授权，人的消息落在它的某条线程上时，无需新的决定即可恢复，但前提是 revalidate(mandate) 在当前策略下通过：来源必须仍在监听原来的线程；明确跟进的授权直接通过；推断的授权需要 auto 模式且匹配的规则仍然启用；来自准入表单元格的授权必须仍能得到至少原来的强度；机器人的授权要求机器人仍在名单中。未通过的工单保持结束，把等待中的消息释放给评估。只有三种操作会改动授权：accept 创建它，人的 stop 撤回它，复验失败吊销它。

      5.3 研判与决定

      推断候选经由 MasterAssessor（src/app/assessment.ts）——Engine 的 Assessor 端口——变成一条决定。Eval 启动时，评估器把一个持久的 assessment effect 排入队列；它的处理器把候选卡片引到主 Session 的当前一轮里，然后调用 candidateDelivered，Eval 的截止时间正是从这一刻开始计算。明确的候选从不走到这里：评估器拒绝它们并指向 orchestrator_route，因为明确的请求走的是路由，不是研判。

      主 Session 用三件工具工作。orchestrator_eval 返回的是上下文而不是指令：触发的文本（至多 4,000 字符）、同批的其余触发、至多八张相关工单、构建这次 Eval 所依据的策略版本，以及一个有界的线程窗口——线程最前面的五条消息，加上触发前后各五条，每条截断到 400 字符，离触发最近的两条放宽到 1,200。orchestrator_eval_read 可以展开其中任何一项——完整消息、更多线程分页、文件、图片——但游标必须从返回的引用里照抄。orchestrator_eval_decide 提交判定，也就是研判。

      assessmentOutcome（src/policy.ts）把这份判定转换成 Engine 的结果，而且它相当严格。它要求对每条启用的规则——无论匹配与否——恰好各给一份规则评估，此外任何情况都会抛出异常。接单必须带着已定案的方向——要么请求了实现，要么指定了目标或依托既有标准，没有悬而未决的设计决定（directionAllowed）——否则降级为一条 ignore，原因为 directionUnsettled；它必须至少匹配一条启用的规则，否则记 noRuleMatched；还必须引用 intent_evidence，即确立意图的那些原话。在 auto 模式之外，推断的接单变成一条 ignore，标记为 would_accept，原因为 observed。Engine 对这些一概不轻信：Evals.decide 会用 admitsInferred 复查每一条推断的接单，不合条件就以 notExplicit 拒绝。

      有一条捷径放过无关紧要的情形。卡片明显不触及任何启用规则的推断候选——普通闲聊、无关讨论——可以直接凭卡片忽略，决定在所给理由之外记录代码 ignoredFromCard，以区别于一次完整的研判。

      5.4 持久化：一个文件、生成列、每张表一个写者

      核心之下是一个 SQLite 文件 <stateDir>/orchestrator.sqlite；它只由 Store（src/app/store.ts）打开，而且要等组合根 Runtime 锁定状态目录之后，因此不会有第二个进程写入同一份状态。它以 WAL 模式加 synchronous=FULL 运行，九张表按“谁可以写”切分状态。

      表写入者
      trigger、dispositionEngine
      threadEngine；来源只写各自的 meta
      ticket、decisionEngine
      trigger_threadStore，作为随它保存的每个触发一并更新的索引
      effectEffects

      每份状态只有一个写入者，这张表编码的就是这条规则；其余角色只能读，或者去问。trigger_thread 不是领域数据，而是 Store 随每个触发一并维护的索引，这样线程的时间线可以按时间再按 id 排序读出，不必扫遍每个触发。

      各行本体是 JSON，工作列由它生成：value -> '$.ended' IS NULL 期间 ticket.open 成立；输入尚未送达，或最新一份派工还在 pending 或 running 时，ticket.active 成立；触发在排队或 Eval 正在运行时，thread.active 成立；只要有任何工单订阅，thread.subscribed——面向来源——成立。每个这样的列都在自己的集合上带一个部分索引，于是一趟 Pass——每两秒扫一次、执行到期的 effect 并运行 Engine.evaluateDue 的那趟扫描——只读活跃的工作。早于某个列的数据库会在打开时补上这一列，由 SQLite 从已存的 JSON 填充。

      时间是文本，这是刻意的。每个触发的时间戳在进入时由 isoTime（src/core/model.ts）规范化成 Date#toISOString 产生的那一种形态，于是已存储的时间在内存里和 SQL 里都能按字典序比较——deadline <= now 就是一次字符串比较。

      事务借助 savepoint 嵌套，afterCommit 是提交与后果之间的接缝：事务内排入的回调只在最外层提交之后运行，回滚会丢弃本层的回调，抛异常的回调会被上报而不连累已提交的事务。它服务的是那些无需熬过崩溃的内存内跟进；持久的副作用则归 Effects 队列。

      kv 表装着其余一切，KV（src/kv.ts）是它的登记处：每个键值记录只声明一次，写明类型和唯一拥有它的组件——schema 版本归 Store，设置的修订记录归 Settings，主 Session 的 id 归 Runtime，读取游标归各来源。每个键只书写一次，归属一目了然。

      schema 的演进刻意保守。SCHEMA_VERSION 是 11，且只增不减（src/app/migration.ts）：版本更新的数据库拒绝启动，比 OLDEST_SCHEMA（10）更老的直接拒之门外，schema 10 的数据库在打开时于一个事务里改写成 schema 11 的形状；一旦失败，文件原封不动。

      5.5 共享谓词

      跨部分的规则不放在各个部分里，而是放在模型旁边，成为每个部分都会调用的小谓词。waitsForPerson（src/core/model.ts）回答：工单最近一份派工是否报告了 blocked 或 failed，且此后没有人的消息到达。它成立期间，Tickets.addInput 扣住自动化输入，ticketStage 把工单归为等人（person）阶段，canRetry（src/core/stage.ts）让它可重试；随后的报告两者皆非、一条人的消息或一次重试，都会解除这个状态。

      followupOwners 回答由谁决定一条人的跟进：那些消息落在其本体线程上、仍能决定且尚未交回的工单——活着的，加上并非被人叫停、还有消息等着将其恢复的已结束工单。只要存在这样的归属者，消息就不进评估，主 Session 对它最多只能叫停工作——这一拒绝由 Evals.decide 借 leftToWorkers 落实。settled 回答一条决定是否了结了请求——stop、unavailable、被拒绝的叫停和路由都不算——正是它让工单得以结束，而不把早有决定的消息再送回评估。

      ticketStage（src/core/stage.ts）就是 docs/003-execution.md 里那张阶段表的代码版，自上而下读取，首个命中的行生效：投递失败、打开的待人工决定或 ready 报告把工单放入 person 阶段，blocked 或 failed 的报告只有在 waitsForPerson 成立时才算，随后是 queued、idle 和 working。canRetry 闭合了这个环，让恰好那些人能补救的 person 阶段停滞——被扣住的工单或失败的投递——变得可重试。

      把它们集中起来的理由不是优雅，而是同一。工单是否在等人，这个问题输入投递、阶段分类器、重试命令和面板都要问；如果各按自己对报告和输入的解读作答，被扣住的输入和 “Blocked” 标签迟早对不上。作为对已存储记录的纯函数——followupOwners 接收的是一个记录接口，同一段代码跑在 SQLite 上、内存里和面板中——它们处处给出同一个答案，只在一处修改，并被各自的测试（tests/stage.spec.ts）钉住。

      第 6 章

      走进机器内部（下）：边缘

      上篇跟着 Engine 走了一遍，那个握有每一次决定的同步核心。可是一颗只会做决定的核心，不过是瓶中之脑。这一篇跟着把它接入世界的机器走：记住承诺过的工作的队列，让智能体按次序开口的 Outbox，给每个工单（Ticket，系统里被接受工作的单位）配上一个外壳和一个执行器 Session（worker）的执行器，管理模型对话的那一层，还有监听 GitHub 和 Feishu 的来源（Source）插件。有一条规则一再重复：决定在事务内做出，工作放到事务之后，从存储出发去执行。

      6.1 效果队列：存下来的工作

      决定之后 dsh-superagent 要做的每一件事——转达 worker 的一条报告（Report）、发起一次派工（Assignment，即工单工作的一次运行）、投递一条输入（Input，发往该 worker 的一条消息）、送出一条回复——都是先存储、后执行。承担这座持久桥梁的是 Effects（src/app/effects.ts）。命令在自己的事务内调用 enqueue(kind, key, payload)；这一行随决定一起落进 SQLite，直到提交之后才开始执行。两个时刻之间崩溃，什么都不会丢。

      队列对每个 kind/key 组合只保留一行。对等待中的 key 重新入队，会替换其载荷、清零失败计数并让它立即到期，而这一行仍保留最初拿到的序号——合并永远不会打乱队列次序。一个世代计数器标记每次替换，正在运行的尝试因此删不掉更新的载荷。处理器按 kind 注册一次，各带并发上限和退避边界；到期的行从最旧的开始分发，失败以指数退避重试，封顶为该 kind 的上限。

      并非每次拒绝都算失败。抛出 Later 异常——没有空闲的 worker 槽位、处理被暂停——会在初始延迟后重新调度该行，而且不计入失败。真正的失败会计数，一旦某个 kind 的一项连续失败三次（src/app/effects.ts 中的 FAILURES_BEFORE_ERROR），该 kind 的健康条目就变为 error，呈现在面板上。

      六种 kind 覆盖了边缘。assessment 效果把一次评估（Eval）——即对主动请求的研判（assessment）——的候选卡片送进主 Session 的回合；收到之后，MasterAssessor 告诉 Engine，由 Engine 启动这次评估的期限计时。launch 效果启动一个待发的派工——准备命令、执行器 Session、派工消息。delivery 效果把工单等待中的各条输入按次序交给它正在运行的派工；它的失败是安静的，因为这些失败早已显示在各自的工单上。relay 效果把 worker 的报告或提问、或某个人的追问送进主 Session 的回合，notice 效果则只注入、不唤醒它；两者都严格排序，一个失败会拦住同 kind 的后来者。reply 效果运送 Outbox 的消息。一轮 Pass——src/app/passes.ts 每两秒一次的清扫——也会取走到期的行。

      6.2 Outbox：按序发言

      当 Engine 决定在某个渠道（Channel）开口——也就是回复要送达的那个地址：对已接受请求的确认、对问题的回答、对已完成工作的结果——Outbox（src/app/outbox.ts）负责把这条消息变成现实。send 在一个事务里记录一张回执并入队一个 reply 效果；回执以忽略重复的方式插入并永久保留，因此一个消息 id 绝不会入队两次，即使跨越重启。

      排序按工单、按会话分别进行。发送之前，处理器会问 receipts.behind（src/app/store.ts）：同一工单发往同一会话的更早消息是否仍在等待、失败是否少于三次；若是，后来者就等。这道阈值是一个安全阀：一旦早先的消息已失败三次、已作为问题浮出水面，它的后继就会发出，而不是堆在它后面。其他工单的消息从不等待。

      等待与丢弃是分开的两回事。只要消息所属的来源关闭或未安装，它就等待。只有在会话永远收不到这条消息时才会丢弃：GitHub 上已删除的 Issue 或已锁定的会话，来源回答 gone；Feishu 消息遭撤回（channelGone）；来源不再监听那个会话（channelIgnored）。丢弃的回执留在记录里，带着何时、为何、属于哪个工单，而一张丢弃的确认回执显示为已丢弃，不是已发送。重试从 5 秒起逐次翻倍，退避到 300 秒。次序之所以存在，是因为会话按时间展开、由人来读：确认必须先于回答，回答先于结果，否则读者会认定智能体根本没听见他们。

      6.3 DshExecutor：每个工单一个 Session、一个目录

      每个工单得到一个 worker Session，命名为 worker-<ticket id>（src/executor/dsh.ts 中的 workerSessionId），外加一个目录。prepare(ticket, outcome) 钩子在接单时把执行事实填齐：一个由一到四个词组成的 kebab-case 短名加 12 个字符的 id 后缀，配置的执行根目录（默认 <stateDir>/work）之下的目录，以及派工文本。

      第一次派工之前，如果目录还不存在，配置的 prepare 命令会在执行根目录下经 sh -c 运行一次，限时十分钟；典型命令是一次 git worktree 检出。失败的 prepare 有意不重试——目录已存在就算已准备好，重试只会追认那条失败命令留下的东西。工单随即标记为 failed，等一个人或一次重试来重新准备。

      WorkerSlots 管理并发。工作经由前面说的 launch 和 delivery 效果到达执行器。工单从一次 launch 的起点（准备工作也算在内）占住一个槽位，或从唤醒其空闲 worker 的那次 delivery 起占住，并贯穿整个回合。生效的是配置的 maxWorkers，外加一个只有人的消息才能占用的额外槽位；唤醒优先于 launch，因此新工作永远拦不住一个人继续已有的工单。各次 launch 并发运行，一次缓慢的 prepare 只拖延它自己的工单。

      一时性的失败有三次机会：transient 判定认识 HTTP 408、429 和 5xx，也认识连接拒绝、连接重置和连接超时。一次瞬态的 launch 失败会随效果退避再次运行；一个失败的回合会在 15、30、60 秒后收到「从中断处继续」的消息。任何其他失败都会让工单失败。

      一个回合结束时，shell 任务或子智能体可能仍在运行。工单保留槽位、保持 working；untilQuiet（src/executor/background.ts）盯着两者，完成的任务或子智能体会带着结果唤醒 worker。每个回合之后，后台工作至多三十分钟：到点后 shell 任务杀掉——worker 会在下一个回合得知是哪些——子智能体则继续，因为停下它们只会再次唤醒 worker，而工单报告为 waiting，附上 worker 的最后留言。派工结束时，任务杀掉、子智能体释放，它们唤起的回合丢弃。交给人的时候，槽位立刻释放：子智能体停止，但留下来供人查看的任务——比如一台运行中的服务器——会继续跑到派工结束，不受时限约束，结束时也照常回收。

      重启也遵循同样的纪律。启动时 resume() 从最旧的开始遍历未结的工单：正在运行的派工报告为 assignmentInterrupted，它会开启一个新的派工，附一条恢复提示——在重复任何对外动作之前，先检查目录、git 历史和 GitHub——待发的 launch 重新入队，除非其工单在等人。prepare 命令和 worker 的提示词从 src/app/execution-environment.ts 接收同一套执行变量：来自执行器的 DSH_SUPERAGENT_DIR、NAME、TICKET 和 BLOCKED_COMMANDS，来自 GitHub 的仓库与 pull request 变量，来自 Feishu 的会话与机器人变量；其中不含任何凭据。

      6.4 Sessions、投递与 MasterAssessor

      Sessions（src/app/sessions.ts）管理两种角色的会话：负责路由和研判的主 Session，以及各个 worker。ensure 按角色所属的模型创建 Session——模型在创建时由 src/app/role-models.ts 一次性指定，不碰宿主的全局默认——并按其预设创建。两个预设 dsh-superagent-router 和 dsh-superagent-worker 定义在 cordis.patch.yml：都会在前台 shell 命令运行 5 秒后把它转为后台任务，并把任务等待的上限设为 5 秒；router 只保留路由工具，worker 只保留干活工具。

      提示词有版本，每次模型请求都把 Session 绑定到当前修订；Session 历次工作所用的修订会持久保存，promptVersion 加上 mayRead 把 worker 限制在它实际运行时的提示词文本之内。内容经两种效果流入：relay 送进主 Session 的回合，notice 只注入、不唤醒它。noWait 守卫不让这个 Session 干等——凡是命令位置上运行 sleep 的 shell 命令、超过 30 秒的 timeoutMs、超过 5 秒的任务等待，一概拒绝——并解释说，它等的东西自己会来。

      投递由 AgentDelivery（src/app/delivery.ts）去重：每个请求 id 只进一次，无论 Session 是现存的还是恢复出来的；已投递的 id 从会话事件、持久化历史和待处理收件箱三处跟踪。每条消息都带插件自己的来源标记，系统的话永远冒充不了一个人的话。

      MasterAssessor（src/app/assessment.ts）是主 Session 望向一次评估的窗口。它的 context、read 和 decide 支撑起三个 orchestrator_eval 工具。context 返回候选内容——触发（Trigger）的文本（最多 4,000 字符）、同批的同伴、相关的未结工单、策略版本（Policy version）——外加一个有界的线程（Thread）窗口，经来源自己的读取器读出：最前面五条消息，加上触发前后各五条，截到 400 字符，紧邻触发的两条放宽到 1,200，其余一律是 50 字符的存根（src/sources/admission-context.ts）。read 展开存根、翻页线程，并从每个评估专属的缓存里读仓库文件和图片。decide 把研判转成给 Engine 的形式，Engine 会对照当前策略再核一遍；评估结束时，release 丢弃缓存的状态，此后的读取一律拒绝。

      6.5 来源：协议背后的插件

      来源是一个把一项外部服务接入领域的插件：它把事件变成触发——即 Engine 存储的那些归一化记录——回答范围问题、发送回复，并为研判读取线程上下文。契约是 SourceKind（src/sources/kind.ts）：身份、配置 schema 与表单字段、派生事实、各自拥有的健康条目；其余都是可选——一条 scope 监听规则、一个带 allowed、send 和 link 的 channel、一个 threadContext 读取器、搜索用的 find、一个策略部分、执行变量。

      SourceRegistry（src/sources/registry.ts）掌管已安装的种类和已存储的实例，并实现 Engine 的 SourceScope，经由该种类回答范围问题。注册会认领该种类的健康条目——重名与保留的 sync: 名字一概拒绝——存储的配置不再通过校验的来源则禁用。插件拿到一个 SourceHost（src/sources/host.ts）；种类代码能看到的只有 src/app/source-context.ts 搭建的窄口 SourceContext：receive 一个触发、读取并修补自己的线程与状态、只能经 bindThread 和 threadClosed 改动工单、经 Outbox notify、并且只在自己声明的条目上 report。

      GitHub 来源（src/sources/github.ts）跑一轮轮询：先通知，再是受观察仓库里新 Issue、新评论和默认分支 CI 的信息流，然后是未结工单的 pull request 及其 CI，最后是订阅的线程。每个 Issue、pull request 和线程独立读取；一次失败的读取把错误留在自己的线程上，并计入来源的错误——默认三轮失败后上报——而已删除的 Issue（HTTP 410）立刻丢弃，失败满一天的读取则放弃。github-trigger.ts 把评论、评审、Issue 正文和 CI 状态迁移归一化成触发。github-pull.ts 把 pull request 绑到工单上——claimPull 接受来源 pull request，或智能体自建、且分支最后一段路径等于工单短名的那一个；observePull 对账关闭事件；pullEndNotices 写入终局的会话通知。github-channel.ts 发布评论和评审回复，内嵌幂等标记，目标评审评论消失时退回 pull request 的会话；github-read.ts 提供 CI 快照和仓库读取。

      Feishu 来源（src/sources/feishu.ts）立在 feishu-loops.ts 的三个循环上：一个从机器人 lark-cli 派生的实时事件消费者，带退避地重启并上报每次失败；一个每分钟对配置会话和已知私聊扫一遍的历史 Pass，顺带找回实时流漏掉的话题回复；还有对订阅话题的轮询。feishu-trigger.ts 里的一条翻译规则同样服务实时事件、历史页和话题页，因此每条读取路径都为一条消息推导出同一个确定性的触发 id。feishu-channel.ts 以消息 id 为幂等键回复到目标所在的话题，遭撤回的目标是 gone；feishu-read.ts 读取触发的消息、根、父级、线程和周边会话；feishu-image.ts 按 img_ 键从携带图片的那条消息下载图片。

      两者都立在 src/sources/poll.ts 上。POLL_HORIZON_MS，十四天，限定一个没有在跑工单的已订阅线程还会轮询多久；cursorAt 把每次轮询的起点回拨五秒，免得错过迟到的事件，重叠部分由触发 id 去重吸收；pollThreads 把失败作为 pollError 留在线程上，下次成功即清除，于是一次坏读取既不毒害其余线程，也不会无声消失。

      6.6 面板与健康

      面板的骨架是工单的阶段（stage）模型，由 ticketStage（src/core/stage.ts）实现：每个未结工单都有一个阶段，由它在等什么决定。表格从上往下读，第一行命中即生效。

      阶段工单在等什么面板标签
      person / delivery向执行器 Session 投递一条输入失败，正按退避重试输入未送达
      person / answer它有一条待人工决定（Attention）——一个问人的问题等待答复
      person / review它最新的报告是 ready等待评审
      person / blocked, failed它最新的报告是 blocked 或 failed，此后没有人的消息到达阻塞 · 失败
      working / queued没有派工，或有一次派工在等 worker 槽位排队中
      idle它最新的报告是 waiting，或其派工已结束等待触发
      working其余一切工作中

      person 阶段意味着工单缺了人就走不下去，而人的一条消息会把 blocked 或 failed 的工单放回它的执行器。这张阶梯表按构造既穷尽又互斥，因此面板上的每一行陈述的都是一个可核验的定义，不是某个内部状态码。

      收场的种种方式也映照着这份诚实。一条 ready 报告让不跟随 pull request 的工单完结；一条 dropped 报告让它不带消息地结束——除非有匹配的规则要求发一条——并保留其订阅（Subscription），日后一条人的评论即可让它恢复。跟随 pull request 的工单，只有当它开启的 pull request 都已不再打开时才算完成——如果一个都没开启，则等到它跟随的每个 pull request 都关闭——然后以最后一次相关关闭的结局收尾，merged 或 closed，并由 pullEndNotices（src/sources/github-pull.ts）向聊天渠道发出最后一条通知。所以「等待评审」的意思是：一条 ready 报告，外加一个 pull request。

      健康也遵循与其他一切相同的单写者规则。HealthBoard（src/infra/health.ts）为每个部分持有一个条目——runtime、evals、models、每种效果一个、worker、每个来源种类的条目、策略同步用的 sync:<id>——每个条目恰好由一个写者认领；第二个认领会抛错。错误只在连续三次失败后才浮出水面，因此一次偶发的网络错误保持安静，一次失败的输入投递则显示在它自己的工单上。这就是面板的承诺（docs/005-panel.md）：健康的状态不占地方，而值守的人真正看到的，要么是需要他们的工作，要么是他们能着手处理的问题。

      第 7 章

      为什么这样设计

      dsh-superagent 把事件流变成队友的工作。来源（Source）——一个 GitHub 仓库或一个 Feishu 会话——产生不可变的事件，称为触发（Trigger）；触发归拢进线程（Thread），也就是它们所属的那场对话；评估（Eval）决定一批触发能否开工；一次 accept（接单）授出一份授权（Mandate，这项工作被记录在案的许可），并开出一张工单（Ticket），派工（Assignment）再把工单交给运行在执行器 Session（worker）里的执行器（Executor）。其中一个 Session 与众不同：主 Session 负责研判与路由。统领全局的理念（docs/000-philosophy.md）是一份注意力预算——尽可能少地占用人的注意力。六个结构性决定承载着这份预算，每一个之所以存在，都是因为某个看起来更省事的替代方案早在纸面上就被拒绝了；这里最有力量的产物，正是这些拒绝。

      7.1 异步世界里的同步核心

      Engine（src/core/engine.ts）是触发、线程、决定（Decision）、工单和派工唯一的写入者，它的每一个方法都是同步的。每条命令都把全部工作包进对 Repositories.atomic 的一次调用：receive、decide、attach、stopTicket 和 report 全是同一个形状。即便是清扫式的方法 evaluateDue——它会访问许多线程和工单——也会为每一个被它改动的评估或工单单独开启一个事务（src/core/engine.ts:75）。核心也不做任何 I/O。src/core 不引用自身之外的任何东西，唯一的例外是 Node 的哈希（src/core/ids.ts 里的 node:crypto）；它接触外部世界只能经由 src/core/ports.ts 的端口，而端口的每个方法都是同步的，“so atomic can wrap a unit of work.”（这样 atomic 才能包住一个工作单元）。

      这里拒绝的替代方案，是人们熟悉的异步编排核心：创建工单，await 启动结果，记录把线程未来消息扇出到工单的订阅（Subscription），再 await 回执。每一个 await 都是一扇崩溃窗口，而每一扇崩溃窗口都是一个可观察到的独立状态——一张没有派工的工单，一条指向从未启动的工作的订阅。领域测试把想要的不变量直接写成了测试名（tests/core-engine.spec.ts:136）：“records an accept with its ticket, subscriptions and acknowledgement together, or none of them”（把一次接单连同它的工单、订阅与回执一并记录，否则一条也不记）。当 prepareTicket 钩子在接单中途抛出时，决定、工单、订阅和排队中的回执一并消失；没有任何交错，因为根本无从交错。

      这份收益向外层层放大。因为核心不做 I/O，整个领域跑在 MemoryRepositories（src/core/memory.ts）上，它的 atomic 先给各张映射表拍下快照，抛出时再原样恢复。tests/core-engine.spec.ts 的一千六百行——接入、评估分批、扇出（fan-out）、恢复、暂停、策略（Policy）变更、中断的派工、失败的投递——完全不 mock 网络；端口是小小的内存替身，时钟经由 Engine 的可选 now 注入。确定性是结构性的：id 由各自的输入推导而来（src/core/ids.ts 的 key），测试用手拨着时间前进。异步的世界——轮询的来源、思考中的 Session、重试中的投递——则被推到了边缘；在那里，崩溃的代价是一次重试，而不是一个谎言。

      7.2 命令在今天，效果在明天

      Engine 提交的每一次状态变更都有一道影子：它所许可的副作用。启动一个 worker，把输入（Input，工单的上下文）投递给正在运行的派工，把 worker 的报告（Report）转交给主 Session，在渠道（Channel，线程的写入侧）上发出一条回复——这些都不发生在命令内部。命令在自己的事务内调用 Effects.enqueue(kind, key, payload)（src/app/effects.ts:61），事务提交之后，处理器才开始运行。这是把事务性发件箱（transactional outbox）模式推广到所有副作用：意图是一条 SQLite 行，与它所追随的状态同样持久。因此，“已决定”与“已执行”之间的崩溃无从观察，因为意图的记录与决定写在同一个事务里；重启时这些行会重放，工作不会丢失。

      有两处细化很关键。按 kind 和 key 合并——一条 INSERT ... ON CONFLICT——会替换仍在等待的那一行的 payload，重置其失败计数，并让它立即到期，而不丢失队列位置：五个输入同时到达，只产生一次投递。而 Later（src/app/effects.ts:5）是把背压挑明了：抛出它的效果——处理已暂停、worker 槽位已满——会被重新调度，且不计为失败。

      Outbox（src/app/outbox.ts）是最纯粹的实例。send 在单个事务里记录一条消息的回执，并把它的 reply 效果排入队列；一个消息 id 只要记录过一次，就绝不会被再次入队，回执也永久保留，于是已发出的回执就始终算作已发出。投递按工单和会话保持有序：只要同一工单、同一会话里更早的一条消息还未决，receipts.behind（src/app/store.ts:259）就会扣住后一条，直到那条更早的失败满三次、转而作为一个问题浮出水面为止。正因如此，回执绝不会抢到紧随其后的答复前面：在结果之前先读到“做完了”的人，会就此不再信任这个智能体。

      7.3 每种状态只有一个写入者

      docs/007-architecture.md 的依赖规则陈述了一条朴素的不变量：每一类状态恰好有一个写入者。Engine 拥有触发、线程、决定、工单和派工；Settings 拥有设置及其历史；Prompts 拥有提示词版本；Effects 拥有效果行；Outbox 拥有回执；每条健康记录属于在 HealthBoard 上认领它的那个部件，而 HealthBoard 拒绝第二次认领；一个来源拥有自己的读取位置和线程元数据。来源甚至不能直接编辑工单——它只能调用 bindThread 和 threadClosed，而这两条都是 Engine 的命令。

      这里拒绝的替代方案是锁和约定。互斥量能把访问串行化，却分派不了责任；一条“来源不该写工单”式的约定会无声地腐烂，直到某个 bug 证明它从来就不承重。在这里，这条不变量读一读类型签名就能核验，因为 Engine 从不把自己整体交出去。每个调用方拿到的是自己那个角色的 Pick：

      export type EngineForSources = Pick<Engine, 'receive' | 'bindThread' | 'threadClosed'>
export type EngineForPeople = Pick<Engine, 'stopTicket' | 'retryTicket' | 'reevaluate' | 'unsubscribe' | 'dismiss'>

      完整的集合——EngineForSources、EngineForMainSession、EngineForPeople、EngineForSettings、EngineForExecutor（src/core/engine.ts:261）——让误用无从表达：来源的代码里没有任何能停掉工单的方法，执行器的接口几乎全是过去时的事实陈述（assignmentStarted、inputsDelivered、turnEnded），而非命令式口吻。每种状态一个写入者，再加上每个 Store 一个进程（Runtime 锁住状态目录），领域里一把锁都不用放，就换来了并发纪律。

      7.4 授权是记录在案的数据

      一次 accept 本可以只意味着“此事曾获准一次”。它实际上产出一份授权（src/core/model.ts:126）：一条不可变的记录，写下策略版本——策略就是那套带版本的接单规则——强度（strength）、范围、发送者在该来源上的身份，还有一个 basis，写明准入（Gate）如何放行了这条触发：可能由名单上的发送者 addressed（指名），可能是在已有工单的线程上 followup（跟进），可能是 admission（准入表）表格里的一个格子，也可能是来源机器人名单上的 bot；凡由规则裁决的情形，都附上命中的规则。这里拒绝的替代方案，是在每个动作处查验的访问控制列表：那会让现行规则去管辖按旧规则接纳的工作，还会把权限逻辑散落到各个调用点，任其在那里漂移。

      这个设计让工作活得比接纳它的规则更久。策略变更时，policyEffects（src/policy.ts:144）精确算出这次变更波及哪些尚未关闭的工单——命中的规则变了或停用了、请求者可能不再能开工、主动接纳终止——Engine.policyChanged 再把这件事作为一条输入，只投给那些工单。这里什么都不取消；docs/001-domain.md 的否决概念表拒绝了 “cancelling running Tickets on a Policy change”（在策略变更时取消运行中的工单），因为变更引发的取消只会留下做了一半的工作。重新校验只发生在恢复时：一张已结束的工单若被某个人的消息唤醒，仍须对照今天的策略通过 revalidate（src/core/tickets.ts:113、src/core/tickets.ts:257），过不了就维持结束，消息转去评估。在这些时刻之间，授权就是真相。

      同一份文档还拒绝了一个更深层的诱惑：把“人”本身做成领域概念。触发携带其行动者的标识符，来源给出什么就携带什么；允许名单是策略中属于某个来源的那部分，用的正是该来源自己的身份；至于同一个人类在 GitHub 和 Feishu 上各有哪些账号，那只是提示词文本，智能体需要时自己去读——src/policy.ts 在文件头部的注释里就是这么写的。跨来源映射身份，等于另建一套自带同步故障的影子身份系统，却换不来授权没有记录的任何东西。

      7.5 状态属于工单，不属于 Session

      想知道一张工单在干什么，最直接的办法是去问运行它的那个智能体 Session。代码库拒绝了这条路：“Ticket state that follows the DSH Session”（跟随 DSH Session 的工单状态）就列在否决清单上，因为工单可以在结束之后恢复、可以重试、可以在宿主机崩溃后重启，还会随时间先后由好几个派工承载。执行器 Session 只是某一次派工的容器，处在领域之外，只能经由派工触达。于是，工单的阶段由 ticketStage（src/core/stage.ts:9）根据工单自己记录在案的事实算出：已结束（ended）；有一次投递失败了；存在未决的待人工决定（Attention，一个等待人来回答的问题）；有一份 ready（就绪）报告等待评审；受阻（blocked）或失败（failed）的工作在等某个人；排队（queued）；空闲（idle）；工作中（working）。

      其中最微妙的是 waitsForPerson（src/core/model.ts:349）：一张工单，当其最近一次派工报告了 blocked（受阻）或 failed（失败），且此后没有任何人类消息到达，就是在等某个人。这个状态由存储的报告和输入计算而来，从不从报告的文字里推断——否决清单拒绝从自由文本推断 “waiting on a person”（在等某个人）。因为计算只读取持久化的行，重启之后依然成立——docs/003-execution.md 的原话是 “It is worked out from the stored Reports and Inputs, so a restart keeps it”（它由存储的报告和输入算出，所以重启之后依然成立）；而重试——结束停滞的派工、在同一份授权下开启新的一次——靠写入新事实解除这一状态，而不是去探测某个进程。Session 可以撒谎，也可以死掉；工单的状态，是领域记录下来的东西。

      7.6 提示词是带版本的数据

      智能体的指令大多放在 prompts/*.md 里，一行一句地写，好让每次编辑都留下可读的 diff；promptFile（src/app/skill-files.ts:29）在加载时用空格把每一段的各行拼接起来。Prompts（src/app/prompts.ts）把配置存成带编号的 Versions，配置里有关于沟通、范围与交付的团队区块，也支持对内置段落的改写；每次改写都记下所基于文本的哈希，于是升级时能精确报告一个团队的措辞之下到底变了什么。

      这里拒绝的另一条路，是把行为做成设置项，或把行为做成代码。理念把界线划得直截了当（docs/000-philosophy.md）：“Behaviour that a team describes in words is prompt text, not a setting”（团队能用语言描述的行为是提示词，不是设置项）。智能体话多时，解药是更短、更严的措辞——保存一下，下一次请求即生效——而不是一次部署。归因是第二重收益：每个模型请求都把它所属的 Session 绑定到当前的提示词修订版，并持久地记录下来（src/app/sessions.ts:329 的 promptFor，存在 KV.sessions.prompts 之下），于是任何动作都能追溯到产生它的那些文字。tests/model-surface.spec.ts 让这些表面保持诚实：它对照工具 schema 和词汇表检查提示词、工具描述与已投递的消息，让旧术语退役，封禁已知有误导性的措辞，并给每个角色强制执行一份字符预算。提示词文本改变的是告诉智能体什么，从不改变系统允许什么；准入和工具留在代码里。

      7.7 小词汇表，少设置项

      理念中的设计规则读起来像一连串减法：概念要少，业务需求来时，就变成既有概念的一个属性、或提示词里的一段话，而不是一个新实体；设置要少，只要一个取值几乎适合所有团队，默认值就顶掉选项；面板把在等人的事项列在最前面，因为健康的状态不占地方。总览（overview）正是这么做的——处于 person（等人）阶段的工单排在最前，用的正是同一个 ticketStage 计算（src/app/views/overview.ts）。

      代码库还自己看守自己的词汇表。核心为何记录一条决定，Reason 代码取自封闭的 REASONS 清单（src/core/reasons.ts）；一个人或一个智能体会因为什么遭到拒绝，UserError 取自固定的 USER_ERRORS 代码（src/core/errors.ts），管理 API 以状态码作答，面板则用自己的语言给出对应的措辞。docs/001-domain.md 的词汇表由面板自己消费——它的问号按钮打开的就是同一套术语，两种语言并陈，出自 src/client/locales.ts 的 GLOSSARY。一个新概念不可能半生不熟地溜进来：屏幕上的词、记录里的原因、文档里的术语，是同一份清单。

      不过最过硬的纪律，是 docs/001-domain.md 的最后一张表：否决概念表。Principal 或 Membership；Eval 自行调度延迟；等待中的 Eval 状态；每个线程一张活跃工单；跟随 Session 的工单状态；策略变更即取消；给失败 worker 的工具上锁。每一行都是一个差点就放进去的设计，旁边写着拒绝它的理由。大多数架构说得清自己做什么；这一个还说得清自己拒绝成为什么——而一个知道自己在哪儿止步的设计，能把那条线以内的所有东西保持简单。

      第 8 章

      一个请求走遍全系统

      8.1 那张图

      场景是一个小团队的仓库，由 dsh-superagent 看护——这个宿主进程负责把消息变成经过授权的工作。它的 GitHub 来源（Source），也就是替智能体账号观察单个仓库的那个适配器，处于启用状态；团队的策略（Policy），即规定谁可以发起工作的配置，把一位队友列入了允许发起的账号，我们姑且叫她玛拉（Mara）。接受模式（accept mode）是 observe，因此主动型工作只会进入研判（Assessment），绝不会自行启动；当前启用着一条主动规则，但它在这里派不上用场，因为玛拉写下的是一条明确的请求。她提交了 issue #412，标题是“不稳定测试：调度器偶尔丢掉一个任务”，并评论道：“@agent 调度器测试在 CI 上大约每五次运行就会失败一次——请找出竞态并修复它。”

      接下来的一切，是一条由具名模块串成的链。来源把她的评论转写成一条触发（Trigger），即领域对一条传入消息的记录；Engine 是事务性核心，也是触发、线程（Thread）、决定（Decision）、工单和派工（Assignment）唯一的写入方，它让这条触发过准入（Gate）、进评估（Eval），再按主 Session 的路由把它变成一张工单（一个获得授权的工作单元），并附上一份授权（Mandate），记录它凭什么获得授权；随后的工作由一个执行器 Session（worker）完成；智能体说的话，则由 GitHub 渠道（Channel）送回去。本章就沿着这条链，一跳一跳地走。

      8.2 从 GitHub 到一条触发

      GitHub 来源没有 webhook，靠轮询。src/sources/github.ts 里的一个 watch 循环每隔 pollSeconds 运行一次 pollRound（默认 60 秒；若 GitHub 的 x-poll-interval 响应头有要求，则更长）。每一轮按顺序读取：智能体账号的通知；团队开启的各条仓库级信息流；处于开启状态的工单的 pull request 及其 CI；最后是每一条已订阅的线程。一切读取都经过 src/infra/commands.ts 里的 Commands——一个子进程封装，其 api 方法以子进程方式调用部署环境的 gh CLI（gh api repos/<owner>/<name>/...），只允许访问配置的仓库，返回值再过 schema 校验。

      玛拉的提及带来一条通知，于是 pollNotifications 把 issue #412 排上读取。readNotified 取回这个 issue，仅当它是在游标之后、由智能体以外的某个人新开时，才为其正文发出一条触发；随后 intakeComments 读取同一游标之后的会话评论。issue 自身的正文在更早一轮就已到达，既无提及，observeIssues 又关着，于是准入以 no_mention 把它挡下，并记录为一条 ignore（忽略）的决定——这就是为什么请求是那条评论，而不是 issue 本身。

      每条评论都经由 src/sources/github-trigger.ts 里的 commentTrigger 成为一条触发。触发携带一个确定性 id，由评论的 URL、id 和更新时间构造而来；携带行为者（human: true，因为玛拉是人，不是智能体本身）；携带所属线程（github:412，即这条触发归属的那场会话）；携带一条用于回复的渠道（githubChannel）；此外，由于 mentions 在正文里找到了 @agent，还携带 addressed: 'mention'——由来源声明的事实：发送者是对智能体说的。

      去重正是由那些确定性 id 加上游标保证的。readNotified 把该线程的游标推进到 cursorAt(round.started)——src/sources/poll.ts 会把时间戳回拨 5 秒，好让迟到的远端事件重新读到——重读因此无害：src/core/intake.ts 里的 Intake.receive 开一个 Engine 事务，发现触发 id 已存过，回答 duplicate。第一次读取时，触发存了下来，线程 github:412 记录时间和关联（Correlation），扇出（Fan-out）循环没有找到订阅这条线程的工单，因此没有触达任何东西。由于没有任何工单的 worker 裁决这条消息，而它的发送者又对智能体点名，queueForEval 把触发 id 放上线程的待处理队列。来源经 SourceContext.receive（src/sources/host.ts）抵达 Engine，这条通路再经 Passes.receive（src/app/passes.ts），于是存下的触发还会请求立即执行一次 pass。

      8.3 准入与候选

      pass 是 Runtime 的心跳：Passes（src/app/passes.ts）每 2 秒跑一趟，任何命令提出要求时再补一趟，先把到期的 Effects（持久化的副作用队列）踢动，然后调用 Engine.evaluateDue（src/core/engine.ts）。这个方法发现线程 github:412 带着一条待处理触发，且没有正在进行的评估——评估是线程层面的研判，以一条决定收尾——Evals.start（src/core/evals.ts）于是在一个事务里开启评估。

      先是准入。src/policy.ts 里的 settingsPolicy 构建一份全新的无状态策略，其 gate(trigger, thread, tickets) 负责给消息分类：玛拉在允许名单上，这条触发又是指名发给智能体的，于是答案是可准入，强度（strength）记为 strength: 'explicit'（明确），依据记为 via: 'addressed'，指名了那次提及与发送者。倘若她没有提及智能体，就要由准入表和接受模式在推断（inferred）候选与拒绝之间做抉择。评估记录落在线程上（thread.evaluating），带着准入的强度、行为者、依据和策略版本（Policy version）；待处理队列整个倒进这条记录；assessor.request 把它的候选交给 MasterAssessor（src/app/assessment.ts），由后者排入一个 assessment effect。

      这个 effect 的处理器构建候选卡片（src/app/links.ts 里的 candidateCard）——消息按 worker 们将要读到的样子渲染，附上来源链接与所回复内容的预览、线程、批次、相关及被引用的工单、强度与模式——随即以 sessions.prompt(..., 'steer') 把它注入主 Session 的回合，再调用 Engine.candidateDelivered，让评估的截止时间从 Session 实际收到卡片那一刻起算。MasterAssessor.context 经 orchestrator_eval 供给的有界线程窗口与策略版本，是给推断候选用的；一张明确的卡片给出的是路由指令，prompts/dispatch.md 告诉主 Session 具体怎么做。

      主 Session——Runtime 持有的、面向 orchestrator 的常驻 Session——读完卡片，带着一个 accept（接单）条目调用 orchestrator_route：一个标题、一个 worktree_name，外加一段点明改动的回执。src/app/tools/main.ts 里的 route() 把它转成 Engine.decide(triggerId, { kind: 'accept', ... })，每个条目各是一条独立的 Engine 命令。

      8.4 原子化的接单

      Engine.decide 把 Evals.decide 包进同一个仓库事务，accept 意味着的一切都发生在其中。Evals.accept 构建授权——强度 explicit、准入的依据、策略版本、行为者，以及主 Session 写下的范围——从评估 id 确定性地推导出工单 id，并记录这条 accept 决定。随后 Tickets.create（src/core/tickets.ts）写入工单：它的来源触发、取自玛拉评论的渠道、一条状态为 pending 的首个派工（派工是工单 worker 的一次运行），以及在评估各条触发的每条线程上添加的订阅（Subscription）——从此 issue #412 属于这张工单。prepareTicket 钩子让 DshExecutor.prepare（src/executor/dsh.ts）填入执行事实：worktree 名、工作区目录、派工文本。最后，若这次 accept 带着回执，Replies.acknowledgeAccepted（src/core/replies.ts）经 Outbox 把它排进队列，executor.start 则把启动排进队列。决定、工单、授权、派工、订阅、回执收据、启动行：一个事务，一个崩溃域。

      这条回执不会丢失，也不会乱序，因为它先是事实，之后才是消息。Outbox.send（src/app/outbox.ts）在同一个事务里以确定性 id key('ack', trigger.id) 持久化一张收据，并排入一个 reply effect；提交之后 effect 才运行，并按退避一直重试，间隔从 5 秒增长到 5 分钟，直到成功为止。顺序有两重保证：reply 这一类 effect 按队列顺序一次只跑一个；receipts.behind 把同一工单发往同一会话的较晚消息，扣在较早的未完成消息之后。等 sendGithub（src/sources/github-channel.ts）终于发出评论时，它会嵌入一个装有消息 id 的 HTML 标记，并先扫描自己是否已留下标记，因此响应丢失后的重试不会发出任何新东西。玛拉在 #412 上看到一条回复，说明智能体将要做什么。

      8.5 启动与工作

      提交之后，launch effect 运行（src/executor/dsh.ts 里的 launchQueued），先于任何等待中的工作预留一个 WorkerSlots 名额，这样两次启动不可能同时拿走最后一个名额。launch 发现没有工作区目录，于是 prepareDirectory 运行团队配置的 executor.prepare 命令——通常是 git worktree——带上工单的执行变量（DSH_SUPERAGENT_DIR、DSH_SUPERAGENT_NAME、DSH_SUPERAGENT_TICKET，以及 GitHub 账号和仓库），上限 10 分钟；prepare 一旦失败就让工单失败，而不是在一个建了一半的目录上反复重试。

      随后 Sessions.ensure（src/app/sessions.ts）在该目录中创建 worker Session worker-<ticket>，套用 dsh-superagent-worker 预设，为它注入执行器的模型，再以组合好的提示词作装饰——来自 prompts/worker.md 及其各小节的角色说明，外加授权自身的限制，而对一条明确的请求，这些限制不添加任何东西——并注册它的六个工作工具。第一条消息以 id assignment:<ticket>:<assignment> 入队：一张 JSON 卡片，载有工单 id、标题、最多 1,500 字符的派工文本，以及内联呈现的来源触发；Session 一经接下，Engine.assignmentStarted 便把派工标记为运行中。

      技术工作归 worker。它阅读仓库的说明与内置的 GitHub 技能，复现竞态，修改调度器，并且只以智能体账号通过 gh 触达 GitHub，提交时使用该账号及其 DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL。长时间的测试运行难不倒消息循环：预设会在 5 秒后把前台命令转为后台作业，这类工作运行期间工单始终占着自己的 worker 名额，直到 30 分钟的 BACKGROUND_LIMIT_MS；超过之后便杀掉 shell 作业并上报，而 subagent 继续运行。

      8.6 报告、绑定与评审人

      worker 以 orchestrator_report（src/app/tools/executor.ts）收尾，报上状态 ready（就绪）和 pull request 的编号。这个工具读取 PR，然后在同一个事务里完成认领与记录。claimPull（src/sources/github-pull.ts）核对 PR 确由智能体账号开出、其分支路径的最后一段正是工单的短名，然后完成绑定——ctx.tickets.bindThread 带 own: true，在线程 github:413 上添加一条订阅，并添加一条 follows 记录——这样一来，终结这张工单的将是 PR 的生命周期，而不是一份单纯的报告。Engine.report（src/core/assignments.ts）把报告（Report）记在运行中的派工上；由于工单此刻跟随一个开着的 PR，ready 并不终结它，它的阶段（stage）变为 person/review。

      同一个事务还把 reportRelay（src/app/notices.ts）排成一个 relay effect，由它把一条 worker_report 消息注入主 Session；按照 prompts/dispatch.md，主 Session 用带 purpose=result 的 orchestrator_reply 在最初发起请求的那场会话里完成交接，落到 issue #412 上，就是一条链接着 PR 的评论。

      随后，一位评审人要求修改。评审到来——经由通知，或经由订阅线程的轮询，两条路径最后都汇入 intakeComments——成为线程 github:413 上的一条人类触发。这一次，线程有了订阅者：Intake.receive 把这条触发作为一条输入（Input）扇出到工单上；又因为一张活跃工单的 worker 裁决自己线程上的消息（src/core/model.ts 里的 followupOwners），评估不再排队，准入的 follow-up 强度也无从登场。Runtime 的事件钩子向主 Session 转发一条 follow_up 通知——消息在这张工单的 worker 手里，由它裁决——与此同时，delivery effect 预留出专为人类消息保留的那个额外名额，把渲染好的触发注入 worker-<ticket>，并上报 Engine.inputsDelivered；当 worker 的 Session 把这条消息纳入一个步骤，Engine.inputsRead 也会记下这一笔。worker 推送修复并报告 progress，这份进展留在系统内部。PR 上的 CI 结果以同样的方式作为机器触发到达：扇出为工单的输入，准入将这一批归档为 not_human，记成一条 ignore 决定——有记录、有送达，绝不会误当成请求。

      8.7 合并与终结

      一位维护者合并了 PR。下一轮轮询中，pollTicketPulls 重新读取所有开启工单的 PR；observePull 看到 merged，closePull 经由 SourceContext.tickets.threadClosed 报告这个事实。在 Engine 内部，Tickets.threadClosed 把那条 follows 记录标记为关闭，附上合并的结果与时间；followsDone 确认工单对自己开出的线程已全部了结，而它的工作已经完成、承接的事项没有一件悬而未决，于是工单终结——by: 'executor'、outcome: 'merged'，时间就取合并那一刻。它的订阅保留着，因此之后 #412 或 #413 上的一条人类评论，仍能在同一份授权之下把它重新唤醒；它 worker 的后台工作则在终结事务提交之后停止。

      ticket.ended 事件变成发给主 Session 的一条 ticket_ended 通知；pullEndNotices（src/sources/github-pull.ts）本可以向工单持有的每一个聊天渠道各发恰好一条终局通知——在这里它一条也不发，因为唯一的渠道就是 GitHub，而 GitHub 的时间线已经显示了这次合并。留下来的是记录，而记录全都在 Store 里（src/app/store.ts，一个 SQLite 文件）：触发带着它的去向（Disposition）——哪次评估与哪条决定接下了它、它到达过哪些工单；accept 决定带着它的授权；工单带着它的派工、报告、输入和所跟随的线程。本章的每一跳事后都能回读，用的正是各个 Session 读取的同一批资源。

      8.8 这一路证明了什么

      这条轨迹展现出四个性质，每一个都由构造保证，而非由警惕维持。每一跳都幂等：触发 id、评估 id、工单 id 和消息 id 都从各自的输入确定性推导而来（src/core/ids.ts 里的 key），因此重读得到 duplicate，重复的 accept 找到它那张工单，重试的评论认得自己的标记。每个事实只有一个写入方：只有 Engine 写触发、线程、决定、工单和派工；来源拥有自己的游标；Outbox 拥有收据；Effects 拥有自己的队列。工作先存储、后执行：收据、启动、投递和转发都是决定它们的那笔事务里的行，提交之后才派发。而人只出现在领域指定的地方——授权的提及、纠正的评审、完成的合并，以及只可能来自允许发送者的 stop（叫停）。

      一个来自 Feishu 聊天的请求只会在边缘处不同：换一个来源（src/sources/feishu.ts，由实时事件驱动而非轮询），为回复换一条渠道；领域路径原样不变，从触发一路走到已合并的工单。

      第 9 章

      源码阅读指南

      dsh-superagent 有一百多个 TypeScript 源文件、十五个提示词文件和六十个测试文件——规模小到花几个晚上就能整体装进脑子。这个项目写出来就是给人读的：文档带编号，代码分层次，还有两个测试让文档保持诚实。本章是第一遍通读的指南。

      9.1 从哪里开始

      先按顺序读文档。docs/000-philosophy.md 给出了评判每个功能的标准——占用的人工注意力越少越好——docs/001-domain.md 则命名了代码、工具和面板共用的词汇表：来源（Source）、触发（Trigger）、线程（Thread）、评估（Eval）、授权（Mandate）、工单（Ticket）等，每一个都附有它要遵守的规则，还有一张刻意拒绝的概念表。此后每份文档加一层：授权、执行、提示词、面板、部署、架构，以及一份新增来源的实操手册。README 说每份文档只建立在它之前的文档之上；tests/docs.spec.ts 强制编号文档只能链接到更早的文档。

      SETUP.md 是把系统各个活动部件最快过一遍的方式：一份让智能体照着走的脚本，用来与运维者敲定一次部署。它的九个问题一条消息问一个，沿着领域模型的流程走了一遍——触发从哪里来（哪些来源、哪个仓库、智能体以谁的账号行事），谁可以索要工作（允许名单），以及执行器（Executor）拿到一张工单后做什么（检出、提交身份、自动合并）。它把一个运行中的系统必须明确说出的每一项决定都摆了出来，也摆出了在"一个值几乎适合每个团队"之处选定的默认值。

      然后在三个位置打开代码。src/index.ts 有 28 行：apply 读取机器配置，构造 Runtime，然后等待它的 ready promise。src/app/runtime.ts——254 行——是在一个构造函数里装配起来的整个系统：它锁定状态目录，打开 Store（整个系统就这一个 SQLite 数据库），再构建 Setup、Effects、SourceRegistry、Sessions、Settings、DshExecutor、MasterAssessor、Outbox、Engine 和 Passes，每个部件都只接上自己用到的那条窄接口；Executor 和 Assessor 拿到的是 getter，因为它们要回调 Engine。它不含任何领域规则。最后，src/core/engine.ts（270 行）是决策点：一个类、五个内部部件，每条命令都包在一个 repo.atomic 事务里，文件底部按角色划定的 Pick 接口则确切告诉你谁可以调用什么。

      9.2 三条线索

      地图有了轮廓之后，走三条路径；每条路径的尽头，都是一个通读之后应当能回答的问题。

      一次明确的请求，从进入系统到 accept（接单）

      从 src/sources/github.ts——GitHub 来源——开始：它的配置 schema（仓库、智能体用的 gh CLI 包装、四个 observe 开关），决定哪些事件会被监听的 scope 函数，以及对智能体账号通知进行的一轮轮询。然后是 src/sources/github-trigger.ts，负载在这里变成领域对象：每条评论、每个 Issue 正文、每次 CI 状态流转都是一个触发——一个不可变事件——带着确定性的 id、一个行为者、是否出自真人的标记，以及文本点名智能体时的 addressed: 'mention'。

      轮询把触发交给它的 SourceContext，后者经由 Passes（src/app/passes.ts）到达 Engine.receive；Passes 是调度器，另外还每两秒跑一轮 pass。src/core/intake.ts（63 行）把触发只存一次——同一 id 第二次送达会返回 duplicate——记录它的去向（Disposition，即这条触发到了哪里），更新它的各条线程以及线程之间的关联（Correlation），把消息作为上下文扇出（fan-out）给订阅了相关线程的工单，并在它的主线程上把它排入评估，除非某张工单的 worker 已经替它做了决定。src/core/evals.ts 在稍后一轮 pass 里启动评估：它把该线程排队的触发合批，向准入（Gate）询问准入的强度（strength）与依据，并让 MasterAssessor 把一张候选卡引导进主 Session（main Session，也就是编排者自己的 DSH Session）。一次 accept——典型情况是 src/app/tools/main.ts 里的 orchestrator_route 调用 Engine.decide——落在 Evals.accept，它构建授权，写明这次 accept 授予了什么：强度、策略版本（Policy version）、依据、范围，然后调用 Tickets.create。

      这些发生在同一个事务里（src/core/tickets.ts:37）：工单和它的各条渠道（Channel）在此组装，prepareTicket 钩子补上 worktree 名称、目录和派工文案，第一条派工（Assignment）随之创建，工单订阅（Subscription）这些触发所在的线程，确认消息经 Replies 排队，随后请执行器启动。src/app/outbox.ts 在一个事务里记录这条确认消息的回执，并把它的 reply 效应入队；提交之后，效应再通过来源把它发出去。问题是：为什么同一条评论可以到达两次、决定两次，最终却只产出一张工单和一条回复？答案是三层的幂等——进入系统时的触发 id、Evals.decide 里"已接受"的检查、Outbox 回执里确定性的确认 id。

      工作及其报告

      src/app/effects.ts 是持久化的副作用队列：命令在自己的事务内调用 enqueue，提交之后执行才开始；副作用共六种（assessment、launch、delivery、relay、notice、reply），抛出 Later 表示推迟且不计为失败，失败的副作用按退避策略重试。src/executor/dsh.ts 将 launch 和 delivery 效应入队：每张工单一个执行器 Session（worker）和一个目录（Session 名为 worker-<ticketId>），WorkerSlots 给并发封顶，一条 prepare 命令把工作区备好。src/app/sessions.ts 创建并装饰两种角色的 Session——提示词、技能、worker 的受限工具清单、主 Session 的"不等待"护栏——并按请求 id 对每条消息只投递一次，同时记录每个 Session 工作时用的是哪一版提示词。

      事实经 src/core/assignments.ts 流回：assignmentStarted、inputsDelivered、inputsRead、turnEnded，而最重要的是 report，worker 的话语在这里变成领域状态——待人工决定（Attention）问题被提出、保留或清除，被替换的问题若有尚未发出的回复，也一并撤回，一份 blocked 或 failed 的报告（Report）会扣住自动输入（Input），直到一条人类消息到来。src/core/stage.ts 总共 26 行，把这些事实收拢成面板展示的那一行阶段（stage）记录。问题是：当 worker 报告 ready 时，谁来结束工单？答案是——由它跟随的线程来结束，除非它一条线程也不跟随——这是整个系统在"谁拥有一个结果"上最锋利的一个想法。

      一次策略变更，端到端

      第三条线索从 src/app/settings.ts 的 save 开始：一次乐观的修订号检查、校验、出处守卫（只有面板可以更改执行环境），以及前后对照 policyVersion——它是规则、接受模式（accept mode）和各来源相关部分的哈希。版本变化时，保存动作会计算 policyEffects，并在与设置写入共用的同一个事务里调用 Engine.policyChanged。src/policy.ts 里的 policyEffects 遍历打开的工单：匹配过的规则停用或变动；请求者不再获准（通过在旧规则与新名单之下重新校验，把发信人失去授权与模式变更区分开）；或者 auto 模式结束时收回主动接受。Engine.policyChanged（src/core/engine.ts:255）把两半放进同一个事务：Tickets.policyChanged 记录通知，Evals.policyChanged 把进行中的评估以原因 policyChanged 结束为 unavailable，并把这些触发重新排队。通知本身是一条输入：Tickets.policyChanged（src/core/tickets.ts:200）为每张受影响的工单添加一条 policy-changed 输入，投递效应把它交给 worker，由 policyMessage（src/executor/dsh.ts）渲染成话：把按如今写法的规则仍然成立的部分做完，否则报告 dropped。问题是：一次策略（Policy）变更对已经接受的工作做了什么？变更本身不取消任何东西、不撤销任何授权；它只负责记录并投递，只有重新校验能够拦下继续。

      9.3 地图

      目录树映照着分层。src/core 装着领域——没有 I/O，也不引用自身之外的模块——承载最多理解的三个文件是 engine.ts（入口和它的五个部件：Intake、Evals、Tickets、Assignments、Replies）、model.ts（领域类型和 waitsForPerson 这样的共享谓词），以及 tickets.ts——多数规则最终汇聚的那条生命周期。src/app 是宿主一侧的机械；除 runtime.ts 之外，值得读 effects.ts 和 outbox.ts，它们定义状态变化如何变成动作。src/app/tools 把工具参数翻译成 Engine 命令——main.ts 对应主 Session 的十四个工具，executor.ts 对应 worker 的六个。src/app/views 只读不写地推导面板的读模型；overview.ts 和 tickets.ts 展示面板认为值得占用一个人注意力的东西。

      src/sources 里有 SourceKind 协议（kind.ts）、持有各实例并实现 Engine 之 scope 的 SourceRegistry（registry.ts），以及两个实现：GitHub（github.ts 及其相邻文件）和 Feishu。src/executor 放着 DshExecutor（dsh.ts）和 worker 的后台工作辅助（background.ts）。src/infra 是进程一侧：commands.ts 负责 CLI 传输，environment.ts 负责智能体的进程环境，health.ts 负责它申报的健康条目。src/client 是 React 面板，只从宿主一侧导入类型：app.tsx 决定它的形状，api.ts（类型来自 src/app/api.ts）对应每一条路由。prompts/ 存放模型要读的指令（orchestrator.md、worker.md、admission.md），skills/ 存放两个来源技能，tests/ 存放测试套件。docs/007-architecture.md 里的模块表和测试表是完整索引；tests/docs.spec.ts 验证它们列全了每一个模块和每一个测试，因此索引不会腐烂。

      9.4 读者必须知道的约定

      先说命名语法。请求做事的方法用祈使动词，而且可能遭到拒绝（stopTicket、bindThread）；记录适配器做过什么的方法用过去式，而且不会遭拒（assignmentStarted、threadClosed）；查询用名词（candidate）。过去式的名字意味着没有拒绝路径可读——这是 docs/007 的"请求与事实"规则。

      拒绝与解释皆有枚举。人或智能体能够引发的拒绝是一个 UserError，代码固定取自 src/core/errors.ts 里的 USER_ERRORS，每一条都标着 missing 或 refused，对 API（404 或 400）和面板使用完全相同的措辞。每个决定（Decision）都自我解释：它的 reason 是一列来自 src/core/reasons.ts 的 Reason { code, values, triggerId }，各道准入和各来源的 scope 提供自己的代码（not_a_member），said 携带某人或某个 assessor 写下的话——因此系统里没有一条记录是无声的。辅助状态有自己的地图：src/kv.ts 把每条键值记录的键、类型和属主恰好各写一次。

      有两个测试是带强制力的文档。tests/class-docs.spec.ts 在 src 中任何一个类缺少紧贴其前的 JSDoc 块时失败；tests/model-surface.spec.ts 把模型读到的一切——工具、提示词、技能、投递下去的输入——对照工具 schema、词汇表和每个角色的篇幅预算逐一检查。最后，prompts/*.md 一行一句地写，由 promptFile（src/app/skill-files.ts:29）拼接成段落，因此修改的 diff 逐句对齐。

      9.5 测试即第二份文档

      测试套件把行为编码在三个逐渐展宽的环里。tests/core-engine.spec.ts 在 MemoryRepositories（src/core/memory.ts）上运行 Engine，配上假的 Assessor、Executor 和 Outbox 端口；它的 describe 块以领域规则命名——intake、订阅扇出、follow-up 归属、被中断的派工、暂停——于是这个文件兼任一份不变量目录。tests/runtime.spec.ts 在 tests/fixtures/host.ts 模拟出的 DSH 宿主上运行整个应用：一个带真实收件箱机制的假 session 控制器（steered 消息与 queued 消息之别、认领步骤、取消）、假的 CLI、一个作业登记表和一个子智能体运行时。面板测试把每个页面对着 tests/fixtures/panel-server.ts 渲染，那是一个覆盖全部管理路由、会记下误用的类型化假件。pnpm check 运行类型检查、测试和构建（package.json）。

      接下来值得读的是三份 spec。tests/policy.spec.ts 端到端覆盖准入——来源 scope、准入、准入表、授权重校验、策略效应——是理解"谁可以开始一项工作"最快的路径。tests/followups.spec.ts 展示完全绕开评估的那条路：一个人在已订阅线程上的 follow-up 直接到达 worker，而主 Session 只是收到告知。tests/runtime-concurrency.spec.ts 考验重叠——一轮 pass 进行时触发到达、投递与启动期间工单变化——单写者设计要么在这些地方站住，要么露出接缝。

      第 10 章

      结语与观察

      README 称 dsh-superagent 为研究原型，"并非 DeepSeek 的官方产品"，它是为公开发表而改编的，不是从生产环境里原样搬出来的。文档对"系统不决定什么"写得异常具体。有意思的收尾问题是：这些缺口里，哪些只是原型阶段的偶然，哪些是承重的留白——在后一种地方，设计者选择了记录，而不是决定。

      刻意留白之处

      最具体的缺口是数据保留。docs/007-architecture.md 的 Persistence 一节说得直白：目前没有任何东西删除旧记录。触发（Trigger）、它们的去向（Disposition）和决定（Decision）永远累积；已结束的工单（Ticket）和它们的线程（Thread）、Outbox 的回执（每条出站消息一条）同样如此；键值区里，保存过的每一份设置修订、每一版提示词、每个 Session 工作时所依据的提示词修订，以及各来源按线程记的簿记，同样无一例外。这句话与其说是待办事项，不如说是设计立场：审计轨迹是系统对"自己为何如此行事"的记忆，修剪它是一个策略问题——谁可以遗忘、何时可以遗忘——而不是一件工程杂务。把原型跑上一年的团队，等于背着自己收到过的每一条消息。

      信任问题更尖锐。一条触发的行为者与线程成员关系来自来源（Source）本身；它的正文与引用文字则出自发消息的人之手。原型记录了每一份授权（Mandate）的依据——谁发的、经过准入（Gate）的哪一格、依据哪个策略版本（Policy version）——但它还没有在"当作证据对待的字段"与"当作主张对待的字段"之间画出那条线。在那条线画出来之前，一段有说服力的消息正文可以声称任何事情，而为它开启的工作背书的，只剩准入对发信人的裁决。部署隔离是同一问题的近亲：智能体运行在自己的 DeepSeek Harness profile 上，悬而未决的是如何把它脚下的安装钉牢，好让机器上别处升级 DeepSeek Harness 时不至于弄坏这个智能体。而且系统在设计上就是单仓库：一个 github.com 仓库、没有 GitHub Enterprise Server、一个智能体账号——跨仓库不是它提供的机制，只能算第二次部署。

      可迁移的东西

      可迁移的想法都是结构性的，没有一条依赖 DeepSeek Harness，也不依赖编码工作。第一条是命令/效应分离：命令在一个事务里改变状态并把副作用入队，适配器在提交之后才执行它们（src/app/effects.ts）。在"决定"与"执行"之间崩溃变得不可能，重试成为队列的性质，而不再是每个调用方各自操心的事。第二条是每类状态单一写者：每一种记录都有唯一一个允许写它的类，其余角色只能读或请求。这条规则付出少量间接性，换来的是只读一个文件就能推断任何一条记录的能力。

      第三条是把授权当作已记录、可重校验的数据。一份授权不是会话里的一个标志位，也不是请求时的一次策略查询；它是一条存档的记录——授予了什么、给谁、依据哪个策略版本、凭什么依据——系统任何时候想知道这份授予是否仍然成立，都可以拿它对照现行策略（Policy）重新校验。第四条是把注意力当作预算：docs/000-philosophy.md 用耗费的注意力评判每一条消息、每一个设置、每一个面板元素和文档的每一段，并删掉收不回成本的东西。把这条标准毫不留情地用到底，正是系统产出如此之少的原因。第五条是一个由拒绝概念清单守卫的小词汇表——docs/001-domain.md 里十二条，每一条都是一个有名有姓的诱惑，并附拒绝的理由——领域模型于是要么靠论证生长，要么根本不生长。第六条是把提示词当作带版本的数据：配置是编号的快照，每个 Session 绑定在自己工作时所依据的修订上，worker 只能读自己用过的版本，这让每一次模型请求都能追溯到产生它的那份确切指令。

      作为成品的哲学

      把代码剥掉，留存下来的成品是一组拒绝。智能体只在一个人必须行动或用得上结果时才开口；通知注入时不吵醒主 Session（main Session），worker 手里除了一个结构化的待人工决定（Attention）问题之外，没有任何向人发问或向人呈报的工具。它只在名单上的人开口、或成文规则允许时行动，记录下是什么授权了这项工作，并让那份记录接受重新校验，而不是相信自己的过去。它拒绝生长：新概念靠指名拒绝一个个诱惑而到来，不是靠功能层层堆积。每一次拒绝都在能力上付出一些代价，合在一起则买来可预测性——团队能预测智能体永远不会做什么，而这是容忍它做什么的前提。这就是值得带进任何自主系统的保守内核：自主性之所以能在团队中存活，只因看住它足够便宜；它保持便宜，只因系统把人的注意力当作唯一印不出来的预算。
