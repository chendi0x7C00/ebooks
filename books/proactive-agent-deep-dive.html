ProactiveAgent 深读：把 LLM Agent 从「等你开口」推到「看见就帮忙」

核心主张：多数 Agent 仍是 reactive（等显式指令再动）；真正有用的个人助手需要 proactive——根据环境事件与用户活动自行推断任务，并在恰当时机提出协助。本文用数据驱动管线造出 ProactiveBench（训练 6,790 / 测试 233 条事件），再训一个对齐人类接受判断的 reward model 当裁判，最后用该数据微调开源模型，把主动协助的 F1 推到 66.47%（Qwen2-7B-Proactive），超过当时对比的闭源与开源基线。

01 · Problem

问题定义：指令缺口 vs 环境可观测性

Reactive agent 在收到用户指令前保持休眠；用户必须先想清楚「帮我约 John」、再打字。Proactive agent 的前提不同：环境里已经有信号（John 的邮件约 10 月 9 日 15:00 Starbucks），agent 应主动问「要不要帮你加进日历？」——用户只需确认或拒绝。

Reactive

  • 输入 = 显式用户查询
  • 无查询 → 无服务
  • 用户承担「发现需求 + 表述需求」全部认知成本

Proactive（本文）

  • 输入 = 环境事件 + 用户活动 + 环境状态
  • 可预测「任务」或「保持沉默」
  • 目标：最大化用户对提议的接受率，而不是最大化提议次数

与「对话里更主动」的区别：相关工作里也有叫 Proactive Agent 的对话系统，多半是把回复写得更有帮助；本文焦点是 在用户尚未提问时，从活动流里发起任务。仍要求先给一句 query 再澄清歧义的系统，不在本文定义内。

02 · Formalization

任务形式化：每个符号第一次出现都有白话含义

时刻 t，agent 看到三类输入，输出一次预测：

Pt = fθ(Et, At, St)

符号含义例子
Et环境事件（environmental events）收到新邮件、应用关闭、网页加载完成
At用户活动（activities）键盘鼠标、与 agent 的对话
St环境状态（state）文件系统、已打开网页内容
fθ参数为 θ 的 proactive agent被微调后的 LLM
Pt该时刻的预测具体任务文本，或空集 ∅（保持沉默）

用户（或模拟用户）给出二元反馈 Rt = g(Pt, At, St)：接受 = 1，拒绝 = 0。为了把「预测为空」和「预测有任务」放进同一套对错，再引入辅助变量：

  • Nt = 1：用户此刻其实需要协助；Nt = 0：不需要。
  • Rt = 1 当且仅当：(Pt ≠ ∅ 且用户接受该任务) 或 (Pt = ∅ 且 Nt = 0)。
  • 优化目标：maxθ E[Rt]——期望接受率，不是期望提议数。
▶ 跑一遍 · 四种对错（后面实验会反复用到）
  1. Correct-Detection (CD)：Nt=1 且 Pt≠∅ 且用户接受 → 做对了「该出手时出手」。
  2. Non-Response (NR)：Nt=0 且 Pt=∅ → 做对了「该闭嘴时闭嘴」。
  3. Missed-Needed (MN)：Nt=1 且 Pt=∅ → 漏帮。
  4. False-Detection (FD)：Nt=0 且 Pt≠∅ → 瞎帮（误报）。

论文 §3.1 与 §4.1；reward model 评估时报告这四类与人类的 agreement。

03 · Architecture

三件套：Environment Gym · Proactive Agent · User Agent

整套方法是数据驱动的：先造「像真的」事件流，再让 agent 预测，再由（人工标注训出的）user 判断器决定接受与否；接受则在 gym 里把任务执行成新事件，形成闭环。

重绘自论文 Figure 2 / Figure 3 的信息结构：数据面（事件）橙色实线，控制 / 判断青色虚线。

Environment Gym

先用基于 ActivityWatch 的监控软件采真实人机交互（键盘鼠标、网页、开发工具），合并成语义片段并翻成自然语言。再以种子任务为起点生成场景（角色、实体、示例事件），事件生成时随机采样示例事件约束粒度；每出一个新事件就更新实体状态与模拟时钟。

Proactive Agent

收到 Et 后更新 memory，结合历史与用户画像提出草稿任务；可经用户反馈 refine。若判定无需任务则沉默。任务被接受后，用场景里生成的工具在 gym 多轮交互执行，直到完成或被打断。

User Agent

生成用户活动，并对预测做接受 / 拒绝。真实标注：9 个模型为每条事件生成多样预测，选 5 个彼此余弦距离最小的候选；三位标注者投票（accept / reject / reject all）。「reject all」对应 Nt=0。最终 1,760 条带标签条目用于训 reward model。

05 · Four quadrants

接受四象限：基线模型最容易翻车的地方

现有模型在 Correct-Detection 上往往不错，但在 False-Detection（不该帮却帮）上惨淡——它们倾向于「有事没事都提一嘴」，哪怕事件毫无实质操作（例如在软件间空切换）。Reward model 的价值正是把「人类会不会接受」学成可复用的裁判。

GPT-4o3.33%100%100%0%—

Ours (RM)80%86.67%100%100%91.80%

摘自论文 Table 2 思路：自家 reward model 在 False-Detection 上与人类 100% 一致，才适合当 ProactiveBench 的自动裁判。人类标注者在 RM 测试集上 agreement 约 91.67%。

06 · Design decisions

关键设计决策

D1用合成闭环造数据，而不是只靠真实日志微调

拒绝

仅用采到的真实轨迹直接监督——规模小、难覆盖「接受后执行」的后续事件。

选择

Gym + Agent + User 迭代：接受则执行并产新事件，拒绝则 gym 自行续写，滚出 6,790 条训练事件。

代价

依赖 GPT-4o 造场景 / 活动，合成分布可能漂移；测试集坚持用 233 条真实事件压住这一点。

启示

主动行为的监督信号稀缺时，先投资「可交互的沙箱 + 可对齐的裁判」。

D2把「沉默」和「提议」统一进 R_t

拒绝

只评估「提了什么任务好不好」——漏掉「不该提却提了」与「该提却沉默」。

选择

引入 N_t，让空预测在「用户不需要时」也算正确；最大化 E[R_t]。

代价

必须额外标注 / 推断「此刻是否需要协助」，标注协议更复杂（含 reject all）。

启示

主动系统的主指标应是接受率，不是召回「能提出多少建议」。

D3单独训 reward model 当自动用户

拒绝

每次评测都找真人点接受，或直接用 GPT-4o 当裁判（Table 2 显示 FD agreement 可为 0%）。

选择

1,760 条三人投票数据微调 LLaMA-3.1-8B 作 RM；F1 对齐人类 91.80%。

代价

RM 仍是模型，会继承标注偏差；后续 Agent 指标都挂在 RM 上。

启示

主观 UX 指标要规模化，先把「人类会不会点接受」产品化成可版本管理的裁判。

D4测试集锁真实世界事件

拒绝

训练和测试都用合成事件——容易自我吻合。

选择

12 场景共 233 条真实采集事件作测试；训练可用合成放大。

代价

真实测试集小，场景覆盖仍窄（作者 Limitations 原话）。

启示

合成负责量，真实负责判据——和许多仿真-to-real 工作同一条缝。

D5允许多候选（pred@3）减轻「猜错一次就挂」

拒绝

永远只吐一个任务——认知负担低，但容错差。

选择

最多 3 个候选；RM 逐个检查，任一接受即算接受。GPT-4o 的 FD 从 51.85% 降到 36.44%。

代价

用户面前选项变多；若模型只会提「含糊建议」，多候选也救不了（文中 LLaMA 案例）。

启示

产品上可「静默生成多候选 → 只展示 RM / 策略筛过的一条」。

D6用 RM 反馈再改写预测

拒绝

一次生成定终身。

选择

§4.3 探究把 RM 反馈喂回模型迭代修改；配合 pred@3 进一步抬指标。

代价

推理成本上升；线上延迟与「打扰感」要重新权衡。

启示

裁判不只用于离线打分，也可作推理时的 critic——但要预算化。

07 · Experiments

实验：微调确实抬 F1，但「爱帮忙」病还在

Agent 子集：Coding / Writing / Daily Life 共 6,790 训 / 233 测。微调 LLaMA-3.1-8B-Instruct 与 Qwen2-7B-Instruct（batch 32，lr 1e-5，3 epoch，8×A100 ≈ 2h）。评测 temperature=0，用同一 prompt，由 reward model 自动打 Rt。

▶ 跑一遍 · 读 Table 3 时别被高 Recall 骗到
  1. GPT-4o-mini Recall = 100%，但 Precision 只有 35.28%，False-Alarm 64.73%——几乎逢事件就提议。
  2. 优化目标是 E[Rt]：乱提议会把「Nt=0 却 Pt≠∅」打成错误，拉低 Precision / F1。
  3. 微调的主要收益：Precision 上移、False-Alarm 下降，F1 越过 GPT-4o；不是把 Recall 从低拉高（基线 Recall 已经很高）。
  4. 产品含义：上线 proactive 功能时，监控 False-Alarm 与用户「忽略 / 关掉建议」率，比监控「建议条数」更重要。

08 · Critique

批判性阅读：贡献、裂缝、可偷走的东西

站得住的贡献

  • 问题切得干净：把 proactive 定义成「无 query 的任务发起 + 可沉默」，并用 Nt/Rt 写成可优化目标。
  • 评测闭环可复现：真实测试集 + 对齐人类的 RM，避免每次实验请人点按钮。
  • 数据配方可迁移：Gym（事件+状态）· Agent（预测+执行）· User（活动+判断）对其他「主动 UX」问题仍适用。

作者自陈的限制（应原样听见）

  • 环境覆盖窄：Coding / Writing / Daily Life 只是起点，泛化未证明。
  • False-Alarm 仍高：即便微调后仍约 50%，会消耗信任。
  • 主动性应可调节：不同上下文需要不同「吵闹程度」，本文未深入做动态策略。
  • 隐私与伦理：预测依赖环境观测（键鼠、页面、邮件等），部署前必须有透明与最小化采集。

读者额外该盯的裂缝

  • 裁判自举：Agent 指标几乎都经 RM；RM 与 Agent 同族数据文化，可能共同偏好某种「可接受的帮忙话术」。
  • 合成训练 / 真实测试缩小了乐观偏差，但 233 条测试对「场景×失败模式」网格仍然稀疏。
  • 与操作系统级助手的工程距离：论文假设事件已被文本化；真实系统还要过采样、脱敏、权限、防提示注入（作者对事件扫描有意识，产品上要升格成威胁模型）。
可直接偷走的工程清单：① 日志里同时记「提议 / 沉默」与用户接受；② 离线训一个接受率裁判再驱动迭代；③ 上线默认偏保守（宁 MN 勿 FD），再按场景放开；④ 多候选只在模型侧生成，UI 仍尽量一条。

真机 Demo：四个 bucket 如何变成一次提议

反馈语义写进产品：点 toast 本体 / 确认 = Accept（agent 继续相关动作）；点关闭 = Reject（下轮换一种提议）；完全不理 = Ignore（视为忙碌，后续减少提议）。这比论文公式里的二元 Rt 多了一档「忽略」，是仓库对真实打扰成本的补丁。

造数与评测脚本怎么串

  1. 场景：dataset/build_scenes.py --seedfile dataset/seedtask.yaml → 场景 YAML。
  2. Gym 滚事件：python -m gym.main <scene.yaml> events.jsonl（读根目录 private.toml 里的 completions 模型）。
  3. Agent 训练集：dataset/build_agent_trainset.py（README 要求先配好 GYM）。
  4. 人工对齐：把测试轨迹放进 dataset/annotation/data，跑 Gradio；可「Reject all」。再 convert_annotations.py → build_reward_trainset.py（LLaMA-Factory 格式）。
  5. 打榜：eval/script.py 产 traces → 改 RM 地址后 sh eval/judge_result.sh → sh calculate.sh。
