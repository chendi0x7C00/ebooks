Before you start

LLVM is a set of tools and libraries for building compilers. A language team can describe a program in LLVM’s instruction language, then reuse an optimizer and code generators for several machines. The first half of this book lets you inspect that process. The second takes you inside an AI compiler, where some of the biggest decisions happen before LLVM sees a single instruction.

Our test case has a reading of 4, a gain of 2, and a bias of 1. You only need to be comfortable reading a function, a pointer, and a loop. The examples introduce assembly and GPU programming as we need them.

To run the examples, save the named files in a working directory. We checked the CPU examples in November 2026 with matching Clang and LLVM 23.1.6 tools on arm64 macOS. Chapter 7 also uses mlir-opt and mlir-translate. Generated names and instructions can vary by version and target. The GPU chapters use published traces that you can read on any machine. The optional timing exercise calls for an NVIDIA GPU.

Part I

How LLVM turns a function into machine code

Chapter 1

Where did my function go?

A sensor sends the number 4. Your application doubles it, adds 1, and reports 9. Put the calculation in one C file and its caller in another. Can Clang compile the caller before it has even seen the calculation?

Save the calculation in scale.c.

Save the caller in caller.c.

The first line in the caller gives the compiler a name, the types of the arguments, and a result type. In a larger project you'd put that declaration in a header shared by both files. Here you can see everything the caller knows on one line. It can supply the three numbers, receive an unsigned integer, and compare it with 9. In a shell, a program that exits with status zero conventionally signals success. That gives us a way to test the whole trip.

Three places to stop

Run these commands in the directory containing the two files. Each one asks Clang to stop at a different point.

Each command starts from the source. The first writes LLVM's intermediate representation (IR), a small instruction language that the compiler can analyze and change. The second writes assembly, a textual way of spelling instructions for the selected machine. The third writes an object file, which packages the machine-code bytes with information other tools need to use them. You can build an executable without ever writing the two text files. Asking the compiler to stop at these points gives you a window into work it normally carries out in memory. [1]

What does the frontend actually contribute? Look at the expression as a small tree. Its top node is addition. The right child is the bias. The left child is a multiplication whose two children are the reading and the gain. That's the consequence of the precedence rules of C. A frontend parses the characters into that structure, resolves the three names to parameters, checks their types, and works out which arithmetic the language requires. Try clang -Xclang -ast-dump -fsyntax-only scale.c and look near the end for the two BinaryOperator entries. AST stands for abstract syntax tree. Parentheses, line breaks and spacing have done their job once the structure is clear. [2]

Open scale.ll and find the line starting with define. Below it, the arithmetic looks like this, with temporary values renamed so you can follow them.

Read the first instruction as “multiply these two 32-bit integer values and call the result scaled.” The second instruction uses that result. The last one gives the value back to the caller. On the machines used here C's unsigned is 32 bits, which accounts for i32. Unsigned arithmetic wraps around at the end of its range. For example, adding one to 4,294,967,295 in this function gives zero. LLVM's plain integer multiply and add produce the low 32 bits of their mathematical answers. That rule preserves what the source expression means even when the numbers get large. Other C types and other operations can bring different rules into play. [3]

An optimizer can find both inputs to the addition by following names. It can see how many bits the addition produces. It can work on the operation without knowing C's rules for parsing * or whether the author used a temporary variable. The backend then figures out how a particular processor can produce the specified value. It can even implement the multiply and the add with a single machine instruction on a target that offers one. Chapter 5 will open both assembly listings.

The caller leaves a name behind

Compile the caller separately and inspect both object files.

On our Mac, among the entries in the first listing were T _main and U _scale_then_bias. The second listing contained T _scale_then_bias. Some platforms spell these names without the leading underscore. The letter T identifies a symbol defined in the object's code section. The letter U identifies an undefined symbol, a name whose definition this object expects to find elsewhere. A symbol gives a tool a name by which to refer to a function or another program entity. [4]

This answers the opening question. The compiler could generate caller.o using the declaration and the target's rules for passing arguments. It left a reference for the linker to resolve. An object can also contain relocations, records telling the linker which encoded references need adjustment when it learns their destinations. The linker brings the objects together, resolves the call using the definition in scale.o, and produces the executable. Exact addresses and any extra indirection depend on the target and link options. [5]

The zero printed by the shell means the caller received 9. As a small experiment, predict which command would first fail if you misspelled the function name in both appearances in caller.c but left scale.c alone. The caller's source is internally consistent. Its object asks for the misspelled symbol. The failure arrives when the linker tries to find that definition. You can now use the phase of a build failure as evidence about what the tools already know.

This division of work is what people mean in practice when they say Clang “uses LLVM.” Clang belongs to the LLVM project. Its frontend understands C, and its driver coordinates the build. The LLVM optimization and code generation libraries operate on the intermediate program. Other languages can reach those libraries by building their own frontends. The original designers wanted useful facts to survive as far as linking. LLVM's name comes from the project's early name, Low Level Virtual Machine. Today its tools also build ordinary native executables, like the one you just ran. A compiler can keep IR in memory or store it in a compact form called bitcode. The readable text in our file is another form of that same program. Whichever form it takes, the optimizer can still see that the multiplication feeds the addition. Add an if and the next fact gets more interesting. Which value supplies the return? [6]

Chapter 2

Which value reaches this line?

A newer sensor still uses a gain of 2, but the application has a switch that enables the bias. Start with a reading of 4 and a bias of 1. Stand at the return statement below. If the switch is off, where did the value you are about to return come from? If it is on, which line supplied that value? Save this version as branch.c.

With the switch off, the multiplication produces 8 and the program jumps straight to the return. With it on, the multiplication again produces 8, the addition produces 9, and that is the value returned. The C code gives both answers the same name, y. To optimize the return, we'd like to inspect the computation that produced its input. We now have two candidates.

Draw the paths

Cut the function into pieces at the places where execution can change direction. In the first piece we multiply, then choose a path. The second piece, reached only when the switch is on, adds the bias. The final piece returns the result.

Each piece is a basic block, a sequence of instructions with a single entry and a final instruction that determines where execution goes next. An arrow connects the instruction ending one block to the block that runs after it. The connected picture is a control-flow graph. We often use these graphs just to answer a question about the program, such as whether the add can ever run before the multiply. Here every path to the addition goes through the multiplication. Every path to the return goes through the multiplication as well, but only one goes through the addition. [1]

An ordinary memory location already lets a computer implement this diagram. Reserve space for y. Store the product there. On the “on” path, read that location, add the bias and store the new value back. At the join, read the location and return what you find. Run the following command to see a version of this approach. The flags choose named values and allow us to run our own optimization on the result.

Find %y = alloca i32. The instruction reserves storage for a 32-bit integer in the current function invocation. The value named %y is the address of that storage. A store changes its contents and a load retrieves them. There is a difference between giving an address a name and giving the number at that address a name. You can see it in store i32 %mul, ptr %y. The number being written is %mul. The destination is %y. In this early form of the program even the incoming arguments may take a trip through storage. Nothing in the C function gives another function access to the address of y.

Replace the local storage with names

Ask LLVM to run a single transformation.

opt is LLVM's command-line tool for applying transformations and running analyses on IR. Here mem2reg looks for eligible local storage whose reads and writes it can account for. If it sees an ordinary local used just in this way, it can express the same calculation using named values. -verify-each asks LLVM to check its structural rules after each transformation. Clang typically emits a marker discouraging optimization at -O0. The extra Clang flag above suppresses that marker so we can watch one transformation at a time. [2] [3]

Here is the shape of branch-ssa.ll with attributes omitted. For readability, this excerpt branches directly on the boolean argument. Our emitted file also converted the boolean to a byte and compared the byte with zero. Both spellings make the same choice.

br means branch. The conditional form reads a one-bit value, i1, and names two destinations, true first. The other br has only one destination. Follow the arrows once more. If execution arrives at if.end straight from entry, the second pair on the phi line supplies %mul, which is 8. Arriving from if.then selects the first pair, %add, which is 9. Each pair in brackets names a value and the block on the incoming path. A phi describes that choice at a join. On the off path the add never runs. [4]

Why invent an instruction just for a join? Try replacing ret i32 %y.0 with ret i32 %add. A reader following the off path has a perfectly reasonable question for the compiler. Where was %add defined on this trip? It wasn't. Using %mul instead would give a defined value on both paths, but the on path would return 8. The phi makes it possible to represent the original program accurately while giving every result name one definition in the program text. This property is called static single assignment, abbreviated SSA.

Why static? Put a multiplication inside a loop and it can execute a thousand times, producing a different answer each time. The instruction still appears once in the program text and still defines one name. An optimizer can start at a use of that name and immediately find the instruction that defines it. At a join, it finds a phi and inspects the possible incoming values. Memory can still change freely when a program calls for it. In chapter 4, a single write will change an answer from 7 to 9.

Take the two paths yourself

Save this driver as branch-check.c. It exercises both incoming edges and a third case in which they happen to deliver the same numerical answer.

We got zero. In the third call, which pair did the phi select? The switch was on, so it took %add from if.then. The bias was zero, so the answer happened to equal the product. Knowing the path tells you which definition ran even when a numerical answer alone cannot distinguish the possibilities.

There's an opportunity hiding in that last call. You and I can see that adding zero leaves every possible product alone. The separate function maybe_bias, considered by itself, must accept all the biases its caller might supply. How could the compiler use a fact known at one call site to simplify the instructions inside a different function?

Chapter 3

Why did a function call disappear?

A customer wants raw readings, so the application calls scale_then_bias(x, 1u, 0u). Open the optimized program in a debugger. Is there still a call to step into?

For this experiment give the compiler the helper and a wrapper in one source file. Save the following as mode.c. Here static gives the helper a name local to this translation unit, roughly the source file after its headers have been included. LLVM can see which implementation the wrapper calls.

In the first listing, find the definition of @unchanged. It includes a call with integer arguments 1 and 0, followed by a return of what the call produced. In the second listing, the wrapper contained just one instruction.

The optimized wrapper has no call to step into. The wrapper supplies its incoming value as its answer. Try x = 4, then the largest 32-bit unsigned value. In both cases multiplying by one leaves all the bits alone, and adding zero does the same. It works for every unsigned input. The calculation also has no side effects to preserve. If the helper incremented a visible counter on every call, returning the argument would account for only part of its job.

Put the caller's facts next to the arithmetic

One way to derive the result is to substitute the helper's body at its call site. Compiler writers call this inlining. On paper, where the expressions are all side-effect-free, we can do it in three lines.

Look at the information each piece of source held before substitution. Inside the helper the multiply had two unknown inputs. Removing it would have made a caller with gain 2 return the wrong reading. Inside the wrapper you could see the constant 1, but the call instruction had no multiplication to simplify. Inlining put those facts together. Saving the cost of placing the call is the smaller benefit here. It gave the compiler enough information to remove every arithmetic instruction in the wrapper.

That also explains our change to the file layout from chapter 1. A normal compilation of caller.c in isolation sees the declaration. There is no implementation for it to open and inspect. A native linker later resolves the name. To simplify the arithmetic, an optimizer also needs the function body. Link-time optimization, or LTO, changes what the toolchain keeps until the link. For example, ThinLTO can use summaries of separately compiled modules to decide which function bodies to import for optimization. You can now see why someone would want to carry program information further into a build. [1]

Run a single pass

LLVM organizes much of this work into passes. An analysis answers a question about a program, such as which blocks can lead to a given block. A transformation changes the program, possibly using facts obtained from an analysis. A pass manager runs work in a chosen order. The name -O1 requests an optimization level. Comparing two files produced at different levels reveals the outcome of many decisions together. It takes a smaller experiment to say which transformation was capable of producing a particular change. [2]

Here is such an experiment. Save this complete, hand-written IR as inline.ll. The internal keyword makes the helper private to the module. The alwaysinline attribute asks for inlining at eligible calls, letting us control that decision for this small case.

The commands start from the same input. The first asks for instcombine, a pass that knows many ways to simplify combinations of instructions. Inspect combined.ll. The multiply and add survived inside @calibration, and the call survived inside @unchanged. The pass had no local expression x * 1 + 0 to work with. The second command selected the inliner for marked functions. In inlined.ll on LLVM 23.1.6, the wrapper already returned %x. The inlining machinery could simplify these trivial operations as it copied the body. The extra line in our diagram explains the arithmetic. In this run LLVM simplified it before the inliner finished. [3]

An optimizer faces a practical constraint you may recognize from an application cache. Building a map of who calls whom costs time, so you want to share it. After the inliner deletes a call, a map saying “unchanged calls calibration” is stale. Each transformation tells the pass manager which kinds of analysis results remain valid. A later consumer can reuse a valid result or arrange to compute a fresh one. The unit of work matters, too. A local arithmetic rewrite usually needs to inspect far less of the program than an inlining decision across multiple functions. [4]

Would it help to inline everything? Consider a helper with a few hundred instructions and fifty callers, each using a gain read from a device. Copying the helper could increase the amount of machine code those callers need while exposing very few constants. Extra instructions occupy space and compete for the processor's instruction cache. This is a decision about whether a legal transformation is likely to pay. You can prefer the convenience of a small helper in your source and let an optimizing build make that choice at individual call sites.

Change one fact

Append a second wrapper to mode.c and rerun the command for mode-O1.ll. Before you inspect the file, cross out everything you can justify on paper.

Our IR for from_setting contained a multiply followed by a return. The add disappeared for the same reason as before. Removing the multiplication would require a further fact about gain. Pick the input x = 4, gain = 2 and you can exhibit the precise failure of a proposed return x. That habit of looking for the input that distinguishes two programs will serve you well when memory enters the picture. A write through one pointer can change the result of a read through an entirely different name.

Chapter 4

Why did the compiler keep that load?

Read the following function as if you were reviewing a colleague's change. They propose replacing return *p; with return 7;. The first line of the function writes 7, and no later line contains the expression *p =. Before you look at the compiler output, find a call that would make the replacement wrong.

Try drawing the two addresses. The cell labels identify objects in the caller. Their old contents don't matter.

Two expressions that can refer to the same storage are said to alias. A name in SSA gives the optimizer a reliable handle on a value. Here each pointer value can be perfectly stable throughout the function. The complication is that each one describes where to look, and a write can change what the next read will find there. SSA names alone say nothing about whether those two locations coincide. [1]

A promise about two pointers

Save observe above in alias.c and append a second version.

Both pointers write to memory. For this function, C's restrict qualifiers tell the compiler that these two writes touch separate objects. A call with &a, &b fulfills the promise. A call with &a, &a violates it. In full generality the C rules concern how a modified object is accessed during an execution of the block. For a function walking slices of an array, the relevant question would be which elements those accesses actually touch. [2]

Look at the end of observe. In our listing its last two instructions loaded the value at %p and returned it. The ret in separate returned the constant i32 7. Both stores were still present. A caller is entitled to inspect the objects after the function returns. Only the final read became unnecessary. Clang carried the access promise across the frontend boundary in the form of a noalias attribute on each pointer parameter. The same LLVM optimizer that handles other languages can use that information. [3]

Here's a driver you can save as alias-check.c. Each return code identifies the call whose result would have surprised us.

Our driver returned zero. For the two arrangements of ordinary aligned integers in our drawing, there is another way to return the right answer without a final load. Test whether the two pointers are equal and select 9 or 7 accordingly, with both stores still performed. The original function's result is required by C. Keeping a load was the implementation chosen by this compiler. This distinction is helpful when you start asking why LLVM “couldn’t” optimize something. Sometimes a particular substitution, such as returning 7 unconditionally, is provably wrong. Sometimes another correct sequence exists and the compiler prefers the one you saw.

When two slices of an array overlap

A device now delivers readings in batches. You want to apply our calibration to every element. Save this function as calibrate-array.c.

If out and in are separate arrays, we could read four readings at once, multiply all four by the gain, add the bias to all four, and write four outputs. One instruction operating on several lanes of values is called a vector instruction. Changing a program that processes single elements into one that can use such instructions is vectorization. Each lane in a vector of four 32-bit integers represents one reading.

Try a call with overlapping slices. Start with unsigned a[] = {1, 2, 3, 4}; and call calibrate(a + 1, a, 3, 2, 1). Here is the trip through the loop by hand.

Iteration Element read and value Element written and value Array after the write
0 a[0] = 1 a[1] = 3 1, 3, 3, 4
1 a[1] = 3 a[2] = 7 1, 3, 7, 4
2 a[2] = 7 a[3] = 15 1, 3, 7, 15

Imagine loading the original first three readings together. Those numbers are 1, 2 and 3, so the calculation would write 3, 5 and 7. But in the source loop the write in iteration 0 supplies the input of iteration 1. This dependence carries a value from one iteration to the next. Even const unsigned *in permits it. const prevents this code from assigning through in. A write through out can still change an element named by in. With the valid overlapping call above, the last element must be 15.

How one compiled function takes two paths

Compile the loop for an AArch64 Linux target and ask LLVM to report a successful vectorization. These commands only produce text. You can inspect it on a different host with a Clang build that supports AArch64.

LLVM 23.1.6 reported a vectorization width of four and an interleaved count of two. The vector body handled two groups of four readings in one trip. Search array.ll for <4 x i32> and you'll find the vector load, multiply, add and store. Then look above the vector body. There was also a check on n and a calculation involving the distance between the two pointers. Those instructions choose how to execute this call. The compiler has written two ways to run the loop and a small piece of code to select between them. [4]

The check needs to rule out overlap that would change the answer for the grouping it chose. In particular, the shifted slices in our example create a dependency across adjacent iterations. Other overlaps can be harmless. If out == in, each iteration reads and writes its own element, leaving its neighbors alone. A simple compiler could conservatively send every overlap to a scalar loop. A more precise distance check can admit some overlapping layouts. The scalar path also handles small inputs for which setting up the group would have little value. After complete groups are processed, a few leftover elements may still require work. [5]

Now you can interpret the compiler remark. It records that a vectorized form exists in the compiled program. The length and addresses of your particular batch determine whether that form executes. Whether the faster-looking form saves time on your workload calls for a measurement. Guard instructions, short batches, the speed of memory and the target's vector instructions all affect the payoff. The ability to prove independence answers a correctness question. Estimating those costs answers a performance question.

Make one final prediction. Suppose the function accepts only separate input and output slices, and the caller guarantees that contract. Could the compiler omit the overlap check? Yes. Could it dispense with all checks on the length for any possible n? It still must arrange for a group access to stay within the valid elements. Removing one uncertainty leaves the others. In chapter 5 we'll take a function whose operands and dependencies are already clear and ask what work remains once LLVM knows exactly which calculation to perform.

Chapter 5

One function, two processors

In the array loop, LLVM had to decide whether several readings could travel together. Take one reading again. Even here, the processor gives the compiler a choice. AArch64 has an instruction that can multiply two integers and add a third. Will LLVM use it?

With inputs 4, 2, and 1, the processor could save 8 somewhere and then add 1. It could also produce 9 in one instruction. The C function gives the caller no way to observe the intermediate 8. For the unsigned 32-bit integers on our two targets, throwing away excess high bits after each operation gives the same low 32 bits as throwing them away at the end. Even an overflowing product leaves that choice open.

Read two pieces of assembly

Use scale.c from chapter 1 and ask Clang for two assembly listings. The source includes no headers and these commands stop before linking, so you can do this without installing a second operating system or owning either CPU. Use a Clang build with both targets enabled.

These are the function bodies from Clang 23.1.6, with assembler directives omitted. The first is for AArch64 Linux.

A register is a small, named storage location within the processor. Here the caller supplies the arguments in the 32-bit register views w0, w1, and w2, in that order. Read the instruction as w0 = w1 * w0 + w2. At entry those names hold 4, 2, and 1 respectively. The instruction reads the original w0 as one of its inputs, then writes the answer there. The caller expects its result in w0. By the time execution reaches ret, the answer is already in place.

Now look at the same computation for x86-64 Linux. This listing uses AT&T syntax, which puts the destination last.

Here the three arguments arrive in %edi, %esi, and %edx. The first instruction multiplies the first two and leaves the low 32 bits of the product in %edi. The second instruction often surprises a reader who knows that parentheses in x86 assembly can refer to memory. Its name stands for “load effective address.” It calculates the address expression inside the parentheses. In this use, that calculation simply adds two register values and takes the low 32 bits for %eax, where the caller expects its answer. The corresponding 64-bit register names %rdi and %rdx appear in the address expression. The instruction finishes without fetching anything from the address it just computed.

Cover the C source and try to recover the answer from either listing. On AArch64 you can point to where 9 appears. On x86-64 you can point to where 8 appears as well. Those observations establish which arithmetic the compiler chose. Predicting elapsed time would take other information, including which processor implements the instructions and what other work it can do while they execute.

Where did the two IR instructions go?

At the LLVM IR level we had a multiply feeding an add. Imagine drawing an arrow from the product to its use. A compiler that translated each instruction as soon as it met it might choose a multiply before discovering what its result was for. An instruction selector can consider a connected piece of the computation. When a target offers an instruction that implements that piece, and the types and arithmetic rules permit it, the compiler can cover several IR operations with one machine instruction. On another target it can cover the same piece in several steps. The exact selection algorithms differ across LLVM backends. [1]

Both assemblers need physical register names. LLVM IR let us invent names as freely as local variables. What's to stop a large function running out of places for all those values? A first answer comes from the x86-64 listing. Our function has finished with the original x by the time the product is ready, so it can overwrite x. The period from when a value becomes available until its last required use is its live range. Values with disjoint live ranges can generally share a register, subject to the instructions' constraints. [2]

Here's a small allocator puzzle. Suppose two work registers are available. They hold product = 8 and bias = 1. Some other work must now use the first register as scratch, and both numbers are needed afterwards. Assume the scratch work can't move and reproducing the product is expensive. Follow the product through one possible solution.

Saving a value out to memory to free a register is called spilling. In this puzzle it costs a store and a later load. No pointer in the original application asked for that traffic. The compiler introduced it because three demands coincided while two registers were available. A different instruction order might shorten a live range enough to avoid it. In the little function we actually compiled there was enough room, as you can check by looking for stack accesses in both listings. The puzzle will come back when we consider combining a lot of calculations in a single GPU kernel. [2]

What can a language team reuse?

Who decided where the first argument goes? A calling convention is an agreement between independently compiled callers and callees about matters such as where arguments and results go and which registers a call must preserve. The target also has a data layout. For example, a C frontend compiling sizeof(void *) for a typical 32-bit system can emit a different constant from the one it emits for a 64-bit system. Once the frontend has emitted “return 4,” switching to a 64-bit backend cannot recover the fact that the programmer originally asked for a pointer size. That is why we ran Clang twice from the source. [3] [4]

You can even see a difference while keeping the processor family fixed. Save this one-line function in layout.c. Its result type is an unsigned integer. The thing it measures is the C type long.

Locate the ret inside each function. For the Linux target we got ret i32 8. For the Windows target we got ret i32 4. Both machines can perform 64-bit arithmetic. The size convention for this C type differs between these platforms, and the frontend has already committed to the answer in the IR. This tiny test is worth remembering if an application serializes a native long into a file that another build has to read.

Now picture the team building a second language. It has its own syntax and type rules. Its users would still like efficient arithmetic on both of these machines. If the team can express its operations and their rules in LLVM IR, it can use the same instruction selectors and register allocators as Clang. A target maintainer's improved instruction choice can then benefit code from both languages. Each language team still has to make its runtime, libraries, and calling conventions work on the target.

That division of labor helped LLVM spread. The Rust compiler team describes what happened when LLVM gained a WebAssembly backend. Rust inherited much of the work required to generate WebAssembly, and the team explicitly credits shared optimization and reduced backend maintenance as reasons for using LLVM. LLVM supplies these components as libraries. A language implementer can use its code generator and bring an existing parser and language design to it. In combination, those features explain how one project could attract contributors with quite different ideas about how programs should be written. [5] [6]

Swift illustrates the other half of the bargain. It first uses its own Swift Intermediate Language. There it can reason about features such as automatic reference counting, which tracks whether an object still has owners. Later it translates the result to LLVM IR. If you were designing a tensor language, what would you want to settle while a whole array was still visible as one value? Consider two instructions that process the same million elements. A backend may choose excellent arithmetic instructions for each. The language team has an earlier opportunity to remove a round trip through a million-element temporary. [7]

Part II

Where LLVM fits in an AI compiler

Chapter 6

What does a temporary tensor cost?

Our calibration took one arithmetic instruction on AArch64. Now suppose a model uses the same formula to adjust a million values. How many times should it visit each reading? The answer depends on a decision that can be made before the compiler has picked a single machine instruction.

We'll use a row of eight numbers to work it out. In machine-learning code such an array is called a tensor. Tensors can have several dimensions, but a single dimension will do. The elements here are 32-bit floating-point numbers, a common numerical type in model code. Count the positions from zero.

Point at position 3. To supply its answer you need the input 4, the gain 2, and the bias 1. You can multiply, add, and report 9 before anyone has told you what lives at position 4. This independence is the property the compiler can put to work.

For the two-traversal program, imagine pausing after the first loop. You could ask for tmp[3] an hour later and retrieve the 8 that was stored there. For the one-traversal program, pause just after the multiply at position 3. There is also an 8, but its only remaining job is to feed the very next add. A register can hold it. As soon as the add consumes it, the register can be used for something else. Joining compatible computations so that they can run together is called fusion. On a GPU a function launched to do work across many elements is a kernel. If each operation originally had its own kernel, fusion can turn two launches into one. [1]

Suppose a benchmark of these implementations shows a speedup of just 10%. Would that invalidate the arithmetic above? The table counts logical accesses. A recently written element might still be in a cache when the next loop asks for it. At the machine level, memory moves in chunks, registers are finite, a kernel launch has overhead, and the device may be waiting for some other resource. To test the effect, measure elapsed time and traffic to main memory for both large and small inputs. If the benefit shrinks when the working set fits in cache, you've learned something the source listing alone couldn't tell you. The PyTorch 2 team tested a related change on an NVIDIA A100 GPU. They disabled both fusion and inlining for a set of Hugging Face models using 16-bit floats. Across that set, their compiler fell behind the ordinary PyTorch mode that runs operations as they are called. The two optimizations were switched off together, so the experiment measures their combined effect. [1]

Which things have been fused?

The AArch64 example combined two integer operations into one machine instruction. Here we've combined two traversals. That choice can preserve two distinct floating-point operations. There is a surprisingly small test that reveals why the distinction matters. Let the three floating-point arguments be the following exactly representable values.

On paper the exact product is 1 - 2^-46. Under the usual binary32 round-to-nearest rule it rounds to 1. A separate add therefore computes 1 + (-1), giving zero. A floating-point fused multiply-add computes the exact product and sum before its single rounding step. Here it gets -2^-46, a representable value. The difference is observable even with completely ordinary finite inputs. Our array fusion feeds the rounded scalar product directly into the add. To contract those operations into a single-rounding operation, a compiler needs arithmetic semantics that allow the change. LLVM even has a floating-point instruction flag called contract for this permission. [2]

When would you keep the temporary?

Give the scaled values a second consumer. Perhaps one calculation wants every value in order and another wants them in the order specified by an index array.

The second consumer might ask for the same position hundreds of times. If you substitute the body of expensive_scale wherever the intermediate is read, you might repeat a costly calculation hundreds of times. Storing it once could be the better deal. The OpenXLA GPU compiler has to confront this problem in real graphs, including a documented example where one consumer reads a computed value directly and another reads a transpose. The compiler examines which elements each consumer needs before deciding how to group them. Even a single consumer can make fusion expensive if it needs many values at once. Keeping those values live can force the register spills we saw in chapter 5. [3]

Return to the eight readings and erase the second consumer. If the compiler had to justify eliminating tmp, which two facts would you write in the margin? Each output at position i uses the product from that same position. The add is the product's sole consumer, so we can discard it immediately afterward. Now we want a way to tell a compiler those facts before the calculation has spread out into loops, pointer arithmetic, and loads. Chapter 8

Who writes the GPU kernel?

A colleague reads a model, finds torch.log2(x) and asks for the file containing the GPU loop. Where would you look? In one published PyTorch compilation, the loop came into existence when the model was compiled. It handled a tensor with two dimensions using a single run of consecutive memory addresses. The compiler chose how to compute the logarithm, where to read its input, and which instructions to run at different stages. [1]

From a tensor operation to one output element

Take a contiguous tensor with two rows and three columns. Put 1, 2 and 4 in the first row, and 8, 16 and 32 in the second. A base-two logarithm asks what power of 2 gives each number. The first output row should read 0, 1, 2. The second should read 3, 4, 5. Computing the value at row 1, column 0 requires only the input at row 1, column 0. This independence is the reason a GPU can split the work among many workers.

The PyTorch 2 authors traced a two-dimensional example through their compiler. PyTorch's Dynamo component watches the Python program and records tensor operations in a graph. In this case the graph contains a logarithm. The compiler then breaks that operation into steps it already knows how to implement. The identity underlying this particular decomposition is log2(x) = ln(x) × (1 / ln(2)). The multiplier is a constant. As usual with floating-point arithmetic, an implementation approximates the mathematical result. TorchInductor, PyTorch's code generator here, now has a recipe for a single element. Here is that recipe in pseudocode for a contiguous input. [1]

Work through row 1, column 0. Its offset is 3. That's where the 8 lives. Now work through the whole array in row order. The offsets are simply 0, 1, 2, 3, 4, 5. Given the contiguity of this input, the generated kernel can count directly in offsets. With a transposed view of the same memory, row 1, column 0 can refer to a different address. The stride tells you how far to move in memory to advance one row or column. The compiler uses both sizes and strides when it simplifies this index.

Five blocks for 1,025 values

Imagine running the example on a longer array. A Triton program instance processes a block, a group of positions. Here is the indexing and masking written in Triton syntax, with names chosen for this explanation. The listing shows the kernel body. A launcher supplies input and output pointers and launches enough instances to cover length. The paper's figure 3 shows its actual generated kernel. [1] [2]

Read positions as a set of consecutive integers. Each position gets its own Boolean in inside. A false value suppresses the corresponding memory access. We chose 1 as the filler for a suppressed load because its logarithm is well defined. The masked store discards that position's result. For a block size of 256, divide 1,025 by 256 and round up to get five program instances.

We have assigned work to instances without specifying one physical thread per element. The number 256 describes how many elements this instance handles. Hardware threads cooperate to process its block. That leaves room for the compiler to change the mapping of elements to threads for different chips. It also gives a debugging clue. A program that works at 1,024 and produces a bad final element at 1,025 has just exercised its first partial block. Inspect both the launch count and the predicate on the final store.

Where LLVM enters

Triton is a language and compiler for writing programs that work on blocks of data. The PyTorch authors followed their example as far as the Triton source that TorchInductor generated. For the next handoff we can open the NVIDIA backend in a particular release, Triton 3.8.0. Its conventional path includes three identifiable stages. make_llir produces LLVM IR after lowering the block computation. make_ptx emits PTX, NVIDIA's virtual instruction language. make_cubin invokes the device assembler to produce a binary for the target GPU. The source of that release and the older paper document adjoining pieces of a pipeline. A fresh framework build can produce a different kernel for the same Python call. [3]

A better instruction selector can improve a load or an arithmetic sequence near the bottom. By then, the kernel's contract already assigns it a set of positions and names the buffers it reads and writes. If an upstream stage split the multiply and addition of our calibration function into separately launched kernels, each would arrive at LLVM as its own job. The decision to allocate the intermediate array and launch twice is visible most clearly in the calling program.

When the compiler calls someone else's kernel

OpenXLA provides a second trail. Its GPU documentation follows GELU, a smooth activation function used in neural networks. You can ignore the formula and observe one property. Every output reads its corresponding input and combines it with constants using arithmetic and a hyperbolic tangent. The published input has shape 6 × 512 × 4,096. Each GPU block in this example covers 512 outputs. Within it, 128 threads each cover four consecutive positions. The index calculation turns a block number, a thread number and a number from zero through three into coordinates in the original tensor. Try block zero, thread one. It owns positions four through seven in the first row. [4]

OpenXLA's own loop emitter builds that traversal and initially puts the formula for one output in a helper function. The intermediate listing includes a call taking an input tensor and three indices. A later listing has the arithmetic inside the loop, much like the inlining we watched in chapter 3. Subsequent stages lower the operations toward LLVM IR. There is no reason for PyTorch's logarithm example and OpenXLA's GELU to pass through an identical set of intermediate languages. They both have to answer who owns each output and where its inputs live. [5]

Now give OpenXLA a matrix multiplication followed by calibration. Each entry in the matrix product sums many products. Nearby output entries reuse some of the same input values. Processing a small rectangle of outputs together, a tile, allows a kernel to keep portions of both inputs nearby and reuse them. A vendor library such as cuBLAS may already have a particularly good implementation for this shape and arithmetic type. Alternatively the compiler can generate a tiled kernel using Triton and incorporate the calibration before it writes the output. The cost comparison includes the speed of the matrix multiplication itself, any extra reads and writes, and the operations the chosen library routine can incorporate. [6]

A single model can use all three routes. On the library route, the relevant artifact in your program might be a call carrying dimensions and pointers. The implementation you would investigate next belongs to the library. On either generated route, looking for the generated device program is a reasonable next step. This is one sense in which LLVM remains relevant to AI. A graph compiler can give LLVM a kernel to finish, alongside other calls whose implementations have already been supplied.

What a new chip still costs

Giving a device a backend is enough to start asking which programs it can run. Getting good use from a specialized arithmetic unit requires more information. Which combinations of inputs will it accept? How are the values arranged when it reads them? Can enough nearby outputs reuse those inputs to pay for moving them into place? NVIDIA's CUDA Tile gives compiler authors operations on whole tiles and leaves the mapping to NVIDIA hardware to its implementation. Even at that level someone must specify what happens at the edge of an array. The CUDA Tile 13.4 release includes clarifications for partial tiles. The same edge case we met at position 1,024 now shapes the interface between a language and its backend. [7] [8]

This cost shows up on CPUs too. LLVM's GlobalISel effort shares machinery for selecting instructions and works on a machine representation spanning a whole function. Target developers still supply rules and measure the result. Arm's LLVM 23 report, for example, found debug-build compilation 15% faster on the CTMark suite on AArch64 and credited improvements to GlobalISel along with debug-information and code-generation work. That measures the time the compiler takes. Your GPU kernel's time on the device measures the compiled program. Those are two different clocks, and a service receives the bill for both. [9] [10]

Why is the first request slow?

A newly started worker receives an array, doubles every value and adds one. The caller waits. A second request with another array of the same length comes back almost immediately. Did the GPU get better at multiplication between requests?

Start a stopwatch just before the application calls the compiled function and stop it when the answer is ready. The first request may pay for discovering the calculation, generating a kernel, assembling it, and running it. Some compilation modes also try several implementations and time them. A later request may reuse the winner. It can have nearly identical arithmetic and a much shorter wait. [1]

Measure a request that has actually finished

GPU launches normally return control to the CPU while the device is still working. A host timer around the Python call alone can therefore measure the time it takes to queue a job. A synchronization waits until the device has finished. Put one before the timer to drain earlier jobs and another before reading the elapsed time. This deliberately includes the waiting time a caller experiences when it needs the result now. In a workload designed to overlap many requests, forcing a wait after every call would change the behavior being measured. [2]

Save the program as measure_scale.py.

The values in these arrays, their doubles and the results of adding one are all exactly representable in 32-bit floating point. An exact comparison makes sense here. Each input is already on the device, so the stopwatch excludes input transfer and process startup. The output is also on the device when the timer stops. An application returning data to a host caller would include that transfer in its own latency budget.

Run the first command in a fresh process for timings, and the second in another process to inspect what happened. Each command asks for a fresh local Inductor cache directory. Look for two pieces of evidence in the second run. A guard is a condition that has to hold before the runtime reuses a compiled version. Our dynamic=False makes dimensions static on purpose. The change to 1,025 is an opportunity to see a failed size guard. Returning to 1,024 gives the first compiled version a chance to match again. The generated code can also show whether calibration uses one kernel and whether there is a separate buffer for the product. Changing dynamic=False to the default dynamic=None lets PyTorch attempt to generalize a changing dimension when it recompiles. A single dynamic version can then cover several lengths if its operations and guards permit them. [5]

Those arrays are tiny on purpose. A first-use delay will stand out. A warm time for 1,024 values can be dominated by Python, dispatch and launch overhead. To investigate arithmetic or memory throughput, use larger arrays, record their sizes and look at a GPU trace. Two timestamps recorded on the same GPU stream can measure elapsed time on that stream once the second event completes. A profiler can show the duration of the particular kernel you care about. End-to-end synchronized latency answers yet another question. Write down which clock a number came from before comparing it to a number in a paper.

Suppose you can build a baseline version in 10 ms and it takes 2 ms per call. An optimized version takes 70 ms to build and 1 ms per call. These are invented numbers. Two different ways to shrink the wait

Consider the CPU code generator in chapter 5. Even at -O0, it must choose instructions, assign registers, and encode something the processor can execute. A recent project called TPDE explores how quickly this work can be done for a baseline compiler. It analyzes the input and emits machine code with prepared instruction encoders. Its LLVM IR backend accepts a subset of LLVM IR and emits native code. That makes it interesting for jobs where a program needs native code quickly, for example a database generating code for a short query. Its Clang integration can fall back to LLVM for unsupported inputs. [6]

The TPDE authors measured integer programs from SPEC CPU2017 using LLVM 20.1.7 on an x86-64 Xeon and an AArch64 Apple M1. Generating code from unoptimized LLVM IR was 8–26 times faster than with LLVM's -O0 backend in that experiment. Include the frontend, and the reported improvement in overall compilation was 9–24%. A C++ file may require substantial work before any LLVM instructions exist. Speeding up the backend leaves the time spent parsing and checking the C++ source in the total. The generated programs' running times were within about 9% of the baseline in this experiment. That is a third measure with its own baseline. [7]

To see why the backend and whole-build numbers differ, imagine a 100 ms build that spends 20 ms generating machine code. Making that step ten times as fast leaves an 82 ms build: 80 ms for the rest, plus 2 ms for code generation. This example uses invented times. The same calculation works with the stages in a trace from your own build.

Now move the stopwatch earlier in a GPU job. How many rows should a matrix tile contain? How many stages of input should be prepared ahead of the arithmetic? One way to choose is to build candidates and run them on the actual device. Every candidate costs time, including ones that turn out to be poor. Helion, a GPU kernel language, can read a kernel's structure and use that information to pick promising initial configurations. The same machine-code backend can be invoked fewer times if the search starts in a better place.

In November 2026 Helion's authors reported results for 38 kernels that each performed one or more matrix multiplications. They tested one shape per kernel. With an unseeded search the median number of configurations tried before getting within 5% of the best observed result was 255.5. With the heuristic supplying starting points the median was 175. The final winners achieved nearly the same speed. The unit here is configurations tried. Converting those counts into seconds would require knowing how long each candidate took to compile and benchmark. The authors also describe errors in predicting where the lower-level compiler will place values, a good reason to test a promising choice on real hardware. [8]

On the timeline above, a TPDE-style intervention shortens an individual code-generation step in a CPU compilation. A Helion-style intervention changes how much search the GPU compiler performs. A reusable shape guard can eliminate a whole trip through compilation. When a request is slow, check whether the runtime reused an existing version. That one observation can rule out compiling and tuning a new kernel for that call.

Who checks a clever optimization?

A compiler sees x + 1 > x. Someone suggests returning true and deleting both the addition and the comparison. Choose an input to test the suggestion. If you chose zero, the original and the proposed replacement agree. The same is true for one, two and quite a few other choices. How would you pick a more revealing input?

A counterexample you can run

Use eight bits for the addition and interpret both operands of the comparison as unsigned. With eight bits, every possible input fits between 0 and 255. A plain LLVM integer addition retains the low eight bits of the mathematical sum. The bit pattern for 256 ends in eight zeroes. So adding one to 255 takes us to zero, and zero is smaller than 255. [1]

Read the following as a specification of the arithmetic we mean. In LLVM IR the comparison ugt means “unsigned greater than.” The eight-bit width belongs to the instruction itself. This precision matters here. Writing the similar-looking C expression using a byte variable can promote the operands to a wider integer before addition.

Save the listing as wrap.ll. The caller widens the one-bit result to an integer process exit code so that the shell can show it to us. A zero here means the comparison returned false.

With LLVM 23.1.6 this prints 0. Replace the three instructions in grows with ret i1 true, leaving the caller alone. This time it prints 1. Both files passed the verifier. The verifier can check, for example, that the function returns the right type and that an instruction's operands have definitions in the right places. Those are properties of one program. To judge the proposed transformation we need a relation between two programs. For this input they produce different observable results. [2]

The failed rewrite suggests a better one. If the input is anything other than 255, incrementing it gives a larger number. If the input is 255, the comparison is false. That describes a single instruction, icmp ne i8 %x, -1. The constant -1 is the bit pattern with all eight bits set, and equality compares those bits. For each of the 256 ordinary byte values, this comparison returns the original answer. Restore the original body of grows, then run opt -S -passes=instcombine wrap.ll -o repaired.ll. In LLVM 23.1.6 the new body of grows contains that exact comparison with -1. The input that broke the first rewrite led us to the same rule LLVM uses.

How to search for a counterexample

A program can test all 256 byte values almost instantly. Two 64-bit inputs already give it 2¹²⁸ pairs to try. Alive2 takes the original LLVM IR and proposed replacement and asks a solver whether the replacement can violate the original's guarantees. A counterexample gives a developer something concrete to add to the tests. For our proposed constant answer, 255 is the whole bug report.

LLVM uses the word refinement for the direction of this check. On inputs where the original promises a particular answer, the result has to respect that promise. Some LLVM operations leave the implementation more freedom under specified conditions. A rewrite can narrow that freedom. Introducing a newly invalid result for a previously well-defined input would break the contract. The plain eight-bit addition above makes a promise at 255 as firmly as it does at 0. Adding an unsigned-no-overflow flag to avoid considering 255 would change the input program's contract. Here the result feeds the comparison, so that flag would require a proof that the input cannot be 255. [3] [4]

Checking a rewrite this way is part of LLVM development. LLVM's guide for contributors to its instruction-combining pass asks for Alive2 proofs when proposing rewrites. In their 2021 study, Alive2's authors reported 47 new bugs from running the tool over LLVM's unit tests. The scope of a successful check matters. The tool can bound loop iterations, run out of solver time, or encounter operations it cannot handle. Its developers explicitly describe limits on transforms across function boundaries. A timeout leaves an open question. A counterexample to a supported transform gives you a definite reason to change it. [5] [4] [6]

Where a model can make the decision

Consider the call to our calibration helper. The compiler establishes whether inlining the call is legal. Even inside that legal set, the decision has consequences. Copying the function into many callers may grow the binary. At a call with gain one and bias zero, exposing the constants may shrink it. A compiler designer could write a scoring rule by hand. LLVM's MLGO framework lets a trained model make that kind of profitability decision. One use is inlining for code size. Another guides the choice of which value to evict from a register. Training on examples can help predict downstream effects. The compiler still implements the transformation, and measurements on relevant workloads tell us whether the choice paid off. [7] [8]

A language model can also propose an ordering of compiler passes. One research group trained a model on LLVM programs with the goal of reducing instruction counts. In this application the model chooses compiler options and the compiler performs the rewrites. Counting the resulting instructions tests the study's chosen objective. To claim faster service responses, someone would still need to measure service responses. And if a model supplies replacement IR directly, the byte example gives us exactly the question to ask of that replacement. Which previously valid input might get a different answer? [9]

The last slow request

Return to the application checking a batch of readings. Here is a fictional incident that uses the observations from this book. A worker takes unusually long to deliver its first calibration result. A later batch is one element longer and brings the pause back. Even after startup, large batches take longer than the team expected.

The team records a host compilation trace and a GPU timeline for the same request. A long host compilation interval comes before a short device launch. The trace for the length change has a second compilation, and the guard log names the previously assumed length. Those two clues suggest a cheap experiment. The service accepts exactly two lengths. The team calls the compiled function at both lengths during worker startup and waits for completion before marking the worker ready. On a replay the pauses move to startup, and neither request triggers compilation. A change in dtype or layout could produce another variant, so the team replays examples from actual requests.

The large-batch problem survives. The GPU trace shows two kernels. One writes a temporary array. The next immediately reads that array and writes the output. Memory counters show high bandwidth use during the two launches. Looking up their callers reveals that the service wrapped scaling and biasing in separately compiled stages. The team puts the two expressions in the same compiled function. With the buffers on the same device and no other user of the intermediate, the generated code now loads each element, applies both operations, and stores the result in one kernel. A new trace shows a single launch, lower memory traffic and a shorter warm request. The team checks the outputs against the reference, including the last element of the odd-sized batch.

Where was LLVM in that incident? On the generated NVIDIA path, it helped turn each kernel into instructions. Give it two jobs and it can compile each one well. The service got faster when a guard log explained when those jobs were built and an extra buffer explained which jobs the service had asked for. After the last change, the team checks position 3. The reading is still 4, the gain 2, the bias 1. A call, a buffer, and a second kernel have all disappeared along the way. The caller gets 9.
