01 / WHY

问题不是单次推理慢，
而是同一个前缀被反复计算。

LM 程序把生成调用、控制流和结构化输入输出串在一起。调用之间天然共享 system prompt、few-shot 示例、聊天历史和搜索历史；传统请求边界却把这些复用机会切断了。

论文所针对的默认路径：请求结束，KV 生命周期也结束

prefill→decode→discard KV→next call re-prefill

RadixAttention：请求结束，前缀进入可淘汰缓存

prefill suffix→decode→insert tree→next call match
只能复用真正相同的前缀KV 由此前 token 决定；本论文不复用“语义相似但 token 不同”的提示词，模糊语义匹配只是未来方向。
GPU 显存不是免费缓存缓存与正在运行的请求共享同一内存池；等待请求需要空间时，可以淘汰全部缓存来扩大 batch。
运行中的节点不能淘汰每个节点有引用计数；只有 refcount = 0 的节点才可回收，叶节点优先淘汰，让公共祖先活得更久。
执行顺序会改变命中率频繁切换到无关请求会导致 cache thrashing，因此调度器本身也是缓存系统的一部分。
▶ 跑一遍 · 首问与追问的 prefill 差在哪示例值
  1. 设首轮完整 prompt 为 800 tokens；第二轮在此前历史上只追加 160 tokens。
  2. 无跨请求缓存：第二轮重新 prefill 800 + 160 = 960 tokens。
  3. 有 RadixAttention：先命中旧 KV 800 tokens，只需 prefill 新增 160 tokens。
  4. 第二轮的缓存命中率是 800 / 960 = 83.3%；这里只比较 prompt prefill，不代表端到端 latency 也下降 83.3%。

机制依据论文 §3 与附录 A.1；数字为本报告构造，未计入 chat template 的额外 token。

▶ 跑一遍 · 一次 fork，为什么既省算力又省显存示例值
  1. 设共享 prompt 为 256 tokens，3 个并行分支各有 128 tokens 的新输入。
  2. 不共享：总 prefill 为 3 × (256 + 128) = 1,152 tokens，三份公共 KV 也分别占用显存。
  3. 共享：先算公共前缀 256，再算三个后缀 3 × 128，合计 640 tokens。
  4. 此算例减少 44.4% 的 prefill token 计算；公共前缀只保留一份 KV，释放的空间可用于更大 batch。
1 − 640 / 1152 = 44.4%　// 仅 prefill；不含 decode、kernel 与调度开销

▶ 跑一遍 · Figure 3 的树如何长出来论文 Figure 3 · 文本化重演
  1. t = 2：首个会话完成 “Hello → Hi”，把 system prompt、用户消息和模型回复作为一条边插入空树。
  2. t = 3：同一会话的下一轮命中已有边，只把新 turn 追加成新节点，不重算历史。

  5. t = 8–9：新的聊天与 self-consistency 请求到来，LRU 依次回收更久未用的叶节点 g / h / i / k / l。

Few-shot：共享示例，问题只算后缀

同一批 MMLU 问题共享 5-shot 示例。RadixAttention 把示例 KV 留在公共祖先，请求只 prefill 各自问题。

  1. 1批量问题与 5-shot 示例进入 prompt stream。
  2. 2match_prefix 找到公共示例前缀，返回 prefix_len。
  3. 3调度器优先执行具有长共享前缀的请求。
  4. 4模型复用公共 KV，只计算各问题后缀并写回共享内存池。
▶ 跑一遍 · 32 个 5-shot 问题要算多少前缀示例值
  1. 论文负载是 5-shot MMLU；这里设 32 个问题，示例前缀 768 tokens，每题后缀 64 tokens。
  2. 无共享：32 × (768 + 64) = 26,624 prefill tokens。
  3. 有共享：首个请求算 768 + 64，其余 31 个各算 64，合计 2,816 tokens。
  4. 缓存命中率 (31 × 768) / 26,624 = 89.4%；调度的任务是尽量让同前缀请求连续执行。

5-shot 来自论文 §6.1；32、768、64 均为示例值。忽略输出 token、模板差异与显存淘汰。

05 / DESIGN

真正值得读的，是这五个取舍。

每张卡都按同一顺序拆解：决策问题、被否决的备选、选择理由、付出的代价。论文结论与本报告的工程解读分开标注。

D1

用 radix tree 组织 KV，而不是一张“完整 prompt → KV”的表

§3 · §7 · Fig. 8(c)

决策问题

如何自动处理多级、动态、不规则的前缀共享，同时支持匹配、插入和淘汰？

被否决的备选

vLLM / ChunkedAttention 的简单前缀复用不覆盖树形多级共享与 LRU；PromptCache 的模块化非前缀复用可能影响精度；论文另测了 No Tree-Structure 表缓存消融。

为什么这样选

压缩 trie 的边直接携带 token 序列；分裂一条边就能暴露新的共享祖先。树同时成为索引、生命周期层级与调度所需的局部性地图。

代价 / 权衡

只能精确匹配 token 前缀；要维护分裂、引用计数与 LRU。树元数据在 CPU，论文测得无命中时管理开销仍低于 0.3%。

D2

把“保留什么”和“先跑谁”合成同一个缓存问题

§3 · Alg. 1 · Theorem 3.1

决策问题

显存有限且请求不断到达时，怎样的淘汰与执行顺序能保住高命中率？

被否决的备选

论文在 Fig. 8(c) 对比 FCFS Schedule 与 Random Schedule；相关工作 vLLM / ChunkedAttention 不具备本文的树形 LRU + 缓存感知调度组合。

为什么这样选

叶优先 LRU 尽量保留公共祖先，refcount 保护运行中节点；等待队列按 matched prefix length 排序，近似 DFS。离线且缓存≥最长请求时，论文证明 DFS 达到最优命中率。

代价 / 权衡

贪心重排可能导致饥饿；在线场景会破坏 DFS，且不可预测的输出长度可能触发重算。最优性定理不能直接当成在线 SLA。

D3

让前端发 fork hint，而不是假装运行时能推断一切

§2–3 · Fig. 8(c)

决策问题

并行分支尚未完整到达时，运行时怎样及时建立共享前缀并安排局部性？

被否决的备选

Guidance / LMQL 侧重语言与后端连接，未采用本文的协同运行时；vLLM / TGI / TensorRT-LLM 从通用请求接口出发，缺少程序结构。论文还测试 No Frontend Hint 与 No Frontend Parallelism。

为什么这样选

fork 时前端先把 prefix 作为提示发过去，再发剩余分支 prompt；共享路径能及时插入树中。异步 stream 同时暴露程序内并行，结果读取点才同步。

代价 / 权衡

性能来自前后端协议而非单模块优化；绕过前端或丢失 hint 会削弱效果。编译器模式的 tracing 还受数据依赖控制流限制。

D4

压缩 FSM 的单值路径，一次 forward 跨过多个 token

§4 · §6.3 · Appendix B

决策问题

JSON 等格式中大量固定字符已由语法唯一确定，为什么仍要逐个 token 解码？

被否决的备选

常规 guided generation FSM（论文引用 Willard & Louf [54]）每轮只根据当前状态掩码非法 token；论文的 normal FSM 对照仍逐 token forward。

为什么这样选

递归合并相邻 singular-transition edges；遇到压缩边上的确定文本就 jump forward。对压缩文本重新 retokenize，保持与原 tokenizer 对齐，并跨请求复用预处理后的 FSM。

代价 / 权衡

只在确定路径上省 forward；每请求重做预处理反而使吞吐降低 2.4×。字符串/token 对齐还会带来概率扭曲，论文将其列为未解问题。

D5

黑盒 API 不能改运行时，就推测后续调用会怎样继续

§5 · §6.2 API models

决策问题

只能调用 OpenAI 等黑盒端点时，多调用程序怎样减少重复输入与往返？

被否决的备选

朴素地为每个 gen 发一次 API 请求；Table 1 中 LMQL / Guidance 都可接 OpenAI 后端，但本文针对的是自身多调用流的额外输出复用。

为什么这样选

第一次调用忽略 stop、额外生成少量 token；解释器保留额外输出并尝试匹配后续原语。命中模板时，可少一次 API 调用与对应的重复输入费用。

代价 / 权衡

不是 KV 复用，也不保证推测正确；依赖提示工程与输出格式。论文的三字段抽取实验约减少 3 倍输入 token 成本，但不能外推到任意程序。

▶ 跑一遍 · 为什么 DFS 顺序可能优于 FCFS示例值
  1. 设请求 A = P + x、B = P + y、C = Q + z；P、Q 各 512 tokens，x/y/z 各 128 tokens。缓存最多容纳一条 640-token 请求路径。
  2. A → B → C（DFS 局部性顺序）：A 全算；B 命中 P 的 512；C 无命中。总计命中 512 / 1,920 = 26.7%。
  3. A → C → B（交错顺序）：在本例的容量与 LRU 假设下，C 进驻时淘汰 P；B 到来时也无法命中，总命中为 0。
  4. 这就是论文 Theorem 3.1 的直觉：沿同一子树走完，公共边会持续被命中；离开子树后才转向其他分支。

算例用于解释机制，不是论文 benchmark。定理还要求离线批处理、缓存容量≥最大请求长度；在线与可变输出情形见论文脚注 2 和附录 A.3。

07 / REVIEW

命中最高的地方，
不一定就是收益最大的地方。

这篇论文最持久的贡献，是把 LM 程序结构转成运行时可利用的局部性。但定理、消融与端到端数字各有边界，阅读时不能混用。

论文自认

作者明确留下的缺口

  • 调度饥饿：贪心缓存感知调度需要与公平调度结合。
  • 在线最优性受限：DFS 会被在线到达打乱；输出长度不可预测还可能导致重算。
  • 缓存层级：跨 DRAM / Disk、多级内存与模糊语义匹配仍是未来方向。
  • 压缩 FSM 概率扭曲：字符串和 token 不完全对齐时，选择概率可能失真。
  • 编译器限制：tracing 不支持数据依赖控制流；GPT-4 代码移动实验可能改变语义。
工程师视角

落地前应该追问

  • 归一化图表缺少绝对值：无法仅凭 Figures 5–7 推导自己的 SLA、成本或容量。
  • 基线是历史版本：结果不能外推到这些系统的新版本；应在自己的模型、kernel 与流量上重测。
  • 长输出会稀释收益：论文明确报告 multi-turn chat (long) 几乎没有加速，因为 decode 主导且跨会话共享少。
  • 命中率不是延迟：高命中只描述 cached prompt tokens / prompt tokens，不含输出长度与每阶段耗时。
  • 分布式证据较窄：附录 A.4 的四 worker + MMLU 线性扩展值得继续验证，不等于所有在线负载都已解决。
可以直接偷的思想

即使不采用 SGLang 也成立

  • 把请求历史当成缓存资产：完成不等于销毁，生命周期应由未来复用价值决定。
  • 树即局部性索引：任何具有公共前缀的 intermediates，都可考虑 radix/tree + LRU。
  • 调度感知缓存：执行顺序不是公平队列的附属品，而是命中率的一阶变量。
  • 缓存与活跃任务共池：让可淘汰缓存把空间让给有需求的运行请求。
  • 把结构信息跨过抽象边界：前端一个轻量 hint，可能比后端复杂猜测更有效。
▶ 跑一遍 · 80% 命中率为何只换来 1.09× 端到端速度示例值
  1. 设无缓存时 prefill 为 100 ms、decode 为 900 ms，端到端总计 1,000 ms。
  2. 理想化地把 80% prompt-token 命中率 近似为 prefill 时间减少 80%，新 prefill 为 20 ms。
  3. decode 不变，新总时间为 20 + 900 = 920 ms，端到端加速仅 1,000 / 920 ≈ 1.09×。
  4. 所以论文中短输出对话收益更明显、长输出对话几乎无加速，并不矛盾：两者的时间分母不同。
speedup = (prefill + decode) / (prefill × (1 − hit) + decode)

这是用于建立直觉的简化模型，并非论文延迟拟合；实际 prefill 时间、kernel 效率、batch 与调度都会改变结果。
