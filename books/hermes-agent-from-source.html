Chapter 1: The Architecture of One Agent

The Problem: One Agent, Many Doors

A useful agent rarely stays in one place. It starts as a terminal chat. Then you want it on your phone, then on a morning schedule, then inside your editor.

Each of these is a door: a way for a person, or a clock, to ask the agent for something. The hard part is what sits behind the doors. If each door gets its own copy of the agent logic, the copies drift. One handles long chats and another does not. One asks before running a risky command and another forgets. Every bug gets fixed four times.

So every agent system must decide early: what is shared by all doors, and what belongs to one?

The Options

  1. One agent per door. Quick to build and easy to tune per surface. Over time the loops stop agreeing on retries, compression, and permissions.
  2. Shared helpers, separate loops. Less copied code, but the loop itself is still copied, and the loop is where most bugs live.
  3. One core loop, thin doors. Every surface calls the same loop and passes its differences in as settings and callbacks. The cost is discipline: the core must never learn about a specific platform.

Hermes’s Choice: A Narrow Waist

Hermes, the open-source agent from Nous Research, takes option 3. Picture an hourglass: many doors at the top, many tools and stores at the bottom, and one thin point in the middle, a class called AIAgent.

AIAgent owns the turn: everything between a user’s message and the reply. It builds the prompt, picks the model, calls it, runs the tools the model asks for, saves the result, and repeats until the model is done. The CLI, the messaging gateway, the editor adapter (ACP), cron, the batch runner, the API server, and a plain Python import are all doors into that one turn.

Even the terminal UI and desktop app are not separate agents. They are clients of a session authority, usually the profile’s gateway, which runs the same turn for them (Chapter 9).

Inside the core, the work splits three ways:

  • Prompt assembly builds one system prompt and does not rebuild it mid-conversation (Chapter 6).
  • Provider resolution turns “this provider, this model” into an API style, an address, and credentials (Chapter 4).
  • Tool dispatch turns a tool call into a real function call, after hooks and safety checks (Chapter 7).

Below them, the session database records every conversation (Chapter 3), and backends decide where tools run: laptop, container, remote machine, or hosted sandbox (Chapter 8).

How a Tool Gets In

No central file lists the tools. Each tool module registers itself when Python imports it, so the registry knows every tool before any agent exists.

Registration (“does this tool exist?”) is settled at import. Availability (“can it work right now?”) is checked later by each tool’s check_fn. If Docker is down, its tools simply drop out of what the model sees.

Every tool description is sent to the model on every call, so a new core tool makes every request bigger for every user. That is why Hermes ranks the ways to add a capability, cheapest first:

Small Public Files

The files other code imports stay small and stable. Growth goes into neighbouring modules. run_agent.py is the public face of AIAgent, but the loop lives in agent/conversation_loop.py and its agent/turn_*.py phases. The database, gateway, and CLI follow the same pattern. Callers depend on one stable name, and a file-size limit stops the public file from becoming a giant again.

Two Rules That Shape Everything

The cached prompt is sacred. Providers can reuse work for a prompt prefix they have already seen, which makes long chats far cheaper. That only works if the prefix stays the same. So Hermes never edits past messages, swaps tools, or rebuilds the system prompt mid-conversation. Commands that would do so wait for the next session unless the user adds --now. Context compression is the one allowed exception (Chapter 15).

Profiles are islands. A profile is its own home directory, with its own settings, keys, memory, and history. Every path goes through one function, get_hermes_home(), which can be overridden per task. Hardcoding ~/.hermes is a bug.

The core also keeps four smaller promises: report every tool run (so it shows up on a phone and in logs), allow any call to be interrupted, contain no platform-specific branches, and boot without optional parts like MCP or memory plugins.

The Same Turn in Different Clothes

  • CLI: the user types, run_conversation() runs the turn, the CLI prints and saves.
  • Gateway: an adapter turns a chat event into a message, the gateway checks the sender and finds the session, then calls the same run_conversation().
  • Cron: each due job gets a fresh agent with the job’s skills attached. Long-term memory loads. Last week’s tool output does not.
sequenceDiagram participant Door as Entry point participant Agent as AIAgent participant Model as Provider participant Tools as Registry participant Store as Session DB Door->>Agent: user text or job prompt Agent->>Agent: reuse cached system prompt Agent->>Model: one API mode Model-->>Agent: tool calls or final text alt tool calls Agent->>Tools: dispatch, hooks, approval Tools-->>Agent: results in call order Agent->>Model: next iteration else final text Agent->>Store: persist the turn Agent-->>Door: reply for this surface end

There is no gateway-only compressor and no cron-only tool runner. Doors make policy choices, such as which tools to allow. The loop stays one loop.

The Trade-offs

  • The core must stay ignorant. Platform needs become settings or callbacks, which takes more design than a quick if.
  • The constructor gets wide. Every way a door may differ becomes a parameter (Chapter 2).
  • Every door inherits every rule. Cron and the editor obey the same cache and safety rules as the CLI, even when a shortcut would be easier.

Hermes accepts these costs because several agents that slowly disagree is worse. Surfaces multiply. The turn does not.

Apply This

One loop, many doors. Put the turn behind one function. Keep surface policy in the caller.

Register at import, check at runtime. Hide tools whose backend is down. “Registered” is not “working.”

Stable public names. Move logic into neighbouring files. In tests, patch the name callers import.

Treat the prompt cache as a rule. Freeze the prompt for a conversation, and let exactly one subsystem rebuild it.

One path resolver. A per-task home override lets one process serve several tenants without leaks.

Chapter 2: Starting the Process

The Problem: Starting in a Known-Good State

Before an agent answers anything, its process has to start correctly. That sounds trivial. It is not, for three reasons any long-lived agent shares:

  • The code may be broken. An agent that updates itself can be killed halfway through an update, leaving a mix of old and new files.
  • The wrong user’s files may be loaded. If one machine holds several setups (say, “work” and “personal”), the process must pick one before it reads any data.
  • Secrets and settings must come from that same setup. Loading the default API keys into the “work” profile is a silent, dangerous mistake.

Each of these can only be fixed at the right moment. Check the code after importing it and you are already running broken code. Choose the profile after reading files and you have already read the wrong ones. Start-up is therefore about order.

The Options

  • Lazy start-up. Load things when first needed. Simple, but whatever touches a file first decides which profile wins, often by accident.
  • Settings in environment variables. Easy to set, but they belong to the whole process, not to one profile. In a process that serves several profiles they leak.
  • A fixed boot order. Repair, then choose the home, then load secrets, then import the rest, then build the agent. More rigid, but each step can assume the previous ones are done.

Hermes’s Choice: A Fixed Order

Hermes uses a strict sequence and treats it as part of the design, not a detail.

flowchart TD A["Process start"] --> B["Bootstrap import"] B --> C{"Checkout torn?"} C -->|yes| D["Restore and relaunch"] C -->|no| E["Apply profile override"] E --> F["get_hermes_home locked in"] F --> G["Load .env from that home"] G --> H["Import agent, tools, CLI"] H --> I["Construct AIAgent"]

1. Repair before import. The very first import is hermes_bootstrap. Straight after it, Hermes checks whether an interrupted hermes update left the checkout half-written. If so, it restores and relaunches before importing the rest of the code. There is no “best effort” mode that carries on with a torn tree. A process that looks alive but runs a random mix of versions is worse than one that restarts.

2. Choose the home. A profile is a directory with everything that belongs to one setup:

graph TD Root["Profiles root"] --> P1["profiles/coder"] Root --> P2["profiles/personal"] P1 --> C1["config.yaml
behavior"] P1 --> E1[".env
secrets"] P1 --> D1["state.db
sessions"] P1 --> M1["memory"] P1 --> S1["skills"]

hermes -p coder sets HERMES_HOME to that directory before the rest of Hermes loads. From then on, every path comes from get_hermes_home(). It checks a per-task override first, then the environment variable, then the default location. A second helper, display_hermes_home(), only formats paths for people to read. Code that opens files with it is a bug.

3. Load secrets from that home. Hermes splits configuration on purpose. .env holds secrets such as API keys. config.yaml holds behavior such as the model, toolsets, and approval mode. The project rejects new environment variables for non-secret settings, because a behavior flag in the environment cannot differ between profiles. If no .env exists, Hermes keeps going and logs it. A missing key fails later, at the provider, which is the right place.

4. Build the agent. Only now does AIAgent exist.

The Constructor Is a Doorway

AIAgent is built from many small mixins: streaming, interrupts, persistence, compression, and more. Its constructor holds almost no logic. It passes its arguments to agent.agent_init.init_agent. Callers keep writing AIAgent(...) while the wiring moves freely behind it.

The constructor’s parameters are the list of everything a door may change: provider and model, enabled toolsets, callbacks, platform identity, session id, budgets, and a few flags such as “skip memory.” Doors differ only in what they pass:

one constructor"] TG["Gateway / Telegram"] -->|"chat callbacks,
platform and chat ids"| K CR["Cron"] -->|"fresh session,

A Telegram turn and a CLI turn get different callbacks. They do not get different start-up code.

What the CLI Is, and Is Not

cli.py is the interactive prompt and slash-command handling. It is not the agent loop. It reads a line, may handle a slash command itself, and then calls run_conversation. Commands that would change the cached prompt, like switching models, wait for the next session unless you pass --now. That is the cache rule from Chapter 1, made visible at the keyboard.

The terminal UI and the desktop app are separate processes. They do not embed the agent. They find or start the profile’s session service (hermes gateway ensure) and send input to it (Chapter 9).

Identity Is Stamped Once

Building an agent does not always create a database row. The first turn that needs storage creates it, recording where the session came from (cli, a chat platform, cron), the model settings, and the profile name. That includes the literal name "default", because an empty value is now read as “no owner” and the session would vanish from profile views. Identity is captured once, from the home and platform that boot already fixed.

Why the Order Cannot Move

Each reordering breaks something specific:

If you… …then
choose the profile after tool discovery availability checks run against the wrong home and cache the wrong answer
load .env before the profile the default profile’s keys quietly satisfy a profile that should fail
build the agent before repair a half-updated tree accepts a message and dies mid-tool
read HERMES_HOME once into a global one process cannot serve several profiles later (Chapter 17)

The Trade-offs

  • Less flexibility. You cannot lazily switch profile halfway through a process. You start a new process, or use the per-task override built for that.
  • Tests must prepare first. Even importing run_agent loads the bootstrap and .env, so tests must point HERMES_HOME at a temporary folder before they touch it.
  • A wide constructor. It is the biggest API in the process. Forwarding keeps that width from turning into tangled logic.

Apply This

Recover before you import what you are recovering. If the program updates itself, the first code to run must detect a torn install and relaunch.

Bind the tenant before any cache, client, or database. Choose the home, then load secrets, then import the product.

Secrets in the environment, behavior in a per-tenant file. Otherwise feature flags cannot differ between tenants.

Make the public constructor a forwarder. Keep the type callers build stable, and keep one wiring path for tests and production.

Write the tenant name explicitly, including “default.” Do not let an empty value mean “the default.”

Chapter 3: State, the Session Ledger

The Problem: A Record That Survives

An agent conversation is more than a chat log. It holds the messages, the tool calls and their results, the model that was used, how much it cost, and where the reply must go. Any serious agent needs that record to:

  • survive restarts, so a crash does not lose the conversation;
  • be searchable, so the agent can recall what was said last month;
  • stay correct when several programs touch it at once, such as a phone chat, a terminal, and a scheduled job;
  • never repeat a side effect after a crash, like sending the same message twice.

The last two are the hard ones. They are less about storage and more about who is allowed to write.

The Options

Where to store it:

  • One file per session (for example JSONL). Simple, but searching across sessions is slow and concurrent writers can corrupt a file.
  • One shared database for everyone, with a column saying which user owns each row. Searchable, but every query must remember to filter, and one forgotten filter leaks data.
  • One database per tenant. Searchable, and isolation comes from the file itself.

Who writes it:

  • Anyone who has the file. Easy, until two processes append to the same conversation in the wrong order.
  • A single owner. Everyone else hands work to that owner. More moving parts, but one transcript, one order.

Hermes’s Choice: One Database per Profile, One Writer

Hermes used to keep a JSONL file per session. It now keeps one SQLite database per profile, state.db, at get_hermes_home() / "state.db". Because Chapter 2 already pointed the home at the profile’s directory, each profile gets its own file automatically.

The database runs in WAL mode. In plain terms, many readers can read while one writer writes. A sidebar can load while a turn is being saved. It does not allow several writers.

identity, model, lineage"] DB --> Messages["messages
full transcript"] DB --> FTS["FTS5 indexes

The sessions table holds identity: where the session came from, the user, the model and its settings, the parent session, the profile name, and routing details for chat platforms. The messages table holds the transcript, including tool calls and the model’s reasoning text.

Search uses SQLite’s full-text engine (FTS5) with three indexes: a default one, a trigram index for substring matches, and one tuned for CJK text, because a single default index searches Chinese or Japanese poorly. The indexes are derived from the messages. If a database is recovered, they are rebuilt, not trusted.

The Gateway Is the Writer

The profile’s gateway is the one writer of canonical sessions. The CLI, terminal UI, desktop app, API server, editor adapter, cron, and background workers are all clients. They admit input to the gateway. They do not open state.db and insert rows themselves.

sequenceDiagram participant Client as CLI / Desktop / ACP participant Auth as Session authority participant DB as state.db participant Agent as AIAgent Client->>Auth: admit input Auth->>DB: FIFO row queued Auth->>Agent: run the turn Agent->>DB: transcript via the owner Auth->>DB: settle admission Note over Auth,DB: owner death mid-turn marks the row unknown

Each accepted input becomes a row in session_admissions, a first-in, first-out queue for that session. The interesting case is a crash:

stateDiagram-v2 [*] --> queued: input admitted queued --> started: owner runs the turn started --> settled: turn reaches a terminal state started --> unknown: owner died mid-turn unknown --> resolved: a person or policy decides note right of unknown Not replayed. Later inputs wait. end note settled --> [*] resolved --> [*]

If the owner dies while a turn is started, the next owner marks that row unknown. It does not run it again. The dead process may already have written a file or sent a message, and replaying would do it twice. Later inputs wait until someone resolves the unknown row. A stuck queue is the intended, safe outcome.

Other tables make the same promise durable: a record of managed worker jobs, an outbox of replies the gateway still owes, and locks so two processes cannot compress the same session at once. Because of this, recovering a damaged database is different from restoring a backup. Recovery copies transcripts and rebuilds search, but leaves out the job ledger, since half a ledger could replay work. A full backup keeps the ledger so start-up can reconcile it.

Rows That Look Like Duplicates

When a long conversation is compacted (Chapter 15), the default is to keep the same session id. The old rows are marked active=0 and kept as an archive. The kept head, the summary, and the tail are inserted again as active=1.

graph LR subgraph Before["Before compaction"] A1["msg 1"] --> A2["msg 2 … msg 400"] --> A3["recent msgs"] end subgraph After["After: same session id"] X["old rows
active=0 (archive)"] Y["head + summary + tail
active=1 (live)"] end Before --> X Before --> Y

So a protected message can appear twice with the same text and timestamp. That is not a bug, and those rows must not be deleted. To diagnose a real double write, filter on active=1. More generally, Hermes never decides “same text means same message.” Duplicates are detected with explicit markers.

Store Everything, Send What Fits

Different providers accept different message fields. Some reject reasoning fields by name, and some require them. Hermes keeps the full version in the database and trims it for each provider at send time. If a provider rejects a field, Hermes notes it for that provider and model, strips the field, and retries once. The stored history is never rewritten to suit one provider, so a session can resume on a different one later (Chapter 4).

The Trade-offs

  • Clients depend on the owner. The CLI and desktop app need the gateway to be running, or started, before they can write.
  • Crashes pause instead of retrying. An unknown row blocks its session until someone resolves it. That is safer, but less automatic.
  • Archive rows cost space and confuse the unwary. Hermes keeps them because they explain what compaction did.

What Hermes refused is just as telling: no database per platform, no JSONL fallback as the main path, and no silent replay after a crash. Each would be easier. Each would lose the property Hermes needs: one transcript, one owner, and a crash that pauses instead of repeating.

Apply This

One database per tenant, found through one path function. Isolation by file beats isolation by a column everyone must remember to filter.

Appoint a single writer. Everyone else hands work to it. Do not allow “temporary” direct writes.

Make a crash an explicit “unknown,” and never replay it automatically. Side effects are not safe to repeat.

Keep archive generations. Mark old rows inactive instead of deleting them.

Store the superset, trim per provider. Never save the trimmed form back over the original.

Chapter 4: Talking to Models

The Problem: Many Providers, One Agent

An agent has to call a language model, and there are many to choose from. Some are hosted services, some run on your own machine, and some sit behind a relay such as OpenRouter. They disagree on almost everything that matters at the wire: the request format, how tool calls are written, how “reasoning” text comes back, how you log in, and where the server lives.

On top of that, one agent makes many kinds of model calls. There is the main chat, but also side jobs: describing an image, summarizing a long chat, flushing memory. Each needs the right model, the right address, and the right key. Send a production key to the wrong host, or let a stale shell variable override a saved choice, and things break in ways that are hard to see.

So any multi-provider agent must answer: how does “use this provider and this model” become a working, correctly credentialed connection, for every caller?

The Options

  • Let each caller build its own client. Easy at first. Over time each “small” client picks keys and URLs slightly differently, and one of them sends the wrong key to the wrong host.
  • Store history in each provider’s own format. Simple to send, but you cannot switch providers mid-session, because the history is written in the old provider’s dialect.
  • One resolver plus one internal format. Every caller asks the same resolver for a connection. History stays in one shape and is converted at send time. More upfront work, but provider switches and fallbacks become safe.

Hermes’s Choice: One Resolver, Three Wire Formats

Every surface in Hermes (CLI, gateway, cron, ACP) and every side job goes through the same runtime resolver (hermes_cli/runtime_provider.py). It returns a small answer: which provider, which API mode, which base URL, which key, and where that choice came from.

Choices are ranked. An explicit request wins, then config.yaml, then environment variables, then the provider’s defaults. A saved choice beats a stale shell export. Otherwise an OPENAI_BASE_URL left over from a debugging session would quietly hijack the endpoint the user picked last week.

flowchart TD A["Who is asking?"] --> B{"Explicit request?"} B -->|yes| C["Use that provider and model"] B -->|no| D{"config.yaml selection?"} D -->|yes| C D -->|no| E{"Environment variables?"} E -->|yes| C E -->|no| F["Provider default or auto"] C --> G{"Which API mode?"} G --> H["chat_completions"] G --> I["codex_responses"] G --> J["anthropic_messages"]

There are exactly three API modes:

  • chat_completions: any OpenAI-compatible endpoint. OpenRouter, local servers, most hosted gateways, and provider: custom live here.
  • codex_responses: OpenAI’s Responses API, using Codex’s own login.
  • anthropic_messages: Anthropic’s native Messages API, through an adapter.

The turn never invents a fourth. A new provider is a plugin that registers itself with an API mode, a base URL, the environment variables that hold its key, and fallback models. It is not a new branch in the loop.

One Internal Transcript

Inside Hermes, history is always OpenAI-style messages: system, user, assistant (with optional tool calls), and tool results. That is the shape Chapter 3 stores. At the moment of sending, the current mode converts a copy of it into the provider’s format.

Reasoning text is the tricky part. Relays return it in several shapes, and some providers reject reasoning fields by name. When a route says “unknown field,” Hermes remembers that for this provider, host, and model, removes the field, and retries once. The stored history is never changed.

Keys are tied to hosts. The OpenRouter key goes to OpenRouter. OPENAI_API_KEY is the custom-endpoint key and a fallback, not a universal token. Logins are handled per mode too. A Codex session with an expired item is repaired by dropping cached items and replaying once, not by logging the user out. An Anthropic 401 triggers a credential refresh, a new client, and one retry. Mixing those two cases up would either loop on a bad item or log out a healthy account.

When a Call Fails: Pools and Fallback

Two tools handle failure.

A credential pool holds several keys for one provider. After a rate limit, Hermes rotates to another key, but only if the pool has more than one entry with one still available. Rotating also means a cold provider cache, so the next request costs more.

A fallback chain is an ordered list of provider and model pairs. It activates after repeated malformed responses, after errors like 401, 403, or 404, or after retries on 429 and 5xx run out. Activation swaps the model, provider, URL, mode, and client in place, then resets the retry count. A latch makes sure it happens only once.

sequenceDiagram participant Turn participant Pool as Credential pool participant Primary participant Fallback Turn->>Primary: request Primary-->>Turn: 429 alt pool has another entry Turn->>Pool: rotate Pool-->>Turn: different credential, cold cache else single credential Turn->>Fallback: activate once Fallback-->>Turn: new mode and client end

Because history is stored in one format, the swap is safe. The next call simply converts it for the new mode. The swap may change the model and client. It may not change the session id or drop tool results.

Not everything inherits the chain:

graph TD R["Runtime resolver"] --> Main["Main turn
uses fallback chain"] R --> Cron["Unpinned cron job
gets the chain"] R --> Pinned["Pinned job or child
no chain: fail instead"] R --> Aux["Side jobs: vision, compression,

Child agents inherit the parent’s provider but not its fallback list (Chapter 12). Side jobs have their own auxiliary.* settings. Setting one to main sends it back through the same resolver. A route that names its provider and model is a promise. Quietly leaving it is worse than failing.

The model’s context length comes from one place, model metadata plus the models.dev registry, and feeds compression and the token estimates in Chapter 5. The loop never keeps its own table.

The Trade-offs

  • Pool rotation and fallback cost money. The provider caches by model and account, so a switch means a cold cache. Hermes shows this cost instead of hiding it.
  • Pinned routes can fail. That is on purpose: a cron job must not quietly deliver a different model’s work.
  • Switching models with /model breaks the prompt cache, which is why it is one of the few allowed prompt-state changes (Chapter 6).

Apply This

One resolver for every caller, including the small ones. Side jobs should not grow their own clients.

Keep one internal transcript and convert a copy at send time. That is what makes provider switches safe.

Tie each key to its host. A key is only valid for the URL it was issued for.

Rotate only when it can help, and fall back only once. Single-key pools fall through. Fallback is latched.

Let pinned routes fail rather than wander. And treat an empty override the same as no override.

Part II — The Core Loop

Chapter 5: The Turn

The Problem: A Loop That Knows When to Stop

At the heart of every tool-using agent is a loop. Send the conversation to the model. If it asks for tools, run them, add the results, and ask again. If it answers in plain text, you are done.

That loop is easy to write and hard to get right. Real turns have to survive a lot:

  • the history may be too long to send;
  • the user may press stop, or send a correction, mid-call;
  • the provider may fail, rate-limit, or return garbage;
  • the model may loop forever, or burn through a budget;
  • several tools may run at once and finish in random order.

And every surface, from the CLI to cron to a child agent, needs the same answers. So the question is: how do you structure the loop so each of these cases has a clear, named outcome?

The Options

  • One big function with callbacks. Fast to write. Each new case adds another branch, and soon no one can say what happens when two cases collide.
  • Exceptions for every failure. The caller gets a generic error and must guess what happened, so “something went wrong” covers six different causes.
  • A phase machine with typed results. The turn moves through named phases, and every way of stopping is a distinct result. More structure, but every surface can explain to a human why the turn ended.

Hermes’s Choice: A Phase Machine

run_conversation lives in agent/conversation_loop.py. Each phase lives in its own agent/turn_*.py module: preflight, iteration prep, request assembly, the API call, response intake, the tool round, the finalizer, and the error and recovery paths. run_agent.py keeps only the public name. chat() is a thin wrapper that returns just the final text. run_conversation() returns the full result: messages, usage, metadata, and why the turn stopped. Every surface calls the latter.

stateDiagram-v2 [*] --> Prepare Prepare --> Preflight: history may be oversized Preflight --> Assemble Prepare --> Assemble: under budget Assemble --> CallModel CallModel --> ToolRound: tool calls CallModel --> Finalize: assistant text ToolRound --> Assemble: results appended CallModel --> Recover: retryable error Recover --> CallModel: same or fallback model CallModel --> Stop: billing, interrupt, budget, compression failure Finalize --> [*] Stop --> [*]

One user turn may contain many model calls. In order, the turn ensures a task id, appends the user message, reuses the cached system prompt, compresses first if the history is too big, builds messages for the current API mode, adds per-call extras that must stay out of the cached prompt, makes the call, and then either runs tools and loops or saves and returns.

Messages follow strict rules that providers enforce. After the system message, user and assistant alternate. A tool round is an assistant message with calls, then one or more tool results. Two user messages in a row are illegal, and so are two assistant messages. So whenever the loop wants to “just add a note,” it has to put it somewhere these rules allow.

Interrupts: Abandon Means Abandon

The model call runs on a worker thread. The main thread waits for the response, an interrupt, or a timeout. A new message, /stop, or a signal abandons the worker, and the partial response is not written to history. A half-parsed tool call in the transcript would make the next request invalid and poison the session. Losing a second of output is the better deal.

Two softer interrupts exist. A redirect cancels the in-flight call and continues the same turn. A steer lands at the next tool boundary. Neither starts a new turn.

What “Stop” Means

The boring stop is plain text with no tool calls. Every other stop is its own result:

graph TD T["Turn"] --> A["Done: text, no tool calls"] T --> B["Iteration budget used up
returns a summary of work done"] T --> C["Interrupted by the user"] T --> D["Billing or entitlement failure"] T --> E["Compression cannot make it fit"] T --> F["Handoff guard: nothing real to answer"]
  • Iteration budget. Each agent has its own IterationBudget. The CLI default is agent.max_turns (500). A child gets delegation.max_iterations (50). A library caller that sets no cap gets no cap, because the surface sets policy, not the library. execute_code iterations can be refunded. At the cap, the agent stops and summarizes. Hermes removed “you are running out of turns” warnings because they taught models to give up early.
  • Wall-clock budget. At 80% of the run budget, a one-time note asks the model to wrap up.
  • Billing errors become a labeled final result, not endless retries.
  • Compression failure. If compression cannot make the request fit, the turn stops instead of sending a request the provider will reject.
  • Handoff guard. After compaction, if the summary dropped the user’s actual request, the loop puts it back. If it cannot, it does not let the summary act as the user.

Fallback (Chapter 4) sits inside this machine. A repetition guard stops runaway loops. These budgets are kept separate on purpose: iterations, wall-clock time, and review tokens measure different things, and merging them either kills healthy long tasks or lets spending run unchecked.

Notes Go on the Newest Tool Result

Mid-turn notices, such as the wrap-up note or an interrupt marker, need a place to live. Putting them at the start of history would break the prompt cache. So Hermes appends them only to the newest tool result that has not yet been saved. If there is no such message, the note is skipped. A quiet turn is cheaper than a broken cache.

saved: frozen"] --> A2["assistant + calls"] --> T2["newest tool result
not saved: notes go here"]

Token estimates follow the same care. When the provider’s own estimate is available, it wins over Hermes’s rough count, so the loop does not compress a session the provider was about to trim anyway.

The Tool Round

One tool call runs on the main thread. Several run in a pool, unless one is clarify (a question to the user), in which case they run one at a time. Results are written back in the model’s call order, not the order they finished. The next request depends on that order.

Four agent-level tools (todo, memory, session_search, delegate_task) are intercepted before the general dispatcher because they need the live agent (Chapter 7). The model cannot tell the difference.

Surfaces watch the turn through callbacks: progress, thinking, streaming, status. The CLI draws a spinner, the gateway posts a chat update, the editor updates its status bar. The loop never imports any UI.

Saving Is the Last Phase

When the turn finishes, new messages go to the session store under Chapter 3’s writer rules. Memory flushes only at a real session boundary such as /new, /reset, or /resume, not after idle time. The door renders the result. No surface calls the model a second time just to “format for Slack.”

Phase code is loaded at import and never hot-swapped mid-turn. New phase code means a restart.

The Trade-offs

  • More result types for callers to handle. Hermes keeps a display label for people and a machine reason for logs.
  • Notes can be skipped. If there is no safe place to put a notice, the model does not get it.
  • Interrupts lose partial output. That is the price of never saving a broken assistant message.

Apply This

Return how a turn stopped, not just that it stopped. Budgets, interrupts, billing, and compression failure are different outcomes.

Give each agent its own budget. Let the surface choose the cap.

Append notices to the unsaved tail. Never edit history the cache has already seen.

Abandon interrupted calls cleanly. Show the user a status. Do not show the model a half-finished message.

Never let a summary pose as the user. Restore the original request, or skip the call.

Chapter 6: The Prompt That Must Not Move

The Problem: Long Chats Are Expensive

Every model call resends the whole conversation: the system prompt, the tool list, and every message so far. In a long chat, that is a lot of tokens, again and again.

Providers soften this with prompt caching. If the start of a request matches a request they saw recently, they reuse that work and charge much less for it. The catch is that caching works on a prefix. The moment one byte near the start changes, everything after it is a cache miss and is billed at full price.

That creates a tension every agent faces. The system prompt wants to carry live information: the date, the user’s memory, which skills exist, what platform this is. But anything that changes near the start of the prompt destroys the cache. So where does each piece of information go?

The Options

  • Rebuild the prompt every call. Always fresh, always correct, and never cached. Long sessions get very expensive.
  • Build once and never change it. Cheap, but the model never learns about anything that changed mid-session.
  • Order by how often things change, freeze the prompt, and send changes another way. Stable parts first, changing parts last, and mid-session updates go on the current user message instead of the system prompt.

Hermes’s Choice: Three Tiers, Built Once

Hermes builds the system prompt once per session (in agent/system_prompt.py and agent/prompt_builder.py) and reuses it on every turn. The only rebuild is context compression (Chapter 15). That rule is the whole chapter.

The prompt has three tiers, ordered from “almost never changes” to “changes most”:

graph LR subgraph stable [Stable prefix] ID["Identity SOUL.md"] G["Tool and model guidance"] PIN["Pinned auto-loaded skills"] CODE["Coding brief, not the cwd"] end subgraph context [Context] SM["Caller system message"] FILES["Project context files"] WS["Frozen workspace snapshot"] HINT["Platform hint, after the snapshot"] end subgraph volatile [Volatile tail] SK["Skills index"] MEM["MEMORY and USER snapshots"] PLUG["Plugin sections"] TS["Profile line and date"] RT["Runtime environment block"] end stable --> context --> volatile

Stable. Identity comes from the profile’s SOUL.md, or a default (child agents use the default so they do not wear the parent’s persona). Then tool guidance, model-specific lines, pinned skills, and the coding brief. Guidance for tools this session does not have is left out.

Context. The caller’s optional system message, then project context files, then a snapshot of the git workspace. Hermes looks for context files in priority order and takes the first match: .hermes.md or HERMES.md up to the git root, then AGENTS.md, then CLAUDE.md, then .cursorrules. Long files are truncated. The workspace snapshot is taken once and pinned for the session, so a new commit does not change the prompt. It is dropped on reset. Platform hints (how to format for Telegram, Slack, and so on) come after the snapshot, and operators can add to them in config.yaml.

Volatile. The skills index comes first in this tier because skills change. Then the MEMORY.md and USER.md snapshots, any external memory provider’s block, plugin sections, the profile line, the date, and the runtime environment block last.

Two small details show the care. The date line holds the date, not a timestamp, so it stays identical all day. A full timestamp would break the cache on every build. And the profile path sits in the volatile tier, so two profiles on one machine can still share an identical stable prefix.

Where Changes Go Instead

Some things change mid-session. None of them touch the cached system prompt:

flowchart TD Change["Something changed mid-session"] --> Q{"What kind?"} Q -->|"skill index changed"| N["One-time note on the
current user message"] Q -->|"switched surface
(desktop → TUI)"| N Q -->|"external memory recall"| N Q -->|"memory tool wrote a fact"| D["Disk now, prompt at
next session or compression"] Q -->|"/model or /skills install --now"| R["Explicit rebuild:
user accepts a cold cache"] N --> Keep["Cached prefix survives"] D --> Keep

Per-call extras are applied at send time and never saved as the system prompt: an ephemeral system prompt, prefill messages, gateway overlays, recall from an external memory provider, and plugin context. Recall and plugin context land on the current user message.

The memory case surprises people. You tell the agent “remember this,” the fact is saved to disk, yet the system prompt still shows the old memory. That is correct. The tool result in the transcript tells this session about the write. The next session reads the file. Rewriting the system message in place would break the cache.

Slash commands that change the prompt wait for the next session. /skills install --now is the opt-in that accepts a cold cache. /model is the other explicit break.

Spending Cache Markers

Anthropic lets a request mark up to four breakpoints, places where the cache may be cut. Hermes spends them on purpose, and first removes any old markers, so a retry can never add a fifth.

flowchart LR B1["Breakpoint: static system prefix"] --> B2["Breakpoint: full system prompt"] B2 --> B3["Rolling: recent message"] B3 --> B4["Rolling: latest cacheable message"]

Cache lifetime is 5m or 1h. With auto, human-paced sessions get 1h and machine-paced ones (cron, subagents, batch, API) get 5m. Caching turns on for Claude models on routes that understand the markers: native Anthropic or OpenRouter.

Some cache misses cannot be avoided. A credential rotation or fallback to another account is a cold cache even if every byte matches, because the provider keys its cache by model and account. Hermes does not pretend otherwise.

The stock prompt is reviewed like code. CI renders the default system prompt and tool list for several surfaces and models, with the clock and paths pinned, and fails if the saved snapshot drifted. Moving one line of guidance between tiers shows up as a readable diff.

The Trade-offs

  • Memory looks stale mid-session. The fact is saved but the prompt shows the old snapshot until a rebuild.
  • Ordering rules constrain features. Every new prompt input must find a tier, and anything that changes often must go last or onto the user message.
  • Some changes cost a cold cache anyway. Model switches and credential rotation cannot be cached across.

The supported ways to change what the model reads are the inputs: SOUL.md, memory files, context files, skills, a system message, overlays, and platform hints. Editing the prompt builder is a product change, because its byte order is what keeps the cache working for everyone.

Apply This

Order the prompt from frozen to volatile. Put tenant names, paths, and dates last.

Send mid-session changes as notes on the current user message. And only when the change itself changes.

Pin anything you probe. Freeze a git snapshot for the session, and drop it on reset.

Spend cache markers deliberately. Strip old ones before adding new ones.

Review the stock prompt in CI. Snapshot the default product, not a developer’s home directory.

Chapter 7: Tools — Register, Gate, Dispatch

The Problem: Turning a Tool Call Into a Safe Function Call

A model cannot do anything by itself. It can only ask for a tool, by name, with some arguments. The agent has to turn that request into real work. That raises three questions every agent must answer:

  1. What tools exist? Someone has to keep the list, and it must match the code.
  2. Which tools can work right now? A Docker tool is useless if Docker is down. Showing it to the model invites failures.
  3. What happens between the request and the result? Bad arguments, safety checks, plugins that want to watch or object, and results too large to send back.

The tool list matters for cost too. Every tool’s description is sent with every model call, and it is part of the cached prefix from Chapter 6.

The Options

  • A hand-written central list. Clear, but it drifts from the code, and every new tool edits a shared file.
  • Self-registration. Each tool enrolls itself when imported. No central list to drift, but registration must be kept separate from availability.
  • Check availability on every call. Always accurate, but slow and flappy, and a list that changes from turn to turn breaks the cache.
  • Check availability with a short-lived cache. Fast and stable, at the cost of being a few seconds out of date.

Hermes’s Choice: Self-Registration, Cached Probes, One Pipeline

The pieces are tools/registry.py (the registry), model_tools.py (building the tool list and dispatching calls), and toolsets.py (named groups of tools).

A tool is a record

Each tool is a ToolEntry: a name, a toolset, the JSON schema the model sees, a handler, an optional check_fn, the environment variables it needs, an async flag, a result-size cap, and optional schema overrides. Those overrides run every time the tool list is built, so a description can show a live limit, such as delegation’s depth cap, without re-registering.

Discovery

Hermes walks the tools package, imports the modules that actually call register(), and caches the list. MCP servers are discovered next, then plugins. A plugin may not replace a built-in tool unless the operator opts in. A silent override would let a third-party package take over terminal.

Gating: is the backend reachable?

flowchart TD A["definitions requested"] --> B{"Toolset enabled?"} B -->|no| Z["omit"] B -->|yes| C{"check_fn cached fresh?"} C -->|hit| D["use cached bool"] C -->|miss| E["run probe"] E --> F{"success?"} F -->|yes| G["cache True"] F -->|no, inside grace| H["return last True, do not cache"] F -->|no, grace expired| I["cache False and omit"] G --> J["include schema"] H --> J

check_fn answers one question: can this process reach the backend right now? It does not answer “does this session want this tool?” Results are cached for about half a minute. A failure shortly after a success is forgiven once. Otherwise a docker version that times out under load could strip read_file from a child agent mid-task. A failure that lasts past that grace window is believed, and the tool disappears.

Which toolsets a session gets is a separate decision. Platform presets choose groups for the CLI, a chat app, or cron. An empty enabled list passed on purpose means “nothing,” not “everything.” AIAgent treats a missing list as “all toolsets,” so unattended surfaces must pass one explicitly.

Some schemas are rewritten when the list is built. execute_code lists only the tools this session can call. Browser tools shrink to match the active backend. delegate_task states its current depth and concurrency limits, so the model reads the policy before it calls. These rewrites happen when the list is built, never per call, because the list is part of the cached prefix.

The first step cleans up model mistakes: repairing malformed JSON, removing characters providers reject, and making tool-call ids consistent. Hooks that throw do not end the turn. The result is always a string, either the output or a JSON error the model can act on.

The approval gate (tools/approval.py) runs before the handler. A plugin’s pre-hook can also deny. A tool that shells out without going through the gate is a bug. Chapter 16 covers the gate in detail, with an interactive trace of this pipeline.

Async handlers need a bridge, and the bridge depends on the caller. The CLI uses a persistent event loop. The gateway, which already runs a loop, uses a throwaway thread. Worker threads keep a loop per thread. One bridge for all three would either deadlock the gateway or reconnect the CLI client on every call.

Each tool’s result is capped. A megabyte of logs becomes a truncated string the model can ask to narrow. Metrics and the UI see the tool name, duration, and a redacted preview. Only the transform hook may change the result.

The Footprint Ladder Is a Cache Policy

The ladder from Chapter 1 (extend a tool, then CLI plus skill, then a gated tool, then plugin, then MCP, then a new core tool) is about cost. A core tool’s schema is in every request of every session with that toolset. A skill costs one index line until it is loaded (Chapter 14). A plugin costs only the profiles that install it.

Tools change at human speed. Discovery is cached on disk, and invalidate_check_fn_cache is for the operator who just installed Docker. A running process does not reload the registry mid-turn. Restart instead.

The Trade-offs

  • Availability can lag. A backend that just died may stay listed for a short window.
  • Rewrites must be stable. Schemas change only when the list is rebuilt, never between calls of one turn.
  • Intercepts are special paths. They are worth it because they keep agent state out of global code.

Apply This

Cache availability probes with a short grace period. Tens of seconds, not tens of minutes.

Rewrite schemas once, when the list is built. Put the limits you enforce into the description.

Return strings, not exceptions, across the tool boundary. Include a stable error key. An empty string looks like success.

Intercept tools that need the conversation, and stub the registry path.

Treat a new core tool as a tax on every request. Climb the ladder first.

Chapter 8: Running Somewhere Other Than the Laptop

The Problem: Where Do Tools Actually Run?

When a model asks to “run the tests” or “open this page,” something has to execute that request on a real machine. For a quick demo, that machine is your laptop. For a real agent, it often should not be. You may want commands to run in a container for safety, on a remote GPU box for power, or in a hosted sandbox so nothing touches your files. You may want browsing in the cloud, except for localhost, which only your laptop can see.

So every agent must decide how tools relate to places. Does the model need to know where its commands run? And who chooses?

The Options

  • One tool per place. docker_exec, ssh_exec, modal_exec, and so on. The model must learn your infrastructure, and every tool adds to every request’s size (Chapter 7).
  • One tool, place chosen by config. The model asks to “run a command.” The operator decides where, per session or profile. The tool list stays short, but each backend must honestly report what it can and cannot do.

Hermes’s Choice: Stable Names, Swappable Backends

The model sees terminal, browser_*, web_search, and web_extract. Behind each name is a family of backends, chosen by configuration when the agent is built.

Placement changes per session or per profile, which is safe for the prompt cache. It never changes mid-turn.

Terminal: One Interface, Seven Places

tools/environments/base.py defines BaseEnvironment. terminal_tool picks an implementation from TERMINAL_ENV.

Each backend knows how to start a session, run a command, stream output, copy files, and clean up. The model only calls terminal. Each toolset’s check_fn probes the chosen backend: is the Docker socket there, are Modal credentials loaded, does the SSH host resolve? A failed probe means the tool is absent, not a shell error halfway through a plan.

Local is the default and carries the most policy. It filters the environment so the agent’s own variables do not leak into the user’s command. Remote backends have a remote workspace instead of a local folder, and file sync is explicit. Assuming the remote disk matches the laptop is how a patch “succeeds” in the transcript but never reaches the repo.

Background processes live in a process registry with a limited output buffer. That is how terminal supports long-running servers and later reads of their output. A backend that cannot do this must say so, rather than pretend and produce endless “session not found” retries.

Parallel tool calls follow Chapter 5’s rules. Two parallel terminal calls in one folder can interleave patches. Backends that cannot run concurrently must declare it. For child agents, Chapter 12 gives each worker its own directory instead.

Cleanup runs at the end of a task and when the process exits. Each closer runs even if an earlier one failed, so a sandbox is not leaked because the browser closer threw first. Ignoring errors is right at cleanup and wrong when running a command. A gateway lives for days, and a forgotten sandbox is a bill.

Browsers: A Second Family

The browser tools are a facade (tools/browser_tool.py) with siblings for CDP, cloud providers, snapshots, sessions, vision, and lifecycle. The backends are:

  • Local headless Chromium, driven by Hermes’s own tools or a Browser Use harness.
  • Cloud: Browser Use, Browserbase, or Firecrawl, chosen by browser.cloud_provider.
  • Camofox: a local anti-detection server reached over REST. It has no CDP, so the raw browser_cdp tool is not offered with it.
  • Lightpanda: a headless engine Hermes can start, with a Chrome fallback for actions it does not support yet.
  • CDP attach (browser.cdp_url, /browser connect) latches onto an already-running Chrome, Brave, Chromium, or Edge.

The subtle part is hybrid routing. A cloud browser cannot open your laptop’s localhost. With browser.auto_local_for_private_urls on, private and loopback addresses go to a local sidecar session, while public URLs stay in the cloud. It is still the same browser_navigate tool. It just picks a different session.

DNS failures are not treated as private. A local proxy’s fake-ip range is excluded, so a proxy that answers for the whole internet does not drag every URL onto the sidecar.

Sessions are reused across steps, so a ten-step scrape does not create ten browsers. Separate vision and snapshot tools exist because “what is on this page” is a different job from “click the button,” and models do better with an accessibility tree or a screenshot than a raw page dump.

Web Search: A Registry of Vendors

web_search and web_extract sit on tools/web_tools.py and a vendor registry. If nothing is configured, Hermes auto-detects available vendors, with keyed vendors before keyless ones, and Firecrawl as the default.

What the Sandbox Can See

The tool worker strips the process environment and adds back only what the backend needs. A skill can ask for extra variables in its frontmatter. The default is never “inherit everything,” because everything includes the agent’s own API keys. Chapter 16 explains the threat.

The Trade-offs

  • The model cannot choose placement. That is on purpose, but it means config must be right before the session starts.
  • Backends must be honest. A backend that cannot run in parallel or keep a process alive has to say so, or the model will plan on things that fail.
  • Explicit file sync. Remote work is safer, but someone must move files deliberately.

Apply This

Hide placement behind one interface and a per-session selector. The model calls run, browse, search. Config picks the place.

Probe once, then hide the tool. Reuse Chapter 7’s cache. Do not add a second one in the backend.

Route by capability inside one tool. Private URLs to a local browser, public ones to the cloud, same tool name.

Fail a stored vendor choice loudly. Autodetect is only for unconfigured installs.

Keep cleanup going after errors, and keep command execution strict. Do not reuse the “never raise” helper around real work.

Part III — Many Surfaces, One Core

Chapter 9: The Gateway

The Problem: A Door That Stays Open

A terminal session ends when you close the window. A chat-app agent cannot work that way. Messages arrive at any hour, from many chats, on several platforms. Someone has to stay awake, accept those messages, decide who is allowed to talk to the agent, keep each conversation separate, and deliver replies back to the right place.

That process also has to answer the hard questions from Chapter 3. Who writes the transcript? What happens to a message that was being handled when the process crashed? Who resolves a stuck turn?

The Options

  • One bot per platform. A Telegram bot and a Slack bot, each with its own session store. Simple, until they disagree about what “the conversation” is.
  • A thin relay to a shared database. Each adapter writes directly. Easy, but now there are many writers, and a crash can replay work.
  • One long-running runner that owns sessions. Adapters only translate platform events into messages. The runner authorizes, queues, runs the turn, and delivers. It is more central, but there is one writer and one queue.

Hermes’s Choice: The Gateway Is the Session Authority

The gateway is a long-running process. gateway/run.py holds the GatewayRunner facade, with sibling modules for startup, adapters, inbound handling, the turn, busy policy, notifications, and shutdown. Platform adapters bring messages in. One AIAgent runs per conversation. Replies go back out. The same process runs the cron clock and writes the session ledger.

sequenceDiagram participant P as Platform participant A as Adapter participant R as GatewayRunner participant S as Session authority participant Agent as AIAgent P->>A: webhook or socket event A->>R: MessageEvent R->>R: authorize sender R->>S: resolve session key, admit input S->>Agent: history + run_conversation Agent-->>R: final text and tool trail R->>A: deliver reply A->>P: platform message

Adapters End at a Message

Platforms are plugins under plugins/platforms/<name>/: Telegram, Discord, Slack, WhatsApp, Matrix, email, SMS, and more. A few special transports (the API server, webhooks, Signal) sit under gateway/platforms/. Adding a platform means writing an adapter, not editing the core.

An adapter owes the runner text (and maybe media), a chat id, a user id, and enough thread information to build a session key. Authorization happens before an agent exists. An unauthorized sender gets no prompt, no tool call, and no session row.

Session keys combine platform, chat, thread, and the profile that owns them, so two Telegram groups never share a transcript. Replies can go back in place, to a configured home channel, or to an explicit platform:chat address, the same address cron uses. Cron output is not copied into a chat transcript. That would break role order and mix a job’s voice into a human conversation.

Images are staged in the profile’s cache and copied into an immutable store when the message is admitted, so a later cleanup cannot change what the turn sees.

The Runner Owns the Queue

Every input enters a durable first-in, first-out queue before the model runs (Chapter 3’s session_admissions).

stateDiagram-v2 [*] --> queued queued --> started: owner begins the turn started --> done: settled started --> unknown: owner died unknown --> interrupted: operator resolves interrupted --> queued: followers may run queued --> dropped: auth or route gone at recovery

If the owning process dies mid-turn, that input becomes unknown and is not replayed. Later inputs wait. Someone resolves it from the desktop, the CLI, or /discard, and the session continues. Chat users are told once that the conversation is paused, and later messages queue quietly. /reset moves the chat to a new session.

On start-up, inputs that never started are recovered only after adapters reconnect, and the sender’s permission is checked again. Each served profile has its own authority and its own state.db (Chapter 17). A shared queue would run user B’s prompt with user A’s credentials.

Local clients (desktop, TUI, hermes chat) use the same authority. hermes gateway ensure finds or starts the profile’s runtime and refuses to start a second one on top of a service it does not recognize. A timeout is not permission to launch a rival writer.

Busy Sessions: Interrupt, Steer, or Queue

What happens when a message arrives while a turn is running? Each live session has a busy policy:

Steer and redirect must name the current turn, so a stale client cannot cancel a newer one. The key distinction: a correction is not a new message, and a new message is not a correction.

What Else Lives in the Gateway

  • Lifecycle hooks (gateway/hooks.py) see messages and sessions, separate from tool hooks in Chapter 7.
  • Cron shares the process so jobs can deliver through adapters that are already connected (Chapter 10).
  • Slash commands and pairing live here because a message may not need the model at all. /help does not deserve a tool loop. A skill invoked by slash command becomes a user message, so the cached prompt is untouched.
  • Progress is shown through callbacks and delivery. The model still speaks once.
  • Process locks in gateway/status.py stop two gateways for one profile from both claiming the adapters.

hermes gateway run works with no platforms configured, which gives desktop-only users a session authority for cron and local clients. Installing it as an OS service is opt-in.

Three Separate Gates

The gateway keeps three kinds of permission apart:

graph LR C["Connection auth
local socket ticket"] --- U["User auth
allowlist or DM pairing"] --- T["Tool auth

Local desktop and TUI connections use short-lived, single-purpose tickets from a same-user control socket. A ticket for one profile or protocol does not work for another. Senders on chat platforms are approved by allowlist or pairing (Chapter 16). Dangerous commands still need approval. None of these implies the others.

Credentials are frozen per session. On restart, inline keys are re-read only if the home, path, and fingerprint still match. A missing or rotated key fails closed, and a new session is how you adopt a new key.

Clarify questions and approvals have their own waiters. The first answer wins. Neither ever times out into “yes.”

Hosted Rooms: Peer Agents Across Gateways

Chapter 12 covers a parent starting a child for a subtask. Hosted rooms are different: several peer agents, each living on its own gateway install, share one logical group without merging their private transcripts.

events + membership"] end subgraph peer["Peer gateway"] M["Member agent
own profile, own state.db"] end Desktop["Desktop may invite"] -.->|"not the courier"| H H -->|"scoped room grant"| M M -->|"dispatch + verify grant"| H M -->|"hidden Group session

Receive path. A peer turn arrives as an API payload with hosted_room_dispatch (and an execution policy). The target gateway checks a room grant (HMAC, scoped, versioned — v2 is not wire-compatible with the unpublished v1 draft). Desktop may bootstrap an invitation, but it is never the issuer or the runtime courier: the target gateway verifies the grant and the task coordinates before any model or tool work runs.

What is shared. The room has an authority gateway, membership, and a sequenced event log (hosted_room_events). Grants and catalogs describe who may dispatch and which capabilities are in play. Execution policy can be bound for the turn so a peer cannot silently widen what the room allowed.

What stays private. Each member runs under its own profile and state.db. Dispatch creates or reuses a canonical hidden group session (session_id = room_ + hash of install, room, …) titled Group: <room_id>. That session’s transcript is not the home gateway’s chat history, and it is not shared byte-for-byte with other members. Profile fences on gateway recovery keep a sibling profile in a shared legacy store from stamping its routing identity onto this profile’s orphaned rows.

Failure modes that matter. Wrong or expired grant → reject. Room execution policy or capability catalog changed under you → typed errors, not a silent continue. Mixed gateways that cannot speak protocol v2 fall back to Desktop-driven rooms rather than accept a weaker token.

This is Hermes’s answer to “several agents in one group”: shared room authority + private member sessions, with cryptographic admission at the edge.

The Trade-offs

  • The gateway is central. Local clients depend on it, so it must be easy to start and hard to duplicate.
  • Crashes pause conversations. Safer than replay, but a person has to resolve them.
  • Strict isolation adds machinery. Per-profile queues, tickets, and frozen credentials all cost code. They prevent the worst bug: one user’s turn running with another user’s keys.

Apply This

Translate every platform into one event, then share one runner. Adapters never leak SDK types into the agent.

Admit durably, and freeze on owner loss. “Unknown” stays unknown until someone resolves it.

Keep scheduled output out of chat transcripts.

Separate connection auth, user auth, and tool auth. Never one trusted flag.

Fail closed when “ensure the service” is unsure. A timeout means “still starting,” not “mine to replace.”

Chapter 10: Cron Is an Agent Job

The Problem: Work With No One Watching

People want agents to do things on a schedule: a morning briefing, a weekly report, a check every two hours. Scheduled work is different from a chat in two important ways.

First, no one is there to answer questions. If the agent stops to ask “which folder did you mean?”, it waits forever.

Second, each run should start clean. If today’s run remembers yesterday’s tool output, it may act on a stale plan. Over weeks, the job drifts.

So a scheduler for agents has to decide: what does each run remember, what is it allowed to do, and where does its output go?

The Options

  • A shell crontab that calls the model. Simple, but it lives outside the agent: no skills, no shared safety rules, no delivery to chat.
  • One long-running session that a timer pokes. The agent keeps context, but it piles up stale history and can ask questions no one will answer.
  • A fresh agent per run, with a closed toolset. Each run starts from durable facts only, cannot ask questions, and delivers to an explicit target. More setup per job, but runs are predictable.

Hermes’s Choice: A Fresh Agent Per Run

A Hermes cron job is a prompt, a schedule, optional skills, and a delivery target. When it fires, the scheduler builds a fresh AIAgent and runs the same turn a person would get. Long-term memory loads. The previous run’s transcript does not.

cron/jobs.py stores jobs, cron/scheduler.py runs them, tools/cronjob_tools.py exposes the cronjob_manage tool to the model, and hermes cron is the CLI.

flowchart TD Tick["Gateway tick"] --> Due{"Job due and enabled?"} Due -->|no| Tick Due -->|yes| Scan["Scan assembled prompt and skill bodies"] Scan -->|blocked| Fail["Deliver a blocked status"] Scan -->|ok| Agent["Fresh AIAgent, no prior run history"] Agent --> Turn["run_conversation"] Turn --> Del["Deliver to origin or target"] Del --> Save["Update next_run and last_status"] Save --> Tick

The Job and the Clock

Jobs live in the profile at cron/jobs.json. Each record holds a name, a prompt, a schedule, attached skills, a delivery target, repeat counts, state, run times, last status, optional model and provider, and an optional script. Schedules come in four kinds: a delay (30m), an interval (every 2h), a standard five-field cron expression, or a one-time timestamp.

stateDiagram-v2 [*] --> scheduled scheduled --> running: due running --> scheduled: interval or cron expression, repeats left running --> disabled: one-shot succeeded or repeats used up scheduled --> paused: pause paused --> scheduled: resume disabled --> [*]

The gateway owns the clock so jobs can deliver through adapters that are already connected (Chapter 9). Two clocks for one profile would be a bug. A standalone scheduler steps aside when it sees a newer gateway for that profile. A running job holds a claim with a time limit that it keeps refreshing, so a slow job is not stolen and a dead owner does not hold the claim forever.

What the Fresh Agent Cannot Do

messaging and clarify are always off. The cronjob tool is off unless the operator enables agent scheduling. That flag prevents loops, a job that schedules jobs, rather than acting as a security boundary. The profile’s disabled toolsets apply on top, so a job cannot widen past the operator’s limits.

The enabled list has one sharp edge. A job’s explicit empty list means “no tools.” It once fell through to “all tools” because an empty list looked unset, and a locked-down job silently got every tool back. AIAgent treats a missing list as everything, so cron must never pass a missing one. If the config cannot be read, resolution fails closed. Enabled MCP servers are merged in unless the job says no_mcp.

Skills, Scanning, Memory, Delivery

Skills. The job names skills in order. At fire time, each skill’s full text is injected, then the prompt runs as the task. This is the right way to grow a scheduled workflow. A two-thousand-word procedure pasted into the prompt works once and rots. A skill is reviewed, scanned, and reusable (Chapter 14).

Scanning. The assembled prompt, skill bodies included, is scanned for injection before the agent starts. Scanning only the prompt field at creation would miss a compromised skill. A hit delivers “job blocked,” not a partial run.

Memory. MEMORY.md and USER.md still load, because they hold facts about the user, not the last run. The prompt must be self-contained: “continue what we were doing” makes no sense with no “we.” Session search can look up old sessions if allowed, but it is better to write jobs that do not need it.

Delivery. Output goes to the origin chat or an explicit platform:id, or a home channel. It is not copied into that chat’s transcript (Chapter 9). A failed run delivers the failure, because a silent failure can kill a daily briefing for a month.

Routing. A job that pins provider and model does not use the fallback chain. An unpinned job does (Chapter 4). A script job is a different kind of job, and does not get to skip the scanner when it still calls the agent.

Unattended Means Approval Is a Choice

A job cannot show a button and wait. So “ask the user” cannot be the approval policy. The safe default is deny, or a policy the operator chose deliberately. YOLO and approvals.mode: off work as anywhere else, but “this is cron” does not imply them. The hardline blocklist still applies (Chapter 16).

Work that needs a person goes back to a session that has one. The job drafts, delivers, and stops. A person continues in the chat if they want changes.

Budgets still apply. Iteration caps come from the same agent.max_turns family as the CLI unless the job sets tighter ones, and the run-budget wrap-up from Chapter 5 helps for jobs that fan out. A short report that says it hit a cap beats a runaway research loop at 9 a.m.

Kanban dispatch is a sibling: another background consumer of an agent, with its own boards and states. The lesson that transfers is “background work is an agent with a closed toolset and an explicit target,” not “every background system is cron.”

The Trade-offs

  • No continuity between runs. Jobs must be written to stand alone.
  • No questions. Anything ambiguous must be settled in the prompt or a skill.
  • Approval is stricter. Risky jobs need a deliberate operator policy, not a quiet default.

Apply This

Run scheduled work in a fresh session with durable facts only. Keep memory. Drop transcripts.

Remove interactive tools from unattended runs. No clarify, no ad-hoc sends, no self-scheduling unless opted in.

Treat an explicit empty list as empty. None means default. [] means nothing.

Scan the fully assembled prompt. Skill bodies count.

Deliver to a side channel, not into a person’s transcript.

Chapter 11: The Editor Session

The Problem: The Agent Inside Your Editor

Developers want the agent where they work: inside VS Code, Zed, or JetBrains. An editor brings its own expectations. It sends screenshots and file attachments, not just text. It wants to branch conversations, cancel them, and show permission dialogs in its own UI. It knows which folder is open.

The temptation is to build a special “editor agent” that understands all of this. That is exactly the second brain Chapter 1 warned against. So the question is: how do you serve an editor’s richer needs without forking the agent?

The Options

  • A separate editor agent. Tailored to the IDE, with its own tools and storage. It drifts from the main agent, and its conversations are invisible to the rest of the system.
  • A thin adapter. Translate the editor’s protocol into things the core already understands: user messages, sessions, interrupts, and approval callbacks. Less tailored, but one agent.

Hermes’s Choice: A Thin Adapter Over ACP

acp_adapter/ speaks the Agent Client Protocol (ACP), JSON-RPC over stdio, and calls the same AIAgent. There is no editor loop. There are three parts: a session manager, a content converter, and a permission bridge.

VS Code, Zed, JetBrains"] -->|"ACP over stdio"| AD["acp_adapter"] AD --> SM["Session manager
create, load, fork, cancel"] AD --> CC["Content converter
blocks → user content"] AD --> PB["Permission bridge

under the profile home"]

Sessions Like Any Other

The session manager tracks live sessions: id, agent, working directory, model, history, and a cancel flag. It can create, load, fork, list, and remove them. Forking matters because editors branch conversations casually. A fork is still a normal session with a parent.

ACP sessions are saved in the profile’s state.db and appear in session_search. Restarting the editor does not create a private transcript the CLI cannot resume. When the session authority is attached, input goes through it, following Chapter 3’s single-writer rule.

Cancel is the editor’s /stop. It sets the same interrupt event the model call already waits on (Chapter 5). The adapter does not kill the process, which would skip sandbox cleanup and the session-end flush.

Changing folders is a session update, not a prompt edit. The workspace snapshot from Chapter 6 is pinned per working directory. Adding “the user opened another folder” to the system prompt on every focus change would break the cache with every click.

Editor Content Becomes User Content

acp_adapter/content.py converts the editor’s prompt blocks:

If every part is text, the result is a plain string, so “hello” and “/help” stay ordinary. If any part is an image, the result is a multipart message that the existing vision path can send. Nothing is dropped silently. A screenshot that cannot be read becomes a note saying so.

When ACP goes through the gateway, images are staged in the profile cache and sent as attachments. Remote image URLs are fetched through the gateway’s SSRF-guarded fetcher. Admission stores a hash-checked copy, so later changes to the staging file cannot change the turn. This is Chapter 9’s media path, reused.

(Older internal notes said non-text blocks were ignored. The current converter handles them.)

The Permission Bridge Is Temporary

acp_adapter/permissions.py maps editor choices onto Hermes’s approval vocabulary. “Allow once,” “allow always,” and “reject” become once, always, and deny. Timeouts and disconnects deny. A hanging editor is not permission.

The bridge installs its callback on the terminal tool for one prompt and restores the previous one afterward, even on failure or cancel. That restore is the whole safety property. A leftover editor handler on a process-wide tool would answer the next CLI turn with a dialog that no longer exists.

An editor user is present, so the bridge asks. A cron job has no user, so it does not. Neither should borrow the other’s default.

Model changes from the editor go through the same /model pipeline as the CLI, with the same cache break. Forks inherit the parent’s route.

What the Editor Must Not Become

  • No editor-only tools. File tools already edit files. An editor_apply_patch tool would be a second patch implementation with a second approval story.
  • No network server. The stdio adapter trusts “the user who launched the editor.” Exposing it on a network port would be a different product needing Chapter 9’s gates.
  • No live buffer watching. Hermes gets the prompt the client chooses to send, plus the working directory. Subscribing to every keystroke would keep rebuilding context and destroy the cached prefix. To show the model a file, send it or let the model read it.

The Trade-offs

  • Less editor magic. No special IDE tools, so rich diffs are the client’s job.
  • Local trust only. ACP relies on the local user boundary, which is weaker than pairing.
  • Folder changes are not instant. The model sees a new folder only when the prompt is rebuilt.

Apply This

Translate foreign content into the user message you already have. And never drop unknown blocks silently.

Borrow the session store. Editor conversations are sessions like any other.

Install interactive callbacks for one prompt, and always restore them. Use a scope guard that also runs on cancel.

Deny on timeout, at human pace. Do not reuse cron’s machine-paced timing for an IDE.

Refuse a second tool surface for “editor things.” If the agent runs it, the agent gates it.

Chapter 12: Delegation

The Problem: Splitting Work Without Losing Control

Some tasks are too big for one conversation. “Review these ten services” or “read these papers and summarize each” go better if the agent can hand pieces to helpers that work in parallel and report back.

Helpers raise hard questions. How many may run at once? Can a helper spawn its own helpers? Whose budget do they spend? Which model and keys do they use? Who approves a dangerous command a helper wants to run, when no one is watching its thread? Get these wrong and you get an exponential bill, a frozen UI, or a helper quietly running on a different model.

The Options

  • A function call with a hidden prompt. Cheap, but it skips everything the real turn does: compression, interrupts, provider handling.
  • A separate orchestration product. Swarms and mailboxes. Powerful, but a whole second runtime to secure and pay for.
  • The same agent, smaller. A child is another AIAgent with its own transcript, its own budget, and narrowed tools, under clear caps.

Hermes’s Choice: A Child Is Another AIAgent

delegate_task is one of the four agent-level intercepts from Chapter 7. A child is a full AIAgent with its own transcript, its own iteration budget, and a toolset narrowed on purpose. There is no swarm mailbox. There is a depth cap, a concurrency cap, and a default of “children do not ask the user.” The settings live in tools/delegate_tool_config.py.

graph TD P["Parent depth 0
budget: agent.max_turns"] --> C1["Child depth 1
own budget, default 50"] P --> C2["Child depth 1"] C1 -.-> G["Grandchild only if max_spawn_depth > 1"]

Flat Unless You Pay for Depth

The parent is depth 0. delegation.max_spawn_depth defaults to 1: the parent can spawn children, and children are leaves. Deeper trees are allowed by config, with a warning that each level multiplies cost. Setting delegation.orchestrator_enabled to false makes every child a leaf regardless.

Budgets add up. Each child has its own IterationBudget, default delegation.max_iterations = 50, while the CLI parent uses agent.max_turns (500). A parent cannot hide unlimited work inside children, and a child cannot eat the parent’s remaining turns.

Concurrency defaults to 10 (delegation.max_concurrent_children), with a warning above that. At capacity, a new background task is rejected, not queued, and the caller runs it synchronously. A queue inside the tool would be a hidden backlog the model keeps filling. One-shot sessions have a separate total, delegation.oneshot_max_children, default 2.

No stopwatch by default. Slow models and long reviews were being killed by timers. delegation.child_timeout_seconds opts back in, and it measures inactivity, not age. The clock resets on each completed call or activity tick, so a frozen child is caught but a child waiting on a slow answer is not.

What the Child Inherits

(one source)"| Child["Child agent"] Parent -->|"capabilities, only if the

Route. The child should call the same endpoint the parent is actually using. The parent’s stored URL and key can lag behind the live client, for example after a fallback. Mixing a live URL with a stale key means an instant 401. So the child takes both from the live client.

Capabilities. Trust decisions tied to a provider and endpoint are inherited only if the child stays on the parent’s exact route. Any provider or URL override starts from deny.

Fallback chains are not inherited. A child that silently switched models would hand the parent results it cannot read as a failure. Pass a chain explicitly if you want one.

Tools narrow. delegate_task’s description states the current limits, so the model knows them in advance. A leaf loses delegate_task itself. A leaf that can still spawn is not a leaf.

Approvals. Worker threads do not inherit the CLI’s prompt, because falling back to input() on a background thread would freeze the UI. Each worker gets an explicit callback: deny, unless delegation.subagent_auto_approve is on, in which case it answers “once” and logs it. In the gateway, children use the per-session approval queue. The hardline blocklist still applies (Chapter 16).

Workspaces. With delegation.worktree_isolation on (default off), each child gets its own git worktree from the parent’s HEAD, so parallel children do not share files. It works only for git on the local backend, and is ignored elsewhere rather than faked.

Results. By default the parent gets one combined message when the batch finishes. With delegation.independent_completions, it gets one per child as each returns.

Background Review Is a Different Thing

After a user turn, Hermes can run a review fork. It is related machinery with a different contract.

flowchart TD T["User turn ends"] --> Q{"Review deferred?"} Q -->|local runtime busy| Later["Idle queue"] Q -->|idle| Fork["Fork with own token budget"] Fork --> Mem["May write memory or skills"] Fork --> DB{"Persistence disabled?"} DB -->|yes| Drop["Do not touch the user session"] DB -->|no| Own["Own session row"]

A review fork has its own input-token budget. It waits if it would compete with a local model the user is using. It can have persistence turned off, so its turn is never flushed into the user’s real session.

An async_delegations table in state.db lets the parent remember background children across a gateway restart. It is not a second transcript. Results still reach the parent as ordinary tool results.

Why the Default Tree Is Flat

A tree of agents is an exponential bill with linked failures. The parent pays for its own turns, each child’s full prompt, and reading the summaries. Children do not share a cache unless someone deliberately gives them an identical prefix. Hermes offers a cap you can explain in one sentence: “this agent can spawn helpers, and those helpers do not spawn.”

Child transcripts are real sessions linked to the parent. Search can find them and compression can run inside a long child. Deleting them is a user decision, not cleanup. Browsers and sandboxes, which are processes, are still torn down.

The Trade-offs

  • Flat by default. Some tasks would benefit from depth, and you must opt in.
  • Children rarely get approvals. Deny-by-default is safe but can stall risky subtasks.
  • No shared cache. Each child pays for its own prompt.

Apply This

Make a child the same runtime with a smaller budget. Do not share the parent’s counter.

Default the tree to one level. Enforce the cap in the tool, and state it in the schema.

Take the child’s route from one live source, and drop capabilities if the route changes.

Give worker threads an explicit approval callback. Deny is recoverable. Allow is a side effect.

Reject extra background work at the cap, and say so. The error should read “at capacity.”

Part IV — What Survives the Session

Chapter 13: Memory, Recall, and the User Model

The Problem: Remembering Across Sessions

A model forgets everything when the conversation ends. For a personal agent, that is a serious flaw. Users expect it to remember their timezone, their test command, and what they discussed last week.

There are two naive fixes. Keep everything and stuff it into the prompt: expensive, slow, and full of noise. Or keep a small notes file: cheap, but the agent cannot answer “what exactly did we decide last Tuesday?”

A memory system also runs into Chapter 6. The system prompt is frozen for the session, so how does a newly saved fact reach the model? And in a gateway shared with other people, how do you stop a stranger’s message from being saved as the owner’s “preference”?

The Options

  • One big memory. Every past chat summarized into the prompt. Simple, but it grows without limit and mixes facts with chatter.
  • Only search. Nothing curated, just full-text search over history. Accurate about what was said, but nothing tells the model what matters.
  • Separate stores for separate questions. A small curated file for facts, a bounded user profile, and search for evidence. More concepts, but each one is easy to reason about.

Hermes’s Choice: Three Stores, Plus One Optional Provider

Hermes has three built-in stores, each answering a different question:

  • MEMORY.md: the agent’s notes, facts that hold in every session.
  • USER.md: a bounded profile of the person.
  • Session search: full-text recall over the session database (Chapter 3), for “what did we actually say?”

Beside them, at most one external memory provider can run as a plugin.

Skills (Chapter 14) are procedures, not a fourth memory. The prompt tells the model: steps belong in skills, and memory is for the few facts that are always true.

graph TD Q1["Is this always true about the user or setup?"] --> M["MEMORY.md / USER.md
small, curated, in the prompt snapshot"] Q2["What exactly was said before?"] --> S["session_search
FTS over state.db"] Q3["How do I do this task?"] --> K["Skills
Chapter 14"] Q4["Extra recall from a vendor?"] --> P["One external provider
beside the files"]

The Built-in Files Are Always On

MemoryStore enforces character budgets: about 2200 characters for memory and 1375 for the user profile by default (memory_char_limit, user_char_limit). Entries are meant to be short. A diary would be truncated into uselessness and would bloat every future prompt.

The memory tool is an agent-level intercept (Chapter 7). It can add, replace, and remove entries. Replace matches a substring, so one entry can be edited in place. Duplicates are refused. When the file is full, the tool returns an error asking the model to consolidate, rather than silently dropping old facts. A scanner checks writes for obvious injection and exfiltration patterns. memory.write_approval can require approval for every write. The default is to write freely. Turning the gate on is how a profile shared with other people stops the model from saving a stranger’s instruction.

flowchart TD T["Model calls memory"] --> I["Agent intercept"] I --> B{"Within char budget?"} B -->|no| E["Error: consolidate"] B -->|yes| S{"Scanner and approval"} S -->|deny| E2["Error to the model"] S -->|allow| D["Write MEMORY.md or USER.md"] D --> N["Tool result in this transcript"] D -.-> P["System prompt unchanged until rebuild"]

The prompt holds a snapshot taken when it was built. The disk changes immediately. The cached prompt does not. This turn sees the tool result. The next session sees the file. Compression’s rebuild also reloads from disk, so a long session catches up without /new. Users sometimes read this lag as “I told it to remember and it forgot.” It is the cache rule at work.

Memory is flushed at real session boundaries (/new, /reset, /resume), not after idle time or at midnight. If a cached agent is evicted to save resources, its transcript is committed to providers first, and the conversation stays open.

A background review can scan a finished session and propose memory updates, using an auxiliary model with its own token cap (auxiliary.background_review). On a local GPU it waits while the user is active. Proposed skill writes go through Chapter 14’s gate.

Good entries are specific: a timezone, a test command, a lesson with a file path. “User likes quality” is not a memory. The budget teaches the difference.

Session Search Is Evidence, Not Memory

session_search queries the full-text indexes from Chapter 3, with trigram and CJK support so the gateway’s real languages work. It is an intercept because it needs this agent’s database.

Memory is a decision: we chose to keep this fact. Search is evidence: someone said this, here, at this time. Evidence can be outdated or out of context. When the user says “like last time,” the model should search before asking them to repeat themselves. When the user says “I always want pytest,” the model should write memory.

Search results are ordinary tool output. They age in the transcript and can be pruned by compression, but the database is untouched, so you can always search again. That is why search may be large while memory must stay small.

One External Provider

MemoryProvider (agent/memory_provider.py) is the plugin interface. memory.provider selects one external provider. Empty, default, builtin, or none mean built-in only. The provider runs beside MEMORY.md, never instead of it. The files remain the record an operator can read with a pager.

graph TD Turn["Turn start"] --> Triv{"Trivial user text?"} Triv -->|yes| Skip["Skip prefetch"] Triv -->|no| Pre["Provider prefetch, bounded"] Pre --> Note["Inject into the user turn, not the cached system prompt"] Files["MEMORY.md + USER.md snapshot"] --> Sys["Volatile tier at build only"] Turn --> Sys

MemoryManager runs the provider’s lifecycle: start-up, a prompt block, per-turn prefetch and sync, tool calls, and shutdown. Prefetch is skipped for trivial replies like “yes” or “thanks,” has a timeout, and drops a stalled provider instead of stalling the user. Live recall lands on the current user message, not the cached system prompt (Chapter 6).

Provider tools (Honcho’s honcho_search, for example) go through MemoryManager.handle_tool_call. Only one provider is active, so two plugins can never race to register search. Context sent back into a prompt is scrubbed of secrets and URL credentials and trimmed if very long.

Background threads copy the caller’s profile context, through a helper called spawn_context_thread. A thread that started with empty context would land on the default profile, which is the Chapter 2 bug in a new form.

Memory Leaves Before the Middle Does

Before compression (Chapter 15) drops the middle of a conversation, providers get an on_pre_compress checkpoint and the built-in files are flushed. Version 1 of the hook is best-effort. Version 2 is opt-in and fail-closed: if a v2 provider fails, compression does not pretend the checkpoint happened. The order is the feature. Summarizing first would mean the provider only ever sees the summary.

Each profile has its own memory. A new profile does not inherit another’s MEMORY.md or Honcho peer.

The Trade-offs

  • Saved facts appear “late.” The snapshot updates at the next session or compression.
  • Small budgets force curation. Some useful detail will not fit, and must go to search or a skill.
  • One provider only. You cannot stack vendors, by design.

Apply This

Split curated facts from literal recall. A short file the model always sees, plus search over the real history.

Snapshot memory into the prompt, and put live recall on the user message. Tell the user when a saved fact becomes visible.

Flush at session boundaries, not on idle.

Run at most one external provider, beside the files. The files are the audit log.

Copy tenant context into every background memory thread. Bind first, then run.

Chapter 14: Skills the Agent Can Grow

The Problem: Teaching an Agent Procedures

Facts are not enough. An agent also needs to know how: how this repo runs its tests, how this user likes pull requests, how to structure a daily briefing. These procedures can be long. Most of them are irrelevant to any given conversation.

Putting every procedure in the system prompt would make every request huge. Writing them as code makes each one a software release. And if the agent can write its own procedures, which is the point of a learning agent, someone has to decide what it may save, because a procedure is instructions the model will obey.

The Options

  • Everything in the prompt. Always available, always paid for.
  • Plugins. Powerful, since a plugin can run Python and register tools. But every procedure becomes code to review, and every core tool taxes every request (Chapter 7).
  • Documents loaded on demand. A short index line is always present, and the full text loads only when needed. Cheap and editable, but a document can carry prompt injection, so writes need gates.

Hermes’s Choice: Skills Are Documents With Two-Phase Loading

A skill is a directory with a SKILL.md, following the agentskills.io layout: frontmatter with name, description, and metadata, a body the model should follow, and optional supporting files. A skill is not a plugin. It can only do what existing tools can do, plus persuade the model.

flowchart TD Start["Session build"] --> Idx["Scan SKILL.md frontmatter only"] Idx --> Vol["Volatile tier: names and descriptions"] Use{"Model calls skill_view or user types /name"} Vol --> Use Use --> Body["Load body into the transcript"] Body --> Act["Follow the procedure with ordinary tools"]

The index (names and one-line descriptions) sits in the cheap, volatile tier of the system prompt (Chapter 6). The body loads only when the model calls skill_view or the user types /skill-name. Either way it enters the transcript as a message and does not touch the cached prompt. That two-phase load is the performance trick. It is also the learning trick. The agent can write a new skill, and the next session’s index includes it, with no release needed.

The memory & skills explorer in Chapter 13 shows both phases side by side with memory.

Where Skills Come From

The source of truth is the profile’s skills/ directory. Fresh installs copy bundled skills there. Hub installs and agent-written skills land there too.

graph TD Proj["Project skills
only if the project is trusted"] --> R["Resolution order"] Local["Profile skills/ directory"] --> R Redir["Create-dir redirect"] --> R Ext["External dirs
(the sharing mechanism)"] --> R R --> Index["Index for this session"] Index --> F{"Fits this platform?"} F -->|no| Drop["Hidden on this surface"] F -->|yes| Show["Listed"]

Precedence is project, then local, then a create-dir redirect, then external directories. Duplicate names in one tier are listed by path instead of silently shadowing each other. Project skills are trusted only after the operator trusts the project. Non-interactive surfaces (cron, API, ACP) never show a trust prompt, so untrusted project skills simply stay out.

Platform metadata can hide a skill from the wrong surface. A skill that drives a local GUI does not belong in a Telegram cron job. Fallback skills load only when a primary is missing. Bundles are named sets installed together.

The Index Line and the Body

The prompt section is small and firm: scan the index and load a skill before inventing a procedure. A skill added mid-conversation reaches the model through Chapter 6’s one-time note, or at the next compression. /skills install --now accepts a cold cache.

Big sources, such as a book or a corpus, become a knowledge-base skill: a map in SKILL.md with the bulk stored outside the loaded body. /learn drafts a skill from a folder, a URL, notes, or a workflow just performed. The draft is a file and passes the same write gate.

Pinned skills (skills.auto_load) are the exception. Their bodies are loaded once and placed in the stable prefix, because they are constant for the session. Everything else stays an index line.

When compression removes a loaded skill body from the transcript, it leaves a marker naming the skill and saying to load it again, and the summary lists pruned skills. “Forgotten” and “never loaded” must look different to the model. Pinned skills are never pruned, because they are not in the transcript.

Writing a Skill Is a Side Effect

skill_manage can create, edit, patch, and delete skills and their files. This is the write half of the learning loop. Memory writes facts. Skills write procedures. Each has its own gates.

sequenceDiagram participant Model participant Tool as skill_manage participant Scan as Optional scanner participant User participant Disk as profile skills dir Model->>Tool: create or patch alt scanner enabled and suspicious Tool->>User: approval with rationale User-->>Tool: deny Tool-->>Model: error else approval required Tool->>User: stage the diff User-->>Tool: allow Tool->>Disk: write else open Tool->>Disk: write end
  • skills.write_approval (default off) stages every agent write for approval, like a dangerous command.
  • guard_agent_created (default off) scans new content for credential harvesting, prompt injection, and exfiltration. It is off by default because real workflows mention ~/.ssh and key names and kept tripping it. Turn it on for profiles exposed to untrusted chats. A hit becomes an approval prompt with the reason, never a silent save or silent drop.

Hub installs are the human-directed path. hermes skills and /skills search official optional skills, skills.sh, well-known endpoints, GitHub, ClawHub, and URLs. Installs are scanned, and --force overrides the scan. Updates do not clobber local edits, and hermes skills reset restores a bundled skill. The agent’s overnight draft and the user’s chosen install share a directory but not an authority.

A skill that needs a token declares it in frontmatter. That is a request. Chapter 8’s sandbox filter makes the decision.

Why Not a Plugin?

A bad plugin is bad code. A bad skill is a bad procedure that the transcript shows. For a personal agent, most “capabilities” are procedures, so skills sit near the cheap end of Chapter 7’s ladder.

The cost is prompt injection. A skill carries the authority of instructions the system prompt tells the model to follow. That is why there are hub scans, cron’s assembled-prompt scan (Chapter 10), the optional write scanner, and project trust. “It’s just markdown” is no excuse. Markdown is the whole attack.

Skills are per profile. To share a library across profiles, point at an external directory on purpose.

The Trade-offs

  • Loading is a step. The model must choose to load a skill, and sometimes it will not.
  • Text is an attack surface. Gates and scans add friction.
  • Per-profile libraries. Sharing takes deliberate setup.

Apply This

Index cheaply, load bodies on demand. Keep bodies small, and move reference material out of the loaded file.

Keep procedures out of the fact file. Steps go in skills. Always-true one-liners go in memory.

Gate agent writes separately from human installs. Default the heuristic off, and turn it on for untrusted profiles.

Make a pruned skill look pruned. Leave a marker with the name.

Treat skill text as untrusted on unattended runs. Scan when it runs, not only at install.

Chapter 15: Compression, the Legal Cache Break

The Problem: Conversations Outgrow the Window

Every model has a context window, a maximum number of tokens it can read at once. A chat that runs for a month will not fit. Neither will a coding session that reads many large files. Something has to give.

The naive fix is to drop the oldest messages. That loses the user’s goal, the decisions already made, and the files already touched. It can also leave broken pairs behind: a tool call whose result was dropped, which providers reject. And any change to the history destroys the prompt cache from Chapter 6.

So an agent needs a way to shrink a conversation that keeps what matters, keeps the transcript valid, and breaks the cache as rarely as possible.

The Options

  • Truncate. Drop old messages. Cheap and lossy, and it often breaks tool pairs.
  • Summarize everything. Replace history with one summary. It loses recent detail the model still needs.
  • Keep the head and tail, summarize the middle. Protect the start and the recent turns, prune old tool output, and summarize what is between into a structured note. More moving parts, but the goal and the recent work survive.

Hermes’s Choice: A Pluggable Engine That Summarizes the Middle

Compression is the one allowed rebuild of the prompt in mid-conversation (Chapter 6). ContextEngine (agent/context_engine.py) is the interface, and ContextCompressor is the default. A plugin can replace it, but never silently. context.engine selects it, and "compressor" always means the built-in. Only one engine runs. Two compactors in a row would summarize summaries until the goal vanished.

An engine must implement four things: a name, recording token usage from each response, deciding whether to compress, and compressing. Everything else has a safe default, so plugins stay small. One optional hook, select_context, may swap the messages for a single request without saving the change. By default it does nothing, so a normal session stays byte-identical.

Two Layers of Defense

flowchart TD In["Incoming turn"] --> H{"Gateway hygiene over 85%?"} H -->|yes| C["Compact before the agent"] H -->|no| A["Agent preflight"] C --> A A --> P{"Anchored tokens over threshold?"} P -->|no| Call["Call the model"] P -->|yes| Eng["engine.compress"] Eng --> Call

Gateway hygiene (gateway/run_turn_hygiene.py) is a safety net at about 85% of the window, for histories that grew while the agent was away. It is set higher than the agent’s threshold on purpose. When both were at 50%, gateway sessions compacted on every turn.

The agent compressor is the main path. It fires at 50% of the model window by default (compression.threshold), with an optional absolute token cap. It measures size with a usage anchor: the provider’s real token counts from the last call, plus a rough estimate of only what was added since. With no anchor yet, a rough estimate over the threshold waits for one real response before compressing, because a rough estimate is not proof that the provider will reject the request.

Four Phases

1. Prune. Old tool results outside the protected tail, longer than a couple of hundred characters, become one-line stubs. No model call is needed. A tool round the model has not answered yet keeps its full content. Pruned skill_view bodies get a marker naming the skill (Chapter 14).

2. Find boundaries. The head (protect_first_n messages after the system prompt) stays. The tail is a token budget counted backward, capped at 20% of the window. protect_last_n (default 20) is a minimum only up to a small floor, so a large value cannot block compression. Tool calls and their results are never split.

3. Summarize. One auxiliary model call fills a structured template: goal, constraints, progress (done, in progress, blocked), decisions, files, next steps, and critical context. On later passes, the previous summary is updated, not rewritten, so items move from “in progress” to “done.” A plain fallback summary is stored too, in case the model call fails after pruning.

4. Assemble. Head, then the summary message (with a role that keeps alternation legal), then the untouched tail. Orphaned tool results are removed. Tool calls whose results vanished get stub results, so the next request is valid. The system prompt gains a one-time note that earlier turns were compacted. That breaks the cache once, which is the price of honesty. Later turns hit the new prefix.

graph LR subgraph Before S1["system"] --> H1["head"] --> M1["middle:
old turns, big tool output"] --> T1["tail:
recent turns"] end subgraph After S2["system + one-time note"] --> H2["head"] --> SUM["structured summary"] --> T2["tail, untouched"] end M1 -. "summarized" .-> SUM

The summary model needs a window at least as large as the main model’s, because the whole middle is sent in one request. If it is smaller, the call fails and the middle is dropped without a summary. This is the most common quality failure, and the fix belongs in the operator’s config, not a retry loop.

By default (compression.in_place), the session keeps its id and old rows are archived as active=0 (Chapter 3). Turning it off creates a child session with a parent pointer instead.

Manual /compress can take a focus topic and skip the cooldown. It still never splits a tool group. If everything is protected, the gateway can report “nothing to compress” without a model call.

Timeouts are layered so a stuck summarizer never stalls a chat: an inactivity limit, a total limit, a short maximum wait for gateway hygiene before the turn proceeds uncompressed, and a per-session cooldown after failures. If preflight times out while the request is still too big, the turn ends with a clear result (Chapter 5).

Some providers compact natively, such as Responses compaction or Codex app-server threads. On those routes the provider owns the job, and the local compressor must not also summarize the same bytes.

Memory Leaves Before the Middle Does

Inside a compressing turn the order is fixed: memory providers get their pre-compress checkpoint, the built-in memory is flushed, and only then is the middle dropped (Chapter 13). After assembly, the handoff guard from Chapter 5 makes sure the user’s latest request is still present. Compression may forget tool output. It may not forget what the user just asked.

Each agent gets its own copy of the engine (clone_for_agent), so a child that switches models cannot change the parent’s threshold. When the model changes, the token counters are reset, so the new model does not inherit the old one’s “we already fit” decision.

Hygiene at 85% and the agent at 50% are far enough apart that a normal session compacts occasionally, not constantly. Each pass loses something, even with a good template.

The Trade-offs

  • Compression is lossy. A structured summary keeps the important parts, but detail is gone.
  • One cache break per pass. The system note and new transcript prefix cost one cold request.
  • Configuration matters. A too-small summary model silently loses the middle.

Apply This

Make compression a plugin with one required decision and many safe defaults. A default that returns nothing is safer than a default that returns a copy.

Prefer real usage over estimates, and wait once without an anchor. One rejected request is cheaper than compacting every new session.

Summarize into a schema, and update it next time. Check the summary model’s window first.

Keep tool pairs whole, and mark stubbed skills. Cap the tail so compression can always free space.

Checkpoint memory before you delete the evidence. Version the hook so best-effort plugins do not become outages.

Part V — Trust, Islands, and Cost

Chapter 16: Who May Act

The Problem: An Agent With Your Credentials

By now the agent can run shell commands, edit files, browse, message people in chat apps, and write its own procedures. It does all of this with the operator’s credentials. And it may be taking instructions from people who are not the operator: anyone who can message the gateway, or anyone who wrote a web page the agent reads.

So every capable agent needs answers to three different questions:

  1. Should this command run? Some commands are routine. Some are destructive. A few are catastrophic.
  2. Should this sender be heard at all? A stranger messaging your bot is not you.
  3. What can a command touch if it does run? Your whole laptop, or a sandbox?

The Options

  • One trusted flag. Simple. It also means a paired chat user can run rm on the host, because “trusted” meant everything.
  • A full policy engine with audit exports. Right for a multi-tenant product, but heavy for a personal agent where the person at the keyboard is both the likely victim of a mistake and the one who wants speed.
  • Layered gates, each with its own default. A small unbreakable floor in code, operator rules in config, a human for the ambiguous middle, a separate gate for strangers, and containment chosen per backend.

Hermes’s Choice: Three Separate Gates

tools/approval.py is the command gate. gateway/pairing.py is the stranger gate. Container flags, write roots, and environment filters are the containment gate. They are not one boolean.

graph LR S["Sender"] --> G1["Stranger gate
allowlist or DM pairing"] G1 --> Agent["Agent turn"] Agent --> G2["Command gate
hardline → deny → allow → ask"] G2 --> G3["Containment
backend, write root, env filter"] G3 --> Effect["Side effect"]

Commands: Hardline, Then Policy, Then a Human

A terminal command goes through a fixed order.

flowchart TD C["Command about to run"] --> H{"Hardline match?"} H -->|yes| Deny["Deny, no override"] H -->|no| U{"User deny rule?"} U -->|yes| Deny U -->|no| A{"Permanent allow?"} A -->|yes| Run["Run"] A -->|no| D{"Dangerous pattern?"} D -->|no| Run D -->|yes| M{"Mode"} M -->|off or YOLO| Run M -->|ask| P["once / session / always / deny"] P -->|deny| Deny P -->|allow| Run
  1. The hardline blocklist runs first and cannot be disabled, not by session settings, not by YOLO, not by approvals.mode: off. It covers catastrophic patterns, where “I approved the session” is not meaningful consent, such as recursive deletes aimed at the runtime itself.
  2. User deny rules (approvals.deny) are the operator’s own policy.
  3. Permanent allowlists cover patterns the operator already accepted.
  4. Dangerous patterns that remain, such as destructive git or privileged commands, go to a human: once, session, always, or deny.

YOLO (hermes chat --yolo) is a session latch. It skips the prompt, never the hardline, and it is saved with the session so /resume remembers it. Off mode stops asking but still hits the hardline. Repeated denials escalate the wording, so a model that keeps pushing gets a hard stop instead of a debate.

Each surface asks differently:

  • Subagents do not inherit the parent’s prompt. They deny by default, unless delegation.subagent_auto_approve is on, and then the answer is “once,” logged (Chapter 12).
  • Gateway approvals use a per-session queue and a platform button, with a timeout. Timeout is deny. Silence is not consent.
  • Cron gets no quieter blocklist (Chapter 10).

execute_code is a command too. A Python sandbox that shells out is still a shell. File writes have protected paths: Hermes’s own home, credentials, and cron state, the things a model would rewrite to persist an attack. An optional write root gives operators a sandbox even on the local backend.

hermes approvals suggest mines history for patterns the operator keeps approving and proposes allowlist entries. It never applies them automatically. An allowlist that grows itself is a slow YOLO.

Strangers: Allowlists and Pairing

Gateway authorization runs before an agent exists (Chapter 9). The static form is platform allowlists. The flexible form is DM pairing.

sequenceDiagram participant X as Unknown sender participant GW as Gateway participant Op as Owner (CLI) X->>GW: first DM alt platform behavior is pair GW-->>X: 8-character code Op->>GW: hermes pairing approve (platform, code) GW-->>X: now approved on this platform else ignore GW--xX: dropped else decline GW-->>X: one short refusal, then ignored for a day end

Codes use 32 unambiguous characters (no 0/O or 1/I). They expire after an hour. Each sender gets at most one request per 10 minutes, each platform at most 3 pending codes, and 5 failed approvals lock that platform’s approval path for an hour. Files are mode 0600 and codes are never logged. Email defaults to ignore, because an inbox is full of people you never meant to enroll. Storage is per profile and resolved at call time, so the approval lands in the right island.

One Docker footgun is worth knowing. The image runs the gateway as an unprivileged user, but docker exec defaults to root. An approval file written as root with mode 0600 is invisible to the gateway, so the approval “succeeds” while the user stays blocked. Approve as the gateway user.

Pairing is not command approval. A paired user can still hit a dangerous-command prompt. Approving a command does not enroll a new chat.

Containment: What the Place Can See

Chapter 8 chose where tools run. This gate decides what that place can see.

Backend What you are trusting
Local the OS user, plus the approval gate and write root
Docker and containers the image and its flags (non-root, limits, dropped capabilities)
SSH the account on the other side
Hosted sandbox the vendor boundary and the credential you passed

Choose the backend to match the trust of the sender, not the operator. A paired stranger plus a local YOLO shell is the operator’s machine.

The environment passed to sandboxes is stripped by default. Skills request extra variables in frontmatter, and policy decides. “Borrowed” logins, such as a Codex or Claude Code credential on disk, let the agent act as that user, so treat them as grants. MCP servers get a safe subset, and tool output is redacted before it reaches logs. Web tools refuse private addresses unless the operator opts in. Content checks look for fetched pages that try to issue commands to the agent. Repo context files are truncated and are part of the same trust decision as project skills (Chapter 14).

This book does not publish detector patterns or bypasses. The pattern is the order of the gates. The contents of the hardline list are the project’s to rotate.

What a Personal Agent Should Not Copy

A multi-tenant product puts every tool behind a policy engine. Hermes puts the floor in code, the deny list in config, and the ambiguous middle in a prompt the operator sees. That fits when the person at the keyboard is the one at risk. It does not fit when the sender is someone else. That is what pairing and profiles are for. Keep a “public bot” home separate from your “laptop shell” home (Chapter 17), and enable YOLO only on the private one, if at all.

The model cannot approve its own escalation by editing config.yaml: protected writes enforce that. Audit is the transcript plus structured denial reasons, not a second log that can drift.

The Trade-offs

  • Prompts slow you down. That is why YOLO exists, with a floor under it.
  • Defaults lean to deny. Timeouts and unattended runs refuse, which can stall work.
  • Containment is the operator’s job. Hermes gives the options. Choosing the right backend for each sender is up to you.

Apply This

Put an unblockable floor under every convenience bypass. Keep the floor small and embarrassing to hit.

Make timeouts and bridge failures deny. Scale the timeout to the surface.

Enroll strangers with a short, rate-limited code, and never log it. Write the approval as the gateway’s user.

Strip the environment, then add grants. Frontmatter is a request, not a grant.

Keep stranger enrollment, command approval, and containment separate. If you need an “admin mode,” that is a different profile.

Chapter 17: Profiles, Multiplex, and What a Turn Costs

The Problem: Many Lives, One Machine, One Bill

Most people who run a personal agent soon want more than one. A public bot for a community chat. A private assistant with shell access. A work setup with different keys. Each should have its own settings, memory, history, and secrets, and none should leak into another.

The simplest answer is one process per setup. That works, but it multiplies processes, ports, and adapters. The harder answer is one process serving many setups. That saves resources, but now every cache, thread, and global variable is a chance for user A’s data to show up in user B’s prompt.

Cost is the other shared concern. Every design choice in this book either saves tokens or spends them. Is there a cost optimizer? Or is cost the sum of the other decisions?

The Options

  • A process per profile. Strong isolation, more overhead.
  • One process with a lock around globals. Cheap, but a global can still hold only one secret at a time, and the gaps around each await are race conditions.
  • One process with a per-task home. Every path is resolved through a context-local override, so each turn sees only its own profile. More discipline, and anything that cannot be isolated must refuse to run.

Hermes’s Choice: Islands in One Process

A profile is a directory with its own config.yaml, .env, state.db, memory, skills, pairing files, cron jobs, and gateway identity. The default profile is a real name (Chapter 3). Without multiplex, one gateway serves one profile. Multiplex lets one process serve many while keeping them separate.

graph TD Proc["One gateway process"] --> Loop["Shared event loop and listener"] Proc --> P0["Default home"] Proc --> P1["profiles/writer"] Proc --> P2["profiles/bot"] P0 --> A0["Adapters, secrets, state.db, cron"] P1 --> A1["Adapters, secrets, state.db, cron"] P2 --> A2["Adapters, secrets, state.db, cron"] Loop --> A0 Loop --> A1 Loop --> A2

Profiles share the event loop, the HTTP listener, the process lock, and the status surface. They do not share adapters, secrets, sessions, or cron ticks. The rule from the multiplexing guide: profile A’s turn must never observe profile B’s state. Anything that cannot be isolated yet fails closed, or is documented as a limitation.

How the Override Works

get_hermes_home() checks a context-local override (in hermes_constants.py) before the environment variable and the platform default. Config, the database, skills, memory, soul, sessions, plugin discovery, and MCP start-up all call it, so they all follow the active profile.

flowchart TD Q["get_hermes_home()"] --> O{"Context-local
override set?"} O -->|yes| H1["That profile's home"] O -->|no| E{"HERMES_HOME set?"} E -->|yes| H2["Env home"] E -->|no| H3["Platform default"] T["Serving a turn for profile X"] -->|"bind override"| O

get_process_hermes_home() exists for the few machine-level things that must not follow the override. A one-time warning fires when profile-scoped code runs without an override where one is expected, because otherwise the bug is silent. You simply get the launch profile’s data.

SessionStore resolves its database handle at call time, keeping one cached handle per profile file. A store object can be shared. The file cannot. Pairing stores and cron ticks are per profile. Clients of a secondary profile find the multiplexer through the default home but attach with their own profile id and their own ticket (Chapter 9).

The danger is everything that runs outside a turn: boot probes, eviction, tickers, deferred callbacks, RPC methods, thread hops, and child processes. Any of them that reads os.environ or a global once will capture the launch profile. Memory plugins use spawn_context_thread (Chapter 13). Child processes must be given HERMES_HOME explicitly. Rebuilding an agent mid-session must keep the session’s database handle and bind the home during construction.

Plugin authors inherit this rule. A plugin that caches the home path at import has chosen the launch profile forever. Open connections on first use, inside the override, or key them by home. Clients must send the profile id on every session call. A missing id is not “whichever was active.” Name the tenant, or do nothing.

What a Turn Actually Costs

There is no cost optimizer in the code, and this book will not invent a price list. The real costs are structural:

flowchart LR Turn["One turn"] --> Cache["Prefix hit or miss"] Turn --> Tools["Schema tokens"] Turn --> Kids["Child prefixes if delegated"] Turn --> Aux["Summary or review, if fired"] Cache --> Bill["Provider bill"] Tools --> Bill Kids --> Bill Aux --> Bill
  • The prefix. Chapter 6’s tiers keep the stable head cached. Memory writes, skill installs, model switches, and credential rotation are deliberate misses. Human-paced sessions use a longer cache lifetime than machine-paced ones. The avoidable mistake is breaking the cache by accident.
  • The tool list. Every enabled schema rides on every request. Chapter 7’s ladder is a cost control. A skill index line is cheaper than a tool, and a hidden unconfigured tool is cheaper than one the model calls and fails.
  • Fan-out. Delegation’s depth of one and the warning above ten children are cost controls (Chapter 12). Each child pays for its own prompt. Background review has its own token cap.
  • Compression. A summary is a side call, ideally on a cheaper model under auxiliary.compression. It costs less than sending a 90% full window forever, and more than not compacting if the threshold is too low. The 50% agent threshold and 85% gateway net are the compromise (Chapter 15).
  • Retries and fallback. Each one cold-starts the cache, but is cheaper than a dead session. The once-only fallback latch is a cost control too.
  • Iterations. agent.max_turns (500) is a ceiling, not a target. The 80% wall-clock wrap-up turns a research loop into a deliverable. Child and batch budgets are lower.

Training data is a separate store. The batch runner can export ShareGPT-style trajectories for training. That is a copy, on purpose (Chapter 3). Do not mine state.db with a job that holds a write lock, and never write labels back into user transcripts.

Observability hooks record guardrail decisions and cache breaks, so an operator can see a miss. They are not billing. For dollars, use the provider’s usage data plus the model id the session row already stores.

The Trade-offs

  • Discipline everywhere. Every background job and plugin must respect the override.
  • Some features refuse to multiplex. Anything that cannot take the override is limited to the default profile, by design. A lock around a global is not isolation.
  • Cost control is indirect. There is no single dial; cost follows from the other rules.

Apply This

Resolve the tenant on every call through one context-local root. Make the scoped function the easy one, and name the process-level one so it sounds dangerous.

Share the event loop, never the meaning of a database handle. Cache handles per home.

Treat cache identity as part of the cost model. Rotate when you must, never when the pool has one key.

Cap fan-out in the tool, not the prompt. Warn where cost turns linear, and keep the default small.

Export training data out of band, and redact it.

Part VI — Transfer

Chapter 18: What Transfers

The Question

This chapter adds no new subsystem. It asks which of Hermes’s bets are worth copying if you are not building Hermes, and which only make sense for a personal agent that lives in other people’s chats. You can copy the decisions into a TypeScript coding agent or a hosted product. You should not copy the surface area and call it architecture.

The Bets, Checked Against the Code

graph TD Bet["One turn"] --> Cache["Frozen prefix"] Bet --> Edge["Tools, skills, plugins at the edge"] Bet --> Learn["Facts, procedures, search"] Bet --> Place["Backends, not tool names"] Bet --> Tenant["A home per island"] Cache --> Cost["Predictable cost"] Tenant --> Safe["Predictable blast radius"]

One core for every surface. CLI, gateway, cron, ACP, batch, and the library all call run_conversation. Surfaces differ by callbacks and settings, cron disables tools instead of forking the loop, and ACP converts editor content into ordinary user messages. The bet holds. A surface that needs a new policy does not need a new loop. If a surface ever needs different compression or a different transcript format, the bet has failed. Notice it instead of hiding it behind a flag.

The cached prefix is a product rule. Tiers run stable, context, volatile. Skill changes and surface switches ride the user message. Memory writes go to disk, not the prompt. Compression is the named rebuild. Fallback and rotation are admitted misses. Most agent codebases break this rule first, because every feature wants to help mid-conversation. When a doc and build_system_prompt_parts disagree, the function is the architecture.

Capability lives at the edges. Tools register themselves and check_fn hides the unavailable ones. The footprint ladder pushes procedures into skills and integrations into plugins and MCP. The four intercepts exist because they need the conversation. This holds as long as intercepts stay rare. A dozen would be a second registry with worse tooling.

Learning is three stores. Facts, a user profile, and full-text recall, plus skills for procedures, plus at most one external provider. A personal agent that forgets your timezone every morning is broken. Do not collapse this to “we’ll just search the transcript.” Decisions and evidence have different lifetimes (Chapter 13).

Execution is a placement, not a tool name. Seven terminal backends share one interface. Browsers and search are registries. The model sees stable verbs, and the operator sees a config key. This is worth it for any agent that might leave the laptop. It is wasted effort for one that is contractually local.

Profiles are islands even inside one process. Context-local home resolution, per-home databases and cron, fail-closed multiplex. A hosted product needs the same idea with a real tenant id instead of a directory. The directory is the implementation. The override is the idea.

What Does Not Transfer Cleanly

graph LR subgraph Copy["Copy as-is"] C1["One loop, many doors"] C2["Frozen prefix + one named rebuild"] C3["Registry + availability probe"] C4["Fresh, closed, scanned unattended runs"] C5["Compression order"] end subgraph Adapt["Adapt to your system"] A1["Unknown-not-replayed queue"] A2["Pairing + hardline floor"] A3["Flat delegation default"] A4["Thresholds like 50% / 85%"] A5["Facade + siblings + size ratchet"] end
  • “Unknown, not replayed.” Right when tools send messages or edit files exactly once. Ceremony if your tools are idempotent and users expect retries. Copy it only if your tools match.
  • Pairing and the hardline floor assume an operator who is not the sender. A single-user coding CLI can just ask every time. A public bot cannot. Cron’s three rules (no clarify, fresh transcript, scan the assembled prompt) transfer to any scheduled agent.
  • Flat delegation is a cost default, not a law. A research product might allow depth and keep the cap. A product with no cap is an unbounded loop.
  • Compression transfers if your sessions are long. Copy the order exactly: checkpoint memory, summarize the middle, keep tool pairs whole, never let the summary pose as the user. Do not copy the thresholds without measuring your own window.
  • Facade plus siblings is a social tool for a big Python repo with many contributors. A small system can keep the loop in one file until it hurts. What transfers at any size: tests patch the name callers import.

A Sketch You Can Build

If you take nothing else, build this turn and stop:

Around it, add doors that only choose a session, a policy, and a delivery callback. Add a registry whose probe can fail without crashing the process. Add one fact file and one search function before a vector database. Add a depth cap the same day you add subagents. Put the tenant in a context variable the same day you serve two.

Then write down the one change you allow mid-session. Hermes chose compression. Choosing none, and then letting every feature edit the prompt, is the failure this book has been circling since Chapter 1.

The Ten Patterns

  1. One agent, many doors. Chapters 1, 9, 10, 11.
  2. Facade and siblings. Chapters 1, 2, 5.
  3. The prefix is sacred. Chapter 6, paid for in 17, broken only by 15.
  4. Register at import, gate with a probe. Chapters 7, 8.
  5. Narrow waist. Chapters 7, 14. A skill is the default capability. A core tool is a tax.
  6. Stateful tools are intercepted. Chapters 7, 12, 13.
  7. Three stores, not one memory. Chapter 13.
  8. Skills load in two phases. Chapter 14.
  9. Cron is a fresh agent. Chapter 10.
  10. The gateway owns the transcript. Chapters 3, 9, 17.

None of these needs Hermes’s model router, skill hub, or any particular chat platform. They need a decision to keep the turn boring. The doors can be as odd as a phone client and an editor protocol. The center should fit on one page and be able to say no.

Build the center first. Once it can say no, each door is a weekend’s work.

Apply This

Write the rule down where features go to die. And name its one exception, as compression is named.

Steal the turn, not the product. Start with the loop, not the UI. Ship one backend.

Isolate tenants the day you have two. It is cheap before the first global cache and expensive after.

Default unattended work to fresh, closed, and scanned. Keep durable facts.

Keep one legal way to forget. One path, explicit markers, a threshold you measured.
