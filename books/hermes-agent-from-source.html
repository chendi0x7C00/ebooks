Chapter 1: The Architecture of One Agent

What You’re Looking At

A chat transcript is not an architecture. A tool-calling demo is not one either. The interesting question is what stays the same when the same agent has to answer a terminal, a Telegram message, a cron tick, and an editor prompt without growing a second brain for each door.

Hermes Agent, from Nous Research, answers that question with a narrow waist. One class, AIAgent, exposed by the run_agent.py facade, owns the turn: assemble a prompt, resolve a provider, call a model, dispatch tools, persist, repeat. The CLI, the messaging gateway, ACP, the batch runner, the API server, and a plain Python import are entry points. They differ in how a user shows up and how a reply is delivered. They do not differ in how a turn is executed. That is the bet this book is about, and every later chapter is a zoom into one segment of it.

What follows is a retrospective map. The six surfaces and the three stores underneath them were not a whiteboard drawn on day one. They are what the tree converges on once a personal agent has to survive real sessions, real caches, and real machines that are not the laptop that started the process.

The public architecture page draws the same picture: entry points on top, AIAgent in the middle, session storage and tool backends underneath. The useful refinement is what “entry point” means. The TUI and the Electron desktop app are not alternate agents. They are clients of a session authority — usually the profile’s gateway — that admits work and then calls the same turn. Chapter 9 is where that authority is earned. For this chapter it is enough to see that a new surface does not get to invent a loop.

Inside the facade the work splits three ways, and the split is the whole product:

  • Prompt assembly (agent/prompt_builder.py, agent/system_prompt.py) builds one system prompt in three tiers and then refuses to rebuild it until compression. Chapter 6.
  • Provider resolution (hermes_cli/runtime_provider.py) turns a (provider, model) choice into an API mode, a base URL, and credentials. The same resolver serves cron and auxiliary summarization. Chapter 4.
  • Tool dispatch (model_tools.py over tools/registry.py) turns a model tool call into a handler, after hooks and an approval gate. Chapter 7.

Under those three sit two persistence and execution planes. hermes_state.py is the session ledger (Chapter 3). Terminal, browser, and web tools are swappable backends behind stable tool names (Chapter 8).

The Import Chain Is the Plugin Model

Tools do not appear because a central file lists them. They appear because Python imported them.

tools/registry.py          no product dependencies; every tool imports it
tools/*.py                 each calls registry.register() at import time
model_tools.py             discovery, schema collection, handle_function_call()
run_agent.py and friends   construct an agent only after discovery has run

discover_builtin_tools() walks the tools package, imports modules that actually call register(), and caches the result. MCP servers and plugins are discovered after the builtins. By the time AIAgent exists, the registry already knows every tool this process might offer. Availability is a separate question, answered later by each tool’s check_fn — Docker might be down, a browser backend might be unconfigured — but registration is not a runtime negotiation.

That chain is why the project’s own rule is “the core is a narrow waist.” Every tool schema is sent on every API call. Adding a tool to the core is not free. The footprint ladder in the root development guide is the social version of this diagram: extend an existing tool, then a CLI command plus a skill, then a service-gated tool, then a plugin, then an MCP server, and only then a new core tool. Chapter 7 is the mechanism. This chapter is the reason the ladder exists.

Facade Plus Siblings

The files you import are not the files that grow. run_agent.py is the public seam: AIAgent, run_conversation as a name other packages patch, session-row helpers. The turn itself lives in agent/conversation_loop.py, and each phase lives in an agent/turn_*.py module. hermes_state.py is a facade over hermes_state_*.py siblings (schema, FTS, compression, gateway). gateway/run.py is a facade over gateway/run_*.py. cli.py is a facade over hermes_cli/cli_*_mixin.py.

# Pseudocode — illustrates the seam, not the source
class AgentFacade(TurnMixin, PersistenceMixin, CompressionMixin):
    def __init__(self, **kwargs):
        init_agent(self, **kwargs)  # real wiring lives next door

def run_turn(agent, user_text):
    return conversation_loop(agent, user_text)  # facade name, sibling body

Siblings late-import the facade inside functions so the import graph does not cycle. Patches belong on the facade, because that is the module production code imports. A patch on the defining sibling can pass silently if the caller already bound the facade’s name. The size ratchet (functions and files may only shrink once they are over the cap) is what forces the next behavior change into a sibling instead of back into the god file. The pattern is boring, which is why it scales. Chapter 2 shows the constructor side of it.

AIAgent itself is a mixin composite: client lifecycle, streaming, interrupts, persistence, compression, vision prep, reasoning parameters, the turn facade. The class body in run_agent.py is mostly forwarding. If you open it expecting the loop, you are in the wrong file on purpose.

What the Core Refuses to Know

Principle What it costs you if you violate it
Prompt stability A mid-chat edit of the system prompt or the tool list breaks the provider prefix cache and multiplies the bill. Compression is the named exception.
Observable execution A tool that runs without a callback is invisible on a phone and unauditable in a gateway log.
Interruptibility A stuck HTTP call that cannot be abandoned turns /stop into a lie.
Platform-agnostic core A if telegram: inside the turn guarantees the next platform will fork the loop.

Two of these are stronger than the table makes them look, and they are the lens for the rest of the book.

The cached prefix is sacred. The root development guide says it outright: mutating past context, swapping toolsets, or rebuilding the system prompt mid-conversation breaks the cache. Slash commands that would change prompt state defer to the next session. --now is the opt-in. The one exception is context compression, which is why it has its own chapter instead of being a helper inside the prompt builder.

Profiles are islands, even in one process. get_hermes_home() consults a context-local override before the environment variable and before the platform default (~/.hermes, or the Windows equivalent). display_hermes_home() is for text the user sees. Hardcoding the default path is a bug with a name in the project’s lint rules. Chapter 17 is the multiplex story; the rule starts here because every later path discussion assumes it.

The Three Flows You Will See Again

The architecture page gives three golden paths. They are the same turn wearing different clothes.

A CLI session goes: user input, AIAgent.run_conversation(), prompt build, provider resolve, an API call in one of three modes, tool calls through handle_function_call() until the model stops, then display and a session-row write.

A gateway message goes: adapter turns a platform event into a message, the runner authorizes the user and resolves a session key, then the same run_conversation(), then the adapter delivers the reply.

A cron job goes: the scheduler loads a due job, builds a fresh agent with no prior run transcript, injects attached skills, runs the prompt, delivers to a target, and updates the job. Durable memory still loads. Last Tuesday’s tool output does not.

sequenceDiagram participant Door as Entry point participant Agent as AIAgent participant Model as Provider participant Tools as Registry participant Store as Session DB Door->>Agent: user text or job prompt Agent->>Agent: reuse cached system prompt Agent->>Model: one API mode Model-->>Agent: tool calls or final text alt tool calls Agent->>Tools: dispatch, hooks, approval Tools-->>Agent: results in call order Agent->>Model: next iteration else final text Agent->>Store: persist the turn Agent-->>Door: reply for this surface end

Notice what is absent. There is no gateway-specific compressor, no cron-specific tool dispatcher, no ACP-specific message format that the model sees. ACP converts editor blocks into the same user content the loop already understands (Chapter 11). Cron disables toolsets the job must not have (Chapter 10). Those are policies at the door. The loop stays one loop.

Apply This

One loop, many doors. Put the agent turn behind a single function and make every surface a caller. The problem it solves: the second platform quietly forks error handling, compression, and persistence until you have two agents that disagree. The pitfall: hiding surface policy inside the loop with platform branches. Policy belongs in the caller — which toolsets, which callbacks, which session row.

Register capabilities at import, select them at runtime. Let modules enroll themselves in a registry with no central list. Gate visibility with a probe. The problem it solves: a hand-maintained tool index that drifts from the filesystem. The pitfall: treating registration as availability. A registered tool whose backend is down must drop out of the schema, not fail on first use with a stack trace the model cannot act on.

A public facade and private siblings. Keep the import path stable and move growth into topic modules that call back into the facade. The problem it solves: a god file that everyone patches and nobody can review. The pitfall: patching the sibling in tests while production bound the facade name. Tests should patch the seam callers actually import.

Make the cache a product invariant, not a performance tweak. Decide which bytes are frozen for the life of a conversation and give exactly one subsystem permission to rebuild them. The problem it solves: well-meaning features that edit the system prompt “just this once” and silently 10x the bill. The pitfall: freezing so hard that compression, the thing that keeps long sessions alive, has no legal path. Name the exception.

Isolate tenants with a context-local home, not with processes alone. Resolve every path through one function that checks a context override before the environment. The problem it solves: a multi-tenant worker that leaks user A’s memory into user B’s prompt because a helper read a global. The pitfall: a second, “just for display” path resolver that people start using for I/O. Display formatting and path resolution are different functions.

Chapter 2: Starting the Process

Chapter 1 put six doors in front of one agent. None of those doors can open until a process has repaired itself, chosen a home, and loaded secrets. Hermes treats that sequence as load-bearing. Get it wrong and the agent you construct is already the wrong profile’s agent.

This chapter is the path from “the user typed hermes” to “an AIAgent exists and has not yet taken a turn.” The turn is Chapter 5. The database that turn will write is Chapter 3. What matters here is the order of side effects, because several of them are illegal to do later.

Repair, Then Import

run_agent.py imports hermes_bootstrap before anything else. On Windows that is UTF-8 stdio. On POSIX it is a no-op that still has to be first, so a partial update cannot skip it by accident. If the bootstrap module itself is missing — an update killed while git was writing the tree — the process may restore and relaunch. If the bootstrap exists but fails to import, the process does not swallow that error. Skipping a broken bootstrap would also skip the environment the package manager just activated.

Immediately after that, if hermes_cli.main is not already on sys.modules, the same file calls an early-recovery helper. An interrupted hermes update can leave the checkout half-written. Recovery runs before the rest of the tree imports. Importing a half-written agent/ and then noticing the damage is how you get a process that looks alive and behaves like a random revision.

# Pseudocode — illustrates boot order
import bootstrap  # must be the first import
if main_module_not_loaded():
    if restore_interrupted_checkout():
        relaunch()
# only now: logging, dotenv, agent, tools

The rule is older than any feature in the loop. A personal agent that updates itself in place has a crash window. The window is closed by refusing to import the product until the tree is whole. There is no “best effort” mode that continues on a torn checkout.

The Home Is Chosen Before the Agent

Named profiles are directories. A profile called coder lives under the profiles root and has its own config.yaml, .env, state.db, memory, and skills. The CLI applies the profile override before it imports the rest of Hermes. An explicit --profile / -p resolves that directory and sets HERMES_HOME. Without an explicit flag, an already-set HERMES_HOME is preserved; otherwise the default root’s active profile may be selected.

get_hermes_home() is the only resolver that counts. It checks a context-local override first, then the environment variable, then the platform default. Changing HOME is not a way to select a profile. A subprocess that drops HERMES_HOME falls back to the default profile even when the parent was not on it, so spawners pass the variable explicitly. display_hermes_home() formats a path for humans (~/.hermes/profiles/coder). It is not a second resolver, and code that opens files with it is wrong.

flowchart TD A["Process start"] --> B["Bootstrap import"] B --> C{"Checkout torn?"} C -->|yes| D["Restore and relaunch"] C -->|no| E["Apply profile override"] E --> F["get_hermes_home locked in"] F --> G["Load .env from that home"] G --> H["Import agent, tools, CLI"] H --> I["Construct AIAgent"]

Two files split configuration on purpose. .env is secrets: API keys, tokens. config.yaml is behavior: model choice, toolsets, compression thresholds, approvals. The development guide rejects new HERMES_* environment variables for non-secret settings. A behavior flag in the environment is invisible to the profile island and tends to leak across profiles that share a process. Chapter 17 shows how bad that leak is under multiplex. The bootstrap rule is the smaller version: secrets ride the home, behavior rides the YAML.

load_hermes_dotenv reads the profile home and, for the checkout itself, a project .env beside the package. If neither exists, the process continues on the system environment and says so in the log. Missing secrets are a later failure at the provider, not a crash at import. That is the right layering. Boot should not pretend to know which provider you will pick in Chapter 4.

The Class You Import Is a Forwarder

AIAgent is a stack of mixins: client lifecycle, stream delivery, status, API-request hooks, error summaries, interrupts, explainers, activity, rate limits, session persistence, compression, the turn facade, vision prep, reasoning parameters. The constructor does not contain the wiring. It builds a keyword dict, warns if a deprecated tool_delay was passed, and calls agent.agent_init.init_agent.

That indirection is the facade rule from Chapter 1 applied to construction. Callers — CLI, gateway, cron, tests — keep writing AIAgent(...). The parameter list can stay the public contract while the body moves. A deprecated argument is accepted and ignored rather than deleted out from under external callers. The comment in the constructor is blunt about it: sequential tool calls no longer sleep between executions. Compatibility is a warning, not a behavior.

What the constructor does accept is the surface contract:

  • provider, model, API mode, base URL, credentials, and an optional fallback
  • enabled and disabled toolsets
  • callbacks for progress, streaming, clarify, approvals-shaped UI, and status
  • platform identity: platform, chat id, user id, thread id, gateway session key
  • session id, an optional injected session database, a parent session id
  • an iteration budget and an optional wall-clock run budget
  • flags to skip memory, skip context files, or load the soul identity
  • a working directory and a capabilities map

Read that list as “everything a door is allowed to vary.” A Telegram turn and a CLI turn differ in callbacks and platform fields. They do not get different init functions. Cron passes a fresh session and a narrowed toolset. ACP passes an editor working directory and an approval callback it will remove when the prompt ends (Chapter 11). The constructor is the widest API in the process, which is why it forwards instead of accumulating logic.

What the CLI Is, and What It Is Not

cli.py is HermesCLI: the REPL and slash-command dispatch, with behavior split into hermes_cli/cli_*_mixin.py. hermes_cli/main.py is the hermes subcommand entry. Setup, config migration, the skills hub, the plugin loader, and gateway start/stop live under hermes_cli/, not inside the agent.

The interactive loop is not the agent loop. The REPL reads a line, may handle a slash command locally, and only then calls run_conversation. Slash commands that would change the cached prompt — installing a skill into the live index, switching models — defer to the next session unless the user passes --now. That policy is Chapter 6’s invariant showing up at the keyboard. The CLI is where a human notices it. The CLI is not where it is implemented.

The TUI (ui-tui/) and the desktop app are different processes that speak to a Python backend. They do not link AIAgent into an Electron renderer and hope. They discover or start the profile’s session runtime (hermes gateway ensure is the supported “is anyone home?” command) and admit input over the session API. Chapter 9 owns that protocol. The boot lesson is smaller: if you are reading apps/desktop/ to find the turn, you are one process too far out.

A one-shot hermes invocation and a long-running hermes chat share the same early sequence. One exits after a single run_conversation. The other sits in the REPL. Neither skips profile binding. A library caller who imports AIAgent directly still inherits the bootstrap import and the dotenv load at run_agent import time, which is why tests are required to point HERMES_HOME at a temporary directory before they touch this module. The state layer will refuse to open a production database from a test context (Chapter 3). Boot is where that discipline starts.

Deep Dive: Session Identity Stamped at First Use

Constructing an agent does not always insert a session row. The first turn that needs the database calls an ensure path. The row records a source derived from platform (cli, a gateway platform, cron, and so on), the model config, and the profile name — including the literal "default". An older convention used NULL to mean the default profile. Profile-keyed consumers now treat NULL as unowned, so a row minted without an explicit name disappears from the sidebar. The code persists the name on purpose.

Only local CLI-family sessions stamp a working directory. Gateway, cron, and remote terminal backends have no stable host cwd to record. Gateway agents also persist an origin JSON — platform, chat id, user id, thread, profile — so later readers see the same routing fields the gateway’s session store writes. A background-review fork can disable persistence entirely so a harness turn is not flushed into the user’s real session. That flag is checked before any lazy open of the default database. Chapter 12 comes back to why.

None of this is the schema. It is the rule that identity is captured once, at first write, from the home and the platform that boot already fixed. A turn that “fixes” the profile later is already too late.

The Order You Cannot Rearrange

People refactor boot to be lazy, and the lazy version ships a bug class Hermes has already named.

If profile selection happens after tool discovery, check_fn probes run against the launch home and cache a yes/no that belongs to the wrong island. If dotenv loads before the profile override, the default profile’s keys satisfy a named profile that should have failed closed. If the agent is constructed before early recovery, a torn tree imports far enough to accept a user message and then dies mid-tool. If a background thread starts at import and reads HERMES_HOME once into a global, multiplex (Chapter 17) cannot correct it.

The implementation is allowed to be dull. The order is not.

sequenceDiagram participant OS participant Boot as Bootstrap participant Home as Profile home participant Agent as AIAgent OS->>Boot: start hermes Boot->>Boot: refuse a torn tree Boot->>Home: bind HERMES_HOME Home->>Home: load secrets, leave behavior in YAML Boot->>Agent: init_agent forwarder Note over Agent: no model call yet

By the end of boot you have a process that knows its home, a registry that has registered tools but not yet filtered them for this turn, and an agent object whose prompt cache is empty. The next chapter gives that agent a database. The chapter after that gives it a model. Neither is allowed to reopen the questions this chapter closed.

Apply This

Put recovery before the import of the system you are recovering. If the process can update its own source, the first code that runs must be able to detect a torn tree and relaunch. The problem it solves: half-imported modules that mask a failed upgrade as a logic bug. The pitfall: catching ImportError broadly and continuing. Only the “bootstrap module is absent” case is a recovery signal. A bootstrap that fails while present is a real error.

Bind the tenant before any cache, client, or database. Resolve the home, then load secrets, then import the product. The problem it solves: probes and connection pools that capture the default tenant at import. The pitfall: a display helper that returns a pretty path and slowly becomes the path used for open().

Split secrets from behavior in the boot contract. Environment for credentials, a file in the tenant home for everything else. The problem it solves: feature flags that cannot be different per profile because they live in the process environment. The pitfall: “just one” behavior variable for a hotfix. It becomes the way every later flag is added.

Make the public constructor a forwarder. Keep the type callers construct stable, and put wiring in a function that can move. The problem it solves: a class body that is simultaneously API and implementation, so every internal cleanup is a breaking change. The pitfall: two wiring paths, one for tests and one for production. There should be one init.

Stamp identity at first persistence, including the default tenant. Write the profile name explicitly. Do not use NULL as a synonym for default. The problem it solves: rows that vanish from every profile-scoped query after a migration that starts treating NULL as unowned. The pitfall: stamping a cwd or a gateway origin on surfaces that do not have one, then building features that require the field.

Chapter 3: State, the Session Ledger

Chapter 2 bound a home before the agent existed. This chapter is what that home stores, and — more importantly — who is allowed to write it. Hermes used to keep a JSONL file per session. It now keeps one SQLite database per profile, state.db, in WAL mode. The file is the system of record for transcripts, usage, routing, and the queue of work a gateway has accepted. Treating it as a convenient log is how sessions fork, replay, and leak across profiles.

The agent loop in Chapter 5 reads and appends messages. Compression in Chapter 15 rewrites them. Neither owns the rules of the file. Those rules live in hermes_state.py and its siblings: schema, FTS, search, compression bookkeeping, gateway columns, portability.

One File, Many Tables

The database path is get_hermes_home() / "state.db". Callers do not hardcode ~/.hermes/state.db. A named profile therefore gets a different file automatically, because Chapter 2 already pointed the home at profiles/<name>/.

sessions holds identity: id, source (cli, telegram, …), user, model, a JSON model config, the system prompt snapshot, parent session id, start and end, end reason, gateway routing columns (session_key, chat, thread, origin_json), workspace fields (cwd, git branch, repo root), profile name, rewind and archive flags, pin. messages holds the transcript. Tool calls are stored as a JSON string. Reasoning fields — reasoning, reasoning_content, reasoning_details, plus Codex-specific item blobs — stay in the row.

That last point is easy to get wrong. On the wire, a provider may reject a reasoning key by name. Hermes records the rejection for that provider, host, and model, strips the field, and retries once. The strip is a transport concern in the message sanitizer. It does not delete history. Strict providers (some hosted OpenAI-compatible routes) see no reasoning key. Others see reasoning_content, or additional OpenRouter-style carriers. DeepSeek, Kimi, and MiMo get a single-space pad on a reasoning-less tool-call turn because those APIs require the field. The database remains the superset. Chapter 4’s adapters project it down.

FTS5 is three virtual tables, not one: a default index over content, tool name, and tool-call text; a trigram index for substring and CJK-unfriendly tokens; a cjk_unicode61 index. Session search in Chapter 13 is a query over these indexes. The indexes are not a second store. If you export or recover a database, FTS is rebuilt, not copied as authority.

WAL mode is the concurrency choice. Many readers, one writer. A gateway with several platforms attached can read a sidebar while a turn appends. It is not a license for several writers.

The Gateway Is the Writer

The session-storage guide is explicit, and it supersedes the simplified “the agent saves the session” arrow on the architecture diagram. The profile’s gateway is the writer of canonical sessions. hermes chat, the TUI, desktop, the API server, ACP, cron, bot chat, and kanban workers are clients. They admit input to that authority. Out-of-process workers write through the owner over an RPC session store. They do not open state.db and insert transcript rows themselves.

sequenceDiagram participant Client as CLI / Desktop / ACP participant Auth as Session authority participant DB as state.db participant Agent as AIAgent Client->>Auth: admit input Auth->>DB: FIFO row queued Auth->>Agent: run the turn Agent->>DB: transcript via the owner Auth->>DB: settle admission Note over Auth,DB: owner death mid-turn marks the row unknown

The ledger tables make that contract durable:

  • session_admissions is a per-session FIFO: queued, then started, then a terminal state. An input that was started when the owner died becomes unknown at the next owner’s start. It is not replayed. Later inputs wait until someone resolves the unknown row. Replaying would repeat side effects the dead process may already have committed — a file write, a sent message, a cron delivery.
  • worker_executions and worker_receipts bind managed child work to a session and an owner epoch. Receipts are ordered and digest-checked.
  • runtime_epoch is the owner’s epoch and instance id.
  • delivery_obligations is the outbox of replies the gateway still owes, created lazily.
  • compression_locks stop two processes from compacting the same session.

Those four runtime tables reference sessions with ON DELETE RESTRICT. Deleting a session retires terminal ledger rows in the same transaction and refuses while work is live or unknown. hermes sessions recover copies row-bearing transcript tables and regenerates FTS. It inventories the runtime ledger and does not copy it. A partial ledger could replay a started effect or adopt another owner’s workers. A full backup restore keeps the ledger so startup can reconcile. Recovery and backup are different operations. Mixing them is how you double-send a message.

Batch trajectories and RL dumps are not this database. Chapter 17 names them so nobody “helps” by inserting ShareGPT rows beside user chats.

Lineage, Archives, and the Rows That Look Like Duplicates

Sessions point at a parent. Compression can split lineage that way: a child session continues from a summary, and parent_session_id is the chain. The default path in current config is quieter. In-place compaction keeps the same session id, marks the old rows active=0, and inserts the retained head, summary, and tail as active=1. A protected message can therefore exist twice with the same content and timestamp, once in each generation. Those archive rows are not duplicates to be deleted. Diagnose a double live write by filtering active=1, and check which profile’s file you opened before you conclude history “reverted.”

# Pseudocode — illustrates generations, not the schema
def compact_in_place(session_id, kept_messages):
    mark_active_rows(session_id, active=0)      # archive, do not delete
    insert_rows(session_id, kept_messages, active=1)
    # same primary key space, same session id, two generations

Undo and rewind are yet another visibility flag. The gateway’s exception-path writer also stamps an owner marker into display metadata so a crash after accept but around agent construction does not append the same user text twice. The probe follows the live compression successor and then ancestors. An unrelated process writing the same session cannot suppress the turn. This is failure-writer arbitration, not universal exactly-once delivery, and historical unmarked rows are not rewritten. Chapter 9 walks the same mechanism from the runner’s side. Here, remember the storage consequence: dedupe keys are explicit markers, not “the text looks the same.”

A Codex app-server path has a similar splice. The agent persists the accepted user input first. Codex then projects that input as a leading user event. Hermes drops only the leading item when it exactly matches what it already stored. Later user events, and a second identical turn that was separately accepted, stay. Content equality is not identity.

Deep Dive: What a Message Row Keeps That the Provider Never Sees

Provider messages must not contain the display-metadata sidecar. Platform message ids used for quote-reply are namespaced by platform, profile, scope, chat, and thread, while the original id remains for the adapter. Background-review harness messages and stale tool-call marker rows can be stripped on the way out to the model and still exist on disk.

Resume and export have size ceilings. Crossing them raises a dedicated error rather than silently truncating a transcript the user thinks they reloaded. The ceilings are configuration, with a safe default, because a multi-megabyte Telegram history will happily OOM a careless SELECT *.

Tests are fenced. Opening a real default-home or real named-profile state.db from a test process raises before the connection is used. The bypass is an explicit environment flag or a pytest mark, and it is not something a normal command sets. Combined with Chapter 2’s temporary HERMES_HOME, this is why the suite can exercise the real SessionDB class without eating a developer’s chats.

AsyncSessionDB sits beside the sync facade for callers that must not block an event loop on SQLite. The schema is the same file. A second database “for async” would split the writer rule in half.

Search indexing is transactional with the message insert on the happy path: the FTS tables are virtual tables fed by the content table, so a reader of session_search sees committed messages, not a side index someone forgot to update. Trigram and CJK tokenizers exist because a single unicode61 index is a bad search engine for the languages the gateway actually receives. Chapter 13 will treat search as a learning tool. The index design is finished here.

What This Chapter Refused

There is no per-platform database. Source tagging on the session row is how you filter Telegram away from the CLI. There is no “the CLI writes JSONL and the gateway writes SQLite” compatibility mode left as the primary path. There is no silent replay of a started turn after a crash. Each of those alternatives showed up in earlier personal-agent designs because they were easy. They lose the property Hermes actually needs: one transcript, one owner, a crash that pauses instead of repeating.

The next chapter chooses a model and an API mode. It reads model and model_config off the session row this chapter defined, and it must not invent a second place to store them. When the provider changes mid-session, the cache bill changes (Chapter 6) and the row records the new config. The messages do not get rewritten to match the new provider’s taste. Projection happens at send time. That split — store the superset, project on the wire — is the state layer’s real contribution to a multi-provider agent.

Apply This

One database per tenant, addressed only through the tenant root. The problem it solves: a shared SQLite file whose rows are “scoped” by a column everyone forgets to filter. The pitfall: a helper that defaults the path when the environment variable is missing. Missing must be the platform default resolved in one function, not a hardcoded string copied into five modules.

Appoint a single writer and make everyone else admit work. The problem it solves: two processes appending to one transcript and producing role sequences the provider rejects, or worse, double side effects. The pitfall: a “temporary” direct write for a migration script that becomes the path desktop uses because it was convenient.

Represent crash as an explicit unknown, and do not replay it. The problem it solves: at-least-once delivery applied to actions that are not idempotent. The pitfall: resolving unknown automatically on startup because the queue “looks stuck.” The queue is supposed to look stuck until a person or a policy says the lost turn will not be repeated.

Keep archive generations. Mark compacted rows inactive; do not delete them to make the table look tidy. The problem it solves: a debugger who cannot tell a rewind from a bug, and a compaction that cannot show its inputs. The pitfall: a unique constraint on (session, content, timestamp) that makes the legal archive insert fail.

Store the superset, project per provider. Reasoning and transport metadata stay in the row. Adapters strip fields the current route rejects. The problem it solves: a history that cannot be resumed on a different provider because it was saved in the first provider’s dialect. The pitfall: persisting the stripped form back into the row after a retry, so the original reasoning is gone for good.

Chapter 4: Talking to Models

Chapter 3 stored a model name on the session row and refused to store the provider’s wire dialect. This chapter is the resolver that fills that row, and the three dialects the turn will speak. CLI, gateway, cron, ACP, and every auxiliary call — vision, compression, memory flush, skills-hub bookkeeping — go through the same runtime resolver. If a surface grows its own “small” client factory, it will eventually send the wrong key to the wrong host. That bug is common enough that the resolver exists to make it structurally hard.

The implementation is split the way Chapter 1’s waist predicts. hermes_cli/auth.py holds the provider registry and resolve_provider(). hermes_cli/runtime_provider.py turns a request into api_mode, base_url, and credentials. providers/ is an ABC plus ProviderProfile records. Bundled plugins under plugins/model-providers/<name>/ register themselves with an API mode, a base URL, the environment variables that carry the secret, and fallback models. A user plugin in the profile home overrides a bundled plugin of the same name. Adding a provider is a plugin that calls register_provider(), not a new branch in the turn.

Three Modes, One Internal Transcript

Internally, history is OpenAI-style dictionaries: system, user, assistant with optional tool_calls, tool with a call id. That is the shape Chapter 3 stores. At the edge of the request the mode projects it.

  • chat_completions is an openai.OpenAI client against an OpenAI-compatible URL. OpenRouter, local servers, most hosted gateways, and provider: custom live here. custom is first-class: any compatible endpoint, plus a providers: map in config for named ones. A legacy list key is still read so old configs do not break.
  • codex_responses uses the Responses API. Credentials come from Codex’s auth store, not from a copied OPENAI_API_KEY. A resumed session can carry encrypted reasoning items the server no longer accepts (invalid_encrypted_content, or a 401 that is really an expired item token). The healer strips those cached items and replays once, before any credential refresh or pool rotation. Items minted after the strip keep replaying. A second rejection in the same session turns replay off. The transcript in SQLite is not rewritten wholesale; the strip is a send-time repair, consistent with Chapter 3.
  • anthropic_messages uses the native Messages API through agent/anthropic_adapter.py. Refreshable Claude Code credentials beat a copied environment token when both exist. Manual tokens still work as explicit overrides. Hermes preflights a refresh, and on a 401 it rebuilds the client and retries once.

def project(messages, mode):
    if mode == "chat":
        return messages
    if mode == "responses":
        return to_response_items(messages)
    if mode == "anthropic":

Reasoning is the sharp edge of projection. OpenAI-compatible relays return reasoning or reasoning_content as strings, as text-part dicts, or as lists of fragments. Hermes flattens those for the stream and for storage, preserving explicit whitespace and not inventing separators. reasoning_details is different: a list of opaque records appended in arrival order, never merged or rewritten, including nested signed payloads. Chapter 3 keeps them. This chapter’s sanitizer decides which carriers the current route is willing to see on the next request. When a route says “unknown field,” the rejection is remembered for that provider, host, and model for the rest of the session, the field is removed, and the call retries once. The memory of the rejection does not touch history.

Keys are scoped to hosts. OPENROUTER_API_KEY goes to OpenRouter. The AI Gateway key goes to the gateway host. OPENAI_API_KEY is the custom-endpoint key and the fallback, not a universal token. A real custom endpoint the user selected is not the same object as the OpenRouter fallback used when nothing is configured. Local servers and saved hermes model endpoints keep working when the shell has no OPENAI_BASE_URL. The resolver exists so those distinctions survive contact with a dozen plugins.

Pools, Fallback, and the Auxiliary Lane

A credential pool rotates after a rate limit only when it has somewhere to go. A single-entry pool retrying itself is not rotation; the turn falls through to the fallback model instead. The helper is deliberately small: the pool exists, it still has an available entry, and it contains more than one entry. Rotation onto a different account also changes the provider-side cache key. The next request pays full input price. That is a property of provider caches, not a Hermes bug, and Chapter 6 will refuse to “fix” it by pretending the prefix still hits.

Fallback is a chain of (provider, model) pairs, tried in order. The legacy single dict is still accepted and migrated on write. The agent stores the chain and a latch, _fallback_activated, so success does not bounce forever. Trigger points in the turn phases are: max retries on a malformed response, non-retryable client errors (401, 403, 404), and exhausted retries on 429 and 5xx. Activation builds a new client through the same auxiliary resolver, sets the API mode from the new provider, swaps model, provider, base URL, mode, and client in place, re-evaluates whether prompt caching applies, and resets the retry counter. It will not activate twice.

Context length is not a guess scattered through the loop. agent/model_metadata.py and the models.dev registry feed the compressor’s threshold and the preflight token estimate. Deep Dive: The Client Is Replaceable, the Transcript Is Not

When fallback swaps the client in place, the message list stays in the internal dialect. The next iteration projects again under the new mode. That only works because Chapter 3 stored the superset and this chapter projects at send time. If fallback rewrote history into Anthropic blocks, a later switch back to chat completions would be a parser. The in-place swap is allowed to change model, provider, base_url, api_mode, and client. It is not allowed to change the session id or to drop tool results that the previous model already produced.

OAuth refresh sits in the same layer. A 401 on the native Anthropic path rebuilds the client after a refresh attempt. A Codex encrypted-content failure is specifically not treated as “refresh the user.” The healer knows the difference between an expired item and an expired account. Collapsing both into one retry policy is how you either loop on a poisoned item or log the user out of a healthy account.

The catalog is large — OpenRouter, Nous Portal, Codex, Copilot, native Anthropic, Gemini, Bedrock, Azure, NIM, Ollama, LM Studio, a handful of regional endpoints, and custom — and it will keep moving as plugins are added. The book does not list it as a promise. The promise is the shape: a profile plugin, three modes, host-scoped keys, one fallback latch, auxiliary calls that are explicit about whether they share the main route.

/model is a shared pipeline (hermes_cli/model_switch.py) for CLI and gateway. It is also a cache break, which is why it is one of the few mutations allowed to rebuild prompt state, and why the user-facing docs warn about cost. The resolver will happily switch. The prompt chapter will explain what you pay.

Apply This

One resolver for every caller, including the “small” ones. Compression summaries and vision captions are not special enough to grow a private client. The problem it solves: an auxiliary path that works on your laptop’s env vars and fails in cron, where the saved config is the only config. The pitfall: a provider=main alias that does not actually re-enter the resolver, so “use the chat model” secretly means “use OpenRouter.”

Project a single internal transcript into N wire formats. Keep history in one dialect and convert at the socket. The problem it solves: a session that cannot resume after a provider switch because the rows were stored as vendor blocks. The pitfall: converting by mutating the stored list in place. Project into a copy. The next mode still needs the original.

Scope secrets to hosts. A key is valid for the base URL it was issued for. The problem it solves: the classic “we sent the production key to a local proxy because it was the first key we found.” The pitfall: a fallback path that swaps the URL and keeps the previous key because the field was already filled in.

Rotate a pool only when rotation can help, and latch fallback so it happens once. The problem it solves: a 429 retry loop against one exhausted credential, or a fallback that oscillates every error. The pitfall: treating a pool rotation as free. It is a new cache identity. Surface the cost; do not hide it.

Let a pinned route fail instead of wandering. If the user, the job, or the child named a provider and model, do not apply the ambient fallback chain. The problem it solves: a cron job that quietly changes models and delivers a different agent’s work. The pitfall: pinning by accident via an empty-string override that the resolver treats as “set.” Empty and absent must be the same.

Part II — The Core Loop

Chapter 5: The Turn

Chapters 2 through 4 produced an agent that knows its home, its database, and its provider. None of that answers a user. run_conversation does. It lives in agent/conversation_loop.py. The phases it calls live in agent/turn_*.py: preflight, iteration prep, request assembly, the API call, response intake, the tool round, the finalizer, and the error, overflow, and recovery paths. run_agent.py remains the name callers patch. The body is not in that file anymore, which is the facade rule doing the job Chapter 1 assigned it.

chat() is a thin wrapper that returns the final string. run_conversation() returns the dict: messages, usage, metadata, why the turn stopped. Every surface in this book calls the second one, even when the user only sees the string.

A Phase Machine, Not a Callback Soup

One user turn is an outer call that may contain many model iterations. The documented skeleton is still the right mental model, with the phase files as the places it got too big to live in one function:

The internal message list is the OpenAI shape from Chapter 4, including the alternation rules providers actually enforce. After the system message, roles alternate user and assistant. A tool round is assistant-with-calls, then one or more tool results, then the next assistant. Two user messages in a row are illegal. Two assistant messages in a row are illegal. Only tool results may sit next to each other, because parallel calls return in a burst. When a code path is tempted to “just insert a note,” it has to insert it somewhere those rules allow. That constraint is why several of the clever injections below target the newest tool result instead of the transcript head.

The API call itself is interruptible. The HTTP request runs on a worker while the main thread waits on the response, an interrupt event, or a timeout. A new user message, /stop, or a signal abandons the worker. The partial response is not written into history. Abandon means abandon. A half-parsed tool call in the transcript is worse than a lost second, because the next request would send a malformed assistant turn and the provider would reject the session.

What “Stop” Is Allowed to Mean

The loop stops for boring reasons and for expensive ones. Boring: the model returns text and no tool calls. Expensive, and each one is a distinct result rather than a generic exception:

  • The iteration budget is exhausted. Each agent holds an IterationBudget. The product default for a CLI turn is agent.max_turns (500). A child gets its own budget, delegation.max_iterations (default 50), so a parent plus children can exceed the parent’s cap. The constructor will also accept an explicit cap, and a library caller that passes none is not silently clamped — AIAgent’s own default is unlimited until a surface supplies the policy. execute_code iterations can be refunded so a programmatic tool loop does not eat the conversational budget. At the cap, the agent stops and returns a summary of work already done. Intermediate “you are running out of turns” warnings were removed: they taught models to give up early.
  • A wall-clock run budget crosses 80%. A one-shot notice is appended, once, telling the model to stop discovering and produce the deliverable from state it already has. The latch lives on the agent. The notice is appended to the newest tool message, and only if that message has not yet been persisted. Editing an older, already cached tool result would break the prefix. If there is no legal place to put the notice, it is not injected.
  • The user interrupts, steers, or redirects. An active-turn redirect cancels the in-flight model call and continues the same turn; steer lands at a tool boundary. Neither creates a new admission. A scaffold marker records that a response was interrupted by a correction so the next model call can see the seam without a second assistant bubble.
  • Billing or entitlement failures. The turn becomes a terminal result with a user-visible label, not an infinite retry.
  • Compression cannot make the request fit, or it times out while the request is still oversized. That is a terminal result, not a silent send of a request the provider will reject.
  • A post-compaction handoff would otherwise be the only thing the model sees. If compaction left a summary and dropped the user’s ask, the loop re-appends the real user message. If it cannot, it does not call the model to “continue” a summary, and the final text is a short status that the previous response is complete. Replaying the previous assistant prose would duplicate it in the transcript and deliver it again as if it were this turn’s answer.
# Pseudocode — illustrates the handoff guard
def before_model(history, original_ask):
    if summary_would_drive(history) and original_ask:
        if history[-1] is not original_ask:
            history.append(user(original_ask))
        return "call"
    if summary_would_drive(history):
        return "skip"  # do not let the summary impersonate the user
    return "call"

Fallback from Chapter 4 sits inside this machine, not beside it. Malformed responses, auth errors, and exhausted transient retries call the activation helper. A Codex turn that stalls on reasoning-only output — several continuations with no visible text and no tool call — fails over with reason incomplete_response. If the stall already spent the iteration budget, the fallback gets one bounded grace call, not a fresh 500. The latch still fires only once.

A repetition guard watches for a runaway loop and interrupts it. A review fork with an explicit input-token budget stops at the start of the next iteration, so the request that crossed the line is allowed to finish. These are different budgets. Conflating “iterations,” “wall clock,” and “review input tokens” into one counter is how you kill a healthy long task or let a detached review spend without a ceiling.

The Tool Round, Briefly

A single tool call runs on the main thread. Several run on a pool, unless one of them is interactive (clarify), in which case the batch is sequential so a question is not asked in parallel with a shell command that assumed the answer. Results are written back in the model’s original order no matter which worker finished first. The next request’s prefix depends on that order. Completion order is an accident; call order is the contract. Chapter 8 is the pool and the backends. Chapter 7 is the registry, the hooks, and the four tools that never reach it.

Agent-level tools — todos, memory, session search, delegation — are intercepted in agent/tool_executor.py before handle_function_call(). They need the live agent. The turn knows about them because their results are still ordinary tool messages. The model cannot tell an intercept from a registry dispatch, which is the point.

Callbacks are how a door watches without forking the loop: tool progress, thinking, reasoning, clarify, step, stream deltas, status. The CLI paints a spinner. The gateway posts a chat update. ACP updates editor status. The turn invokes a callback if one was passed at init. It does not import Ink or Telegram.

Deep Dive: Ephemeral Pressure Without a Cache Break

Preflight compression, covered properly in Chapter 15, runs before the request when the anchored token estimate crosses the threshold. The turn’s job is to call it and to survive it. Two details are turn policy rather than compressor policy.

First, token estimates lie, and the loop knows which lie it is telling. A session that is about to be pruned by native Responses compaction must not use the generic “sum the whole transcript” estimate for the mid-turn guard. That estimate counts messages the transport will checkpoint away, fires a long local compression the request never needed, and stalls the user. When the native estimate is available it wins. When it is not, the generic estimate remains, plus a rough tool-schema cost. The system prompt is counted once, not once in the messages and again beside them.

Second, a persisted tool row is immutable for the purpose of notices. The run-budget wrap-up, the iteration-budget note, and the interrupt scaffold all refuse to edit a message that already carries the database-persisted marker. The newest unpersisted tool result is the only mutable tail. This is the same idea as /steer. If you need the model to notice something mid-turn, you append to the tail. You do not reopen history.

Context-engine hooks (on_session_end, turn-complete) are best-effort and must not raise into the user’s turn. Plugin and engine failures are logged. A context engine that throws during a transition does not discard the reply the model already produced. Session end flushes the engine at the same moment memory flushes, so per-session engine state cannot leak into the next session. That pairing is Chapter 13 and Chapter 15’s problem to justify. The turn just refuses to let either of them be “whenever someone remembers.”

Outer-loop errors have a display path that is not the Python traceback. Failed turns get a kind, a notice, and a redacted metadata blob safe to put in a gateway message. A provider stream parse error is classified rather than shown raw. The user on Telegram did not ask for a stack frame, and the stack frame may contain a URL with a credential.

Persistence Is the Last Phase, Not a Side Effect

When the turn finalizes, the session store receives the new messages through the writer rules in Chapter 3. Memory flush runs if this boundary is a real one, not merely “a turn happened.” Idle time does not finalize a conversation. /new, /reset, and /resume do. The turn returns a dict the door can render. A gateway will deliver it. A CLI will print it. A cron job will hand it to the delivery target. None of them re-enter the model to “format for Slack.” Platform hints were already in the prompt, or will be, in Chapter 6. Formatting-by-second-call is a cache and a latency mistake.

The phase files are bound at import. A comment in the loop says why: a source-tree swap must not load a skewed phase in the middle of a turn. Hot reload of the brain under a live conversation is not a feature. If you need new phase code, you restart the process. The early-recovery path in Chapter 2 is how that restart stays safe.

You now have a turn that can call a model and stop for reasons you can name. The next chapter is why step 3, “build or reuse the cached system prompt,” is the most expensive line in the skeleton to get wrong.

Apply This

Encode termination in the result, not in an exception hierarchy. Budgets, interrupts, billing, handoff skips, and compression failure are different outcomes a caller must explain to a human. The problem it solves: a bare RuntimeError at the gateway boundary that becomes “something went wrong” for six unrelated causes. The pitfall: so many result kinds that callers match on three and ignore the rest. Keep a display kind for humans and a machine reason for logs.

Give each nested agent its own budget, and refund work that is not a turn. The problem it solves: a shared global counter that lets a child starve a parent, or a parent hide unlimited spend inside children by not counting them at all. The pitfall: a default cap baked into the library constructor so embedded callers inherit a CLI policy. The surface passes the cap. The counter just counts.

Append notices to the unpersisted tail. Mid-turn warnings belong on the newest tool result that has not been written to the store. The problem it solves: a “helpful” system message inserted at the head of history that invalidates the cached prefix every time the budget ticks. The pitfall: appending even when the only tool result is already persisted. Skip the notice. A cache break costs more than a quiet turn.

Abandon interrupted requests without splicing a partial assistant. The problem it solves: a cancelled stream that leaves a tool call without results, which the next request then sends and the provider rejects, poisoning the session. The pitfall: cancelling the HTTP call but still committing the tokens you already parsed “so the user sees something.” Show them a status. Do not show the model a lie.

Do not let a summary impersonate the user. After compaction, restore the original ask or skip the model call. The problem it solves: a continuation that treats the handoff as a new instruction and does a second, unrequested piece of work. The pitfall: restoring by copying the previous assistant text into the final response, which duplicates it in the transcript and delivers it twice.

Chapter 6: The Prompt That Must Not Move

Chapter 5’s skeleton builds a system prompt once and then reuses it. This chapter is that prompt: three tiers, a handful of bytes that are allowed to change, and a cache plan that spends Anthropic’s four breakpoints on purpose. Get the tiers wrong and every later feature — memory, skills, platform hints, a clock — becomes a bill.

The files are agent/system_prompt.py and agent/prompt_builder.py, with markers applied by agent/prompt_caching.py. The prompt is built once per session and reused across turns. Context compression is the rebuild. That sentence is the invariant. The rest is how the code keeps it true while still telling the model what it needs to know.

Three Tiers, Joined in an Order That Protects the Prefix

build_system_prompt_parts returns stable, context, and volatile. The full prompt is those strings joined, dropping empties. The stable tier is also cached on the agent as the static prefix so cache markers can split “rarely changes” from “changes on a rebuild.”

Stable. Identity comes from the profile’s SOUL.md, or a built-in default when soul loading is off — delegation sets that so a child does not inherit a persona it should not wear. Tool guidance, a skill-pointer paragraph chosen only when skill_view exists and the hermes-agent skill is actually in the index, model-specific lines, and the coding operating brief sit here. Pinned skills that were resolved once at session start are constants, so they stay in the stable prefix too. Guidance that mentions tools the session does not have is omitted. An absent tool must not widen another tool’s job; the memory guidance says this in prose the model reads, and the builder enforces it by which paragraphs it includes.

Context. The caller’s optional system message, then project context files, then the worktree snapshot. Context-file discovery is a priority walk, first match wins: .hermes.md / HERMES.md up to the git root, then AGENTS.md, then CLAUDE.md, then .cursorrules and .cursor/rules. SOUL.md is not loaded twice if identity already took it. Long files are truncated. The workspace block is a live git probe, and that is dangerous: re-probing on every compaction rebuild would change bytes whenever the repo moved and defeat the “keep the stored prompt” fast path. So the snapshot is pinned on the agent for the session, keyed by the cwd a gateway might be serving many of, seeded from the stored prompt when this process did not build it, and dropped on session reset.

If there is no workspace snapshot, the trailing coding guidance and the platform hint stay in the stable tier. There is nothing worktree-shaped whose later position would lengthen a shared prefix. If there is a snapshot, those blocks follow it, in the context tier, so two worktrees of one project can still share the prefix through the shared AGENTS.md. The platform hint is part of that post-workspace group: a one-line environment probe (skipped for remote backends and when nothing is wrong), bot-mode protocol, then platform_hint. Operators can append or replace a single platform’s hint from config.yaml without editing Python. A bare string means append. A malformed entry is ignored, so a bad value cannot break assembly or leak into another platform. Cron runs as platform cron but also carries the delivery channel’s hint under a “delivery destination” line, which is why a Slack append shows up in a Slack-delivered job.

Volatile. The skills index leads this tier, on purpose. Skills are mutable. On a longest-prefix cache an unchanged index is still inside the reused prefix; a changed index re-prefills only from here. Then the frozen MEMORY.md and USER.md snapshots, the external memory-provider block, plugin sections anchored after memory, the active profile line, a date line, and finally the runtime-environment block with an explicit end marker.

The profile line names this home’s path, so it cannot live in the stable tier. If it did, two profiles on one host could not share a byte-identical scaffold. The date line is the date, not the timestamp: byte-stable for the calendar day, with zone and offset so the model still knows where it is. A full ISO timestamp would bust the cache every build. Session start time is anchored so a rebuild during compression does not pretend the conversation began at the rebuild.

The runtime block is last so quoted examples inside AGENTS.md or a plugin cannot be mistaken for the real cwd. When a stored prompt is checked against the running process, the matcher reads the host paragraph after that heading and trusts the end marker. Model and provider are read before the boundary. Platform: is deliberately not an identity field.

What Is Not in the Cached Prompt

These are applied at API-call time and are not persisted as the system prompt:

  • the ephemeral system prompt and HERMES_EPHEMERAL_SYSTEM_PROMPT
  • prefill messages
  • gateway session overlays
  • external recall injected into the current user message, not the system prompt
  • pre_llm_call plugin context, concatenated onto that same user message

A skill index that changed under a long-lived CLI, TUI, or desktop session is handled the same way. Each turn compares the stored <available_skills> block with the index a fresh build would produce. The delta rides a one-shot note on the user-message channel, and only when the delta itself changes. The in-process index cache is keyed on file signatures, so another process’s write is visible. The stored prompt’s index converges at the next rebuild, which means compaction. A surface switch, desktop to TUI, keeps the stored bytes and delivers the new surface’s guidance as that same kind of note (agent/surface_switch.py). The prefix survives.

# Pseudocode — illustrates where a change is allowed to land
def assemble_request(stored_prompt, history, user_text):
    system = stored_prompt                      # do not rebuild
    note = skill_index_delta(stored_prompt)     # may be empty
    note += surface_switch_note()               # may be empty
    history[-1] = attach_note(user_text, note)  # per-turn channel
    return [system, *history]

Mid-session memory writes update disk and do not touch the cached prompt. The model keeps the snapshot it was given at build until compression or a new session reloads it. That feels like a bug the first time you tell the agent “remember this” and the system prompt still shows the old fact. It is the cache invariant. The memory tool’s result, in the transcript, is how the current session sees the write. The next session sees the file. Chapter 13 is the user-facing consequence. Do not “fix” it by rewriting the system message in place.

Slash commands that change prompt state defer to the next session. /skills install --now is the opt-in that says the user accepts a cold cache. /model is the other explicit break, and Chapter 4 already warned that a model switch is a new cache identity even if the bytes matched.

Deep Dive: Four Breakpoints, Spent on the Prefix

Anthropic allows four cache_control breakpoints. apply_anthropic_cache_control strips any previous decoration first, then spends them idempotently so a retry cannot accumulate a fifth marker.

When the stable prefix is known, the static system prefix and the full system prompt each get a marker, and the remaining two go to the latest cacheable non-system messages. When it is not known, the legacy layout is “system and 3”: the system prompt, then the third-to-last, second-to-last, and last cacheable non-system messages. A direct native tool-cache layout moves the volatile system’s budget onto the tools array: only the static prefix is marked on the system side, the last tool definition carries a marker, and two completed transaction endpoints in the message list take the rest.

flowchart LR B1["Breakpoint: static system prefix"] --> B2["Breakpoint: full system prompt"] B2 --> B3["Rolling: recent message"] B3 --> B4["Rolling: latest cacheable message"]

Markers are ephemeral, with TTL 5m or 1h. prompt_caching.cache_ttl: auto resolves once per session: 1h for human-paced sources, 5m for machine-paced ones (subagent, cron, oneshot, webhook, kanban, api, tool, batch). Auxiliary calls treat auto as 5m. Caching turns on for Claude models when the route understands cache_control — native Anthropic or OpenRouter. A string system content is wrapped into a text block to hold the marker. List content gets the marker on its last element. Tool messages can carry it on the native path.

Compression invalidates the cached transcript region and leaves the system breakpoint able to hit again once the stored prompt is the new one. The rolling window re-warms within a turn or two. A credential-pool rotation or a fallback onto another account is a cold cache even when every byte matches, because the provider keys the cache by model and account. Hermes does not pretend otherwise. Features that silently swap model or credentials mid-session are rejected on cost grounds, not taste.

reconstruct_static_prefix exists because only the full prompt is persisted. On restore, on keep-prompt compression, and on mid-turn failover onto a cache-capable provider, the stable tier is rebuilt and used only if the stored prompt literally starts with it. Otherwise the stored bytes are sent untouched and the static split stays empty. A failed rebuild is memoized per stored string so the retry loop does not redo the file reads. Legacy prompts that predate the tier reorder still validate; they are not rewritten to the new layout just to make the matcher happy.

The prompt surface is reviewed like code. A CI render builds the stock system prompt and the tool list for several surfaces and model families, with the clock and paths pinned, and fails if the committed snapshot drifted. A one-line guidance move between tiers shows up as a diff a reviewer can read. User SOUL.md and installed skills do not touch that snapshot. The render is the stock product, not your home directory.

Why the Builder Is Not a Config File

The supported ways to change what the model reads are the inputs: SOUL.md, MEMORY.md, USER.md, project context files, skills, an optional system message, ephemeral overlays, platform_hints. Editing prompt_builder.py is a product change. The file is the plumbing that keeps the prefix stable for everyone. The project’s own review guidance says that plainly, and it matches the waist: identity and procedure live at the edges, the order of bytes lives in the core and is jealous of its order.

You can now see why Chapter 5 treated “reuse the cached prompt” as a step rather than a function call you re-run every iteration. The next chapter puts tools into that same frozen surface. A toolset swap mid-conversation is a prompt edit, whether or not you touched the system string. The schema list is part of the prefix.

Apply This

Order the prompt from frozen to volatile, and put identifiers last. Identity and standing guidance first, tenant-specific names and clocks at the end. The problem it solves: a profile path or a timestamp early in the prompt that makes two tenants share nothing. The pitfall: a “small” identity line that includes the cwd. One volatile field in the stable tier zeroes the win.

Put mid-session deltas on the current user turn. Skill-index changes and surface switches are notes, not system-prompt rewrites. The problem it solves: a long-lived session whose cache dies every time a skill file changes on disk. The pitfall: emitting the note on every turn even when the delta is unchanged. The note itself must be stable or you have invented a new bust.

Pin anything you probe. A git workspace snapshot is a probe. Freeze it for the session. The problem it solves: compaction rebuilds that see a new commit and rewrite an otherwise identical prompt. The pitfall: forgetting to drop the pin on /reset, so the next session inherits the previous repo’s snapshot.

Spend cache breakpoints explicitly and strip them before reapplying. Four markers, idempotent. The problem it solves: retries that stack markers until the provider rejects the request. The pitfall: marking the volatile tail of the system prompt when you meant to mark only the static head, so every memory edit looks like a prefix change even on routes that could have cached the head.

Separate the stock prompt you review from the user prompt you load. Snapshot the default surface in CI. Load SOUL.md at runtime. The problem it solves: a guidance tweak that ships unnoticed because nobody renders the prompt the model sees. The pitfall: snapshotting a developer’s home directory and calling it the product.

Chapter 7: Tools — Register, Gate, Dispatch

Chapter 6 froze the system prompt and warned that the tool list is part of the same prefix. This chapter is that list: how a function becomes a schema, how a schema disappears when its backend is down, and why four tools the model can call never run through the generic dispatcher.

The pieces are tools/registry.py (ToolRegistry, ToolEntry), model_tools.py (get_tool_definitions, handle_function_call), and toolsets.py (groups and platform presets). Agent-level intercepts live in agent/tool_executor.py, called from the turn in Chapter 5. Read them in that order or the intercepts look like a special case someone forgot to register. They are registered. Their handlers are stubs if you skip the intercept.

A Tool Is a Record, Not a Function

# Pseudocode — illustrates the record, not the dataclass
Tool = {
    "name": "read_path",
    "group": "files",
    "schema": {...},                 # what the model sees
    "handler": read_path,
    "available": probe_or_none,      # check_fn
    "needs_env": ["SOME_TOKEN"],
    "is_async": False,
    "result_cap": 50_000,
    "schema_extra": lambda: {},      # merged at every definitions build
}

ToolEntry carries the name, the toolset, the JSON schema, the handler, an optional check_fn, required environment names, an async flag, a description, an emoji for the UI, a result-size cap, and optional dynamic schema overrides. Those overrides are a zero-arg callable merged onto the schema every time definitions are built, so a description can reflect a live limit — delegation’s depth cap, for example — without a new registration. Identity matters: restore and compare-and-swap paths use is, not name equality, so two entries with the same string are not the same tool.

Registration is a call at import. Discovery walks the tools tree, parses modules cheaply to see whether they actually call register, imports those, and caches the module list. A file that defines a helper and never registers is not a tool, no matter what its name suggests. MCP discovery runs next (tools/mcp_tool.py and its siblings read server config and register the remote tools). Plugin discovery runs after that, from the user home, the project, and package entry points. A plugin may not replace a builtin unless the operator opted in. The refusal string names the plugin and the tool. Silent override is how a third-party package becomes a backdoor into terminal.

Gating Is a Probe with a Memory

check_fn answers “can this process reach the backend right now?” Docker, a Modal SDK, a browser binary, an API key. It does not answer “does this session feel like using the tool?” Per-session surface changes are a different mechanism. The development guide is strict about that: a check that flips every turn will thrash the schema and the cache.

Probes are slow and flappy, so results are cached for a short TTL, on the order of half a minute, keyed so a profile dimension cannot grow the cache without bound. A failure inside a short grace window after a success returns the last good True and does not cache the failure. A docker version that times out under load must not strip read_file from a child agent mid-build — the symptom is a subagent reporting that a core tool does not exist. A failure that outlives the grace window is honored, so a backend that is actually dead stops advertising tools. Some checks are marked uncached because they only read local config and must be exact. Browser identity keys are part of the cache key where a session-scoped browser would otherwise leak another task’s “yes.”

Toolsets are named groups. Platform presets decide which groups a CLI session, a Telegram chat, or a cron job receives. Old names ending in _tools still map forward. Selection is two lists, enabled and disabled, applied to the discovered set. An empty enabled list is not “everything” when a caller passed it on purpose; cron learned that the hard way, and Chapter 10 keeps the distinction. AIAgent treats a missing enabled list as “all toolsets,” which is why unattended surfaces must pass an explicit list.

Dynamic rewriters then edit schemas the model will actually see. execute_code advertises only the tools this session can call. Browser navigation, CDP, and exec schemas shrink or vanish based on the active backend. delegate_task’s description grows the current depth and concurrency limits so the model reads the policy in the tool it is about to call. Rewriters compose. They run at definition time, not at call time, because the schema is the contract the provider cached.

The Dispatch Pipeline

handle_function_call is the seam. The shape, with agent-level tools already peeled off by the turn:

guard the name and the arguments
run request middleware
pre_tool_call hook, unless a caller suppressed it
approval gate for dangerous commands
execute, or bridge an async handler onto a loop
transform_tool_result hook
post_tool_call hook
return a string the model can read, or a JSON error

Hooks that throw do not take down the turn; the registry’s job is a string result either way. Argument JSON is repaired when models emit trailing commas or truncated objects. Surrogates are sanitized before they hit a provider that rejects them. Tool-call ids are canonicalized because strict providers dedupe or reject duplicates, and Codex’s Responses ids are not the same shape as chat-completions ids. That work is sanitization at the boundary, Chapter 4’s projection applied to the tool channel.

Async handlers cannot be called from the sync dispatcher directly. The bridge depends on who is asking. A CLI with no running loop uses a persistent event loop so cached async clients stay alive. A gateway that already has a loop spins a disposable thread with asyncio.run so it does not deadlock the platform loop. Worker threads in the parallel tool pool keep a per-thread loop in thread-local storage. One bridge for all three will either deadlock the gateway or reconnect a CLI client on every call.

Approval sits in this pipeline and is implemented in tools/approval.py. Chapter 16 is the threat model: hardline blocklist, user deny rules, YOLO, gateway prompts. The dispatch chapter’s only claim is that the check happens before the handler, and that a plugin pre-hook can also deny. A tool that shells out inside the handler and skips the gate is a bug, not a shortcut. An interactive trace of this pipeline, with the command gate expanded, sits in Chapter 16.

Result size is capped per tool. A terminal session that returns a megabyte of logs will blow the next request and then force compression. The cap turns that into a truncated string the model can ask to narrow. Observers — metrics, the UI — get a side channel of tool name, duration, and a redacted preview. They do not get to rewrite the result unless they are the transform hook, which is explicit.

Schemas for all four are still registered, so get_tool_definitions includes them and the model sees a normal tool. If dispatch reaches the registry handler anyway, it returns a stub error. The intercept is not an optimization. It is the only path that has the live objects. Chapter 12 (delegation) and Chapter 13 (memory and search) own what the intercepts do. This chapter owns why they exist: agent state is not a global the registry may import without tying every tool import to the agent class, which is the cycle the facade layout exists to avoid.

Plugin tools and memory-provider tools take a related path. Context engines may expose their own tools the same way. The pattern repeats because the state those tools mutate is per conversation. A process-global handler would cross sessions the moment the gateway ran two chats.

Deep Dive: The Footprint Ladder Is a Cache Policy

The root guide’s ladder — extend, CLI plus skill, service-gated tool, plugin, MCP, new core tool — reads like governance. It is also a prefix-cache policy. Every core schema is present in tools[] on every request of every session that enabled the toolset. A tool used by three people still costs every user’s cached prefix the day it joins _HERMES_CORE_TOOLS. A skill costs an index line until someone loads the body (Chapter 14). A plugin tool costs only the profiles that installed it. MCP costs the sessions whose config enabled that server.

Service gating via check_fn is the middle rung that people skip. The tool is core code, but it is absent from the schema when the probe is false, and the probe is not allowed to mean “this session.” Session-scoped enablement belongs in toolsets and in the enabled list passed to AIAgent, which changes between sessions, not between turns. Mid-turn toolset swaps are prompt edits. Chapter 6 already forbade those without an explicit rebuild.

invalidate_check_fn_cache exists for the operator who just installed Docker and should not wait for the TTL. It is not called between tool calls of one turn. Discovery itself is cached on disk so the next process does not re-parse every module. Both caches assume tools change at human speed. An agent that writes a new tool file and expects the running process to see it has misunderstood the layer. Restart, or send the user through the plugin loader’s explicit refresh. Do not importlib.reload the registry under a live turn.

Apply This

Make availability a cached probe with a last-good grace. The problem it solves: a flapping dependency check that removes a toolset for one build and breaks every child spawned in that window. The pitfall: a grace window so long that a genuinely removed binary stays advertised for the rest of the day. Tens of seconds, not tens of minutes.

Rewrite schemas at definition time, in one pass. The description the model reads should include the limits you will enforce. The problem it solves: a tool doc that says “spawn as many children as you need” while the handler rejects depth greater than one. The pitfall: rewriting on each call so two iterations of one turn see different schemas and the provider cache splits.

Return strings, not exceptions, across the tool boundary. Hooks, probes, and handlers fail closed into a JSON error the model can correct. The problem it solves: a plugin bug that aborts a twenty-minute turn. The pitfall: swallowing the error into an empty string. Empty looks like success. Include a stable error key.

Intercept the tools that need the conversation, and stub the registry path. The problem it solves: handlers that import the agent facade at module level and cycle, or that use a global “current agent” and cross sessions. The pitfall: forgetting the stub, so a missed intercept writes memory with no store and returns a confusing success.

Treat a new core tool as a tax on every request. Climb the ladder first. The problem it solves: schema bloat that shows up as a cache and token regression the feature’s author never measured. The pitfall: hiding a core tool behind a check that defaults to true. A probe that always passes is not a gate.

Chapter 8: Running Somewhere Other Than the Laptop

Chapter 7 put a name on a tool and refused to run it when a probe said the backend was missing. This chapter is what those probes are protecting: the same tool names executing in different places. A personal agent that only runs on the machine where the REPL is open is a demo. Hermes treats the execution environment as a plugin behind terminal, browser_*, and web_search / web_extract.

The terminal family is the clearest, because it has an ABC. tools/environments/base.py defines BaseEnvironment. terminal_tool selects an implementation from TERMINAL_ENV. The modules in the tree are local, Docker, SSH, Singularity, Modal (direct and a managed variant), Daytona, and Vercel Sandbox, with shared helpers for remote transports, file sync, output, and streams. The architecture diagram’s “seven backends” is this list, not a metaphor.

Each backend knows how to start a session, run a command, stream output, copy files, and tear down. The model does not. It calls terminal with a command. The environment was chosen when the agent was built, usually from config, sometimes from an explicit flag for a one-shot remote job. check_fn for the toolset probes the chosen backend — is the Docker socket there, are Modal credentials loaded, does the SSH host resolve — and the schema from Chapter 7 includes or omits the tool accordingly. A failed probe is a missing tool, not a shell error halfway through a plan.

Local is the default and the one with the most policy: environment filtering, a Python path that does not accidentally export the agent’s own environment into the user’s command, and a cwd that Chapter 2 only stamps for local CLI sessions. Remote backends do not invent a host cwd for the session row. They have a remote workspace instead. File sync is explicit. Assuming the remote disk matches the laptop is how a patch “succeeds” in the transcript and never lands in the repo the user has open.

Cleanup is a turn-end and a process-end concern. The facade tracks the active environment and will call a VM cleanup and a browser cleanup even if one of them throws, so a Daytona sandbox is not leaked because the browser closer failed first. Background processes live in a process registry with a bounded output tail. Readers of that registry do not consume the notifications meant for the model. A UI poll and a tool result are different consumers of the same bytes.

Concurrency of tool calls is the turn’s policy from Chapter 5, restated where it bites. One call, main thread. Many calls, a pool, results restated in model order. Interactive tools refuse the pool. The pool size is capped. Parallel terminal calls against one local cwd are how two patches interleave. Parallel calls against one exclusive sandbox are worse. Backends that cannot actually run concurrently have to say so; the pool will not infer it from the tool name. Worktree isolation for child agents (Chapter 12) is the delegation-shaped answer to the same problem: give parallel workers different directories instead of hoping the backend locks.

Browsers Are a Second Family, Not a Flag on Terminal

The browser tools are a facade (tools/browser_tool.py) plus siblings for CDP, cloud providers, snapshots, sessions, vision, and lifecycle. The docstring names the backends the facade actually switches on:

  • Local headless Chromium, driven either by Hermes’s own tools or by a Browser Use harness.
  • Cloud: Browser Use, Browserbase, and Firecrawl. No local browser required. browser.cloud_provider selects among them.
  • Camofox: a local anti-detection server (Firefox-based fingerprint spoofing) spoken to over its REST API. It is selected as a provider (camofox), not by the mere presence of CAMOFOX_URL once a selection exists. It has no CDP endpoint. Setups that need raw CDP keep the built-in tools instead of the harness.
  • Lightpanda: a headless engine Hermes can spawn, including inside the Browser Use harness via an engine flag, with a Chrome fallback for actions Lightpanda does not implement yet.

That is more than the “five backends” line in older architecture diagrams, and the honest count is “a local engine, three cloud providers, Camofox, and Lightpanda,” with CDP attach (browser.cdp_url, /browser connect) as a mode that latches onto an already-running Chrome, Brave, Chromium, or Edge rather than a separate product. Raw browser_cdp is its own tool, gated on a CDP endpoint existing. Camofox is REST-only and the CDP tool’s check fails closed there, with a message that says so.

Hybrid routing is the subtle bit. Cloud browsers cannot open your laptop’s localhost. When a cloud provider is configured, Camofox is off, no CDP override owns the whole session, and browser.auto_local_for_private_urls is on, a private or loopback URL is sent to a local sidecar session keyed beside the cloud session. Public URLs stay on the cloud browser. The sidecar is not a second tool name. It is the same browser_navigate choosing a session key. DNS failures are not treated as private; only obvious names and resolved private, loopback, link-local, and CGNAT addresses are. A local proxy’s fake-ip range is excluded so a proxy that answers for the whole internet does not drag every URL onto the sidecar.

Browser sessions outlive a single navigation and die at task teardown. Cloud sessions are cached per provider and scope so a ten-step scrape does not create ten browsers. Vision and snapshot siblings exist because “what is on the page” is a different operation from “click the button,” and the model is better at the former when you hand it a structured accessibility tree or a screenshot through the vision path instead of a raw DOM dump. Credential passthrough for logged-in browsing is a security decision Chapter 16 constrains. The backend only provides the pipe.

Web Search Is a Registry of Vendors

web_search and web_extract sit on tools/web_tools.py and agent/web_search_registry.py. The architecture diagram’s “web (four backends)” is stale. The code autodetects, in order, Tavily, Perplexity, Exa, Parallel, Keenable, Firecrawl (key, self-hosted URL, or the managed tool gateway), SearxNG, Brave’s free tier, and DDGS, then any plugin-registered provider, then a keyless tier that must not preempt a keyed one. The default named fallback when nothing is configured and nothing is detected is Firecrawl, for compatibility. A stored web.backend is returned as-is, with no availability probe and no silent reroute. A broken selection should surface the vendor’s error. nous as a managed selection is serviced by Firecrawl through the tool gateway for the shared path; search specifically can be served by a managed Perplexity route when that is the configured search backend. Per-capability keys (web.search_backend, web.extract_backend) do not reroute the other capability.

Deep Dive: Why the Model Sees One Name

The temptation is a tool per backend: docker_exec, ssh_exec, modal_exec. The schema tax from Chapter 7 is the reason not to. The model plans in operations (“run the tests,” “open the docs,” “search the web”). The operator plans in placements (“this profile’s terminal is a Daytona sandbox,” “this one is SSH to a GPU box”). Those change at session or profile granularity, which is legal for the cache, not at turn granularity.

Environment variables the sandbox receives are a deliberate subset. The tool-call worker strips the process environment and re-adds the keys the backend legitimately needs. A skill can declare extra passthrough in frontmatter. The default is not “inherit everything,” because everything includes the agent’s own API keys. Chapter 16 is the threat; the mechanism is here so you see it beside the ABC rather than as a security afterthought.

terminal also has a lifecycle distinct from a single command: long-running servers, background jobs, a later read of their output. The process registry is that lifecycle. Backends that only support a one-shot exec have to emulate it or refuse it. Pretending a serverless sandbox is a persistent TTY produces transcripts full of “session not found” that the model then retries into a cost spike. The probe and the schema rewriter should remove operations the backend cannot do, the same way CDP disappears on Camofox.

Teardown is part of the contract. A gateway process lives for days. A sandbox created on Monday and forgotten is a bill. The agent facade’s quiet cleanup runs sibling closers and swallows their exceptions so one failure cannot skip the rest. Swallowing is correct at teardown and incorrect at call time. Do not copy the teardown helper into the dispatcher.

Apply This

Hide placement behind an ABC and a session-scoped selector. The model calls run and browse and search. Config picks the place. The problem it solves: a tool list that teaches the model your infrastructure diagram and breaks when you move a workload off the laptop. The pitfall: a selector that can change mid-turn. Placement is session state. Changing it is a new session, or at least a new prompt build.

Probe once, then omit the tool. A missing Docker socket is a schema decision. The problem it solves: plans that depend on a backend and fail on the third step. The pitfall: probing on every call and flapping, which Chapter 7’s grace window exists to dampen. Use that cache. Do not invent a second one in the backend.

Route by capability inside one tool when the name should stay stable. Private URLs to a local browser while public URLs stay on a cloud browser is a session-key choice, not a new tool. The problem it solves: cloud browsers that cannot see localhost, without making the model remember which tool is which. The pitfall: classifying every DNS failure as private and silently moving traffic onto a sidecar that was meant for exceptions.

Fail a stored vendor choice loudly. Autodetect is for the unconfigured install. A user who pinned a backend gets that backend’s error. The problem it solves: a silent fallback that spends a different vendor’s quota and returns a different shape of result. The pitfall: autodetect order that prefers a keyless scraper over a key the user just exported. Keyed rungs first, keyless last.

Tear down in a loop that continues after errors. Execute in a path that does not. The problem it solves: leaked sandboxes when the first closer throws. The pitfall: using the same “never raise” helper around the command itself, so the model receives an empty success and continues.

Part III — Many Surfaces, One Core

Chapter 9: The Gateway

Chapters 5 through 8 defined a turn that can run anywhere. The gateway is the door that stays open. It is a long-running process: platform adapters in, one AIAgent per conversation, delivery back out, plus the clock for cron and the writer of the session ledger from Chapter 3. gateway/run.py is the GatewayRunner facade. Siblings split startup, adapters, inbound handling, the turn, busy policy, notifications, and shutdown. Slash commands live beside them. If you are looking for “the Telegram bot,” you are looking for an adapter that normalizes a webhook into a message and then gets out of the way.

Adapters End at a Message

Bundled platforms live under plugins/platforms/<name>/ with an adapter and a manifest: Telegram, Discord, Slack, WhatsApp, Matrix, email, SMS, and the rest of a list that moves. A few legacy or special transports — the API server, webhooks, Signal — still sit under gateway/platforms/. The registry loads them lazily. Adding a platform is an adapter guide, not a core edit, which is the waist applied to I/O.

The adapter owes the runner a text (and maybe media), a chat id, a user id, and enough thread structure to build a session key. The runner owes the adapter a reply or an explicit drop. Authorization happens before an agent is constructed. Allowlists, a global allow, and DM pairing are the policy; Chapter 16 is the threat model and the code’s actual limits. An unauthorized DM does not get a prompt, a tool call, or a session row full of their text.

Session keys isolate conversations: platform, chat, thread, and the profile home that owns them. Two Telegram groups do not share a transcript because they share a process. gateway/session.py builds those keys and reads history through the authority. Delivery (gateway/delivery.py) can reply in place, send to a configured home channel, or target platform:chat explicitly — the same address cron uses. Cross-platform delivery is allowed. Mirroring is not automatic. In particular, cron output is not copied into the gateway chat transcript. Doing so breaks role alternation and mixes a scheduled job’s voice into a human conversation. The job has its own session. Chapter 10 depends on that refusal.

Media is staged into the profile’s image cache and, on the authority path, copied into an immutable store at admission time so a later cleanup of the staging file cannot change what the turn executes. The ordinary image pipeline then decides between native image parts and a text description. That is the same vision prep the CLI uses. The adapter’s job was to get bytes into the cache safely.

The Runner Owns the Queue

Chapter 3 introduced session_admissions. Here is what the runner does with them. Input is accepted into a durable FIFO before the model runs. A turn that was started when the owning process died is recovered as unknown. It is not replayed. Followers stay queued. Someone — desktop, the CLI, /discard — resolves the unknown row, the session resumes, and the next input runs once. Messaging users whose session is paused this way are told once, through the normal reply path, that the conversation is paused. Later messages queue silently. /reset rotates the route onto a new session; the lost turn stays on the old one.

stateDiagram-v2 [*] --> queued queued --> started: owner begins the turn started --> done: settled started --> unknown: owner died unknown --> interrupted: operator resolves interrupted --> queued: followers may run queued --> dropped: auth or route gone at recovery

Startup recovery of never-started native inputs waits until adapters are connected and routes are published. It rechecks sender authorization. If the route or the grant is gone, the row stays queued for a later start. Completed inputs are not inferred again. Under multiplex, each served profile home has its own authority and its own state.db. Recovery, FIFO order, and exactly-once settlement are per profile. A secondary profile’s rows never land in the default ledger. Chapter 17 is the isolation argument. The queue is why isolation has to be true: a shared FIFO would run user B’s prompt with user A’s credentials.

Local clients — desktop, TUI, hermes chat — use the same authority. hermes gateway ensure finds or starts the profile runtime and refuses to start a second one on top of a service it does not recognize. Exit codes distinguish “not ready yet” from “wrong profile” and “incompatible protocol.” A timeout is not permission to launch a rival writer. That would be two writers, which Chapter 3 forbade.

Busy policy is per live session: interrupt, steer, or queue. Changing it does not change the profile config and does not rebuild the prompt. Steer and redirect require the current execution generation so a stale client cannot cancel a newer turn. They do not create an admission. If you only remember one distinction, remember that one. A correction is not a new user message in the queue. A new message is not a correction of the running turn.

What Else Hangs off the Same Process

Hooks (gateway/hooks.py) are a gateway lifecycle, separate from the plugin pre_tool_call hook in Chapter 7. They see messages and sessions, not model tool schemas. Built-in hooks are an extension point; the tree can ship with none registered. Do not invent a hook “for later.” The contribution guide rejects hooks with no consumer.

The cron ticker shares this process so a job can deliver through adapters that are already connected. The runner is the clock. Job semantics — fresh agent, no clarify, skills injected — are Chapter 10. Pairing storage and slash-command dispatch live here too, because both are “a message arrived and we might not call the model.” /help and /status do not deserve a tool loop. Skill invocation from a slash command resolves to a user message and is then admitted through the normal FIFO, so the skill body does not rewrite the cached system prefix. That is Chapter 6’s note channel, implemented at the door.

Observability is callbacks plus delivery, not a second transcript. Tool progress can be posted into the chat. Reasoning can be shown or hidden per platform. The model still speaks once. A “typing” indicator that is actually a second agent is how bills double.

gateway/status.py holds token locks and profile-scoped process tracking so two gateway processes for one profile do not both believe they own the adapters. Service install is opt-in. hermes gateway run works with no platforms configured, which is how a desktop-only user still gets a session authority for cron and for local clients. Declining the OS service means messaging and jobs stop at logout. The choice is stored. An unset choice is not permission to install.

Deep Dive: Authorizing the Connection Is Not Authorizing the User

Local desktop and TUI connections authenticate to the authority with tickets minted from a same-user control socket: short expiry, one purpose, loopback peer, no Origin header. A ticket for native HTTP is not a ticket for WebSocket and not a ticket for another profile. Cross-profile selectors return a scope mismatch. Discovery endpoints can list sibling profiles without granting their data. This is an OS-user boundary, not an OAuth bypass for remote clients. An exposure proxy that replaces the caller’s credential with its own native grant is broken by design.

Frozen launch credentials are a different lock. A session records the policy it was created under, not a copy of every secret pasted into the process. On restart, inline credentials are re-read from the profile only if the home, the path, and a fingerprint still match. A missing or rotated key fails closed. An ad-hoc --api-key dies with the process. The transcript remains readable. Creating a new session is how you adopt a new key. Chapter 4’s resolver still runs; the authority simply refuses to swap secrets underneath a live session and call it a resume.

Clarification and approval have their own waiters. A clarify question can be rendered as a platform card and, on the authority socket, as an event with a prompt id. The first answer wins. Approvals use a different verb. Neither is a new admission, and neither is allowed to time out into “yes.” Chapter 16 states the default-deny rule. The gateway’s contribution is the waiter: the agent thread blocks in the approval callback, the platform delivers a button, the callback returns once, always, or deny.

Apply This

Normalize every door into one event, then share one runner. The problem it solves: a Telegram bot and a Slack bot that each grew a private session store and now disagree about what “the conversation” is. The pitfall: leaking platform payload types into the agent. The adapter strips. The runner never imports an SDK.

Admit durably before you infer, and freeze on owner loss. The problem it solves: a crash that retries a turn whose tools already ran. The pitfall: treating the FIFO as an at-least-once queue and redriving started. Unknown is a terminal state until a human resolves it.

Keep scheduled and background output out of the interactive transcript. The problem it solves: role alternation bugs and a chat history no human can read because nightly jobs filled it. The pitfall: a “mirror everything” debug flag that becomes the default in production.

Separate connection auth, user auth, and tool auth. A local socket ticket, a DM pairing decision, and a dangerous-command prompt are three gates. The problem it solves: a desktop session that is treated as paired, or a paired user whose shell is treated as pre-approved. The pitfall: one boolean, trusted, threaded through all three.

Make “ensure the service” fail closed when identity is ambiguous. The problem it solves: a client that starts a second gateway because the first did not answer quickly enough, and now two writers share a profile. The pitfall: interpreting a timeout as absence. Timeout means “still starting or unreachable,” not “mine to replace.”

Chapter 10: Cron Is an Agent Job

Chapter 9 made the gateway the clock. This chapter is what a tick runs. Hermes cron is not a shell crontab that happens to call an LLM. A job is a prompt, a schedule, optional skills, and a delivery target. When it fires, the scheduler constructs a fresh AIAgent, with durable memory and without the previous run’s transcript, and calls the same turn as a human would. cron/jobs.py stores the jobs. cron/scheduler.py decides they are due and runs them. tools/cronjob_tools.py is the model-facing tool, cronjob_manage, for create, list, update, pause, resume, run, and remove. The CLI is hermes cron.

The freshness rule is the whole design. A job that remembered last Tuesday’s tool output would eventually act on a stale plan, and a job that could ask clarify would block forever in a queue nobody is watching.

The Record and the Clock

Jobs live in the profile home at cron/jobs.json, written by temp file and rename. A record carries an id, a name, a prompt, a schedule, attached skill names, a deliver target, repeat counts, state, enabled flag, next and last run, last status, optional model and provider overrides, and an optional script. The schedule is one of four kinds: a relative delay (30m), an interval (every 2h), a five-field cron expression, or an ISO timestamp for a one-shot.

The gateway owns the ticker so delivery can use connected adapters. A standalone scheduler still exists for processes that are not inside the runner, but two tickers for one profile are a bug. The scheduler yields the tick when it can see a fresher gateway for that profile — a code revision mismatch is the signal — rather than racing it. Heartbeats distinguish “stale code, yielding” from “dead.” A job claim has a TTL and a refresh while the run is alive, so a slow job is not stolen and a dead owner does not hold the claim forever.

State transitions are boring on purpose: scheduled, running, paused, and a last status of ok or error. next_run_at is updated from the schedule after a fire, not from “thirty minutes after we felt like it.” A one-shot delay or timestamp disables itself after success. An interval and a cron expression keep going until paused, removed, or their repeat count is exhausted. repeat.times null means forever; completed is the counter.

What the Fresh Agent Is Denied

_resolve_cron_disabled_toolsets builds the denylist. messaging and clarify are always off. A job cannot ask a question, and it cannot send ad-hoc chat messages through the messaging toolset when delivery is already a structured field. cronjob is off unless cron.allow_agent_scheduling is set. That flag is loop prevention, not a security boundary: a job that can schedule jobs is a fan-out with a bill. The profile’s agent.disabled_toolsets is layered on top so a per-job allowlist cannot widen past the operator’s denylist.

Enabled toolsets resolve in the other direction. A per-job list, including an explicit empty list, wins. Empty must not fall through to “all toolsets,” which was a real bug: an unattended job with no tools silently regained every tool because a falsy list looked unset. Enabled MCP servers are merged in unless the job said no_mcp, so an allowlist of native toolsets does not strip MCP by accident. If the platform config cannot be read, resolution fails closed. AIAgent treats a missing enabled list as everything. Cron must never pass missing.

# Pseudocode — illustrates the closed set
def toolsets_for(job, config):
    disabled = ["messaging", "clarify"]
    if not config.cron.allow_self_scheduling:
        disabled.append("scheduler")
    disabled += config.agent.disabled
    enabled = job.enabled_toolsets  # [] is intentional, not "default"
    if enabled is None:
        enabled = platform_defaults("cron")
    if enabled is None:
        raise ConfigUnreadable
    return enabled, disabled

Skills are the other input. The job names them in order. At fire time each skill’s body is loaded and injected as context, then the prompt is the task. The agent does not have to discover the skill from an index mid-run; the operator already chose it. That is why Chapter 14’s documents are the right way to grow a scheduled workflow. Pasting a two-thousand-word procedure into prompt works once and rots. A skill is reviewed, scanned, and reusable from the CLI too.

The assembled prompt, including those skill bodies, is scanned for injection before the agent starts. Create-time scanning only saw the prompt field. A malicious or compromised skill could carry instructions the non-interactive job would obey under auto-approve. The scanner closes that gap. A hit raises a dedicated error and delivery becomes “job blocked,” not a partial run.

Memory still loads. MEMORY.md and USER.md are facts about the user, not about the last run. The prompt must still be self-contained: no “continue what we were doing,” because there is no we. Session search can recall older sessions if the toolset allows it, which is a deliberate lookup, not an implicit transcript. Prefer writing the job so it does not need that.

Delivery targets the origin chat or an explicit platform:id. The result is not mirrored into that chat’s gateway session (Chapter 9). Home-channel delivery exists for jobs that should show up somewhere even when they have no originating conversation. A failed run delivers the failure if a target exists. Silent failure is how a daily briefing dies for a month.

Provider and model on the job pin the route. A pin does not inherit the ambient fallback chain (Chapter 4). An unpinned job does, matching the gateway. The script field, when set, is a different kind of job — code the scheduler runs — and it is not an excuse to skip the prompt scanner on jobs that still call the agent. Do not blend them into one execution path that sometimes skips policy.

Deep Dive: Non-Interactive Means Auto-Approve Is a Choice

A job cannot render a Telegram button and wait. Dangerous-command approval therefore cannot mean “ask the user” unless a gateway waiter is actually attached, and even then a cron fire is not that user sitting in the chat. The safe default is the subagent default from Chapter 12’s neighborhood: deny, or a profile policy the operator set with their eyes open. YOLO and approvals.mode: off exist and are honored the same way as anywhere else; they are not implied by “this is cron.” An unattended shell plus a default of allow is how a scheduled agent becomes an incident. Chapter 16 puts the hardline blocklist under even YOLO. Cron does not get a quieter copy of that list.

Work that needs a human goes back to a session that has one. The pattern is: the job drafts, delivers, and stops. A person continues in the gateway session if they want changes. The job does not poll for their approval inside the agent loop. There is no clarify tool to do it with, on purpose.

Output size and runtime still need ceilings. A job that searches the web and writes a report can run long; the claim refresh exists so the scheduler does not start a twin. Iteration budgets still apply, from the same agent.max_turns family as the CLI, unless the job’s agent is constructed with a tighter cap. A runaway research loop at 9am is worse than a short report that says it hit the cap. The run-budget wrap-up from Chapter 5 is available if the caller sets a wall clock. Use it for jobs that fan out.

Kanban dispatch is the sibling the outline refused to give a chapter. It is another scheduler-shaped consumer of a fresh or bound agent, with its own invariants in the cron area guide, sharing the gateway’s worker ledger. If you are designing from this chapter, the transferable idea is “background work is an agent with a closed toolset and an explicit deliver target,” not “every background system should be cron.” Kanban tasks have boards and states. Cron has time. Do not overload jobs.json into a ticket tracker.

Apply This

Run scheduled agent work in a fresh session with durable facts only. The problem it solves: jobs that condition on last run’s rambling tool output and drift. The pitfall: also stripping MEMORY.md, so the job forgets the user’s name and timezone every morning. Facts stay. Transcripts do not.

Delete the interactive tools from unattended runs. No clarify, no ad-hoc send, no self-scheduling unless an operator opts in. The problem it solves: a job blocked forever on a question, or a job that schedules copies of itself. The pitfall: treating the denylist as a security boundary. It is loop prevention. The approval layer is still required.

Treat an explicit empty capability list as empty. The problem it solves: a falsy-list bug that restores full permissions to the job someone tried to lock down. The pitfall: using if not enabled as “fall back to defaults.” None means default. [] means nothing.

Scan the fully assembled prompt, not the field the user typed. Skill bodies and templates count. The problem it solves: injection that arrives through an attachment the create form never showed. The pitfall: scanning only at create time and caching a pass forever while the skill file changes underneath.

Deliver into a side channel, not into the human’s transcript. The problem it solves: scheduled noise and role-alternation bugs in the chat session. The pitfall: a mirror flag “so the user sees it in context” that becomes impossible to turn off once clients depend on the duplicated messages.

Chapter 11: The Editor Session

Chapter 9’s gateway admits work from messaging platforms. ACP admits work from an editor. The adapter in acp_adapter/ speaks the Agent Client Protocol over stdio — JSON-RPC to VS Code, Zed, JetBrains, and anything else that grew an ACP client — and then calls the same AIAgent. There is no editor loop. There is a session manager, a permission bridge, and a content converter.

That is a smaller surface than the gateway, and it should stay smaller. The failure mode this chapter exists to prevent is a second agent “because the editor is special.”

Sessions the Editor Can List

acp_adapter/session.py tracks live sessions: id, agent, cwd, model, history, a cancel event. The manager is thread-safe and can create, get, remove, fork, list, clean up, and update the cwd. Fork matters because an editor will branch a conversation without the user thinking of it as delegation. It is still a session with a parent, persisted like any other.

ACP sessions are written into the profile state.db. They show up in session_search. Restarting the editor does not invent a private transcript format that the CLI cannot resume. The storage rules of Chapter 3 apply, including the writer rule: when the desktop or the editor is attached through the session authority, admission goes through that owner. The in-process ACP server still constructs an agent; it does not open a side database.

Cancel is the editor’s /stop. It sets the cancel event the interruptible API call in Chapter 5 is already waiting on. The adapter does not kill the process. Killing the process would skip teardown of sandboxes from Chapter 8 and skip the session-end flush from Chapter 5.

Working directory updates are session updates, not prompt rebuilds by themselves. The pinned workspace snapshot in Chapter 6 is keyed by cwd. A cwd change that should be visible to the model is a new pin and, if you are honest about the cache, a new prompt build. The adapter’s job is to pass the cwd through. The prompt builder’s job is to decide whether the stored prompt still matches. Do not concatenate “the user opened a different folder” into the system prompt on every file focus event. That is a cache break per click.

Prompt Blocks Are Content, Not a New Message Type

Older ACP notes said non-text prompt blocks were ignored. The current converter in acp_adapter/content.py does not ignore them. prompt_blocks_to_user_content walks the editor’s blocks:

  • text stays text
  • an image block becomes an OpenAI-style image_url part, either a data URL or the URI the editor handed over
  • a resource link that points at an image is read, size-capped, and turned into a text header plus an image part; a failed read becomes a text error the model can see
  • an embedded resource that is an image is inlined the same way, and an oversized one becomes a text explanation rather than a silent drop
  • other resource text is included as text

If every part is text, the result is a plain string so slash commands and text-only providers keep working. If any part is an image, the result is a multipart user content list, which the vision prep on AIAgent already knows how to send. Pure text in, string out. That branch is what makes “hello” and “/help” stay ordinary.

# Pseudocode — illustrates the conversion
def editor_prompt_to_user(blocks):
    parts = []
    for block in blocks:
        if block.kind == "text":
            parts.append(text(block.text))
        elif block.kind == "image":
            parts.append(image_url(block.data_or_uri))
        elif block.kind == "resource" and is_image(block):
            parts.append(text(f"attached {block.name}"))
            parts.append(image_url(read_capped(block)))
        else:
            parts.append(text(resource_as_text(block)))
    if all_text(parts):
        return join_text(parts)
    return parts

When ACP is bridged through the gateway authority rather than an in-process agent, acp_adapter/gateway_media.py stages image bytes into the profile cache and submits them as attachments on prompt.submit. Remote image URLs are fetched through the gateway’s SSRF-guarded fetcher, not by passing the editor’s URL straight to the model. Admission stores a hash-checked copy. Later mutation of the staging file cannot change the turn, including across an owner restart. This is the Chapter 9 media path, used by the editor instead of a private one. The “ignored non-text” sentence in older internals docs is stale relative to content.py. Trust the converter.

The Permission Bridge Is Temporary

acp_adapter/permissions.py maps editor decisions onto Hermes approval outcomes. Allow once, allow always, and reject become the same once / always / deny vocabulary the terminal tool already understands. Timeouts and bridge failures deny. The editor hanging is not permission.

The adapter installs that callback on the terminal tool for the duration of the prompt and restores the previous callback afterward. The restore is the whole safety property. An ACP session-specific handler left installed on a process-global tool would answer the next CLI turn with an editor dialog that no longer exists, or worse, auto-resolve it. Gateway sessions are unaffected when they use the per-session approval queue; the bridge is for the in-process tool callback the CLI also uses. Chapter 16 is the policy. This chapter’s rule is the try/finally around it.

sequenceDiagram participant Ed as Editor participant Bridge as Permission bridge participant Tool as Terminal tool participant User as Editor UI Bridge->>Tool: install callback Tool->>Bridge: dangerous command Bridge->>User: permission request User-->>Bridge: allow once / always / reject Bridge-->>Tool: once / always / deny Note over Bridge,Tool: timeout or disconnect denies Bridge->>Tool: restore previous callback

Subagent auto-deny does not replace this bridge. An editor user is present. A cron job’s user is not. The adapter should not copy cron’s “never ask” default into an interactive IDE, and cron should not start popping IDE dialogs because the bridge was left global.

Model and provider changes requested by the editor go through the same /model pipeline as the CLI, with the same cache break. The adapter does not keep a private “editor model” that diverges from runtime_provider. Forked sessions inherit the parent’s route unless the editor asks otherwise, and a route override is the Chapter 4 pin: no silent fallback unless the surface passed a chain.

Deep Dive: What the Editor Is Not Allowed to Become

Streaming updates map onto ACP session notifications: message chunks, tool progress, plan entries if the client renders them. They are the callback surface from Chapter 5, serialized. A client that wants a pixel-perfect diff view can render tool results. The agent should not grow an editor_apply_patch tool that bypasses patch just because the client is an IDE. File tools already edit files. The cwd is the workspace. A special tool would be a second patch implementation with a second approval story.

Authentication of the stdio server is “the user who launched the editor.” That is a local trust boundary, similar to the desktop control socket and weaker than DM pairing. Binding an ACP server to a network port and calling it the same adapter is a different product. Do not reuse the stdio permission bridge on a multi-user socket. There is no pairing step in ACP, because there is no remote stranger. The moment there is, you want Chapter 9’s gates, not this chapter’s.

Limits that remain real: the editor’s notion of a selection, a terminal panel, and a file watcher are client concerns. Hermes receives the prompt the client chose to send, plus the cwd. It does not subscribe to every buffer change. Subscribing would rebuild context continuously and destroy the prefix Chapter 6 protects. If a client wants the model to notice a file, it sends the file or it lets the model call read. Both are already possible.

Apply This

Translate foreign content into the user message you already have. Images become image parts; everything else becomes text or a capped error string. The problem it solves: a protocol adapter that grows a parallel message type the turn does not understand. The pitfall: dropping unknown blocks silently. A dropped image looks like the model ignored the user’s screenshot. Say you could not read it.

Borrow the session store. Editor conversations are sessions. The problem it solves: a transcript trapped in the IDE that session search, compression, and resume cannot see. The pitfall: writing it through a side connection that violates the single-writer rule. Admit through the authority when one exists.

Install interactive callbacks for the prompt and always restore them. The problem it solves: a leaked handler that answers the next surface’s approval with the wrong UI. The pitfall: restoring only on success. The failure path, including cancel, must restore. Use a scope guard.

Default the bridge to deny on timeout. The problem it solves: a disconnected editor window that counts as yes. The pitfall: a short timeout that denies while the user is still reading the diff. Match human pace for interactive surfaces; do not reuse the machine-paced cron assumption.

Refuse a second tool surface for “editor things.” Diffs, cwd, and cancels map onto existing tools and the interrupt event. The problem it solves: two patch implementations drifting apart. The pitfall: letting the client pass a raw shell with the bridge uninstalled because “the editor already asked.” If the agent runs it, the agent gates it.

Chapter 12: Delegation

Chapter 7 listed delegate_task as an intercept. This chapter is the intercept’s reason: a child is another AIAgent, with its own transcript, its own iteration budget, and a toolset that was narrowed on purpose. It is not a function call with a hidden prompt, and it is not a separate orchestrator product. Hermes will spawn children. It does not, on the evidence of the delegation config, grow a swarm mailbox. If you came looking for one, what you actually have is a depth cap, a concurrency cap, and a default of “children do not ask the user.”

The knobs live in tools/delegate_tool_config.py and are read by the delegate tool. Logs still use the tool’s logger name so a split file does not look like a new subsystem.

Flat Unless You Pay for Depth

Depth 0 is the parent. The default delegation.max_spawn_depth is 1: the parent may spawn children, and those children are leaves. The floor is 1. Deeper trees are an integer in config, with no ceiling in code and a warning in the comments that each extra level multiplies API cost. delegation.orchestrator_enabled defaults true; set it false and every child is a leaf even if the depth cap would have allowed grandchildren.

Each child has its own IterationBudget. The module documents the parent’s cap as max_iterations (the CLI passes agent.max_turns, default 500) and the child’s as delegation.max_iterations, default 50. Totals add. A parent cannot hide infinite work inside children by sharing one counter, and a child cannot consume the parent’s remaining turns just by existing. Programmatic execute_code iterations can still be refunded inside whichever agent ran them.

Concurrency defaults to 10 (delegation.max_concurrent_children), overridable by config or DELEGATION_MAX_CONCURRENT_CHILDREN, floored at 1, with no hard ceiling. Above 10 the loader warns once that cost scales linearly. Background delegation uses the same cap. At capacity a new async dispatch is rejected, not queued, and the caller runs it synchronously. A leftover max_async_children key is ignored with a one-time warning. Rejecting is the right default: a queue inside the tool is a silent backlog the model will keep filling.

A finite one-shot session has a separate total, delegation.oneshot_max_children, default 2, where 0 means unlimited. One-shot and interactive are different products. A CLI user who says “fan out across these services” is not the same as a scripted invocation that should not spawn a tree.

There is no default wall-clock kill for a child. Long reviews and slow models were being murdered by a stopwatch. delegation.child_timeout_seconds opts back in, floored at 30 seconds, and the clock is inactivity, not age: it resets on a completed call, a tool change, or an activity tick. A child frozen for the whole window is caught. A child waiting on a five-minute completion is not. Stuck-child detection is that heartbeat, not a second policy hidden in the scheduler.

What the Child Inherits

Credentials are the sharp edge. The child should call the endpoint the parent is actually calling, taken from one source. The parent’s stored base URL and API key can lag the live client — an old OpenRouter URL versus a local server the fallback just swapped in. Pairing a live URL with a stale surface key is an instant 401. The loader prefers the live client’s URL and key, and uses the surface attributes only when there is no live OpenAI-compatible client (native Anthropic and Bedrock keep that client empty). Capability maps are trust decisions scoped to a provider and endpoint. They are inherited only when the child stays on the parent’s exact route. Any provider or base URL override is default-deny. That matches /model: a new route does not keep the old route’s extra permissions.

# Pseudocode — illustrates inheritance
def child_route(parent, override):
    if override.provider or override.base_url:
        caps = None  # default deny
    else:
        caps = parent.caps
    url, key = live_client_pair(parent) or surface_pair(parent)
    return Route(url, key, caps, fallback=None)

Fallback chains are not inherited. Chapter 4 said this and the delegate tool is why. A child that silently walks the parent’s fallback list will change models in a branch the parent is waiting on and return prose the parent cannot interpret as a failure. If the child should have a fallback, the delegation config passes one. A pin stays a pin.

Toolsets narrow. The child’s schema rewriter from Chapter 7 describes the limits in the tool the parent is about to call, so the model is not surprised by a depth error. MCP toolsets are inherited when delegation.inherit_mcp_toolsets is true, the default, so a parent whose only useful tools are MCP does not spawn a child that cannot see them. Narrowing is allowed to remove delegate_task itself at the leaf floor. A leaf that can still spawn is not a leaf.

Approvals do not use the parent’s TUI callback. Worker threads do not inherit the CLI’s thread-local approval function, and falling back to input() deadlocks a prompt-toolkit UI. Every worker is initialized with an explicit callback: deny, unless delegation.subagent_auto_approve is true, in which case the callback returns once and logs it. Both paths warn, so the audit log shows the decision. Gateway sessions are different. They already resolve approvals through the per-session queue in tools/approval.py, and a child spawned there should use that queue’s policy rather than a stdin prompt. Auto-approve is opt-in YOLO for children, not the default, and it is not the hardline bypass. Chapter 16’s blocklist still holds.

delegation.worktree_isolation defaults false. When true, each child gets a git worktree off the parent’s HEAD so parallel children do not share a working copy. It is git-only and local-backend-only. On SSH or Docker it is silently ignored rather than faked. delegation.independent_completions defaults false: one consolidated message when the batch finishes. True means a completion per task as each child returns, which is noisier and better when the parent wants to start integrating early.

Background Review Is a Fork, Not a Child Task

The turn file in Chapter 5 mentioned a review fork. It is related machinery and a different contract. A detached review can carry an input-token budget that trips at the next iteration boundary. It can be deferred when it would contend with a managed local runtime — the same GPU the user is waiting on. Persistence can be disabled so the harness turn is not flushed into the user’s real session. The session database is not lazily opened for a fork that said it does not persist. Opening it “just for search” would re-arm the flush.

Async delegation bookkeeping has a table in state.db (async_delegations). It is how the parent process remembers children across a gateway restart. It is not a second transcript. Results still enter the parent’s history as tool results, in call order, or as the consolidated completion message. The model sees tool results. The ledger exists so a crash does not orphan a Modal sandbox and also forget to tell the parent.

Kanban workers and cron are not delegate_task, but they share the worker ledger from Chapter 3: executions and receipts bound to an owner epoch. Delegation’s lesson for those systems is the same inheritance rule. Copy the route from one source. Default-deny capabilities when the route changes. Do not inherit a fallback chain you did not mean to run unattended.

Deep Dive: Why the Default Tree Is Flat

A tree of agents is an exponential bill with correlated failures. The parent pays for its own turns, for each child’s full prefix, and for the summary it then reads. Cache sharing across children is not free: they are different sessions unless you deliberately give them a byte-identical prefix and a provider that can use it. Hermes does not promise the fork-and-share trick some coding agents use. It promises a cap you can explain to a user in one sentence: “this agent can spawn helpers, and those helpers do not spawn.”

Raising max_spawn_depth is legal and sometimes right — a research lead that splits into readers that split into extractors. The config comment tells you the cost model. There is no adaptive depth. The model does not get to negotiate the cap mid-run except by failing and telling the parent, which is the correct channel. Dynamic schema text is updated when definitions are rebuilt, which is session build, not each grandchild.

Child transcripts are real sessions with parent linkage, so session search can find them and compression can run inside a long child. They are not ephemeral scratch pads. A child that runs for fifty iterations produces a transcript you may want. Treat deletion as a user action, not as delegate_task cleanup. Teardown of browsers and sandboxes still runs, because those are processes, not history.

Apply This

Make a child the same runtime with a smaller budget. The problem it solves: a “subagent” code path that forgets compression, interrupts, or provider projection and fails only on the hard tasks people delegate. The pitfall: sharing the parent’s iteration counter so either the child starves or the parent’s cap becomes a fiction.

Default the tree to one level. The problem it solves: recursive spawn that multiplies spend before anyone notices. The pitfall: enforcing the cap only in the prompt (“please don’t nest”) while the tool still works. The tool returns an error at the floor. The schema tells the model the floor in advance.

Inherit the live route from one source, and drop capabilities if the route changes. The problem it solves: a child with a URL from the live client and a key from a stale field, or a child that keeps a trust decision made for a different host. The pitfall: inheriting the fallback chain “so children are as reliable as the parent.” Reliability and surprise are different. Pass a chain explicitly or not at all.

Give worker threads an explicit approval callback. The problem it solves: input() on a thread that does not own the terminal, which deadlocks the UI and hangs the parent. The pitfall: defaulting that callback to allow because deny “gets in the way.” Deny is recoverable. Allow is a side effect.

Reject extra background work at the cap instead of queueing it. The problem it solves: a model that schedules unbounded follow-up children because every call returned success. The pitfall: a synchronous fallback that still runs them all, just more slowly, with no signal to the model that it hit the cap. The error string has to say “at capacity” so the parent can narrow the fan-out.

Part IV — What Survives the Session

Chapter 13: Memory, Recall, and the User Model

Chapter 6 froze a snapshot of memory inside the system prompt and refused to edit it mid-session. This chapter is the rest of the loop: what gets written, what gets searched, and what a plugin is allowed to add beside the built-in files. Hermes does not have one memory. It has three stores that answer three questions, plus at most one external provider.

  • MEMORY.md — the agent’s notes, facts that should apply in every session regardless of task.
  • USER.md — a bounded profile of the person.
  • Session search — full-text recall over the ledger in Chapter 3, for “what did we actually say?”

Skills, next chapter, are procedures. They are not a fourth memory. The guidance in the stable prompt tells the model so: task-shaped procedures go to skills; memory is the narrow exception. The tool surface enforces the same split.

The Built-in Store Is Always On

MemoryStore is constructed with character budgets. The tool defaults are about 2200 characters for memory and 1375 for the user profile, both configurable (memory_char_limit, user_char_limit). Entries are short on purpose. A memory file that is a diary will be truncated into uselessness and will also bloat every future prefix, because the snapshot sits in the volatile tier of every session until you stop writing.

The memory tool is an agent-level intercept (Chapter 7). Actions add, replace, and remove. Replace is substring match, so a single entry can be edited without rewriting the file, and a careless substring can edit the wrong sentence. Duplicate suppression refuses a second line that says the same thing. When the file is full, the tool returns an error the model can act on — consolidate, don’t append — rather than silently dropping the oldest fact. Security scanning looks at writes for the obvious exfiltration and injection shapes. memory.write_approval gates writes behind the same approve/deny path as dangerous commands when the operator turns it on. The default is to write. Turning the gate on is how a profile that shares a gateway with other people stops the model from persisting a stranger’s instruction as a “preference.”

flowchart TD T["Model calls memory"] --> I["Agent intercept"] I --> B{"Within char budget?"} B -->|no| E["Error: consolidate"] B -->|yes| S{"Scanner and approval"} S -->|deny| E2["Error to the model"] S -->|allow| D["Write MEMORY.md or USER.md"] D --> N["Tool result in this transcript"] D -.-> P["System prompt unchanged until rebuild"]

What the prompt contains is a snapshot taken at build. Disk can change immediately. The cached system prompt does not. The current turn sees the tool result. The next session sees the file. Compression’s rebuild reloads from disk, which is why a long session eventually catches up without a manual /new. Users experience the lag as “I told it to remember and it forgot.” The troubleshooting page for this is real, and the fix is not to poke the system prompt. It is to understand the snapshot.

Session boundaries flush external providers and the built-in manager: /new, /reset, /resume. Idle time and a daily rollover do not finalize a conversation. Resource-pressure eviction of a cached agent commits the transcript to providers before it drops the in-memory object, and it does not close the durable conversation. The next turn reloads the same id. Chapter 5 paired this flush with the context engine’s on_session_end so the two cannot drift.

Background review is the forgetting pass. An auxiliary model can scan a finished session and propose memory updates, on auxiliary.background_review, with its own input-token cap. Notifications are configurable because a chat that announces “I updated my notes” on every turn is noise. On a local GPU the review defers while the user is active (defer), which is the same fork Chapter 12 warned must not persist a harness turn into the user’s session. The review may also propose skill writes. Those go through Chapter 14’s gate, not through this one.

Good entries are specific and packed: a timezone, a test command, a lesson with a file path. Bad entries are “user likes quality” and a paragraph that belongs in a skill. The character budget is the teacher.

Session Search Is Not Memory

session_search queries the FTS indexes from Chapter 3: content, tool names, tool-call text, with trigram and CJK tokenizers so the gateway’s actual languages work. It is an intercept because it needs this agent’s session database, and a persistence-disabled fork must not lazily open the real one.

The split is the thing to teach the model, and the prompt already tries. Memory is a decision: we chose to keep this fact. Search is evidence: someone said this, in this session, on this platform, at this time. Search can be wrong, outdated, or someone else’s chat in a shared gateway if authorization was sloppy. Memory can be wrong too, but it is short enough to audit. When the user says “like last time,” the model should search before it asks them to repeat themselves. When the user says “I always want pytest,” the model should write memory, not hope the next search finds the sentence.

# Pseudocode — illustrates the two reads
def recall(query):
    facts = snapshot_from_prompt()       # frozen, small, curated
    hits = search_fts(query, profile_db) # historical, large, literal
    return facts, hits

Search results are tool output. They enter the transcript and then age like any other tool output, including being pruned by compression. The database is untouched by that prune. You can search again. That asymmetry is why search is allowed to be large and memory is not.

One External Provider, Beside the Files

MemoryProvider is the ABC in agent/memory_provider.py. Plugins ship in plugins/memory/<name>/ or the catalog. memory.provider selects one external name. Empty and a set of sentinels (default, builtin, none) mean “built-in only.” The built-in store is not a plugin and must not be looked up as one. The external provider does not replace MEMORY.md. It runs beside it. This is the mistake vendor integrations make: they take over “memory” and the operator loses the file they can read with a pager.

MemoryManager owns the lifecycle: initialize, a system-prompt block, prefetch and sync per turn, tool dispatch, shutdown, and optional hooks. Prefetch is skipped for trivial prompts — yes, thanks, a slash command — so a one-word reply does not pull a page of biography into the turn. The matcher is anchored; “k8s” does not count as “k”. Prefetch has a timeout. A stalled provider is dropped from the hot path rather than stalling the user. Background threads are spawned with the caller’s context variables copied in. A worker that starts with an empty context lands on the default profile, which is the Chapter 2 bug in a new costume. The helper spawn_context_thread exists so memory plugins do not reintroduce it.

Provider tools (honcho_search, and whatever the active plugin registers) route through MemoryManager.handle_tool_call, not the generic registry. Schemas are added to the model’s tool list for the session. Only one external provider is active, so two plugins cannot both register search and race. Catalog providers — Honcho is the documented example, now installed from the catalog rather than vendored — follow the same contract: a prompt block, tools, and a cadence for how often they refresh. Honcho’s own knobs (context cadence, dialectic cadence, depth) are that plugin’s cost model. The core’s promise stops at “one provider, redacted before it leaves the process, tools dispatched with the session id.”

Recall injected later in the conversation lands on the current user message (Chapter 6), not in the cached system prompt. The frozen snapshot and the live prefetch are different channels. Mixing them is a cache break and a staleness bug at the same time.

on_pre_compress is the provider’s chance to checkpoint before Chapter 15 throws the middle of the transcript away. The API has a version. v1 was best-effort with the raw message list. v2 is an opt-in fail-closed checkpoint: normalized evidence, and strict mode propagates failure. A provider that only implements v1 still works. A provider that claims v2 and fails does not let compression proceed as if the checkpoint happened. Memory flush before context loss, which Chapter 5 listed as a core responsibility, is this hook plus the built-in file flush. The order is the feature. Summarizing first and writing memory second means the summary is all the provider ever sees.

Redaction runs on the way out. Provider context that will re-enter a prompt is passed through a scrubber that strips secrets and URL credentials and elides the middle if it exceeds a few thousand characters. A memory plugin that “just stores the raw transcript” in a third-party cloud is the operator’s choice; the core still will not put an unredacted blob back into the system prompt.

Profile isolation is per home. A new profile does not inherit the previous profile’s Honcho peer or MEMORY.md. Backfill is an explicit migration, not an accident of a shared API key.

Apply This

Split curated facts from literal recall. A short file the model always sees, and a search tool over the real history. The problem it solves: either a tiny window with no past, or a prompt stuffed with every prior chat. The pitfall: teaching the model, in prose only, which is which. The tools should be different, and the file should have a budget that makes diaries fail.

Snapshot durable memory into the prefix, and put live recall on the turn. The problem it solves: a memory write that rewrites the cached system prompt every turn. The pitfall: users interpreting the snapshot lag as data loss. Say it in the tool result: saved, visible next session, visible now as this tool output.

Flush on session boundaries, not on idle. The problem it solves: a provider that finalizes and forgets a conversation the user still considers open because they went to lunch. The pitfall: never flushing, so a killed process loses the in-memory extract. Eviction under memory pressure commits; it does not finalize.

Run at most one external provider beside the built-in files. The problem it solves: three plugins injecting three biographies and three search tools. The pitfall: letting the provider replace the files. The files are the audit log the operator can read without the vendor.

Copy tenant context into every background memory thread. The problem it solves: a prefetch worker that writes user A’s extract into the default profile because it read the environment at thread start. The pitfall: a “helpful” context-copy helper that copies after the thread has already read a global. Bind first, then run.

Chapter 14: Skills the Agent Can Grow

Chapter 13 stored facts. This chapter stores procedures. A skill is a directory with a SKILL.md, compatible with the agentskills.io layout: frontmatter for name, description, and metadata, a body the model should follow, optional supporting files. Skills are not plugins. A plugin can register a tool and run Python. A skill is text the agent loads, plus the discipline to keep that text out of the prompt until it is needed.

The index lives in the volatile tier of the system prompt (Chapter 6), which is the cheap part. The body is loaded by skill_view or by invoking /skill-name, which becomes a user message and does not rewrite the cached prefix. That two-phase load is the whole performance trick. It is also the learning trick: the agent can write a new skill with skill_manage, and the next session’s index picks it up without a core release.

Where a Skill Is Found

The source of truth is the profile’s skills/ directory, ~/.hermes/skills/ unless the home says otherwise. Fresh installs copy bundled skills out of the repo into that directory. Hub installs and agent-created skills land there too. The agent may modify or delete any of them, subject to the gates below. External directories can be scanned beside the local one. A project can carry skills; those are trusted only after the operator trusts the project. Precedence is project, then local, then a create-dir redirect, then external dirs. Same-name duplicates in one tier are listed by path instead of silently shadowing.

flowchart TD Start["Session build"] --> Idx["Scan SKILL.md frontmatter only"] Idx --> Vol["Volatile tier: names and descriptions"] Use{"Model calls skill_view or user types /name"} Vol --> Use Use --> Body["Load body into the transcript"] Body --> Act["Follow the procedure with ordinary tools"]

Non-interactive surfaces — cron, API, ACP — do not pop a “trust this project?” dialog. Untrusted project skills stay out. Cron’s explicit skills: list is the operator choosing bodies to inject, which is a different path from “scan the cwd and hope.” Chapter 10 scans those bodies at fire time because injection through a skill is the threat.

Platform metadata can hide a skill from the wrong surface. A skill that shells out to a local GUI does not belong on a Telegram cron job. The index builder drops incompatible rows for that platform rather than letting the model load them and fail.

Conditional fallback skills load only when a primary is missing. Bundles are named sets — several skills for one kind of work — installed and inspected as a unit. Both are index-time features. They do not change the rule that the body waits.

The Index Line and the Body

The prompt section is mandatory in tone and small in bytes. It tells the model to scan the index and call skill_view before inventing a procedure. Categories group names. Descriptions are a line, not the body’s introduction pasted into the prefix. A skill added during the conversation updates disk immediately and updates the cached index only by the delta note Chapter 6 already described, or at the next compression rebuild. /skills install --now is the user saying the cold cache is acceptable.

Large sources — a book, a corpus — become a knowledge-base skill: a map in SKILL.md and the bulk outside the always-loaded path, so skill_view does not paste a novel into the transcript. /learn is the interactive version: point at a directory, a doc URL, a workflow the conversation just performed, or a pile of notes, and the agent drafts a skill. The draft is still just a file. It goes through the same write gate as a hand-written one.

# Pseudocode — illustrates two-phase load
def index_entry(path):
    meta = parse_frontmatter(path)      # name, description, platforms
    return f"{meta.name}: {meta.description}"

def load_body(name, roots):
    path = resolve(name, precedence(roots))
    return strip_frontmatter(read(path))  # this string enters the transcript, not the system prompt

Pinned auto-load (skills.auto_load, or an invocation flag) is the exception that proves the rule. Those bodies are resolved once and placed in the stable prefix, because they are session constants. Chapter 6’s builder does this only for that set. Everything else stays an index line. Putting every bundled skill’s body in the prefix would dominate the cache and the bill, which is why the bundled set is an index plus opt-in load.

When compression stubs a skill_view result, it does not pretend the instructions are still in context. The tool result is replaced with a marker that names the skill and says to load it again, and the summary lists pruned skills. A reload after the boundary returns the full body. Skills that were inlined by a slash command get the same marker. Skills that were pinned into the system prompt are never compacted, because they are not in the transcript. Chapter 15 owns the algorithm. The skill system only requires that “forgotten” and “never loaded” look different to the model.

Writing a Skill Is a Side Effect

skill_manage can create, edit, patch, delete, and write supporting files. The curator path is how a background review or the agent itself turns a repeated workflow into a file. This is the closed loop’s write half. Memory writes facts. Skill writes procedures. Both are gated separately.

skills.write_approval defaults false. When true, every agent write is staged for an explicit approve, the same mechanism as a dangerous command. Independent of that, guard_agent_created can scan the new content for credential harvesting, obvious prompt injection, and exfil instructions. It defaults off, because real workflows mention ~/.ssh and API key variable names and were tripping the heuristic. Turn it on when the profile is exposed to untrusted chats. A hit becomes an approval prompt with the scanner’s rationale, not a silent save and not a silent drop. Denied writes return an error string the model sees.

Hub installs are the other write path, human-directed: hermes skills and /skills search official optional skills, skills.sh, well-known endpoints, GitHub, ClawHub, and direct URLs. Trust levels differ by source. A scan runs at install; --force is how an operator overrides it, and it should be rare. Updates are a lifecycle, not a re-download that clobbers local edits. hermes skills reset can re-baseline or restore a bundled skill without deleting the operator’s other files. Publishing your own tap is a repo layout the hub already understands. None of that is required to understand the agent. It is required to understand that “the agent learned a skill” and “the user installed a skill” share a directory and do not share an authority. The user’s install is allowed to be trusted more than the agent’s overnight draft. The gates encode that.

Security setup that a skill needs — env passthrough declared in frontmatter — is consumed by Chapter 8’s sandbox filter. A skill that says it needs a token should not receive the entire environment. The frontmatter is a request. The sandbox is the decision.

Deep Dive: Why This Is Not a Plugin

A plugin can do anything the process can do, so it lives in a review queue and a loader. A skill can only do what the existing tools can do, plus persuade the model. That sounds weaker. For a personal agent it is the right default, because the failure mode of a bad skill is a bad procedure the transcript shows, and the failure mode of a bad plugin is code. The footprint ladder in Chapter 7 puts skills near the top for exactly this reason. Most “capabilities” are procedures: how this repo tests, how this user likes pull requests, how a daily briefing is structured. Shipping them as core tools would tax every session’s schema. Shipping them as plugins would mean a Python review for a markdown file.

The cost is prompt injection. A skill is instructions with the same authority as the user, sometimes more, because the system prompt says to follow it. Hence the hub scanner, the assembled-prompt scanner in cron, the optional write scanner, and project trust. You do not get to skip those because “it’s just markdown.” Markdown is the whole attack.

Skill directories are per profile. A second profile does not inherit the first’s agent-written skills. That will annoy someone who wanted a global library. External dirs are the supported sharing mechanism, pointed at on purpose, not an accidental shared folder inside the default home.

Apply This

Index cheaply, load bodies on invocation. The problem it solves: a system prompt that contains every procedure you might someday need. The pitfall: a body so large that one skill_view blows the context window. Split reference material out of the file the loader returns in full, or cap and paginate inside the tool.

Keep procedures out of the fact file. If it is a sequence of steps, it is a skill. If it is true in every session, it is memory. The problem it solves: a memory budget full of runbooks, and a skill index full of “user timezone is X.” The pitfall: a skill the model must load to learn the timezone, which it will forget to load. Put the one-liner in memory.

Gate agent-authored writes separately from human installs. The problem it solves: a background review that overwrites a careful human skill, or a human install path that blocks on the same prompt as a model patch. The pitfall: a scanner that defaults on and trains the operator to hammer “allow” because legitimate files mention secrets. Default the heuristic off; default untrusted-chat profiles on.

Make a pruned skill look pruned. When compression drops a loaded body, leave a marker with the name. The problem it solves: the model following a half-remembered procedure and inventing the rest. The pitfall: reloading every pruned skill automatically, which undoes the compression. Reload is a tool call the model can choose.

Treat skill text as untrusted input on unattended runs. Scan it at execution, not only at install. The problem it solves: a skill that changed after the install scan, or a skill the job attached by name. The pitfall: scanning the prompt field the user typed and assuming attachments are clean.

Chapter 15: Compression, the Legal Cache Break

Chapter 6 allowed exactly one mid-conversation rebuild of the system prompt. This chapter is that rebuild. ContextEngine (agent/context_engine.py) is the ABC. ContextCompressor is the default. A plugin can replace it; nothing replaces it silently. The turn from Chapter 5 calls the engine. The session ledger from Chapter 3 stores the result, either as a child lineage or, by default, as inactive archive rows on the same session id.

Compression is not a polish pass. It is the reason a Telegram chat that has been alive for a month still fits in a context window. It is also the easiest way to destroy a prefix cache and a user’s trust in one shot. Both facts are why it is a dedicated engine with thresholds, timeouts, and a structured summary instead of “drop the oldest messages.”

The Contract an Engine Must Keep

The ABC requires a name, update_from_response (record the provider’s token usage), should_compress, and compress. Compress takes the messages, an optional token count, an optional focus topic from manual /compress <focus>, a force flag that asks to bypass a cooldown, and a memory-context string for the handoff. The host filters kwargs by the implementation’s signature so an older plugin that lacks focus_topic does not crash.

Everything else has a default, which is how plugins stay small:

Hook Default behavior
should_compress_info The bool, plus a reason string if the engine wants to explain a skip
prune_tool_results_only No-op. A cheap, LLM-free trim of old tool payloads
select_context Return nothing. Optional request-only replacement that must not be persisted
on_turn_complete Observe a finished turn. Best-effort; some failure returns skip it
should_compress_preflight False. A rough check before any provider usage exists
on_session_start / on_session_end No-op. End is a real boundary, never “every turn”
on_session_reset Zero the token counters. Not the “compression just ran” sentinel
get_tool_schemas / handle_tool_call No tools
clone_for_agent Deep copy, so a child cannot mutate the parent’s budgets

select_context is the dangerous optional. It may replace the messages for this request only — retrieval, a branch, a topic slice. The session database stays as it was. The host runs it before cache markers and sanitizers. Returning a different list means accepting a different cache prefix. The default returns nothing so a stock session stays byte-identical.

on_session_reset sets last prompt tokens to 0, not to the -1 sentinel that means “compression just ran, wait for real usage.” A model switch must not inherit the previous model’s “we already fit” decision. That bug is a real oversized send after a switch to a smaller window. The comment in the ABC is the design.

Plugin selection is context.engine in config. Resolution checks plugins/context_engine/<name>/, then the general plugin registry, then the built-in compressor. Plugins are never auto-activated. "compressor" always means the built-in. One engine is active. Two compactors in a row is how summaries summarize summaries until the goal disappears.

Token fields the turn reads directly — last prompt, completion, total, threshold, context length, compression count — are attributes on the engine, not a side channel. threshold_percent defaults to 0.75 on the ABC and is overridden by config for the built-in; the product default people actually hit is the compressor’s 50% (compression.threshold). Protect-first and protect-last defaults on the ABC are small integers; the compressor config’s protect_last_n default of 20 is the user-facing knob, and the algorithm below still caps the tail at a fraction of the window so a large protect_last_n cannot forbid compaction. When you read a number, read it off the engine you are running.

Two Layers, Then Four Phases

Gateway session hygiene (gateway/run_turn_hygiene.py) is a safety net at about 85% of the window, before the agent starts, for histories that grew while the process was away. It prefers real usage from the last turn, then a usage anchor persisted on the session row, then a rough character estimate. It fires only when there is enough history and compression is enabled. It is intentionally higher than the agent’s threshold. Setting both at 50% compacted gateway sessions on every turn.

The agent compressor is the primary path, defaulting to 50% of the model window, with an optional absolute token cap that wins when it is lower. A per-model override can raise the ratio for families that need it. The usage anchor is the provider’s last prompt and completion counts plus a rough estimate of only what was appended since, fingerprinted so a gateway that re-reads SQLite every turn still matches. Compaction, reset, and native Codex compaction clear it. Without an anchor, a rough estimate over threshold waits one request for real usage, even if the estimate exceeds the window. Estimate magnitude is not proof the provider will reject. After a model switch the wait applies again. Idle compaction is a separate opt-in and does not share that wait.

flowchart TD In["Incoming turn"] --> H{"Gateway hygiene over 85%?"} H -->|yes| C["Compact before the agent"] H -->|no| A["Agent preflight"] C --> A A --> P{"Anchored tokens over threshold?"} P -->|no| Call["Call the model"] P -->|yes| Eng["engine.compress"] Eng --> Call

compress() on the built-in engine has four phases.

Prune. Old tool results outside the protected tail, larger than a couple hundred characters, become a one-line stub. No LLM call. A tool round the model has not answered yet keeps its text and its images. A single round that is itself enormous can still be summarized so compaction can make room. Every skill_view body that this pass stubs is replaced with an explicit pruned-skill marker naming the skill (Chapter 14), and the summary lists them. Skills pinned into the system prompt are not in this pass.

Boundaries. Head messages (protect_first_n, in addition to the system prompt) stay. The tail is a token budget walked backward, capped at 20% of the window, with protect_last_n acting as a minimum only up to a small floor. Tool-call groups are atomic: the boundary walks back to the assistant message that issued the calls. The middle is what will be summarized.

Summary. One auxiliary call (call_llm(task="compression")) with a structured template: goal, constraints, progress done and in progress and blocked, decisions, files, next steps, critical context. The summary model needs a context window at least as large as the main model, because the middle is sent in one request. If it is smaller, the call fails and the compressor drops the middle without a summary. That silent loss is the most common quality failure, and the warning belongs in the operator’s config, not in a retry loop that sends a still-too-large middle. The summary budget scales with the content, with a floor and a cap so a huge middle does not produce a huge summary. On later passes the previous summary is updated, not rewritten from scratch. Items move from in progress to done. A deterministic fallback summary is stored too, because that string is what the transcript now contains if the model call fails after a prune.

Assemble. Head, then a summary message whose role keeps alternation legal, then the untouched tail. Orphan tool results are removed. Tool calls whose results vanished get a stub result so the next request still validates. The system prompt gains a one-time note that earlier turns were compacted. That note is a cache break on the system breakpoint once, which is the price of honesty. Subsequent turns hit the new prefix.

In-place mode (compression.in_place, the default) keeps the session id and archives old rows as active=0 (Chapter 3). Turning it off is how you get a child session and a parent pointer instead. Do not delete the archives to “dedupe.” Iterative recompression reads them as the previous summary’s source of truth only through what was stored in the summary message, not by resurrecting archived tool output into the live window.

Manual /compress can pass a focus topic and can force past a cooldown. It still will not split a tool group, and has_content_to_compress lets the gateway say “nothing to compress” without an LLM call when the transcript is entirely protected.

Timeouts are layered because a stuck summarizer must not stall a chat forever: an inactivity budget, a total ceiling even while tokens stream, a short maximum hold for gateway hygiene before the turn proceeds uncompressed, and a failure cooldown that backs off per session. A SessionDB commit that has already started is not abandoned. Preflight that times out while the request is still oversized is a terminal turn result (Chapter 5), not a send.

Native Responses compaction, on routes that support it, is a different owner. The provider checkpoints the transcript. The local compressor must not also summarize those bytes, and the mid-turn token estimate must use the native figure or it will fire a useless local pass (Chapter 5). Codex app-server thread compaction is that family’s version of the same idea. The engine stays responsible for Hermes-owned sessions that are not on those routes.

Deep Dive: Memory Leaves Before the Middle Does

The order inside a compressing turn is: give memory providers their pre-compress checkpoint, flush built-in memory, then drop the middle. The checkpoint API’s strict mode exists because a provider that fails open will claim it remembered a conversation it never stored. v1 plugins stay best-effort so old installs do not start failing compaction. v2 plugins opted into being load-bearing.

The handoff guard in Chapter 5 sits on the other side of assemble. If the summary would be the only user-visible steering into the next model call, the original ask is re-appended. Compression is allowed to forget tool output. It is not allowed to forget what the user just asked.

clone_for_agent is called because the plugin system holds one engine instance and each agent needs its own counters. A child that calls update_model must not change the parent’s threshold. Engines with locks or database connections override the clone and share the durable backend while copying the budgets. The default deep copy is correct for the built-in and wrong for a plugin that holds a sqlite connection. The docstring says to override. Believe it.

Prompt-cache interaction, restated once: after compaction the transcript prefix is new, the system prompt may have gained a single note, and the rolling breakpoints re-warm within a turn or two. What you must not do is compact on a timer that fires every turn at a low threshold. Hygiene at 85% and the agent at 50% are far enough apart that a normal session compacts occasionally, not continuously. Continuous compaction is a quiet tax and a quality leak, because each pass is lossy even when the template is good.

Apply This

Make compression a plugin with a required decision and a lot of default no-ops. The problem it solves: a core loop full of vendor summarizers, and plugins that break because they did not implement an observability method. The pitfall: a default select_context that returns a copy of the messages. Return nothing unless you mean to change the request. Copies invite accidental mutation.

Prefer a real usage anchor over a character estimate, and wait once when you have no anchor. The problem it solves: compacting on a wild overestimate, or never compacting because you refuse to estimate at all. The pitfall: treating “over the window according to the heuristic” as proof you must compact before the first token. One rejected request is cheaper than compacting every new session.

Summarize the middle into a schema, and update that schema next time. The problem it solves: unstructured summaries that drop the goal and keep the small talk. The pitfall: a summary model with a smaller window than the main model, which fails and drops the middle raw. Check the window before you enable the route.

Keep tool pairs atomic and tell the model when a skill body was stubbed. The problem it solves: illegal transcripts and procedures the model half-remembers. The pitfall: protecting so much tail that the middle is empty and compaction “succeeds” without freeing space. Cap the tail at a fraction of the window.

Checkpoint memory before you delete the evidence. The problem it solves: a summary that is the only remaining record, written after the provider already had its chance and missed it. The pitfall: fail-closed checkpoints on providers that did not opt in, turning a best-effort plugin into an outage. Version the hook.

Part V — Trust, Islands, and Cost

Chapter 16: Who May Act

The agent you have built can run a shell in a sandbox, edit files, browse, message a stranger’s chat, and write its own procedures. This chapter is the stack of refusals in front of those side effects. Hermes is a personal agent: one operator, many possible senders, a process with the operator’s credentials. The interesting design is not a permission modal. It is which gates exist, which ones YOLO is allowed to skip, and which ones it is not.

tools/approval.py is the command gate. gateway/pairing.py is the stranger gate. Container flags, write roots, and passthrough filters are the containment gate. They are not one boolean named trusted.

Commands: Hardline, Then Policy, Then a Human

A terminal command walks a fixed order. The hardline blocklist runs first and cannot be disabled by session settings, by YOLO, or by approvals.mode: off. It exists for catastrophic patterns — the ones where “I approved the session” is not a meaningful consent. Recursive deletes aimed at the runtime itself are in that family. A user deny list (approvals.deny) sits with the policy the operator wrote on purpose. Permanent allowlists cover patterns the operator has already accepted. What remains that still looks dangerous — destructive git, privileged commands, the detectors in the approval module — goes to a callback.

YOLO is a session latch (hermes chat --yolo, or a frozen environment flag some embeds set at launch). It skips the interactive prompt. It does not skip the hardline. Subagents do not inherit the parent’s TUI prompt; Chapter 12 gave them deny-by-default unless delegation.subagent_auto_approve is set, and even then the return value is “once,” logged, not a permanent allow. Cron does not grow a quieter blocklist. Gateway approvals use a per-session queue and a platform button instead of stdin, with a timeout. Timeout is deny. Silence is not consent.

Modes worth knowing, without pretending the enum is the architecture: a normal interactive mode asks; an off mode stops asking and still hits the hardline; YOLO is that choice scoped to a session and seeded into the session’s stored model config so /resume does not forget it. A smart-deny path can still let an interactive owner override a classifier’s no, once, for that operation. Consecutive denies escalate the copy so a model that keeps pushing gets a hard stop instead of a debate. The exact detector patterns change. The order does not.

execute_code is in scope. A Python sandbox that shells out is still a command. File writes have their own protected paths — Hermes’s own home, credentials, the things a model should not rewrite to persist an attack — and an optional write root for operators who want a sandbox even on the local backend. Cron state is included in “do not let the model edit the scheduler to escape.” A tool that writes by opening files itself and skipping these checks is the bug Chapter 7’s pipeline was meant to prevent.

hermes approvals suggest mines history for patterns the operator keeps approving, so the permanent allowlist is earned from behavior rather than guessed in a config edit. Suggestions are not auto-applied. An allowlist that grows itself is a slow YOLO.

Strangers: Allowlists and Pairing

Gateway authorization runs before an agent exists (Chapter 9). Platform allowlists and a cross-platform allowlist are the static form. Allow-all exists and is documented as extreme. The flexible form is DM pairing.

An unknown sender on a platform whose unauthorized-DM behavior is pair receives an 8-character code. The owner runs hermes pairing approve <platform> <code> on the CLI. That user is then approved for that platform. ignore drops the message. decline sends one short refusal and then ignores that sender for a day. Email defaults to ignore because an inbox is full of people you did not mean to enroll. Platform sections override the global default, so Telegram can pair while WhatsApp stays silent.

Storage is per-platform JSON under the profile’s pairing directory, resolved at call time so a context-local home is honored. A path computed at import would freeze the launch profile and approve a user into the wrong island.

Docker is a footgun the docs call out because it is operational, not theoretical. The image runs the gateway as an unprivileged user. docker exec defaults to root. An approval file written as root with mode 0600 is invisible to the gateway, and the approve “succeeds” while the user stays unauthorized. Approve as the gateway user. The failure mode is a silent ignore, which is the worst UX a security control can have. Log the skip at warning level if you build a sibling; Hermes’s fix is the documented command plus an entrypoint that repairs ownership on start.

Pairing is not command approval. A paired user can still hit a dangerous-command prompt. A command approval does not enroll a new chat id. Chapter 9 asked for three gates. This is the second of them, fully specified.

Containment: Backends and Passthrough

Chapter 8 picked a place to run. This chapter is what that place is allowed to see.

Docker backends add the usual hardening: non-root where the image allows it, resource limits, a filesystem that persists only what the profile configured, dropped capabilities. SSH is only as contained as the account on the other side. Local is contained by the approval gate and the write root, which is to say it is not contained if YOLO is on and the write root is unset. The comparison table operators need is short: local trusts the OS user, containers trust the image and the flags, hosted sandboxes trust the vendor boundary and the credential you passed them. Pick the backend to match the trust of the sender, not the trust of the operator. A paired stranger plus a local YOLO shell is the operator’s machine.

Environment passthrough defaults to a stripped set. Skills request extra names in frontmatter. Credential files (OAuth tokens for a specific CLI) can be mounted explicitly. The sandbox filter still drops the agent’s own provider keys unless a skill asked and the operator’s policy agrees. “Borrowed” logins — a Codex or Claude Code credential on disk — are a product feature with a blast radius: the agent acts as that user. Treat them as grants, not as ambient Unix.

MCP servers receive a safe environment subset, and tool output is redacted before it lands in logs. Web tools inherit SSRF protection: private addresses refused unless the operator opts in, with a fake-ip exception so a local proxy that uses a carrier-grade range does not get classified as the user’s LAN by mistake. Content-level checks look at fetched pages that try to issue commands back to the agent. Context files from a repo are truncated and are not a hidden system prompt the repo author fully controls; they are still an injection path, which is why untrusted project skills are gated in Chapter 14 and context files are part of the same trust decision.

The contributor guide’s security split matters for anyone extending this: a vulnerability that crosses the boundary in the project’s security policy goes to a private channel, not to a public issue. This book does not publish exploit strings, detector regexes, or bypasses. The pattern is the order of the gates. The patterns inside the hardline list are the project’s to rotate.

Deep Dive: What a Personal Agent Should Not Copy from a Multi-Tenant One

A multi-tenant product often puts every tool behind an allowlist and a policy engine with audit exports. Hermes puts the hardline in code, the deny list in config, and the ambiguous middle in a prompt the operator sees. That is appropriate when the person at the keyboard is the victim of a mistake and the beneficiary of speed. It is inappropriate when the sender is not that person. Pairing is how the gateway refuses to pretend otherwise. Profiles are how one operator keeps a “public bot” home separate from a “my laptop shell” home (Chapter 17). If both senders share a profile, no approval mode can express the policy you want. Split the home first, then set YOLO on the private one if you must.

Supervised-gateway restrictions exist so a gateway that is supposed to ask does not get flipped to off by a config reload the model initiated. The model cannot approve its own privilege escalation by writing config.yaml. Protected writes are that sentence enforced in the file tools.

Audit is the callbacks and the session transcript, which already contain every tool call (the observable-execution principle from Chapter 1). A parallel audit log that can drift from the transcript will drift. Prefer the transcript plus structured denial reasons. Do not build a second store of “what we allowed” unless it is derived.

Apply This

Put an unblockable floor under every convenience bypass. YOLO, mode off, and subagent auto-approve skip the prompt. They do not skip the catastrophic list. The problem it solves: a session flag that becomes a full disable because every check consulted the same boolean. The pitfall: growing the floor until it includes judgment calls, so operators disable the whole mechanism. Keep the floor small and embarrassing to hit.

Make timeout and bridge failure deny. The problem it solves: a lost gateway button that defaults to allow because the code returned None and the caller treated None as yes. The pitfall: a timeout shorter than a human reading a long command. Scale it to the surface. Cron should not wait for a human at all; it should deny or follow an explicit unattended policy.

Enroll senders with a short, rate-limited code, and never log the code. The problem it solves: static user-id allowlists that break the moment a platform rotates ids, and codes that leak through debug logs into the same chat the attacker can read. The pitfall: writing the approval file as a different Unix user than the gateway, so the allow is invisible. Same user, mode 0600, path resolved per tenant at call time.

Strip the environment, then add grants. The problem it solves: a sandbox that inherits the agent’s API keys and posts them to a log the model was told to upload. The pitfall: a skill frontmatter that is treated as the grant by itself. Frontmatter is a request. Policy still decides, especially on unattended runs.

Separate stranger-enrollment from command-approval from process containment. Three gates, three defaults. The problem it solves: a paired DM that is interpreted as permission to run rm on the host. The pitfall: adding a fourth “admin mode” that skips all three. If you need that, it is a different profile, not a flag.

Chapter 17: Profiles, Multiplex, and What a Turn Costs

Chapter 2 gave every profile a home. Chapter 9 ran one gateway for one home. This chapter is the step where one process serves many homes, and the bill that falls out of the choices in the rest of the book. There is no separate cost optimizer in the tree. There is a set of invariants that keep a turn from being more expensive than the operator already agreed to, and a multiplex design that fails closed when it cannot keep those invariants per profile.

Islands in One Process

A named profile is a directory: its own config.yaml, .env, state.db, memory, skills, pairing files, cron jobs, and gateway identity. The default profile is a real name, not a NULL (Chapter 3). Switching profiles is not cd. It is a different root passed through get_hermes_home().

Without multiplex, one gateway process serves exactly one profile, and a second profile means a second process. Multiplex collapses the processes and keeps the islands. The default profile and each served named profile get their own adapters, secrets, sessions, and cron ticks. They share one event loop, one HTTP listener, one process lock, and one status surface. The constraint, from the multiplexing guide, is the product: profile A’s turn must never observe profile B’s state. Secrets, homes, sessions, and adapter lanes are isolated. Anything that cannot be isolated yet fails closed or is written down as a limitation, not papered over with a lock.

The mechanism is a context-local override inside hermes_constants.py, consulted by get_hermes_home() before the environment variable. Config, the database, skills, memory, soul, sessions, plugin discovery, and MCP startup follow the active profile because they all call that function. get_process_hermes_home() exists for the few machine-level assets that must not follow the override. A registry that needs a cache key uses a home key, not the path string some caller happened to compute. A one-shot warning fires if profile-scoped code runs without the override where one is expected. The warning is an admission that the bug is silent: you get the launch profile’s data and nothing throws.

SessionStore does not bind a database handle at construction. Handles resolve at call time through the active override, one cached handle per profile file. A store object can be shared. The file cannot. Pairing stores are built per served profile. Cron ticks are per profile. A secondary profile’s clients discover the multiplexer through the default home’s descriptor and attach with their own profile id. They do not inherit the default’s ticket (Chapter 9).

# Pseudocode — illustrates the override, not the contextvar API
def get_home():
    if override := context_local_home():
        return override
    if env := environ.get("HERMES_HOME"):
        return env
    return platform_default_home()

def serve_turn(profile, msg):
    with home_override(profile.root):
        agent = build_agent()   # sees this profile's keys, db, skills
        return agent.run(msg)

The bug class this prevents is specific. Boot probes, eviction, tickers, deferred callbacks, RPC methods, thread hops, and child spawns all run outside “the turn” and will capture the launch profile if they read os.environ or a module global once. Memory providers already have spawn_context_thread (Chapter 13). Every other background job needs the same discipline. A child process must be given HERMES_HOME explicitly. Dropping it is a switch to the default profile, not “inherit the parent.”

In-process agent rebuilds — a toolset change, a bot-chat capability refresh — must keep the session’s database handle and bind the profile home during construction. Releasing the old agent must not close a handle the replacement inherited. Explicit profiles that do not resolve fail before they touch another profile’s history.

What a Turn Actually Costs

The architecture does not publish a price list, and this book will not invent one. The costs that are real are structural.

The prefix. Chapter 6’s tiers exist so the stable head hits a provider cache. A mid-session memory write, skill install, model switch, or credential-pool rotation is a miss on purpose. Machine-paced sessions use a short cache TTL; human-paced sessions use a longer one. You pay full price on the first turn after a break longer than the TTL, and on the first turn after any of those breaks of identity. The controllable mistake is busting the cache by accident. The unavoidable one is busting it by changing models.

The tool list. Every enabled schema rides on every request. Chapter 7’s ladder is a cost control. A skill index line is cheaper than a tool definition. A check_fn that hides an unconfigured backend is cheaper than a tool the model calls and fails.

Fan-out. Delegation’s default depth of one and concurrency warning above ten (Chapter 12) are cost controls. Each child pays for its own prefix. There is no promise of cache sharing across children. Background review has an input-token cap and defers on a busy local GPU so the review does not steal the interactive turn’s accelerator.

Compression. A summary call is an auxiliary request, ideally on a cheaper model configured under auxiliary.compression. It is cheaper than sending a 90% full window forever, and more expensive than not compacting if you set the threshold so low that you summarize every turn. The 50% agent threshold and the 85% hygiene net are the compromise in the tree. Native provider compaction, when the route has it, avoids the local summary cost and must not be double-paid by a local estimate that ignores the checkpoint.

Retries and fallback. A pool rotation and a fallback activation each cold-start the cache. They are still cheaper than a dead session. The latch that fires fallback once is a cost control as much as a correctness control.

Iterations. agent.max_turns defaults to 500 on the CLI. That is a ceiling, not a target. The run-budget wrap-up at 80% of a wall clock exists so a research loop produces a deliverable instead of exploring until the cap. Child budgets default much lower. Batch runs default lower still, because a batch of hundreds of prompts at 500 turns is a different product from a chat.

Trajectories are the escape hatch that is not the session database. The batch runner and the trajectory helpers can emit ShareGPT-shaped records for training. They are a different store, on purpose (Chapter 3). Do not mine state.db with a training job that holds a write lock, and do not write training labels back into user transcripts. Export is a copy. The ledger stays the user’s.

Observability hooks record guardrail decisions and cache breaks so an operator can see a miss without a custom dashboard. They are not a billing system. If you need dollars, you need the provider’s usage API plus the model id the session row already stores. The book stops at “the row has the usage.” It does not invent a tariff.

Deep Dive: Fail Closed Is a Feature List

Multiplex’s known limitations are part of the design, not a backlog you should hide. When a subsystem cannot yet take the context override — some native resource, some library that reads the environment itself — the supported behavior is to refuse that feature on secondary profiles or to run it only on the default, documented as such. A lock around a global is not isolation. The global still holds one secret at a time, and the await points between set and unset are races.

Plugin authors inherit this. A plugin that caches get_hermes_home() at import has already chosen the launch profile forever. The loader can document that. It cannot fix it after the plugin captured the path. The same is true of database connections opened at import. Open them on first use inside the override, or key them by home.

Desktop and CLI clients that talk to a multiplexer must send the profile id on every session verb. A missing id is not “whichever was active.” Discovery may list siblings. Discovery does not authorize them. Chapter 9’s ticket rules and this chapter’s homes are the same policy at two layers: name the tenant, or do nothing.

Apply This

Resolve the tenant on every call through one context-local root. The problem it solves: a process that serves two users and leaks one’s memory into the other’s prompt via a cached path. The pitfall: a second getter “for the process level” that feature code starts using because it does not require a context manager. Name it so it sounds dangerous. Make the easy function the scoped one.

Share the event loop, never the database handle’s meaning. A handle cache keyed by home is fine. A handle opened at startup and reused for every request is a cross-tenant write. The problem it solves: SQLite lock contention that someone “fixes” by using one file. The pitfall: closing a shared handle when one profile’s agent shuts down. Refcount per home, or do not share.

Treat cache identity as part of the cost model. Model, account, and the frozen prefix are the price. The problem it solves: a fallback path that looks free in tests because tests do not pay, and melts a budget in production. The pitfall: disabling fallback to save cache hits and leaving the user with a 429. Rotate when you must, and do not rotate when the pool has one key.

Cap fan-out in the tool, not in the prompt. Depth, concurrency, and per-child iteration budgets are the cost ceiling. The problem it solves: a model that treats “be thrifty” as optional. The pitfall: a cap so low that legitimate parallel reads never work, training users to raise it to a hundred and leave it there. Warn at the point where cost goes linear, and keep the default small.

Export training data out of band. The session ledger is not a dataset. The problem it solves: a training job that contends with the gateway writer, and a user who did not agree to have chats rewritten into labels. The pitfall: a trajectory format that includes secrets because the exporter dumped raw tool results. Redact on the way out, the same way memory providers redact on the way back in.

Part VI — Transfer

Chapter 18: What Transfers

The previous chapter closed the loop on money and tenants. This one does not add a subsystem. It asks which of Hermes’s bets are worth stealing if you are not building Hermes, and which are accidents of a personal agent that lives in other people’s chats.

The source is a Python process with a narrow waist, a jealous prompt cache, and a home directory per profile. The lesson is the set of decisions that waist forces. You can copy them into a TypeScript coding agent or a hosted multi-tenant product. You should not copy the product’s surface area and call it an architecture.

The Bets, Checked Against the Tree

One core for every surface. CLI, gateway, cron, ACP, batch, and the library call run_conversation. We watched the constructor accept callbacks and a platform string instead of a class hierarchy, the cron runner disable toolsets rather than fork the loop, and the ACP adapter convert editor blocks into ordinary user content. The bet holds. A surface that needs a new policy does not need a new loop. The moment a surface needs different compression or a different transcript dialect, the bet has failed and you should notice, not paper over it with a flag.

The cached prefix is a product invariant. Tiers are ordered stable, context, volatile. Skill-index deltas and surface switches ride the current user turn. Memory writes hit disk and not the system prompt. Compression is the named rebuild, and it is a real engine with a threshold rather than a helper someone calls from a slash command. Fallback and pool rotation are admitted cache misses. This bet is the one most agent codebases violate first, because every feature wants to be helpful mid-conversation. Hermes’s development guide says no, in public, and the code matches it more closely than the guide’s older diagrams. When a doc and build_system_prompt_parts disagree, the function is the architecture.

Capability lives at the edges. Tools self-register and then check_fn hides them. The footprint ladder pushes procedures into skills, integrations into plugins and MCP, and new core tools into a review that should feel like a tax. Delegation, memory, session search, and todos are intercepted because they need the conversation, not because the registry was too hard to use. The bet holds as long as intercepts stay rare. A dozen intercepts is a second registry with worse tooling.

Learning is three stores. Curated facts, a user profile, and FTS recall, plus procedures as skills, plus at most one external memory provider beside the files. Background review can propose writes and must not impersonate the user’s session. This is a personal-agent bet. A coding agent that forgets between sessions can get away with a repo file and a search index. A personal agent that forgets the user’s timezone every morning is broken. Do not collapse the three stores to “we’ll just RAG the transcript.” Chapter 13 is the argument: decisions and evidence have different lifetimes.

Execution is a placement, not a tool name. Terminal backends from local through Docker, SSH, Singularity, Modal, Daytona, and Vercel Sandbox share an ABC. Browsers split across local Chromium, Lightpanda, Camofox, and cloud providers, with hybrid local routing for private URLs. Web search is a vendor registry with a loud pin and a quiet autodetect. The model sees stable verbs. The operator sees a config key. This bet transfers to any agent that might leave the laptop. It is wasted complexity for an agent that is contractually local. Do not build the ABC “for later” if later is imaginary. Do not skip it if you already have one customer on SSH.

Profiles are islands even when the process is not. Context-local home resolution, per-home databases, per-home cron, fail-closed multiplex. The bet is how you run a personal agent for more than one life — a public bot and a private shell — without two codebases. A hosted product needs the same isolation with a real tenant id instead of a directory. The directory is an implementation. The context override is the idea.

What Does Not Transfer Cleanly

The gateway owns the transcript, and a lost turn becomes unknown. That is right for a process that can send a message or edit a file exactly once. It is ceremony for a pure function that only returns text. If your tools are idempotent and your users expect at-least-once, replaying started may be correct. Hermes’s choice is the opposite because its tools are not idempotent. Copy the choice only if your tools match.

DM pairing and the hardline blocklist assume an operator who is not the sender. A local coding CLI with one user can ask on every dangerous command and skip pairing entirely. A public bot cannot. Cron’s “no clarify, fresh transcript, scan the assembled prompt” rule is the unattended version of the same idea. If you schedule an agent, those three constraints transfer even when nothing else about Hermes does.

Flat delegation is a cost default, not a law. Some jobs are trees. Hermes makes you opt into depth because the bill is exponential and the product is personal. A research product might flip the default and keep the cap. A product with no cap is not a different philosophy. It is an unbounded loop.

In-place compression with a structured summary transfers if you have sessions long enough to need it. The part to copy exactly is the order: checkpoint memory, summarize the middle, keep tool pairs atomic, do not let the summary impersonate the user. The part to leave behind is any threshold copied without measuring your own window. Fifty percent is Hermes’s number for its models and its hygiene net at eighty-five. Yours should be an argument, not an import.

Facade-and-siblings plus a size ratchet is a social technology for a large Python repo with many contributors. A small system should just keep the loop in one file until that file hurts. The idea that does transfer at any size is: the name callers patch is the seam, and tests patch the seam.

If you take nothing else, build this and stop.

# Pseudocode — a waist small enough to finish
def run_turn(session, user_text, tools):
    session.messages.append(user(user_text))
    if over_budget(session):
        checkpoint_memory(session)
        session.messages = compact(session.messages)
    prompt = session.frozen_prompt or freeze(build_prompt(session))
    while session.budget.consume():
        reply = project_and_call(session.route, prompt, session.messages, tools)
        if not reply.tool_calls:
            session.messages.append(reply)
            save(session)
            return reply.text
        results = run_tools_in_order(reply.tool_calls, session.policy)
        session.messages.append(reply)
        session.messages.extend(results)
    return budget_exhausted(session)

Around that function, add doors that only choose a session, a policy, and a delivery callback. Add a registry whose availability probe can fail without taking the process down. Add one fact file and one search function before you add a vector database. Add a depth cap the same day you add subagents. Put the tenant id in a context variable the same day you serve two tenants.

Then write down the one mutation you allow mid-session. Hermes chose compression. You might choose something else. Choosing none, and then letting every feature mutate the prompt, is the failure mode this book has been walking around since Chapter 1.

The Ten Patterns, Earned

The README lists ten patterns. They are no longer proposals. Each one has a chapter that would be worse if the pattern were removed.

  1. One agent, many doors — Chapters 1, 9, 10, and 11. Cron and ACP are policies in front of the same turn.
  2. Facade and siblings — Chapters 1, 2, and 5. The file you import is not the file that grew.
  3. The prefix is sacred — Chapter 6, paid for in Chapter 17, broken only by Chapter 15.
  4. Register at import, gate with a probe — Chapters 7 and 8. Registration is not availability. Grace windows exist because probes flap.
  5. Narrow waist — Chapters 7 and 14. A skill is the default capability. A core tool is a tax.
  6. Stateful tools are intercepted — Chapters 7, 12, and 13. Memory, search, todos, and delegation need the live agent, and the registry path is a stub.
  7. Three stores, not one memory — Chapter 13. Facts, profile, and FTS. One external provider beside them, never instead of them.
  8. Skills load in two phases — Chapter 14. Index in the prompt, body in the transcript, writes behind a gate the human installs do not have to share.
  9. Cron is a fresh agent — Chapter 10. No prior transcript, no clarify, assembled prompt scanned, delivery kept out of the chat log.
  10. The gateway owns the transcript — Chapters 3, 9, and 17. Other doors admit work. A turn lost with its owner is unknown, not replayed. Profiles stay islands inside the process that serves all of them.

None of these require Nous Research’s model router, Hermes’s skill hub, or any particular messaging platform. They require a decision to keep the turn boring. Boring is the point. The surfaces can be as strange as a phone client and an editor protocol. The center should be explainable in a page, and enforceable when a feature wants to be clever.

If you build from this book, build the center first. The doors are a weekend each once the center can say no.

Apply This

Write the invariant down where features go to die. Hermes uses “the prefix is sacred” and “the core is a narrow waist.” The problem it solves: reviews that relitigate the architecture every pull request. The pitfall: an invariant with three undocumented exceptions. Name the exception, as compression is named, or it will multiply.

Steal the turn, not the product. A phase machine with a typed stop reason, a frozen prompt, and a tool pipeline transfers. A twenty-platform gateway does not, until you have users on two platforms. The problem it solves: a rewrite that starts at the UI. The pitfall: a turn so abstract it cannot send a tool result. Ship one backend.

Isolate tenants the day you have two. A context-local root is cheap before the first global cache and expensive after. The problem it solves: a demo that grew a second customer. The pitfall: isolation by process only, which you will abandon the first time you want one port and two profiles, taking the globals with you.

Default unattended work to a fresh session, no questions, and a scanned prompt. The problem it solves: a scheduler that “just calls the agent” and blocks on clarify at 3am, or obeys a skill that changed yesterday. The pitfall: stripping durable facts along with the transcript. The user is still the same person. The conversation is not.

Keep one legal way to forget. Compression, with memory checkpointed first and the user’s ask preserved, is a complete design. The problem it solves: five ad-hoc truncators that each drop a different field. The pitfall: a second forget path for “just the tool output” that does not tell the model the skill body is gone. One path, explicit markers, a threshold you measured.
