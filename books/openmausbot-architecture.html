OpenMausBot · source architecture report

One room.Separate minds.

How a local harness turns a chat transcript into coordinated work—without giving every agent the same memory, tools, or authority.

High-level design firstGroup-chat deep diveLow-level + reading guide Reviewed commit 0bfaa886 29 October 2026

The central idea: OpenMausBot is a transcript-centered orchestrator, not a swarm of agents listening to a shared socket. The harness decides who speaks, builds that speaker’s own prompt and tool profile, normalizes the resulting provider events, and persists the outcome for the next speaker.

01

The mental model

Three separations explain most of the implementation: client versus harness, shared transcript versus private model context, and conversational mentions versus durable delegation.

A

The room is a record, not a brain.

A room owns messages, roster, bulletin, responder policy, and optionally a working folder. It does not own one universal AI context. Each responder gets a separately assembled turn.

B

The harness is the only speaker scheduler.

Provider CLIs do not autonomously wake each other. startGroupTurn selects responders and runGroupMemberTurn executes them in order; a mention can extend that controlled round.

C

Two event streams serve two purposes.

Provider events tell the harness what an engine did. Server-Sent Events update clients. Neither is a broadcast inbox that every agent reads.

Read “shared” carefully. Shared transcript does not imply shared native session; shared working folder does not imply shared tools; seeing a teammate’s request does not grant its authority.
02

System map: where responsibility lives

The UI is intentionally thin. The local Node harness owns identity, state, orchestration, tool proxies, and provider processes; Electron supplies desktop lifecycle and native capabilities.

Why this shape matters

  • One durable authority. Rooms, bots, transcripts, assignments, and permission decisions do not depend on a renderer staying open.
  • Many provider protocols, one runtime language. Drivers implement a common adapter contract and emit a canonical event union.
  • Tools cross back through the control plane. The agents MCP proxy can discover teammates and request work, but the harness validates access, approvals, destination, recursion, and delivery.

04

How modules communicate

Four communication styles coexist. Keeping them separate prevents the common mistake of treating “SSE,” “agent context,” and “tool result” as the same channel.

1 · Command → HTTP

The client sends JSON commands such as POST /api/groups/:id/messages. Admission can return an accepted message or a durable queue receipt. A sendId supports at-most-once retries.

2 · Engine → canonical event

Drivers normalize native output into RuntimeEvent: session, turn, content, tool item, permission request, usage, and error events. Server folds turn these into durable messages and state.

3 · Harness → client SSE

/api/events carries message, group, runtime, and configuration frames with sequence cursors. EventSource resumes from a replay buffer or requests a fresh snapshot if continuity is unsafe.

4 · Agent → MCP → guarded route

A model calls a mounted tool over stdio JSON-RPC. The proxy calls an internal HTTP endpoint with turn identity and capability. The harness—not model text—checks roster, peers, approvals, and lineage.

The event bus is a fan-in, not a pub/sub network for agents

EventBus.attach subscribes to each provider adapter, stamps the instance id, coalesces text deltas, queues secret-redacted NDJSON writes, and delivers the event to registered server listeners. One important listener broadcasts a public projection over SSE; others fold text and tool activity into transcripts, track context, drive recovery, and update room sessions.

A second agent learns what happened only when a later prompt is composed from durable transcript and assignment records, or when a tool response returns to its current model turn.

05

Room routing: who gets a turn?

Every human line is appended first. Explicit addressing wins over the room’s default responder policy. Hidden and held members are filtered before a provider turn begins.

Precedence, in plain language

  1. @everyone selects every available member.
  2. Otherwise, named @mentions select those members, regardless of the un-mentioned default.
  3. With no mention, Everyone selects all; Lead selects one; Only mentions selects nobody.
  4. Auto first computes a lead fallback. For an un-mentioned chat line with multiple routable members and the decision job enabled, it asks Jev or OpenRouter for a member or “several members.” A confident result replaces the round; otherwise the fallback remains.

When several responders are selected in an ordinary chat round, they run sequentially. Each later speaker’s room window includes earlier replies, so this is ordered collaboration, not independent parallel answers.

Real-world flow: an @mention chain

A launch channel contains Research and Reviewer. The user asks Research for risks, then asks Reviewer to challenge them. No agent calls a teamwork tool; the room host does all coordination.

What makes this cooperation?

Reviewer does not receive Research’s tokens directly. Research’s terminal assistant text becomes an attributed message in the room store. When Reviewer’s turn begins, the transcript renderer includes that line, so Reviewer can build on it. The harness’s event folds and the transcript are the bridge.

Bot-to-bot mentions follow a bounded extension

After an ordinary root speaker settles, the host scans its final reply for room-member mentions. It can dispatch the mentioned teammate with hop + 1, using the same round and transcript. MAX_GROUP_HOPS = 1 allows this immediate follow-on but blocks an open-ended mention loop; a spoken set suppresses repeats. Explicit handoffs disable this casual-follow path and use the coordinator instead.

Real-world flow: durable agent handoffs

Now suppose Director asks Research for evidence, Builder for a migration guard, and Reviewer for a risk assessment. coordinate_bots turns those requests into a durable assignment tree—not just more chat text.

Director · requester

Calls coordinate_bots with 1–4 teammate ids, an explicit brief, optional done_when, and reply mode. Ends its turn after dispatch.

→

Coordinator · source of truth

Revalidates peers and destination, applies approvals and lineage limits, writes assignments to runtime.db, queues or runs each child.

→

Teammates · assignees

Each gets a trusted assignment envelope plus only the room/thread context available to it. Each uses its own model, tools, permissions, and working place.

The return edge is the important half

  1. Work completes. The coordinator records result text and observed evidence, not just a chat bubble.
  2. A report is composed. It distinguishes the teammate’s account from harness observation and the user’s approval.
  3. The requester resumes. With reply: "resume", settled downstream work wakes Director with reports to verify and reconcile. With reply: "none", ownership stays at the destination. External standing runtimes can poll instead.
  4. Director closes the loop. It can request concrete rework, perform missing verification, and then give the user one consolidated answer.

Work

Delegate a concrete task with acceptance criteria. Results return by default; no casual @mention follow chain is needed.

mode: work
reply: resume | none | poll

Consult

Ask for advice without authorizing action. The envelope explicitly says to answer from knowledge or quick checks and act on nothing.

consult: true
response resumes requester

Notify

One-way delivery. Nothing resumes the sender, and the recipient owns subsequent results and questions.

reply: none
no return wait

Post to room

A separate, budgeted post_to_room tool appends a bot-authored row but starts no turns. It is a bulletin push, not delegation.

09

Concurrency, context, and memory

Three different mechanisms are easy to conflate: ordering room speakers, resuming provider sessions, and compacting context. They solve different problems.

Default schedule

One speaker per room thread

A per-thread promise chain serializes room operations, and a multi-responder round awaits each member. Separate room tasks/threads can overlap. A busy bot is waited on or skipped depending on the path.

Opt-in schedule

Parallel job lanes

features.parallelRoomJobs allows multi-member coordinated jobs to open separate bot work threads. Their result cards return to the room; the requester resumes once with the settled set.

Opt-in reuse

Same-speaker deltas

Eligible Claude room sessions can resume and receive only new or changed lines. Configuration changes, speaker switches, stale/expired sessions, uncertain delivery, and near-compaction force a full replay.

Context control

Fresh session + recent room

Each member has its own context reading. At the default 90% threshold—or on explicit Compact now—the next room turn starts fresh with recent room messages rather than preserving a bloated native session.

What survives across turns?

  • Durable room truth: attributed transcript rows, bulletin, roster, policy, task ids, pinned working folder, and queue records.
  • Durable coordination truth: assignment trees, requester/assignee lineage, status, result, evidence, and inbox rows in SQLite.
  • Per-bot continuity: native resume cursors and handed-message bookkeeping where supported; persona, memory, skills, model choices, and permissions.
  • Ephemeral execution: the current speaker claim, process handles, turn-scoped internal capability, computer lease, live deltas, and watchdog state.

Automatic room recall explicitly does not search arbitrary private conversations. Optional recent-work and shared-team-memory features can add selected context, but they should not be mistaken for mirroring every bot’s private history into the room.

Trust boundaries and failure design

The architecture does not rely on well-behaved model prose. Identity, authority, and delivery are established from server records, then repeated in prompts so the model can interpret what it sees.

Provenance

Who wrote this line?

Transcript lines carry speaker attribution. Peer, webhook, and outside-API content receives explicit labels. escapeNotes defuses model-written imitations of harness envelopes.

Authority

A teammate cannot grant permission

Every assignment repeats that another bot’s message is not user approval. Effective approval mode and tool scope come from current records and the user’s decisions.

Loop safety

Budgets at several levels

One casual mention hop, coordinator depth/request/execution limits, duplicate suppression, ancestor refusal, per-turn post limits, and room posting budgets constrain runaway cooperation.

Failure recovery

Replay when certainty is lost

Full room windows, recovery text, session-reset paths, durable assignments, restart reconciliation, and stale-turn guards favor repeated context over silently missing work.

Failure is split into recoverable categories

A provider rejection is not the same as a completed turn with no summary, a human approval wait, a busy teammate, a stalled computer claim, or a server restart. The room host tracks turn outcomes and ownership; the coordinator separately tracks assignment lifecycle. That separation lets a downstream result return even when the requester’s original process invocation has ended.

Important: a teammate’s report is intentionally labelled as a claim to verify, not independent evidence. This is both a security boundary and a quality-control mechanism.

Low-level design: one turn, unwrapped

The detailed implementation follows a pipeline of synchronous claims and asynchronous setup. Names below are the actual functions and data structures to look for.

POST /api/groups/:id/messages
  validate body, group, thread, reply target, sendId
  sendSequencer.run(fingerprint)          // idempotent client retry
  admit("room", workingState)             // start now or durable queue

startGroupTurn(group, text, thread)
  append attributed user message
  responders = roomResponders(text, members, policy)
  if Auto and un-mentioned: await bounded decision, else use fallback
  groupQueues[thread] = previous.then(run this operation)
  for responder in round:
    await waitForChatRoomMember(...)
    await runGroupMemberTurn(...)

runGroupMemberTurn(group, thread, bot, hop)
  re-read fresh bot/group/engine and permissions
  claim bot activity + room speaker + internal generation
  roomWindow = roomTranscript.window(thread, reader=bot)
  mount per-bot agents/apps/browser/computer/data/MCP integrations
  system = buildSystemPrompt(identity, SOUL.md, room + private parts)
  tail = reply-as + coordination + held/card instructions
  dispatch = roomSessions.dispatch(fullWindow, optionalDelta, recovery)
  adapter.sendTurn(turn identity, prompt, model, cwd, integrations, approvals)
  consume canonical events until outcome
  persist terminal reply; release capability/speaker/resources
  optionally follow one level of room mentions

The data stores and their roles

messages.db

Message JSON, active branch leaf, follow-up queue, idempotency receipts, notifications, and full-text search. Shared room context is derived from these records.

runtime.db

Assignments, assignment events, and inbox rows. The full assignment record is schema-validated on every read.

events/<thread>.ndjson

Canonical provider event history. Secret-redacted and append-batched by the EventBus; useful for protocol and recovery investigation.

bots.json / groups.json

Durable registries for bot profiles/settings and room rosters/policies. Client wire projections omit server-private fields.

Bot folders

SOUL.md, memory, skills, and workspaces. Room cwd can pin a common folder, but each bot keeps its own environment.

In-memory maps

Speaker claims, per-thread promise queues, provider turn ids, context readings, capability generations, and resource leases. Durable stores are the recovery anchor.

Key low-level contracts

ProviderAdapter

The seam between orchestration and a provider. Inputs include thread/bot identity, text and optional recovery text, stable/volatile system halves, resume/reset controls, model selection, approval mode, tool scope, integrations, images, and cwd. Outputs are a turn id plus canonical events.

RoomWindow

Contains the rendered text, individual attributed lines, full context order, and readable ids. Keeping both text and ids enables session code to prove which exact lines a provider has—or has not—seen.

HandedState

Tracks the provider session, configuration, and message ids/cursors already delivered. Room sessions reuse this bookkeeping to avoid duplicates without gambling on missing context.

Assignment

A durable unit with root/parent lineage, origin, requester, assignee/destination, mode, reply behavior, level, status, result, evidence, budgets, and restart metadata. This is why delegation can outlive a single model turn.

Evidence, interpretation, and limits

The report describes the checked-out source at one commit. It is an architecture reading, not a benchmark or a claim that every optional integration was exercised.

Observed in source

Call paths, data structures, prompt composition, route/admission behavior, event shapes, persistence schemas, policy defaults, and end-to-end test scenarios. Inline file-and-line links provide the evidence trail.

Interpretation

“Transcript-centered orchestrator,” “separate lenses,” and the control/execution plane framing are explanatory models derived from those observations. Example agents and launch scenarios are illustrative.

Not claimed

No live provider, cloud computer, model quality, latency, or production-load measurement. Optional room sessions and parallel job lanes are identified separately from defaults. Source may have moved after this commit.

Scope. The report prioritizes the runtime and group-chat architecture. Team Cloud tenancy, voice, routine scheduling, packaging, and the many individual provider protocols are treated as adjacent modules, not exhaustively analyzed.
