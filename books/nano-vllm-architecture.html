From a request queue to a KV slot

A visual guide to nano-vLLM: a compact, synchronous offline inference engine whose central trick is to keep scheduling policy, physical cache ownership, and GPU execution separate.

SNAPSHOT bb823b3 · 26 APR 202621 PYTHON FILES · 1,450 LINESSTATIC SOURCE ANALYSIS · NO GPU BENCHMARK RUN

The public LLM class inherits the engine. A caller submits prompts; the engine repeatedly chooses one batch, runs the model, and feeds sampled token IDs back into request state. There is no HTTP serving layer in this snapshot.

The architecture in one sentence

The scheduler says which token positions need work, the block manager says where their KV state belongs, and the runner turns both into the tensors consumed by attention.

What this report establishes

Behavior is read from commit bb823b3. Performance benefits below are architectural interpretations, not measured speedups. README benchmark results remain author-reported.

JOURNEY

A token’s journey through an 8,000-token request

An enterprise-support assistant combines a system prompt, tool definitions, conversation history, and a new question. Follow that one request through nano-vLLM—then follow its first generated token, g₀, back into the next model invocation.

Narrative adapted from the local nano_vllm/flow.md. The six conceptual stops below are mapped to the frozen nano-vLLM implementation; broader platform examples in that narrative are not treated as features of this engine.

Illustrative configuration, not a benchmarkexact prompt = 8,000 IDsblock_size = 256prefill budget = 1,024max_model_len = 8,192max_tokens = 1288,000 + 128 = 8,128 ≤ 8,192

Assume the model supports at least 8,192 positions and enough KV capacity / sequence slots are available. The default max_model_len is 4,096, so this prompt requires a changed configuration. Callers must keep total positions in range; the setting is not an admission guard.

The exit is a branch, not another decode. EOS (unless ignored) or 128 completion tokens finishes this example and releases its block references. The final sampled ID may never acquire KV because there is no next run for it. After all queued inputs finish, generate() decodes collected completion IDs and returns ordered {text, token_ids} dictionaries.

flow.md’s six stops, mapped to concrete code

These are six responsibilities, not six sequential services. Cache ownership is decided during admission and used in every attention layer; cluster topology surrounds the loop. Sampling repeats inside it, and text decoding happens on completion.

USE CASES

Three cluster workloads, one engine-group architecture

A cluster runs many inference jobs, but the code here implements one cooperating engine group on one host. These three workload shapes show what flows through that group and which architectural boundary does useful work. A cluster’s job queue, routing, and serving adapter are deployment context; they are not implemented by nano-vLLM.

A · Bulk document summarization / offline analytics

What flowsThe batch of token histories becomes bounded spans of positions, then one contiguous input tensor plus attention metadata. Incomplete chunks update KV progress, not generated text.

Why the boundaries helpThe scheduler limits prompt work; BlockManager supplies physical addresses; the runner batches the selected positions without changing the model’s forward interface.

What remains costlyChunking does not reduce admission’s prompt-block reservation. Prefill has priority over running decode, so this simple policy does not promise decode fairness.

B · Repeated-prefix assistant / repeated-template burst

What flowsFour cached blocks become shared physical addresses and references. Only 64 suffix queries are computed, while attention reads 1,088 KV positions. Later decode batches change as requests finish.

Why the boundaries helpBlock tables join shared immutable prefixes to private mutable tails. Eligible decode graphs reduce repeated model-body launch work; they do not include logits or sampling.

What remains costlyPrefix hits do not eliminate full-context attention or decode. Cache is resident per engine group, with no cross-host sharing guarantee. Under pressure, preemption returns a request to prefill, reusing surviving eligible blocks and recomputing the rest—without CPU KV swapping.

“Assistant burst” describes the request shape or an offline replay. The supplied generate() enqueues its prompt list before stepping; an asynchronous serving adapter is outside this snapshot.

C · Large-model long-form / code generation on four GPUs

What flowsOne scheduled batch fans out as host metadata. Rank-local projections and KV heads operate on the same logical tokens; row outputs reduce across GPUs, then vocabulary logits gather to rank 0 for one sample.

Why the boundaries helpLarge projection weights and KV heads are partitioned across GPUs, while one coordinator preserves a single request lifecycle. This is capacity-driven cooperation inside each layer.

What remains costlyAll-reduces recur through the model and full vocabulary logits meet on rank 0. Four GPUs do not imply four times the throughput; this code has no multi-node router or distributed KV cache.

POLICY

Prefill first; reclaim by recomputing

The scheduler maintains two deques. It tries the head of waiting before touching running. A step never combines the two phases in one batch.

What “recompute” means

Preemption preserves the sequence’s prompt and generated token IDs. It clears the block table and marks the sequence for prefill again. A later admission can reuse still-cached full prefixes; any remainder is recomputed. There is no CPU KV swap path here.

What this policy favors

Interpretation: strict prefill priority and tail preemption make the policy compact and easy to follow. An already running request can wait while new prompt work is selected; this is not a latency/fairness policy with independent per-request priorities.

MEMORY

A block table is the bridge to the cache

Three objects are easy to confuse: a sequence’s logical token blocks, the block manager’s physical-ID metadata, and the runner’s GPU KV tensor. Only the last contains attention keys and values.

Sharing ends before the mutable tail

The prefix probe loops over range(seq.num_blocks - 1) and stops at the first missing or mismatched block. Shared blocks are already computed; the final block is freshly allocated and recomputed. That keeps the tail writable without a copy-on-write branch.

A free queue is also a retention policy

Released cached content survives opportunistically. A block can be both free for allocation and useful for a cache hit. Reuse revives it; a fresh allocation overwrites its identity. Interpretation: this is inexpensive retention tied to the allocation queue, rather than a separate cache-capacity controller.

DATA

Prefill and decode feed different attention APIs

The model sees flattened input IDs and positions. The runner installs attention metadata in a per-process Context; attention reads that context without widening every layer’s forward signature.

RUNTIME

Warm up once; replay selected decode shapes

Optimization is layered: selected elementwise helpers use torch.compile, attention uses FlashAttention and a custom Triton store kernel, and suitably sized decode batches can replay a CUDA graph. The whole model is not wrapped in torch.compile.

Cache budget, not a fixed request limit. The runner estimates bytes per block as 2 × layers × block_size × local_KV_heads × head_dim × dtype_bytes. Available block count comes from the configured GPU-memory fraction minus observed use and warmup peak overhead. This is computed per rank before the scheduler is constructed.
SCALE

One coordinator, sharded work on every GPU

Tensor parallelism partitions the tensor work inside each layer. Rank 0 stays in the caller’s process and owns the engine; ranks 1…N−1 are spawned ModelRunner processes. All ranks execute the same model layer sequence.

Why worker state is smaller during decode

Once a sequence is in decode, a worker needs the last token plus length, cached/scheduled counts, and physical block IDs. It does not need to receive the entire growing token history every step. The coordinator retains that history for output, preemption, and future prefill.

MODEL

A small model spine over reusable layers

The runner directly instantiates Qwen3ForCausalLM; there is no model-type dispatch registry. The HF config supplies dimensions and options, while custom modules implement the forward pass and tensor-parallel weight layout.

Practical boundaries to check before changing configuration

Model and execution stack are specific

The model class is hardcoded. The runner initializes NCCL, selects CUDA devices, and relies on Triton and FlashAttention; this snapshot has no CPU fallback path. A local model directory is required.

Graph coverage assumes a covered batch range

Buckets are [1,2,4,8] plus multiples of 16 up to min(max_num_seqs,512). With max_num_seqs=20, a decode batch of 17–20 has no covering bucket. Use a covered limit or disable graphs.

max_model_len is not an admission guard

It bounds config/warmup/graph sizing, but add_request() and completion handling do not enforce a prompt-plus-generation context cap. Callers should keep total token positions within the configured/model limits.

Sampling is deliberately narrow

The supplied parameters are temperature, max completion tokens, and EOS behavior. Temperature must be positive; the sampler has no greedy branch, top-k, or top-p controls.
