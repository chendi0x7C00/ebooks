OSDI 2022 Seoul National University · FriendliAI LLM Serving Continuous Batching 原点

Orca：把调度粒度从「请求」砍到「迭代」

一句话 thesis：自回归生成模型的每次前向只产出一个 token，因此推理 serving 的调度单位不应该是「一整个请求」，而应该是「一次迭代」——Orca 用 iteration-level scheduling（后来被称为 continuous batching）让每个 token 边界都成为调度点，再用 selective batching（只对非 Attention 算子做批处理）解决任意请求集合无法拼成大张量的矛盾，最终在 GPT-3 175B 上拿到同延迟下 36.9× 于 NVIDIA FasterTransformer 的吞吐。

01 · Problem

问题定义：生成式推理为什么撑破了旧 serving 范式

Triton、TensorFlow Serving 这一代 serving 系统建立在一条隐含假设上：一个请求 = 一次模型执行（ResNet、BERT 都满足）。GPT 类自回归模型打破了这个假设——一个请求要跑几十上百次迭代，每次只出一个 token，且每个请求需要的迭代数事先未知。

C1 · 早退的请求回不去，晚到的请求进不来

旧范式下调度器以请求为粒度把一批请求派发给引擎，引擎直到批内所有请求全部结束才整体返回。论文 Figure 3 的例子：x1（"I think" → 再生成 3 个 token）和 x2（"I love" → 只生成 1 个 token "you"）同批执行，x2 在第 2 次迭代就结束了，但引擎在第 3、4 次迭代里仍然为 x2 计算无意义的「占位 token」，x2 的结果也要等到第 4 次迭代批结束才能返回客户端。批执行期间新到达的请求，则必须排队等整批跑完。

▶ 跑一遍 · 请求级调度到底浪费了多少（论文 Figure 3 原样数据）
  1. 批 = {x1: 输入 2 token + 生成 3 token，x2: 输入 2 token + 生成 1 token}，共需 4 次迭代（initiation 1 次 + increment 3 次）。
  2. x2 在 iter 2 产出 <EOS>，已经死了；但 iter 3、iter 4 里它仍占着一个 batch 槽位，每次迭代对 每一层做一次完整前向 → 白算 2 次迭代 × 全部层。
  3. x2 的客户端等待 = 自己的 2 次迭代 + 陪跑 2 次迭代，归一化延迟直接翻倍。
  4. 若批内最长请求要生成 128 token（论文 trace 的 max_gen_tokens 上限），而某请求只生成 1 个——它要陪跑 127 次迭代。

来源：§1、§3 C1、Figure 3；128 取自 §6.2 trace 的 U(1,128)。

C2 · 迭代级调度想用，但「任意请求集合」拼不成批

把调度粒度降到迭代后，调度器每次选出的请求可能处在完全不同的状态，论文列出三种无法同批的情况（§3 C2）：

情况两个请求的状态为什么不能拼成 [B, L, H]图 4 中的例子
①都在 initiation 阶段输入 token 数不同（2 vs 3），L 维对不齐x3 与 x4
②都在 increment 阶段已处理 token 数不同，K/V 状态张量形状不同x1 与 x2
③一个在 initiation、一个在 increment一个并行吃全部输入 token，一个只吃 1 个 tokenx1 与 x3

传统批处理要求每次迭代的输入能 coalesce 成形状整齐的 [B, L, H] 三维张量。在真实负载下，恰好凑齐「同阶段、同长度」请求的概率随 batch size 指数下降（§3 C2 原文），不解决这个问题，迭代级调度就只剩「逐请求执行」，白白丢掉 GPU 的并行能力。

与前人的分水岭在哪

此前 · 请求级世界

  • Triton / TF Serving：只负责组批与派发，调度粒度是请求；引擎（FasterTransformer 等）内部把整批跑到完。
  • BatchMaker（RNN serving）：在 RNN cell 粒度调度+组批，思想最接近；但 RNN 每个 cell 计算完全相同，Transformer 每个 token 位置的 cell 依赖不同 K/V，图里有 L 种不同 cell（论文实验中 L 从 33 到 640），几乎永远凑不齐同构 cell，退回串行执行。

Orca · 迭代级世界

  • 调度器与引擎每次迭代交互一次：选请求 → 跑一次迭代 → 拿回 token → 更新池子。
  • 用 selective batching 让「任意请求集合」都能进同一个批：非 Attention 算子按 token 拍平成 [ΣL, H] 统一批处理，Attention 按请求拆开单独算。
  • 设计原则（§7）：每读一轮模型参数，尽量多做计算——参数从显存读出是大模型推理的主要瓶颈。
▶ 跑一遍 · 为什么 Attention 不批处理代价也很小
  1. 大模型推理是显存带宽瓶颈：每次迭代要把全部参数从 HBM 读进 SM。175B 模型 fp16 参数约 350 GB（论文 Table 1 + fp16 设定推得），摊到 16 张卡每卡约 22 GB。
  2. 批处理 Linear 层时，B 个请求共享同一份参数读取——读一次 22 GB 算 B 份，这是批处理的核心收益。
  3. Attention（狭义定义，§3 脚注 1）不含任何模型参数，Q·K、softmax、加权 V 只碰激活与 K/V 缓存。
  4. 所以对 Attention 不组批，没有「参数复用」这块收益可损失；代价只是 kernel 变小、启动次数变多——§6.1 实测单 VM 内性能差距「relatively small」。

来源：§3 S2、§6.1 Figure 9a/9b。350GB/22GB 为从论文配置直接推算。

▶ 跑一遍 · Selective batching 的张量形状（论文 Figure 5 原样）
  1. 调度器某轮选中 (x1, x2, x3, x4)：x1 increment（1 token）、x2 increment（1 token）、x3 initiation（2 token）、x4 initiation（3 token）→ 共 7 个 token。
  2. 拍平成 [7, H]，依次过 LayerNorm → QKV Linear（变 [7, 3H]）→ Split。
  3. Attention 按请求拆 4 路：[3,H]（x1 含历史 K/V 共 3 个 key/value）、[1,H]、[2,H]、[3,H]——x1、x2 的历史 K/V 从 K/V Manager 按 request id + token index 取地址。
  4. Merge 回 [7, H] → Attn Out Linear → 后续 MLP / Add / LayerNorm 全部按 token 批处理。整个 Transformer 层里只有 Attention 一处需要「请求」概念。

来源：§3 S2、Figure 5。一次迭代覆盖 4 个状态迥异的请求——这在请求级调度下根本不可能成批。

05 · Design Decisions

关键设计决策：五张卡片看懂 Orca 的取舍

每张卡片固定四段：决策问题 → 被否决的备选（点名同行工作）→ 为什么这样选 → 代价。这是全文最有价值的部分。

D1调度粒度：迭代级，而不是请求级

决策问题

serving 系统与执行引擎多久交互一次？交互的间隔就是请求能加入/退出批的最小窗口。

被否决的备选

  • 请求级（Triton、TF Serving、Clipper + FasterTransformer 等一切现有组合）：批一旦派发就冻结，早退的陪跑、晚到的干等。
  • Cell 级（BatchMaker，RNN）：对 Transformer 凑不齐同构 cell（每个 token 位置 K/V 不同），退回串行。

为什么这样选

自回归生成的天然节拍就是「一次迭代一个 token」。调度器每迭代拿回结果：完成的请求立刻释放+响应，新请求最坏只等一次迭代就能上车。调度器由此获得对批组成的完全控制权。

代价 / 权衡

① 调度器与引擎必须紧耦合，牺牲了 Triton 式「serving 层 / 引擎层」的抽象分离（论文 §7 自认留给 future work）；② 每迭代一次控制往返，调度回路本身不能成为瓶颈——这逼出了 D4 的控制/数据面分离。

D2Selective batching：只对非 Attention 算子做批处理

决策问题

迭代级调度选出的请求状态各异（不同长度、不同阶段），无法 coalesce 成 [B,L,H]——批处理还要不要？

被否决的备选

  • 全量批处理：物理上不可能，三张量形状对不齐（§3 C2 三种情况）。
  • 放弃批处理逐请求跑：丢掉 GPU 并行度与参数复用，大模型下吞吐崩盘。

为什么这样选

把所有 token 拍平成 [ΣL, H]——Linear / LayerNorm / Add / GeLU 根本不需要「请求」概念，照批不误；只有 Attention 需要请求边界，Split 开逐请求算、Merge 回来。而 Attention 不含参数，不批它不损失参数复用收益。批处理的肥肉全保住了，只扔了骨头。

代价 / 权衡

① Attention kernel 变成许多小异形计算，Orca 用「把各请求的 thread block 拼进一个 kernel」的激进融合来压启动开销（§5，自认违背 CUDA 常规实践）；② 单 VM 纯引擎微基准下略慢于全量批处理的 FasterTransformer（§6.1 承认 similar or slightly worse）。

D3K/V 显存：按请求 max_tokens 预留，slot 记账防死锁

决策问题

K/V 缓存要持有到请求结束才能释放，显存先到先得可能让调度器陷入「任何请求都无法再前进一步」的死锁。怎么管？

被否决的备选

  • 按模型 max_seq_len 统一预分配（FasterTransformer：每请求按 2048 上限预留）→ 13B 模型 batch≥8、101B batch≥16 直接 OOM（§6.1 实测）。
  • 不预留、用到再分 → 上述死锁。

为什么这样选

请求首次被调度时按其 max_tokens 属性一次性预留 slot（n_rsrv += max_tokens ≤ n_slots 才放行），结束时归还。只要放行就保证够用到底——不死锁是构造出来的，不是碰运气。且 n_slots 是唯一显存旋钮，运维「用满即可」，无需调参实验。

代价 / 权衡

按上限预留是保守的：请求若提前 EOS，多占的 slot 直到结束才还。这条浪费后来被 vLLM 的 PagedAttention（分页按需分配）解决——本篇论文没走到那一步。

D4控制面 / 数据面分离：gRPC 走 CPU，NCCL 只搬张量

决策问题

worker 之间每次迭代都要交换控制消息（batch 里有哪些请求、各自 token index……），走哪条通道？

被否决的备选

一切走 NCCL（FasterTransformer、Megatron-LM 的做法）：NCCL 是 GPU↔GPU 通道，CPU 要读消息必须 GPU 同步——每迭代每进程一次 CPU-GPU sync，开销不可忽略。

为什么这样选

控制消息与 token 走 gRPC（纯 CPU 通道），NCCL 只用于 GPU 产生/消费的中间张量。Worker 的 controller 解析完消息就发 kernel、并立即把控制消息转发给下一个 Worker，不等本机 GPU 算完；只有末尾 Worker 同步一次取回 token。175B 纯引擎对比中 Orca 因此快出至多 47%。

代价 / 权衡

多维护一条通信栈（gRPC + NCCL 并存），且 CPU 线程异步发 kernel 要求控制消息自包含（request ids + token index + 输入长度），消息设计不能偷懒。

D5流水线：整批流水，不切 microbatch

决策问题

多个 inter-layer 分区（Worker）如何流水起来，让每个 Worker 都不闲着？

被否决的备选

microbatch 流水线（FasterTransformer）：把一批切成 microbatch 在分区间流水。但 microbatch 越小批处理收益越薄，越大则流水线气泡越多——批处理效率与流水线效率被迫二选一。

为什么这样选

迭代级调度天然允许「上一条批还没回来就注入下一条」：调度器保持 in-flight 批数 = Worker 数（Algorithm 1 line 9-10），批次整体流动，不用切。批处理效率和流水线效率两头都拿满。

代价 / 权衡

in-flight 批数翻倍意味着 K/V 显存里同时挂着更多请求的缓存，n_slots 要相应放大；调度回路复杂度也随之上升（返回的批不一定是最后注入的批）。

▶ 跑一遍 · D5 的两难：microbatch 到底亏在哪（Figure 8b）
  1. FasterTransformer + 3 个分区：批 AB 切成 microbatch {A}、{B} 流水 → 每个分区每次只对 1 个请求做批处理，GPU 并行度浪费一半。
  2. 不切（mbs = max_bs）→ 分区 2、3 等分区 1 把整批算完才能开工，流水线退化为串行，气泡率 2/3（示例值：3 分区仅 1 个在忙）。
  3. Orca：批 AB 整批流过 W1→W2→W3，同时 CD、EF 紧跟其后——任意时刻 3 个 Worker 各算一个完整批。两难消失。

来源：§4.2 Pipeline parallelism、Figure 8。

同质请求 trace：Orca 的优势从哪来、又不是什么（Figure 11）

当 trace 中所有请求输入/生成长度完全相同（(32,32) 或 (256,256)），早退问题消失，FasterTransformer 调大 batch 后性能回升——但 Orca（max_bs ≥ 8）仍然胜出；唯一例外是 max_bs = 1 的 Orca 退化成不批处理的纯流水线而落败。工程师视角：这组对照实验干净地证明了 Orca 的增益大头来自调度机制本身（迭代级 + 流水），而非 kernel 实现差异——单 VM 微基准里两家 kernel 是打平的。

07 · Critical Reading

批判性阅读：局限、质疑与可以直接偷的思想

论文自认的局限

  • trace 是合成的。没有公开的生成式请求 trace，只能采样 U(32,512) × U(1,128) + Poisson 到达；且假设模型永远生成到 max_gen_tokens（没有真实 checkpoint，无法知道 <EOS> 何时出现）。真实分布可能更友好或更恶劣。
  • 只在语言模型上验证。方法声称适用于一切自回归 Transformer（图像、语音等），但实验只有 GPT。
  • serving 层与引擎层失去抽象分离。论文明确说「如何设计一个既支持这两项技术又保持两层解耦的通用接口」留给了 future work（§7）。
  • max_bs 仍需人工调。论文承认增大 max_bs 不保证在任何硬件/负载下都不伤延迟。

读者（工程师视角）的质疑

  • FCFS + 按上限预留，是双重的保守。一个 max_tokens=640 的请求先占住 640 个 slot，实际可能 50 token 就 EOS；FCFS 又没有抢占与优先级——头部长请求会拖住短请求的 TTFT 体验吗？论文没有给出分位数延迟（只有中位数），P99 的表现是未知数。
  • n_rsrv 记账粒度是「请求」而非「token」。这正是 vLLM（PagedAttention, SOSP 2023）后来攻击的点：按需分页分配把 K/V 浪费从「max_tokens 上限」降到「一个 page 以内」。Orca 开了调度的口子，vLLM 补上了内存的口子。
  • 没有失败与 SLA 叙事。Worker 挂掉怎么办？多租户优先级？论文完全聚焦吞吐/延迟，生产运维面留白。
  • 47% 引擎优势的边界。该数字来自 175B 双 VM 场景且「up to」；单 VM 内 Orca 反而略慢——跨机控制消息越频繁收益越大，单卡小模型场景迭代级调度的开销能否回本，论文未测。

可以直接偷的思想

  • Continuous batching 本身。「每个 token 边界都是调度点」如今已是 vLLM、TGI、TensorRT-LLM（in-flight batching）、SGLang 的标配——这篇论文是整个现代 LLM serving 调度层的原点。
  • 按 token 拍平 [ΣL, H]。把 batch 维从张量里抹掉、只在需要序列边界的算子处 Split/Merge——今天的 ragged batch / varlen attention kernel（flash-attn 的 varlen API）是同一条血脉。
  • 「Attention 无参数 ⇒ 不批它代价小」的账本思维。判断一个算子值不值得批处理，先问它有没有参数可复用。这套 memory-bound 视角可以推广到任何算子取舍。
  • 控制面绝不碰 GPU 通道。CPU 要读的消息走 CPU 网络（gRPC），GPU 通道（NCCL）只搬 GPU 数据——消除隐藏同步点，对任何分布式推理/训练系统都成立。
  • 「放行即保证够用」的资源记账。调度器在准入时就预留全部所需资源（n_rsrv ≤ n_slots），把死锁从运行时风险变成编译期（准入口）不可能事件。
