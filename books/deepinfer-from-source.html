A developer submits two prompts to LLM.generate. Request A is a long explanation request. Request B is a short question with a small output limit. The caller wants two answers in input order. The hardware sees work that changes shape as the requests progress: many prompt tokens at first, then a stream of smaller steps, with B finishing before A.

The model can score the next token. Someone still has to decide which requests run, where their history lives, and when their results are safe to return. DeepInfer puts those responsibilities in an inference engine. Its public LLM wrapper submits requests and repeatedly advances that engine; its worker executes the selected model work. The offline wrapper, the worker step

This book follows A and B across that boundary. Their words, token counts and timing examples are teaching inputs. They are not a recorded execution or the tokenizer output of a particular checkpoint. When A later receives an image, or B must return JSON, we keep the same questions: what state changes, who owns it, and which operation can legally happen next?

Begin with the smallest machine

Consider a function that accepts a token history and returns scores for possible next tokens. A sampler chooses one token from those scores. Append it to the history and repeat until a stop condition holds. This is enough to describe autoregressive generation: each new token depends on the preceding tokens.

Teaching pseudocode, showing the dependency without the runtime:

history = encode(prompt)
answer = []
while len(answer) < output_limit:
    scores = model(history)
    token = choose(scores)
    history.append(token)
    answer.append(token)
    if token == end_token:
        break

The loop leaves several costly decisions implicit. Recomputing the whole history at every step repeats work. Holding every request's intermediate state forever exhausts memory. Processing A to completion before admitting B prevents them from sharing a batch. Copying results too late can read storage that the engine has already reused.

These are properties of the problem. DeepInfer's particular answers include block-managed cache storage, a native scheduler, pooled metadata and outputs, and an execution path that can overlap CPU and accelerator work. Other runtimes can use different scheduling or memory strategies while preserving the same ownership and dependency rules. Scheduler inputs and outputs, output lifetime

Two different shapes of work

Prefill processes the supplied prompt and builds the state needed to continue it. Decode extends a sequence whose prompt has already been processed. A long prompt exposes many positions for one prefill operation; ordinary autoregressive decode must wait for the previous token before it knows the next input. Speculative decoding changes how many proposed tokens can be checked together, but still has to decide which proposals become committed history.

That difference affects batching. A batch chosen for prompt work has different input lengths and costs from one chosen for continuation work. The frozen scheduler marks a step with prompt_run, carries query lengths in seqlens_q, and records its token count and estimated floating-point operations (FLOPs). The names describe scheduling data; they do not measure the time the batch will take. The step description

For our two requests, the engine must preserve A's history while B makes progress, then reclaim B's resources without disturbing A. A useful minimal state model therefore needs a request identity, token history, generation rules, cache ownership, and execution status. It also needs a temporary description of the work selected for one step. Keeping the request and the step description distinct lets a long-lived request participate in many differently shaped batches.

The design inference is that this separation makes ownership easier to reason about as work moves between Python, native code and the device. The implementation gives those responsibilities concrete names: Sequence, SequenceMetadata, SchedulerOutputs, and WorkerStepState. Their lifetimes become central in chapter 2 and chapter 5. Follow responsibilities across the language boundary

The Python entry point accepts strings or token IDs, prepares per-request sampling parameters, and restores input order in the returned results. LLMEngine connects that interface to the scheduler and workers. This is a convenient place to read the system because the orchestration is visible without starting at a device kernel. Input handling, result collection

The C++ scheduler chooses requests and produces the metadata for a step. Python receives both the sequence metadata and SchedulerOutputs. It arranges any cache/state copies, then coordinates worker execution. Native ownership bookkeeping and Python orchestration are therefore parts of one path, not separate implementations of the same engine. The engine's scheduling boundary

The worker has a precise ordering: run the current forward pass, post-process the previous step, sample the current step, then either post-process it immediately or retain it for the next step. Prefill and non-overlapped execution take the immediate path. Overlapped decode retains prev_step_state. This is why “the next token” and “the output returned by this call” cannot always be treated as the same temporal event. Execution order

An offline core with service extension points

The release studied here supports DeepSeek-V4.1-Flash on NVIDIA SM100 GPUs and Huawei Ascend 950 NPUs. Its prerequisites name Linux, Python 3.12, GCC 13 or newer, and the corresponding CUDA or CANN toolchain. These are version constraints of the frozen release, not requirements inherent to every inference engine. Supported model and hardware

The README separates the supplied core from a complete inference service. It lists a KV cache system, Vision Encoder/Prefill/Decode disaggregation, and load balancing across data-parallel replicas as missing service components. This does not mean the code has no local cache allocation. The block managers and device cache are necessary for execution inside the engine; a larger cache storage and reuse service has a different scope. Release boundary

Likewise, EngineType exposes NORMAL, PROMPT, and COMPLETION. These modes help explain where an integration could separate stages. Their existence alone does not provide a deployed network protocol, load balancer, or storage service. The public wrapper sets offline_inference=True when it builds EngineArgs. Engine modes, offline construction

What can go wrong before an answer exists?

An invalid call can fail before admission: the wrapper rejects missing prompts and token IDs, or mismatched list lengths when both are supplied. Resource pressure can prevent a request from running in a chosen step. Once execution overlaps, an apparently finished scheduling loop can still have output in flight. The wrapper explicitly calls flush_inflight_reqs when it sees no unfinished work, and clones each raw output before retaining it. Validation, flush and clone

Cancellation and shutdown are separate operations. abort_request targets request identities through the scheduler and multimodal processor. close stops engine-owned facilities and workers. Neither should be assumed to supply a universal recovery protocol for an arbitrary process crash. Later chapters follow their actual scope, including paths that have not yet entered the scheduler. Abort, close

For your own engine, start with the simple generation loop and write down every value that outlives one iteration. Decide who may mutate it, who may borrow it, and what event ends the borrow. Then introduce batching and overlap. A synchronous implementation can be easier to inspect and adequate for a small workload; an overlapped implementation needs a more explicit account of unfinished work. The next chapter follows that account from the first API call.

A developer passes two prompts, A and B, to LLM.generate. A has the longer prompt. B will reach its generation limit first. The caller wants two answers in input order, even if the engine processes their tokens at different times.

A prompt can span several steps. Each step may produce no token, one token, or several accepted speculative tokens. Requests can also finish while the device still has work in flight. The engine needs a persistent request object whose identity survives every temporary batch.

For the examples in these chapters, A contains 12 toy prompt tokens and allows four output tokens; B contains four prompt tokens and allows two. These numbers illustrate state transitions. They are not a model tokenizer's output or a measured workload.

Admission creates a boundary

LLM.generate accepts text, token IDs, or both. It requires at least one input form, converts a single string into a list and checks that text and token-ID lists have matching lengths when both are present. It then submits every input before running the engine loop. This makes the batch available to the scheduler as a collection of independent requests. Input handling.

The wrapper assigns each request a string ID from a counter. It deep-copies SamplingParams, tokenizes text when the caller supplied no IDs, and converts IDs to a NumPy int32 array. Copying parameters gives A and B separate mutable parameter objects even when the caller supplied the same object for both. The engine later adds its EOS identifier and may adjust options, so isolation has an observable purpose. Request preparation, engine parameter setup.

There are two levels of identity. request_id identifies the caller's request; seq_id identifies a particular native sequence. Ordinary offline requests have one sequence each. The distinction becomes useful when a cached sequence is forked: a branch retains the request identity while receiving a new sequence ID. The scheduler and overlap machinery can then distinguish branches that belong to one request. Sequence creation, fork identities.

Admission can fail before a sequence reaches a queue. The engine raises ValueError for an empty prompt. For token IDs outside the permitted vocabulary range, it logs the problem and returns None. Those behaviors differ from a request that enters the scheduler and later receives a terminal rejection record. The wrapper does not make submission transactional: if a later input raises, earlier inputs may already have been enqueued. An integration built around this API must account for that distinction. Validation and construction.

A sequence keeps the facts that a batch cannot

The Python name Sequence refers to a C++ class imported through _C.engine. At that boundary, the constructor requires C-contiguous int32 arrays and copies their tokens into native vectors. Changing the caller's array afterward does not edit that stored history. The binding does not silently convert an arbitrary list or incompatible array. The wrapper's NumPy conversion handles common inputs, while direct engine users must satisfy the native contract. Native binding, token storage.

The native object groups its state by responsibility:

State What must survive a step
Request Request ID, sequence ID, user and arrival information
Input Committed token history, compressed token history and multimodal data
Generation Parameters, captured sampling scalars, stopping rules and prompt log probabilities
Cache Physical block IDs, cached-token count and optional model-state slot
Scheduling Status, readiness, branch, chunk progress and in-flight reservations
Speculation and constraints Draft/accepted tokens, speculative slots and grammar-matcher state

These groups are fields inside one sequence, not independent services. A step creates a smaller SequenceMetadata view for execution. That view copies scalars such as the selected query length, while borrowing several vectors from its sequence. State groups, sequence and metadata construction, borrowed metadata.

The constructor tests document that boundary carefully. They cover ordinary arrays, compressed-token arrays, incompatible dtypes, noncontiguous views and read-only frombuffer inputs. They also permit an empty native sequence, even though engine admission rejects an empty prompt. These are tests of a lower-level storage contract, not evidence that every engine input is accepted or that inference has run successfully. Constructor test intent.

WAITING means the request still needs admission or more prompt processing. RUNNING means it has entered generation. A sequence can be marked running when its final prompt chunk is scheduled, before that device work completes. Queue membership and status therefore answer different questions. The scheduler's step output also retains shared pointers to scheduled sequences while their work is in flight. Admission transition, step ownership.

Prompt work changes into generation

Prefill computes the model state for prompt tokens. Decode extends a request after that prompt state is available. A's first chunk might only advance its cached-token count. Its last chunk can produce its first output token. B can complete its shorter prefill in the same later step. Chunk completion, unfinished chunks.

When results return, the scheduler appends accepted tokens to the committed history. It checks stopping conditions after each appended token, so an accepted speculative prefix can stop partway through a step's possible outputs. The checks recognize EOS unless ignored, total sequence length beyond max_model_len, and output length equal to max_tokens. A terminal status records why generation ended. Token commitment, stop checks.

B reaches two output tokens first and becomes FINISHED_LENGTH_CAPPED. A remains eligible for more work. Logical completion does not release every resource at once. A later scheduling boundary removes finished running entries; the engine's pre-sampler callback finalizes them and returns their cache blocks. Finished removal, finalization callback.

Cancellation marks state before cleanup

abort_request asks the scheduler to mark matching unfinished entries in waiting and running as FINISHED_ABORTED. It also removes multimodal processing records and returns counts of aborted sequences and their tokens. The scheduler does not immediately erase every marked entry or return all memory from this method. Abort implementation, engine abort.

This separation matters when the device already holds a request. Its physical computation may complete, but output processing sees the terminal status and commits no new tokens. Waiting entries are collected by a later scheduler pass. An abort is thus a state transition followed by cleanup, rather than proof that no further device work occurred. Late-result handling, waiting cleanup.

Cancellation has a version boundary. The native abort scan covers two queues; it does not scan the prompted fork queue. Grammar compilation can also hold a request outside the scheduler, and the engine's abort method does not cancel that pending builder work. A service wrapper would need a wider cancellation protocol, including admission that completes after cancellation. This release explicitly provides an offline wrapper rather than an online-serving wrapper. Delayed grammar admission, release scope.

The caller needs its own output lifetime

Engine steps return an array of integer addresses for native RequestOutput objects. The pool constructs these objects in reusable storage and destroys them when the engine releases the step's results. An address is useful for fast access while the object is live; keeping the number does not extend that lifetime. Output pool.

The offline wrapper immediately calls RequestOutput.clone for every returned address. The binding creates an independent object by copying the original. The wrapper groups these clones by request ID and sorts numeric IDs before returning results, which restores input order despite B finishing first. Clone binding, collection loop.

By default, decode_sequence=True turns each request's cloned token results into a decoded string before returning. Setting it to False returns a per-request list of cloned RequestOutput objects, preserving token IDs, probabilities and finish information for the caller. Both modes use the same internal cloning step; they expose different final representations. Return-mode default, result conversion.

See diagram: A clone crosses the result lifetime boundary →

The final flush handles a remaining decode step whose CPU postprocessing was deferred. It is a normal completion operation, separate from close, which shuts down engine resources. Flush, close.

Persistent request state, temporary execution views and caller-owned results have different lifetimes. Separate representations let the engine reuse hot-path objects without making the caller track device events or scheduler queues. An integration that exposes native step outputs must preserve that boundary itself: read or clone each live result before allowing the engine to recycle it.

A and B have been admitted, but admission does not make accelerator capacity unlimited. A's 12 prompt tokens require more work than B's four. Their cached histories occupy memory after prefill, and future decode steps need room to grow. The scheduler must choose a batch that satisfies all of these constraints while preserving each request's progress.

A useful minimum model has two queues, two kinds of work and several budgets. Waiting requests need prefill. Running requests need decode. A token budget limits work in one step, a sequence budget limits active requests, and a block budget limits stored model history. DeepInfer adds model-specific state slots, image boundaries, context-parallel alignment and speculative work to that model.

A step has one phase

DeepInfer's NORMAL engine selects either a prompt step or a decode step. A prompt step can include several requests, but the scheduler does not mix ordinary prefill and decode requests into one heterogeneous batch. PROMPT and COMPLETION engine types select their respective phase directly. Phase dispatch.

This choice extends across data-parallel ranks. Data parallelism, abbreviated DP, assigns different requests to cooperating ranks. Each rank can have a different local queue, yet the group must agree on the phase of a step. The scheduler uses collective votes to coordinate that agreement. The design inference is that a locally attractive phase cannot be chosen independently when the execution group requires matching operations. Group phase selection.

A rank wants prefill only when its waiting head is ready and reported cache usage is at most 90%. At an ALL attempt point, every rank must want it. At an ANY point, one rank is sufficient. The defaults attempt ALL every 70 decode steps and ANY every 100; an ANY point takes precedence when both coincide. Prompt steps reset the decode counter, allowing consecutive prefills when the ALL condition holds. Vote conditions, defaults.

The second vote checks whether any rank actually produced prefill output. A ready queue can still fail admission because slots or blocks are unavailable. If every rank came back empty, the group decodes instead. Otherwise a rank without local prompt work runs an empty prompt step to stay in phase with its peers. This prevents a loop of empty prompt attempts that repeatedly resets the decode counter. Empty-attempt handling.

Waiting does not mean schedulable

The prefill scheduler examines the waiting queue from its head. It removes requests already marked aborted or failed. A request whose dependencies are unfinished blocks admission at that point. For example, adding an image to A makes it initially unready; multimodal processing later marks it schedulable. B can wait behind A even when B itself is ready. This is head-of-line blocking, an explicit consequence of the queue walk. Queue walk, initial readiness, readiness update.

Memory admission has three answers. OK means the blocks are available now. LATER means the request could fit but current free resources are insufficient. NEVER means its requirement reaches or exceeds the manager's total count, including reserved block zero. A temporary shortage stops the queue walk; an impossible request becomes FINISHED_IGNORED and the scheduler continues. Prompt length beyond the configured prompt limit produces the same terminal status. Allocation outcomes, admission decisions.

Temporary shortage leaves a request queued because existing work may release enough memory. An impossible requirement ends the request because an empty engine would still be too small. Stopping at a temporarily blocked head trades selection flexibility for a straightforward queue discipline: a smaller request behind A cannot use spare capacity until the walk can pass A.

Chunks bound work per step

Give the teaching engine an eight-token prefill budget, two sequence slots and context-parallel size one. Disable drafts and lookahead, and assume sufficient KV blocks, model-state slots and context-length allowance. These are chosen teaching conditions, not runtime defaults. With chunked prefill enabled, A first contributes eight tokens. It keeps waiting because four prompt tokens remain. On the next prompt step, A contributes four and B contributes four. Both prompts finish, and both can produce their first output token.

The source computes remaining prompt work as full token history minus cached tokens. It limits that work to the remaining batch-token allowance, rounded for context-parallel alignment. It can shorten the chunk at an explicit checkpoint. Image units add another boundary: a chunk must not cut between an image marker and its padding tokens. The first request can be extended to include an image unit only if the batch budget still permits it. Work and alignment, image-unit adjustment.

Other limits remain active. The scheduler counts available request slots, caps the sum of full context lengths, requires enough work for configured lookahead, and checks that the final token count fits the batch limit. A chunk still needs those conditions; enabling chunking does not override them. Admission limits, final batch check.

The context and work limits count different things. On the second teaching step, A contributes four new prompt tokens but has a 12-token history. B contributes four and has a four-token history. Their new work totals eight, while the scheduler's full-context sum is 16. A batch can therefore fit the token-work limit and still exceed the context limit. Keeping both counts makes that failure explainable; one generic "batch size" would hide which resource prevented admission.

Chunking changes compute allocation more than initial memory allocation in this version. The scheduler checks the sequence's full block requirement before choosing a chunk and allocates those blocks when it commits admission. Why equal slot counts can still be slow

Equal numbers of stored experts do not guarantee equal work. If A and B repeatedly select experts on rank 0, rank 1 can finish early and wait. The slowest rank delays the collective step.

Expert parallel load balancing, EPLB, uses observed routing counts to change placement. Each layer records physical expert receive counts. The load balancer collects a window of those counts, maps physical copies back to logical identities, and combines the histories across EP ranks. It can then decide which experts deserve extra copies and where every copy should live. Source: statistics window, logical history aggregation.

The source policy performs two greedy searches. First, it allocates redundant copies using the historical per-step loads. Next, it orders physical copies by their total per-copy load and places each on a rank with remaining capacity. The placement score is the sum, over history steps, of the largest rank load. This captures complementarity: two experts busy on different steps can fit together better than two experts busy together, even if their total counts match. Ties preserve original physical order during sorting and prefer the smallest rank ID during placement. Source: replica allocation, placement objective.

The lab divides each logical expert's work evenly among its copies. The policy uses this per-copy estimate. Measured latency also depends on communication, matrix sizes and future routing changes.

Moving weights without changing meaning

An updated routing map is useful only after its destination slots contain the correct weights. DeepInfer computes the next maps, shuffles expert weights, then copies the maps into the runtime state. In a suitable GPU domain, shuffle uses symmetric memory mirrors; the alternative uses distributed transfer. The first rearrangement also releases cached device memory before allocating shuffle support. Source: shuffle setup, shuffle-before-map update.

Rearrangement has a cost. It communicates counts, moves weights, consumes temporary memory and can synchronize the device through an explicit exception to the launch-time synchronization guard. A static layout can be preferable when routing is stable or the expected savings are smaller than that cost. Recent history is also an estimate of future demand; the source does not guarantee that every rearrangement improves the next batch.

Each model round includes input preparation, kernel launches and distributed coordination. If A could obtain several useful tokens from that step, it might need fewer rounds. A smaller draft computation can propose those tokens first, then the main model can check them together.

The constraint is that a proposal has no authority to change the request's committed history. Once one proposal fails, later proposals were conditioned on a history the request will not keep. The runtime must commit only a valid prefix, choose a replacement at the failure point, and start drafting from that new boundary.

Two rounds share one proposal record

After a decode round has chosen its final token, DeepInfer's DFlash module generates proposals for the next round. The next main-model forward evaluates the scheduled proposal prefix. Sampling verifies that prefix, identifies the final row, and launches DFlash again from the newly chosen token. Prefill already updates the draft model's main-token cache during the main forward; it does not run an extra draft prefill through the sampler. Source: sampler phase contract, decode integration.

Suppose A proposes [41, 72, 19]. If 41 passes and 72 fails, the emitted sequence is [41, replacement]. Token 19 contributes nothing to the committed prefix. If all three pass, the final fresh-sampling row supplies one further token. A row can have been computed without becoming output.

The proposal record must preserve more than IDs. Verification needs the distribution that produced each draft token. MTPInfoPool stores proposal IDs, log probabilities and confidence in stable GPU slots owned by the scheduler. Slot 0 is reserved for padding, and writes to it are skipped. Full-vocabulary proposal log probabilities occupy rows × vocabulary × four bytes; a restricted top-k representation needs an additional vocabulary-ID map. Source: proposal pool.

The current implementation orders proposal writes and next-round verification reads on the same stream. Moving either onto another stream would require an explicit dependency.

What DFlash computes

The frozen runtime supports DFlash speculative heads. The runtime class is DFlash; checkpoint fields retain dspark_ names for target-layer IDs, a noise-token ID and Markov rank. The number of draft decoder layers is also separate from the maximum number of proposed tokens. Source: head construction, DFlash validation and settings.

The main model extracts attention-input features from configured layers. DFlash projects those features and writes main-token keys for its own layers. Draft execution then embeds a fixed-width block whose first token is the chosen token and whose remaining entries are noise tokens. It runs the draft layers over that block. Sampling visits proposal positions in order; when enabled, a Markov embedding of the preceding token adjusts logits and contributes to confidence prediction. Source: feature extraction constraints, cache update and draft initialization, proposal sampling.

The code calls that first chosen token golden_tokens. Here it means the final token selected for this round; it need not come from the separate teacher-forcing override.

DFlash and the main model must use the same sliding-window size because they share the cache layout. The main forward can write keys at positions that are later rejected: the subsequent draft write overwrites those positions before they are read. The overwrite must happen before the next read. Source: equal-window requirement, overwrite argument.

Acceptance needs both distributions

Use p for the draft distribution and q for the main model's processed target distribution. In ideal speculative rejection sampling, a proposed token x passes with probability min(1, q(x) / p(x)). If it fails, choose a replacement from probabilities proportional to max(q − p, 0).

For example, if p(x) = 0.5 and q(x) = 0.2, acceptance probability is 0.4. A uniform draw of 0.7 rejects it. The replacement favors tokens whose target probability exceeds their proposal probability, correcting the draft's excess mass.

See diagram: Ideal correction and the source adjustment →

That is an ideal mathematical model. DeepInfer uses the same acceptance ratio, but its residual weights are max(q − αp, 0), with α = exp(−0.00005). It also accumulates sampling mass in fixed-point form and falls back to the first maximum-logit token if residual mass is zero. The shared constants file derives a bound on the distribution change caused by the penalty. The implementation therefore should not be described as exactly identical to ideal real-arithmetic rejection sampling. Source: acceptance and residual, fallback, penalty and bound.

Independent per-row decisions still need prefix logic. The sampler packs accepted draft IDs separately from the first rejected or final fresh row. It returns the request-local offset of that row as last_valid_offset, which also locates the next draft boundary. Source: finalization contract.

Confidence decides how much to verify

Proposing several tokens does not make verifying all of them worthwhile. Each extra verification row costs work, and a late proposal is useful only if every earlier proposal survives.

DFlash predicts a confidence for each position. The scheduler converts these into prefix-survival estimates by multiplication. With confidences [0.9, 0.8, 0.5], the estimated value of verifying successive proposals is [0.9, 0.72, 0.36]. Across A and B, the scheduler can allocate a shared row budget to the most promising positions, while giving each request one base query row.

The CPU scheduler evaluates candidate total budgets using expected emitted tokens divided by estimated forward-plus-sampler time. The time estimate includes the captured graph bucket, a measured forward correction and recent sampler timings. Consequently, an additional row can be cheap inside an existing bucket and more expensive when it requires the next bucket. If no performance curve is available, the scheduler uses all available draft tokens. Source: budget search.

Where speculation stops helping

A poor draft spends work on rows that the main model rejects. A small batch can also make the draft overhead harder to repay. The confidence scheduler addresses the amount of verification work; it cannot make an inaccurate draft correct.

When an emitted prefix contains a configured stop token, the sampler sets the next draft confidences to zero. This discourages allocating useful verification work to a request that is about to finish. The request/output lifecycle still enforces generation limits and cleanup, as described in chapter 2. Source: stop-confidence handling.

A schema alone cannot describe B's next legal tokens. The grammar matcher also needs B's accepted prefix. After an opening brace, a token may be legal that would be illegal after a completed object.

Moving legality to the device

Grammar matching runs on the CPU, while logits and sampling run on the accelerator. Failure belongs to a defined boundary

An unexpected matcher rejection or runtime exception marks B's structured-output status as failed. The sampler catches it at the request boundary because raising through the shared CP sampling path could affect every request and stall collectives. The pending compiler queue has a cancellation gap in this frozen engine. abort_request aborts scheduler requests and multimodal work, but does not remove the builder's pending entries. Prompts A and B can share an engine only after its workers agree on devices, communication groups, model state, and memory capacity. At the other end, their results can outlive a generation step while device operations and communication buffers remain active. Startup and shutdown are therefore part of the same dependency problem: a resource must exist before its users begin, and those users must finish before it disappears.

This chapter follows that dependency order. The frozen release has NVIDIA GPU and Ascend NPU adapters. Their common interfaces allow much of the worker path to remain shared, while device initialization, collective backends, memory registration, and graph behavior retain platform-specific conditions. Platform interface and adapters

Visibility comes before runtime initialization

A process-local device index has meaning only relative to its visible-device list. If a library initializes an accelerator runtime first, changing that list later may arrive too late. DeepInfer's package initializer consequently avoids importing PyTorch or initializing devices. It selects an extension-library directory using lightweight signals, enables the NVML-based CUDA availability check, and resolves PLATFORM lazily. The NVIDIA fallback used for extension-directory selection is a packaging choice; it does not provide a CPU inference backend. Package initialization, lazy platform

The example constructor makes the order explicit: configure environment and device visibility, then import PyTorch and LLM, then construct the engine. On Ascend it sets ASCEND_RT_VISIBLE_DEVICES alongside CUDA_VISIBLE_DEVICES. Its comments explain why importing PyTorch or starting a profiler earlier can initialize the runtime before this setup. Example launch boundary, construction order

A design consequence is to fix resource-identity configuration before the first subsystem can cache that identity. Lazy imports enforce that boundary only if callers respect it. They cannot undo an already initialized runtime.

An adapter carries operational differences

The GPU adapter selects CUDA kernels and NCCL collectives; the NPU adapter selects Ascend kernels and HCCL. Both expose host-memory registration through pin_host_memory and unpin_host_memory. Workers can ask for the operation without embedding the backend's registration API in every buffer owner. GPU operations, NPU selection

The NPU initializer checks that the two visible-device lists agree, applies runtime settings, and imports transfer_to_npu, which maps CUDA-style calls onto NPU operations. It also pins TileLang's default target to Ascend unless the caller already set one. This compatibility layer explains why shared code can contain torch.cuda names on an NPU host. Those names alone do not establish which accelerator executed a path. NPU initialization

Compatibility remains conditional. Missing ACL host-registration symbols fail initialization. A later registration failure warns that transfers will use pageable memory; the adapter first binds a device context because ACL's context is thread-local. Worker kernel setup rejects the NPU batch-invariance option in this version, while enabling deterministic kernel settings for NPU execution. Support for an adapter therefore does not imply every optimization has identical availability or guarantees. ACL resolution, kernel conditions

The engine starts non-driver context-parallel workers as spawned daemon processes and constructs the driver worker in its own process. A worker selects its local device, configures kernel libraries, binds CPU resources, sets its seed, and initializes communication. Non-driver workers enter a command loop; the driver broadcasts method names and arguments, then invokes the same method locally. Worker creation, device setup, command dispatch, driver dispatch

Control and device communication have separate groups. The initial distributed group uses Gloo. The parallel-state layer creates accelerator groups with the selected NCCL or HCCL backend and CPU groups with Gloo. A nontrivial context-parallel group also creates a shared-memory message queue for object commands. Distributed initialization, parallel groups

Captured execution needs stable storage

A graph records an execution pattern for replay. A graph bucket is a recorded input shape; the runtime selects the smallest recorded shape large enough for the current work. Reusing it requires buffers and supported shapes to remain available. DeepInfer prepares full-size input and output storage, creates smaller views, warms each selected batch size, and captures sizes in reverse order. Captures share a graph memory pool. Shutdown follows the remaining dependencies

Normal offline generation drains any in-flight overlapped result after unfinished requests reach zero, then clones outputs into caller-owned objects. Closing the engine is a separate operation. Its close path shuts down a lazily created structured-output builder, stops workers, stops multimodal preprocessing, and finally marks itself closed. This code does not establish transactional cleanup after every partial-construction or stop failure, and close itself does not invoke the generation drain loop. Generation drain, engine close

Worker shutdown has a stricter internal order. Workers meet at a barrier, explicitly destroy user buffers, and meet again. Decisions to carry into another system

Start with the smallest useful owner for a piece of state. A request owns its identity and history; a step describes one selection of work; a retained in-flight object keeps borrows alive until the consumer is done. These boundaries make it possible to add batching without letting a batch silently become the owner of every request it contains.

Treat overlap as a change to the state machine. It introduces a period in which scheduling information is tentative and a device result is still authoritative. A synchronous implementation may be entirely adequate when CPU overhead is small relative to device work, or when simplicity matters more than throughput. The timing lab in chapter 5 exposes those conditions without claiming a measured speedup.

Keep identity separate from placement. A logical expert remains the same model component when its physical copies move. A sequence remains the same request when its blocks change or its work is postponed. That separation is useful in storage systems, job schedulers and distributed execution engines as well as inference.

Finally, state the boundary of your evidence as carefully as the boundary of your module. A reader can inspect the pinned source for a fact, operate a toy model to build intuition, and run a hardware experiment to measure an outcome. Each has a different job. For A and B, the engineering task is to make their progress observable without losing the history, ownership and sampling rules that give their output meaning.

Terms used in the source

Glossary

Prefill
Process the prompt to build model state and obtain the next-token distribution.
Decode
Extend an existing sequence, normally one target step at a time. Speculation can verify several proposed tokens.
KV cache
Stored attention keys and values, or the model-specific compressed state used in their place.
DP
Data parallelism: attention replicas handle different requests.
CP
Context parallelism: ranks cooperate on portions of a sequence’s context.
EP
Expert parallelism: expert weights and routed work are distributed across ranks.
EPLB
Expert-parallel load balancing: choose physical expert replicas and their placement from observed load.
ZOS
Zero-overhead scheduling: the project’s name for overlapping CPU scheduling with device execution. It is not a promise of zero elapsed overhead.
MTP / NextN
Multiple-token prediction and the source naming for drafting future tokens. DSpark is the release’s feature name; DFlash appears in implementation identifiers.
SWA
Sliding-window attention: attend to a bounded recent context.
YOCO
The model’s split between cache-producing and cache-consuming layers. Use the frozen source’s implementation constraints.
Rank
A numbered participant in a distributed process group.
Logit
An unnormalized score for a candidate token, before conversion to a sampling probability.
Golden
A stored or supplied expected result used by a test. Its workload and platform are part of the comparison.
