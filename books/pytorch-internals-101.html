PyTorch is a tape recorder
around a math library.

That one sentence is the whole machine — and this book proves it in about fifteen minutes. A library of number blocks (tensors), a router that runs each operation on whatever hardware you have (the dispatcher), and a recorder that writes down every operation so it can replay them backwards to compute gradients (the tape). Three ideas; everything else is scale and conveniences. If you have solid CS fundamentals and no ML background, you are exactly the intended reader.

01 / THE MACHINE

Three Layers, One Machine

PyTorch is a tape recorder wrapped around a math library: a thin Python skin, a routing table, and kernels that own the bytes.

Strip the branding and import torch gives you three layers. The Python API is a thin skin — torch.Tensor, a + b, torch.nn — that mostly parses arguments and hands them down. The dispatcher is a routing table, one per operator: it inspects the tensors in each call and picks an implementation. The kernels are compiled functions that loop over raw memory to do the actual arithmetic — one set per device, because CPU, CUDA GPUs, and Apple's MPS each want different code.

The layering earns its keep twice. One op name runs anywhere: the same a + b reaches a laptop CPU or a data-center GPU unchanged, because routing is decided per call, by the tensors themselves. And autograd — the derivative machinery training feeds on — plugs in between API and kernel as a wrapper: when a tensor is recording gradients, an extra layer takes notes, then calls the real kernel. Execution stays eager throughout: each op runs the moment its line is reached, like any other scripting-language call.

The rest of this run walks the stack once: what a tensor is (02), one op's trip through the router (03), the tape autograd writes on the way (04), and the four-line loop that trains everything (05).

Takeaway: thin Python skin, one routing table, kernels that own the bytes.

02 / TENSORS

A Tensor Is Metadata Over Raw Memory

One flat block of bytes plus a reading order — shape, dtype, strides, offset — and nothing else.

Every tensor is a pointer to a Storage — one flat, untyped block of memory — plus four pieces of metadata: shape (size of each axis), dtype (bytes per element and how to interpret them), a stride per axis (elements to jump along it), and a storage offset (where the view starts). No per-element headers, no lookups — an element's location is pure arithmetic:

element_offset = storage_offset + Σ index[i] · stride[i]

Take a 3×4 float32 tensor, built row-major so memory holds 0, 1, 2, …, 11 in order:

>>> a = torch.arange(12, dtype=torch.float32).reshape(3, 4)
>>> a.stride(), a.storage_offset()
# → ((4, 1), 0)

Strides (4, 1): down a row skips 4 elements, right a column skips 1. So a[1, 2] lands at 1·4 + 2·1 — element 6, byte 24. Every kernel from section 01 finds its bytes with this exact formula. Poke the pairing yourself:

Transposes are where the design shows off. .t() moves zero bytes: it swaps the stride tuple to (1, 4) and keeps the same data_ptr, so the same twelve floats are read column-first. Slicing works the same knob — the second column a[:, 1] is a view at storage_offset 1 with stride (4,), still jumping row to row. Views share storage, so writing through one writes the base tensor.

Reshaping follows the same economy. .view() re-tags the storage with new strides and never copies — legal only when the current layout can express the new shape. .reshape() returns a view when possible and silently copies when not. What decides is contiguity: strides matching plain row-major order, last axis fastest. .t() and column slices break it; .contiguous() repairs it by copying.

Byte budgets are then head arithmetic: bytes = numel × element_size. float32 is 4 bytes, so a million floats is 4 MB; a 7-billion-parameter model in bf16 (2 bytes) weighs 14 GB — which is why dtype is a deployment decision, not a formality.

Takeaway: tensor = storage + shape + strides + offset; transposes are metadata edits.

03 / ONE OP

What a + b Actually Does

Five hops from Python to silicon — and only one of them decides anything.

a + b calls Tensor.__add__, which lands in an auto-generated C++ binding: parse the arguments, release the GIL, call the operator. Every operator — add, matmul, relu — is declared once in ATen, PyTorch's operator library, by a schema fixing its name and signature. The whole of a + b is:

aten::add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor

Below the schema sits the dispatcher: per operator, a table of function pointers indexed by dispatch key — a vtable per operator, not per class. Each tensor argument contributes its key set (a backend key from its device, plus functionality keys like Autograd); the sets union, and the highest-priority key picks the row. Autograd keys outrank backend keys, so if either input records gradients, that row runs first: it writes an AddBackward0 node on the tape (section 04), then redispatches with Autograd excluded, and the same lookup lands on the real kernel. Autograd never reimplements math — it takes notes, then calls the kernel that does. The table itself is a registration grid, one cell per (operator, dispatch key); an exact cell beats a catch-all, and a catch-all beats a column-wide fallback.

Which backend row runs is the tensors' own business: each carries its device in its metadata, and its storage lives in that device's memory. There is no global "current device" flag for ops. Mixing devices in one call errors, and .to('cuda') is an explicit copy. Ride along:

Takeaway: every op is a table lookup; which row runs is the tensors' choice.

04 / THE TAPE

The Tape, End to End

The forward pass takes notes; backward() replays them in reverse — one sweep, every gradient.

Training adjusts a model's parameters to push a loss — a scalar scoring how wrong the model is — downward, and the correct nudge for each parameter is the derivative of the loss with respect to it. A model has millions of parameters, and reverse-mode autodiff produces all of those derivatives in a single backward sweep: while ops run, record each one's local derivative; afterward, apply the chain rule in reverse — multiply along edges, sum where paths merge.

Recording switches on per tensor. Give one requires_grad=True and every op touching it writes a node — the grad_fn — holding that op's backward formula plus links to the nodes that produced its inputs. Chained together, the nodes are the tape. It records the ops that actually executed — the taken branch of an if, the real loop count — and it is rebuilt from scratch every iteration: what you run is what you differentiate.

>>> x = torch.tensor(2.0, requires_grad=True)   # recording leaf
>>> y = 3*x**2 + 2*x
>>> y
# → tensor(16., grad_fn=<AddBackward0>)
>>> y.backward(); x.grad
# → tensor(14.)

The whole mechanism is that expression with named intermediates t = x², a = 3t, c = 2x:

y.backward() seeds y with 1.0 and the engine walks root to leaves, each node multiplying its local derivative into whatever arrives. x sits at a fork — reached through x² and through 2x — so its contributions, 3·4 = 12 and 1·2 = 2, sum: x.grad = 14 = dy/dx = 6x + 2. Nobody coded that formula anywhere; it composes itself out of local facts. Step it by hand:

Two consequences of the leaf's AccumulateGrad node. It does x.grad += incoming, never assignment — so nothing clears .grad on its own, which is why optimizer.zero_grad() exists, and why accumulating gradients across micro-batches (backward per micro-batch, one update) is free. Only leaves get a .grad at all — intermediates like t stay None unless you ask with t.retain_grad(). And the tape has two off switches: torch.no_grad() runs ops without recording; x.detach() returns the same storage severed from the graph — the value without the history.

Takeaway: forward writes the tape; backward replays it — multiplying along edges, summing at forks, += into leaves.

05 / THE LOOP

Four Lines Train Everything

The whole training regime is one loop: zero, forward, backward, nudge.

Everything above assembles into four lines. A model is an nn.Module — a tree of submodules holding the parameter tensors as recording leaves; calling model(xb) runs ordinary Python that issues ops. An optimizer is an update rule aimed at those parameters.

for xb, yb in loader:
    optimizer.zero_grad()            # clear last step's .grad (set to None)
    loss = loss_fn(model(xb), yb)    # forward: ops run eagerly, tape written
    loss.backward()                  # engine: root→leaves, .grad += on leaves
    optimizer.step()                 # read .grad, nudge parameters in place

Read it as forget, predict-and-record, critique, correct. Zeroing exists because of section 04's +=. The forward pass computes the loss and writes the tape. Backward fills .grad on every parameter. Step reads those gradients and updates the parameter tensors in place. SGD, Adam, AdamW differ only in the arithmetic of that last line.

A GPU changes none of the lines. Move model and data with .to('cuda') and the same ops dispatch to wider kernels over faster memory. Two things are mechanically different. Launches are async: each op is queued on a per-device stream and executes in order — an unawaited promise — so your Python races ahead, and you actually wait only at .item(), .cpu(), or a print, all of which force a sync. And every launch costs CPU time, so on small models launch overhead dominates and the GPU loses to the CPU. torch.compile is the escape hatch: trace the Python once, emit fused kernels, and both overheads shrink.

Takeaway: training is a loop — zero, forward, backward, nudge; GPUs make it wide and async, not different.
