01 · From LM to reasoning

From language model to reasoning model.

A reasoning model is not a different architecture. It is the same transformer, trained and used differently, so that it works through problems step by step before committing to an answer.

The previous article built a GPT-style language model end to end: tokenization, causal self-attention, pretraining on next-token prediction, and instruction fine-tuning. That model is a strong pattern matcher — it predicts plausible continuations. What it does not do reliably is reasoning: multi-step problems where the answer must be derived, not recalled.

Four ideas close the gap, and each is a section of this article:

Evaluation

You cannot improve what you cannot measure, so we first build a verifier that grades free-form math answers automatically.

Inference-time scaling

Without any training, we can sample smarter: temperature, top-p, and majority voting over multiple attempts.

RL with verifiable rewards (RLVR)

The verifier doubles as a reward signal. GRPO uses it to push the model toward answers that verify — no human preference labels, no separate reward model.

Distillation

A strong teacher writes out reasoning traces; a small student learns to imitate them with plain supervised learning — no RL at all.

One discipline, three kinds of blocks

Everything below follows observable behavior → the math → executable code. Implementation excerpts come from examples/reasoning/, output blocks are recorded runs of those programs, and the optional real-model commands in §11 target the pinned upstream repository.

02 · The laboratory

Our laboratory: a 106,624-parameter stand-in.

The book this article is based on uses a pretrained Qwen3-0.6B model and the MATH-500 benchmark — about 1.2 GB of downloads and hours of compute. We scale the task down instead of faking the results.

Model2-layer, 4-head decoder-only transformer (tiny_lm.py, 106,624 parameters) — the same architecture family as Article 1's GPT, fixed 24-token vocabulary
Taskone-digit addition: Compute 3+4. → \boxed{7}; train pool (80) and eval pool (20) disjoint by construction
Starting pointbrief instruction tuning (100 steps, prompt-masked cross-entropy) → 85% greedy accuracy on the train pool, still making interesting mistakes
Why this is a fair stand-in

Addition has the two properties the real pipeline relies on: answers are exactly and cheaply verifiable, and a partially trained model produces a mix of correct and incorrect attempts — which is precisely what GRPO's group-relative signal needs. Where the toy behaves differently from a real model (and it does, twice), we say so and show the numbers anyway.

03 · Measure first

A math verifier: extract, normalize, verify, grade.

Ask a model Compute 1/2 + 1/6 and it might answer \boxed{\dfrac{2}{3}}, \boxed{2/3}, 0.667, or bury the answer in three paragraphs. Grading that at scale needs a deterministic pipeline, not vibes.

Original diagram. The same four steps grade a benchmark (evaluation) and score training rollouts (RLVR rewards, section 6).

Extraction: find the final answer

We ask the model (via the prompt template) to put its final result in \boxed{...}. Extraction takes the last \boxed in the response and matches braces with a depth counter, so nested content like \boxed{\frac{1}{2}} survives. If there is no boxed answer, we optionally fall back to the last number in the text:

examples/reasoning/verifier.py
def extract_boxed(text: str) -> str | None:
    start = text.rfind("\\boxed")
    if start == -1:
        return None
    i = start + len("\\boxed")
    while i < len(text) and text[i].isspace():
        i += 1
    if i >= len(text) or text[i] != "{":
        return None
    i += 1
    depth, content_start = 1, i
    while i < len(text) and depth > 0:
        if text[i] == "{": depth += 1
        elif text[i] == "}": depth -= 1
        i += 1
    if depth != 0:
        return None
    return text[content_start : i - 1]

Normalization: one canonical form

The same value appears as \dfrac{14}{3}, 14/3, $14/3$, or (14)/(3). A normalization pass rewrites the common surface variations — LaTeX fractions and roots, ^ → **, Unicode superscripts (2² → 2**2), thousand separators (1,000 → 1000), degree marks, \text{...} wrappers, multiple-choice labels (c. 3 → 3):

examples/reasoning/verifier.py · abridged
def normalize_answer(text):
    out = RE_SPECIAL.sub("", text).strip()  # drop <|assistant|>-style tokens
    # Leading multiple-choice label: "c. 3" -> "3"
    # Degree markers: 30° / 30^{\circ} -> 30
    # Unwrap \text{...}; strip \( \) \[ \] and \left \right
    out = out.replace("\\dfrac", "\\frac").replace("\\tfrac", "\\frac")
    # Unicode superscripts: x² -> x**2
    out = re.sub(r"\\sqrt\s*\{([^{}]*)\}", r"sqrt(\1)", out)
    out = re.sub(r"\\frac\s*\{([^{}]+)\}\s*\{([^{}]+)\}", r"(\1)/(\2)", out)
    out = out.replace("^", "**")            # 2^3 -> 2**3
    out = re.sub(r"(?<=\d)\s+(\d+/\d+)", r"+\1", out)  # "2 1/2" -> "2+1/2"
    out = out.replace("{", "").replace("}", "")
    out = re.sub(r"(?<=\d),(?=\d\d\d(\D|$))", "", out)  # 1,000 -> 1000
    return out.strip().lower()

Verification: symbolic, not string, equality

String comparison fails on 1/2 vs 0.5. So after a fast string-equality short-circuit, both sides are parsed into SymPy expressions and compared symbolically — the difference simplifies to zero exactly when the answers are mathematically equal. Three guards matter because model output is arbitrary text: inputs longer than 2,000 characters are rejected; since SymPy's parser uses eval() internally, nothing reaches it unless it passes a strict allowlist (numbers, + - * / **, parentheses, and sqrt(...); every other identifier, attribute, or string is refused); and numeric literals and parenthesis depth are bounded, so short but explosive inputs like 9**999999999 are rejected fast instead of hanging the evaluation:

examples/reasoning/verifier.py
def answers_equal(a, b):
    if a == b: return True
    ea, eb = _parse_expr(a), _parse_expr(b)  # allowlist-checked, or None
    if ea is not None and eb is not None:
        return simplify(ea - eb) == 0
    return False

Unparseable or non-allowlisted garbage (models sometimes emit it) parses to None and simply fails the check — it can never execute as code.

Why the verifier matters beyond evaluation

It is deterministic and reproducible — the same answer always gets the same grade, with none of the noise of human preference labels or a learned reward model. In section 6 it becomes the reward function for reinforcement learning. Everything that can go wrong with rewards (section 8) starts here, in what the verifier can and cannot see.

04 · Inference-time scaling

Better answers without training.

Before touching the weights, there is a cheaper lever: spend more compute at generation time. Three knobs, all implemented in examples/reasoning/generation.py and exercised by demo_inference_scaling.py.

Temperature: reshaping the next-token distribution

The model ends every forward pass with a logit vector over the vocabulary; softmax turns it into a probability distribution. Dividing the logits by a temperature T first sharpens (T < 1) or flattens (T > 1) that distribution:

examples/reasoning/generation.py
def scale_logits_by_temperature(logits, temperature):
    if temperature <= 0:
        raise ValueError("Temperature must be positive")
    return logits / temperature

Measured on our toy model (next token after Compute 3+4., top-5 candidates):

Recorded output · demo_inference_scaling.py
  T=0.5: '\boxed{': 1.000, '1': 0.000, '0': 0.000, '}': 0.000, '2': 0.000
  T=1.0: '\boxed{': 0.998, '1': 0.000, '0': 0.000, '}': 0.000, '2': 0.000
  T=2.0: '\boxed{': 0.825, '1': 0.018, '0': 0.017, '}': 0.011, '2': 0.010

The trained model is already confident, so low temperature changes little; T = 2 visibly spreads probability mass to alternatives. Temperature does not change the ranking — it changes how often sampling explores below the top choice.

Top-p (nucleus) sampling: truncating the tail

Sampling from the full distribution occasionally picks an absurd low-probability token. Top-p keeps only the smallest set of tokens whose cumulative probability reaches p, then renormalizes:

examples/reasoning/generation.py · abridged
sorted_p, idx = torch.sort(probas, dim=-1, descending=True)
prefix = torch.cumsum(sorted_p, dim=-1) - sorted_p
keep = prefix < top_p
keep[..., 0] = True            # always keep the single best token
# zero out the rest, scatter back, renormalize to sum 1
Recorded output · demo_inference_scaling.py
  top_p=1.0: kept ['0.50', '0.25', '0.15', '0.06', '0.04']
  top_p=0.9: kept ['0.56', '0.28', '0.17']          (renormalized)
  top_p=0.6: kept ['0.67', '0.33']                  (renormalized)
  top_p=0.4: kept ['1.00']                          (renormalized)

Note the boundary rule: the token that crosses the threshold is kept (the cumulative mass before a token must be below p), and the top token is always kept. These two details are where off-by-one implementations diverge; the test suite pins both.

Self-consistency: vote over sampled attempts

Sample k completions at moderate temperature, extract the final answer from each with the verifier's extractor, and return the majority:

Recorded output · demo_inference_scaling.py
  problem: Compute 2+9.  (correct answer: 11)
  sampled final answers: ['10', '13', '14', '10', '15', '10', '10', '10']
  vote counts: {'10': 5, '13': 1, '14': 1, '15': 1} -> winner '10' (tied=False)

  over 10 problems: greedy 10/10 | majority vote 5/10 (8 samples, T=1.0)
An honest negative result

On this toy task, voting loses to greedy decoding: the model's errors are systematic (it is biased toward certain wrong digits), so the majority confidently amplifies a wrong mode. Self-consistency pays off when sampled reasoning paths are diverse but converge on the correct answer — that is the regime the book demonstrates on the real 0.6B model (ch. 4), where chain-of-thought makes mistakes decorrelate. Our toy answers are bare digits with no reasoning path to diversify, so the mechanism is real but the benefit is absent. We report it as measured.

The same section of the book also covers self-refinement — scoring a draft response (with rule-based scores or the model's own log-probabilities as a confidence measure) and feeding the critique back for another pass. We leave it at this pointer; the GRPO machinery below reuses the same log-prob scoring in a different role.

05 · From RLHF to RLVR

Rewards you can verify, not preferences you must model.

To go beyond inference-time tricks we need a training signal for "good reasoning".

The 2022 InstructGPT recipe, RLHF, gets it from humans: annotators rank candidate responses, a separate reward model is trained on those rankings, and the LLM is then optimized against the reward model's scores. That works, but it means training and maintaining a second model roughly the size of the first, and the signal inherits the noise and inconsistency of human judgment.

Reasoning tasks admit something cleaner. For math (and for code that must compile), correctness is verifiable: the verifier of section 3 grades a response deterministically, 1 for correct and 0 otherwise. Reinforcement learning with verifiable rewards (RLVR) replaces the entire reward-model stage with that check — no human preference labels are needed, though the problems and their ground-truth answers are still given. The recipe became prominent with DeepSeek-R1 (2025): its R1-Zero variant showed that pure RL with verifiable rewards can grow reasoning behavior from a base model, and the full R1 pipeline combined a small cold-start SFT stage with RL.

Our reward is section 3's pipeline, with one strictness knob: a response without a \boxed{} answer scores 0 — no fallback — so the reward pressures the model to produce a parseable final answer:

examples/reasoning/rewards.py
def reward_correctness(response_text, ground_truth) -> float:
    extracted = extract_answer(response_text, require_boxed=True)
    if not extracted:
        return 0.0
    return float(grade_answer(extracted, ground_truth))

RLVR decides what signal we learn from. The remaining question is how to turn a binary grade into weight updates. That is GRPO.

06 · GRPO from scratch

The group is the baseline.

Group Relative Policy Optimization (GRPO, from the DeepSeekMath paper) is the policy-gradient algorithm used to train DeepSeek-R1 — and our toy model. Its selling point over PPO is that it needs no value model: instead of learning a separate network that estimates how good a response is expected to be, GRPO samples a group of responses to the same prompt and uses the group itself as the baseline.

Original diagram. One GRPO update, five stages; the dashed path is the gradient update feeding the next iteration.

Stage 1–2: rollouts and rewards

For one prompt, we snapshot the current policy (the old policy — frozen, gradients off) and sample a group of completions with temperature and top-p, under torch.no_grad(). Each completion is graded by the verifier:

examples/reasoning/grpo.py · abridged
old_model = copy.deepcopy(model)
for p in old_model.parameters():
    p.requires_grad = False

group = sample_group(old_model, tokenizer, example,
                     num_rollouts=8, max_new_tokens=8,
                     temperature=1.0, top_p=0.95, seed=seed)
# rewards like [1, 1, 0, 1, 0, 0, 1, 0]

Stage 3: group-relative advantages

Rewards are absolute; the learning signal is relative. The advantage standardizes each reward within the group:

Aᵢ = (rᵢ − μᵣ) / (σᵣ + ε)A rollout above the group mean gets a positive push; below it, a negative one. ε = 1e-4 is numerical stability.
examples/reasoning/grpo.py
def compute_advantages(rewards):
    r = torch.tensor(rewards, dtype=torch.float32)
    return (r - r.mean()) / (r.std() + 1e-4)
The worked example from the book (ch. 6): rewards [1, 1, 0, 0] become advantages [+0.866, +0.866, −0.866, −0.866]. Correct rollouts get pushed up, incorrect ones down, by exactly the same amount.
  • Centered by construction — the advantages of a group always average to ≈ 0; the group is its own baseline.
  • Degenerate groups carry no signal — if all rollouts earn the same reward (all right or all wrong), every advantage is 0 and there is nothing to learn from that prompt.

Stage 4: sequence log-probabilities

To increase the probability of good rollouts we need to differentiate through "how probable was this response". The sequence log-prob sums the log-probs of the answer tokens — and only the answer tokens. This is Article 1's shifted-target construction with a mask: position t of the logits predicts token t + 1, so the first position that predicts an answer token is prompt_len − 1:

examples/reasoning/grpo.py · abridged
def sequence_logprob(model, token_ids, prompt_len):
    ids = torch.tensor([token_ids])              # (1, seq_len)
    logits = model(ids)[0].float()               # (seq_len, vocab)
    logprobs = torch.log_softmax(logits, dim=-1)
    targets = ids[0, 1:]                         # shifted by one
    selected = logprobs[:-1].gather(1, targets.unsqueeze(-1)).squeeze(-1)
    return selected[prompt_len - 1:].sum()       # answer positions only

The same forward pass is run three ways: under the old policy (detached — it is a constant reference), under a frozen reference model when KL is used (also detached), and under the current trainable policy — the only one that carries gradients.

Stage 5: the policy-gradient loss, and the detach that matters

The chapter-6 form of the loss weights each rollout's log-prob by its advantage and averages over the group, with a sign flip (optimizers minimize; we want to maximize advantage-weighted probability):

LPG = − (1/N) Σᵢ Aᵢ · log pθ(y⁽ⁱ⁾ | x)The inner log pθ is the sequence log-prob of rollout i under the current policy; Aᵢ is its detached group-relative advantage.
examples/reasoning/grpo.py
adv = advantages.detach()      # fixed learning signal — see below
pg_loss = -(adv * new_logps).mean()
The .detach() is the whole point

The advantages are constants for this update: they were computed from rewards, which come from a non-differentiable verifier. Without .detach(), autograd would try to flow gradient through the advantage computation into however it was produced. With it, gradient flows only through new_logps — the current policy's log-probability of each token it generated. The same discipline applies to the old-policy and reference log-probs below. The test suite verifies that a backward pass reaches the policy's parameters and that the advantage tensor carries no graph.

One subtlety you will notice in any training log: the logged loss right after the old-policy snapshot is ≈ 0. The advantages average to zero, and (as we will see next) the policy ratio starts at exactly 1 — so the scalar loss is uninformative by construction. The informative metrics are reward_avg, advantage statistics, entropy, and response length. The book's training runs make the same point: GRPO's loss is a sanity check, not a progress meter.

Does it learn? Measured on the toy task

demo_grpo.py runs 300 GRPO updates (8 rollouts per prompt, 24-prompt train subset, temperature 1.0, top-p 0.95) and measures sampled accuracy — the model's own rollouts graded by the verifier — before and after:

Sampled accuracy on the trained problems climbs from 53% to 93% in twelve seconds of CPU time — the verifiable reward doing its job. The log also shows the mechanics live: entropy declines as the model grows confident, and steps with reward_avg 0.000 or 1.000 have adv_std=0 (degenerate groups, no signal). And the held-out column is the honest caveat: this toy model memorizes rather than generalizes, so unseen problems stay at 0%. Real RLVR results carry the same warning — reward on training prompts is not reasoning ability on unseen ones.

07 · Keeping GRPO stable

Ratios, clipping, and the KL term.

Chapter 6's loss lets the policy move arbitrarily far in one update. Over a long run that invites a familiar failure: a few aggressive steps shift token probabilities too much, rewards crash, and the run never recovers. Chapter 7 adds three stabilizers, all present in examples/reasoning/grpo.py.

The policy ratio and clipping

Because rollouts were generated by the old policy (the snapshot), we can ask how far the current policy has drifted since. Per rollout:

ρᵢ = exp( log pnew(y⁽ⁱ⁾) − log pold(y⁽ⁱ⁾) )A ratio of 1 means "unchanged since the snapshot".

Instead of weighting log-probs directly, the clipped objective scales the advantage by the ratio and takes the pessimistic (minimum) of the unclipped and clipped forms:

Lclip = − meanᵢ [ min( ρᵢ·Aᵢ, clip(ρᵢ, 1−ε, 1+ε)·Aᵢ ) ]
examples/reasoning/grpo.py
ratio = torch.exp(new_logps - old_logps)          # old_logps detached
clipped = torch.clamp(ratio, 1.0 - clip_eps, 1.0 + clip_eps)
obj = torch.minimum(ratio * adv, clipped * adv)
pg_loss = -obj.mean()
The pessimistic minimum in both advantage regimes (drawn with ε = 0.2 for readability). Good rollouts (A > 0) stop being rewarded for pushing ρ further up; bad rollouts (A < 0) stop being penalized for pushing ρ further down. DeepSeek-R1 used a very weak ε = 10 (almost no clipping); PPO-style RLHF typically uses ε ≈ 0.1–0.2.

Right after the snapshot, ρ = 1 exactly and the loss is −mean(A) ≈ 0 — which is why the logged loss in section 6 sits at zero even while the model improves. The ratio only becomes meaningful when rollouts are reused for several inner update epochs, or when monitoring drift over a run.

The KL term, and an honest caveat about what it estimates

The original GRPO formulation adds a penalty that keeps the policy near a frozen reference model (the initial model; DeepSeek-R1 refreshed it only every 400 steps):

L = Lclip + β · meanᵢ [ log pnew(y⁽ⁱ⁾) − log pref(y⁽ⁱ⁾) ]β ≈ 0.001–0.05 in practice; the bracketed term is a signed surrogate, see below.
examples/reasoning/grpo.py
ref = torch.stack(ref_logps).detach()      # frozen reference policy
kl_loss = kl_coeff * kl_surrogate(new_logps, ref)   # signed, off-policy
loss = pg_loss + kl_loss
This is a signed, off-policy surrogate — not an exact KL divergence

The rollouts were sampled from the old policy, not the current one, so mean(new − ref) over these samples is a convenient estimate of drift — direction matters, and new − ref (penalizing drift from the reference) is not interchangeable with old − new. The value is signed: it can be negative, so it cannot be read as a non-negative KL magnitude. The book's own KL run is the cautionary tale: accuracy rose from ~15% to ~40%, then rewards and accuracy collapsed to zero with the model emitting gibberish. Many recent math-reasoning recipes (DAPO, Dr. GRPO, DeepSeek-V3.2) simply drop the KL term; our implementation follows the book in keeping it optional (kl_coeff=0.0 by default), exposes it as kl_surrogate(), and pins its signed semantics in a test.

Metrics that actually tell you something

Since the scalar loss is ≈ 0 by construction, the diagnostics that matter, all logged by train_grpo:

Zero-advantage skips

Groups whose rewards are all equal produce zero gradient — so we can skip the update entirely (skip_zero_advantage=True, the DAPO "filter zero-gradient prompts" trick). A test pins the semantics precisely: an untrained model, which cannot produce a single correct answer, yields all-zero rewards, every step is skipped, and its weights are bit-identical afterwards. The same test guards against a subtle bug class — "skipping" a step while still mutating the model.

08 · When rewards lie

Reward hacking: the model optimizes the specification, not your intent.

A verifier only sees what it checks. Anything the reward pays for, the model will eventually produce — including cheap ways to look right.

The book demonstrates this with a format reward: paying a bonus for emitting <think>...</think> tags regardless of correctness. In that run, the format-reward share climbs while evaluation accuracy collapses — the model learns to look thoughtful instead of being right.

Our toy reproduces the incentive gap directly. We train the model to answer with <think> traces, then sample 160 responses on held-out problems (where it is often wrong but always well-formatted) and score them two ways (demo_grpo.py, part 2):

Recorded output · demo_grpo.py, part 2
  160 sampled responses, 154 incorrect; of the incorrect
  ones, 154 still carried a valid <think> format.
  mean reward if format pays unconditionally: 1.038
  mean reward if format requires correctness: 0.075
  gap = 0.963 of free reward for wrong-but-formatted answers
Measured on the toy task. Under an unconditional format reward, 96% of responses are wrong yet the mean reward is 1.038 out of a nominal 2.0 — the gradient cannot tell "looks right" from "is right". Conditioning the bonus on correctness collapses the gap.

The standard mitigations, both in the book and in rewards.py: shrink the auxiliary weight (1.0 → 0.1), or make the bonus conditional on the correctness reward firing. The deeper lesson generalizes: a reward is a specification, and the model optimizes the specification — not your intent.

09 · Evaluation leakage

Train and test must never meet.

RLVR makes one data mistake catastrophic: if evaluation problems (or near-duplicates) sit in the training pool, reward climbs and the benchmark number means nothing.

The book is explicit about the separation — GRPO trains on 12,000 MATH training problems that exclude every MATH-500 evaluation problem (the exclusion is a published, inspectable dataset diff).

We hold the toy to the same rule: data.py draws the 20-problem evaluation pool once, with a fixed seed, and train_baseline / train_grpo never see it. That is why the held-out numbers in this article (0.00 before and after GRPO for the memorizing toy model; 0.35 for the distilled student) are worth reporting at all — and it is why section 6 reports both train-pool and held-out accuracy rather than letting the flattering number stand alone.

10 · Distillation

Reasoning without reinforcement learning.

RLVR is powerful but expensive: every update needs a group of fresh rollouts. There is a cheaper route that skips RL entirely.

Hard distillation: let a strong teacher generate reasoning traces, keep the ones that verify, and fine-tune a small student on them with ordinary supervised cross-entropy. (Its sibling, soft distillation, trains the student to match the teacher's full next-token distribution; it carries more information but needs the teacher's logits, a shared tokenizer, and much more storage. The DeepSeek-R1 distilled variants use the hard form — which, notably, is just SFT on synthetic data.)

Original diagram. Hard distillation: no rollouts, no rewards, no RL — but the same answer-only masking as instruction tuning, so the student learns to respond, not to echo prompts.

The one detail that makes it work is the loss mask. Position t of the logits predicts token t + 1 (Article 1's shifted targets), and only positions that predict answer tokens — from prompt_len − 1 onward — contribute:

examples/reasoning/distill.py
def masked_answer_loss(model, token_ids, prompt_len):
    ids = torch.tensor([token_ids],
                       device=next(model.parameters()).device)
    logits = model(ids)[0]                 # (seq_len, vocab)
    answer_start = prompt_len - 1
    pred_logits = logits[answer_start:-1]  # positions predicting answer tokens
    targets = ids[0, answer_start + 1 :]
    return F.cross_entropy(pred_logits, targets)

demo_distill.py runs the whole story: a teacher (baseline accuracy 1.00 on the train pool) generates one trace per training problem, the verifier keeps only the correct ones (80/80 survive here), and a fresh student trains on the surviving traces for 40 epochs:

Recorded output · demo_distill.py

  example trace:
    prompt:     'Compute 0+0.'
    completion: '<think>0+0=0</think>\boxed{0}'

  student val loss after training:  0.3849

  student greedy accuracy on held-out eval:   0.35

The student absorbs both the answer format and the trace structure from teacher-written text alone. Its held-out accuracy (0.35) is a single seeded run, not a controlled comparison — we report it as an observation, not evidence of causation. Distillation and RLVR are complements in practice: distill to bootstrap reasoning format cheaply, then use RL to push past the teacher's ceiling on verifiable tasks.

11 · The real-model path and limitations

The same stages, at real scale.

The conceptual stages of this article map directly onto the book's full-size setup — verifier, rollout groups, clipped objective, distillation loop. The toy's tokenizer, reduced verifier subset, and hardware path do not; the real pipeline below replaces them.

    --steps 500 --max_new_tokens 1024                         # GRPO with clipping + KL

Known limitations of the toy laboratory, stated plainly:

  • The 24-token vocabulary and one-digit task make memorization dominant; the toy does not demonstrate generalization gains from RLVR, and self-consistency shows no benefit (section 4 explains why this is expected, not a bug in the method).
  • Our GRPO uses one prompt per step and a single inner epoch, so the policy ratio sits at 1.0 and clipping/KL effects are demonstrated by construction and unit tests rather than by long-run curves.
  • The verifier implements a reduced subset of the book's LaTeX normalization; exotic answer formats would need the full pipeline (reasoning_from_scratch/ch03.py).
