01 / Goodput, not throughput

两个延迟目标，被同一批 GPU 和同一种并行策略绑在一起

现有系统把 prefill 与 decoding 放在同一 GPU 上连续组批，能提高整体 token throughput，却在严格 SLO 下被迫二选一或超额配置。DistServe 的问题定义是：在每块 GPU 成本固定的前提下，最大化同时满足 TTFT、TPOT 与 attainment 目标的请求率。

论文 §1–2 · Figure 1 / 2per-GPU goodput = 满足双 SLO 的最大 request rate / 配置的 GPU 数
双 SLO

TTFT：从到达到首个 token 的 prefill 延迟。TPOT：首个 token 之后，平均每个输出 token 的 decoding 延迟。SLO attainment 是同时满足这两个要求的请求比例。

工程师视角 · 指标变换

tokens/s 只回答“机器做了多少工作”，goodput 回答“多少工作仍被用户视为合格”。提高 batch 可能提升前者，却让排队延迟突破后者；两者并不等价。

PREFILL / 一次性处理整个 prompt

计算密集，怕排队，也怕长任务阻塞

  • 输入 token 并行计算，长 prompt 往往使 GPU compute-bound。
  • 较小 batch 更合适；超过饱和阈值 Lm 后，多加请求只延长整批时间。
  • 低到达率或严格 TTFT 时，intra-op 降低执行时间更有价值。
DECODING / 每步只生成一个 token

显存带宽密集，需要大 batch 摊薄权重读取

  • 每步仍要读取模型权重和活跃请求的 KV cache。
  • 大 batch 提高利用率，但受显存容量与 TPOT 限制。
  • 严格 TPOT 用 intra-op 降延迟；超出后 inter-op 近线性扩容。
为什么现有替代方案不够

Orca／vLLM 的 colocated continuous batching 无法消除相位干扰；DeepSpeed-MII／SARATHI 的 chunked-prefill + piggyback 只是用 TTFT 换 TPOT，并增加 KV 重读；简单优先级或串行调度仍留下排队与 GPU 利用不足。

02 / High-level design

离线决定“怎么部署”，在线只保持简单、短路径的调度

DistServe 把复杂性前移到放置算法：用历史负载与模拟器搜索每个相位的 TP／PP 和实例数，再按网络约束落到物理集群。运行时由 centralized controller 做 FCFS 分发，prefill 留存 KV，decoding 按需拉取，双方按自己的节奏运行。

03 / Placement to request trace

先找到 goodput 最优放置，再让一个请求穿过它

点击步骤或用左右方向键。前四步发生在部署与周期性 replan，后三步发生在在线请求路径；不要把离线搜索成本误算进每一次请求的 TTFT。

Algorithm 1 / 2 · §4.3 / §5TP = intra-op / tensor parallelism；PP = inter-op / pipeline parallelism
01

把应用需求转成可搜索的输入

收集模型、GPU 显存与集群拓扑，以及目标流量 R、TTFT、TPOT、SLO attainment 和历史输入／输出长度。

发生什么

从历史 trace 拟合长度分布并重采样，用 Poisson 到达或相应历史模型构造模拟负载；不是试图准确预测下一秒，而是估计较长窗口的统计特征。

工程要点

SLO 不是附属标签，而是 goodput 的组成部分。没有 TTFT、TPOT 与 attainment 目标，就无法比较两个放置谁更好。

input = (G, N, M, C, W, R, TTFT_SLO, TPOT_SLO, attainment_goal)§4.1 · §6.1
02

独立搜索 prefill 实例

枚举可行的 intra-op 与 inter-op 组合，用模拟器和二分搜索找到满足 TTFT 的最大速率。

发生什么

对每个配置计算 goodput，再除以该实例占用的 GPU 数；随后复制 prefill 实例，直到容量覆盖目标 R。

工程要点

prefill 通常小 batch。低于 Lm 时可合并短 prompt 靠近饱和点；严格 TTFT 倾向更强 intra-op，高到达率时 inter-op 可降低排队。

configₚ* = argmax [ goodput_prefill(configₚ, W, TTFT_SLO) / num_gpus(configₚ) ]§3.1 · Algorithm 1
03

独立搜索 decoding 实例

对 decoding 做同样的配置枚举与二分搜索，但这次满足的是 TPOT，并显式考虑大 batch 与 KV 显存。

发生什么

选择每 GPU goodput 最高的 decoding 配置，再复制实例达到目标速率。多个 prefill 实例可以对应一个 decoding 实例。

工程要点

decoding 先用大 batch 提高带宽利用；严格 TPOT 可用 intra-op 降执行时间，超出 latency 拐点后用 inter-op 或复制扩 rate capacity。

config_d* = argmax [ goodput_decoding(config_d, W, TPOT_SLO) / num_gpus(config_d) ]§3.2 · Algorithm 1
04

按节点亲和性选择放置算法

高速跨节点网络可独立优化两类实例；低带宽集群必须联合考虑 segment 放置与显存。

高节点亲和 · Algorithm 1

分别求 prefill 与 decoding 最优配置，再按目标 R 复制。允许跨任意节点放置，前提是 KV 传输开销足够小。

低节点亲和 · Algorithm 2

按 inter-op stage 切分 instance segments，把同一层的 prefill／decoding segments 放同节点，强制 KV 走 NVLINK；同时检查节点 GPU 与显存约束。

stage ℓ: prefill_segment(ℓ) + decoding_segment(ℓ) → same node → NVLINK§4.1 / §4.2
05

控制器选择最短 prefill 队列

请求进入 FCFS 控制面，被分到一个 prefill 实例；该实例处理全部 prompt，产出首 token 和 KV cache。

发生什么

短请求可组批到总长度接近 Lm，长请求单独执行，减少 inter-op pipeline 中因输入长度不齐产生的 bubbles。

工程要点

prefill 完成后不立即把 KV 推给 decoding，而是先留在自己的 GPU 内存中。这样它可继续服务其他请求，也把缓冲压力显式保留在上游。

request → prefill instance with shortest queue → first token + KV§4.3 · Reducing pipeline bubbles / Combat burstiness
06

decoding 按需 pull KV，逐 token 生成

请求被分配到 least-loaded decoding 实例；该实例拉取 KV 与首 token，进入连续 decoding steps。

发生什么

节点内用 asynchronous CudaMemcpy，跨节点用 NCCL。传输与计算尽量异步，实例无需复杂全局同步。

工程要点

pull 是自然背压：decoding 有能力时才取 KV，避免突发流量瞬间淹没其显存。代价是 prefill 需要承担队列缓冲与故障依赖。

decoding ready → pull KV → decode token 2 … token T → stream response§4.3 / §5 · Figure 6
07

复制实例覆盖流量，周期性重规划

当前放置按目标 R 复制 n、m 个实例；profiler 发现负载分布显著变化后重新运行搜索。

发生什么

算法搜索是秒到分钟级，权重重载为分钟级，论文把其放在小时级负载变化背景下；运行时不做频繁全局重配置。

工程要点

现有实现未包含高级 preemption 与 fault tolerance。FCFS 可能有 convoy effect，且一个 decoding 故障可能影响映射到它的多个 prefill 实例。

编码助手更怕“想了太久才开始写”

  1. ① 严格首 token 延迟使 prefill 成为主要约束。
  2. ② 搜索自动增加 prefill intra-op，降低执行与排队时间。
  3. ③ KV 进入 decoding 后，较宽松 TPOT 允许容量扩展。

05 / Design decisions

真正值钱的不是“拆”，而是拆开后的六项配套选择

相位解耦会复制权重、引入 KV 传输和故障依赖。论文的价值在于同时给出 goodput 目标、独立并行搜索、带宽约束、背压和重规划，而不是只画两个资源池。

D1

优化 goodput，而不是最大 token throughput

决策问题

系统应该追求“做得多”，还是“在延迟合格的前提下做得多”？

被否决的备选

Orca／vLLM 以 colocated continuous batching 最大化总 token/s；只追求大 batch 也可能让 P90／P99 延迟突破 SLO。

为什么这样选

goodput 把 TTFT、TPOT 和 attainment 同时纳入目标，并除以 GPU 数，直接对应查询成本与服务质量。

代价 / 权衡

必须获得双 SLO、到达过程和长度分布；没有这些输入，goodput frontier 无法定义，且离线吞吐场景未必适合。

D2

拆分两个阶段，而不是继续优化共置调度

决策问题

怎样消除长 prefill 对 decoding 的干扰，以及资源与并行配置耦合？

被否决的备选

vLLM 共置；DeepSpeed-MII／SARATHI 的 chunked-prefill + piggyback；简单优先级或串行执行仍留排队与利用不足。

为什么这样选

独立实例从执行路径上去除 interference，并让 prefill 与 decoding 各自扩展 batch、GPU 数和 TP／PP。

代价 / 权衡

两份模型权重、KV 传输、更多部署单元和故障传播。单 GPU 或极少资源环境无法充分利用这套设计。

D3

分别搜索 batch 与并行，而不是共享一种配置

决策问题

计算密集的 prefill 与带宽密集的 decoding，如何避免互相迁就？

被否决的备选

为两阶段指定同一并行度；vLLM++ 虽枚举共置并行策略，仍受 interference 限制，在论文消融中没有超过默认 vLLM。

为什么这样选

prefill 小 batch，低 rate／严 TTFT 偏 intra-op，高 rate 偏 inter-op；decoding 大 batch，严 TPOT 用 intra-op，随后用 inter-op 或复制扩容量。

代价 / 权衡

需要模型执行预测、显存约束和负载模拟；非均匀 prompt 会产生 pipeline bubbles，M/D/1 结论只能作为指导。

D4

把带宽写进放置，而不是拆完再付网络账单

决策问题

跨节点 KV 传输可能要求数十到上百 Gbps，如何保证解耦仍有净收益？

被否决的备选

不考虑拓扑，任意跨节点放置；或简单要求每对 prefill／decoding 实例都同节点——175B 两份权重可超过节点容量。

为什么这样选

高速网络用 Algorithm 1 分相优化；低带宽用 Algorithm 2，将相同 layer stage 的 prefill／decoding segments 同节点放置，强制 KV 走 NVLINK。

代价 / 权衡

低亲和约束缩小搜索空间并可能降低 goodput；节点内配置组合增加求解时间，但换来可忽略的传输延迟。

D5

decoding 拉取 KV，而不是 prefill 主动推送

决策问题

突发流量下，如何避免大量 KV 同时涌入 decoding 显存？

被否决的备选

prefill 一完成就 push；这会让下游无法按自身容量控制 KV 到达节奏，突发时增加 memory overload 风险。

为什么这样选

decoding 需要时才 pull，prefill 的 GPU HBM 兼作队列缓冲，形成自然背压，让两类实例以各自节奏运行。

代价 / 权衡

上游仍需保留 KV，队列与缓存生命周期更复杂；decoding 故障也会阻塞映射到它的 prefill 路径。

D6

模拟 + 周期重规划，而不是逐请求在线求解

决策问题

如何在可接受的规划成本下，从大量配置中找到 SLO 最优放置？

被否决的备选

对所有候选做真实集群 profiling，时间成本过高；或在每次请求时进行全局优化，控制面会进入关键延迟路径。

为什么这样选

用历史分布重采样、离散事件模拟和二分搜索评估候选，按小时级负载变化周期 replan；Table 2 中模拟与实测误差小于 2%。

代价 / 权衡

历史分布漂移与短期突发不可准确预测；规划需要秒到分钟，权重重载也需分钟级。现有 FCFS 仍无高级抢占与容错。

▶ 跑一遍 · chunked-prefill 的 KV 重读为什么会变成平方项
示例值把一个 prefill 等分为 N=4 个 chunks
逐块计算第 1 块读 1 份历史 KV；第 2 块读 2 份；第 3 块读 3 份；第 4 块读 4 份
累计4 + 3 + 2 + 1 = 10 个 chunk 份 KV
相对不切块不切块累计 4 份；10 / 4 = 2.5×

N=4 为本报告示例值，推导对应 §2.3 的 N+(N−1)+…+1=O(N²)，不切块为 O(N)。它解释为什么 piggyback 虽能缓解 decoding 等待，却不是无成本替代。

07 / Critical reading

拆开以后，性能问题变成了一门容量、拓扑与运维的联合题

论文明确指出离线吞吐、资源受限和极小集群并非最佳场景。进一步看，DistServe 的收益依赖可信的负载分布、足够的 GPU、网络拓扑和可接受的运维复杂度。

论文自认 · §7 / §4.3

离线吞吐场景可能不占优

不敏感于延迟时，chunked-prefill + piggyback 可让每批接近 compute-bound，简单共置架构反而可能更合适。

资源很少时搜索空间受限

几块甚至单块 GPU 的环境无法充分拆分与调并行，论文承认可能难以奏效，简单系统可降低运维复杂度。

没有高级抢占与容错

FCFS 有 convoy effect；前后实例依赖引入故障传播，一个 decoding 故障可能影响多个 prefill 实例。

工程师视角 · 进一步质疑

SLO 是经验设定，不是行业统一标准

作者明确说没有可用的应用 SLO 设置，因此经验选择 Table 1；数据集没有时间戳，到达时间由 Poisson 生成。换一组 SLO 或到达模型，结论边界会改变。

模拟器校准不能无限外推

Table 2 的 <2% 只针对特定模型、负载与配置。非均匀 prompt 会产生 pipeline bubbles，论文也说明 M/D/1 结论会出现偏差。

两份权重与实例管理不是免费资源

per-GPU goodput 已把 GPU 数纳入分母，这是公平之处；但大模型仍需额外权重副本、KV 缓冲与更多实例生命周期管理，节点容量会成为硬约束。

GQA／MQA 的“会更好”仍是作者推断

§6.1 认为新模型因 KV 更小、传输更低会表现更好，这是合理方向，但本文端到端证据主要来自使用经典 MHA 的 OPT，而不是对 GQA／MQA 的直接对照。

突发背压并不等于完整过载治理

pull 能防止 KV 瞬间淹没 decoding，却没有消除 prefill 缓冲占用、请求排队、长任务 convoy 和下游故障。生产部署仍需准入、抢占与恢复策略。

长上下文结论有机制支持，也有验证边界

§7 认为 prefill 二次增长会让传输相对变小、相位差异更大，因此解耦仍有前景；但这不等同于在 1M context 上完成了端到端验证。

可以直接偷的思想

不实现 DistServe，也能复用这六条

  1. 把 SLO 写进吞吐指标。任何“更快”的系统都应先回答多少请求仍满足用户体验约束。
  2. 先找相互干扰、优化目标不同的阶段。拆分不是为了微服务化，而是为了独立资源配置。
  3. 资源数与并行策略必须联合搜索。只换 GPU 数量，可能错过低延迟与高容量之间的拐点。
  4. 把网络与显存作为放置约束。拓扑不是部署后的细节，而是架构成立的前提。
  5. 用 pull 建立自然背压。让下游按能力取数据，比上游无节制推送更能抵抗突发。
  6. 用模拟做慢决策，用简单调度跑热路径。profiling、模拟和周期 replan 不必进入每个请求的关键路径。

读到这里，应该记住的一句话

DistServe 的核心不是“prefill 与 decoding 分机器”这句话，而是一个完整的 goodput 优化闭环：双 SLO 定义合格工作，分相搜索决定资源与并行，带宽约束决定放置，pull 与 replan 维持在线运行。
