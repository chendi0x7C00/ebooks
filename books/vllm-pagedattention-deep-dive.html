PagedAttention：把操作系统的虚拟内存，搬进 GPU 的 KV cache

LLM 推理的吞吐被 KV cache 内存卡死，而不是被算力卡死。vLLM 的核心洞察是：KV cache 的管理问题本质上是操作系统 60 年前就解决过的内存分页问题——把每个请求的 KV cache 切成固定大小的"页"，逻辑块按需映射到非连续的物理块，辅以引用计数与写时复制实现跨请求共享。浪费从 60–80% 降到接近零，同样延迟下吞吐提升 2–4×。

01

问题定义：吞吐的天花板是显存，不是算力

自回归解码每迭代只为每条序列算 1 个 token，是 matrix-vector 运算——GPU 的算力大量闲置，整个负载是 memory-bound。提高吞吐的唯一出路是 batching，而 batch size 的上限由 KV cache 能塞进多少显存决定。

以 13B 模型 + A100 40GB 为例：约 65%（26 GB）显存被静态模型参数占满，接近 30% 是随请求动态增减的 KV cache，激活值只占零头（Fig. 1 左）。参数是死的、激活是短暂的——KV cache 的管理方式几乎单独决定了最大 batch size。

现有系统错在哪：把动态的东西按静态处理

FasterTransformer、Orca 等系统遵循深度学习框架的惯例：每个请求的 KV cache 是一块连续张量，且因为输出长度事先不可知，按最大序列长度（如 2048）一次性预分配。这产生三种浪费（Fig. 3）：

浪费类型成因何时能被发现
预留 reserved为"未来会生成的 token"占坑，请求存活期间别人不能用最终会用上，但占着茅坑的阶段是纯机会成本
内部碎片实际长度远短于最大长度（Fig. 11 的长度分布方差极大）请求结束后才知道浪费了多少
外部碎片各请求预分配尺寸不一 + buddy allocator 粒度服务开始前就注定永远用不上

论文实测（Fig. 2）：现有系统里真正存 token 状态的显存占比最低只有 20.4%——也就是说，一张 40 GB 的 A100，可能有 30 GB 的 KV 空间里躺着 24 GB 的空气。

为什么难：三个约束互相咬合

① KV cache 太大。OPT-13B 单 token 800 KB，GPU 显存容量增长远慢于算力（A100→H100：FLOPS 翻 2 倍多，显存停在 80 GB）——内存墙只会越来越厚。② 解码算法要共享。并行采样共享 prompt 段，beam search 共享前缀树且共享模式随解码动态变化；连续存储下共享无从谈起。③ 长度不可预知。输入长度分布差异巨大（ShareGPT 均值 161 token vs Alpaca 19 token），输出长度更是运行时才知道，调度器必须随时准备驱逐与恢复。

分水岭前人（Orca）把功夫下在调度上——iteration-level scheduling 让请求按迭代进出 batch；vLLM 把功夫下在内存上——让更多请求的工作集同时塞进显存。两者互补：调度越细，内存管理越关键（§9）。
▶ 跑一遍 · 一个 token 的 KV cache 有多大

架构总览：一个"操作系统"长在了推理引擎里

vLLM = FastAPI 前端 + 集中式 Scheduler + KV Cache Manager（维护 block table）+ 若干 GPU Worker（各持模型分片与 Cache Engine）。控制面与数据面分离：调度器每迭代广播一次"输入 token + block table"，之后 Worker 之间用 all-reduce 自行同步，不再需要调度器参与。

vLLM 系统架构（HLD）
控制面核心（CPU 侧） 控制面：调度指令 / block table 广播（虚线） 数据面：KV 读写 / all-reduce（实线） CPU RAM swap 空间
依据论文 Figure 4 重绘。关键观察：Megatron 式张量并行下所有 Worker 处理相同的 token 位置（SPMD），因此全局只需一份 block table，由集中式管理器统一下发——各 Worker 只存自己负责的那部分 attention head 的 KV。

核心流程：一个请求在 vLLM 里的一生

点击或用 ← → 键切换，跟随一条请求穿过调度器、block table 与 PagedAttention kernel。

▶ 跑一遍 · 一个 decode 迭代里 kernel 做了什么
  1. Scheduler 拼批：把当前迭代所有输入 token 拼成一条序列（prompt 阶段请求的全部 token + 解码阶段请求的最新 1 个 token）。
  2. 对 batch 中每条序列，PagedAttention kernel 按 block table 逐块取 K/V。查询 token "forth" 的 q 向量依次与块 0（"Four score and seven"）、块 1（"years ago our fathers"）、块 2（"brought"）的 K 做点积（Fig. 5）。
  3. 块内是连续 16 个位置 → kernel 可以并行读、合并访存（每个 GPU warp 读一个块）；块间通过 block table 间接寻址。
  4. softmax 分母要跨块累加 o_i = Σj=1..⌈i/B⌉ V_j · A_ijᵀ（论文 Eq. 4 的分块形式）。
  5. 新 KV 经"融合 reshape + 块写入" kernel 落到 block table 指定的槽位——一次 launch 完成切分、重排、写回。
算式来自论文 Eq. 4 与 §4.3、§5.1；warp 分配策略见 §5.1(2)。

05

关键设计决策：每一张牌怎么打，放弃了什么

D1

KV cache 分页存储，允许物理上不连续

被否决的备选

① 连续张量 + 按最大长度预分配（FasterTransformer、Orca）；② 连续分配 + 定期 compaction 整理碎片（Pacman 式思路）——KV cache 体量太大，搬运成本在服务路径上不可接受，且仍无法支持共享。

为什么这样选

固定块大小直接消灭外部碎片；按需分配把内部碎片区限于每序列最后一块（< 4%）；块级映射让共享变成"多填一行 block table"。分页是 OS 验证过 60 年的答案。

代价 / 权衡

attention kernel 必须自己处理间接寻址、分支与变长序列——换来 20–26% 的 kernel 级额外延迟（Fig. 18a），并需要 2K 行定制 C++/CUDA。论文赌注：这点算力开销远小于内存省出来的 batch 收益——实验证实赌对了。

D2

块大小默认 B = 16

被否决的备选

① B = 1～8：块太小，kernel 无法并行读取足够多位置，GPU 利用率低；② B = 128～256：Alpaca 这类短序列负载上内部碎片暴涨（序列比块还短），共享概率也随之下降。

为什么这样选

消融实验（Fig. 18b）：ShareGPT 上 B = 16–128 都是最优平台期；Alpaca 上只有 16/32 不劣化。16 是"足够大以喂饱 GPU、足够小以兜住碎片"的交点。

代价 / 权衡

每条序列仍浪费最多 B − 1 = 15 个 token 槽（≈ 12 MB / 序列，示例值按 800 KB/token 推算）；块大小是全局静态配置，无法按负载自适应。

D3

集中式调度器 + 全局唯一 KV cache manager

被否决的备选

每个 GPU worker 各自管理本地 KV 内存、分布式协商映射——需要 worker 间同步内存管理状态，每步多出协调开销与一致性复杂度。

为什么这样选

Megatron 式张量并行是 SPMD：所有 worker 在每一步处理完全相同的 token 位置，因此一份 block table 对全员有效。调度器把 block table 随输入一起广播，worker 只管用——内存管理零同步。

代价 / 权衡

调度器是单点：每迭代一次广播在 worker 极多时会成为控制面瓶颈（论文未测超大规模）；Python 实现的控制逻辑也有性能上限。

D4

抢占 = 整条序列驱逐（all-or-nothing）+ swap / recompute 双恢复

被否决的备选

OS 式 LRU 等启发式逐块驱逐——LLM 的访问模式是"一条序列的所有块同时被访问"，逐块预测毫无意义的徒增复杂；只 swap 不 recompute 则小 Block 下 PCIe 小包传输把带宽打骨折。

为什么这样选

利用应用语义：要么全要、要么全不要，驱逐策略从预测题变成送分题。recompute 是 OS 做不到的大招——已生成 token 拼回 prompt 一次 prefill 即可再生全部 KV，开销与块大小无关（Fig. 19）。

代价 / 权衡

一旦发生 swap，vLLM 停止接收新请求直到被抢占序列全部完成（§4.5）——宁可让新请求排队也不让系统颠簸；FCFS + 后来者先被抢占保证公平，但对延迟敏感业务偏粗糙。B = 16–64 时两种恢复方式端到端打平。

D5

引用计数 + 块粒度写时复制实现共享

被否决的备选

现有系统对 beam search 的做法：候选分叉时整段复制 KV cache——Fig. 9 的例子中候选 3 要拷贝候选 2 的大部分 KV 才能继续。共享前缀场景则每请求重算 prompt。

为什么这样选

映射层把"共享"变成纯元数据操作：多填一行 block table + ref count++。写时才付一次单块拷贝。实测省下 beam search 37.6–66.3% 的 KV 内存（Fig. 15），且让不同解码算法的请求可以同批混跑。

代价 / 权衡

block table 要维护 ref count 与 CoW 状态机；beam search 每步候选洗牌都要精确增减计数——实现复杂度从 kernel 转移到了控制面（Python 的 block manager）。

D6

三个融合 CUDA kernel，而不是复用通用 API

被否决的备选

① 用 cudaMemcpyAsync 逐块拷贝——CoW 会产生大量小传输调用；② 直接改 PyTorch 算子——无法融合"按 block table 读 + attention"路径，launch 开销与访存都不优。

为什么这样选

① 融合 reshape + 块写入：一次 launch 完成切分/重排/写回；② 改造 FasterTransformer attention kernel 按块表读 KV，每 warp 读一块保证合并访存；③ 融合块拷贝：把多个不连续块的拷贝批成一次 launch。

代价 / 权衡

2K 行 C++/CUDA 要跟随新硬件与新模型持续维护；kernel 仍比 FT 慢 20–26%——间接寻址的税只能减免、无法豁免。

▶ 跑一遍 · 块大小对碎片的影响（决策 D2 的量化直觉）
  1. 每条序列的内部碎片期望 ≈ B / 2 个 token 槽（最后一槽均匀分布，示例假设），上界 B − 1。
  2. B = 16：每序列浪费约 8 × 800 KB ≈ 6.4 MB；30 条并发序列 ≈ 192 MB，占 12 GB KV 空间的 1.6%。
  3. B = 256：每序列浪费约 128 × 800 KB ≈ 100 MB；Alpaca 平均序列仅 78 token（Fig. 11b 均值之和）——一条序列连半个块都填不满，碎片率超 60%。
  4. 结论与论文一致：B = 16 是 ShareGPT / Alpaca 两种负载下都不劣化的最大并行度甜点（Fig. 18b）。
B/2 期望为示例值假设；序列均值与消融结论来自论文 Fig. 11、Fig. 18b。

  2. B = 16 → 物理块总数 ≈ 15.7K ÷ 16 ≈ 983 块
  3. ShareGPT 平均序列长 = 161（输入）+ 338（输出）≈ 499 token → 每序列约需 499 ÷ 16 ≈ 32 块
  4. 满载并发序列 ≈ 983 ÷ 32 ≈ 30 条——与 Fig. 13a 实测平均 batch 30.42 几乎严丝合缝：vLLM 把显存利用率直接兑换成了 batch size。
槽位数与 trace 均值来自论文 Table 1 / Fig. 11；32 块/序列与 30 并发的对应为工程师视角推算（忽略块内碎片与混合长度）。

批判性阅读：边界、质疑与可以直接偷走的思想

论文自认的边界

论文 §8 自述这套技术只在"动态分配 + memory-bound"的负载上成立。DNN 训练张量形状静态、非 LLM 服务是 compute-bound——引入间接寻址与非连续块反而可能降低性能。
论文 §7.1 自述PagedAttention kernel 比高度优化的 FasterTransformer 慢 20–26%。优势完全来自内存侧，不是算子侧。
论文 §4.5 自述swap 发生后停止接收新请求直到被抢占序列全部完成——过载期的尾延迟行为相当粗糙。

工程师视角的追问

质疑 · 调度公平FCFS + "最晚到达者先被抢占"对长输出请求不利：一条快写完的长序列可能因为内存耗尽前新来的请求而……不，反过来——新请求会被抢占。但长请求的 KV 占用时间本身就在挤压系统，论文没有讨论按 SLO 或剩余长度调度的空间。
质疑 · 基线强度Orca(Oracle) 不可达，真实世界的 Orca 更接近 Pow2/Max——对 Pow2 的 2.7–8× 才是实务参考值。另外 Orca 未开源，基线是作者自行复现，buddy allocator 假设可能放大或缩小差距。
质疑 · 规模外推集中式调度器 + Python 控制面在 8×A100 内验证充分；跨节点、数百 GPU 时单点广播与 block manager 是否成为瓶颈，论文未覆盖。
质疑 · 时代变量论文（2023.09）未涉及之后成为标配的 chunked prefill、prefix caching 自动复用、投机解码等；但这些全部建立在本文的块管理地基上——地基本身没有过时。

可以直接偷的思想

  • ▸给"动态增长、长度未知"的 GPU 状态做分页。任何这类状态（多模态中间特征、agent 长上下文、diffusion 历史）都可以套"固定块 + 逻辑/物理映射"的模板。
  • ▸映射层即解耦层。上层算法（beam、采样、前缀共享）只操作逻辑块，下层存储随意排布——加一个 indirection，复杂度各归各位。论文原话：kernel 只看到一串物理块 ID。
  • ▸recompute 当恢复手段。OS 不能把丢掉的页"算"回来，但 LLM 的 KV 可以由输入再生——当你的系统状态是确定性函数输出时，checkpoint 可以被"重放"替代。
  • ▸用访问语义简化驱逐。已知"一条序列的块永远一起被访问"，LRU 之类的逐块预测就是过度设计——all-or-nothing 反而最优。先问负载语义，再选通用算法。
  • ▸不可变前缀 + CoW 是通用的省内存范式。fork 进程、共享库、beam 树——凡是"大量副本共享前缀、偶发写分叉"的结构，引用计数 + 写时复制几乎总是对的。
一句话收束vLLM 没有发明新的数学，它发明的是一个对应关系：KV cache ≈ 进程地址空间。一旦这个对应成立，操作系统六十年积累的分页、共享、写时复制、swap 工具箱就全部解锁——这正是系统研究最漂亮的赢法。
