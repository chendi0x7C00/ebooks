01 / THE CAST

Only One of These Layers Talks to Silicon

PyTorch decides what to run, the CUDA runtime packages the calls, the kernel driver owns the hardware, the silicon executes — and the compilers built the kernels ahead of time or just in time.

The long book ended its GPU chapter at a convenient black box: a kernel enqueued on a stream. This book opens that box. Between a + b on CUDA tensors and arithmetic units flipping bits stand four honest layers plus a compiler sidecar, each with one clean job. This chapter is roll call — who they are and what each owns, no mechanics yet. Every chapter that follows begins by naming which of them is acting.

PyTorch decides what. Op semantics come from ATen schemas; TensorIterator resolves shapes, dtypes, and layouts; and — the part that surprises people — PyTorch computes the launch configuration itself: element count, block size, grid dimensions, vectorization width (chapter 3). CUDA never hears "add these tensors." It receives a function handle and a handful of integers, all chosen before CUDA is involved at all. PyTorch is not a skin over CUDA; it is CUDA's most demanding client, and a client with opinions.

The CUDA runtime (libcudart) is the convenient face of the stack: a thin C API — cudaLaunchKernel, cudaMalloc, cudaMemcpyAsync, streams. The Programming Guide is blunt about its rank: "the CUDA runtime is written on top of the lower level CUDA driver API." Its real job is implicit state: a current device, a context (the runtime's auto-created one is "the primary context"), and the kernel modules that <<<>>> and cudaMalloc quietly assume. Convenience, not magic.

The kernel driver (libcuda, userspace half of the OS-level driver) is the only software in the picture that talks to the hardware — nothing else may. Its interface is "a handle-based, imperative API," initialized by an explicit cuInit(). Contexts and modules, implicit upstairs, are explicit here: a context is "analogous to a CPU process," and modules — the containers of kernel code — are "dynamically loadable packages of device code… akin to DLLs." Some power lives only at this level: "some advanced interfaces, such as Virtual Memory Management, are only exposed in the driver API." That is why PyTorch, though mostly a runtime client, calls cuMemCreate/cuMemMap directly when its allocator runs in expandable-segments mode — a structural dependency, not an incidental one.

The hardware employs two kinds of worker. Streaming multiprocessors (SMs) are the compute: thousands of simple cores that execute your kernel warp by warp (chapter 6). Copy engines are the movers: dedicated DMA units that shuffle bytes across the bus while the SMs keep computing (chapter 7).

The compilers get a sidecar because they act at a different time, outside the call path: nvcc turned PyTorch's CUDA C++ into PTX and SASS at build time, while NVRTC and Triton compile new kernels at runtime, on first use. Chapter 5 unpacks both pipelines.

One framing to bind the cast: PyTorch sits on the driver stack the way your browser sits on the OS network stack — it calls the equivalent of send() and never learns the wire format.

That is the whole org chart, and the map for the rest of the book. When launch arguments are validated and packed, that is the runtime. When memory is mapped, commands are emitted, or hardware is told anything at all, that is the driver — always the driver. When SASS retires and a completion value lands in memory, that is silicon (chapter 4 explains why even that last step is reverse-engineered, not documented). And when the kernel being launched did not exist an hour ago, that was a compiler. Every chapter from here on names the acting layer, scene by scene, down to chapter 8's end-to-end trace.

Carry this forward: PyTorch decides what; the runtime packages it; only the driver talks to hardware; the compilers supply the code.

02 / DISPATCHER

The Dispatcher Is a Bitset, a Subtraction, and a Jump

No loop over backends, no vtable walk: every tensor carries a 64-bit key set, every call is two lines of set arithmetic plus one indexed read — and no_grad, inference_mode, and torch.compile each disturb a different piece of it.

The long book left you with a serviceable picture: a vtable per operator, the tensors' device picking the row. Right shape — and this book can afford the real thing. Here is what actually happens on every tensor operation you run: a 64-bit word inside each tensor, a union, a subtraction, and one array index. The three autograd-off modes differ only in which of those pieces they touch.

One 64-bit word per tensor

Every tensor's TensorImpl carries a DispatchKeySet — the field is literally key_set_, documented as "This is the information used to dispatch operations on this tensor." It is a plain uint64_t split into two orthogonal halves. The bottom 16 bits are backend bits — CPUBit, CUDABit, MPSBit, MetaBit, and twelve more; a compile-time static_assert reads "No More Than 16 Backends." Above them sit the 47 functionality bits — Dense, BackendSelect, Fake, Python, ADInplaceOrView, the Autograd family, the Autocast family, and the rest — with the two groups' sizes locked by another static_assert so everything fits in the one word.

The subtle part: a runtime key like CPU is not its own bit. DispatchKeySet(CPU) stores the pair (Dense functionality bit + CPUBit); CUDA is (Dense + CUDABit); AutogradCUDA is (AutogradFunctionality + CUDABit). The functionality half says what kind of handling applies, the backend half says for which hardware — neither means anything alone. Verified from the TensorImpl constructor, here is what real tensors carry:

tensorkey_set_ stored in the TensorImpl
cpu float, requires_grad either way{CPU, ADInplaceOrView, AutogradCPU, AutocastCPU}
cuda float{CUDA, ADInplaceOrView, AutogradCUDA, AutocastCUDA}
the same cpu tensor inside no_gradidentical — no keys move
cuda tensor created inside inference_mode{CUDA, AutocastCUDA} — autograd keys gone, version counter gone

Two rows pay off later. BackendSelect is absent everywhere because it arrives via thread-local state, not the tensor — factories like torch.zeros have no tensor argument to union. And the Autocast bits sit in every set as dead bits: excluded by default until torch.autocast includes them.

Priority is the bit order itself — "higher bit indexes get handled by dispatching first," because the extraction counts leading zeros on the word. Two placements in the verified enum order matter below: every Autocast key sits above every Autograd key ("Autocasting precedes VariableTypeId, to ensure casts are autograd-exposed"), and Python — the key behind __torch_dispatch__ — sits below ADInplaceOrView and Autograd, so dispatch modes see operations only after autograd has wrapped them.

The two lines at the heart of every call

The entire per-call computation, verbatim from DispatchKeyExtractor.h:

c10::impl::LocalDispatchKeySet tls = c10::impl::tls_local_dispatch_key_set();
auto dispatch_keys = (ks | tls.included_) - tls.excluded_;

ks is the OR-union of key_set() across every tensor argument — tensor lists, optional tensors, and defined generators included. tls is thread-local include/exclude state. Union, then subtract; a follow-up per-operator mask (explained under fallthrough) clears keys this op does not service. Then, no loop: std::bit_width finds the highest set bit, arithmetic turns it into a table index, and the kernel is read straight out of the array. In ezyang's phrasing, the dispatcher performs "an indirect jump." Total cost: one TLS read, an OR, a mask, a leading-zero count, an indexed load.

The TLS defaults are load-bearing. Included: BackendSelect and ADInplaceOrView. Excluded: all ten Autocast keys — hence the dead bits above. When the two sets disagree, "Exclusion wins over inclusion."

Flip the toggles below — device, requires_grad, mode, in-place — and watch the three stages update live: the 64-bit strip lights up, the TLS mutation applies, and the priority-sorted shortlist crowns a winner with the wrap-and-redispatch sequence it implies.

The three modes, truthfully

no_grad, inference_mode, and the tracing machinery under torch.compile are usually taught as three shades of "don't do autograd." In dispatch terms they are three different mechanisms — this table is the chapter's payoff:

modewhat it actually changesthe autograd kerneltensors created inside
torch.no_gradone plain TLS boolean (GradMode); no key set, no include/excludestill wins, still runs — reads the boolean, records nothingbyte-identical key sets
torch.inference_modeTLS exclude set gains the Autograd family; ADInplaceOrView leaves the include set; new tensors' key sets strippednever runs — its bit was subtracted before the jump{CUDA, AutocastCUDA}, no version counter
TorchDispatchMode / FakeTensor (torch.compile)tls_set_dispatch_key_included(Python, true) — the include set gains the Python keyruns first as usual; the mode sees the op after the wrapperfakes: metadata only, no storage

Read the middle row twice: inference tensors' version counters genuinely do not exist — the constructor builds one only for non-inference tensors — so a later grad-recording use cannot silently misbehave; it errors. The InferenceMode header states the invariants: "ADInplaceOrView is never in the excluded set; Autograd is never in the included set; Setting InferenceMode will set GradMode accordingly, but not vice versa."

Inside the Autograd wrapper

When AutogradCUDA wins the jump, the kernel that runs is generated code. If any input requires grad, it records a grad_fn node — one saved field per backward need, generated from derivatives.yaml — then redispatches under an ExcludeDispatchKeyGuard: functional ops use AutoDispatchBelowADInplaceOrView (excludes the Autograd family plus ADInplaceOrView), view and in-place ops use AutoDispatchBelowAutograd. The redispatch passes a precomputed key set — that "saves the dispatcher from having to read from TLS" — and the guards enforce the invariant: "Once you are in VariableType/ADInplaceOrView kernel for an op, you never go back to a kernel on same dispatch key until you finish the current op." Autograd wraps exactly once and steps out of the way.

Not every op gets a wrapper. Kernels registered only to CompositeImplicitAutograd — pure mathematical definitions valid on every backend — are copied into the op's Autograd cells wholesale: no grad_fn, no ceremony. Custom ops with no Autograd registration land in an Autograd fallback that falls through when nothing requires grad.

ADInplaceOrView, and the wrong gradient it prevents

The ADInplaceOrView kernels do one of three things: in-place ops redispatch, then increment_version each returned tensor; view ops redispatch, then as_view wires up view metadata; everything else falls through. The version counter is what makes autograd's saved tensors trustworthy:

s   = torch.ones(1, requires_grad=True)
out = s * s            # backward saves s's value
s.add_(1)              # version counter: 0 → 1
out.backward()         # → error (paraphrased): a tensor saved for
                       #   backward was modified after it was saved

Suppress the bump — the source note does this under a below-autograd guard — and the same three lines produce, in the note's exact words, "WRONG GRADIENT! s.grad() are now computed using s value after the inplace update." No exception; just silently incorrect derivatives, because the saved s now reads the post-update value. Inference tensors skip counting entirely — that is the trade their restrictions pay for.

Where the winning kernel lives

The table the jump lands in belongs to the operator, not to a class — "Dispatch tables are allocated per operator, whereas vtables are allocated per class." Each OperatorEntry holds a std::array<KernelFunction, 137> — 47 functionality slots plus the per-backend runtime slots — kept contiguous "because … dispatchTable is accessed often and should be kept small to fit into CPU caches." When several registrations could fill a cell, the rule is exact: "exact kernel registrations have the highest precedence, and catch all kernels take precedence over fallback" — a specific (op, key) registration beats a catch-all row beats a backend's fallback column, and within a cell the newest registration wins.

Fallthrough is the pleasant surprise: a distinguished fallback meaning "skip me, take the next key" — which the dispatcher arranges to never even pay, by pre-masking fallthrough keys out of the candidate set before the jump. The boxing code's own words: "it is FAST; it is no overhead to fallthrough… this does NOT actually go through the boxing/unboxing codepath." (Boxing is the generic-argument wrapping a fully dynamic call would need.) BackendSelect, for instance, is fallthrough for every op except factories.

Cells are filled at two different times. Static: TORCH_LIBRARY expands to a static initializer run at library load — how ATen's own kernels register, via build-generated files. Runtime: Dispatcher registration calls under a global mutex — precisely what torch.library drives from Python:

lib = torch.library.Library("myops", "DEF")
lib.define("sumsq(Tensor self) -> Tensor")   # publish the schema
lib.impl("sumsq", sumsq_cuda, "CUDA")        # fill the (sumsq, CUDA) cell

Your kernel now wins the jump like a native one; add a register_fake implementation and torch.compile can trace it too.

Two no_grad misconceptions

First: "the dispatcher loops over backends until one matches." It never loops — one union, one subtraction, one bit count, one array read; a per-op scan of 16 backends would be visible in any profile. Second: "no_grad removes the Autograd keys so kernels run directly." The table above is the refutation: inside no_grad a tensor's key set is byte-identical. The Autograd kernel still wins and still runs — it reads one boolean and records nothing. If you want the keys actually gone, that service is inference_mode, and its restrictions are the price.

Chapter 3 follows today's winner — the CUDA cell for add — into TensorIterator, where PyTorch, not CUDA, computes the launch configuration.

Carry this forward: dispatch is one bitset union, one TLS subtraction, one indexed jump — and each mode differs only in which of those it disturbs.

03 / SCHEMA TO KERNEL

The Kernel Body Is One Line; TensorIterator Is Everything Else

The CUDA row of the op table is a codegen'd trampoline. By the time it touches CUDA, PyTorch has already computed the entire launch configuration — block size, vector width, elements per thread, grid — in plain C++, on the CPU.

Chapter 2 ended with the dispatcher selecting the CUDA row of the op table for add.Tensor. Here is what runs in that row. In native_functions.yaml, add.Tensor is declared with structured_delegate: add.out: the schema you called forwards to a structured kernel that inherits from TensorIteratorBase. torchgen turns that declaration into ufunc_add_cuda, and the generated body is a single call — gpu_kernel(iter, functor). The functor, the only line that knows this is addition, is at::native::ufunc::add: self + alpha * other. The kernel body is a one-line functor; everything else is TensorIterator.

TensorIterator itself is built by a fixed pipeline, TensorIterator::build. In three sentences: compute_shape broadcasts the operand shapes into the result shape, and compute_types promotes everything to a common dtype with explicit cast decisions. Then the memory half runs — compute_strides, reorder_dimensions (the source's own comment says it permutes "to improve coalescing"), output allocation, and coalesce_dimensions, which merges adjacent dimensions with compatible strides into one flat loop. What enters as two tensors of arbitrary shape, dtype, and layout leaves as one near-contiguous iteration space plus typed, alignment-checked data pointers.

Concretely: broadcast a (128,) fp32 tensor against a (4, 128, 128) one, and build hands the kernel two flat loops over 65,536 elements — the small operand with stride 0 on the broadcast dimensions, so every lane re-reads the same word and the cache makes that nearly free. Broadcasting is not a preprocessing pass that materializes anything; it is a stride assignment inside this box.

Now the fact this chapter exists to plant: the launch configuration is computed here, by PyTorch, on the CPU — before CUDA is involved at all. gpu_kernel inspects the iterator's element count and pointers and picks everything CUDA will be told. Simplified but real, constants verified against current main — source comments kept, annotations mine:

// launch_vectorized_kernel (CUDA branch), simplified — CUDALoops.cuh:
const uint16_t max_vec = memory::can_vectorize_up_to<func_t>(data); // per-operand pointer alignment, max 8
uint16_t vec_size = 16 / sizeof(cpp_type);      // fp32 -> 4, fp16 -> 8, i8 -> 16 elems per vector
vec_size = min(vec_size, max_vec);              // float4 only if EVERY pointer is 16B-aligned
if (devProp->major != 9 && devProp->major != 10) // vec8: sm_90/sm_10x only
  vec_size = min(vec_size, 4);
int tws = elems_per_thread<io_size>();          // 16 if io bytes==1 else 8 elems/thread (fp32 add: 8)
int bws = tws * num_threads();                  // 8*128 = 1024 elems/block; num_threads() = 128
int64_t grid = (N + bws - 1) / bws;             // no clamp: N<=INT_MAX, bws>=1024
vectorized_elementwise_kernel<4,func_t,...><<<grid, num_threads(), 0, stream>>>(N, f, data);

// device index math — legacy path (non-contiguous), same file:
__global__ void elementwise_kernel(int N, func_t f) {  // nt=128, vt=2 (4-byte dtypes) or 4
  int idx = nt*vt*blockIdx.x + threadIdx.x;            // linear element index
  #pragma unroll
  for (int i = 0; i < vt; i++) { if (idx < N) { f(idx); idx += nt; } } // guard, not grid-stride
}

Walk the host half. num_threads() is C10_WARP_SIZE * 4 = 128 on CUDA — every PyTorch elementwise block is 128 threads, which is four warps, the execution unit chapter 6 introduces. vec_size wants 16 / sizeof(elem) elements per load: 4 for fp32, meaning float4, one aligned 16-byte vector. It is clamped twice — by can_vectorize_up_to, which checks the actual data pointers of every operand and stops at the first misalignment (8 is the CUDA maximum), and to 4 unless the target's major compute capability is 9 or 10; sm_90 and sm_10x are the only architectures that compile 8-wide vectors.

Then the arithmetic: tws is 8 elements per thread for an fp32 add (16 only when an op's inputs and outputs total one byte). 8 per thread × 128 threads = 1,024 elements per block, so the grid is ceil(N / 1,024) blocks — a one-million-element add gets 977. No grid clamp is needed: with at least 1,024 elements per block, grid.x stays far under its own 2³¹−1 limit for anything that fits 32-bit indexing. The device half is deliberately dumb — idx = nt*vt*blockIdx.x + threadIdx.x, apply the functor, advance, bounds-check every step. The legacy kernel shown is the non-contiguous fallback; the vectorized policy replaces each scalar access with float4 slots. Either way, all the intelligence was spent on the numbers passed in. The kernel is a loop; the loop was planned on the CPU.

"Huge tensors use a grid-stride loop"

A persistent folk story says PyTorch's elementwise kernels fall back to a grid-stride loop when a tensor is too big. Current PyTorch has no grid-stride loop anywhere on this path. When numel or any operand's byte-offset span exceeds INT32_MAX (2³¹−1), can_use_32bit_indexing fails and gpu_kernel recurses over sub-iterators, splitting along the dimension with the largest stride×size, until each piece fits — one kernel launch per piece. The fallback for a tensor too big for 32-bit indexing is more launches of the same kernel, not a different loop shape.

This deserves a chapter because for an elementwise op the arithmetic is trivial — one FADD per element — so performance is decided almost entirely by how the loop moves bytes: vector width, block size, coalesced index order. That is why reorder_dimensions bothers to permute for coalescing, and why launch config quality lives in PyTorch, tuned once for every elementwise op at once, rather than re-derived per kernel in CUDA. Chapter 6 prices these choices in sectors and cycles.

What leaves this chapter is a launch — vectorized_elementwise_kernel<<<grid, 128, 0, stream>>>(N, f, data) — three pointers deep, on a stream PyTorch picked, with a grid PyTorch computed. Chapter 4 shows what happens to this <<<...>>> call as it becomes command bytes in host memory and finally reaches the hardware.

Carry this forward: PyTorch computes the launch config — 128-thread blocks, float4 when alignment allows, grid = ceil(N/1,024) — on the CPU; the kernel is just a guarded loop over indices it was handed.

04 / THE LAUNCH

A Launch Is a Command Buffer, Not a Call

cuLaunchKernel validates your launch, packs the arguments into one contiguous host buffer, and returns — the GPU fetches the commands itself. Cost, streams, sync, and graphs all fall out of that shape.

Chapter 3 ended with the CPU holding a complete launch plan: kernel handle, grid, block size, all computed by TensorIterator inside PyTorch. This chapter follows that plan across the boundary. The short version: a kernel launch is not a function call into the GPU — it is packaging. Argument bytes in host memory, command words in a ring buffer, one notification write; the GPU fetches the rest. The long version has eight stations, two lanes, and an honesty ledger between what NVIDIA documents and what researchers measure.

The documented contract: cuLaunchKernel

Every launch path bottoms out in the same driver call, and everything CUDA needs is in its signature:

CUresult cuLaunchKernel(
    CUfunction f,                    // "Function CUfunction or Kernel CUkernel to launch"
    unsigned gridDimX, gridDimY, gridDimZ,   // "Width/Height/Depth of grid in blocks"
    unsigned blockDimX, blockDimY, blockDimZ,
    unsigned sharedMemBytes,         // dynamic shared memory per block, in bytes
    CUstream hStream,                // "Stream identifier"
    void **kernelParams, void **extra);

The handle f points into a module the driver loaded (chapter 5 explains where modules come from); the grid and block dimensions are chapter 3's arithmetic. kernelParams is an "array of pointers to kernel parameters" — for our add, three pointers and the element count. Nothing else is transmitted; the compiled code already sits in device memory.

The most revealing parameter is extra: its documented option CU_LAUNCH_PARAM_BUFFER_POINTER accepts "a pointer to a buffer containing all the kernel parameters," and the API's contract is "all kernel parameters in one contiguous buffer." Your three pointers and the count — the entire payload of torch.add — end up packed back to back. There is no RPC here, no marshalled handoff to a waiting GPU thread: the GPU will read your argument bytes out of pinned host memory itself. A launch is data, not a call.

Below the API: the submission path, reverse-engineered

Here the documented contract ends — the Programming Guide says only that a launch asynchronously enqueues work into a stream. Below that line nothing is official, but NVIDIA's open-source kernel driver and a 2026 instrumentation study (arXiv 2604.26889, which set watchpoints on the doorbell registers) agree on the mechanism. Labeled reverse-engineered, here it is:

  • Each channel — the driver's per-context conduit — owns a pushbuffer: a ring buffer in pinned host memory.
  • libcuda translates your launch into GPU-specific command words written into that ring: 4-byte entries, described by 8-byte GPFIFO descriptors.
  • The driver then rings the doorbell — "by writing the channel/context identifier to a doorbell register," a write to a GPU register memory-mapped into the driver's address space (MMIO via PCIe).
  • The GPU's front-end responds: "the GPU PBDMA (pushbuffer DMA) engine fetches the newly enqueued GPFIFO entry" — the GPU pulls commands across the interconnect by DMA; the CPU never pushes.

This layout kills one belief outright: the GPU does not execute commands as the CPU writes them. Launches are asynchronous because everything up to the doorbell is just the CPU writing its own memory — everything after is the GPU's problem: PBDMA hands the fetched work to the front-end's queues, blocks land on SMs, and what happens there is chapter 6's story.

Documented vs. reverse-engineered

Pushbuffer, GPFIFO, doorbell, PBDMA: consistent across the open kernel driver's source and independent instrumentation, yet deliberately absent from the CUDA docs — and that absence is a feature. Your code binds to the documented contract (async enqueue into a stream) and keeps working if NVIDIA redesigns the submission path tomorrow. Treat the mechanism as an explanatory model — it turns "launches cost microseconds" from folklore into physics — not as an API. In this book, "documented" means in the manuals; everything else is labeled.

Step through all eight stations in the widget below — from Python's a + b at station one to the semaphore writeback at station eight, with the dispatcher, TensorIterator, launch-API validation, pushbuffer write, and doorbell in between. The rest of the chapter zooms into the costs of stations four through six, and the completion end of station eight.

What a launch costs

The docs admit a per-launch tax without pricing it: "These operations, necessary for setting up and launching the kernel, are an overhead cost which must be paid for each kernel." No official microsecond figure exists. Measurements fill the gap: the 2026 study clocks a minimal submission at 1.8–1.9 µs; NVIDIA's forums carry ~5 µs as the folklore number for back-to-back empty kernels; a 2019 ICPP poster splits that total into API, driver, and submission stages. Summary: roughly 1–10 µs of CPU time per launch, machine- and workload-dependent.

The number that explains the pain is not latency but serialization: one CPU core emitting commands at a measured 205–450 MiB/s. When each kernel runs for less time than its submission costs, that core saturates in driver code while the SMs idle between snacks — thousands of tiny kernels starve the GPU. The docs put it gently: "For a GPU kernel with a short execution time, this overhead cost can be a significant fraction of the overall end-to-end" time. The long book showed this symptom from Python; the cause lives here.

Streams and events, in three sentences

A stream "operates like a work-queue": launches and copies appended to it execute in order, because "An operation in a stream cannot leap-frog other operations." Every device has a default stream, and the legacy default stream (the NULL stream, ID 0) is special — it is a blocking stream that waits for all other blocking streams and is waited on by them. Since CUDA 7 you can instead opt into a per-thread default stream that "does not synchronize with other streams."

Cross-stream ordering needs events. cudaEventRecord() snapshots a stream's progress ("When an event reaches the front of a stream it records a timestamp"), and cudaStreamWaitEvent() on another stream makes all later commands "delay their execution until the given event has completed" — a dependency edge between queues. PyTorch leans on stream order for free correctness: "Each backward CUDA op runs on the same stream that was used for its corresponding forward op," so gradients accumulate race-free with no stream plumbing in autograd.

The mysterious serialization

Two streams that should overlap but mysteriously don't? Hunt for work on the default stream: "Two operations from different streams cannot run concurrently if any CUDA operation on the NULL stream is submitted in-between them." The legacy stream is a barrier in disguise — "the legacy stream first waits on all blocking streams, the action is queued in the legacy stream, and then all blocking streams wait on the legacy stream" — and one unqualified copy between your streams erases the overlap.

Completion: how the CPU ever finds out

Documented behavior first. cudaStreamSynchronize() "will block until all the work in the stream has completed"; cudaStreamQuery() returns ready-or-not; cudaDeviceSynchronize() drains every stream. How the waiting thread waits is a policy you select with the CU_CTX_SCHED_* flags: spin — "Instruct CUDA to actively spin when waiting for results from the GPU" (lowest latency, burns a core); yield — "yield its thread when waiting"; blocking sync — "block the CPU thread on a synchronization primitive"; plus an auto heuristic.

What the GPU does to end that wait is again undocumented but measured: completion is a semaphore writeback. The driver appends a semaphore-release command — optionally timestamped — to your work; when the GPU retires it, a value lands in memory and the host's synchronize spins or blocks on that location. No interrupt path is documented anywhere in CUDA — polling a memory location is the whole trick.

.item(), end to end

The long book called .item() "the await." Here is what it awaits, verified in the PyTorch source. Tensor.item() dispatches to the ATen op _local_scalar_dense; its CUDA implementation allocates a pinned CPU scalar — the source comment says why: "Create pinned memory for the scalar value to avoid implicit locking/sync in cuda library" — issues cudaMemcpyDeviceToHost on the current stream, then synchronizes the stream before reading the value:

loss.item()                          # Python asks for a float
 → _local_scalar_dense               # the ATen op behind .item()
   → allocate one pinned host scalar # "avoid implicit locking/sync"
   → cudaMemcpyDeviceToHost          # one scalar, on the current stream
   → synchronize the stream          # ← Python blocks here

NVIDIA's CUDA-graphs guidance says the same from the other side: "Using GPU tensor values in Python control flow (either through .item() or implicit .is_nonzero()) forces GPU→CPU sync to materialize the value." A print(loss) inside a training loop is a full stream drain per iteration — physics, not style.

CUDA graphs: pay the toll once

If the launch tax is CPU serialization, the cure is to pay it once. During capture, "work launched into the stream is not enqueued for execution" — it is "appended to an internal graph," cross-stream event dependencies included. On replay, per the PyTorch notes, "a replay submits the entire graph's work to the GPU with a single call to cudaGraphLaunch… eliding CPU overhead is the main benefit." In the submission-path picture — mechanism reverse-engineered, benefit documented — one traversal of stations four through six replaces a thousand cycles of pack, translate, emit.

One input in the signature above is still unexplained: where the CUfunction handle and its machine code come from. That is the compilers' story — chapter 5.

Carry this forward: a launch is CPU-packaged commands that the GPU fetches itself; when launches are many and small, the CPU is the bottleneck — batch, fuse, or graph them.

05 / PTX & SASS

PTX Is the Contract; SASS Is What Actually Runs

PyTorch's kernels ship as fatbins — SASS for the architectures nvcc knew, PTX for the ones it didn't. When neither matches, the driver JIT-compiles at first load, and torch.compile's Triton kernels replay the same last mile.

Chapter 4 followed a single launch from <<<>>> down to the hardware, quietly assuming the kernel's code was already sitting in VRAM as a loaded module. It was — because a compiler put it there, either years before you installed PyTorch or just in time, moments before your kernel ran. This chapter is about the formats those compilers produce, and the doors through which a kernel becomes executable bytes.

The formats form a ladder. CUDA C++ compiles to PTX, described by its own specification as "a low-level parallel thread execution virtual machine and instruction set architecture." Read that literally: PTX is assembly for a virtual GPU. It has virtual registers declared in bulk by name (%r1, %rd7) with no allocation limits, no scheduling, no memory-system detail — its design goal is to "provide a stable ISA that spans multiple GPU generations." SASS is what a specific GPU actually executes: native machine code with real registers, different for every architecture, produced from PTX by ptxas — the nvcc documentation calls it "the PTX optimizing assembler," and it is where register allocation and instruction scheduling actually happen. nvcc bundles some number of SASS cubins plus optional PTX into a fatbin — the format "may contain multiple PTX and CUBIN files" — and embeds it in the host library. That fatbin is the kernel code PyTorch ships.

Which architectures get cubins is decided at build time. TORCH_CUDA_ARCH_LIST (say "8.0;8.6+PTX") is parsed into one nvcc -gencode flag per entry; the +PTX suffix additionally embeds PTX, which the driver can runtime-compile for any GPU of higher compute capability. PyTorch's released builds embed SASS for a list of architectures plus PTX for the highest. Your install will tell you what it carries:

>>> torch.cuda.get_arch_list()
# → a list like ['sm_80', ..., 'compute_90'] — sm_XX = embedded SASS, one compute_XX = the PTX tail

That PTX tail is a forward-compatibility promise, and the driver redeems it. Module loading accepts PTX or cubin, and "embedded PTX code is dynamically compiled by the CUDA runtime system if no binary load image is found for the current GPU." That is driver JIT: at cuModuleLoad, libcuda itself compiles the PTX to SASS for the GPU in the machine. Real compilation takes real time — which leads to a classic gotcha.

"Why is the first run slow?"

Run a fresh PyTorch build on a GPU newer than its newest embedded SASS, and the first CUDA op stalls while the driver JIT-compiles PTX for that architecture. The results are cached on disk — default size 1 GiB, maximum 4 GiB, under ~/.nv/ComputeCache — so the cost is paid once per kernel per machine, not once per process. The same first-run lag appears, for a different reason, with torch.compile: Triton kernels are compiled on first call (below).

Two runtime compilers matter to PyTorch users, and their jobs are routinely swapped in retellings. torch.utils.cpp_extension.load_inline — the feature everyone calls "PyTorch's JIT" — does not use NVRTC at all: it shells out to nvcc through ninja, which is exactly why it demands a full CUDA toolkit install. The actual in-PyTorch user of NVRTC — "a runtime compilation library for CUDA C++" that takes source as a string, spawns no compiler process, needs no toolkit, and can emit PTX or cubin — is the JIterator: for certain complex pointwise ops it compiles a functor string through a lazily dlopened libnvrtc.so, loads the result with cuModuleLoadData, and caches it in-process, keyed by source, vectorization width, and device.

torch.compile's kernels come from Triton, whose pipeline is longer because it starts from Python. The verified stage list: Python traces lower to Triton IR (TTIR), get shaped for the GPU (TTGIR), lower to LLVM IR (LLIR), then to PTX — and from there take the same last mile as everyone else: the external ptxas produces a cubin, cuModuleLoadData loads it, cuLaunchKernelEx launches it. The door chapter 4 dissected is the same door. Why compile at all? The tutorial's own phrasing: the speedup "mainly comes from reducing Python overhead and GPU read/writes." Fusion is the second half of that sentence — one Triton kernel replaces a chain of elementwise ops, so intermediates stay in registers instead of round-tripping through HBM — the GPU's high-bandwidth DRAM (a trip chapter 6 prices at ~600 cycles), and the Python and dispatch machinery runs once per fused region, not once per op.

The widget above walks the ladder interactively; here is the static version. Below is the same one-element-per-thread add kernel at the two bottom rungs. Both are representative and simplified — exact SASS varies by architecture and ptxas version; generate your own with nvcc -ptx and cuobjdump -sass.

// PTX — representative, simplified:
.visible .entry addf(.param .u64 A, .param .u64 B, .param .u64 C, .param .u32 N) {
  .reg .b32 %r<4>; .reg .b64 %rd<7>; .reg .f32 %f<2>; .reg .pred %p1; // virtual registers, declared in bulk
  ld.param.u64 %rd1,[A]; ld.param.u64 %rd2,[B]; ld.param.u64 %rd3,[C]; ld.param.u32 %r1,[N];
  mad.lo.s32 %r4, %ctaid.x, %ntid.x, %tid.x;   // i = blockIdx.x*blockDim.x + threadIdx.x — ch3's index math
  setp.ge.s32 %p1, %r4, %r1;  @%p1 bra DONE;   // if (i >= N) skip the body
  cvta.to.global.u64 %rd4,%rd1; cvta.to.global.u64 %rd5,%rd2; cvta.to.global.u64 %rd6,%rd3;
  mul.wide.s32 %rd7, %r4, 4;                   // byte offset = 4*i
  ld.global.f32 %f1,[%rd4+%rd7]; ld.global.f32 %f2,[%rd5+%rd7]; add.f32 %f1,%f1,%f2; // load, load, add
  st.global.f32 [%rd6+%rd7], %f1;
DONE: ret;
}
// SASS — representative shape, NOT a dump; varies by arch & ptxas version:
        IMAD.MOV.U32 R1, RZ, RZ, c[0x0][0x178]  ; // param/const setup (representative)
        S2R R0, SR_CTAID.X ; S2R R1, SR_TID.X    ; // special registers -> scalars
        IMAD.S32.U32 R2, R0, 0x80, R1            ; // i = ctaid*128 + tid: index math folded into one multiply-add
        LDG.E.128.CONSTANT R4, [R2.64+0x0]       ; // 128-bit load: ONE instruction, 16 bytes — float4 made real
        LDG.E.128.CONSTANT R8, [R3.64+0x0]       ; // PyTorch's vectorized kernel; a scalar kernel shows LDG.E
        FFMA/FADD R0, R4, R8, RZ ; STG.E.128 [R6.64+0x0], R0 ;
        EXIT ;

What to notice. In the PTX: the .reg line simply claims virtual registers by name — no counts against a budget, no assignment to hardware — and instructions sit in program order; nothing says which functional unit runs them or when. In the SASS: real register names (R2, R4), the multiply and add for the thread index collapsed into a single IMAD, and — the shape of chapter 3's vectorized policy — LDG.E.128, one instruction moving a 16-byte float4. The lowering filled in everything the virtual machine left open.

"The GPU executes PTX."

False. Nothing executes PTX. SMs run SASS only; every bit of PTX gets there through ptxas at build time or the driver's JIT at load time. PTX is not an execution format — it is the compatibility contract that lets one PyTorch wheel span GPU generations it was never compiled for.

Carry this forward: a fatbin is SASS for known architectures plus PTX as the forward-compatibility promise, and every kernel becomes SASS — via nvcc's ptxas or the driver's JIT — before anything runs it.

06 / ON THE GPU

The Warp Is the Machine

Blocks land on SMs and are sliced into 32-lane warps — the warp, not your thread, is what executes. A contiguous warp buys memory in 32-byte sectors; a strided one pays for bytes it never reads.

Chapter 5 left our add kernel as SASS inside a loaded module; chapter 4 showed its launch becoming commands the GPU fetches. Now the hardware acts on them. The grid PyTorch computed — ceil(N/1,024) blocks of 128 threads — is distributed across the chip's streaming multiprocessors (SMs), the compute units the cast met in chapter 1. The Programming Guide describes the handoff: "When an SM is given one or more thread blocks to execute, it partitions them into warps and each warp gets scheduled ... by a warp scheduler," with each warp's execution context — registers, program counter — kept on-chip for the warp's lifetime. That scheduling model also implies a locality rule every CUDA programmer relies on: a block runs on the SM that received it and never straddles two.

The partitioning is not a scheduling decision; it is the hardware. Threads are "organized into groups of 32 threads called warps," and "All threads in the warp execute the same instruction simultaneously." That is SIMT — single instruction, multiple threads — and it means the warp, not your thread, is the unit of execution: one program counter per warp, one instruction issued on behalf of 32 lanes. Each of an SM's several warp schedulers "selects a warp with threads ready to execute its next instruction" and issues — roughly one instruction per cycle, per scheduler. If lanes disagree on a data-dependent branch, "the warp executes each branch path taken, disabling threads that are not on that path": the paths run one after the other, so divergence costs serialization (compute capability 7.0 added Independent Thread Scheduling — per-thread program counters that let warps diverge and reconverge at sub-warp granularity — but a branch taken both ways still executes both). Our add has exactly one branch, the idx < N guard, so at most the last, partial warp in the grid ever diverges — a rounding error of a cost.

Divergence is usually not the villain

The Best Practices guide's own caveat: divergence cost is often marginal, because warps are scheduled independently — one warp's branch costs another warp nothing — and predication can eliminate short branches entirely, turning them into instructions every lane executes with some results discarded. The pathological cases are long, load-heavy paths diverging inside a hot loop, not the boundary guard on a final block.

A warp's state lives in the SM's register file — "Each SM has a set of 32-bit registers that are partitioned among the warps" — and that is why switching between resident warps is nearly free: the registers are already on-chip, held per warp for its whole life, so a scheduler can ping-pong between warps without saving or restoring anything. The budget is finite, though. A kernel that wants more registers per thread than it can get spills the excess to local memory — which despite the name is device DRAM, cached through L1/L2, sitting at the slow end of the ladder below. Register pressure is the quiet reason a kernel with plenty of parallelism can still run slowly.

Now run our kernel. Block b, thread t: chapter 3's vectorized policy gives each thread two float4 slots — slot i covers elements 1,024·b + 4·(t + 128·i) through +3 — and the body is two rounds of load, load, add, store on 16 bytes each. Zoom in on one warp of that block, slot 0: lanes 0–31 issue a single LDG.E.128 (the instruction from chapter 5's SASS) whose 32 addresses are consecutive 16-byte chunks — 4 × 128 B = 512 contiguous bytes, fetched by one instruction. The legacy scalar kernel from chapter 3 does the same job with idx = 128·vt·blockIdx.x + threadIdx.x and 4-byte loads; either way, the mapping is the one TensorIterator planned on the CPU.

What the memory system does with that instruction is the most consequential rule in this book. Global loads and stores by a warp are "coalesced ... into as few as possible transactions," and since compute capability 6.0 the granularity is the 32-byte sector. A warp loading 32 consecutive 4-byte words touches exactly 128 bytes — 4 × 32-byte sectors, four transactions, zero wasted bytes. Our float4 warp touches 512 bytes = 16 sectors, every one fully used. Contiguity is the whole trick, and it is precisely what TensorIterator's reorder and coalesce steps, and PyTorch's contiguous-first layouts, were buying. Break it — stride the same warp by 8 elements — and each lane's word lands in its own sector: 32 transactions moving 1,024 bytes to deliver the 128 requested, an 8× collapse in efficiency.

What a transaction costs, in cycles — microbenchmark approximations from a Hopper-architecture study (arXiv:2501.12084; treat as order-of-magnitude, chip-dependent):

leveltypical latencywhat it is
registersno round tripthe warp's own on-chip context
shared memory / L1~30 cyclesper-SM SRAM — scratchpad + cache
L2~200–500 cyclesdevice-wide cache shared by all SMs
HBM (global memory)~600 cycleswhere the tensors themselves live

Put issue rates next to that. A scheduler issues roughly one instruction per cycle, so a single ~600-cycle HBM round trip is ~600 issue slots — enough to hand each of 32 resident warps about 20 instructions while the stalling warp waits. One miss to DRAM pays for a great deal of arithmetic; the FADD it was fetching operands for costs a rounding error next to it. That is why latency hiding, not raw ALU speed, is the GPU's whole game: keep enough warps resident that whenever one stalls on memory, another is ready to issue. The SM is not fast because its arithmetic is exotic — it is fast because it is never caught waiting.

Our add kernel is the poster child. Per element it moves 12 bytes — 4 in from a, 4 in from b, 4 out — and performs one FADD. That arithmetic intensity is so low the kernel is pure memory bandwidth: the SM could issue all of a block's adds in a handful of cycles, then wait hundreds for the loads. Which is exactly what the hardware design absorbs: with 977 blocks for our million-element add, an SM hosting even 8 of them has 32 warps of independent work to rotate through while any one warp sits on an HBM stall. Elementwise kernels saturate memory not by being clever but by never running out of warps that are ready.

At the fast end of the ladder sits shared memory, with a misconception attached: it is not a cache. Shared memory is a software-managed scratchpad — you declare it (__shared__), you index it, it is addressable and private to a block — while the hardware cache occupying the same physical SRAM is L1, with a configurable carveout dividing the two. A cache decides what it holds; shared memory holds exactly what you put into it. That explicitness is the point: shared memory is how you stage a tile of data that many threads reuse, the trick behind every fast matmul — a proper treatment of tiling is its own book, and the shelf's How CUDA Works does it justice. Our add has no reuse and needs no scratchpad; it lives or dies by coalescing alone.

All of this turns "more threads are always faster" on its head. Occupancy is "the ratio of the number of active warps per multiprocessor to the maximum number of possible active warps" — 64 warps per SM on Hopper, so 32 resident warps is half occupancy. Occupancy is a means, not a KPI: you need enough resident warps to hide the ~30-to-600-cycle stalls above, and the Best Practices guide is explicit that beyond the level that hides latency, more occupancy can hurt — it means fewer registers and less instruction-level parallelism per thread. A memory-bound elementwise kernel at modest occupancy with perfectly coalesced access beats a register-starved one at 100%.

So the trip our op started in chapter 3 ends here: every block retires — 1,024 elements per block loaded, added, stored — and what the kernel leaves behind is bytes in HBM plus, by chapter 4's mechanism, a completion signal written back for the host to find. The numbers are out of VRAM and the semaphore writeback is next — chapter 7 moves the data, chapter 8 replays the whole trip.

Carry this forward: warps of 32 — not threads — execute; contiguous access buys 4 sectors where strided buys 32; and ~600-cycle memory latency is why hiding stalls matters more than ALU speed.

07 / DATA

Three Roads Across the Bus

Chapter 6's kernels compute on bytes already in VRAM — but every tensor was born in host RAM. Which road the bytes take to cross decides most of your data pipeline's speed.

Chapter 6 followed a kernel onto the SMs, assuming its data was already there. It was — because something moved it. Every batch begins as ordinary CPU memory coming out of a DataLoader, and the crossing is governed by one question this chapter answers three ways: where were those bytes allocated? First, the road itself.

A PCIe 4.0 x16 link moves ≈31.5 GB/s per direction; PCIe 5.0 x16 doubles that to ≈63 GB/s (line-rate arithmetic after 128b/130b encoding — spec math, not promises). NVLink plays another sport: NVLink 4 on H100/H200 provides 900 GB/s total bidirectional (450 GB/s per direction across 18 links), and NVLink 5 on Blackwell reaches 1.8 TB/s, per NVIDIA's own pages. For scale, an H100's HBM serves ≈3.35 TB/s (the SXM datasheet figure) and measured transfers land below line rate — but the ordering holds: the interconnect is the narrowest pipe in an otherwise bandwidth-soaked machine.

The bytes are usually moved by dedicated hardware, not the SMs. Copy engines are DMA units dedicated to transfers: while SMs run kernels, copy engines run copies. "The number of copy engines on a GPU is given by the asyncEngineCount field of the cudaDeviceProp" — with one engine a GPU overlaps a single async transfer with kernels, with two it can run one host-to-device and one device-to-host simultaneously. (Terminology caveat: "copy engine" is official-but-archived vocabulary from the Best Practices guide; the restructured current guide no longer uses it.) One reverse-engineered footnote: instrumentation found that tiny copies — under ~24 KiB on the tested GPU — can be inlined into the pushbuffer for the compute engine instead; routing is size- and driver-dependent, and undocumented.

For host-to-device transfers there are exactly three paths, decided by the allocation:

Pageable memory — anything from malloc or new — cannot be DMA'd, period. Mark Harris's canonical explanation: "The GPU cannot access data directly from pageable host memory, so when a data transfer from pageable host memory to device memory is invoked, the CUDA driver must first allocate a temporary page-locked, or 'pinned,' host array, copy the host data to the pinned array, and then transfer the data from the pinned array to device memory." Two copies — your bytes cross the CPU's memory controller twice — and the async API quietly gives up: cudaMemcpyAsync "will function correctly if host memory which is not pinned and page-locked is used, but it will revert to a synchronous behavior."

Pinned memory removes the staging: allocate with cudaMallocHost/cudaHostAlloc (or cudaHostRegister an existing range) and the copy engine DMAs straight from your buffer. "Page-locked host memory is required for asynchronous copies" and "also improves performance of synchronous copies." The gap is not subtle: Harris's classic measurements on one PCIe Gen2 card had pageable transfers crawl at 2.3 GB/s where pinned reached 5.8 GB/s — more than 2× for one allocation call. This is exactly what PyTorch's notes ask for: "Host to GPU copies are much faster when they originate from pinned (page-locked) memory… once you pin a tensor or storage, you can use asynchronous GPU copies. Just pass an additional non_blocking=True argument."

>>> loader = DataLoader(ds, batch_size=32, pin_memory=True)
>>> x = batch.to('cuda', non_blocking=True)  # pinned → direct DMA, overlaps compute

One reassurance from the same notes: "PyTorch automatically performs necessary synchronization when copying data between CPU and GPU or between two GPUs" — non_blocking changes the overlap, never the correctness.

Mapped memory takes pinning to its conclusion: the buffer stays in host RAM and the GPU dereferences it directly over the interconnect — no copy, historically called "zero-copy." Unified memory goes the other way: managed allocations live in "a single virtual address space" spanning host and device and migrate at page or cache-line granularity when the other processor touches them.

Pinned memory is a limited resource

Pinning locks physical pages — the OS can no longer swap or move them — so over-allocating pinned memory degrades the whole machine, not just your process. Pin the steady pipeline (the DataLoader's staging buffers), not every tensor you own.

PyTorch keeps asking you to pin and batch because per-transfer overhead is roughly fixed, so throughput is bytes-per-transfer: one pinned, batched copy of a 32-sample stack amortizes that fixed cost and keeps the copy engine fed, where 32 small pageable copies pay staging, serialization, and latency 32 times. The long book covered the queuing view — copies overlapping compute on separate streams; this chapter added the road surface under it.

Chapter 8 assembles the full journey — dispatch, launch, execution, and one of these three crossings — into a single numbered trace of y = a + b.

Carry this forward: pageable pays twice, pinned pays once, mapped pays every access — pick the road per use, and keep the transfers big.

One Op, Twelve Beats, Zero Gaps

y = a + b on two CUDA float tensors with requires_grad=True — every previous chapter, played once, in order, from __add__ to the semaphore writeback nobody is waiting for.

Chapter 7 closed the tour at the bus; this chapter runs the whole distance without stopping. The cast: a and b are 2²²-element (4,194,304-element) contiguous float tensors on one GPU, both with requires_grad=True, and Python evaluates y = a + b. Nothing below is new — each beat cites the chapter that earned it. Read for where the GPU actually is.

  1. Python — a + b calls Tensor.__add__; the op underneath is add.Tensor. PyTorch the deciding client (ch1).
  2. Binding — argument parsing and default-filling in C++, then the GIL is released for the numeric work (the long book).
  3. Key computation — union of both key sets, plus TLS include, minus TLS exclude; AutocastCUDA dies (excluded by default), and the highest surviving bit pairs AutogradFunctionality with CUDABit (ch2).
  4. Autograd wrapper — the AutogradCUDA kernel records AddBackward0 on y (nothing to save — gradients pass through) and redispatches below ADInplaceOrView (ch2).
  5. TensorIterator — same shape, nothing to broadcast; the contiguous vectorized path: 128 threads per block, float4 (vec 4), 8 elements per thread → 1,024 elements per block, grid = ceil(4,194,304 / 1,024) = 4,096 blocks (ch3).
  6. Launch API — the call bottoms out in cuLaunchKernel: validate, resolve the function handle, pack three pointers plus N into one contiguous parameter buffer (ch4).
  7. Driver — libcuda writes command words into the pushbuffer ring in pinned host memory and rings the doorbell; the GPU's front-end fetches the commands itself [3P] (ch4).
  8. Code — the SASS for the vectorized add kernel is already resident: nvcc compiled it at build time, the fatbin loaded at import. No JIT on this path (ch5).
  9. Execution — 4,096 blocks spread across SMs; each block runs as 4 warps of 32; a warp's float4 load touches 512 contiguous bytes — fully coalesced (ch6).
  10. Results — the sums retire through L2 into HBM; y's bytes sit in VRAM (ch6).
  11. Writeback — the GPU appends a semaphore release; a completion value lands in host-visible memory [3P] (ch4).
  12. Nobody waits — Python got y's handle the moment the launch call returned, at beat 7, and never waited; the first true block is a sync, and .item() forces exactly that: a D2H copy plus a stream drain (ch4).

[3P] marks the reverse-engineered beats — consistent across NVIDIA's open kernel driver and independent instrumentation, absent from the official manuals; chapter 4 keeps the ledger. The shape to notice: beats 1–7 are CPU-side packaging, beat 8 was finished at build time, and only 9–11 touch silicon. The per-op CPU tax spans beats 3–7 — the launch toll proper is beats 6–7 — paid again for every op in your model.

That is precisely what torch.compile attacks. Inductor traces a region, fuses elementwise chains into one Triton kernel (compiled once at first run: Triton IR → LLVM → PTX → ptxas → cubin), and replays it thereafter. For a fused a + b * c, beats 1–7 happen once for the whole chain instead of per op, and the GPU makes one pass over the inputs rather than writing and re-reading an intermediate — the tutorial's own phrasing is that the gains come "mainly from reducing Python overhead and GPU read/writes."

Carry this forward: an op is twelve beats, seven of them CPU-side packaging — fuse, batch, and graph are all ways of deleting beats, not shrinking them.
