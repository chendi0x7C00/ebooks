01 / Problem Statement

##问题定义：一个带 SLO 约束的吞吐最大化问题

LLM 推理的两次"性格分裂"是整篇论文的地基：Prefill 是 compute-bound，Decoding 是 memory-bound。把它俩塞进同一个实例，是大多数调度痛苦的来源。

两个阶段的计算特征

  • Prefill（预填充）：一次性并行处理全部输入 token，生成第一个输出 token 并写入 KVCache。Attention 计算量随输入长度超线性增长（O(n²)），属于 compute-bound。它的 SLO 指标是 TTFT（Time To First Token）。
  • Decoding（解码）：自回归地逐 token 生成，每步只算 1 个 token、却要读全部 KVCache，属于 memory-bandwidth-bound。计算时间随 batch size 亚线性增长——这正是 continuous batching 有效的原因。它的 SLO 指标是 TBT（Time Between Tokens）。

优化目标 vs 约束——矛盾在哪里

提升吞吐有两条经典路径，但每一条都会咬到延迟 SLO：

  • 复用 KVCache 省算力 → 但缓存若在远端/低速存储，加载会拉长 TTFT；
  • 加大 decoding batch 提升 MFU → 但 batch 越大 TBT 越高，且受 VRAM 中 KVCache 总容量限制。

于是问题形式化为：max 有效吞吐（goodput），s.t. TTFT/TBT 的 P90 SLO。论文对 goodput 的定义比前人更苛刻——只有完整跑完的请求才计入；中途被丢弃的请求，已消耗的算力全部记为浪费。这个定义直接催生了第 7 节的"早拒绝"机制。

▶ 跑一遍 · 一个平均请求的 SLO 账本
1取 trace 中的平均请求：input 8,590 tokens / output 182 tokens（真实分布的均值）
2假设单节点空载 prefill 速率 4,000 tok/s（示例值）→ 空载 TTFT ≈ 8,590 ÷ 4,000 ≈ 2.1s
3假设空载 TBT = 20ms → 生成 182 tokens ≈ 3.6s，期间每步都要读完整 KVCache
4按论文实验的 SLO 定义（P90 = 空载的 10× / 5×）→ 线上允许 TTFT ≤ 21s、TBT ≤ 100ms
5调度器的全部工作 = 在这个余量空间里做权衡：多用 1s 加载远端缓存换 1.5s 少算，值不值？——这就是第 6 节 D4 算法每天回答的问题
工程师视角 · 为什么这篇论文值得读

大多数 serving 论文假设资源充足、优化利用率；Mooncake 假设的是长期过载——GPU 供给受限、请求量指数增长、无法弹性扩容。它回答的不是"怎么跑得更快"，而是"资源永远不够时，怎么把每一块 GPU 的有效产出榨干，同时不违反 SLO"。这是生产系统和论文玩具的分水岭。

02 / High-Level Design

##架构总览：三种资源池 + 一个调度器

Mooncake 把 GPU 一体机（HGX/DGX 式节点）拆开重组为三个逻辑资源池：Prefill 池、Decoding 池、以及横跨所有节点的分布式 KVCache 池。调度中枢 Conductor 以 KVCache 的分布为核心状态做全局决策。

读图要点

  • 解耦的不只是计算，还有状态。P/D 分离在很多论文里都有（Splitwise、DistServe、TetriInfer），Mooncake 的增量在于把 KVCache 本身也池化——利用 GPU 节点上大量闲置的 CPU、DRAM、SSD，组成一个"不要钱"的分布式缓存层。
  • 控制面与数据面分离。Conductor 只做决策（选实例、复制/换出缓存、拒绝请求），搬数据的是每节点上的 Messenger 进程（GPUDirect RDMA）。
  • 两个池的优化目标相反，这决定了它们各自的本地调度器、并行策略、资源约束都不同——这正是坚持解耦的论据（见决策 D1）。

03 / Request Lifecycle

##一个请求的四步旅程

Conductor 为每个请求选一对 prefill / decoding 实例，然后按以下流水线执行。点击每一步查看工程细节。

关键工程细节

第 3 步与第 2 步是异步重叠的：prefill 每算完一层，该层的 KVCache 立刻经 Messenger 流式发往 decoding 节点的 DRAM，而不是等全部算完再搬。同理，decoding 侧在 GPU 解码的同时异步把下一批请求的 KVCache 从 DRAM 载入 VRAM。整条流水线上没有"纯搬运"的等待段。

▶ 跑一遍 · 同一份 128K 财报，首问 vs 追问
1用户上传一份 128K tokens 的财报，首次提问「去年毛利率多少？」——哈希链匹配 0 blocks，全量 prefill
2Conductor 选 2 节点 CPP 组：输入切 8 chunks × 16K，两节点流水并行，prefill 时间 ≈ 单节点的 1/2 + 少量流水线填充（见 D2 时间线图）
3每层 KVCache 算完即经 RDMA 流往 decoding 节点；最后一个 chunk 算完时，前面的 KVCache 早已到齐——传输被完全藏住
4增量 KVCache（128K tokens × 全部层）同时写回分布式缓存池，本次会话的 hash 块登记进全局索引
5一分钟后用户追问「那净利率呢？」——新输入 ≈ 128K + 20 tokens，前缀命中 ≈250 blocks（全部历史），只需增量 prefill 约 20 个 token：TTFT 从十几秒降到 亚秒级

05 / The Cache Layer

##KVCache 池：前缀哈希链 + 分页块存储

缓存层的核心数据结构是一条哈希链：每个块的 key 由"自身内容 + 前驱块的哈希"共同决定。这让前缀匹配变成了逐块的 key 比较，同时天然支持全局去重。

▶ 跑一遍 · 两条真实 trace 的前缀共享（论文 Listing 1 原样数据）

2请求 B：input_length = 6,472 → 13 个块，hash_ids = [46…57, 2366]
3逐块比对：前 12 个 ID 完全相同 → 前缀共享 12 × 512 = 6,144 tokens（同一篇长文档的两轮提问）
4B 只需增量 prefill 6,472 − 6,144 = 328 tokens，省掉约 95% 的 prefill 计算——TTFT 几乎只剩排队时间

06 / Design Choices

##六个关键设计决策

每张卡片按同一结构拆解：决策问题 → 被否决的备选方案 → 选择理由 → 付出的代价。这是论文里最有工程含金量的部分。

D1

坚持 P/D 解耦，而不是 chunk 内联进 decoding batch

问题：有了 chunked prefill（SARATHI 路线），还有必要把 prefill 拆出去吗？统一池调度更简单、还能提高 decoding batch 的计算强度。

Mooncake 的答案：拆，但留一个例外——只有当请求无需切 chunk、且不破坏 TBT SLO 时，才允许把它的 prefill 内联进 decoding batch。其余全部走独立 prefill 池。

被否决的方案
  • 全量 chunked prefill 内联（SARATHI / vLLM 式统一调度）：所有节点同构，调度最简单
为什么解耦
  • Prefill 需要不同的跨节点并行设置来压长上下文的 TTFT（见 D2），与 decoding 节点同构等于放弃这个自由度
  • 独立 prefill 池带来一个独特机会：省 VRAM（见 D3），让 prefill 调度可以无视 VRAM 容量
代价 / 权衡
  • 多了一次跨节点 KVCache 传输，依赖 RDMA 网络质量
  • Prefill / decoding 实例比例需预设，失衡时吞吐受损（实验里 2P+2D 的 TTFT 反而不如 3P+1D）
D2

长上下文并行：Chunked Pipeline Parallelism（CPP），而非 SP

问题：128K~1M 上下文的 prefill 想用多节点并行压 TTFT，选哪种并行策略？

做法：把 prefill 集群每 X 个节点组成一个流水线组，单请求的输入按 prefill_chunk（通常 >1000 tokens）切块，同一请求的不同 chunk 由不同节点同时处理，靠逐层流式传输衔接自回归依赖。据作者所知，这是 token 级流水线并行首次用于推理（此前只出现在训练系统如 TeraPipe）。

被否决的方案
  • 跨节点 TP：每层两次 RDMA all-reduce，MFU 骤降
  • Sequence Parallelism（Ring/Striped Attention）：每层至少一次跨节点通信，MFU 仍低于单节点 TP，且与 KVCache 传输抢网络
  • 弹性 SP（LoongServe）：需预建全局通信组 + 动态伸缩节点组，Conductor 调度复杂度爆炸
为什么 CPP
  • 跨节点通信只发生在 chunk 边界，可与计算重叠——MFU 更高，不与 KVCache 传输争网
  • 长短上下文通吃：短请求单节点即可，无需弹性调整节点分组，部署形态静态
代价 / 权衡
  • 流水线组内存在 bubble（论文未展开量化）
  • 调度器要同时管"节点组"和"单节点"两种 prefill 形态
D3

Layer-wise Prefill：逐层异步 load/store，把传输藏进计算

问题：长上下文请求的 KVCache 巨大（S），处理时间长（T），驻留 VRAM 的占用成本是 S×T。怎么把这笔账降下来？

做法：prefill 本来就是逐层计算且 compute-bound，于是每层 attention 开始前等待该层 KVCache 异步加载完成、同时触发下一层的异步加载；该层算完立即异步写回 DRAM。全部用 launch/wait 原语实现。

收益
  • prefill 执行时间 ≈ max(计算时间, KVCache 加载时间)，传输基本被藏住
  • prefill 调度从此可以无视 VRAM 容量——只要能装下单个请求即可，调度只看缓存分布和 DRAM
  • 长上下文存储延迟显著下降（论文 Figure 7，128K 时 layer-wise 优势最大）
代价 / 权衡
  • 实现复杂度：每层都要穿插异步 IO 的 launch/wait 编排
  • 对 RDMA 带宽有硬要求（实验节点 800 Gbps 互联）
D4

Cache-aware 全局调度：以 TTFT 估计为准绳选 prefill 实例

问题：选"缓存命中最长的实例"还是"负载最轻的实例"？两个目标经常冲突。

答案：都不直接选——把两者统一折算成 TTFT 估计值（排队时间 + prefill 执行时间 [+ 缓存迁移时间]），选 TTFT 最短的。若估计值违反 SLO，直接返回 429。

// Algorithm 1 — KVCache-centric Scheduling（论文伪代码的精简注释版）
block_keys ← PrefixHash(R.prompt_tokens, B)
(best_len, best_node) ← FindBestPrefixMatch(P, block_keys)

for instance in P:
    T_queue   ← EstimatePrefillQueueTime(instance)          // 队列中所有请求的 prefill 时间求和
    if (best_len − instance.prefix_len) < kvcache_balancing_threshold:
        T_total ← T_queue + EstimatePrefillExecTime(len, instance.prefix_len)
    else:                                  // 缓存差距大：宁可迁移热点缓存
        T_total ← EstimateTransferTime(instance←best_node) + T_queue
                + EstimatePrefillExecTime(len, best_len)
    保留 T_total 最小的 instance → p

d ← SelectDecodingInstance(D)             // 纯负载均衡
if TTFT > TTFT_SLO or TBT > TBT_SLO: reject R  // → HTTP 429
if best_len − p.prefix_len > threshold: TransferKVCache(best_node → p)  // 热点迁移

P112 blocks（6,144 tok）1.20s3,856 tok ÷ 2,000 tok/s = 1.93s—3.13s

P2 与最优缓存（P1 的 12 blocks）差距 6 blocks，超过 kvcache_balancing_threshold → 走迁移分支：把 P1 的热点缓存复制到 P2。一次调度同时完成了"选最快实例"和"热点块自动扩散"两件事——D5 的启发式就是这样搭 D4 便车的。

工程要点
  • Prefill 时间用离线数据拟合的预测模型估计——Transformer 计算模式规整，误差界很小
  • 所有实例的 TTFT 并行计算，调度开销相对推理可忽略
  • 难点在传输时间估计：取决于数据量 + 发送端网络是否拥塞
代价 / 权衡
  • kvcache_balancing_threshold 目前是人工调参（作者承认，留作自适应化的 future work）
  • vLLM 开源版只有本地 KVCache 缓存，这套是全局缓存视角的调度
D5

缓存负载均衡：启发式热点迁移，而非用量预测

问题：要不要收集全局块用量、建模预测未来热度，再做复制/换出？

答案：不。对快速增长的服务，负载高度动态，精确预测未来用量不现实。改用启发式：当请求因负载原因没路由到"命中最长"的实例时，若估计的额外 prefill 时间 > 传输时间，就把缓存位置转发给备选实例、由它主动拉取并本地留存——热点块被访问得越多，就自然被复制得越广，无需任何预测模型。

为什么优雅
  • 复制行为是请求的副产品，零额外控制循环
  • 与 D4 的调度算法共用同一套时间估计，没有第二套模型要维护
  • 实测（8P+8D 集群回放 2.3 万真实请求）：平均 TTFT 从负载均衡调度的 60.41s 压到 6.26s
代价 / 权衡
  • 启发式不保证全局最优，理论上存在震荡复制的边界场景
  • "宁可重算也不搬缓存"的分支依赖同一个阈值参数
D6

Messenger：独立进程 + GPUDirect RDMA 的传输层

问题：KVCache 在 GPU/CPU/跨机之间怎么搬，才能不干扰推理主循环？

做法：每个节点跑一个独立的 Messenger 进程，接收信号后执行 GPUDirect RDMA 传输。推理进程只管发信号，搬运完全旁路。这套架构还顺带让 Mooncake 能对外提供 context caching API（用户显式复用 KVCache，类似后来的 commercial context caching 产品）。

收益
  • 传输与计算进程隔离，故障域清晰，可独立升级
  • GPUDirect 绕过 CPU 拷贝，GPU↔远端内存直通
代价 / 权衡
  • 对 RDMA 网络（800 Gbps 级）是硬性依赖，普通云网络难以复现同等效果

07 / Overload-oriented Scheduling

##过载调度：早拒绝，以及它引发的震荡

这是全文最"生产系统"的一章：当请求量永远大于供给，调度器的核心动作从"排得好"变成"拒得早、拒得准"。但朴素的早拒绝会让集群负载像失控的反馈回路一样震荡。

三个递进的策略

  • 基线：prefill 完成后再由 decoding 端按负载拒收 → prefill 算力白烧（论文 goodput 定义下的纯浪费）。
  • Early Rejection：请求到达时，Conductor 取 prefill 池与 decoding 池负载的较大者决定是否接受，把 decoding 的负载评估提前到 prefill 开始之前。
  • 基于预测的 Early Rejection：不用"当前" decoding 负载，而用预测的"prefill 完成后那一刻"的 decoding 负载来决策。

解药：系统级负载预测

精确的 request-level 预测（预测每个请求的输出长度）成本高、准确率低，过载时尤其不可靠。Mooncake 选择更粗糙但稳健的 system-level 预测：

  1. 假设每个请求的 decoding 阶段耗时统一为 td；
  2. 对目标时刻 t：把 t 前能完成 prefill 的请求加进 decoding 实例，把执行时间将超过 td 的请求移除；
  3. 统计所有 decoding 实例的平均 TBT 与 l_tbt 的比值，作为 t 时刻的预测负载。
▶ 跑一遍 · t+8s 的 decoding 负载预测（示例数值）
1设定：统一解码时长 td = 10s；某 decoding 实例容量 50 个并发请求，当前在跑 40 个
2新请求 R 到达，prefill 预计耗时 8s → 需要回答：t+8s 时 decoding 池还塞得下吗？
3加：prefill 池排队中的请求里，15 个会在 t+8s 前完成 prefill → 加入 decoding
4减：在跑的 40 个里，18 个到那时已运行超过 td → 移除
5预测负载 = (40 − 18 + 15) ÷ 50 = 74% → 平均 TBT 比值 < 1 → 放行 R。若算出 110% → 直接 429，R 不消耗任何 GPU

效果（2 倍速回放真实 trace、8P+8D 集群）：基线拒绝 4,183 个请求 → 朴素早拒绝 3,771 → 预测式早拒绝 3,589。拒绝数下降意味着更少算力浪费和更高的集群承载上限。

工程师视角 · 这是控制理论问题

把 Conductor 看成一个控制器：朴素早拒绝 = 用滞后一个环节的测量值做反馈控制，必然震荡（相位裕度不足）。预测式早拒绝相当于加了前馈环节——用模型预估未来状态再决策。如果你在自己的系统里见过"限流阀值导致流量锯齿"，病根一模一样。

09 / Critical Reading & Takeaways

##批判性阅读：这套架构的边界在哪

论文自己承认或未解的问题

  • P/D 比例是静态预设的。实验里 2P+2D 因两池负载失衡 TTFT 反而变差；论文把"动态转换 prefill/decoding 实例"留作 future work。比例选错，解耦反而放大浪费。
  • 阈值靠手调。kvcache_balancing_threshold（搬缓存还是重算的分界）目前人工调整。
  • decoding 端二次校验仍可能拒收：prefill 完成后 decoding 负载可能已变化，本地调度器再查一次 TBT SLO，拒收则 prefill 算力浪费——早拒绝只是降低了概率，没有消除。
  • 复用率天花板：真实负载下即使容量无限、TTFT 约束无限宽松，理论复用率也只有 55%（特定场景如 papers.cool 可达 90%）。缓存不是银弹，收益高度依赖业务形态。
  • 硬件门槛：整套设计依赖 800 Gbps RDMA 互联和节点上大量闲置 DRAM/SSD；没有这张网，逐层流式传输的收益兑现不了。

如果你在做 serving 系统，可以直接偷的思想

  • 把缓存位置变成调度的输入，而不是调度完成后的被动结果。TTFT = 排队 + 计算 + 搬运，三项都建模再取 min。
  • 热点复制用启发式而不是预测：让请求路径顺带完成复制，省掉一整个预测子系统。
  • 逐层 overlap 是通用模式：任何"逐层算 + 逐层有产出"的流水线（prefill、长视频生成）都能把 IO 藏进计算。
  • 过载是常态，把拒绝做成一等公民：定义"完整跑完才算 goodput"，然后用预测式早拒绝把浪费压到最小。警惕滞后反馈造成的负载震荡。
  • Goodput 的定义决定调度器的形状。先定义清楚"什么算有效产出"，再谈优化。
延伸

论文 v5 之后的演进值得跟踪：Mooncake Store 已独立开源（kvcache-ai/Mooncake），社区出现了与 vLLM/SGLang 的集成；attention offloading、异构加速器（带宽型 vs 计算型）是论文点名的大方向。DeepSeek 的 MLA 从算法侧提高算术强度，与这套系统侧解耦互为正交优化。
