ISCA 2024 · SYSTEMS FOR LLM INFERENCE

Splitwise把一次推理解体，按阶段重组集群

一句话 thesis：将计算密集的 prompt 阶段与显存密集的 token 阶段拆到不同机器，用逐层 KV-cache 传输隐藏交接开销，再用混合资源池吸收碎片，让每个阶段按自己的瓶颈调度。

01
The mismatch

同一次推理，其实住着两种负载

Splitwise 的出发点不是“GPU 不够快”，而是同机混合调度把两种资源剖面绑在一起：一边要算力，另一边要显存；一边影响首 token，另一边影响流式节奏。

PROMPT / PREFILL

计算密集，怕排队与功率 cap

§III-B–G

所有输入 token 在一次迭代中并行计算，产生第一个输出 token 和注意力 KV-cache。

  • TTFT 随 prompt 长度近似线性增长； batch 超过 2048 tokens 后吞吐下降。
  • 功耗随 batch 增大而上升；功率 cap 会显著拉高 prompt 延迟。
  • 更依赖新 GPU 的 compute / HBM 带宽，而非无限堆 batch。
TOKEN / DECODE

显存密集，靠大 batch 摊薄权重读取

§III-B–G

每步只输入上一 token，却读取截至目前的整段 KV-cache；输出严格串行，延迟体现在 TBT。

  • batch 提到 64，TBT 仅约 2×；吞吐持续上升，直到 HBM 容量耗尽。
  • token 阶段功耗对 batch 不敏感；从 700W cap 到 350W 几乎无延迟影响。
  • conversation 中 60–70% 时间只有不超过 20 个 active tokens，算力经常闲置。
与前人工作的分水岭：Orca 的 continuous batching 在每次 forward pass 前调度，但 batch 仍只含单一阶段；SARATHI 的 mixed batching 把 chunked prefill 与 decode 放在一起，缓解却没有消除相互拉长。Splitwise 则把两阶段放到不同机器，从根本上分开 batch 与硬件策略。§II-D、§VIII
调度方式一次 batch 里有什么解决了什么还留下什么
Request-level整批请求跑完才接新请求实现简单长 decode 阻塞新请求，TTFT / E2E 排队明显

▶ 跑一遍 · 输入很长，不代表 prefill 占大头论文数值 + 算术
  1. coding trace 的中位请求是 1500 输入 tokens / 13 输出 tokens，看起来应由 prompt 主导。Fig. 3
  2. 但在 BLOOM-176B 上，一次 1500-token prompt 的耗时，约等于仅 6 个输出 tokens 的生成阶段。§III-C
  3. 用论文的等价关系做量级演算：13 ÷ 6 ≈ 2.2。也就是说，不能凭“1500 ≫ 13”推断 prefill 支配 E2E；逐次 decode 的累计成本才是系统必须拆开的原因。

此处的 2.2 是帮助理解量级的工程师演算，不是论文报告的一个独立延迟比值；不同 batch 与硬件会改变比例。

02
High-level design

三类机器池，两级调度，一条 KV 数据面

CLS 决定“去哪里”，MLS 决定“这台机器下一次迭代跑什么”。所有机器预加载模型；P / T 专职池保证隔离，mixed pool 在高峰回收因比例错配而闲置的容量。

03
Request trace

跟着一个请求，从到达到释放

点击步骤，或用左右方向键切换。重点不是六个框框，而是每一步由谁做决策、什么状态必须已经存在，以及延迟藏在哪一段。

CLS / CLUSTER LEVEL

同时选定 prompt 与 token 机器

请求到达后，CLS 用 Join the Shortest Queue 分别选择 P、T 两端；队列长度按 pending tokens 计算，而不是请求条数。

  • 机器定期上报队列与显存状态，不是每个 iteration 都同步。
  • 在 prefill 前确定 token 端，是后续逐层异步传输的前置条件。
  • 队列过长时，启用 mixed pool 或从相反角色池借机器。

此步建立的不变量

请求尚未开始计算，KV 的目的地已经可知。

论文 §IV-A
▶ 跑一遍 · 1500-token prompt 的逐层交接示例组合
  1. 取 coding trace 的中位输入 1500 tokens，放进 Llama2-70B / 80 layers 的心智算例；H100 上它超过论文的 512-token 小 prompt 边界，因此走 per-layer transfer。
  2. 第 1 层算完：异步发送 KV₁；GPU 不等网络，继续算第 2 层。重复为 KV₂ … KV₈₀。
  3. 所有层的 put 都已发出后，prompt 端通过同一 InfiniBand 连接发出 semaphore；token 端等待对应请求的 semaphore，而非对整个 batch 做一把大锁。
  4. 论文实测优化后未隐藏部分约 5ms（H100）；E2E 影响 0.8%，但第二 token 仍有 16.5% 延迟增幅。

1500 tokens 与 80 层来自论文不同位置，这里仅组合成机制算例，并非论文单列的一条实测请求。机制与开销见 §IV-C、§V-A、§VI-A。

05
Engineering decision records

真正值得学的，是六次取舍

每个决策都同时看备选路径、收益与代价。这里把“论文明确做的对照”和“工程师视角的归纳”分开，不把后见之明伪装成作者原话。

按阶段拆机，而不是继续优化同机混合

PHASE SPLIT

决策问题

如何消除 prompt 与 token 同批执行造成的 TBT 干扰，并让两类资源分别扩张？

备选路径 / 未采用

Orca 的 continuous batching 仍同机切换阶段；SARATHI 的 chunked prefill + decode piggyback 仍同批，论文认为它只能减轻、不能消除干扰。

为什么这样选

拆机后，prompt 端可限 batch 保 TTFT，token 端可尽量大 batch 提吞吐；还能分别选择 GPU 代际与 power cap。

代价 / 权衡

把本地显存读取变成跨机状态迁移；同时引入 P/T 配比错误时的容量碎片，所以传输优化和 mixed pool 不是附属品，而是拆分成立的条件。

两级调度 + 第三资源池，避免静态分区 stranded capacity

ELASTIC POOLS

决策问题

集群路由需要全局视野，batch 又需要本地实时状态；固定 P/T 配比遇到负载漂移怎么办？

备选路径 / 未采用

纯静态 Splitwise-AA / HH 分区会在负载偏离预期时空置一侧；Orca 式迭代调度解决单机 batch，却不负责跨池容量。论文也未让 CLS 每次 iteration 都同步。

为什么这样选

CLS 用 JSQ 管池与路由，MLS 用本地队列 / HBM 管每次 forward；高峰把机器借入 mixed pool，反向队列清空后再归还原池。

代价 / 权衡

CLS 可能成为大集群瓶颈；定期状态上报意味着路由基于近似状态。高负载下越来越多机器 mixed 后，系统会退回接近普通 baseline 的行为。

两端都用 FCFS，但 batch 策略故意不对称

BATCHING

决策问题

同一种“越大越好”的 batch 规则，为什么不能同时服务 prefill 与 decode？

备选路径 / 未采用

默认 request-level batching 让新请求等整批结束；SARATHI mixed batch 与无限 prompt batch 都会让长 prefill 影响单次迭代；Orca 的 prompt 抢占又可能伤 TBT。

为什么这样选

prompt 端总输入限制为 2048 tokens，因为之后吞吐下降；token 端则持续合批，直到接近 HBM 耗尽再排队，因为 TBT 对 batch 相对不敏感。

代价 / 权衡

2048 是特定模型 / 硬件的 profiling 结果，论文明确说可配置，不是跨模型常数；token 端“尽量大”也把准入控制与显存预估变成正确性关键。

大 prompt 逐层传，小 prompt 反而串行传

KV HANDOFF

决策问题

如何隐藏 KV-cache 跨机传输，同时不让细粒度通信反过来拖慢 prefill？

备选路径 / 未采用

naive Splitwise 在 prefill 完成后一次性串行传 KV；Ray / Dryad 等通用 dataflow 能表达两阶段图，却不是为这种逐层 GPU 状态交接专门设计。

为什么这样选

每层 KV 生成后立即用 MSCCL++ zero-copy one-sided put 异步发送，与下一层计算重叠；小 KV 没必要承担干扰，因此选择串行。

代价 / 权衡

需要每层同步、每请求 semaphore 与 vLLM block 连续性感知；H100 上 <512 tokens 走串行这一边界来自本文环境，迁移系统时必须重新 profile。

把新算力给 prompt，把旧 GPU / 降功耗给 token

HETEROGENEITY

决策问题

H100 算力相对 A100 增长 3.43×，HBM 容量却没涨；怎样不把昂贵算力浪费在 decode 上？

备选路径 / 未采用

Splitwise-HH 全用 H100 简单同构；BigDL-LLM、Numenta 探索 CPU / 低算力设备，FlexGen 探索单 GPU offloading；它们降低资源门槛，但未采用本文的跨机 P/T 分池。

为什么这样选

Splitwise-HA 用 H100 跑 prompt、A100 跑 token；HHcap 给 token H100 降功耗。依据是 TBT 的代际敏感度低于 TTFT，且 token 对 power cap 较钝感。

代价 / 权衡

数据中心 GPU 型号更碎；论文也承认 H100 ↔ A100 的 InfiniBand 配置未必现成。HA 在负载从 coding 切到 conversation 时有 7% 吞吐回落。

用性能模型 + 事件模拟搜集群，而不是拍脑袋定配比

PROVISIONING

决策问题

给定 trace、硬件、吞吐目标和 SLO，如何找到 P/T 台数，并把成本或功耗作为真正的优化目标？

备选路径 / 未采用

只按平均利用率或单点吞吐 provisioning，无法覆盖尾部；InferLine / MArk 是相关 provisioning 思路，但面向通用推理链路，未处理本文的 LLM 两阶段 batch 细节。

为什么这样选

piece-wise linear 性能模型预测 TTFT / TBT，事件模拟器搜索 P/T 台数；P50 / P90 / P99 × TTFT / TBT / E2E 共 9 个 SLO 必须全满足。

代价 / 权衡

集群结论依赖 trace 与模型准确度；论文只优化 provisioned power，不是动态功耗。性能模型 MAPE <3% 并不等价于所有大规模生产尾部都被真实验证。

▶ 跑一遍 · 2048-token prompt batch 预算示例值 + 论文阈值
  1. FCFS 队列依次是 1024、768、512、384 四个 prompt（示例值）。
  2. 装入前两个：1024 + 768 = 1792，仍低于 2048。
  3. 再装第三个会变成 2304 > 2048，所以本批停在 1792；512 与 384 留给后续 batch。
  4. 同一时刻，token MLS 不套用 2048 规则：它继续吸纳 decode，直到接近 HBM 上限。两套策略来自两套瓶颈，而不是调度器实现不一致。

2048-token 上限来自 §IV-B / Fig. 6a；四个请求长度是示例值。论文也说明该上限应按模型与硬件重新配置。

Read past the abstract

限制、追问，以及可以直接偷走的思想

Splitwise 的贡献很扎实，但它不是“拆了就赢”。真正的适用条件是：两阶段资源剖面不同、KV 能高效交接、负载需要 SLO 隔离，而且混合池能回收比例错配的容量。

    P 或 T 机器失败时从头重启请求；KV checkpoint 与恢复只是可能方向，安全高效的设计超出本文范围。§IV-E

  • CLS 扩展性

    大集群中可能成为瓶颈；分区或复制调度被留作正交优化。§IV-E

  • 互连与异构可得性

    HA 的 H100 ↔ A100 InfiniBand 不一定现成；低带宽 RoCE / Ethernet、KV 压缩和其他硬件仍需验证。§VII

  • 功耗口径有限

    只考虑 provisioned power，不研究动态功耗；对话上下文缓存也可能改变 prompt 的显存行为。§IV-D、§VII

  • 原型验证范围

    附录明确写道，因硬件有限，artifact functionality 只对 traces 与 SplitwiseSim 做过测试。Appendix A

工程师视角

落地前还应该追问

  • 集群尾部是否被模拟器充分覆盖？

    MAPE <3% 是性能模型误差，不是生产集群所有尾延迟的保证。网络拥塞、状态陈旧、故障与多租户干扰仍需要独立压测。

  • pending tokens 是否足够代表剩余工作时间？

    相同 token 数在不同输入长度、KV 体量与硬件上服务时间不同；JSQ 可能还需要纳入显存和预计 iteration time。

  • 短输出对第二 token 开销敏感吗？

    0.8% E2E 很漂亮，但 16.5% 的第二 token 增幅并非零。极短交互、严格 streaming SLO 应按自己的分布重测。

  • 前缀缓存与会话复用会改变多少收益？

    characterization 为安全考虑不做跨请求 KV 复用；若生产开启复用，prompt 工作量、KV 位置和跨机传输方向都要重算。

  • 模型覆盖面仍窄

    实测聚焦 BLOOM-176B / Llama2-70B、8-GPU TP、A100 / H100。作者对 MoE 等的适用性论证合理，但不是同等的实测证据。

Ideas worth stealing

即使不实现 Splitwise，也可以直接拿走六件事

  • 分阶段 profiling。不要只看整请求 GPU utilization；分别记录 prefill / decode 的 FLOPs、HBM、功耗、TTFT 与 TBT。
  • 按瓶颈设相反 batch 策略。计算密集阶段限制迭代体量，显存带宽阶段用准入控制换取更大有效 batch。
  • 状态生产一层，就发送一层。任何跨阶段大状态交接，都可先问能否与后续计算 overlap，而非结束后一次性搬运。
  • 保留混合溢出池。专职池解决隔离，弹性 mixed 容量解决比例错配；两者不是二选一。
  • 把 SLO 写成向量。同时看 P50 / P90 / P99 的 TTFT、TBT、E2E，避免 averages 掩盖 streaming 尾部。
  • 先声明约束，再报倍率。iso-cost、iso-power、iso-throughput 是三种不同产品决策；机架空间与旧 GPU 可得性也应进入目标函数。
▶ 跑一遍 · 同一个 256-token prompt，何时不该逐层传256 为示例值 · 512 为论文边界
  1. 在本文 H100 设置中，<512 tokens 被当作小 prompt；因此 256-token 输入走 serialized KV transfer。
  2. 原因不是“串行永远更快”，而是小 KV 的总传输量很小，逐层 overlap 能隐藏的绝对延迟有限，却可能带来同步与计算干扰。
  3. 同一个 256-token 请求若处于极高负载、放松延迟 SLO 的批量集群，还可能进入 mixed pool；此时系统逐渐接近普通 mixed-batching baseline。
  4. 工程判断：不要把“512”复制成全局配置。正确做法是分别测 serial 与 per-layer 的 TTFT / 第二 token / E2E 曲线，再按模型、硬件、网络和 batch 选阈值。

512-token 边界与 mixed 行为来自 §VI-A、§VI-E；最后一条是基于论文机制的工程建议，不是论文新增的实验结果。
