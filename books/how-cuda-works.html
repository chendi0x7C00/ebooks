How CUDA works

You know processes, threads, and memory. Let’s follow a computation from an ordinary CPU program into a GPU—and back.

For experienced web developers · Read in order or use the contents · No GPU needed to read or explore

Baseline: one discrete NVIDIA GPU. Classic SIMT CUDA C++ is the focus; newer systems and higher-level programming models add options.

A loop with independent work

You already know how to make a service handle more requests: find independent work, distribute it, and avoid making every worker wait on one shared resource. GPU programming starts with the same questions, at a much smaller scale.

for (int i = 0; i < n; ++i) {
    c[i] = a[i] + b[i];
}

Each output depends only on two inputs at the same index. Computing element 900 does not require element 899 to finish. If we have many arithmetic units and can supply their inputs, we can calculate many elements together. The obstacle shifts from “how fast can one instruction finish?” to “how much useful work can the machine finish per second?”

Latency is the time for one operation. Throughput is the amount completed per unit of time. A GPU spends much of its hardware budget on parallel execution and on feeding that execution with data. A CPU invests heavily in making a small number of instruction streams progress quickly, including through unpredictable branches. Both have caches, parallel execution, and sophisticated schedulers; the balance differs. [7]

This is why a large image transform is a plausible GPU workload, while a single request that reads a row, branches on permissions, and calls another service is a less obvious one. A GPU is useful when the computation has enough parallel work. Having many concurrent HTTP requests does not automatically provide the right kind.

What CUDA adds

CUDA is NVIDIA’s computing platform and programming model. It lets a CPU program arrange memory and launch GPU functions, called kernels. Here “kernel” means a function executed by GPU threads; it does not mean your operating system’s privileged kernel. We will use CUDA C++ to make the underlying operations visible. [1] [2]

The whole machine: where the bytes go

Begin with a file containing two arrays. Storage keeps the persistent copy. The application reads the bytes into host memory: the RAM attached to the CPU. In our baseline system, the discrete GPU has separate device DRAM, often called VRAM. We allocate space there and copy the inputs across PCIe, the interconnect between host and device.

Once the inputs are on the GPU, its compute units load them from device memory, perform arithmetic, and store results there. A result needed by the CPU must become available to the CPU before it is read. Our example does that with an explicit copy back. Intermediate results can stay on the device for another kernel. [1] [7]

The distinction between control and data movement matters. CPU software arranges a transfer, but DMA engines can move the bulk bytes without CPU cores executing a load and store for each byte. DMA means direct memory access. The transfer still consumes interconnect and memory bandwidth. It may pass through host-side PCIe hardware without passing through CPU arithmetic units. [12]

For a familiar analogy, submitting a GPU job resembles submitting work to a local accelerator service: choose inputs, submit work, track completion, consume outputs. The analogy stops at the boundary. This is a device managed by your OS and driver, using memory mappings and hardware queues; the kernel is not an HTTP handler.

Three questions to ask at every step

Where do the bytes physically live? Which processor can access them? What proves the previous writer has finished? A pointer value answers none of these questions by itself.

From your source file to GPU instructions

A CUDA application still starts as an ordinary CPU process. The OS schedules its CPU threads. Those threads run application logic and call CUDA APIs. The CUDA runtime provides convenient memory and launch operations on top of the lower-level driver API; the NVIDIA driver manages the device-facing machinery. A GPU kernel runs within this managed environment, not as a new host process. [2]

The CUDA Toolkit contains development tools, headers, and libraries; the NVIDIA driver is a separate installation. Shipping a compiled GPU library does not require compiling it on every request. Device code can already be packaged in the binary, with PTX available for supported just-in-time compilation. Initial context setup, loading, or JIT work can make the first call different from a warmed-up call. [2] [3]

Compute capability describes the GPU’s hardware feature level. It is different from the CUDA Toolkit version. Deployment must line up the GPU, compiled targets, toolkit/runtime requirements, and driver compatibility. A container does not replace the host’s GPU driver. Consult the compatibility guide and hardware list when choosing targets. [17] [18]

A complete computation, from the CPU’s point of view

We will add 1,000 pairs of numbers. The small size makes the indexing easy to inspect; it is a correctness example, not a useful GPU benchmark. a, b, and c belong to host memory. da, db, and dc name device allocations. The prefix is just our naming convention.

__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

// Host code, after allocation and upload:
add<<<4, 256>>>(da, db, dc, 1000);

__global__ marks a GPU kernel. The launch requests four blocks of 256 threads, giving 1,024 logical invocations of the same function. Each thread computes its own index; the final 24 threads skip the memory access. Passing da passes a pointer value to an allocation already accessible by the GPU. It does not upload the pointed-to array. [4]

A launch returning does not mean its outputs exist yet. cudaGetLastError() checks the launch-side error status; execution failures may be reported by a later synchronization. The explicit cudaDeviceSynchronize() below makes that distinction visible. The subsequent synchronous device-to-host copy also waits for its copy to complete. [4] [9]

Full example · allocation, error checks, validation, cleanup

Save as vector_add.cu. This is a short-lived teaching program; on a CUDA error its checker terminates the process. A reusable service should manage ownership and failure recovery explicitly.

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>
#include <vector>

static void check(cudaError_t result, const char* expression, int line) {
    if (result != cudaSuccess) {
        std::fprintf(stderr, "Line %d: %s: %s\n", line, expression,
                     cudaGetErrorString(result));
        std::exit(EXIT_FAILURE);
    }
}
#define CUDA_CHECK(expr) check((expr), #expr, __LINE__)

__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

int main() {
    constexpr int n = 1000;
    const size_t bytes = n * sizeof(float);
    std::vector<float> a(n), b(n), c(n);
    for (int i = 0; i < n; ++i) {
        a[i] = static_cast<float>(i);
        b[i] = 2.0f;
    }

    float *da = nullptr, *db = nullptr, *dc = nullptr;
    CUDA_CHECK(cudaMalloc(&da, bytes));
    CUDA_CHECK(cudaMalloc(&db, bytes));
    CUDA_CHECK(cudaMalloc(&dc, bytes));
    CUDA_CHECK(cudaMemcpy(da, a.data(), bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(db, b.data(), bytes, cudaMemcpyHostToDevice));

    constexpr int threads = 256;
    const int blocks = (n + threads - 1) / threads;
    add<<<blocks, threads>>>(da, db, dc, n);
    CUDA_CHECK(cudaGetLastError());
    // Deliberately explicit for learning and error attribution.
    CUDA_CHECK(cudaDeviceSynchronize());
    CUDA_CHECK(cudaMemcpy(c.data(), dc, bytes, cudaMemcpyDeviceToHost));

    bool valid = true;
    for (int i = 0; i < n; ++i) {
        // These small integer-valued floats have exact sums.
        if (c[i] != a[i] + b[i]) {
            std::fprintf(stderr, "Mismatch at index %d\n", i);
            valid = false;
            break;
        }
    }
    CUDA_CHECK(cudaFree(da));
    CUDA_CHECK(cudaFree(db));
    CUDA_CHECK(cudaFree(dc));
    if (!valid) return EXIT_FAILURE;
    std::printf("Verified %d results; c[999] = %.1f\n", n, c[999]);
}

On a compatible NVIDIA GPU system with the CUDA Toolkit and a supported host C++ compiler:

nvcc -O2 -lineinfo -arch=native vector_add.cu -o vector_add
./vector_add
# Expected: Verified 1000 results; c[999] = 1001.0

-arch=native targets the GPU visible on the build machine and omits a PTX fallback; choose explicit deployment targets when building elsewhere. This page works on any modern browser, but the CUDA sample needs a compatible NVIDIA environment. [3] [18]

Work units and hardware are different things

Think of a grid as the work requested by one launch and a block as a group of threads that can cooperate. A thread is one logical execution of your kernel, with its own indices and private state. These are programming concepts. The physical GPU contains SMs, which provide scheduling, registers, shared memory, and execution units.

A block executes on one SM; an SM can hold several blocks if resources allow. Blocks may run in any order, and a large grid runs in waves as resources become available. The grid is therefore allowed to be much larger than the machine. Do not assume that block 0 finishes before block 1, or that all blocks are resident together. [1]

The formula is just chunked-array arithmetic. With 256 threads per block, block 3 begins at element 768. Thread 231 within it owns element 999. The launch rounds up because 1,000 is not divisible by 256. This mapping is a choice in the kernel: a thread could instead loop over several elements, or help compute one shared output.

Two- or three-dimensional indices make images and volumes easier to address. They do not turn the silicon into a two- or three-dimensional array of your chosen shape. “256 threads per block” is a launch choice, not the number of arithmetic units in an SM. [5] [6]

How an SM actually makes progress

An SM groups threads within each block into warps of 32. A scheduler selects a ready warp and issues an instruction for its active lanes. Each lane uses its own register values and addresses. Registers are tiny on-chip storage locations for current operands and intermediate values. A spill happens when the compiler stores some of that private state in device-backed local memory because it cannot keep it all in registers. This is SIMT: single instruction, multiple threads. You write the behavior of a thread; the machine exploits the common instructions across threads. [6] [21]

For vector addition, the interesting instructions are conceptually “load a,” “load b,” “add,” and “store c.” The addresses differ by lane, but the operation is shared. This is related to CPU SIMD vector instructions, except CUDA exposes individual thread state and control flow instead of asking you to express every operation as one explicit vector value.

If lanes choose different paths, some instruction opportunities have fewer participating lanes. That is warp divergence. The cost depends on the generated code and the work on each path; an if does not automatically halve performance. Modern independent thread scheduling allows finer-grained progress, but it does not make divergent lanes free. It also means code must not use assumed warp lockstep as a substitute for synchronization. [6]

Waiting for memory without idling the whole SM

A warp waiting for a load cannot execute a dependent addition yet. If another resident warp is ready, the scheduler can issue its work. The waiting warp’s execution state is already held by the SM; this ordinary selection does not involve an OS context switch. Having enough independent ready work can hide latency. It cannot manufacture memory bandwidth or resolve a dependency chain. [6]

Occupancy is the number of resident warps relative to the hardware maximum. Registers, shared memory, and other limits constrain it. More occupancy can provide more choices to the scheduler, but maximum occupancy is not the goal by itself: forcing fewer registers may introduce costly spills. Measure the useful work completed. [7]

Memory: scope, location, and access pattern

“Memory” is not one uniform place. A variable can be private to a thread yet stored far from the arithmetic units. Conversely, a small on-chip region can be shared by a group of threads. Separate who can use a value from where it is stored.

Storage / address spaceVisibility and lifetimeWhat to remember
RegistersThread-private; execution stateFast but finite. More per thread can reduce residency.
Local memoryThread-private; used for spills or some local objectsBacked by device memory, despite the word “local.”
Shared memoryShared within a block; block lifetimeOn-chip, explicitly managed; cooperation needs ordering.
Global memoryDevice-accessible allocation; survives launches until freedWhere our arrays live; other kernels can reuse them.
Constant memoryDevice-visible, read-only to kernelsA specialized cached path, useful when lanes read the same value.

Coalescing: look across lanes, not down one thread

Suppose all 32 lanes load one four-byte float. The useful payload is 128 bytes. Under a 32-byte segment model, an aligned run of 32 adjacent floats touches four segments. If each lane instead reads a float 32 bytes away from its neighbor, the same payload touches 32 segments. The addresses requested by the warp for one instruction determine how well requests combine. [5]

In web code, an array of objects may be natural: each object keeps its fields together. If a GPU kernel reads only one field across thousands of records, separate contiguous arrays for those fields may give neighboring lanes more useful neighboring bytes. The choice follows the access pattern; there is no universal rule that one layout wins for every kernel.

Shared memory: pay for a load, then reuse it

Vector addition uses each input once, so adding a shared-memory staging step has little to reuse. Matrix multiplication is different. For C[row,col], you multiply a row of A by a column of B and sum. Neighboring outputs reuse many of the same A and B values. A block can load a small tile, synchronize, and reuse it for many products before loading the next tile.

Let the tile width T = 2. Load two 2×2 tiles—eight values total—then use them to update four output sums. An accumulator is the running sum for one output. Each further tile stage contributes another part of the dot product.

A producer/consumer pattern needs a barrier after loading and, when reusing the same scratchpad, often another before overwriting it. Keep the block barrier outside per-thread bounds conditions; out-of-range threads can fill neutral values and still participate. __syncthreads() coordinates one block, not the grid. Two threads writing the same location still need a correct ownership or atomic-update design. [20]

Ordering is part of the program

Imagine uploading a batch in one queue and launching a reader in another. If nothing connects the queues, the reader could run before the upload finishes. The fact that the host submitted one call first is not a general cross-stream dependency.

A stream is an ordered sequence of device operations. In the simple case, one stream gives the order upload → kernel → download. Different streams permit overlap when dependencies and resources allow it. An event marks a point in a stream; another stream can wait on that event before using the result. Concurrency is permitted, not guaranteed. [8]

The familiar “submit, then await” idea helps, but distinguish a CPU wait from a device dependency. cudaStreamWaitEvent orders subsequent device work; cudaStreamSynchronize makes the calling host thread wait. cudaDeviceSynchronize waits for preceding work across the current device’s streams in the application’s context. A wait is also where asynchronous errors can surface. [8]

The default stream has special rules: legacy default-stream behavior can introduce synchronization with other blocking streams. Explicit nonblocking streams avoid that particular interaction; per-thread default streams have different semantics. Choose deliberately before expecting overlap. [8]

“Async” does not settle every question

cudaMemcpyAsync with pageable host memory may need staging or host synchronization. Even cudaMemcpy has direction-dependent return behavior. Read the precise API contract, keep buffers alive until their work completes, and do not equate “the CPU call returned” with “all bytes reached their destination.” [9]

Inside a kernel, give each output one owner when possible. For a reduction such as a sum, combine partial values with a deliberate reduction algorithm or suitable atomic operations. A plain sum += value from many threads is a race. For a whole-grid phase boundary, separate kernels in one stream are a straightforward design; ordinary blocks must not spin waiting for an unscheduled block. Specialized cooperative launches and clusters have additional contracts. [1] [20]

One address does not mean one physical memory

We used separate host and device allocations to make placement obvious. CUDA also supports more convenient forms of access. Keep the address-space concept separate from the physical data path.

A pointer holds a virtual address. Address mappings connect it to physical storage, usually in chunks called pages. A page fault means an access needs mapping or placement work before it can proceed; it need not mean a programming error. Pinning keeps host pages in RAM with stable backing for transfers. The pointer can remain unchanged while the physical location or access cost changes.

MechanismWhat changesWhat still costs something
Explicit device allocationcudaMalloc creates device storage; copies are explicit.Upload, readback, and enough device capacity.
Pinned host memoryHost pages are kept resident; use cudaMallocHost or register a region.It is still host RAM. Pinning consumes a limited system resource.
Mapped host memoryGPU code accesses a mapped host buffer.Remote accesses cross the interconnect. “Zero copy” does not mean zero traffic.
Unified virtual addressing (UVA)Allocations occupy a coordinated virtual address space.Addresses do not merge DRAM or grant universal dereference permission.
Unified MemoryCPU and GPU can access managed data; placement/access is system-managed.Migration, faults, remote accesses, and synchronization may remain.

cudaMallocManaged is one way to request Unified Memory. On supported Linux systems, heterogeneous memory management (HMM) or address translation services can extend GPU access to ordinary system allocations. Exact behavior depends on the OS, GPU, and driver. Consult capabilities rather than assuming an ordinary host pointer is valid in device code. [10] [11]

The virtual-memory analogy is useful: a stable virtual address does not imply stable physical placement. A managed page may move toward the processor using it, or the hardware may access it remotely. Alternating CPU and GPU writes can therefore cause expensive movement. Shared accessibility also does not establish happens-before ordering: wait for the GPU before consuming its output on the CPU. [11]

How newer systems change the original machine diagram

NVLink and coherent CPU–GPU systems. Interconnect topology varies. Grace systems with NVLink-C2C can support hardware-coherent CPU–GPU access. This changes how remote data is accessed; it does not erase physical locality. Do not generalize CPU–GPU C2C behavior to every GPU–GPU NVLink setup, or assume that cudaMalloc pointers become directly host-readable. [11]

GPUDirect Storage. On a supported and configured storage stack, storage data can move to GPU memory without a host-RAM bounce buffer. CPU software still arranges the I/O. Compatibility modes can use staging, so calling the API alone does not prove the transfer used the direct path. [12]

Our first diagram is deliberately the ordinary explicit-copy case. These alternatives change access and transport; the questions about location, bandwidth, ownership, and completion still apply.

A faster kernel can still make a slower application

Suppose a CPU stage takes 8 ms and a GPU kernel takes 1 ms. Calling that “8× faster” describes only those two stages. If the GPU path also spends 10 ms moving data, it loses on the complete request. The relevant unit of optimization is the workload boundary you actually care about.

TGPU path = preparation + upload + submission + kernel work + download + consumption

This additive budget assumes phases do not overlap. A pipeline needs a critical-path analysis instead. It should also include cold initialization, allocation, or JIT costs when those occur inside the measured request. A warmed-up steady-state measurement answers a different question.

Two bandwidth limits, at different boundaries

First, the host–device link must move inputs and required outputs. Then the device’s memory system must feed the kernel. For our streaming float add, the ideal data demand is two four-byte reads plus one four-byte write per addition: 12 bytes for one floating-point operation. That gives an arithmetic intensity of about 1/12 FLOP per byte, when those bytes reach device DRAM and there is no useful cache reuse.

A basic roofline bound says throughput cannot exceed either the arithmetic capacity or the memory supply rate multiplied by work per byte. It is an upper bound, not a prediction: latency, dependencies, and other bottlenecks can keep execution far below both ceilings. Use the bandwidth of the memory level being analyzed and the matching arithmetic precision. [14]

FLOP/s ≤ min(compute ceiling, memory bytes/s × FLOP/byte)

Shared-memory tiling can raise useful work per device-memory byte. Keeping intermediate arrays on the GPU can reduce host-link traffic. These fix different bottlenecks. Buying more advertised arithmetic throughput would fix neither by itself.

The model’s break-even condition is simple. Savings per stage must pay for the initial and final transfer. If a stage saves 2.69 ms after submission cost and the transfer costs 8 ms, three stages can just repay that cost. If every stage requires a CPU round trip, the transfer bill grows too, and this calculation no longer applies.

Use Amdahl’s law for the larger service. If only 20% of request time can be accelerated, making that part infinitely fast gives at most 1 / 0.8 = 1.25× speedup before adding overhead. The fraction you accelerate matters as much as its isolated speed.

Putting CUDA behind a web application

For a hypothetical image-analysis endpoint, keep HTTP parsing, authentication, batching policy, and response construction on the CPU. Send a dense batch of numeric data to the GPU. Keep reusable model weights and intermediate results there when capacity allows. Return the output the application needs, rather than every internal array.

A long-lived worker can reuse allocations and initialized state. Bound the work queue and account for device memory per in-flight batch. Batching may raise throughput while adding queueing delay to individual requests; measure both completion rate and tail latency. More CPU workers do not automatically create more GPU capacity.

You often do not need to write kernels yourself. GPU libraries such as cuBLAS for linear algebra and cuFFT for Fourier transforms, or higher-level frameworks, provide established implementations. CUDA knowledge still helps you spot an accidental download, undersized batch, needless synchronization, or data layout that causes excess traffic. [19]

Measure in layers

  1. Establish correctness. Compare all outputs against a reference, including awkward sizes such as 1,000. Run Compute Sanitizer for invalid accesses; its race and synchronization tools address additional classes of error. [15]
  2. Measure the whole request. Include required completion before stopping the host timer. Record batching, warm-up, allocation, transfers, and numerical precision.
  3. Inspect the timeline. Nsight Systems helps locate CPU gaps, CUDA API calls, copies, kernels, and synchronization. Determine whether the GPU is waiting for the host or the host is waiting for the GPU. [13]
  4. Inspect the important kernel. Nsight Compute reports memory and execution behavior. Use its roofline and other metrics to distinguish bandwidth, instruction, and residency limits. [14]
# On the NVIDIA machine, with these tools installed:
compute-sanitizer --tool memcheck ./vector_add
nsys profile --trace=cuda,nvtx -o vector-add ./vector_add
ncu ./vector_add

CUDA events placed before and after work in the same stream measure an interval on the device timeline. Wait for the final event before reading elapsed time. That interval differs from a CPU stopwatch around the launch, and it can include interference from other work. Neither replaces end-to-end latency. [8]

For realistic floating-point workloads, correctness usually needs an appropriate tolerance. Changing reduction order or using fused multiply-add can change rounding even when both implementations are valid. Our tiny integer-valued float example uses exact equality only because its sums are exactly representable. [16]

Check your mental model

Try answering these before opening the explanations. They test the boundaries that are easiest to carry over incorrectly from CPU programming.

I launched a million threads. Did I create a million OS threads?

No. You described a million logical GPU executions, grouped into blocks and warps. The GPU schedules that work onto finite SM resources. The host OS did not create a pthread for each CUDA thread.

The launch returned. Can I serialize the output now?

Only after the required GPU work and readback have completed. A launch return establishes submission, not result availability. Use the appropriate stream/event synchronization or a copy operation whose contract provides the completion you need.

Why does a thread-private array sometimes generate memory traffic?

Private scope does not guarantee register storage. Local memory is private to a thread but backed by device memory; some local objects and register spills use it.

Why can matrix multiplication benefit more than vector addition?

Both offer independent work, but matrix multiplication can reuse input values for many arithmetic operations. Vector addition does very little work per input/output byte. A well-designed implementation can turn matrix reuse into higher arithmetic intensity.

Does Unified Memory remove the need to think about copies?

It can remove explicit copy calls. Physical movement or remote access can still happen, and correctness still requires proper synchronization. Locality remains a performance question.

Would this same CUDA kernel run on an ordinary browser GPU?

This tutorial’s controls simulate ideas in JavaScript; they do not run CUDA. CUDA targets compatible NVIDIA hardware and its software stack. Browser GPU APIs and other vendors’ compute platforms are separate environments.

You can now trace the whole path: a CPU process arranges accessible inputs, submits a grid of work, the GPU schedules blocks and warp instructions, memory supplies the operands, and an explicit dependency tells the consumer when the outputs are safe to use. The useful optimization question is always concrete: what is preventing the next useful piece of work from completing?
